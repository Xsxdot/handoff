## L4 判断（按出现顺序）

1. **书写权是通知的第一道硬门**：`agent:handoff` Send 走 `sendToSession` → `VerifyWriter`，不是成员即 `ErrNotWriter`。拆解与契约未写项目房间里系统身份怎样成为书写者 → §0 Q1。读数显示 `CreateSession` 把 owner 记为首个显式成员——owner=`agent:handoff` 即零 collab 改动。
2. **恰一条的承重点不在认领本身，在「认领让过时消费循环怎么办」**：`ClaimWake=false` 不区分他人在飞与已终局；若让过即标 seen，而持有者崩溃，在飞认领永久挡水位，本机游标卡死（500 条窗口满后整轮停摆）。卡唤醒路径「拿不到不标 seen、下轮再试」是先例。通知若挂在 seen 判定之后、复用 `automationSeen`，就得改多处 seen 写点 → §0 Q6 倾向通知器自持 handled 集、旁路调用。
3. **拆解 §5.3「写通知后、标水位前重启 → 认领键保证不重发」只对 CompleteWake 之后成立**：Send 与 CompleteWake 是两次独立提交，二者之间崩溃 → 租约 5 分钟后他人接管重发。→ §0 Q7（幂等锚）、知悉 N2。
4. **同进程双 `Server` 同 holder**：`hostname#pid`，同进程两个实例互为「同持有者可续期」，并发跑会双发——这是测试夹具不能编码的世界。机内多机证据只能用预占 `other-holder` + 租约到期接管（仓内先例），真并发归真机。→ 知悉 N1、真机 O1-1。
5. **`project` 键装配点**：`summarizeSession` 是 CLI 与 HTTP 列表/详情共用的唯一装配点；`proto.Session` 无 project，加字段越过 T0 冻结面 → 装配须经 LedgerClient 新读方法。gateway 装饰会让 CLI `--json` 与 HTTP 两份投影分叉。→ §0 Q9 倾向 collab。
6. **`by_system:null` 行**：`Recipients` 对已解码消息看不到 null，若照常调用会把结构行算成普通消息、可能给出地址（不出键）——与 C-202 冲突。→ §0 Q10。
