# B409.6 计划：S4 账本端到端诊断闭环

**阶段**：L3 重档子卡 plan；本稿只交接实现，不含实现或验收结论。

**批准基准**：用户批准的 B409 r2 `docs/superpowers/specs/2026-09-24-ledger-read-performance.md`；`docs/superpowers/specs/b409-breakdown.md` §U6；S1 摘要冻结 `docs/superpowers/specs/b409-contract.md`；Wave 0 历史切片计划/验收 `docs/superpowers/plans/2026-09-24-b409-wave0.md` 与 `docs/superpowers/ledgers/2026-09-25-b409-wave0-acceptance.md`；B409.1–B409.5 当前计划及其各自引用的既有契约。基线日志样例为 Wave 0 `RoomMessagesBeforeContext` 路径和 `TestSetupLedgerFailureDoesNotLogDSNCredentials`。

**工作单元**：B409.6 / U6 / S4。交付 B409 真实账本读取的端到端可诊断闭环：请求/CLI 总耗时、连接池等待、SQL 与读取行/字节、collab 投影、逐 target 远端耗时与状态、取消阶段与原因都可查询并相互对账；合法空、成功、部分成功、失败和取消可以明确区分。它不实现新的通用 metrics 子系统，不改业务 JSON/CLI wire，也不裁决 2026-09-23 20:00–22:00 故障根因。

## 交付目标与当前生产路径

B409 r2 已测到 PostgreSQL 单页执行远快于用户端体验，但现有请求缺少按一次操作串起连接获取、SQL 读数、Go 解码/聚合、远端 target、JSON/CLI 输出的共同诊断记录。S4 使同一次读取能回答“慢在哪一段、读了多少、失败/取消发生在哪里”，同时证明确认没有远端执行机或载体额度时，本地账本内容仍然可读。测得当前性能并不能补造历史故障时段缺失的日志。

执行者开始时须核 `B409.1–B409.5` 的已审查实现 SHA，并以该版本重走以下生产链；计划行号不能代替源码：

- **卡片**：`GET /api/cards` → `Server.withLedger` → `Server.handleCardsList` → `Store.ListCards`、U1 `OpenTicketCounts` 与已有本地读面 → 组装 CardView → JSON。U2 已计划将 `unlinked` 改为读缓存快照并后台刷新；当前 checkout 源码仍是 `handleCardsList → unlinkedSummary` 同步 fan-out。U6 必须对实际集成后的 U2 行为计时：HTTP 请求仅计入本地读与缓存投影，后台 `unlinked` 刷新单独记录，不得让远端 RPC 回到 cards 请求关键路径。
- **会话列表与详情**：`GET /api/sessions` / `GET /api/sessions/{id}` → `withRooms`、服务端控制台身份 → `handleSessionsList` / `handleSessionDetail` → `collab.ListSessionsContext` / `SessionDetailContext` → U4 有界 ledger 读取 → summary / nodes / timeline 投影 → JSON。源代码当前 handler 有成功/失败日志但没有统一请求总时长、HTTP 状态/响应字节和跨层关联 id；U4 负责恢复字段/未读/LastActivity/cancel 语义，U6 仅补读诊断。
- **房间列表与历史**：`GET /api/rooms` → 分页和身份校验 → `ListRoomsPage` → 本地 attach 缓存投影并启动后台刷新 → JSON；target attach 不应阻塞主列表。`GET /api/rooms/{id}/messages` → `handleRoomMessages` → `collab.HistoryContext` → `LedgerClient.RoomMessagesBeforeContext` → `Store.RoomMessagesBeforeContext`。Wave 0 已先例：ledger 显式 `DB.Conn(ctx)` 量 `pool_wait_ns`，再记录 `sql_call_ns`、`row_read_ns`、`db_read_ns`、`rows_returned`、`payload_bytes`、`elapsed_ns`；collab 记录 `ledger_call_ns`/`assembly_ns`；agentd 在 JSON 写出后记录整体耗时。U6 保留这些阶段边界并补齐关联 id、状态、响应字节与一致错误/取消分类，不另造第二套 history logger。
- **远端摘要与逐房间 attach**：U2 的 `/api/cards` 摘要刷新使用 Store 读、target pool、逐台任务查询和 status cache；U4 的 room attach 通过缓存读、后台 `lookupRoomAttach` / `targetclient.Pool` 刷新。两者有不同生命周期与缓存语义，分别产生 `refresh_id` 维度的每 target 结果；都不能把后台耗时并到触发刷新的 HTTP 请求总耗时。
- **CLI 与消息消费**：`cmd/session.go` 的 `session wait` → `openRoomService` → `ledger.Store`/collab 寻址、游标、backlog/follow，用户可取消 SIGINT/SIGTERM；U5 冻结的 stdout JSON 不得混入诊断文字。已有 `cmd/room.go` `room read` 是 Wave 0 CLI 入口，stdout 为消息正文，stderr 有结束日志；只在需要闭合 CLI 端到端计时且不影响此输出时补字段。`Pending`、`Mentions`、`Consume` 及回复清理由 U5 的 collab/service 与限域 ledger query 生产路径承担。

## 日志诊断约定

每个同步 agentd/CLI read 操作须有服务端生成且贯穿同一请求的 `operation_id`；背景刷新另有 `refresh_id`，两者可关联“请求安排刷新”而不能被误读为同一耗时。操作以受限 route/command 名记录，不记录原始 URL/query string；同一次关联记录使用一致字段名和纳秒单位。最小字段集合：

| 阶段 | 必需信号 |
|---|---|
| HTTP/CLI 外围 | `operation_id`、路由模板/command、`elapsed_ns`、结果类别、HTTP `status_code` 与 `response_bytes`（CLI 为 `stdout_bytes`）；结束时间覆盖 JSON/命令结果成功写出。 |
| pool/ledger | `pool_wait_ns`、`sql_call_ns`、`row_read_ns`、`db_read_ns`、`rows_read`、`result_bytes`/`payload_bytes`；失败也保留已完成阶段时间与已读行数。 |
| collab/投影 | `ledger_call_ns`、`projection_ns` 或既有 `assembly_ns`、`rows_returned`、`payload_bytes`，可与外围操作 id 一起拼回一次读取。 |
| remote target | 独立 `refresh_id`、`target`、`target_call_ns`、`outcome`（success/empty/error/deadline/canceled）、可用时 `task_count`、缓存命中/年龄、target 总数与失败数、摘要 `status`/`observed_at`。每个配置 target 均有单独结果，包括拿不到 Pool client 的失败。 |
| 取消/错误 | `failed_stage`、安全 `error_class`、`cancel_reason`（至少区分 context canceled 与 deadline exceeded；server shutdown 只在来源确定时标注）。取消发生在 pool acquire、SQL/query、row iteration、collab projection、target call 或 stdout/write 中哪一步须可见。 |

一个结果使用显式类别区分 `success_nonempty`、`success_empty`、`partial`、`error`、`canceled`；同一 HTTP 200 可以是本地账本 `success` 且远端摘要 `partial/stale/unavailable`，两者分开记。对慢请求应能由同一个 id 找到完整阶段；阶段时间有父子关系时注明是否重叠，不能把重叠阶段相加冒充总时长。pool wait 用 Wave 0 的 `DB.Conn(ctx)` 单次测量原则，不能拿进程全池累计统计冒充请求级数值。

日志/测试产物不得包含 DSN URL、用户名/密码、Bearer/cookie/relay credential、消息正文/`@` token/`reply_to` body、请求/SQL bind 内容或 target task 的 title/workdir；也不得将任意 driver error 原文当 `cause` 写日志，因为底层错误字符串不可视为安全。保留错误返回用户/上层的原有行为，日志只写有限错误分类、阶段和可安全定位的行数/字节/seq 范围。DB 的 `database` 标签沿用 `ledger.Store.Open` 已有 safe label。远端诊断只写 target 名与数量/状态，不写任务内容。

## 实现顺序

1. **核依赖与最终生产路径。** 逐 SHA 核 U1–U5 的 plan 对应已实现代码、调用者和测试；对照本节列出的 API/CLI/target 路径，记录哪些日志来自 Wave 0、哪些已有、哪些缺 request id/状态/response bytes。U5 contract gate 未过、前序读取接口仍在改或 request context 未贯通时停止 U6 实现，按归属交回协调者。
2. **锁日志字段和关联方案。** 用现有 `slog` 结构化日志、Wave 0 `elapsed_ns/pool_wait_ns/sql_call_ns/row_read_ns` 术语；生成 B409 read 的内部 operation id，并通过当前 context 关联到 collab/ledger，不把 id 加到 API 或 CLI JSON。只创建最小的进程内日志关联 helper；若它演变为跨故事公共读契约或要改 DTO，回 contract，不在此扩建观测子系统。
3. **完善 ledger 查询阶段。** 在 U1–U5 读取函数内部以每次 `DB.Conn(ctx)` 量 pool acquire，再分开量 `QueryContext`、Rows iteration/scan 和完整 db read。累计实际返回 rows 与字段/payload 字节；将 connection/query/scan/cancel/error 各分支纳入同一字段形状。保留 Wave 0 房间历史现有观测字段，补缺失的关联与一致分类；不记录 SQL 文本、绑定参数、正文或 raw DSN。SQLite/PG 两方言需输出同义阶段信号。
4. **完善 collab 应用投影。** 在 U1 工单 counts、U4 session list/detail、room list/unread、U5 Pending/Mentions/Consume/reply cleanup 与 wait 所在投影点记录账本调用和后续应用处理时间。统计只读结构/行数/JSON 字节，不另复制耗时很高的整对象 JSON marshal 来“测 byte”；如现成接缝已算出 payload bytes 则直接复用。对真空、optional source 降级、读错、取消分别落可查询 outcome。
5. **补齐 HTTP 外围。** 给上述 B409 GET/read handlers 记录一次入口与写出完成；一个只用于有限 JSON 路由的 response recorder 统计实际 status/写出 bytes，必须保留 handler 既有状态码与 `Flusher` 等必要接口行为。错误路径和 client cancel 也必须有结束记录。cards 请求的 local ledger 和 U2 cached remote summary 独立结案；后台 refresh 不在同步请求内等待。
6. **给后台 remote worker 按 target 记账。** U2 unlinked summary 的每个配置 target 和 U4 room attach 的每个实际 lookup 都记独立延迟、结果/失败类别、cache freshness/观测时间；对于总 deadline、单 target timeout、server shutdown cancel 分别给出准确的已知原因。保留 U2 `latest/partial/stale/unavailable` wire、30 秒资格与 unknown target 语义，保留 U4 attach 缓存/刷新范围；不得为日志改为串行等待或扩大本页 fan-out。
7. **贯通 CLI 诊断。** 为 U5 `session wait` 总启动、backlog、单次 live hit/timeout/cancel 记录耗时与 outcome，跟 stdout 写入分开计数；诊断只去 stderr，stdout JSON 的每行和 one-shot/follow/exit code 不变。已有 `room read` 可保留 Wave 0 日志形状；只在当前代码实际缺失 total/output bytes 时补齐，不重复同一事件日志。
8. **建故障金样与日志脱敏反例。** 用可控 test logger 覆盖日志字段、关联 id、成功/空/错误/cancel、状态码/字节；在隔离 PG 中制造连接池占满、SQL 锁等待/失败和 cancel；用受控 target 制造逐台成功/慢/拒绝/超时/全不可达。扩展 DSN redaction 夹具，注入 sentinel DSN password、Bearer/relay token、消息正文/@ token、SQL 参数/错误串与远端 task title，断言它们没有进入所有关联日志。保留有用的 `error_class`、stage 与 `dsn_configured` 布尔而不回归为沉默。
9. **交 S4 证据并保留 U7 边界。** 以真实 agentd route、隔离 PG 和 CLI `session wait` 走一个成功非空和合法空读，再各注入 DB 不可达/锁等待取消、collab 读失败、target partial/all down；保存同 operation id 的原始结构化日志、HTTP/CLI 用户观察、客户端端到端秒数、数据库/服务 build SHA。该组验收可检查读数分段和故障可辨，不跑/不宣称 B409 r2 三阶段 100 样本全量 p95 通过；完整三增长档、所有 endpoint/Web/CLI 性能回归由 U7/协调者完成。

## 可复核验收矩阵与必须为红的反例

| 场景 | 用户/调用方结果 | 必须可复核的日志事实 |
|---|---|---|
| 有内容的卡片、session、room 与历史读取成功 | 原有内容/JSON 或 CLI stdout 不变 | 单一 operation id 下有 request/command 总耗时、池等待、DB rows/bytes、SQL/row-read、collab projection、response/stdout bytes；阶段关系能对账。 |
| 有效的合法空列表/空房间 | 正常成功与空数组/现有空态 | `success_empty`，返回行数为 0；没有伪造 SQL/连接错误。 |
| 隔离 PG 不可达或 SQL 失败 | 沿现有错误状态/CLI error 返回，绝不变成成功空结果 | 失败阶段是 pool/open 或 query/scan；记录已耗时/读数与安全 error class，外围 5xx/error 与 operation id 对齐。 |
| 请求 cancel / deadline / CLI 信号 | 符合现有 cancel/timeout 语义；未写出数据不谎报成功 | operation 标为 canceled/timeout，指出 pool/query/row read/collab/CLI 阶段与可证明原因；SQL 不在 context 取消后继续消费结果。 |
| pool 饱和 + SQL 锁等待 | 主请求按当前总 deadline/cancel 行为结束 | `pool_wait_ns` 与 `sql_call_ns` 各自反映真实受控等待；不得仅靠 `DB.Stats()` 聚合值、不得将二者揉成 `sql_ns`。 |
| 每台 target 全成功、部分失败、全部失败、无 target、陈旧缓存 | 本地 cards/rooms/session 主数据先返回；U2 remote 状态按冻结 contract；room attach 刷新仍后台 | 每个 target 有耗时/outcome；unlinked 状态、`observed_at`、成功/失败 target 数可对账；main request 总时长不含 worker 挂起时间；无配置 target 是合法最新空，不是 unavailable。 |
| 隔离敏感值哨兵 | 用户结果仍如冻结语义 | DSN/凭据/body/@ token/query 参数/task title/workdir 不能在聚合日志、错误日志和测试证据中出现；安全 stage/status/数量字段保留。 |

**必须为红**

- 空列表和数据库错误都记录 `success_empty`，或 SQL/Pool/target 失败在用户结果上被报告成零任务/空消息而没有可观测降级；DB/collab 真实错误被吞掉或覆盖为 success。
- 某 operation 缺 request id、SQL 日志无法对应其 HTTP/CLI 入口、调用阶段总和无法解释 handler elapsed；只靠同一 `room_id` 与时间猜并发请求身份。
- 使用全池 `DB.Stats().WaitDuration` 差值冒充每请求 pool wait；Pool 等待被记进 `sql_call_ns` 但被声称已分离；行迭代/扫描、collab projection 或 response write 的长尾无对应阶段。
- target 成功/失败只给聚合总耗时而无法指出哪台；target worker time 错记成 HTTP request wait；单 target 慢使 cards/session/room 主请求等它返回；U2 部分/陈旧被记成完整 latest。
- 取消发生后 DB/row iterator 继续工作、cancel 被记为泛化 500、CLI 把诊断写到 stdout 导致原 JSON 解码失败，或 server shutdown 被误报为 client abort。
- 任一日志/原始验收文件包含 sentinel DSN/密码/token/body/SQL bind/task title；或者只验证“敏感字段日志里没搜到”却也把 stage/error class/status 全删光，导致无法诊断。
- 只跑 SQLite 或 SQL `EXPLAIN`、只看服务端日志，就宣称真实 API/CLI S4 闭环或网络端到端耗时已证明；仅凭 S4 通过宣称 B409 最终 3 档矩阵或历史故障原因已验收。
