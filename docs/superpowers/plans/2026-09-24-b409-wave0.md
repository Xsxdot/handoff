## 交付目标

用户从会话侧栏打开一间已有消息的会话，首次显示最近 200 条消息，按 seq 升序排列；翻页仍按既有排他 `beforeSeq` 工作。读取只传回目标房间所需的消息，取消请求会停止数据库读取。真空房间显示空态，查询失败/超时显示错误态，不把失败说成“没有消息”。

贯穿真实路径 `GET /api/rooms/{id}/messages`（`internal/agentd/roomsapi.go#handleRoomMessages`）与 `room read`（`cmd/room.go#roomReadCmd`）→ `collab.Service.HistoryContext`（`internal/collab/service.go#HistoryContext`）→ `LedgerClient.RoomMessagesBeforeContext` → ledger Store。保持现有 HTTP `{messages: [...]}`、CLI 输出、消息 DTO、寻址、未读和消费语义不变。浏览器页面不等待远端执行机或载体状态。

## 已核实的边界和假设

- `d_collab` 拥有房间/会话业务判断；`d_ledger` 拥有追加历史及其查询。查询仍经既有 `d_collab → d_ledger` `LedgerClient` 接口；契约冻结在 `25fa5c5f`。不要把房间 SQL 放入 collab，也不要改 `EventsFromAsc` / `Store.Follow` 的全流游标与无卡事件语义。
- 当前 `HistoryContext`（`internal/collab/service.go#HistoryContext`）先调用 `ReadAllEventsContext`（`internal/collab/room/room.go#ReadAllEventsContext`），再在内存过滤消息类型、房间 ID 和 `beforeSeq`。当前 HTTP handler 已传 `r.Context()`；`History` CLI 包装保持后台 context。`RoomIDOf`（`internal/collab/room/room.go#RoomIDOf`）规定非空 `card_id` 优先作为卡房间 ID，否则读消息载荷的 `Room` 字段，旧消息必须继续可见。
- 当前 `SessionTab`（`web/src/app/rooms/SessionTab.tsx#SessionTab`）通过 `fetchRoomMessages`（`web/src/api/rooms.ts#fetchRoomMessages`）读取历史；`SessionChat`（`web/src/app/rooms/SessionChat.tsx#SessionChat`）已分别呈现 loading、error 与真空状态。先用现有测试钉住它们，只在真实路径回归失败时改对应 UI 文件；不重做会话 UI。
- `codegraph sym` 未覆盖 `HistoryContext`、`ReadAllEventsContext`、`SessionTab`、`SessionChat`、`fetchRoomMessages`；已回落核对源码，符号覆盖债记在 B409 contract 台账。`Store.EventsFromAsc` 与 `Service.History` 的图节点有 `moved` 锚，源码版本优先于旧签名片段。
- 计划编写时本机 Docker daemon 未启动，且没有本机 `psql`/`postgres`。Wave 0 的 PG 验收前须启动本机 Docker Desktop 并创建专用可丢弃数据库 `handoff_b409_test`。任何种子/清理逻辑须先确认 `current_database()` 精确等于该名称；不得使用共享生产账本 DSN 写入测试数据。若专用 PG 未就绪，停在 PG 验收门，不声称通过。

## 工作顺序

1. **先写红测**：对 LedgerClient 与 Store 的房间消息读添加同一金样断言：多房间交错、卡房间与 `session:<n>` 房间、同房间超过 200 条、`beforeSeq` 排他、升序返回、非正 limit 错误、空/不存在房间为空切片、取消传播。证明旧全流扫描若被再次调用会违反查询范围/传回行数断言。
2. **账本限域读取**：实现冻结的 `RoomMessagesBeforeContext`，查询在账本边界完成房间、事件类型、seq 上界和 limit 限制；不得把全局 payload 拉回 collab 再筛。若添加投影列、索引或缓存，旧 `card_events` 必须能重建它，初始化/回填需幂等且有失败可见恢复。具体 SQL 与辅助结构是实现选择，不能改变冻结语义。
3. **竖切接线**：Facade 直通 Store；Service.HistoryContext 调新增方法；保留 `History` 包装和 `beforeSeq` 兼容。HTTP 请求 context 贯穿数据库调用。账本错误完整传播，消息页不得将错误包装成空列表。
4. **可观测性与意图注释**：在新增读路径记录服务入口与结束、账本调用前后、取消及错误分支；日志带 room ID、beforeSeq、limit、耗时、返回行数/字节和可归因的错误，不记录消息正文、凭证或 DSN。复用项目现有结构化日志约定，不引入新的日志抽象。新增/改动文件写清职责，导出 API 按项目惯例补文档；对房间身份兼容规则、SQL 限域与可重建辅助结构写明原因。日志必须能区分连接等待、SQL 与上层组装阶段，且成功、空结果、取消、失败各有可检索的诊断信号。
5. **局部验证**：先跑 ledger/API/collab/agentd 的房间历史测试，再跑 `cmd` 的 `room read` 测试与 `SessionTab`/`SessionChat` 测试。为所有 Go 包做编译检查；之后按 implement 三段律跑目标测试、构建及全量 Go/前端测试。
6. **隔离 PG 与数据增长**：建立 PostgreSQL 与 SQLite 同构金样。PG 性能库的合成数据不复制真实消息正文：总量对齐已测规模（约 21,270 events，其中 9,337 条代表性镜像事件的 payload 合计约 6.31 MB），目标会话至少 250 条消息；再分别增加至少 20,000 条无关事件、以及在第二组上将镜像行数与 payload 字节至少翻倍。记录实际行数/字节，任何情况下都不向共享生产账本写入合成数据。
7. **API 性能验收**：每组先单列首请求，再做 5 次预热和 100 次串行样本。对 `GET /api/rooms/{id}/messages` 按 nearest-rank 报 p50/p95/max、错误数、响应字节与目标消息条数；每组 p95 ≤2 秒且不得漏/重/串房间消息。分段记录数据库连接等待、SQL 执行、返回行数/字节、collab 组装与 HTTP 总耗时；PG `EXPLAIN` 仅作辅助证据，不能替代端到端时间。
8. **真 CLI 与 Codex 内置浏览器**：以测试 PG 配置运行当前分支构建的本机 agentd，经真实 `room read` 和会话 UI 打开带消息与真空会话。每组在 Codex 内置浏览器对会话列表/消息工作区做 100 次导航/硬刷新，从导航开始计到消息可见，按 p50/p95/max/错误数报告；页面可见 p95 ≤2 秒。暂停隔离测试 PG 验证真实错误态，再恢复并确认消息可重读。UI 走内置浏览器，不经 SuperDev。临时测试配置须单独保存；不与用户数据合并。验后恢复原本机 agentd 配置/版本并核实 `127.0.0.1:7777` 健康。
9. **阶段结论**：记录代码 SHA、PG/SQLite 版本、数据行数/字节、计时原始结果、内置浏览器截图、错误/取消行为、临时数据回收、`codegraph check`/`validate` 与图覆盖债。失败时回到具体根因修复，不放宽 2 秒目标、不把 SQLite 结果当 PG 结果。Wave 0 通过后由协调者追加本计划交棒，随后按 Charter 要求让独立 agent 起草 L3 breakdown，再决定余下故事和工作单元。
