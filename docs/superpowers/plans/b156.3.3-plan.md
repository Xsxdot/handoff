## 2. 设计定案

### D1 CLI 走网关 HTTP，不直连编制域（依赖方向论证，本 plan 最重的一个决定）

`codegraph/target.json` 冻结方向里 **没有 d_cli→d_scheduling**；best.json 里
k_schedclient_* 归 d_scheduling 名下——cmd 若 import scheduling/schedclient 即产生
未声明跨域边，graph check 硬闸当场变红，而给 target.json 加方向属契约变更（本卡
「零新增接缝」承诺破产）。三条既有约束同向：

1. contract §8：「适配器是双向门面的法定形态，实现类只在组装点认识两边具体类型」
   ——facadeAsRegistry 不能复制进 cmd；
2. breakdown §四-5 门禁族：「gateway 端点与 CLI 写命令最终都汇入 scheduling.Service
   **单一入口，不存在旁路**」——CLI 直连就是第二条入口；
3. ledgercli.go 文件头的直连理由（「账本操作不应依赖 agentd 存活」）针对的是
   card/workflow/decision 等**裸账本读写**；小队登记是编制域规则调用（校验/角色词表/
   成员存在性都在 Service 里），不是裸账本操作，前提不同。

结论：squad 族与 card coordinate 经 `newTargetClient()`（cmd/root.go:242，target 空=
本机模式）→ internal/client 新方法 → gateway 端点 → scheduling.Service。代价：本机
agentd 必须在线——登记面本来就是控制面配置，该前提成立；够不着时报
ErrUnreachable 可行动错误。

### D2 读面三方法与版本行

冻结签名 Carriers() ([]Carrier, error) / Squad(name) 不许改；而 Web 编辑回路需要
registry 版本做 CAS expect。故**新增**三个只读方法（不动任何既有签名）：

- `SquadRows() ([]SquadRow, error)` / `CarrierRows() ([]CarrierRow, error)`：
  写入序稳定，每行带 Version（CAS 编辑回路唯一权威来源）；
- `QueueSnapshot() ([]QueuedRequest, error)`：按 QueueKinds 顺序遍历两队列，
  Position 是全局 1 基位次（launch_queue 整队在前——清队循环的出队次序就是看板
  该呈现的次序），队内序与 PopReady 完全同判。

**排序比较器唯一化**：PopReady:257 与 position:454 今天各自内联一份相同的四级比较
（就绪度降序 → orderRank 词表 → 首次入队序 → registry Seq）。QueueSnapshot 若再写
第三份必漂移。提取包级 `queueLess(queueOrder, queueOrder) bool` + `sortedQueue(kind)`
助手，三处共用。**行为差异声明**（唯一一处，有意为之）：现 position 对解码失败的
损坏行静默跳过继续排位，改后与 PopReady 同判整队报错（position 返回 0）——损坏行
静默跳过会让 Enqueue 返回错位的位置号，报错是更诚实的失败；position 结果只进日志，
不影响任何语义分支。竖切回归（TestIgnitionVerticalSlice 覆盖 Enqueue/PopReady 排序）
+ Task A 新测试共同锁定改写等价性。

### D3 端点与 wire 形状总表（TS 镜像与 K6 消费的唯一依据）

| 方法与路径 | 请求 | 成功响应 | 失败 |
|---|---|---|---|
| GET /api/squads | — | 200 `{"carriers":[CarrierView...],"squads":[SquadView...]}`；空库=两个空数组（非 null） | 503 未装配 / 500 registry 故障 |
| PUT /api/squads/carriers/{name}?expect=N | CarrierInput JSON | 200 `{"name":"<name>","version":N+1}` | 400 缺 expect/解析败/校验拒（ErrInvalid）/body.name 与路径不符；409 ErrCASConflict；500 其余 |
| PUT /api/squads/squads/{name}?expect=N | SquadInput JSON | 同上 | 同上（另：成员引用不存在 → 400） |
| GET /api/queue | — | 200 `{"queue":[QueueEntry...]}` 按 D2 位次；空=`"queue":[]` | 503 / 500 |
| POST /api/cards/{id}/coordinator/launch（K4 实现） | `{}` 空对象 | 200 CoordinatorLaunchResp | 400 含指路文案（岔口四）/404 卡不存在…由 K4 定，K3 只锁命令侧渲染 |

expect 必填且缺席一律 400：不许「没带就当 0」——那会把更新静默变新建（或反之）
造成覆盖他人改动；客户端从 GET 各行的 version 取值，新建传 0。PUT 返回的 version =
expect+1，即「本次写入产生的版本」；随后他人的并发写会再推进，编辑回路每次 GET 重取。

### D4 错误哨兵与翻译

scheduling 哨兵区追加两个导出值（不改既有四个）：

- `ErrInvalid`：PutCarrier/PutSquad 的输入校验错误改以 `%w` 包装它（名字缺失/凭据
  来源词表外/角色词表外/成员引用不存在）。今天这些是裸 fmt.Errorf，gateway 无法区分
  「用户输入错（400）」与「registry 故障（500）」；
- `ErrCASConflict = schedclient.ErrCASConflict`：再导出别名。d_gateway 的 entries 只有
  `scheduling.Service` 与包级函数，handler errors.Is 判 409 不应 import schedclient。

gateway 翻译表：ErrNotFound→404（预留）、ErrInvalid→400、ErrCASConflict→409、
其余→500。CLI 侧无需翻译：httpStatusError.Error() 已含服务端正文原样（client.go:96）。

### D6 组装点 CAS 哨兵翻译缺口（基线新发现，本卡必须修，K2 被同一缺口挡住）

**现状事实（读码实证，出处见 §0 末行）**：registry 层冲突包装的是
`ledger.ErrCASConflict`（internal/ledger/registry.go:50「…: %w」）；组装点适配器
`facadeAsRegistry.translateRegistryErr`（server.go:2294–2300）**只翻 ErrNotFound，
不翻 ErrCASConflict**——冲突错误原样穿透到 scheduling.Service。后果两条：

1. 生产链路上 `errors.Is(err, schedclient.ErrCASConflict)` **恒 false**。今天的
   stepRunning（scheduling.go:424）靠它决定重试——单线程竖切测不出，一旦真并发，
   重试环第一次冲突就当致命错误返回；
2. **K2 plan 的并发原子化（b156.3.2-plan.md Task A，acquire 循环 462 行同样判
   schedclient.ErrCASConflict）在同一缺口上会翻红**——它的并发测试把这类失败
   「一律判负」，成功数到不了 M。

修法（落在本卡 Task C，因为本卡的 409 映射同样依赖它）：translateRegistryErr 补一个
case——`ledger.ErrCASConflict → fmt.Errorf("%w: %s", schedclient.ErrCASConflict, err)`
（保留原文细节，恢复 Is 可判性）。这是组装点适配器的法定职责（contract §8「翻译
Record/ErrNotFound/ErrCASConflict 形状差」原文点名了 CAS，实现漏了半个），属缺陷
修复而非语义变更。**跨卡审计必须把这条带给 K2**：若 K2 先合并并在并发测试上翻红，
先查这里再查重试预算。

```go
package scheduling

import (
	"encoding/json"
	"fmt"
	"sort"
)

// queueOrder 是队列排序键的统一视图。
type queueOrder struct {
	req    IgnitionRequest
	seq    int64 // 首次入队序（重复入队保留原值）
	regSeq int64 // registry 全表写入序（终极 tie-break）
}

// queueLess 是队列排序的唯一比较器（契约 §4.2 条 4）：就绪度快照降序 → 卡
// 优先级（orderRank 出厂词表）→ 首次入队序升序 → registry 写入序升序。
// PopReady、position、QueueSnapshot 三处共用；出现第四份内联排序副本即违约。
func queueLess(a, b queueOrder) bool {
	if a.req.Ready != b.req.Ready {
		return a.req.Ready
	}
	if ar, br := a.req.orderRank(), b.req.orderRank(); ar != br {
		return ar < br
	}
	if a.seq != b.seq {
		return a.seq < b.seq
	}
	return a.regSeq < b.regSeq
}

// queueRow 是 sortedQueue 的一行：排序键 + 出队所需的删除元数据。
type queueRow struct {
	id      string
	version int // registry 行版本（PopReady 的 CAS expect）
	actor   string
	order   queueOrder
}

// sortedQueue 读一个队列并按 queueLess 排好序返回。解码失败整队报错，
// 与 PopReady 原语义一致（position 因此从「静默跳过损坏行」改为同判，见 D2）。
func (s *Service) sortedQueue(kind string) ([]queueRow, error) {
	entries, err := s.repo.List(kind)
	if err != nil {
		return nil, err
	}
	rows := make([]queueRow, 0, len(entries))
	for _, rec := range entries {
		var e queuedEntry
		if err := json.Unmarshal(rec.Body, &e); err != nil {
			return nil, fmt.Errorf("queue %s/%s 解码失败: %w", kind, rec.ID, err)
		}
		rows = append(rows, queueRow{id: rec.ID, version: rec.Version,
			actor: e.Req.Actor, order: queueOrder{req: e.Req, seq: e.Seq, regSeq: rec.Seq}})
	}
	sort.SliceStable(rows, func(i, j int) bool { return queueLess(rows[i].order, rows[j].order) })
	return rows, nil
}

// SquadRows 列出全部小队（写入序稳定），携带各自 registry 版本——CAS 编辑回路
```

```go
// registerSchedulingRoutes 注册编制域端点（Handler() 内调用一次）。
func (s *Server) registerSchedulingRoutes(api *http.ServeMux) {

	api.HandleFunc("PUT /api/squads/carriers/{name}", s.withScheduling(s.handleCarrierPut))

// withScheduling 与 withLedger 同形：编制域未装配时 503 并给出可行动原因。
func (s *Server) withScheduling(h http.HandlerFunc) http.HandlerFunc {
	return func(w http.ResponseWriter, r *http.Request) {
		if s.scheduling == nil {
			writeJSON(w, http.StatusServiceUnavailable, map[string]string{
				"error": "编制域未装配（SetupAutomation 未执行）",

			return
```

```go
// decodeWire 整段读入再解码（Decoder.Decode 只吃第一个 JSON 值、尾随内容被
// 静默丢弃，截断或串包会被当成有效响应——理由同 CardStep 的注释）。
func decodeWire(resp *http.Response, into any) error {
	body, err := io.ReadAll(io.LimitReader(resp.Body, 1<<20))
	if err != nil {
		return fmt.Errorf("读取响应: %w", err)
	}
	if err := json.Unmarshal(body, into); err != nil {
		return fmt.Errorf("解析响应 %s: %w", string(body), err)
	}
	return nil
}
```
