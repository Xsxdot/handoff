## 稿首待拍板清单

以下均是实现提案，尚未获得技术裁决；不能以本计划自批。

1. **P0 承重门优先**：先验证当前 hostapi 唯一已实装载体 opencode 的权限事实与 allow/deny 握手。`run --format json` 不应被假定可交互；若不成立，比较官方可用的会话/权限 API 或现有载体能力，带真实版本、影响面回协调者裁决。失败只阻塞 S3 及四卡整体收口，S1/S2 和任务侧 S4 可继续；禁止把未接上的协调者入口报绿。
2. **首故事选 S1 竖切**：P0 后，以任务工单人工保存规则→真实下一请求命中→撤销为第一条完整故事，统一规则权威随此故事落地。B458 与 B470 的触及部分串行施工；不先做无消费者规则平台。其余故事沿同一分支串行，四张现有卡分别留验收记录，不再造技术子卡。
3. **持久化与管理权**：提议沿用共享 ledger 注册表 CAS，规则语义归 approval；每次裁决读取权威状态，不靠离线 allow 缓存。必须先证明“明确人类授权”来源及管理入口认证，不能把 registry actor 字符串当管理员资格。若现有认证无法区分模型调用与人类保存规则，阻塞规则写入入口，带最小可信确认方案返回裁决，不能仅加 `confirmed=true` 自证。
4. **跨机撤销线性化边界**：建议撤销提交后新开始的裁决必须见撤销；已经返回且投递的单次许可不追杀。读取到投递之间撤销的窗口，须由首故事明确为版本复核/有界单次授权的哪种语义并回写冻结；不能承诺远端动作与账本共同事务。不能证明新鲜性时升级人工。
5. **UI 最小形态确认**：在现有工单内增加“仅本次批准 / 保存规则并批准”的显式确认及条件/范围/来源/覆盖项；规则查看与撤销先提议就近入口。实现前依据 `prototyping-in-brainstorm` 从 `prototypes/base/` 做分支副本，展示保存确认、管理/撤销、失败三个状态，由用户确认；本计划没有预先批准新页面布局。CLI 可先完成行为，不替代最终 UI 验收。
6. **冻结时机**：本稿冻结下述语义提案；精确 DTO/错误码/新增导出面在 P0 和 S1 真实承重结果后收敛，以同批文档和可编译契约审查，未经拍板不开始依赖它的后续单元。现有 `hostapi.Host.RunTurn` 标有冻结签名，任何签名/承载模式改变必须显式审核。

## 顺序与可检查交付

### P0：承重核验（不改产品行为）

协调者直接执行，本 task 不派发。读当前二进制路径/版本/help、实际 opencode 对应源码/官方权限协议，核 current hostapi 环境与权限配置。使用隔离 HOME、隔离工作目录、明确要求审批的无害本地动作；不得读取生产密钥或执行真实部署/push。

- 抓取权限请求是否真实产生、完整字段来源、权限 ID/session 关联、如何暂停并返回 allow/deny、拒绝后行为、超时/退出；保存脱敏原始事件、argv/配置差异、版本与时序。
- 分别跑 launch/resume；验证无法取得载荷、格式异常、取消/进程退出、重复事件时不会绕过审批；记录 CLI 是否默认 auto-reject，不能把 error 事件当权限事件。
- 若只能通过切换承载形态交互，输出最小差异提案（会话连续性、隔离 HOME、取消/进程树回收、超时和旧调用兼容性），回到稿首 P1/P6 拍板。不给 `stdin` 写任意 JSON 假定已支持。
- 同时核 ledger 管理 API 的认证与 actor 来源、跨机读一致性；确认规则创建的可信人类授权链。产物是能力矩阵/失败读数，不是“完整 DTO 已成立”。

阻塞范围：CLI 握手失败阻塞 S3 与双入口 S4；管理员来源失败阻塞 S1 规则写入及全部持久授权，仍可做 S2、已有上下文核对和只读承重实验。运行环境缺失要标未验证，禁止换 mock 结案。

### U1：S1 首故事与任务侧 S4（详细下一段）

依赖：P0 的存储/认证承重结果（硬依赖）；CLI 握手不是本段硬依赖。

- [ ] 在 `internal/approval` 内确定最小规则模型与管理/评估能力：非空条件、主体适用范围、项目/全局范围、规范化工具/操作/路径等已可证明事实、来源与明确人工限制覆盖集合、规则 ID/版本、撤销。未知条件/字段/规则版本拒绝授权。不能以一个宽泛命令字符串授权任意 shell 组合。
- [ ] 经 ledger 既有注册表读写实现版本化持久化，approval 管语义；确认 CAS 冲突/撤销不会丢失更新。沿用现有账本原语，不另造规则数据库。读不到与确定不存在严格区分；任何权威读取异常不得用旧规则 allow。
- [ ] 统一评估先把原静态门禁结果及具体限制标识交给规则权威；明确规则只能覆盖列出的限制。缺失结构/主体/授权来源不可证明不由规则补猜。未命中保持现有静态→模型→人工语义；模型一次 approve 不触发管理写路径。
- [ ] 接任务真实 gate 回答：仅本次沿用原行为；保存规则必须显式提交可审阅条件/来源/覆盖项，持久化成功后才走本次授权。跨域不伪造原子事务：规则保存成功但本次回传失败时明确显示两种事实；重试按操作身份幂等，不重复扩大规则；保存失败不得落批准。
- [ ] 给 CLI 规则查看/创建/撤销和工单快捷保存接管理 API；先核现有 `reply --approve` 兼容性。管理写口和工单保存共享校验/人类授权检查，非 gate/已回答工单不得偷偷转成规则。
- [ ] 完成稿首最小 UI 分支原型确认，再接 TicketsPanel/真实 API；确认单次与持久动作可区分、失败草稿不丢、来源与覆盖项可读、撤销结果可查。UI 不维护授权本地真相。
- [ ] **日志**：按现有结构化 logger 记录管理请求进入/结果、CAS/外部存储调用前后、规则版本/命中或未命中原因、撤销和本次投递失败；关联 request/permission、真实主体、规则 ID/version，不记录凭据/完整敏感命令。
- [ ] **意图注释**：新增文件责任边界、导出方法合同、显式人类来源与规则/本次分开提交的原因、撤销新鲜性及 fail-closed 分支。
- [ ] 验收真实任务工单：本次批准不建规则；保存→下一请求命中→撤销→再请求人工；空条件、缺事实、未授权覆盖、损坏数据/断连、CAS 并发、失败重试、重复回传均有反例。至少一支测试穿过 CLI/UI请求→proto JSON→agentd→approval→ledger→真实任务消费者，区分缺失与空/零值。

首故事检查点：用户能从真实入口完成生命周期；协调者审核 U1 并回写接缝，才开始 U2/U3。不用纯函数匹配测试代替故事。串行无独立子卡合并，因此不制造 `--no-ff` 首子卡；若改为扇出，必须补子卡计划并以首故事无快进合入提交作为共同基线。

## 需冻结的外部承诺（语义提案，待拍板）

新增跨进程管理 API/审批上下文涉及对外 wire，冻结以下可独立判定行为；具体字段由 U1/P0 补源码符号/版本，不复制全部内部方法。

1. 任务与协调者主体在 wire 中明确区分；协调者请求不要求伪 task 标识。
2. 缺失/未知规则条件、规则版本或必需上下文不能产生自动授权。
3. 一次批准不写持久规则；模型批准不能调用可信人类创建通路。
4. 新规则必须可追溯明确人类确认来源；伪造 actor/确认字段不能绕过入口授权。
5. 单条规则仅覆盖其明确列出的人工限制，其他限制仍升级。
6. 保存失败不得导致本次许可；保存已成功而原生投递失败须分别报告。
7. 撤销提交后新裁决不使用撤销前缓存；并发投递边界按稿首 P4 审定。
8. 规则创建/撤销并发冲突不会静默覆盖，审计可从规则身份/版本关联到请求及主体。
9. hostapi 权限回复使用真实 CLI 支持的协议；不支持/失联/超时不能表现为已批准或成功空回合。

既有契约引用：基线 `internal/hostapi/hostapi.go` 的 RunTurn/TurnRequest、`internal/proto/approver.go` 和 registry CAS 原语。精确版本/字段/错误白名单与手写投影清单须在首次新增 wire 前登记；无真实消费的字段不冻结。冻结调整回协调者审核，不由后续单元自行兼容猜测。
