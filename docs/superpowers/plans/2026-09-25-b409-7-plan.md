## 2. 真实生产路径与必须守住的边界

### 账本、权威事实与派生投影

- `internal/ledger/store.go#Open` 按 DSN 选择 PG/SQLite，并经 `ensureSchema` 安装/升级 schema；所有 Store 写操作由 `mutate` 事务收口。PG 写事务以 advisory lock 串行化；SQLite 使用单连接。S5 必须通过这条真实启动/事务路径验证升级，而非只直接建一张当前投影表。
- 镜像事件生产入口是 `internal/ledger/mirror.go` 中的 `Store.AppendMirroredEvent`：幂等键校验后向 `card_events` 追加 `type=task_mirrored` 事实。B409.1 负责的未决工单投影消费者是 `internal/ledger/taskstate.go` 中的 `Store.OpenTickets` / `OpenTicketCounts`；其它单元若新增派生 projection，也由其所有者明确 source kind、key、更新原子性与有效 watermark。`card_events` 永远是重建依据和唯一权威历史；不得将测试表或 projection 值称为第二事实源。
- S5 比较 watermark 时须按各投影已冻结/实现的覆盖范围解释：对照该投影负责的 source event kind / 序列边界与 canonical `seq`；不能要求只消费 `task_mirrored` 的投影追到每一种无关事件，也不能用未声明的全局 `MAX(seq)` 掩盖它没有消费应处理的事件。当前 `Open`/DDL、镜像 writer 与各投影实现若和本文交接边界有差异，执行者须按已审查实现更新核对表；不得自造表名、SQL 或 watermark 语义。

### 各故事的真实消费者闭环

- **S1**：`GET /api/cards` → `internal/agentd/ledgerapi.go#Server.handleCardsList` → `Store.ListCards`、U1 `OpenTicketCounts` 与 U2 `unlinkedSummary` → `web/src/api/ledger.ts#fetchCards` → `CardsPage`、Shell badge/filter；CLI `handoff card list --json` 读卡列表，`handoff card wait <id>` 经 `cmd/card_wait.go#runCardWait` → `encodeCardWaitSnapshot` → U1 `OpenTickets` 生成首行 `card_snapshot`。远端 target 只由 U2 缓存摘要提供，不能卡住本地账本主读。
- **S2**：`GET /api/sessions` 和 `/api/sessions/{id}` → `sessionsapi.go` → `collab.Service.ListSessionsContext` / `SessionDetailContext`；`GET /api/rooms?project=&limit=&cursor=` 与 `/api/rooms/{id}/messages?before=&limit=` → `roomsapi.go` → collab room list/history → `ledger.Store.RoomMessagesBeforeContext` 等限域读。CLI 入口包括 `handoff session list --json`、`handoff session detail <id>`、`handoff room list`、`handoff room read <room>`。Web 的真实工作台是 `/`，会话列表在 `Shell` / `SessionSidebar`，详情、房间切换和历史经 `SessionTab`/rooms API；`/rooms` 是 API，不是页面路由。Wave 0 的最近 200 条房间历史验收是回归基线，不得外推为剩余 S2 通过。
- **S3**：`GET /api/inbox` 与 `handoff room inbox` 走 agentd inbox 汇总；collab `Pending/Mentions/Consume` 和同房间回复清理拥有成员/房间消费语义。`handoff session send` 与 `handoff session wait [--follow]` 在 `cmd/session.go` 组装 collab 与账本，`MessageWakeTargets` 是唯一寻址判定，持久 `session_delivery_cursors` 驱动恢复。U7 只验证已批准 contract 下的交付及 SQL/结果，不更改 wait、stdout、cursor 或消费语义。
- **S4**：账本/房间现有诊断已分开记录连接池等待、SQL 调用、行读取、返回行数与 payload bytes、collab 组装和 handler 总时长（例如 `internal/ledger/rooms.go`、`internal/collab/service.go`、`internal/agentd/roomsapi.go`）；U6 负责其余 B409 入口的缺口闭环。U7 用端到端记录核 stage 对账，并以错误/取消/target 不可达场景检查日志可检索且脱敏；不新增通用 metrics 子系统。
- **S5/增长**：Store 查询使用各 unit 对应的真实 Ledger/Facade/Collab/HTTP/CLI/Web 入口；不能用一个模拟 Store 或直接 SQL 的输出值，代替生产消费路径。现有 `internal/ledger/rooms_history_perf_test.go` 是 Wave 0 的 PG 房间历史 harness，已含隔离库名校验、空库检查、分阶段 seed 统计与 history 样本；执行者应核实可复用部分后扩展为完整矩阵，不把现有单房间测项伪报为全故事通过。

1. **先过计划与依赖门。** 确认 B409.1–B409.6 计划齐全、U6 单卡 review/挂卡状态可追溯，且 U1–U7 全计划集已通过非作者独立 `charter:plan` 审计；确认 U1–U6 已 review 并集成到同一候选版本。U5 的全流物理读与 r2 有界候选读 contract delta 未冻结前，禁止派发本卡实现/宣称 U7 可开始。另确认 U5 责任卡已提交真实 CLI→共享 PG→另一机器同 member 重挂的 S3 故事证据；若缺失，U7 不得用本地 mock/单机测试替代，阻塞 S3/U7 故事闭环并交回 U5 owner。执行者记录卡号、冻结 base、代码 SHA、contract/spec SHA、DB driver/server 版本与已有 Wave 0 ledger 证据。
2. **锁定跨方言金样与独立 oracle。** 以同一组逻辑事件/会话/卡/消息/cursor/未决工单夹具分别建临时 SQLite 与专用 PG 库，按真实生产写入/初始化路径建立，顺序固定。用独立事件重放 oracle 校验 source seq、卡/target/task/ticket 身份、创建/答复/作废/终态、session/room/member、消费和 cursor 边界；对每个投影的行字段与可见 watermark 逐项对照。贯通 Store → 已集成 Facade/Collab → HTTP JSON/CLI stdout，输出与冻结业务金样一致；空、失败、取消不能相互混淆。对用户可见 JSON/NDJSON 按字段、数组顺序、状态/游标和值核对，原始 payload 仅在既有 contract 要求字节保真处做字节相等断言；同时独立记录每方言实际读回的 payload bytes，不静默规范化可观察差异。
3. **验证旧库升级、重建和中断恢复。** 用真实 pre-projection schema fixture（来源 revision 留档）先载入 canonical `card_events`，再通过正常 `ledger.Open`/`ensureSchema` 升级；PG 与 SQLite 均须得到与 oracle 相同的投影、查询和 watermark。对空/已有 projection 执行 rebuild，再重复 rebuild；投影行、开票结果和有效水位相同，无重复/漏算。确定性地在重建中途注入一次仅测试使用的失败，确认错误和落后/未就绪状态可观察，不能把半成品报成最新；修复故障后重开 Store/重试重建，必须从权威事件恢复到预期水位和结果。对事件追加期间的中断按已审查实现验证：若 event+projection 同事务，失败时二者都不提交；若实现有独立补偿/追赶阶段，则必须显式暴露 lag 并幂等 catch-up。任何路径都不得出现事件已落账、读者长期看到“完整最新”但投影缺行的静默分叉。不要为了测试擅自新增线上 failpoint；若现实现无测试注入点，使用包内最小 test-only seam 或数据库故障注入，并保证生产没有启用开关。
4. **构造三阶段隔离 PG 增长矩阵并核对真实 seed。** 延用现有 B409 harness 的唯一数据库名 `handoff_b409_test` 检查与 run ID 清理边界；另要求协调者确认 `LEDGER_TEST_PG_DSN` 是可丢弃隔离库。每个新运行先确认所有相关表/夹具范围为空或使用全新隔离库；禁止用 `newPGStore` 这种无专用库名保护的通用 helper 执行清理/大规模 seed。SQLite 使用独立 `t.TempDir()` 文件。

   | 阶段 | PG canonical `card_events` | 必须验证的数据形状 |
   |---|---:|---|
   | ① 当前量级 | 约 21,270 events | 恰按实际统计报告 `task_mirrored` 数；基准约 9,337 行、payload 总量约 6.31 MB；固定各故事目标结果集与已冻结金样。 |
   | ② unrelated 增长 | 阶段① + 至少 20,000 条 unrelated、非 `task_mirrored` 事件 | target 结果集/业务输出不变；mirror 行数与 payload bytes 对照阶段①并说明。 |
   | ③ mirror 增长 | 阶段②基础上增加镜像事件 | `task_mirrored` 行数与其 payload 总 bytes **各自至少是阶段①的 2 倍**（基准构造时至少 18,674 行、约 12.62 MB）；新增镜像样本不得改变固定目标业务结果。 |

   每阶段以数据库实测计数/字节作为通过依据，不以配置数字作证：记录总事件行数、按 `type` 分组的计数、精确 `task_mirrored` 行数、payload bytes、目标 fixture 行数与清理结果；明确检查没有将 `mirror_event` 等其它 type 混计成 `task_mirrored`。用被审查过的 B409 seed helper；如果现有 helper 的 envelope 不再等同真实 `AppendMirroredEvent` 持久格式，先在隔离 DB 对照真实 writer 写出的样本，再修正测试 helper，不改权威事件 schema。阶段③计算基准至少按阶段①分母报告，若阶段②镜像量因 seed 实测不同则同时列两组比例。

5. **按冻结范围量 HTTP/API、Web，并完成功能级 Store/CLI 验收。** 三个数据档分别测 r2 冻结的 HTTP 场景：`GET /api/cards`、`GET /api/sessions`、`GET /api/rooms` 与单房间最近 200 条消息首屏（`GET /api/rooms/{fixture}/messages?limit=200`）。对应 Web 首次可用内容测 `/cards` 卡片列表与工作台 `/` 的 session/room/message 首屏；`/rooms` 是 API 路径，不作为 Web 页面。每个数据档、每个适用 HTTP/Web 场景单列一次首请求，再做 5 次预热和 100 次计入样本；nearest-rank 报 p50/p95/max、错误数与响应 bytes，失败保留为失败样本。只有这些冻结 HTTP/Web 场景承担 p95 ≤2 秒门槛；HTTP 各路由、Web 各用户可见路径分别报告，不合并平均数。Store 阶段 rows/payload bytes 与耗时从这些真实请求贯穿到 DB 的同一批调用日志/探针中采集，作为各请求的解释性阶段数据，不另造 Store 独立 100 样本或 p95 门槛。

   - **API 功能覆盖与描述性耗时**：另以真实 agentd 路径覆盖 `GET /api/sessions/{fixture}` 与 `GET /api/inbox` 的成功、空、错误/权限/取消语义；按实际请求记录 U6 stage 与完整 response bytes。它们不属于 r2 明确的数值性能 target，耗时只作描述性数据，不设 100 样本或 p95 ≤2 秒门槛。

   - **Web 首次可见内容**：Codex 内置浏览器连接真实 agentd。`/cards` 验证卡片行、工单计数、freshness badge/filter；工作台 `/` 验证 SessionSidebar、打开目标 session、切换至有消息的 room 并等最近消息首屏可见。每数据档、每个用户可见路径单列首请求，再做 5 次预热与 100 次计入样本，从导航开始计至目标内容可见，记录 p50/p95/max、错误与 response bytes，以及 build/服务/浏览器/PG 位置。不得以 jsdom、组件 mock、截图或 API 计时替代真实首屏样本。

   汇总中分开记录合格 HTTP 请求内部的 PG 查询/读回 rows+bytes、collab 应用折叠、HTTP 序列化与响应 bytes；Store rows/bytes 必须对应上述真实 HTTP 操作，不以 CLI 单测或独立 Store 查询冒充。CLI 的首次 stdout 与 cursor/watermark 作为故事证据并可附描述性耗时。比较 stage ①→②→③时固定业务结果和实际读回规模；对非目标历史增长，已限域读路径的 DB 实际返回 rows/bytes 不得随无关 event 线性增长；目标 mirror 量增加时仅相应结果域可增长，不得把无关 payload 重新全量搬到应用层。

## 5. 成功条件与必须为红的反例

### 成功条件

- 同一逻辑事件 golden 在 PG/SQLite 中逐 seq 对应、行字段/投影结果、watermark 解释、上层 JSON/CLI JSON 和错误/空/取消语义等价；方言差异只限已核实、未破坏冻结输出的底层编码，不得静默吞掉字节或排序差异。
- pre-projection 旧库走真实 `Open` 升级后保留全部 canonical events，projection 与独立 replay oracle 一致；连续两次 rebuild 结果/有效水位不变；中途失败明确返回且不暴露半成品“最新”；故障清除后重开/重试能幂等补齐。任何事件事务与投影分离窗口均有可观测 lag/恢复路径；同事务策略则证明失败时二者原子回滚。
- 三阶段 PG 种子以数据库实际统计验证约 21,270/9,337/~6.31MB、+≥20,000 unrelated non-mirror、mirror 行数和 payload bytes 双倍；真实测量无 `mirror_event` 冒充镜像。固定业务金样无意外变化，SQL/driver 实际 rows 与 payload bytes、各层可见时间和响应 bytes 均逐入口保留。
- 每数据档、每个 r2 冻结 HTTP/Web 性能场景均单列冷首请求、5 次 warm-up 和 100 个样本，nearest-rank p50/p95/max、错误和响应 bytes 完整报告，适用路径 p95 ≤2 秒；Store rows/bytes 来自这些真实 HTTP 调用的内部阶段数据。CLI/API 其余路径完成故事功能、真实 stdout/state 断言并附描述性耗时，不加 100 样本或 p95 ≤2 秒门槛；`session wait --timeout 5s` 仍须 30 次每次 ≤6 秒。
