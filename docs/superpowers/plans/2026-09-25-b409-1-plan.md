> **批准基准**：[`2026-09-24-ledger-read-performance.md`](../specs/2026-09-24-ledger-read-performance.md) r2；S1 wire 约束见 [`b409-contract.md`](../specs/b409-contract.md) v1；本工作单元边界见 [`b409-breakdown.md`](../specs/b409-breakdown.md) §U1。
> **适用既有契约**：B380 C-2（[`b380-contract.md`](../specs/b380-contract.md)）冻结 `OpenTickets` 的终态关单语义，是本单票据状态的直接契约。B156.2 contract A.5 已关闭 History/Pending 的旧“超过 10^5 行才重议”性能护栏；它不定义本单票据状态，但作为性能门槛先例，本故事不得用账本未到阈值为由跳过实测。B156.2 §3.6 的收件箱 eligibility（等待人工输入、`Hub.Watchers` 与破坏性工单）属于 gateway 编排，不下沉进 ledger 投影；其房间历史接口 §3.4.1 也不属于 U1。
> **事实基线**：计划定位时当前工作树 `codex/session-reliable-mentions` / `286261113bbc8a205b90287747294271c976d9f6`；实现开始时须复核卡冻结的 base 与下列生产路径，不能把本计划的行号当作锚点。

## 1. 交付目标

让既有 `ledger.Store.OpenTickets()` 与 `OpenTicketCounts()` 不再为每次读取把全部 `task_mirrored` payload 拉入 Go 并重放；普通明细读只返回未决工单所需 payload，计数读不返回工单正文。`card_events` 仍是唯一权威事实源。任何新增派生读模型必须可从 `card_events` 幂等重建，并与追加事件在同一事务内维护，避免事件已提交而投影静默落后。

对每张卡，新的 `OpenTickets` 明细与 `OpenTicketCounts` 计数必须等价于按 `card_events.seq ASC` 对当前镜像事件重放；保持现有方法签名、字段和值语义，供 `/api/cards` 与 `card wait` 原样消费。本工作单元只交付账本侧读模型及其 SQLite/PostgreSQL 验证，不代表 S1 故事完成，也不负责最终 B409 性能验收。

## 2. 改动边界与真实生产路径

### 允许触及

- `internal/ledger/taskstate.go`：`OpenTickets`、`OpenTicketCounts` 及本包内私有回放/投影函数。
- `internal/ledger/mirror.go`：仅当持久投影需要在镜像事件追加时同步更新；入口为 `(*Store).AppendMirroredEvent`，必须复用它现有幂等检查与 `mutate` 事务。
- `internal/ledger/store.go`：仅当需要新增可重建投影的 schema 时，PG 与 SQLite 两套 DDL、索引和初始化/升级路径须成对修改。
- `internal/ledger/taskstate_test.go`、必要的新 ledger 测试文件及 `internal/ledger/ddl_parity_test.go`：重放等价、投影、方言对等和增长回归。

### 生产消费者（只核对兼容，不在本卡修改）

- `GET /api/cards` → `internal/agentd/ledgerapi.go#Server.handleCardsList` → `Store.OpenTicketCounts()` → 卡片 `open_tickets` 计数。
- `handoff card wait` 建连 → `cmd/card_wait.go#encodeCardWaitSnapshot` → `Store.OpenTickets()` → 按当前卡/子树成员过滤并写出现有 `card_snapshot.actionable`；过滤继续留在 CLI 消费端。

不要改 agentd/Web 的摘要 wire、`cmd/card_wait` 的成员过滤或 JSON 形状（分别由 U2/U3 负责）；不触碰 collab/room/session 路径、`EventsFromAsc`/`Store.Follow`、wakeconsumer、远端 target 请求、工单写入/审批业务或 `card_events` 权威历史。不得新增跨包公开方法/DTO；若实现需要改变公共接缝，停止并交协调者返回 contract，不在 U1 内扩面。

## 3. 工作顺序与承重假设

1. **先复核基线与状态机。** 对照 `taskstate.go`、`mirror.go`、`store.go`、`taskstate_test.go` 和 B380 C-2；确认唯一生产镜像追加入口是 `AppendMirroredEvent`，投影 key 与当前 key 一致：`(card_id, source_target, source_task, ticket_id)`。确认当前规则：`permission_request` / `question` 创建或替换对应 ticket；`ticket_answered`（最终答复事件）按 ticket id 关闭；`tickets_voided`（回合撤回/作废）按任务关闭全部；任务 `completed`、`failed`、`archived` 关闭该任务全部。投影消费的是账本 `seq` 顺序；不要把这里的“关单终态集合”复制进 `mirrorTaskTerminal`，B380 明确 `completed` 在镜像订阅视角仍可等待后续事件。遇到真实基线与冻结契约冲突先停下报告，不自行更改事件语义。
2. **立回放 oracle 与红测。** 在 SQLite 上扩展现有 `TestOpenTicketCounts` / B380 终态测试，准备多卡、多 target、多 task、重复镜像、答复/作废/终态及交错事件。以独立、直接读取 `card_events` 的参考回放作为 oracle，分别比较 `OpenTickets` 的逐条字段（含创建 payload 原始字节、排序）和 `OpenTicketCounts` 的逐卡结果；不可用实现函数自身充当 oracle。先加入新投影断言并运行 `go test ./internal/ledger/ -run 'TestOpenTicketProjection' -count=1`，确认它在旧全流实现上因“无关 payload 仍被扫描/计数读仍取正文/无投影重建能力”中的实际不满足项而 RED；同时运行 `go test ./internal/ledger/ -run 'Test(OpenTicketCounts|OpenTicketsTerminalMirrorClosesAll|OpenTicketsTerminalBeforeAnswerDoesNotResurrect)' -count=1` 确认既有语义基线，再实现。
3. **实现有界热读。** 采用账本内部的可重建未决工单投影，使 `OpenTickets` 从投影只取仍未决的行，`OpenTicketCounts` 直接在投影中按卡聚合，不读取明细 payload。镜像追加在 `AppendMirroredEvent` 的同一 `mutate` 事务中、幂等键确认并插入权威事件后同步应用状态变化；重复 source tuple 不重复改变投影。投影包含重建所需的事件水位/版本标记；初始化、升级或显式重建须从 `card_events` 原子、幂等地重算，并在失败时保留可检测错误，不能把缺失/损坏投影当合法空结果。
4. **证明投影不成第二真相，并跑可复核增长矩阵。** 加入重建测试：从空投影和已有事件建立；同一事件重复重放不双算；重复重建结果逐字一致；人为清空/损坏可由重建恢复；投影更新失败时权威追加与投影不得部分提交。增长样本只在隔离、可丢弃的 SQLite/PG 测试库用合成账本构造，不复制或写入生产账本；三阶段沿用 B409 r2 的规模，且每阶段固定相同的 **100 条未决工单（4 张卡各 25 条）**：

   | 阶段 | 隔离数据集 | 固定业务状态 |
   |---|---|---|
   | ① | 约 21,270 条 `card_events`，其中约 9,337 条 `task_mirrored`，镜像 payload 总量约 6.31 MB | 100 条未决工单；在 4 张固定卡上各 25 条 |
   | ② | 阶段①再加至少 20,000 条无关、非 `task_mirrored` 事件 | 与阶段①完全相同的 100 条未决工单及卡分布 |
   | ③ | 阶段②基础上，`task_mirrored` 行数与其 payload 总字节数都至少为阶段②的 2 倍；若阶段②按基准数构造，即至少 18,674 行、约 12.62 MB | 与阶段①/②完全相同的 100 条未决工单及卡分布；新增镜像事件不得改变这 100 条的开闭状态 |

   每阶段运行同一语义 oracle，并用测试 query/driver 观测实际从 DB 送到应用的行数及字节：`OpenTickets` 必须稳定返回同一组 100 行、其 `Payload` 字节和固定业务结果一致；`OpenTicketCounts` 必须稳定得到 4 张卡各 25 条，数据库结果只有按卡聚合的 4 行且传回工单 payload 字节为 0。阶段②/③的无关事件和无关镜像 payload 增长不得增加任一热读送入应用的行数或 payload 字节。记录每阶段种子实际事件数、镜像行数、payload 字节数、两方法结果行数/字节及 PG/SQLite 方言；只断言输出值或读 SQL 文本、只提供 `EXPLAIN` 均不足以证明搬运边界。
5. **跨方言和调用兼容。** 无条件跑 SQLite 定向回归及 `TestDDLDialectParity`；PG 使用 `LEDGER_TEST_PG_DSN` 运行同一金样/重建测试。DSN 必须指向隔离、可丢弃的测试库，禁止对共享或生产账本跑会清理数据的测试。检查现有 `handleCardsList` 与 `encodeCardWaitSnapshot` 的结果字段/顺序/过滤未变；不以本地 SQLite 单测替代 PG 实际运行。
6. **交棒。** 留下实际运行命令、原始通过/失败结果、PG 服务器版本与测试库隔离说明、重建前后比较及增长样本的观测行数/字节；将 U1 结果交独立 `review`。review 通过后由协调者集成，再由 U2/U3 使用同一读面；U1 PASS 不得写成 S1 或 B409 完成。

### 明确验收判据与关键反例

**成功条件**

- `OpenTickets`、`OpenTicketCounts` 对事件重放 oracle 完全等价，保持空集、计数键和值、明细 `Payload` 原始内容及现有序排序语义。
- `permission_request`、`question`、`ticket_answered`、`tickets_voided`、`completed`、`failed`、`archived` 的开单/逐单答复/批量作废行为与 B380 C-2 一致；不同卡、target、task 间 ticket ID 相同不得串单。终态之后的迟到答复不复活已关工单。
- 重复镜像幂等；PG/SQLite 对同一事件序列返回完全相同结果；重建可重复、失败有错误且不静默错读。
- 大量无关镜像事件及大型无关 payload 不会在热读时被拉回应用；计数读不带出明细正文。保留测得的行数/字节对照作为证据。

**必须为红的反例**

- 删除 `ticket_answered` 关闭逻辑、把 `tickets_voided` 仅按 ticket ID 而非任务清空、漏掉任一 B380 `completed/failed/archived` 终态、或终态后迟到答复让单复活时，相应测试必须失败。
- 将 key 缩成全局 `ticket_id`、丢掉 `source_target/source_task`、重复应用同一镜像事件导致双计数时，隔离测试必须失败。
- 只对空账本测通过、对无关 payload 增长仍线性取回；`OpenTicketCounts` 通过 `OpenTickets` 搬出所有明细 payload；PG/SQLite 任一方缺表/索引/初始化步骤；清空投影后不能重建；投影更新失败仍提交事件——以上任一情形均不通过。
- 把 `completed` 加入 `mirrorTaskTerminal`、改 `card wait`/`/api/cards` 输出或调整事件类型/持久格式来让测试变绿，属于越界改语义，不得通过。

性能故事的端到端 p95 ≤2s 与 B409 r2 三组 100 样本 Web/API 读数由 S1 集成和 U7 最终增长验收负责；U1 仅核验 ledger 热读的数据搬运边界，不承诺或宣称端到端 p95 ≤2s 已达成。

## 4. 决策权限、阻塞条件与交棒责任

执行者可在本包内选择投影表/私有函数、索引、幂等重建和事务内维护细节；必须保留追加式 `card_events` 为唯一事实源、现有 `Store` 公开签名与消费者结果。

以下情形须停止并交协调者，不得自行解决：

- 当前运行事实证明 B380 冻结状态列表不完整，或必须改变 ticket 的业务关单/复活语义；需要变更契约后再继续。
- 投影方案无法与镜像事件在同一事务维护，或无法提供可重复重建与可见失败；先回报架构风险，不做异步静默双写。
- 需要增加/改变跨包公开 Ledger API、Wire DTO、card wait 输出，或改动 S1 contract/breakdown 所定接缝。
- `LEDGER_TEST_PG_DSN` 未设置、指向共享账本或无法确认是隔离库：可完成本地 SQLite 开发和定向测试，但 U1 的双方言验收保持阻塞，不得报告完整 PASS。隔离 PG 数据库由协调者提供/确认；不得拿生产数据做种子。
- **计划集派发门**：即使本 U1 plan 完成，也不得据此派发 implement。须先等 B409.2–B409.7 的 plan 全部齐稿，再由非本 plan 作者的独立上下文按 `charter:plan` 对完整计划集执行跨卡审计并通过；若审计要求修改计划，相关计划修订后重跑审计。审计通过前所有 B409 子卡的 implement 派发门保持关闭。

计划集审计通过并获协调者准许派发后，U1 执行者才进入 implement；实现完成后的下一节点由独立 reviewer 对照本计划、B409 r2、B380 C-2 和测试证据做双轴 review。review 通过后，协调者负责 S1 集成与分派 U2/U3；U1 执行者不改其他卡状态、不部署 agentd。
