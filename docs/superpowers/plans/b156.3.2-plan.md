## 2. 设计定案（拍板已定，不重开方案讨论）

### D1 准入原子化形态（岔口三·方案 A 的落地解释）

现状缺陷（contract §15 澄清 4）：`resolve()` 经 `hasSlot()` 读计数做预检，`acquire()`
再无条件 +1——检查与动作两步分离。基线探针实证 16 路打 4 上限成功 6 路。

改法：**上界判断折进 acquire 的 CAS 循环**——每次尝试先读两级计数、各自对上限复核
（任一满员返回 `ErrNoSlot`），再 CAS 递增；冲突带着新读数重试。`Admit`/`LaunchAdmit`
签名与流程不动，仍无锁直调。

改后两份上界判断的分工（判据形状要求 5 的逐份点名）：
- `hasSlot()`（resolve 内，既有）：**成员选择与错误分类**的预滤——决定选哪个成员、
  全满时返回 ErrNoSlot 还是全不健康返回 ErrNoHealthy；
- `acquire()`（Task A 改写）：**唯一防超发的执法闸**。

变异复验的靶子只是第二份：去掉 `acquire()` 内的上界判断，并发测试必翻红（基线探针
已证明该形状下 successes 会越过上限）；只去掉 `hasSlot()` 的判断不会翻红——它本来
就不承担防超发，这正说明执法副本只有一个、变异靶没有歧义。

已知良性偏保守（写进验收注记，不是缺陷）：并发输家可能在另一成员恰有空位的瞬间拿到
ErrNoSlot（它的成员预滤读数已过时）。方向安全（宁可排队不可超发），下一次准入或出队
自愈。完美全局最优需要锁，正是方案 B 被否的原因。

### D2 解析层插入点与解析栈

插入点 = `startCardStep` 同步段，`ResolveNode` 之后、纪律解析之前（有效目标机要等
Binding 出来才知道，能力位探活必须打 Binding.Target）。存量门是单一开关
`node.Override.Squad != ""`，空 = 原代码路径逐字节保留。

有效三元组的解析栈（依据 types.go:176-180 冻结注释「绑定后……由编制域按小队成员载体
解析，显式 Target/Executor/Model 仍可一次性覆盖」+ §4.2 条 8）：

```
请求一次性覆盖(req.Target/Executor/Model) > 节点覆盖(Override.*) > 载体字段(Machine/CLI/Model) > [模板 ModelByTarget，仅当载体 Model 为空时经既有兜底生效]
```

装配侧因此要有一份「req ⊕ node 合并公式」的副本（`effectiveCovers`），与
ledgerstep 内部那份（dispatchNodeWithGate，runner.go:311）成对规则逐行一致。
两份公式各自的锁 + 等价声明见 Task C 的 TestEffectiveCoversParityMatrix 与既有
TestRunnerExecutorModelOverridePriorityAndPairRule（runner_test.go:117）。
模板 Target/Executor 在小队路径永远够不着（Binding.Target/Executor 恒非空，
作为 req 层覆盖注入）；载体 Model 为空时模板 ModelByTarget 兜底生效是**有意保留**
的既有行为（该表本身按机器配置），T1 不对 Model 为空场景断言模板值。

### D3 三种同步结局与处置分流

| 结局 | 触发 | 处置 |
|---|---|---|
| admitted | Admit 成功 | Binding 三元组接管 StepRunner 覆盖，继续原装配链（纪律解析改用 binding.Target） |
| queued | `errors.Is(err, ErrNoSlot)` | Enqueue(kind=ignition_queue) → 日志带位置 → 释放卡槽位 → 返回 nil。不起 goroutine、无 task、卡事件流零写入 |
| error | 其余一切（ErrNoHealthy / ErrNotFound / ErrRoleMismatch / registry 故障） | 包装后原样上浮 → handleCardStep default 分支回 400（ledgerapi.go:507-510），与排队的静默形态可区分；若已 Admit 成功先 `Release` 回滚两级名额（幂等），防计数泄漏假满 |

nil 防御：`node.Override.Squad != ""` 且 `s.scheduling == nil`（测试服务器或组装
遗漏）→ 同步可行动错误，绝不静默当无小队处理。

### D4 Ready 快照取值决策（plan 级定案，进待拍板清单供复核）

冻结文本只说「Ready 是入队时刻快照」，没给谓词。本 plan 定：**Ready 恒 true**——
点火请求由显式的环节受理动作产生，受理即视为就绪；恒真使排序第一键退化，队列顺序
实际由 卡优先级 → 入队序 决定（§4.2 条 4 的其余两级不受影响）。理由：任何更聪明的
谓词（按列名/按等人标记推就绪度）都是冻结文本里不存在的语义发明。协调者若另有裁决，
改 Task C 一行常量即可，判据不受影响。

### D5 已知边界与移交注记（如实声明，不伪装已解决）

1. **Release 生产接线无人认领**：全仓无生产调用方（台账核实）。K2 之后，被 Admit 占
   用的两级名额没有任何任务终态回收路径，小队会在 M 次派发后假满。契约 §11 只授权
   「发现漂移后加启动时对账」。**本 plan 不自行把终态 Release 接线塞进 K2**（观测
   任务终态属 K5 的消费者循环地盘，塞进来必越有界文件集）——列入 §6 待拍板。
2. **Extra 不随队列存活**：IgnitionRequest 是冻结 schema（contract §4.1，九个字段），
   没有 Extra 槽位。用户随环节提交的临时补充说明在满员转排队后会丢失。不自造字段
   （那是 contract 变更）；K5 出队真派再次走入口时 Extra 为空。移交注记。
3. **计数 CAS 重试预算与并发规模的关系**（拍板附加约束要求的注记）：域内单次计数
   变更长重试 8 次；基线探针实测 N=16 高争用下存在预算耗尽型失败（错误为
   「连续冲突」，非语义错）。为此新增哨兵 `ErrRetryExhausted` 承载分流：验收翻红时
   先看它——它是预算形状，不是超发；语义失败长 `ErrNoSlot`/成功数越界的脸。

// 每次尝试先读两级计数并各自对上限复核，任一级满员返回 ErrNoSlot（调用方转
// 排队），再以 CAS 递增；冲突则带着新读数重试。「谁调用都安全」由本函数单独
// 保证；resolve/hasSlot 的判断只是成员选择与错误分类的预滤，不是防超发的闸。
//
// 计数键只有 squad/<名> 与 carrier/<名> 两类，按（角色,名字）二元组计数不按卡
// （契约 §15 澄清 3），不得引入第三类。MaxConcurrency<=0 视为不设上限：两个
// 上界分支恒不走时，本函数等价于无上界的 CAS 直增（与改前行为一致）。
//
// 半程回滚：小队侧 +1 成功而载体侧失败时，用带符号减法回滚小队侧而不是按版本
// 回写——期间可能有第三方又动了小队计数，按版本回写会把别人的增量踩掉。回滚
// 失败只吞掉：计数偏高是保守方向（多拒不超发），偏低才会超发。
func (s *Service) acquire(q Squad, c Carrier) error {
	squadKey := kindSquad + "/" + q.Name
	carrierKey := kindCarrier + "/" + c.Name
	for attempt := 0; attempt < maxCASAttempts; attempt++ {
		squadRunning, squadExpect, err := s.readCount(squadKey)
		if err != nil {
			return err
		}
		carrierRunning, carrierExpect, err := s.readCount(carrierKey)
		if err != nil {
			return err
		}
		if q.MaxConcurrency > 0 && squadRunning >= q.MaxConcurrency {
			return ErrNoSlot
		}
		if c.MaxConcurrency > 0 && carrierRunning >= c.MaxConcurrency {
			return ErrNoSlot
		}
		if err := s.casCount(squadKey, squadExpect, squadRunning+1); err != nil {
			if errors.Is(err, schedclient.ErrCASConflict) {
				continue
			}
			return err
		}
		if err := s.casCount(carrierKey, carrierExpect, carrierRunning+1); err != nil {
			_ = s.stepRunning(squadKey, -1)
			if errors.Is(err, schedclient.ErrCASConflict) {
				continue
			}
			return err
		}
		return nil
	}
	return fmt.Errorf("%w: %s 与 %s", ErrRetryExhausted, squadKey, carrierKey)
}
