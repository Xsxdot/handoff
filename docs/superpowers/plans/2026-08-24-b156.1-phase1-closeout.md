# B156.1 一期收尾 · 执行计划

- **spec**：`docs/superpowers/specs/2026-08-24-b156.1-phase1-closeout.md`（已批准）

## 为什么这份 plan 不派发

本卡的每一项工作都在**驱动 handoff 自身**（`card close` / 并发 `card dispatch` /
`card wait --subtree` / `card unmerge` / `workflow put`）。一期设计 §9 开头与
`charter:plan` 的红线是同一条：需要驱动派发系统自身的验收步骤由协调者本地执行，
不写进派发 plan（B105 教训）——派出去执行者会撞上「不许调 handoff CLI」的纪律块，
等于没验。

## 基线核验（2026-08-24 已在本机跑过，判据不是凭记忆写的）

## Task 0：搭隔离账本

**为什么隔离**：③⑥⑫要造的是异常态（blocker 被终止、认领冲突、拆回）。在真账本上造异常态，
万一 CAS 或关系边有缺陷，损坏的是 107 张真卡的审计链。

1. `DataDir=/tmp/b156-acc/data`（**短路径**：PTY 的 socket 路径有 104 字节上限，
   不能放 scratchpad），独立端口 7788，独立 config。
2. 起独立 agentd 实例——**不要动 launchd 托管的本机 agentd**，它会用旧二进制被拉回来。
3. 灌定义，顺序不可反：`template put charter-default` → `workflow put charter`。
4. **完成判据**：`handoff --config <隔离config> workflow list` 输出 charter v7，12 节点。

## Task 1：判据③ blocker 终止不解锁

1. 隔离账本建两张卡 P1、P2；`card link P1 P2`（P1 阻塞 P2）。
2. **判据先跑**：`card list --blocked` 应列出 P2。列不出就先停下——是判法错了不是实现错了。
3. `card close P1 --reason 取消 --yes`。
4. **完成判据（三条全中才算）**：
   - `card show P2` 仍显示 blocked；
   - P2 新增 `needs_human`，reason 含「前置终止」类文案；
   - `card list --needs` 能过滤出 P2。
5. **任一条不中**：如实记红，落卡并进 roadmap，**不要改判据去迁就实现**。

## Task 2：判据⑥ 并发认领恰一成功

1. 隔离账本建一张卡 P3，挂好 spec 附件、move 到 plan 列。
2. 两个 shell **同时**发 `card dispatch P3 --executor fake`（用 `&` 并发，不要串行）。
3. **完成判据**：恰一个 exit 0；另一个非零且报「已被 <会话> 认领」；
   `card show P3` 的事件流里 `dispatched` **恰一条**。
4. 收尾：`handoff stop` 掉那个 fake 任务（fake 不发终态事件，会一直挂 running）。

## Task 3：判据① 子树部分 + 改写后的⑤

1. 隔离账本建父卡 P4，`card split P4` 出两张子卡。
2. 一个 shell 挂 `card wait P4 --subtree --timeout 10m`。
3. 另一个 shell 向某张子卡 `card dispatch --executor fake`。
4. **完成判据**：
   - ①：wait 输出含该子卡的事件，单条 wait 覆盖整棵子树；
   - ⑤（改写后）：把 wait 收到的事件按 `(source_target, source_task, source_seq)`
     三元组与账本 `card_events` 里同 task 的集合**做集合比对**，两侧相等。
     **不比连号**——原判据把「不漏」错编码成「连号」，实测单 task 37 条跨 8897–9516。

## Task 4：判据⑫ unmerge

1. 隔离账本建 P5、P6；`card merge P6 --into P5 --yes`（以 `card merge --help` 的实际
   flag 形态为准，**先看 help 再敲**）。
2. 记下 P6 合并前的 `acceptance_recorded` 事件数（先 `card accept P6 --unverified` 造一条）。
3. `card unmerge P6`。
4. **完成判据**：P6 恢复自主状态流转（能独立 `card move`）；其 `acceptance_recorded`
   事件数与合并前一致。

## Task 5：produces 修复（真账本）

**这一项在真账本上做**，因为要改的是现役 charter 流。

1. 导出 charter v7 定义到临时 JSON。
2. 给三个节点补 `produces` 声明（kind 与门对齐）：
   - `contract` → `{"kind":"contract","path":"<契约文档路径模板>"}`
   - `breakdown` → `{"kind":"breakdown","path":"<拆解文档路径模板>"}`
   - `plan` → `{"kind":"plan","path":"<计划文档路径模板>"}`
   路径模板的可用变量以 `RenderOutputPath`（`internal/ledgerstep/runner.go:167`）
   的实现为准——**先读那个函数再写路径**，不要凭猜。
3. `workflow put charter` 成 v8。
4. **备份先行**：put 之前 `sqlite3 .backup` 一份，v8 有问题要能退回 v7。
5. **完成判据（配置层）**：`workflow show charter` 的 v8 里三个节点 `produces` 非 None，
   且 12 节点、四道门与 v7 逐字一致（**只加不改**）。

## Task 5b：produces 的真机端到端验证

配置写对了是 API 事实，自动挂是**行为事实**，静态核验不了（spec 的测试决定明写不接受
「配置写对了」当证据）。

1. 真账本建一张探针卡，挂 spec 附件，move 到 plan 列。
2. `card dispatch --step plan --target linux-01` 派**一轮真的 plan 节点**
   （fake 不产生裁决，验不了）。任务内容取最小：产出一份三行计划文档。
3. **完成判据**：裁决 pass 后——
   - 卡上**自动**出现 `plan:` 附件（没有人工 `card update --attach`）；
   - 卡**自动**移进 implement 列；
   - 事件流里**没有**「裁决已落账但移列失败」的 `needs_human`。
4. **红了怎么办**：退回 v7（Task 5 的备份），把发现落卡+roadmap，不硬推。
5. 收尾：探针卡 `card close --reason 废弃`。

## 红线

- **不许为了让判据变绿去改判据**。判法错了（如⑤）在 spec 里已显式改写并说明理由；
  执行期发现的红一律如实记，退回裁决归用户。
- **不许拿真卡做 ③⑥⑫ 的异常态实验**（三张已并卡全是终态，动它们等于改写归档历史）。
- **不许动 launchd 托管的本机 agentd**（会被 KeepAlive 用旧二进制拉回来）。
