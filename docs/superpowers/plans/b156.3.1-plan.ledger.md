## 设计决定（含被否方案）

1. **run 形态而非 serve 协议形态**：四跳探针本身就是围绕 `run -s` 展开的
   （contract §1 台账⑫行原词「`run -s` resume / TUI 吃 `-s`」）；run 形态
   让假 CLI 桩测试天然可行（breakdown K1 验收指定「shell 脚本桩」），而 serve
   形态要求桩模拟 HTTP 服务（shell 做不到，违背验收形状）；会话身份由
   opencode 自家存储（隔离 HOME 内）承担，hostapi 零状态。被否：serve 协议
   驱动（复用 api.go 全套）——能力过剩且与桩测验收形状冲突。
2. **裸 exec + 进程组超时杀，不经 prochost shim**：shim 的 detached 语义与
   TaskID/MarkRoot 归属判定是执行任务形状，协调者回合借用会把伪 task 凭据
   泄进归属子系统；孤儿风险由 Timeout 上界兜底（breakdown 缺陷族 1 明文
   接受「runner 进程孤儿——hostapi.Timeout 是唯一上界」）。
3. **空 prompt 响报守卫**：F5 证明 run 形态无原生支撑；今天全部调用方
   （keystone.launchRound 简报）恒非空，出现空值即接线 bug——宁可响报也不
   造没人要的模型回合。与 keysclient.Launch 注释承诺的张力挂跨卡审计待拍板。
4. **T4 反面断言加「未实装」标记词**：变异审查发现只断言含 CLI 名会假绿
   （删掉门禁后 LookPath 报错同样含名字）；断言必须同时含「未实装」。

## 探针 P0：plan Task 3 组装形态的 argv[0] 重复问题（实装前发现并实证）

plan 原文 `exec.Command(bin, buildArgv(bin, req)...)` 且 buildArgv 首元素为 bin
→ 子进程 argv = [bin, bin, run, ...]。假桩分辨不出（"$@" 不含 $0），机内测试恒绿。
用真二进制无害探针（`run --help`，隔离 HOME）：

```
形态一 argv=[bin run --help]      → err=nil，输出 "opencode run [message..]…"（run 子命令 help）
形态二 argv=[bin bin run --help]  → err=nil，输出根 banner + 根 Commands 列表（binpath 被当未知位置参数吞掉）
```

结论：**照抄 plan 组装会在真机上打出根命令而非 `run`**，四跳必炸而桩测全绿。
修法：§二签名 `buildArgv(bin string, req TurnRequest) []string` 一字不改，
语义改为返回完整 argv，调用侧 `cmd := exec.Command(bin); cmd.Args = buildArgv(bin, req)`
（argv[0]=bin 恰一次）。偏离理由与证据如上。
