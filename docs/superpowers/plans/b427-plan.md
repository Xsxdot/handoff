## 边界、现状与权限

代码范围以 `web/src/app/cards/CardsPage.tsx`、`CardDrawer.tsx`、`web/src/app/shell/Shell.tsx` 及其生产数据 hook 与相应测试为主。根据实际实现可做这些范围内的局部类型/数据注入调整；任务轮询的启停调整须保留所有既有消费者缺省行为。`web/src/api/ledger.ts` 的既有 fetch 契约可以复用，不新增端点或更改响应 wire。

基线事实与行号在 spec「问题与现状」列明；先核对再写测试。图覆盖债见 spec。B426 S1/S3/S4 已在此基线，所有工作须保留其双端状态 chip、移动头部、抽屉筛选与队列行为。Shell 的桌面 `/cards` 独立路由与移动条件挂载都要区分，不能仅把独立页数据 hook 删除。

承接基线已有一项测试形态漂移：`Shell.test.tsx:1609` 移动项目工作项导航用例仍在列表主面找项目 combobox；B426 S4 已将该筛选移至详情。更新断言时须进入详情读取项目筛选并继续验证实际过滤，不能删除行为断言或回退生产形态。协调者已跑基线结果为 198 passed / 1 failed，见台账。

执行者可选择最小的内部状态表示、请求取消与注入形式。改变用户结果、数据来源权威、历史范围语义、后台生命周期或 wire 契约须先升级给协调者。不得因本机接口快就宣布手机问题解决。

## Task 1：先锁住请求范围，再修当前详情与终态深链（S2、S3）

1. 在真实 CardsPage/Drawer 生产组件测试中，走移动卡点击→URL→抽屉→关闭；fetch 边界断言普通点卡不拉 `all=1`。先保留基线失败输出，失败应指向隐式范围扩张。
2. 增加不在现役列表的终态深链反例：单卡详情能呈现目标 ID、关闭后现役列表仍可见；404 展示错误，切到另一 ID 不留旧目标。显式历史开关与桌面普通点击作回归。
3. 去掉卡 URL 作为列表历史范围开关；复用既有单卡详情路径恢复深链。尽量复用 Drawer 已有详情请求，若父页需目标卡元数据，应检查避免同一恢复链无谓重复取目标详情。
4. 添加意图注释：深链为什么不改变列表范围、为什么按 ID 恢复终态卡。采用已有结构化日志风格记录详情恢复的目标、范围、成功/失败；不输出凭据、整卡内容或每次渲染日志。
5. 运行 CardsPage/CardDrawer 触及范围测试，将红→绿与请求证据落台账。

## Task 2：移动工作项消费 Shell 数据（S1、S5）

1. 在真实 Shell→CardsPage 组件链测试进入工作项、切回会话、再次进入：用已有 fetch 边界区分每种请求，证明现役卡/决策/任务只由一个生产来源维护。不能 mock 掉 CardsPage 后声称生产消费成立。
2. 为移动挂载点注入已有卡、决策、任务的结果与刷新/错误状态，抑制被取代的本地首拉与周期轮询；独立路由缺省仍加载自身数据。不得依靠延长定时器掩盖两条流。
3. 验证未完成首拉、已有快照、401、网络断线与恢复；数据来源切换后的旧请求不能污染新来源。共享刷新与卡操作后的刷新仍能更新可见列表。
4. 注释明确移动消费的权威来源与独立页缺省行为。日志在来源选择、刷新失败/恢复等关键点记录 source/loading/stale/status；避免为轮询成功的每次渲染新增高频日志。
5. 运行 Shell、CardsPage、触及数据 hook 测试，保留 B426 已有形态断言。记录请求反例与修复后 DOM 结果。

## Task 3：钉版本工作流逐项缓存（S4、S5）

1. 用真实 CardsPage 请求入口安排至少一个成功版本与一个 404，先锁住失败版本造成成功结果丢失、后续轮询重取的现状。
2. 各版本独立保存成功结果；同作用域内保存已知 404，成功项和缺失项不随每次卡轮询反复请求。暂时网络失败仍保留可恢复路径，不永久当成不存在。
3. 请求处理中版本集合变更、组件卸载、数据来源切换都不得造成迟到结果串入新状态。按来源隔离失效记录，保持成功钉版本参与看板和筛选；未知版本沿用现有降级语义。
4. 注释解释逐项结算与 404/暂时失败区分；结构化日志记录工作流名、版本、结果类别与状态，不打印整批响应。
5. 运行工作流部分失败、重复轮询、来源切换与恢复反例，并记录红→绿。无需新增通用缓存层或持久化缓存。

## Task 4：全量检查与真实手机验收（S1–S5）

1. 先完成触及范围测试；在 `web/` 运行 `npm run typecheck`、`npm test`、`npm run build`，记录每条实际退出结果与测试总计。未跑到结果不能写通过。
2. 确认受管运行时及代码部署版本；浏览器/手机运行入口按 SuperDev 接管状态推进。当前 57017 不可达且 `adb devices -l` 列表为空，只说明当前调试/设备入口限制，不推出应用故障。受管服务不可用时明确记录，不能擅自另起服务替代受管验证；继续完成实现、构建与独立审阅等已授权工作，不将等待设备变成停止这些工作的理由。
3. 同一真实手机/同一服务入口复测列表首次、点开当前卡、返回再进入和终态深链；记录网络等待、响应范围、可见 DOM 完成时间与服务 SHA。与修改前相同环境证据比较，无修改前手机证据时如实写明。
4. 检查数据源只有一套卡/决策/任务流、点卡无隐式全历史请求、缺失版本不按卡轮询重取；检查 B426 形态及桌面普通路径回归。保存请求日志/截图等可审阅证据。
5. 台账说明自动化、本机 API、模拟视口与真实手机分别验证了什么。若缺真实手机证据，交给 review 的结论为「代码阶段待审，手机性能验收未完成」，不能把 B427 标作最终通过。
