## 1. 交付目标

交付 S1-U2 的 `/api/cards` 远端未挂账摘要状态和 Web 消费：本地卡片账本数据先返回，远端摘要只由已缓存观测组成，刷新在后台进行；摘要能区分 `latest`、`partial`、`stale`、`unavailable`。只有 30 秒内完整观测可作为当前数量、dock 角标与未挂账筛选。部分/陈旧观测可以查看并说明未知或观测时间，但不得伪装成完整当前值。`unavailable` 与合法的最新空结果必须明显不同。

本工作单元不宣称 S1 完成，不验收 U1/U3 的账本工单读面，也不宣称父故事 B409 或 p95 ≤2s 性能目标完成。S1 的真实 agentd + Codex 内置浏览器演示及最终回归由协调者在集成/验收负责。

## 2. 改动边界与真实生产链

### 生产链和现状

- 后端：`GET /api/cards` 在 `internal/agentd/ledgerapi.go#Server.registerLedgerRoutes` 注册，经 `withLedger` 到 `Server.handleCardsList`；先取本地 `ListCards`、U1 `OpenTicketCounts` 和已有本地徽标，再组装 `unlinked` 并 `writeJSON`。当前生产链为 `handleCardsList → unlinkedSummary → Store.AllTaskLinks → projectTaskLinks("")`；`projectTaskLinks("")` 除读取 `card_tasks` 外，还扫描 `card_events` 中全局 `EvDispatched` 历史以投影 Node/Attempt，而 `/api/cards` 实际只用结果中的 Target/TaskID 构造 linked key 集合。随后 handler 对每个配置 target 调用 `pool.For`/`ListTasks`（单 target 2 秒超时），远端调用完成前不会写响应。该全局事件投影是本读路径的无关历史读取；仅加 context/deadline 会把随账本增长的工作藏到后台，并不能消除根因。缓存窗口是 30 秒，但现有 JSON 只有 `count/tasks/unknown_targets`，没有状态和观测时间。
- Web：`web/src/api/ledger.ts#fetchCards` 读取 `/api/cards` 并声明 `UnlinkedSummary`；`CardsPage` 的 `cardsPoll` 周期请求并渲染 `UnlinkedRow`；`Shell` 的 `cardsState` 把结果转换为 `unlinkedTaskIds`，交给 dock 角标以及 `BoardOverlay`/`BoardPage`；`web/src/app/board/columns.ts#unlinkedOnly` 在集合为 `null` 时不过滤。
- 冻结契约逐键要求 `unlinked` 保留 `count/tasks/unknown_targets`，新增 `status/observed_at`；所有列表字段保持数组、`count === tasks.length`；`unavailable.observed_at` 为 JSON `null`；超过 30 秒后仍保留并显示最后观测，没有 5 分钟隐藏上限。不可达目标不能被折成完整零结果。

### 允许触及

- `internal/agentd/ledgerapi.go`：`handleCardsList`、`unlinkedSummary` 与其私有摘要状态/组装。远端刷新需异步、单飞；请求内只读缓存快照并安排刷新，不可持有摘要锁拨号 target。保留 `targetclient.Pool` 的鉴权、请求校验和现有单 target 超时。摘要仅是本地账本主数据的附加信息；`ListCards` 的失败照旧返回账本错误。
- `internal/agentd/server.go`：仅调整/增加 `Server` 上未挂账摘要缓存、更新时间、单飞/停止状态与私有 refresh context/cancel/WaitGroup；将 `CloseTargets` 作为现有关停收口点，停止新刷新、取消并等待在途刷新后再关闭 Pool。`NewServer` 当前没有通用生命周期 context；真实调用序列是 `cmd/agentd.go` 的 `Serve → GracefulShutdownCleanup(wdCancel) → CloseTargets`，本卡不新增公开 setter 或改 `cmd/agentd.go`。

- `internal/ledger/tasks_test.go`、`internal/ledger/store_pg_test.go`：覆盖新增 key-only context-aware 读取、取消路径，以及固定 linked key 集合下增加大量无关 `EvDispatched` 历史时数据库实际返回 rows/列值 payload bytes 的增长验证。用隔离 PostgreSQL 的真实 Store/driver 读路径和测试专用读结果探针，比较无关历史增长前后的实际返回行数与 payload 字节；不能用 SQL 文本、方法返回 JSON 长度或 mock 调用次数替代。若计划集审计发现其它工作单元也要依赖该新增读面，再冻结共享 seam contract 后共同使用。

## 3. 工作顺序与承重假设

1. **复核依赖与基线。** 在批准执行分支确认 U1 的 `OpenTicketCounts` 实现与现有每卡输出兼容，复读 B409 r2、contract v1、breakdown §U2；核对当前 `registerLedgerRoutes`、handler、摘要缓存字段、Web 类型与消费链。未经计划集审计或 U1 集成，不开始实现。
2. **先锁住 handler 的非阻塞边界、限域 Store 读与 worker 生命周期。** 将响应中的远端摘要改为快速读取最近缓存快照；在没有观测或观测超过刷新窗口时只安排一次后台刷新，所有请求都不等待 target，也不把 request context 传给后台 worker。刷新在锁外用同一个 refresh context 调新的 link-key Store read 与 targets。该读面只取得 linked 集合必需的 Target/TaskID 键，不进入 `projectTaskLinks("")`，不读全局 `card_events/EvDispatched` 历史；若实现选择不同的限域路径，必须由 schema/查询证据和增长测试证明实际返回数据只随所需链接键规模变化。对整个刷新（限域本地链接键读取 + target fanout）设固定 **2 秒总 deadline**；每个 target 仍保持现有最多 2 秒的调用上限，并使用受限并发 fanout，避免顺序等待将 `N×2s` 累加。总 deadline/Server cancel 到期后所有尚未完成的 SQL/target 请求都要收到取消；已成功目标保留，未成功或未能在 deadline 前查询的目标列入 `unknown_targets`。超时导致至少一台未知时发布 `partial`（有成功观测）或 `unavailable`（从未有任何成功观测），不冒充 latest 零；本地链接键读取被取消/失败时不发布部分完成的摘要、不把链接集合替换为空，并保留上次可读快照作为历史状态。无 target 配置时可直接形成 `latest` 空观测。
3. **建立无竞态的 Server 关停门。** `NewServer` 初始化私有刷新 context。一个与 `unlinkedRefreshing`、`unlinkedStopping` 同一把锁保护的启动入口负责检查未关闭、置单飞状态并在解锁前执行 `WaitGroup.Add(1)`；已标记 stopping 后不得再启动 goroutine。`CloseTargets` 在同一把锁下标记 stopping 并 cancel refresh context，解锁后等待已登记的 worker 退出，再调用幂等的 `Pool.Close`；不得让 `Wait` 与未同步的 `Add` 并发。重复 `CloseTargets` 安全返回，不复活刷新任务。整个刷新共享的 2 秒 context 必须覆盖新的 key-only Store 查询与 target fanout，确保停止时可取消并有限收敛；worker 不得依赖 `r.Context()`，也不得持有摘要锁等待 SQL/网络。
4. **逐状态实现冻结金样。** `latest` = 当前刷新覆盖全部配置 target 且年龄 `<=30s`；`partial` = 至少有成功 target 观测、同时按名称列出失败 target，`tasks/count` 只含成功子集；`stale` = 最后一份完整或部分观测年龄 `>30s`，完整保留其 tasks/count/unknown_targets/observed_at，后台刷新失败不清空历史；`unavailable` = 当前没有任何可用 target 观测，返回 `count:0`、`tasks:[]`、`observed_at:null`，并让未知 target 保持可见。所有成功且无配置 target 是 `latest` 零值，不是 unavailable。观测时间用 UTC RFC3339；`count` 始终等于数组长度。年龄恰好 30 秒仍可 latest/partial，超过即 stale。
5. **贯通 Web 消费，不让历史子集成为筛选事实。** `UnlinkedSummary` 类型增加受限状态联合和可空 `observed_at`；缺字段、未知状态按 `unavailable` 处理。`UnlinkedRow`：latest 显示当前数量；partial 显示“部分观测”和未知 target；stale 显示上次数量、时间和年龄且持续可见（包括超过 5 分钟）；unavailable 显示尚无摘要/未知，不得显示成合法 0。只有 latest 可生成 `unlinkedTaskIds`；其余状态传 `null`，使 `unlinkedOnly` 原样返回 tasks，dock 不拿部分/陈旧子集显示当前角标。
6. **交付证据。** 执行者给出实际命令与结果、Go handler JSON 样例、UI 状态到 badge/filter 的链路断言、远端慢/失败 target 的耗时边界，然后交独立 review。执行者不跑真实生产部署、不改卡状态；真实 agentd + 内置浏览器验收由协调者集成时执行。

## 4. 验收断言与阻塞

### 后端与 JSON

- 通过真实 `GET /api/cards` JSON 序列化边界逐键断言四种状态；`status`、`observed_at`、`count`、`tasks`、`unknown_targets` 均按 contract 输出。特别断言 `null` 时间与空数组/零值不同；`count === tasks.length`；JSON 不把数组输出为 null。
- 覆盖完整非空、全部成功合法空（无 target）、部分成功含具体失败 target、从未观测且不可达、30 秒边界和超时后 stale。老快照遇到 refresh 失败不能被清空或当作当前值；新增 link-key 读取失败不能变成全量未挂账的 false latest。
- 承重反例：使用受控慢 target 暂停 `ListTasks`，`/api/cards` 仍快速返回本地卡片且后续请求也不被摘要锁串行卡住；释放 target 后下一轮轮询能看到已刷新状态。测试还要证明并发请求不会重复风暴刷新。超时/失败通过既有 Pool 路径归入 unknown，不绕过认证。该延迟测试证明 handler 不等远端，不代替 S1 全矩阵 p95。
- request context 与 worker 解耦：启动一次受控 refresh 后取消原 HTTP 请求，target 请求仍由 Server refresh context 管理并可完成缓存发布；后续请求能读到结果。相反，在 Server close 时取消 refresh context，阻塞 target 观察到取消并退出，`CloseTargets` 等到已登记 worker 收敛后才关闭 Pool。
- 并发/关停竞态：并发 GET 只产生一个 refresh；测试并发触发刷新与 `CloseTargets`，确认 stopping 一旦置位就没有新的 `WaitGroup.Add`/worker 启动、没有 Wait/Add race，所有已启动 worker 均被取消并收敛；重复调用 `CloseTargets` 无错误且不重启工作。
- 总时限反例：一台 target 即时成功、另一台持续阻塞直到 context deadline；整个 fanout 不超过 2 秒总预算（测试允许调度容差），即使前一 target 慢也不把多台各自 2 秒顺序相加。deadline 到来后成功观测保留为 partial，未完成 target 明确 unknown；不可用时为 unavailable，不能返回合法空 latest。
- 限域 Store 读与增长反例：新增 link-key read 在 context 已取消时返回 cancellation error，SQL 读尊重 refresh context；它不调用 `projectTaskLinks`，也不获取 `EvDispatched` 的事件行。固定同一组 `card_tasks` 链接键，在隔离 PostgreSQL 中将无关 dispatched 事件从小基线扩增到至少 10,000 条后，通过真实 Store/driver 读结果边界的测试专用探针统计数据库实际返回 rows 与列值 payload bytes；两项均须受所需 link-key 集合约束，不得随无关事件数量线性增长。测试还需断言新方法得到的 Target/TaskID 键集合与旧 `AllTaskLinks()` 结果投影出的键集合相等。另在 PostgreSQL 持有相关读面所需表的排他锁时启动读取、取消 refresh ctx，断言 handler/`CloseTargets` 在总期限内收敛；具体锁定对象由实施者按最终读面核实，不预设未验证 SQL。不得只测试 target 超时而留下 SQL 读无法取消的路径。

### Web 与端到端串接

- 使用与 Go JSON 金样字段一致的真实 JSON 响应穿过 `fetchCards` 的 JSON 解码，再由卡片摘要消费；UI 断言 latest、partial、stale、unavailable、旧 agentd 缺字段、未知枚举各自显示正确。陈旧观测大于 5 分钟仍显示历史值和时间；不可用状态不得被当成数值 0。
- `Shell` 消费端断言只有 latest 可产生 task ID 集、dock 当前角标与过滤集合；partial/stale/unavailable/missing/unknown 均交付 null，且 `unlinkedOnly(..., null)` 保留全部输入 task。latest 空集合可正确表示“已确认无未挂账任务”。
- 用例要穿过 Go wire JSON → `fetchCards` → `UnlinkedSummary` → `CardsPage` 状态行以及 `Shell` → `BoardPage/unlinkedOnly` 的生产消费接缝；Go 和 TS 各自孤立单测不算全链证据。最终真实 agentd + Codex 内置浏览器验收由协调者完成；jsdom 不代替该验收。
- 定向验证由 implement 执行者依 charter implement 三段律完成：Go handler 测试、对应 Vitest 文件；记录新增/失败/跳过。全量 Go/Web 与真实集成回归由集成/验收阶段负责。B409 全增长矩阵、端到端 p95 ≤2s、linux-01/本机部署也归最终协调者，不可在 U2 结果中宣称已通过。

## 5. 决策权限与回退条件

执行者可在本卡内部选择私有缓存类型、锁粒度、受限并发 fanout，以及在不读取全局 dispatched 历史的前提下取得 link-key 集合的具体 Store 查询实现；需保持一份摘要刷新单飞、固定 2 秒整批刷新 deadline（含 context-aware Store 读）、逐 target 最多 2 秒、独立于 HTTP request 的取消、Server 停止门与 `CloseTargets` join、无远端 I/O 在 HTTP 请求关键路径、缓存状态可确定地映射冻结 contract。新增 context-aware key-only Store 方法是本卡供唯一 U2 消费者使用的 additive 读面；旧 `AllTaskLinks()` 与 `projectTaskLinks` 保持原兼容语义，不增 public wire DTO/endpoint。

**U4/U5 seam 核对**：已检查当前 [`B409.4 plan`](2026-09-25-b409-4-plan.md) 与 [`B409.5 plan`](2026-09-25-b409-5-plan.md)：两者分别规划的 LedgerClient scoped reads 与本卡 Store link-key read 不同，现稿未要求复用本卡新增方法，因此当前不加跨卡 contract。计划集独立审计时必须复核最新稿及 B409.1 的 seam；若发现其它工作单元需要共同依赖此 Store read，则先冻结最小共享 contract 再允许跨卡消费，不能复制实现或无契约依赖。

以下情况阻塞 U2 并交协调者处理：U1 未完成或读面接口不兼容；实现需修改 `b409-contract.md` 的字段/状态/30 秒/陈旧展示语义；target Pool 无法在保持既有鉴权、校验与 per-target timeout 的情况下刷新；新增 key-only Store 查询不能取消并通过有限关停断言，或无法证明数据库实际返回 rows/bytes 不随无关 `EvDispatched` 历史线性增长；或 UI 结构无法安全 fail-closed。不要私自调整状态名、期限、目标授权、local cards 主结果或用户可见 JSON。

**L3 计划集门禁**：本计划完成不授权 implement 派发。须等 B409.1–B409.7 计划齐稿后，由非计划作者的独立上下文按 `charter:plan` 审计全部计划的共同契约/生产边界、依赖与验收归属并通过；如需修改计划，修订后重审。门禁通过且协调者明确派发前，所有 B409 子卡保持 plan 节点。U2 implement 完成后由独立 reviewer 按本计划、r2 与 contract v1 做双轴 review；父卡 S1 最终集成与真实浏览器验收由协调者负责。
