# B399 spec：唤醒回合的上界、续接与增量简报

**上游状态：已批准**（用户 2026-09-22 批准；同日拍板三处改动）
**级别：L2 单子系统**（`internal/agentd` 的回合上界与 ctx + `internal/keystone` 的续接/重建判据与简报；先例：B393「`internal/agentd` + `internal/keystone`」同形）
**入口节点**：debug（现场取证已完成，见卡上 2026-09-22 三段）；本节点只出 spec，不动实现

---

## 1. 问题陈述

重上下文卡的唤醒回合**必然撞界**，而撞界后的退化链把「被杀一轮」升级成「唤醒永远失败」。

现状读数（`9b7f855b`）：

- 唤醒回合的挂钟上界由驱动租约派生：`coordWakeTurnTimeout = ledger.DriverLeaseTTL / 2`（`internal/agentd/server.go:1182`，用于 `readyCtx`，`:1189-1194`）⇒ **2m30s**。
- 真机（B382，卡上有 190+ 事件）：19:02:57 回合开始 → 19:04:04 `resume` 相位撞界被杀（日志：`已终止进程树: context deadline exceeded`）→ 自动走「重建」相位 → 同样撞界 → 19:07:57 整轮报失败、落 `needs_human`。**三个相位没有一个能在 2m30s 内收口**——光判断「该续接还是该重建」就用掉约 5 分钟（用户 2026-09-22 观察）。
- 退化的原因还在于**错误不分流**：`keystone.Wake`（`internal/keystone/keystone.go:151,157`）把**任何** resume 错误都交给 `rebuildAfterResumeFailure`（`:160`）⇒ 重建（`Launch` 新会话）；超时本不是「会话不在」，却因此丢掉会话、并且再被同样时限杀掉，最终落「resume 与重建均不可用」。
- 简报把「读卡」写成了开场指令：`briefing`（`internal/keystone/keystone.go:322-329`）首句是「醒来第一件事：读卡、查依赖、看基线新鲜度」——对重上下文卡，这等于每轮都从零把整张卡读一遍。
- 可见性不对称：成功路径写「唤醒回合开始/结束」两行，**失败路径只写失败行**（真机三次失败均无 end 行）。

后果：卡越重（事件越多）越唤不动——唤醒链在最需要它的卡上最先失效。

## 2. 级别与档位

**L2 单子系统**：改动落在 `internal/agentd`（回合上界与 ctx）与 `internal/keystone`（续接/重建判据、简报），不新增子系统、不新增依赖方向、不改任何 wire 契约。

## 3. 方案（含弃选与理由）

**采用（用户 2026-09-22 拍板，三处改动都在现有唤醒回合内）：**

1. **墙钟改用 hostapi 既有上界（30 分钟）**：唤醒回合不再由 `DriverLeaseTTL` 派生上界。
   事实依据：驱动租约**本身可续租**——`DriverLeaseRenewInterval = 2m` < `DriverLeaseTTL = 5m`（`internal/ledger/binding.go:22-27`，常量注释即「生产续租 goroutine 的默认节拍」）。所以「回合超过 5 分钟就越过租约语义」不成立：席位由续租保证，回合可以更长。
   **边界不变**：仍有上限（30 分钟），**不回到无界挂死**（B393 的红线：有界退出必须保留）。
2. **超时后仍续接同一 session**：resume 错误必须分流——「回合超时」≠「会话不在」；只有 stderr 里真正的 `Session not found`（`internal/hostapi/driver.go:160-164` 的判据注释即为此留的通道）才降级到 `Launch`（重建）。超时则**保留会话**，下一轮仍 resume 同一个 session，从上一轮停下的地方继续。
3. **简报只带增量**：删掉「醒来第一件事：读卡」这类开场指令；简报只带本卡最小指针（卡号、标题、基线）**与本次唤醒事件**。会话里已有的上下文留在会话里，账本只补充增量。

**失败收口（兜底，用户原话「那种情况用失败收口就够了」）**：仍不收敛的回合——到点杀进程、**会话保留**、**恰一次**落「需要人」、下一轮仍续接同一 session；并补上失败路径的「唤醒回合结束」行，使 start/end 对称、可按 round_id 对账。

**弃选：A（把唤醒拆成「只做决定」，重活交给派发节点）**——用户裁定不适合本卡，理由三条：① 那等于把一次超时扩成一套新工作流（哪些算重活、派给谁、产出怎么回到下一轮唤醒，都得另写）；② 协调者这一轮本来就在「读、想、决定要不要点火」，**这个决定本身就会超过两分半**（本轮真机实测：判断「该续接还是该重建」用了约五分钟，尚未动手改任何东西）；③ 两分半连一次判断都包不住，禁止在唤醒里思考是舍本逐末。
**弃选：重写租约语义**——不必要（续租机制已存在且够用）。

## 4. 用户故事

1. 作为卡协调者，我在一次唤醒里能读完卡、想清该做什么、点火，而不会在中途被 2m30s 砍掉。
2. 作为接管者，当一轮被时限终止时，**我的会话还在**，下一轮从上次停下的地方继续，而不是被迫换新会话重讲一遍上下文。
3. 作为排障者，我能从日志区分「这轮被时限终止」与「会话不存在」——两者走不同的退化路径。
4. 作为审阅者，我能看到失败轮也写 end 行，start/end 对称、按 round_id 可对账。
5. 作为后来者，我读到「恰一次落需要人」的收口，不会看到同一失败被重复刷屏。

## 5. 实现决定

- **上界来源唯一**：唤醒回合的挂钟上界取 hostapi 既有缺省（30 分钟），不再由 `DriverLeaseTTL` 派生；席位占用由既有续租机制保证，不引入新租约语义。
- **错误分流是契约**：resume 结果分三类——① **被时限终止**：会话保留、本轮收口、下轮续接同一 session；② **会话不存在**（stderr 含 `Session not found`）：降级 `Launch` 重建；③ 其他：维持既有语义，但判据必须显式（不得再用「任意错误 ⇒ 重建」兜住）。
- **失败收口恰一次**：同一失败在同一轮只落一条「需要人」；失败路径补「唤醒回合结束」行（含 round_id 与失败分类）。
- **简报瘦身**：只在简报里给卡的最小指针 + 本轮事件；不指示模型「先读卡」——是否读卡由协调者自己判断（上下文已在会话里）。
- **不动**：租约/续租语义、`Launch` 的语义、唤醒映射（`automationWakeEvent`）、派发与路由。

## 6. 测试决定（接缝清单）

**接缝 1（承重缝）**：唤醒回合的上界与错误分流——`internal/agentd` 的回合 ctx（现状 `server.go:1189-1194 readyCtx`）+ `internal/keystone` 的 `Wake`/`rebuildAfterResumeFailure`（现状 `keystone.go:151,157,160`）。
调用方（现状）：消费轮（`internal/agentd/wakeconsumer.go`）与转交唤醒端点（`internal/agentd/coordapi.go:48` 路由 → `handleCoordWake`）。
断言：① 上界 == hostapi 缺省（30 分钟），不再等于 `DriverLeaseTTL/2`；② 注入「被时限终止」的 resume 错误 ⇒ **不**调用 `Launch`、会话保留、下一轮仍以同一 session 调 resume；③ 注入含 `Session not found` 的错误 ⇒ 调用 `Launch`。

**接缝 2**：简报生成——`internal/keystone` 的 `briefing`（现状 `keystone.go:322-342`），调用方 `Wake`。
断言：① 简报不含「读卡」类开场指令；② 含本轮唤醒事件清单与卡最小指针；③ 会话已有上下文不被重复塞入。

**接缝 3（可见性与收口对称）**：唤醒回合收尾路径（失败出口）。调用方：`wakeCoordinatorRoundID` 的失败分支与 `keystone` 的收口。
断言：① 失败轮写「唤醒回合结束」行且带 round_id；② 同一失败只落一条「需要人」；③ 失败分类（超时/会话不存在/其他）在日志与账本上可区分。

**回归与改写**：B393 带入的既有测试（`internal/agentd/b393_timeout_test.go` 的 `TestB393ResumeHangsBoundedByTimeout`、`internal/hostapi/b393_timeout_bound_test.go`）按新语义**改写**——红线保留「有界退出、不永挂」，改的是「被界砍掉之后不许把会话丢掉、不许无脑重建」。

**假缝禁令核对**：三条缝都在生产路径上、都有真实调用方；无「未导出、无生产调用方」的纯函数占名额。

## 7. Out of Scope

- **不做 A**（拆小唤醒回合 / 重活改派发节点）——用户 2026-09-22 裁定，理由见 §3。
- **不做**：租约语义与续租机制的重写；`Launch` 语义变更；唤醒映射变更；派发/路由变更。
- **拆出本卡**：**唤醒失败期间账本对客户端不可用数分钟**（现象已证：两台机器 CLI 卡死数分钟、agentd HTTP 秒回、重启 agentd 无效；CLI 直连账本 ⇒ 属 DB 侧）。机制未定位（曾误判连接池=1 已更正），另立卡处理，本卡不动。
- **本期不做、后续要做**：协调者回合的**成本**观测（每轮 token/时长/动作数），用于判断「30 分钟是否够」与后续调参；残余落 roadmap。
