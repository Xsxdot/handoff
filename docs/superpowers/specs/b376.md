## 问题陈述

谁：执行机上的权限门（静态白名单 + 廉价审批者 + 人工升级）。

条件：linux-01 近 14 天 `approver_decision` 1690 次（放行 1069 / 升级 509 / 出错 112）；本机审批几乎闲置。白名单已经吃掉单段 `go test` / `grep` / `git status|diff|log`（同期 `permission_auto_allow` 701）。仍进审批的大宗是「白名单命令被包了一层」：`cd <dir> && …`（391）、白名单命令 `| head/tail/grep`（约 140）、分号串（61），以及产品已点名但表上还没有的 `rg` / `codegraph` 查询 / 只读 git 查看补全。

通道：既有 `Gate.Judge` → AutoAllow 静默 / Consult 交审批者 / Escalate 叫人。审批者今天是执行机 `config.yaml` 的单值 `approver.executor`。

要变的事实：

1. **复合只读可以静默。** `&&` / `||` / `;` 本身不是风险。拆成段后每一段都能证明只读、且无写重定向、无管道进写工具 → 整条静默。不能证明则**整条** Consult，不做半段放行。
2. **白名单仍只认单段。** 禁止把整串 `a && b` 塞进白名单表。复合只多一层「拆段 + 全静默」。
3. **审批失败可观测，failover 后才叫人。** `approver.executor` 改为有序多选；第一个不可用/失败试下一个；全部失败才 Escalate。禁止「连升三次后无声停」——跳闸必须留下 `approver_disabled`，之后升级工单的理由必须点名停用，不得再写成「黑名单未命中」。

谁能观察到：`grep a && grep b`、`cd dir && rg x`、`ls | head`、`sed -n '1,20p' f; echo "=== x"` 零审批卡；`grep a && rm x`、`echo x > f` 不得静默；白名单外只读走出 `approver_decision` 而不是直接叫人；审批者全挂时协调者看到的是带停用原因的升级卡。

## 方案

### 第 1 条：拆段静默（政策）

**选定：白名单继续只认单段；在 `judgeBash` 里、既有黑名单/自指令/越界判定之后，对仍为 Consult 的命令做「按 `&&` `||` `;` 拆段 + 每段可静默」一层。**

一段可静默，当且仅当：

1. 命中单段白名单（含本卡补的条目）；或
2. 该段是 `cd`（可带一个路径）；或
3. 该段含管道，但**每一级**都是可静默命令，且最后一级不是写工具（`tee`），且没有非丢弃写重定向。

`2>/dev/null`、`2>&1`、stdout 丢到 `/dev/null` 不算写重定向。

整条静默当且仅当所有段可静默。任一未知段、写重定向、管道进写工具 → **整条 Consult**。不因连接符 Escalate。

**本卡补进单段白名单的形态**（产品已点名 + 2026-09-17 用户批准的补洞）：

| 形态 | 约束 |
|---|---|
| `rg` | 只读检索；与 `grep` 同档 |
| `codegraph` 查询/读图 | 子命令闭集：`sym` / `who-calls` / `chain` / `flow` / `tree` / `context` / `entity` / `domains` / `check` / `validate` / `summary`，以及 `--help` / `--version` / 无子命令。未知子命令 → Consult |
| 只读 git 补全 | 现有九个之外加 `branch`（出现 `-d/-D/-m/-c/-C/--delete/--move/--copy/--force` → 非只读，Consult）、`merge-base`、`ls-tree`、`rev-list` |
| `sed -n` | 必须有 `-n`，且无 `-i` / `--in-place` |
| `npm --prefix <dir> test\|run` | `--prefix` 插在 `npm` 与 `test`/`run` 之间也要命中；`ci`/`install` 仍非静默 |
| `cd <path>` | 仅作静默段，让后面的只读段能带上工作目录 |
| `echo` / `printf` | **无重定向**才静默。现场大宗是 `sed -n …; echo "=== 标签"; sed -n …`——拆 `;` 后 `echo` 自己是一段，不收就整条 Consult。`echo x > file` / `printf … > file` 是写，不静默 |

既有单段（`go test`、`grep`、`git status` 等）与 ledger amend 不变。

**弃选：把整串 `a && b` 写进白名单表。** 表会随连接符爆炸，且与「白名单只认单段」冲突。

**弃选：半段放行。** 产品已禁；`grep a && rm x` 整条 Consult。

### 第 2 条：审批者 failover（执行机配置）

**选定：`approver.executor` 从单值改为有序多选；配置在执行机本机 `config.yaml`，不在协调者 Mac。**

- YAML 标量 `"codex"` 与序列 `[codex, grok]` 都合法；空=关闭（与今天一致）。
- 一次权限请求内：按序调用；某个候选 **不可用或 Decide 返回 Err** 才试下一个。候选给出干净 approve / 干净 escalate → 停，不再试下一个。
- 全部候选都 Err → 本请求 Escalate，并写 `approver_decision`（看得到试过谁、各失败原因）。
- 一次请求里 failover 用尽仍失败，计 **1 次**请求级失败，不是每个候选各计 1。连续 3 次请求级失败才跳闸（样本量含义与今天 `maxApproverFails` 相同）。
- 每个候选用自己的 `env.For(名字)`。共用一个 `approver.model`；空=该执行者自己的默认。不为每个候选单独配模型。
- `handoff init` 仍问一个审批者（列表长度 0 或 1）。多选用手改 yaml。

**弃选：候选失败也算模型干净 escalate 再试下一个。** 模型明确「升级」是职权，不是故障。

### 第 3 条：失败可观测

**选定：不改 wait 假集合；把「停用」写进升级理由。**

- 每次候选尝试都落 `approver_decision`，payload 能看出 `executor` 与 `decision`（approve / escalate / error）。
- 跳闸仍写一次 `approver_disabled`（今天就有）。
- 停用之后的 Escalate，工单/事件理由必须带「审批链已停用（连续 N 次失败）」——禁止再回落「黑名单未命中」。
- wait 继续不因 `approver_decision` / `approver_disabled` 叫醒（B233.1）。当次失败本身已经 Escalate 成 `permission_request`，协调者会被叫醒；show 能对质审计事件。

**弃选：把 `approver_disabled` 改成 wait 可交付。** 会碰冻结的假集合，且当次已经有升级卡。

## 用户故事

1. `grep a && grep b`、`cd src && rg foo`、`git status && git branch --show-current && git rev-parse HEAD`、`ls \| head`、`sed -n '1,20p' file`、`sed -n '219,300p' f; echo "=== cursor"`、`codegraph sym Gate.Judge`、`npm --prefix web test` —— **零审批卡**，事件流可有 `permission_auto_allow`。工单全文里的 `bash:` 只是工具名，判据吃的是命令本体。
2. `grep a && rm x`、`git branch -d topic`、`sed -i`、`ls \| tee out`、`echo x > file` —— **不得静默**；只读段不能把写段带过门。
3. 白名单外的只读（如 `find`、`python3 -c 'print(1)'`）—— 走审批者，事件流有 `approver_decision`，不直接出协调者卡（审批者干净 escalate 除外）。
4. 执行机配 `approver.executor: [codex, grok]`。codex 超时/不在 → grok 接着裁；两边都挂 → 升级卡，理由列得出试过谁。
5. 审批者连续三次请求级失败后停用：下一条权限的升级卡理由点名停用；`handoff show` 看得到 `approver_disabled`。不是无声停。

## 实现决定

- 拆段只服务静默判定，落在 `Gate.Judge` / `judgeBash` 一侧；Consult/Escalate 出口语义不变。
- 配置兼容用自定义反序列化，不要另起键名。
- failover 收在审批者入口内部，调用方仍是一次 Decide。
- 不改执行器上报形态（不剥 `/bin/bash -lc` 外壳做静默匹配）。近 14 天 linux 此形态为 0。
- `bash:` / `Bash:` 是工具名（`NormalizePermTool`），判据只看 `PermRequest.Command`，不把前缀当命令正文。
