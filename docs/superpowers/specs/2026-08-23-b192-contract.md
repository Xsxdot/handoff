### 1.1 依赖与既成行为

- `internal/agentd/workspace.go:820` 的 `FetchTimeout` 为 `2 * time.Minute`；`ResolveBaseBranch` 在 `internal/agentd/workspace.go:1098-1101` 用 `context.WithTimeout(ctx, FetchTimeout)` 包住 `git fetch`。本契约不改时限；本地工作分支路径不得创建该网络操作。
- `internal/agentd/server.go:1124` 用 `json.NewDecoder(io.LimitReader(r.Body, 4<<20))`，派发请求体读取上限为 4 MiB；新增一个布尔键不改变上限。
- 当前客户端 `internal/client/client.go:254-267` 构造的 `http.Client` 未设置 `Timeout`；Go 1.26 标准库 `net/http.Client.Timeout` 的定义（`/usr/local/go/src/net/http/client.go:90-105`）规定零值为无超时，实际取消依赖 `NewRequestWithContext`（`internal/client/client.go:409`）传入的 context。新字段不引入第二套超时。
- Go 标准库 `encoding/json.Decoder` 默认不拒绝未知对象字段（`/usr/local/go/src/encoding/json/stream.go:41-44` 只有显式调用 `DisallowUnknownFields` 才打开拒绝）。因此新客户端向旧 agentd 发送 `local_base_branch` 时旧端会静默忽略该键；本期不伪造兼容成功，真实能力与拒发行为留给实现/验收节点。

## 2. 契约增量

### 2.1 账本侧：工作分支带目标机

```go
type WorkBranchInfo struct {
    Branch string // 最近一次非审阅派发的工作分支名
    Target string // 该次派发的目标机；空值表示历史快照没有目标机信息
}

func (s *Store) WorkBranch(cardID string) (WorkBranchInfo, error)
```

语义逐条冻结：

1. 按 dispatched 事件升序扫描，只消费非审阅快照；没有非审阅快照返回既有 `ErrNotFound` 包装错误。
2. `Branch` 与 `Target` 必须来自同一个最新非审阅 `DispatchSnapshot`，不得分别取两个快照。
3. 历史快照 `Target == ""` 时不能证明同机；后续起点裁决按「存在且上次目标机与本次相同」的正向条件处理，不能静默回落卡基线。

选择直接改返回值，不新增旁路查询：当前生产调用方只有 `internal/ledgerstep/dispatch.go:138` 一处；分支与目标机同源返回可避免两个查询在追加式事件流上各自取到不同快照。

### 2.2 wire 标记：`LocalBaseBranch`

四层形状全部冻结为布尔值，JSON 字面值为 `local_base_branch`：

```go
// internal/ledgerstep/dispatch.go
type DispatchOpts struct {
    // existing fields...
    ResolveDefaultBase bool
    LocalBaseBranch     bool
}

// internal/client/client.go
type DispatchOpts struct {
    // existing fields...
    ResolveDefaultBase bool
    LocalBaseBranch     bool
}

// internal/agentd/server.go
type dispatchRequest struct {
    // existing fields...
    ResolveDefaultBase bool `json:"resolve_default_base"`
    LocalBaseBranch    bool `json:"local_base_branch"`
}

// internal/agentd/manager.go
type DispatchReq struct {
    // existing fields...
    ResolveDefaultBase bool
    LocalBaseBranch    bool
}
```

穿线签名与现状保持不变：

```go
func (c *Client) Dispatch(ctx context.Context, opts DispatchOpts) (*proto.Task, error)
func (s *Server) handleDispatch(w http.ResponseWriter, r *http.Request)
func (m *Manager) Dispatch(ctx context.Context, req DispatchReq) (task *proto.Task, err error)
func (s *Server) stepTransport(ctx context.Context, opts ledgerstep.DispatchOpts) (string, error)
```

字段语义：`LocalBaseBranch == true` 表示 `Base` 是**目标机本地**工作分支名；agentd 只允许解析 `refs/heads/<Base>`，不执行远端补拉。本字段不是「本地项目路径」或「已存在分支检出」模式。

原子不变式：

- `LocalBaseBranch == true` 与 `ResolveDefaultBase == true` 互斥；两者同时为真在建任务、建 worktree、fetch 之前拒发。
- `LocalBaseBranch == true` 时 `Base` 必须非空；空值不得被解释为 HEAD 或项目默认分支。
- 本地 `refs/heads/<Base>` 不存在时拒发，错误必须是 `ErrBadWorkspaceReq` 包装，并说明「工作分支只存在于创建它的那台机器」以及「先 push 到 origin，再用显式 `--base` 指定」的出口。
- `LocalBaseBranch == false` 的普通 CLI/显式基线/卡空基线语义保持不变；尤其 `ResolveDefaultBase` 仍只负责 `origin/HEAD` 缺省解析。

### 2.3 起点裁决矩阵

`ViaTemplate` 负责决定 `Base` 与标记；卡上下文里的 `EffectiveBaseBranch` 仍只是合并目标，不能被本次派发起点替换。

| 情形 | `Base` | `LocalBaseBranch` | 结果 |
|---|---|---:|---|
| 首轮，无工作分支 | 卡有效基线；为空则保持 `ResolveDefaultBase` 路径 | `false` | 沿既有基线/默认基线语义 |
| 有工作分支且上次目标机等于本次目标机 | `WorkBranchInfo.Branch` | `true` | 目标机本地解析，禁止 fetch |
| 审阅轮 | `WorkBranchInfo.Branch` | `true` | 审阅分支仍从工作分支起，不改变现有 `-review-N` 命名 |
| 有工作分支但上次目标机不同（或目标机信息缺失） | 不生成任务 | 不适用 | 在派发前拒绝；提示 push + 显式 `--base` |

跨机拒发发生在 `ViaTemplate` 的 Transport 调用之前，不落 `DispatchSnapshot`、task 或孤儿 worktree。自动 push 工作分支与把起点改成 SHA 均不在本期接口里。

## 3. Ticket 0 边界

本提交只落契约层字段、返回类型、参数接缝与 JSON 直通镜像。`resolveDispatchBase` 已接收 `localBaseBranch`，但本轮以 `_ = localBaseBranch` 保留空壳；真正的 `refs/heads` 只读、无网络解析与错误文案属于后续实现节点。`ViaTemplate` 当前仍保留既有分支命名与审阅接线，目标机比较和跨机拒发也属于后续实现节点。

因此本轮没有把「已实现但零测试」混入欠账：新增 `WorkBranchInfo.Target` 的现有事件语义用 ledger 测试冻结；新增 JSON 键用 client 金样本测试冻结；未实现的行为只以空壳交棒。

## 4. 拍板记录（三重闸门命中）

### 4.1 `WorkBranch` 直接扩展返回值，不新增旁路查询

这是难逆转的 API 形状（会影响账本调用方与下游节点），无上下文时后人会惊讶为什么一个只返回字符串的查询突然返回结构体，且存在被否的像样方案（保留旧方法并新增 `WorkBranchTarget`）。选择直接返回结构体，是因为当前生产调用方仅一处，分支和目标机必须来自同一快照；被否方案会让调用者自行拼接两个查询并可能跨事件快照漂移。

### 4.2 新增显式本地起点标记，不改写 `ResolveBaseBranch` 的全局语义

这是跨 CLI/agentd wire 与工作区解析的难逆转契约；无上下文时后人会倾向把 `ResolveBaseBranch` 改成「本地有就不拉」，但该函数注释明确刻意无条件 fetch。存在真实取舍：全局改写代码少，却会让普通卡基线取陈旧本地分支；显式标记只影响卡工作分支接续，保留普通分支名的 freshness 保障。

### 4.3 跨机不静默回落卡基线

这是跨执行机接续的难逆转失败语义；无上下文时后人会惊讶为什么明明有工作分支却拒绝派发；存在取舍——回落卡基线能提高派发成功率，但会静默丢失上一节点产出。选择拒发并给出 push + 显式 `--base` 出口，优先保证产出不被吞掉。

## 8. 拆解阶段边界澄清（2026-08-23）

以下结论是对本契约冻结物的归属澄清，不新增字段、端点、状态或契约方向；写回
契约是为了让后续拆解与 review 对同一行冻结物核对，不把边界判断只留在拆解稿里。

1. `WorkBranchInfo`、`Store.WorkBranch` 与 `ledgerstep.DispatchOpts` 属于
   `d_ledger` 的包内 API；`WorkBranchInfo` 不穿 HTTP/JSON，也不进入
   `internal/proto` 的 Go↔TS fixture。它的 `Target` 只由同一条 `DispatchSnapshot`
   事件读取，不能另查一条快照拼接。
2. `ledgerstep.Transport` → `agentd.stepTransport` 是现有注入适配缝；本次只在已有
   `client.Dispatch` → `POST /api/tasks` → `Manager.Dispatch` 链路上透传
   `local_base_branch`，不登记一条虚构的 `d_ledger → d_remote` 直接契约边。
3. 「同一台目标机」的判定是账本快照 `Target` 与本次请求目标机字符串的精确相等，
   不是网络可达性、仓库 origin 相等或执行机操作系统相等。历史快照 `Target == ""`
   不足以证明同机，按第 2.3 节的拒发路径处理。
4. 本地工作分支解析属于 `d_controlplane` 工作区内部规则：`LocalBaseBranch` 为真时
   只解析目标机仓库的 `refs/heads/<Base>` 并转成提交号交给既有工作区准备；它不是
   新的本地路径/检出模式，也不改变普通 `ResolveBaseBranch` 的补拉语义。
5. 旧版 agentd 忽略未知 JSON 键的事实不构成兼容成功承诺。若后续要求旧版 agentd
   对 `local_base_branch` 安全拒绝或协商版本，必须先回到 contract 增加显式能力/版本
   契约；本卡实现与验收只把同版本目标机作为可通过对象，并把旧版行为列入真机清单。
