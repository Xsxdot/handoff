# B433 — iOS 待办处理后的图标角标同步回归

类型：B432 验收后 bug，debug → L1 小修；既有 agentd 推送旁路与 APNs 接缝内修复。

## 根因与目标

用户已回复五条裁决，`handoff room inbox` 新鲜 count=0，手机角标仍为 5。
旧实现只在新增 decision/ticket/mention 时发通知，明确忽略 `decision_answered`，
没有处理后同步计数。B432 的「角标与未处理数一致」没有覆盖递减/归零，原验收结论存在遗漏。

修复目标：裁决已回复、工单已答复/作废、用户回复消费提及后，复用真实收件箱计数发送
badge-only APNs 更新；0 显式编码，完全省略 alert/sound，不产生新的待办横幅或声音。
新增待办的标题、声音与点击落点保持既有契约。无设备/未授权继续静默降级。

## 边界与验收

不新增 REST、表、绑定函数或原生 HTTP 客户端；不复制收件箱计数规则，不改权限判定。
内部 `badge_update` 只是既有 fanout 的投递模式，不进入收件箱词表。
公共推送网关与多用户凭据托管是不同的发布架构问题，本卡不实现。

- 真账本依次创建五条裁决，逐条答复，经生产消费者投递 5→4→3→2→1→0。
- APNs 实际 HTTP 载荷包含 `badge:0`，无 `alert` 与 `sound`；正常通知回归通过。
- 已处理工单的生产事件钩子与真实回复消费提及路径均归零。MarkRead 仅设置未读游标，
  不改变既有提及消费语义。
- 真机复验处理后图标归零且无新增横幅；未复验前不宣告完成。

## 执行计划

1. 生产缝回归测试先红：第一条回复没有投递；badge-only 旧载荷带空 alert/default sound。
2. agentd 消费处理事件并复用 fanout 发送最新计数，APNs 按模式省略 alert/sound。
   更新关键路径日志与意图注释，不记录 token/密钥。
3. 触及包 Push/APNs/RoomRead 测试、race、全量编译、全量静态与集成检查；变异确认断言有牙。
4. 经官方服务命令重载已构建产物，真实 iPhone 验证后落账，再按 finish 收尾。
