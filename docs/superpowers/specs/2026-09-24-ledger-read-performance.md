## 问题与现状

会话列表、房间历史和工作项看板在小账本上仍需数秒至十余秒。已验证的主要问题是消费层反复读取并重放超出当前展示所需的大量事件；PostgreSQL 查询执行时间远短于客户端端到端耗时。客户端传输与应用处理都在端到端读数内，但本轮没有把网络传输占比、连接池等待和应用折叠分别完整量化，不能将 Tailscale 链路单独判为根因。

本轮只读实测对象为本机 agentd `3390cd2f3e7c`（PID 60150，运行约 4 小时 57 分）、工作树 `codex/session-reliable-mentions` / `186bd7ba1f0e` 与其所连共享 PostgreSQL。当前账本约 21,270 条 `card_events`（最大 seq 21,319）、404 张卡、14 个会话；其中 9,337 条 `task_mirrored` 的 payload 总计约 6.3 MB。当前连接使用 Tailscale 地址；Tailscale 探测走 direct peer path、约 9ms，不是 DERP 中继。读侧 `SELECT 1` 12 次平均约 29ms、最高 221ms。

关键读数：

- `handoff session list --json` 13.59s / 14 行；`handoff room list` 13.68s / 414 行。两者远慢于用户期望。
- 从 PG 顺序读取完整事件流：21,270 行、22 个 1,000 行分页，客户端耗时 12.08s，平均每页 549ms、最慢 1.06s。单页 1,000 行的 PostgreSQL `EXPLAIN ANALYZE` 执行约 0.19ms。
- 本机真实 `GET /api/cards` 约 8.3–9.7s / 34 张卡；连续两次请求都在 8.3s 左右。直接 `handoff card list --json` 约 0.9–1.5s，`--all` 读 404 张卡约 1.25s。
- 看板额外读取的 `task_mirrored` 事件：PG 执行计划扫描 9,337 行并做外部归并排序（临时盘约 4MB），数据库执行约 20ms；客户端实际收取 9,337 行 / 6.31MB payload 耗时 7.95s。当前 PG 观测到 0 个锁等待、0 个被阻塞会话。

以上说明“PG 查询执行时间”和“用户请求耗时”差了几个数量级。`GET /api/cards` 的主要已证路径是每次重新传输及解码全量镜像工单事件；会话/房间读的主要已证路径是从 seq 0 全流分页再按房间过滤。当前还不能据此还原 2026-09-23 20:00–22:00 的具体不可用原因；当时缺少请求级数据库/网络/连接池阶段日志。

## 级别与档位

**L3 重档**：本期覆盖 `d_ledger` 的持久化读路径、`d_collab` 的会话/房间/消息消费语义，以及 agentd、CLI、Web 看板的生产消费路径；要在 PostgreSQL 与 SQLite 上守住同一事件语义，并通过真机读取与等待验证，工作量超过轻档固定成本。现有公开字段与输出行为作为兼容基准；凡本轮要改变的既有冻结读形状或新增 Web 摘要状态，须在对应故事实现前回到 contract 明确语义和消费断言。内部查询签名仍留给 Wave 0 / plan；若新增接缝被多个独立工作单元共同依赖，在 breakdown 前冻结。

## 推荐方案与弃选

推荐把**按用户查询形状计算的读模型收回账本边界**：卡片列表只取展示所需的聚合结果；房间、会话、卡片与 wait 均使用范围和游标受限的查询。`card_events` 保持追加式权威历史，任何派生摘要都必须能从它重建，不能产生第二份不可审计的业务真相。协作域继续拥有未读、成员、寻址和房间语义；它通过账本读契约取需要的消息与摘要，不直接访问账本 SQL，也不再把全流下载到内存中过滤。准确的索引、投影表或 SQL 表达由 Wave 0 计划/实现决定，不在此 spec 抢写内部签名或 DDL。

不把以下方案作为单独修复：

- **只加索引**：可减少 PG 扫描/排序，但不能消除当前把 6MB 事件 payload 每次搬到应用的成本。
- **只加缓存**：不能修复会话全流分页，跨进程失效和长尾缓存也无法保证断线恢复语义；本轮两次连续看板请求仍约 8.3 秒。
- **只换 PostgreSQL 网络/供应商**：当前 peer 探测是 direct path，数据库执行只需毫秒级；网络改造可能改善长尾，但不应继续让页面重复传输与展示无关的事件。

账本页面的主请求不等待执行机或模型载体响应。未挂账等外部摘要由后台刷新，不得延迟卡片、会话和消息的主内容。推荐对用户可见的摘要状态语义如下，确切 JSON 字段在 S1 contract 冻结：

- 完整刷新每 30 秒触发一次；所有 target 查询成功且最近一次刷新不超过 30 秒时标为“最新”。有 target 查询失败时标为“部分”，保留可读 target 的结果并列出失败 target，不把缺失目标当成零。
- 最近一次完整/部分结果超过 30 秒后标为“陈旧”，显示最后观测时间和数据年龄。摘要可继续作为“上次观测”供查看，不得被呈现为当前值；这份参考信息没有固定隐藏时限。
- 从未成功取得摘要时标为“不可用/尚无结果”，不得用 `count: 0` 表示合法空结果。刷新失败时主账本读照常成功，保留最后观测并明确陈旧或部分状态。
- 这份摘要当前还喂给任务兜底看板的未挂账 ID 集合、角标和“仅看未挂账”过滤器（`web/src/app/shell/Shell.tsx:188-195,790,1151-1159`、`web/src/app/board/columns.ts:155-165`）。只有完整且不超过 30 秒的最新结果可驱动过滤和当前数量角标；部分、陈旧或不可用时必须退化为不过滤，避免把不可达目标的任务藏掉或把已变化的旧任务误当当前状态。陈旧详情仅作带时间戳的参考，不作为筛选事实。
- 当前 `count/tasks/unknown_targets` 使用者必须能区分最新、部分、陈旧、不可用；如加状态与时间字段，Web/CLI 消费者金样须在 S1 前冻结。这里的 30 秒沿用现有刷新缓存窗口；陈旧值不设 5 分钟硬截止，因为它只作为带年龄的历史观测展示。

## 全部必交用户故事

1. **S1 卡片看板、列表与 card wait 快照**：用户打开工作项看板、过滤列表或执行 `card wait` 时，拿到卡片、未决工单数、等人/冻结/阻塞等既有标记和该卡/子树的未决工单快照。结果与当前事件重放语义一致；接口不把全部 task mirror payload 拉到应用层。远端未挂账摘要失败时仍先显示账本数据，并按“部分/陈旧/不可用”规则标明未知，不能以零冒充无工单。
2. **S2 会话/房间列表、未读与消息历史**：用户打开会话、切换会话、查看房间列表/未读数或读取房间历史时，先看到会话状态和正确消息窗口；历史首屏为最近 200 条消息、按 seq 升序呈现，游标继续沿既有排他边界分页。只有真实空会话才显示空态，查询失败/超时必须显示错误和可恢复入口，不能伪装成无消息。覆盖 session list/detail、room list、history、`Unread` 及列表未读汇总，不允许为每个房间再重复扫全局流。
3. **S3 定向收件箱、消费与 wait 恢复**：`Pending`、`Mentions`、`Consume`、回复后提及清理和 `session wait` / `--follow` 按成员、房间及游标范围读取，保持现有寻址/消费语义。wait 从已有共享交付游标继续，断线期间未交付的定向消息可补收，stdout 成功写出即交付、无逐条确认，已交付水位不重复推进；不因 listener 重启从全局 0 无条件重放。`--timeout 5s` 一次性空等不能晚于 6s 退出；`--follow` 的 timeout 继续表示命中之间的空闲上限。
4. **S4 账本可用性与故障可诊断**：即使所有模型载体额度用尽、执行机不可用，已落账的卡片/会话/消息仍可读取。数据库不可达、查询取消、连接池等待、远端摘要失败与合法空结果可区分；日志能分解端到端请求、连接等待、SQL 执行/行数与字节、应用投影、远端等待和取消阶段，不记录正文、token 或凭据。
5. **S5 方言与数据正确性**：同一查询语义在 PostgreSQL 与 SQLite 通过；游标边界、session 隔离、未读/消费标记、工单开启—答复—作废、`@` 寻址和断线补收保持现有契约。任何派生投影能由事件重建并验证一致，不能出现事件提交而投影永久静默落后的状态。

## 目标架构与接缝语义

- `d_ledger` 仍是事件事实与查询投影的唯一持久化所有者；canonical `card_events` 只追加，不因性能目标重写或删除历史。
- `d_collab` 拥有消息所属房间、成员、已读/消费、未读和定向投递规则；范围查询可以在账本边界执行，但业务判定不能下沉成协作层的 SQL。
- agentd/CLI/Web 是消费与投影面，不负责从全局事件流拼装一份全量账本；页面首屏只请求有界展示所需的数据。远端 target 状态不进入账本主查询的同步关键路径。
- 新派生状态若落库，必须明确可重建、幂等、追到事件 seq 水位，写入与消费失败均有可见恢复方式；不能出现事件已提交但读模型永久落后的静默双写。
- 现有 CLI wait、Web API 和 UI 的用户可见字段/行为作为兼容基准；性能优化可改变读取形状，不能改变寻址、游标、排序、空结果和交付结果。
- contract 修订时点：S2 Wave 0 前修订 B156.2 A.5 的“>10^5 行才重议”护栏，因为 21,270 行实测已证明较小账本也有显著延迟；S3 实现前修订 B358 与 r2 session contract 中“全流分页”读侧描述，保留 `(cursor, MaxSeq]`、升序、命中筛选、摘要输出、共享水位、断线补收及无逐条确认语义；S1 实现前冻结远端摘要状态字段及 UI 消费行为。实现节点不得擅自修改这些已冻结外部语义。
- 新增内部查询接缝的精确类型/SQL 不在 spec 冻结；先以真实生产消费者验证。若 breakdown 后多个独立工作单元共用该接缝，再在 breakdown 完成前冻结其协作契约。
- `room read --after` 的参数方向错误保持独立反例；当前帮助声称“之后”，实现实际传 `beforeSeq`，详见排查台账与 roadmap 队列 1。

## 实现与测试决定

- 性能目标（用户已于 2026-09-24 同意 p95 ≤2s）：在固定 agentd/客户端/数据库版本及固定网络路径下，`/api/cards`、`/api/sessions`、`/api/rooms`、单房间首屏，以及对应 Web 首次可用内容，在下述三组隔离数据上均 p95 ≤2s：①当前实测规模（约 21,270 事件、9,337 镜像事件/6.31MB）；②①加至少 20,000 条非镜像无关事件；③②并将镜像事件行数和 payload 字节至少加倍。每个 HTTP 场景每组 100 个样本，先单列首个请求，再做 5 次不计入的预热与 100 次计入样本；按 nearest-rank 计算 p95，同时报告 p50、最大值、错误数与响应字节。所有失败样本计入错误，不得静默剔除。
- Web 首屏测量使用 Codex 内置浏览器对每组测试数据下的 `/cards`、`/rooms` 和一间已有消息的房间各做 100 次导航/硬刷新，以导航开始到卡片/消息可见为止；报告 p50/p95/max 与错误数。记录 app build、PG 版本、服务和浏览器位置、DB peer 路径/RTT、服务缓存条件；不得把 Tailscale ping RTT 当吞吐证据。若最终验收环境与基准链路不同，分别报告，不混算。
- `session wait --timeout 5s` 的一次性模式在无积压、无新匹配消息的隔离库运行 30 次；从 CLI 子进程启动计时到退出，每次均须 ≤ 6s（含打开账本与连接池等待）。恢复验收覆盖游标存在/缺失、断线补拉、多条积压、已交付后重连、follow 空闲上限、取消及数据库错误；各类消息不得漏读或改变 r2 水位语义。
- 基准只在隔离、可丢弃的 PostgreSQL 测试库构造，镜像事件使用代表性 payload 并核对种子行数/字节；共享生产账本只读取，不写合成事件。另用 SQLite 对同一查询语义与金样确认同构。
- 分阶段记录数据库连接/池等待、SQL 执行、传回行数与字节、应用折叠、远端摘要、页面/CLI 可见时间。不能把服务器 `EXPLAIN` 执行时间报告成端到端通过；冷启动首请求与重复/预热后的分布分开报告。
- CLI/UI 验收走真实入口；UI 使用 Codex 内置浏览器，不经 SuperDev。所有 target 均不可达或载体额度耗尽时，页面仍应显示完整本地账本事实，远端摘要只显示其最新/部分/陈旧/不可用状态。
