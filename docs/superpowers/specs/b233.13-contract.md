## 2. 冻结后的精确形状

### 2.1 编排 client 接口（gateway 侧，使用方）

接口定义在 gateway 包（架构法第九条：接口归使用方）；实现是迁出后的编排 `Manager`。Ticket 0 已落可编译空壳：`internal/agentd/orchestration_client.go`。

```go
type TerminalOutcome struct {
	Claimed         bool
	WorktreeRemoved bool
}

type OrchestrationClient interface {
	// 任务生命周期
	Dispatch(ctx context.Context, req DispatchReq) (*proto.Task, error)
	Continue(ctx context.Context, taskID, instructions string) error
	Done(ctx context.Context, taskID, note string) (TerminalOutcome, error)
	Stop(ctx context.Context, taskID string) (TerminalOutcome, error)
	RelayAnswer(taskID, ticketID, answer string) error
	NoteDeliveryFailed(taskID, ticketID string, cause error)
	RecoverStuck(taskID string, force bool) (*RecoverReport, error)

	// 任务查询与回收
	Status() (*proto.StatusResp, error)
	FootprintAll() (*proto.FootprintResp, error)
	ReclaimList() (*proto.ReclaimListResp, error)
	Reclaim(ctx context.Context, taskID string, force bool) (*proto.ReclaimResp, error)
	GC(ctx context.Context, force, execute bool) (*proto.GCResp, error)

	// 项目位置
	RegisterProject(ctx context.Context, req RegisterProjectReq) (proto.ProjectLocation, error)
	ListProjects(ctx context.Context) ([]proto.ProjectLocation, error)
	UnregisterProject(ctx context.Context, name string) error

	// 执行者名单
	ExecutorNames() []string

	// 工作区能力只读透传（本卡不迁工作区）
	Workspace() workspace.Capability
	RequireWorkspace() error
	AssembleResultRef(ctx context.Context, task *proto.Task, repo, headRev string) (workspace.ResultRef, error)
	InspectRepoDir(ctx context.Context, dir string) (root, origin string, err error)
}
```

方法集是 handler 今日对 `s.mgr` 生产调用的**闭包**：多一个即越界，少一个即 handler 编不过。`RequireWorkspace` / `AssembleResultRef` / `InspectRepoDir` 由现未导出方法导出得来，语义不变（直通镜像）。

### 2.2 编排实现包

- 实现包路径冻结为 `internal/orchestration`（spec 实现决定）。`Manager` 及其仅服务编排的同包文件迁入；gateway 不得 import 该包的内部实现（组装点 `main.go` / `server.go` 绑定具体实现除外）。
- `internal/orchestration` 不得 import `internal/agentd`（否则 gate 侧与实现侧成环）。
- 组装：`cmd/agentd.go` 构造编排实现并赋给 `Server` 的接口字段；`*Manager` 只在组装点 `new`。
- `server.go` 整文件仍在 target.json `assembly` 名单，**本卡不撤**（撤名单、`internal/<sub>/internal/`、预算棘轮到 0 留给 B233.17）。

### 2.3 终态占用只核销一次（P1-4）

- `Done`/`Stop` 的状态迁移必须 CAS（期望态 → 终态），沿用 `store.UpdateTaskState` 的 `WHERE state = 旧值` 语义。
- 只有本次把任务迁到终态的那一次调用返回 `TerminalOutcome{Claimed:true}`。
- `transit` 看到「已经是目标态」即 `return nil`（现状 `internal/agentd/manager.go:3731`）只表示幂等成功，不表示「我是释放者」；该分支必须返回 `Claimed=false`。
- handler 仅当 `Outcome.Claimed` 为 true 才调用 `releaseTaskCarrierOccupancy`；`Release` 签名不变（不新增 task id）。
- `Done` 的已 `completed` 重发仍 HTTP 200 幂等，但不再 `Release`。

## 4. 依赖库既成行为（契约的一部分）

- `store.UpdateTaskState` 先 `GetTask` 读旧态、`proto.CanTransit` 校验、再 `UPDATE … WHERE id=? AND state=?`（CAS），影响 0 行返回 `ErrBadTransit`；`internal/store/store.go:525-552`。终态竞争只能由这一层判定，handler 不得自行推断「我是不是赢家」。
- `transit` 在 `cur.State == to` 时直接 `return nil`（不做 `UpdateTaskState`），因此「幂等成功」与「本次迁移成功」必须在返回值上区分；`internal/agentd/manager.go:3726-3766`。
- `releaseTaskCarrierOccupancy` 对空 `Carrier` 直接返回不 Release；`internal/agentd/server.go:1822-1845`。本卡不改该门，只改调用条件。
- `handleDone` 现有的已 `completed` 短路（`internal/agentd/server.go:1746-1751`）在 `Done` 调用之前；本卡实现后仍须短路，不得依赖 `Done` 内部幂等来避免二次释放（两道都要有）。

### 5.1 包与接口边界

1. `OrchestrationClient` 是 gateway 生产路径持有的编排类型；`Server` 不再以 `*agentd.Manager` 为生产字段类型。
2. `OrchestrationClient` 定义在 gateway 包（使用方）；`internal/orchestration` 不 import `internal/agentd`。
3. `OrchestrationClient` 方法集等于 handler 生产调用闭包：不新增 handler 未使用的编排能力，不遗漏任一 handler 调用。
4. `Manager` 不在 `internal/agentd` 包；编排实现只在组装点 `new`。
5. 具体实现只在登记的组装点绑定；handler 不 `new` 编排实现。
6. `server.go` 仍在 target.json `assembly`；本卡不撤。

### 5.2 终态 CAS 与释放

7. `Done` 在任务不是 `waiting_review` 且未完成到 `completed` 的迁移时返回错误，不释放。
8. `Done` 把任务从 `waiting_review` CAS 到 `completed` 成功的那一次返回 `Claimed=true`。
9. 已在 `completed` 的第二次 `Done` 返回 `Claimed=false` 且 `err==nil`；HTTP 层 200 幂等。
10. `Stop` 把非终态任务 CAS 到 `failed` 成功的那一次返回 `Claimed=true`。
11. `Stop` 对已终态任务返回 `store.ErrBadTransit`（HTTP 409），不释放。
12. `handleDone` 仅当 `Outcome.Claimed==true` 时调用 `releaseTaskCarrierOccupancy`。
13. `handleStop` 仅当 `Outcome.Claimed==true` 时调用 `releaseTaskCarrierOccupancy`。
14. 同一任务并发两次 `Done`，终态迁移恰好成功一次，`Release` 调用总次数恰为 1。
15. `Release` 签名不变；不以 task id 参与释放。
16. `Stop` 成功路径 `WorktreeRemoved` 恒为 false（现场留存）。

### 5.3 不回归

18. 不新增 HTTP 路径、CLI 命令、事件类型字面值、顶层领域。
19. 状态迁移仍经 `store.UpdateTaskState` 的 CAS；不引入无 CAS 的直接 `UPDATE tasks SET state`。

## 7. 三重闸门拍板记录

1. **终态释放凭证是 `TerminalOutcome.Claimed`，不是「HTTP 成功」或「transit 返回 nil」。** 难逆转：改 `Done`/`Stop` 返回形状，波及 handler、store CAS 与全部调用点；无上下文会惊讶：后人会觉得 handler 在 `Done` 成功后直接释放更简单，从而把并发双释放带回来；真取舍：被否方案是 handler 重读任务状态自行判定赢家（重复 CAS 逻辑、仍会与 `Release` 竞态），或让 `Release` 带 task id（改编制域签名，越本卡边界）。显式不做：本卡不改 `Release` 签名。
2. **工作区/项目只读能力并入同一个 `OrchestrationClient`，不另立第二接口。** 难逆转：接口形状决定 handler 与组装点；无上下文会惊讶：`Workspace()`/`InspectRepoDir()` 属工作区关注点，后人会想拆到独立接口；真取舍：被否方案是本卡另立 `WorkspaceAccess` 小接口并让 Server 持两个字段（handler 今日是单 `s.mgr`，拆两会扩大本卡扇出，且工作区迁移是 B233.15）。显式不做：本卡不迁工作区实现。
3. **Ticket 0 只落接口空壳，字段切换与 Manager 迁包归实现节点。** 反过来把 `Server.mgr` 当场切成接口会拖动 3959 行 Manager 及其同包文件，超出 contract 的「空壳/直通镜像」边界；现有测试可仍绿，必须靠冻结 1/4/5 锁住。显式不做：本节点不迁包。
