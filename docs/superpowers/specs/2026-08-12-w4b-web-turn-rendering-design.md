> 上游：W4a（结构化回合流）产出的 `Frame` 契约、`frames.jsonl`、`GET /api/tasks/{id}/frames`
> 下游：无。`handoff tui`（W4e）与本期共享同一份契约，但各自渲染，互不依赖

> 没有它们执行者无法真机验证。本 spec 与实现计划可先行完成

## 1. 问题

今天任务详情页的「实况正文」（`web/src/app/task/RenderPanel.tsx`）把 `render.log` 整个塞进一个
`<pre>`。审阅者看到的是一片未分化的文本：模型的话、思维链、工具调用、工具输出混在一起，
靠缩进和符号勉强区分，而这些符号本身还因 executor 而异。

W4a 已经把四个 adapter **本来就解析出来的**结构（思维链、工具调用、工具结果）落成了
`frames.jsonl`。本期把这份结构渲染出来，让审阅者能一眼分清「模型在想什么 / 说什么 / 做了什么 /
得到了什么」。

### 1.1 本期做什么

任务详情页新增一个**结构化回合时间线**，与现有「实况正文」并存、可切换。

### 1.2 本期不做

- `render.log` 退役——W4a spec §5 已定：留到 W4b 落地后单独决定，不在本期范围
- 完整 markdown 渲染（见 §6）
- 列表虚拟化（见 §5）
- 时间线内审批（见 §4）
- 跨任务 / 跨机的帧聚合
- 任何后端改动。本期**只动 `web/`**，不碰 `internal/`

## 2. 与「实况正文」并存

结构化时间线是默认视图，一个开关可切回原始 `render.log` 流。

**为什么不直接取代**：这批帧是四个 adapter 各自分流出来的，质量并不齐平——W4a spec 自己记着
grok 的工具信息只是 200 字符的人类摘要、codex 没有真实抓包因而没有 golden 基线。头几周撞上
「某家 adapter 的帧不完整」的概率不低。那时能一键退回原始文本，是区分**「渲染错了」还是
「采集错了」**的关键证据；没有这个兜底，审阅者只能干瞪眼。

等信任建立、四家帧质量都被真机验证过，再按「取代」收口，那时退役 `render.log` 也才有依据。

**两个视图各自维护加载位置**，切换时不试图对齐滚动位置。对齐两条不同数据源（字节流 vs 帧流）
的位置是伪需求：成本高，且必然对不准。

`RenderPanel.tsx` 与 `useRenderStream.ts` **一行不改**，原样作为开关的另一半保留。

## 3. 形态：线性时间线

回合之间只用分隔线断开，**不做可折叠的回合区块**。思维链与工具调用各自就地折叠。

### 3.1 为什么不是回合折叠

「每个回合一个可折叠块」看起来更能压缩长任务，但它折叠掉的东西是错的：审阅一个回合时需要的是
**「说了什么 → 做了什么 → 得到什么 → 于是又说什么」这条因果链**，而回合折叠会把整条链一起
藏起来，包括最该留在视野里的正文。

它想解决的「回合太多」，在真实任务里是靠滚动加回合锚点解决的，不是靠折叠正文。

### 3.2 块的类型

| 帧 type | 渲染成 | 默认态 |
|---|---|---|
| `turn_start` | 回合分隔线，`reason` 映射为「派发」/「续发指令」 | — |
| `text` | 正文段落 | 永远展开 |
| `reasoning` | 思维链块，左侧色条区分 | 折叠，只显示「🧠 思维链 · N 字」 |
| `tool_call` + `tool_result` | 一张工具卡（名字、参数摘要、状态徽章） | 折叠，展开后见输入与输出 |
| `event` | 一行打断标记 | 不可展开、不可操作 |
| 未知 type | 一行中性条目，可展开看原始 JSON | 折叠 |

**未知 type 必须渲染而不是丢弃**。契约会演进，而前端比后端晚部署是常态；遇到新类型就白屏或
静默吞掉，都是不可接受的失败模式。

## 4. 事件：三处各司其职

同一张权限工单会出现在三个地方，这是**有意的**，各自理由不同：

| 位置 | 职责 | 形态 |
|---|---|---|
| 时间线（本期新增） | **因果**——模型正说着话，在这里被打断了五分钟，批复后接上 | 一行标记，不可操作 |
| `EventsPanel` | **实时**——监控条，WS 增量 | 一行简览，列表封顶 |
| `TicketsPanel` | **裁决**——唯一能批准/拒绝的地方 | 工单全文 |

这是对 `EventsPanel.tsx` 头注释里既有纪律的延伸：原来是「简览 vs 全文」两分，现在是三分。

**时间线里不提供审批入口。** 审批不可逆且要当真（master spec §4.7），给它开第二个入口、还是开在
一条摘要旁边，风险和收益不成比例。

## 5. 加载、跟随、回翻

### 5.1 端点

复用 W4a 的 `GET /api/tasks/{id}/frames?offset=<n>&tail=<n>&follow=1`：

- `Content-Type: application/x-ndjson`
- `X-Handoff-Frames-Size` 是响应开始时的文件大小
- `offset` 与 `tail` 的单位都是**字节**，不是行数、不是帧数
- 文件不存在返回 200 空内容而非 404

### 5.2 进入与跟随

进页面请求 `?tail=65536&follow=1`，与今天 `RenderPanel` 同量级。

跟随复用 `RenderPanel` 已验证的 stick-bottom 逻辑：距底 40px 以内才自动跟随，用户往上翻即停止
跟随，不抢滚轮。

### 5.3 加载更早

记住本次响应的起始 offset，「加载更早」按钮往前请求一页（65536 字节）并 **prepend**。

- **prepend 时必须按 `scrollHeight` 差值补偿滚动位置**，否则每次加载都把用户弹到别处
- 起始 offset 归零后按钮消失
- 半行两侧都防：服务端保证只在完整行边界切（W4a §7.2）是契约，客户端仍缓冲一层不完整行兜底

### 5.4 回合锚点

顶部一条锚点，从**已加载帧**的 `Turn` 字段生成，不需要任何新接口。

必须**明确标注只覆盖已加载范围**（例如「回合 7–12，更早的需先加载」），不假装是全量目录。

### 5.5 体量的硬边界

不做虚拟化——YAGNI，且引入虚拟化会让 stick-bottom 与 prepend 补偿都变复杂。

但不做虚拟化就必须有一个说得出口的边界：**已加载帧数封顶 5000**，到顶后停止 prepend 并提示改用
`handoff frames`。没有边界的后果不是"偶尔慢"，而是在最长、最需要审阅的那些任务上悄悄卡死。

单行帧的 16KB 上限由 W4a 保证，前端不重复设限。

## 6. 正文渲染：只管代码围栏

三段代码围栏 ` ``` ` 与行内 `` `code` `` 渲染成代码样式，其余一律纯文本
（`whitespace-pre-wrap`）。零第三方依赖。

**为什么不引 markdown 渲染器**：收益分布很不均匀。审阅时真正需要和散文区分开的是**代码块**；
标题、粗体、列表不渲染也完全读得懂。为这部分边际收益引入一个体积不小的依赖，外加 XSS 面
（必须禁 raw HTML）和**流式抖动**——增量是逐字到达的，围栏闭合前渲染器会把后续内容当普通段落，
闭合瞬间整块重排——不划算。

**围栏未闭合时按纯文本降级**，因此流式过程中不抖。

范围被「只管代码围栏」钉死，所以它不会长成一个必须维护的半吊子 markdown 实现。将来真需要，
从本方案换成 react-markdown 是纯替换，没有沉没成本。

## 7. 文件结构

全部新增在 `web/src/app/task/` 下。解析、I/O、展示三分：

| 文件 | 职责 | 边界 |
|---|---|---|
| `frames.ts` | 纯函数：ndjson 文本 → 可渲染块。半行缓冲、delta 合并、`RefSeq` 配对 | 不碰 DOM、不发请求 |
| `useFramesStream.ts` | 加载 / 跟随 / 回翻的 hook | 只管 I/O 与状态，不决定长什么样 |
| `TimelinePanel.tsx` | 容器：回合分隔、锚点条、加载更早、跟随徽章、切换开关 | 不解析原始文本 |
| `TextBlock.tsx` / `ThinkingBlock.tsx` / `ToolCard.tsx` / `EventMark.tsx` | 四种块的展示 | 各自独立可测 |
| `codeText.tsx` | 代码围栏渲染 | 范围钉死在三段围栏 + 行内 code |

**这样切分的理由**：`frames.ts` 是本期唯一有真实逻辑复杂度的地方（半行、合并、配对、坏行），
把它做成纯函数意味着它能脱离浏览器被穷举测试，而组件只剩下"给定块，画出来"。

修改的既有文件只有 `TaskPage.tsx`——在原「实况正文」的槽位放入带切换的时间线。

## 8. 帧到块的规则

### 8.1 delta 合并

`text` 与 `reasoning` 帧携带增量。**同一 `(turn, type, part)` 的连续帧拼成一个块**；`part` 变化即
开新块。

### 8.2 工具配对

`tool_result.RefSeq` 指向对应 `tool_call.Seq`。未配上结果的 `tool_call` 分两种状态，不含糊成同一种：

- 任务 `running` 或 `waiting_answer` → 「进行中」
- 任务 `waiting_review` / `completed` / `failed` → 「未返回」

`waiting_answer` 归入「进行中」是刻意的：那说明回合被工单挡住了，工具调用确实还在等，
不是没有回音。

「未返回」是真实信号：executor 半路死掉时，工具调用就是发出去没有回音，把它显示成
「进行中」是在撒谎——而这次 W4a 的第一轮派发就是这么死的，审阅者当时看不出任何异常。

### 8.3 截断

帧带 `Truncated: true` 与截断前的 `Bytes` 时，展开处显示「已截断（原始 N 字节，保留头 4KB +
尾 4KB）」。要看全文的出口是 `handoff diff` / `fetch` / `run`，不在本期加旁路。

## 9. 错误与边界

| 情况 | 处置 | 理由 |
|---|---|---|
| 帧文件不存在（200 空内容） | 显示「等待模型输出…」 | 任务刚派发、模型还没吐第一帧是正常态，**不是错误** |
| 流中断 | 徽章标注 + 重试按钮 | 不静默。断了却看着像"还在跟随"是最坏的一种 |
| 单行 JSON 解析失败 | **跳过该行并计数**，顶部显示「N 行无法解析」 | 一行坏数据不该让整条时间线白屏 |
| 未知帧 type | 渲染成中性条目 | 见 §3.2 |
| 组件卸载 | `AbortController` 中止 | `RenderPanel` 头注释记着这个坑：不中止则每次进出详情页泄漏一条常驻连接 |

## 10. 测试

### 10.1 `frames.test.ts`（重点）

纯函数，穷举边界：

- 半行切分：一帧被拆在两次 chunk 之间
- delta 合并：同 part 连续帧合一块；part 变化开新块；turn 变化开新块
- `RefSeq` 配对：正常配对、未配对（两种状态各一）、结果先于调用到达
- 未知 type：不丢弃、不抛异常
- 坏行：非 JSON、JSON 但缺 `seq`、空行——均跳过并计数，不影响其余帧

### 10.2 组件测试

只断言关键行为，不测样式：默认折叠态、事件标记不可点、`offset=0` 时「加载更早」消失、
坏行计数出现在顶部。

### 10.3 契约对齐

类型来自 W4a Task 1 产出的 `web/src/api/testdata/Frame.json`；既有 `src/api/contract.test.ts`
自动覆盖契约漂移——后端改字段未同步 fixture 则 Go 测试红，前端按旧字段写则 vitest 红。

## 11. 验收基准

原型 `prototypes/w4b-timeline/`（方案二最终形态）是形态验收对照物：回合分隔与锚点、思维链默认
折叠、工具卡的三种状态（成功 / 失败 / 未返回）、截断提示、事件打断标记、坏行提示、切回原始视图
的开关。真实页面开发完成后对照它验收。

功能验收：

- `npx tsc --noEmit` 干净
- `npx eslint .` 无 error
- `npx vitest run` 全绿
- `npx vite build` 成功
- 真机：对一个真实跑过的任务，时间线能正确显示回合分隔、思维链、工具调用与结果配对；
  「加载更早」能翻到第一个回合；切回原始视图内容与 `handoff frames` 输出一致

## 12. 已知取舍

| 决策 | 放弃了什么 | 换来什么 |
|---|---|---|
| 与 `render.log` 并存 | 一份 UI 与一条连接的管理成本 | adapter 帧质量存疑时的兜底证据 |
| 线性而非回合折叠 | 长任务的压缩率 | 因果链完整，正文不被折叠藏起来 |
| 不做虚拟化 | 超长任务的流畅度 | 实现简单；用 5000 帧上限换一个明确边界 |
| 只渲染代码围栏 | 标题/列表/粗体的观感 | 零依赖、无 XSS 面、流式不抖 |
| 事件三处并存 | 「一处看全」的简洁 | 因果、实时、裁决三种诉求各得其所 |
