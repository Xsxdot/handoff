# B196（含并入的 B189）：卡驱动租约在节点流上没接上

> 级别：**L2**　路由：plan → implement → review → acceptance → finish
> 状态：**已批准** —— 2026-08-23 用户授权自主推进（原话「直到完成能自主推进的所有任务」）。
> 承载卡：B196；B189 已 `card merge` 并入。

## 问题陈述

「卡的驱动是谁」这件事，库层的三个原语都写好了，但**生产代码一个都没调**。
两个半边各自造成一处真实故障：

1. **压根没认领（原 B196）**。走 charter 节点流的卡（`card dispatch --step ...`）
   派发后，`card show` 的 `driver_session` 恒为空、`driver_heartbeat_at` 恒为零值；
   同一台 agentd 上不带 `--step` 派发另一张卡，`driver_session` 立刻有值。
   两个后果：① B184 的「卡驱动归属」播报分支在节点流上永不触发——`status` 里那些
   任务只会显示「无人值守」，看不到是哪张卡、哪个会话在驱动（2026-08-23 三态同屏
   实测：普通派发那条显示「无人订阅（卡 B2 驱动 cli:…#14647，心跳 0m 前）」，
   `--step` 派发那条显示「无人值守」）；② 节点流失去并发认领保护，两个会话同时
   `--step` 同一张卡，CAS 拦不住。
2. **认领了没人续期（原 B189）**。租约 TTL 5 分钟，过期即可被抢占，而续心跳的原语
   全仓零生产调用点。后果：任何长时驱动的会话（挂 `card wait` 盯几十分钟、或一个
   跑几十分钟的 verdict 节点）在认领 5 分钟后租约即过期，别的会话可以合法抢走它
   正在推的卡，而驱动身份字段仍显示原主——**归属信息本身会腐坏**。

两条是同一件事的两半：租约的**取得**与**保持**都没接上。只修其一都得不到一个可信的
「这张卡现在归谁」——不认领的话没有归属可保持，不续期的话归属五分钟后就是假的。

## 现状事实（读数，由 implement 对本轮工作树复核）

| 事实 | 出处 |
|---|---|
| `--step` 非空时 RunE 第一件事就是转进节点路径，认领写在它**下面**的普通派发路径里 | `cmd/card_dispatch.go` 的 `cardDispatchCmd.RunE` |
| 普通派发路径用的是「转状态 + 落驱动」的合并原语（会把卡推到「进行中」） | `internal/ledger/move.go#Store.ClaimCard` |
| 只认领驱动、**不动状态列**的原语已经存在，且**全仓零生产调用点**（只有测试调） | `internal/ledger/tasks.go#Store.ClaimDriver` |
| 续心跳原语同样存在、同样零生产调用点 | `internal/ledger/tasks.go#Store.HeartbeatDriver` |
| 租约 TTL 5 分钟；心跳过期即允许他人抢占 | `internal/ledger/tasks.go` 的 `driverLeaseTTL` 与 `ClaimDriver` |
| CLI 与 agentd 的节点执行装配的是同一个编排体，编排只有一处 | `cmd/card_node.go#runStepDispatch`、`internal/agentd/cardstep.go#Server.startCardStep`，都构造 `ledgerstep.StepRunner` |
| 节点执行的一次完整回合收口在编排体的入口方法上 | `internal/ledgerstep/runner.go#StepRunner.Run` |

`ClaimDriver` 与 `HeartbeatDriver` 是**为这条路径造的、然后忘了接线**——这不是设计
缺口，是接线缺口。

## 方案

### 采纳：节点流用「只认领驱动」的原语，并在回合期间续期

**规则一（取得）**：节点执行开始时认领驱动权，用**不动状态列**的那个原语——
节点流的列由节点自己推进（`plan` → `implement` → …），把卡推去「进行中」是
实现流的语义，套到节点流上是错的。认领失败（已被别的会话持有且租约未过期）即拒绝
执行，报文带持有者会话名，与普通派发路径的报文同形。

**规则二（保持）**：节点执行期间周期性续心跳，续期间隔取 TTL 的**一半以内**
（安全裕度，具体值归 plan），执行结束即停。

**规则三（释放）**：回合结束（无论成败）释放租约，与普通派发路径失败回滚时的释放同形。

**收口位置**：三条规则都落在编排体的入口方法上——CLI 与 agentd 装配的是同一个
编排体，写在那里两条入口自动都有；分别写在两个装配层等于给同一条纪律准备两份会漂移的副本。

`card wait` 的长时订阅也属于「长时驱动」，但它不认领、只观察——**本 spec 不给它加
认领**（那会让「看一眼」变成「抢占」）。它的归属显示问题由规则一二解决：真正在驱动的
那个会话会持续续期，看的人读到的就是活的归属。

### 弃选

| 方案 | 弃选理由 |
|---|---|
| **在节点路径上直接复用普通派发的「转状态 + 落驱动」合并原语** | 它会把卡推到「进行中」。节点流的列是 `plan`/`implement`/`review`…，硬塞一个「进行中」既不在列序里，又会被工作流门拒——这正是卡上记的「裸 `card dispatch --template` 会把卡认领回进行中，与卡当前所在列冲突」那条 |
| **把 TTL 判据换成「有活跃订阅即视为在驱动」**（B189 卡上的候选修法之一） | 把租约的权威从账本挪到连接状态。连接会因为网络抖动断开又重连，租约会跟着抖；而且 agentd 侧的订阅数与协调者会话不是一一对应 |
| **干脆去掉 TTL，租约只能显式释放** | 会话崩溃就永久占着卡，需要人工解锁。TTL 是防僵死的，不该为了省续期把它拆了 |
| **在两个装配层（CLI 与 agentd）各写一份认领** | 同一条纪律两份副本，必然漂移。编排体就是为收口这类事存在的 |

## 用户故事

1. 作为协调者，我 `card dispatch <卡> --step <节点>` 之后，`card show` 能看到
   `driver_session` 是我这个会话，`handoff status` 里那条任务显示「卡 X 驱动 <会话>」
   而不是「无人值守」。
2. 作为协调者，我的节点跑了四十分钟，期间租约一直有效，别的会话来 `--step` 同一张卡
   被干净拒绝并被告知持有者是谁。
3. 作为第二个会话，我在第一个会话崩溃 5 分钟后可以接管这张卡（TTL 语义不变）。
4. 作为协调者，节点跑完（成功或失败）之后租约被释放，同一张卡的下一个节点可以由
   任何会话推进，不需要等 TTL。
5. 作为看板用户，`card wait` 观察一张卡不会把驱动权从真正在推它的会话那里抢走。

## 实现决定

- 续期的定时器随回合的上下文取消而停——不留后台 goroutine 泄漏。
- 续期失败（租约已被别人抢走）**不中止正在跑的回合**，但要落一条警告日志：回合已经
  派出去了，硬中止只会留下一个没人收的任务；归属丢失是可观测的事实，交给协调者判。
- 释放用幂等语义、只动自己持有的那份（既有原语已是这个语义），避免误释别人的租约。

## 测试决定（接缝清单）

一个缝：`ledgerstep.StepRunner.Run`（`internal/ledgerstep/runner_test.go` 已在这个缝上）。
四条断言：

1. 跑一个节点 → 卡的驱动会话被落上，且**状态列没有被改成「进行中」**；
2. 卡已被**别的**会话持有且租约未过期 → `Run` 拒绝，报文含持有者；
3. 回合结束（含失败路径）→ 租约被释放；
4. 长回合期间心跳被续过至少一次（用可注入的时钟或续期钩子断言，不靠真等 5 分钟）。

第 4 条要求 `Run` 里的续期有一个可注入的接缝；那个接缝的形状归 plan，但**必须存在**
——靠真实时间等 TTL 的测试是慢且偶发的，正是本仓已经吃过亏的那一族。

## Out of Scope

| 不做 | 分类 |
|---|---|

| 把租约状态推送到看板做实时归属显示 | 本期不做、后续要做（属自动化层，B156.3 一族） |
| B184 的播报逻辑本身 | 永不做改动——2026-08-23 实测已确认它的渲染路径是对的，缺的只是上游没人写驱动身份 |
| 普通派发路径（不带 `--step`）的认领行为 | 永不做改动——它已经对了 |
