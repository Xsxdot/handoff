# grok 任务级 home 的凭据归属设计（B26）

> 目标：让 handoff 跑 grok 任务不再破坏用户本人的 grok 登录态，也不再因为凭据被轮换走
> 而导致后续 dispatch 必然失败。
>
> 来源：backlog B26（优先级高）。2026-08-09 B3 真机验收实证。

## 1. 缺陷与根因

### 1.1 现象

任务 `30b92291` 跑完一个完整回合后，`<taskDir>/grokhome/auth.json` 从软链变成了
`-rw-------` 的普通文件（内容与 `~/.grok/auth.json` 不同），而 `~/.grok/auth.json` 仍停在
更早的旧令牌。后果有两层：

- **用户本人的登录态失效**：服务端已把旧 refresh token 轮换掉，用户的 `grok` CLI 只能
  重新 `grok login`；
- **handoff 自己也坏**：此后新派发的 grok 任务，软链指向的正是那份已被作废的旧凭据，
  `session/new` 直接返回 `Authentication required`，dispatch 报 500
  `grok 未登录或凭据已失效`。

### 1.2 触发频率（实测，不是估算）

devbox 上 `~/.grok/auth.json` 的账号条目实测字段：

```
create_time = 2026-08-09T09:55:11.522980Z
expires_at  = 2026-08-09T15:55:11.522980Z
```

**access token 寿命 6 小时。** 因此这不是罕见地雷——持续使用 grok 的一天里，每 6 小时
必然出现一次「任务跨过令牌刷新」的窗口。

> backlog B26 原记「跑完一个 grok 任务就把登录态弄失效」过强（已在 08-09 更正为
> 「任务恰好跨过一次刷新」）；本节把该条件量化为 6 小时一次，严重性回到高位。

### 1.3 根因

`EnsureAuthLink` 的函数注释写的原则是**准确**的：

> 为什么用软链而非拷贝：拷贝会让每个任务 home 各自持有凭据并独立刷新，而刷新令牌轮换
> 可能反噬用户本人的登录态——凭据只应有一个权威副本。

refresh token 是**一次性轮换**的：任何一方用它换到新令牌，服务端立即作废旧的，另一方
手里那份随之变成废纸。所以「只有一个权威副本」不是整洁诉求，是正确性要求。

**但软链执行不了这条原则。** grok 刷新令牌时是**替换目录项**（rename 或 unlink+create），
不是顺着软链写回目标文件。实证就是软链变成了普通文件而目标文件纹丝未动。硬链接同样
挡不住——替换目录项对硬链接的效果与软链一致。

`EnsureAuthLink` 的注释里其实已经记着「spike 实测任务级 home 的软链会在 token 刷新前后
消失」，但当时的对策只是「Start 与 Resume 都重建软链」——**重建只让下一次启动能读到
文件，救不回已经被轮换走的令牌**。

## 2. 不变量重述

原不变量「禁止出现第二份副本」无法维护（grok 会造，我们拦不住）。改成一条**可维护**的
形式：

> 权威副本永远是 `~/.grok/auth.json`。任务 home 里出现的副本是**临时的**，必须在有限
> 时间内被收回并消灭。

从「禁止出现」改成「允许出现，但必须及时收编」——这是软链做不到而周期巡检能做到的。

## 3. 被排除的方案

本节存在的目的是**防止后人重走弯路**，每条都钉上证据。

### 3.1 让任务级 home 复用真实 `~/.grok`，只隔离 config.toml —— 不可能

backlog B26 备注里记的第二个方向。三条独立证据否掉它：

1. `grok agent serve --help` 没有 `--permission-mode` / `--allow` / `--deny`（这些只在
   顶层 `grok` 命令上有），因此无法用命令行强制权限模式；
2. README 的 Environment Variables 表里，配置目录只有 `GROK_HOME`
   （「Override config directory (default: `~/.grok`)」）一个入口，**没有单独指定
   config 文件路径的变量**，因此无法把 config 指到 home 之外；
3. README 第 2021 行明写：**项目级 `.grok/config.toml` 只支持 `[mcp_servers]`，
   其余节（models 等）只从 `~/.grok/config.toml` 读**。

**config.toml 就是 home。** 要压掉用户真实配置里的 `permission_mode = "always-approve"`
（这是任务级 `GROK_HOME` 存在的首要理由，见 grok adapter spec §3.3），任务级 `GROK_HOME`
就取消不掉。凭据问题只能在「任务级 home 依然存在」的前提下解决。

### 3.2 用 `auth_provider_command` 接管刷新 —— 是假根治

grok 有企业级外部凭据助手契约（`[auth] auth_provider_command`，等价环境变量
`GROK_AUTH_PROVIDER_COMMAND`）。README 称「一个会话内两种方式互斥——配了
`auth_provider_command` 就由它承担全部中途刷新，否则才走 OIDC 静默刷新」。听上去能让
grok 在任务 home 里根本不自轮换，问题直接消失。

**它关不严。** 三条理由，第一条是决定性的：

1. **关不掉启动时的自轮换**。README 第 331 行描述的 login 时序是：先试 OIDC 静默刷新
   （**只要 `auth.json` 里存在 `refresh_token`**），再试外部助手，最后才是浏览器登录。任务 home 的
   auth.json 软链到真实文件，里面永远有 `refresh_token`——所以配了助手，**任务启动时撞上
   临期令牌，grok 照样自己轮换**。要堵住就得把 `refresh_token` 从 grok 看到的文件里剥掉，
   那是在篡改一个无文档的内部结构，破坏面不可预估。
2. **要维护两个无文档契约**。助手的 stdout 契约是文档化的，但「把刷新结果写回
   `~/.grok/auth.json` 供用户本人使用」要求精确复刻 auth.json 的内部结构（账号键格式、
   `key` / `auth_mode` / `expires_at` 等字段）。grok 升级改一个字段名，用户登录态就被我们
   **写坏**——比现状更糟，因为现状至少不碰权威文件的内容格式。
3. **并发协调一分没省**。多任务共用同一个 refresh token，助手一样要串行化、一样要合并
   写回。§4 方案里的全部「脏活」原样存在，只是换了触发点，再叠上协议风险。

结论：不是「巡检 vs 根治」，是「巡检 vs 一个关不严的假根治」。

> 助手无头刷新只有 7 秒超时，超时即被杀——这不是排除它的主要理由（refresh grant 就是
> 一次 HTTP POST，7 秒绰绰有余），但会放大上面第 2 条的风险，一并记录。

### 3.3 从头就用拷贝，放弃软链 —— 严格更差

既然软链终归会被替换，何不一开始就拷贝？不行：**软链的价值在被替换之前**。用户中途
重新 login、或别的任务刷新后被收编写回，软链任务能实时读到新凭据；拷贝任务抱着过期
快照，到点必死。「软链 + 被替换后收编恢复」是「尽量共享、破了就修」，严格优于「从不
共享」。

### 3.4 派发前临期预检 —— YAGNI，明确排除

「token 剩余寿命 < 阈值就先预刷新或拒发」。§4 的巡检已经把权威副本陈旧窗口收敛到 30
秒，预检是叠在上面的第二层保险，不做。

### 3.5 改用 `XAI_API_KEY` —— 技术上可行且能根治，因计费换轨而不做

**这条路线经真机验证确实成立**，记在这里是为了让后人知道它可行、以及为什么没选它。

实测（2026-08-09 devbox，全新 `GROK_HOME`，只放 `config.toml`、**不放任何 auth.json**，
设 `XAI_API_KEY` 后跑 `grok -p`，`--debug-file` 取证）：

```
resolved credentials model=grok-4.5 auth_type=ApiKey
authMethods: [xai.api_key, grok.com]   defaultAuthMethodId: "xai.api_key"
sending "authenticate" request: {"methodId":"xai.api_key"}
received "authenticate" response: {}
Received new session request ... session_id=019fe62d-...
```

跑完后该 home 目录里**从未出现过 `auth.json`**。

在这条路线上 B26 不是被缓解而是**不存在**：任务 home 里没有 OAuth 凭据，没有软链、
没有刷新、没有轮换，用户登录态在物理上不可能被碰；§6.1 与 §6.2 两条残余风险也一并
消失（API key 不过期）。下发通道现成——B19 的 env 注入正是干这个的。

不做的理由与代价：

- **计费换轨**：API key 走 console.x.ai 的按量计费，不是 Grok 订阅额度。这是产品决策
  不是技术决策，不该由本 spec 替用户决定；
- **握手要补一步**：当前 adapter 是 `initialize → session/new`
  （`adapter.go:202`、`adapter.go:211`），没有 `authenticate`——OAuth 路径下凭 auth.json
  已是已认证态。API key 路径必须显式发 `authenticate {"methodId":"xai.api_key"}`，且要
  按「是否注入了 key」条件分支，不能无脑加。

**因此本 spec 只实现 §4 的巡检写回。** 若将来用户愿意换轨，这条路线是 §6 两条残余风险
的彻底出路，届时单独立项即可，与 §4 不冲突（有 key 时跳过 `EnsureAuthLink` 即可共存）。

> 本节所有 README 行号取自 grok 1.0.0 自带的 `~/.grok/README.md`，随版本会漂移；引用的
> 是**内容**，行号只为方便复核。

## 4. 方案：周期巡检 + 收编写回

### 4.1 落点

新文件 `internal/executor/grok/authsync.go`。**不新增 goroutine、不动 agentd、不碰
`executor.Adapter` 通用接口**——搭在已有的 per-task 看门狗 `Adapter.watchdog`
（`internal/executor/grok/resume.go:118`）上：

- 看门狗在 `Start`（`adapter.go:185`）与 `Resume`（`resume.go:103`）两条路径都会起，
  覆盖全部活跃任务，包括停在 `waiting_review` 等审核的；
- 生命周期天然正确：`evClosed` 即退场，不会泄漏 goroutine；
- 看门狗循环节拍是 200ms/2s 双档，凭据巡检按运行态上的 `lastAuthSync` 节流到
  **30 秒一次**。`lstat` 是微秒级，节流只是为了别让日志和写盘变吵；
- `lastAuthSync` **只被该任务自己的看门狗 goroutine 读写**，因此是普通字段、不加锁；
  跨任务的并发面只在写权威文件那一步，由 §4.3 的包级锁收口。实现时不要顺手给它套
  `turnMu`——那会把一个无竞争的字段绑到高频回合锁上；
- **退场前补最后一次巡检**：serve 判死或任务终结时，若任务 home 里正躺着更新的凭据，
  不收编就永久烂在即将被归档的任务目录里。这不是第二套机制，是循环的出口路径。
  看门狗有**两个出口**（`evClosed` 正常退场、连续探活失败判死退场），**两个都要补**，
  漏一个就等于漏掉「任务跑挂了但刚刷新过」这一类。

`EnsureAuthLink` 保持不动。它负责「让任务能启动」，authsync 负责「让权威副本追上」，
两件事、两个函数。

### 4.2 一轮巡检

```
lstat(<taskDir>/grokhome/auth.json)
  ├─ 仍是软链 → 什么都没发生，直接返回（绝大多数轮次走这里，零成本）
  └─ 已变成普通文件 → 说明 grok 刚在这里刷新过
       ├─ 读任务副本 + 读 ~/.grok/auth.json，各自解析成账号字典
       ├─ 逐账号键比 expires_at：仅当任务侧严格更晚才收编该键，
       │  其余键保留权威副本原值
       ├─ 有要收编的键 → 在 ~/.grok/ 下写临时文件 + fsync + rename
       │  原子替换 ~/.grok/auth.json（0600）
       └─ 末尾一律把任务 home 的 auth.json 恢复成软链，不变量复位
          （无论本轮是否收编到东西；两处例外见 §5）
```

`expires_at` 按 RFC3339 解析成时间值比较，**不做字符串比较**；任一侧解析失败即视为
「不更晚」，走不收编路径（fail-closed，宁可少写一次也不写错）。

临时文件必须建在 `~/.grok/` 目录内——`rename` 只在同一文件系统内保证原子，写到
`/tmp` 再搬过去会退化成非原子的跨设备拷贝。

四个刻意选择：

**按账号键合并、不整文件覆盖。** `auth.json` 实测是
`{"<issuer>::<client_id>": {...}}` 的字典（devbox 实测键为
`https://auth.x.ai::b1a00492-…`），天然支持多账号。整文件覆盖会在用户有第二个账号时把
它抹掉。

**「严格更晚才写」是防误伤的核心。** 用户自己刚 `grok login` 过、权威副本比任务侧更新
时，绝不能倒着写回去。比较前重读一次权威文件，把竞态窗口压到 rename 前的几微秒。

**恢复软链是功能件，不是洁癖。** 不恢复也能持续收编，但那样任务 home 会长期持有独立
副本、独立刷新——更要命的是**其他任务的 home 里躺着的是旧拷贝**，下次临期必然拿旧
refresh token 去刷、必然失败。恢复软链才能让它们重新接上被收编后的权威副本，防的是
连环失败。恢复成本是一次 `symlink`；即使恢复瞬间 grok 又来替换，无非下一轮再收编一次，
无损。

**「没收编到东西」也必须恢复软链。** 这条是自审时补的，容易漏：任务侧副本**比权威副本
更旧**是真实场景（用户中途自己重新 login 过，或别的任务的新凭据已被收编写回），此时
任务 home 里躺的是一份陈旧拷贝，任务下次临期必然拿已作废的 refresh token 去刷、必然
失败。所以判据不是「收编成功才复位」，而是**「只要不是软链就复位」**——收编与复位是
两件独立的事，前者可能无事可做，后者只要发现破链就必须做。

### 4.3 并发写回

单个 agentd 进程内，多个任务的看门狗可能同时要写回。用**包级互斥锁**串行化 handoff 侧
的写回即可——不引入文件锁：

- grok 自己的 `~/.grok/auth.json.lock` 协议无文档（实测 15 字节，疑似 PID），跟着猜不如
  不猜；
- 原子 rename 保证并发读者（用户的 grok CLI）永远读到完整文件，不会读到半截；
- 与用户 CLI 同一瞬间写入的丢更新窗口被「重读 + 严格更晚才写」压到几微秒，且方向安全
  （只会少写一次，不会写旧覆盖新）。

## 5. 错误处理

| 情况 | 行为 |
|---|---|
| `~/.grok/auth.json` 不存在 | WARN 跳过，**且不恢复软链**（软链会指向一个不存在的目标，反而让下次启动更难诊断）。用户可能刚 `grok logout`，不替他凭空造回来 |
| 任一侧 JSON 解析失败 | ERROR 记录，**绝不写**权威文件；仍恢复软链（让任务接回权威副本，比留着一份读不动的拷贝好） |
| 任务侧凭据不比权威副本新 | Debug 记录，不写回，**照常恢复软链**（正常情况：用户自己重登过，或并发任务里第二个看到的已是收编后的） |
| 写临时文件或 rename 失败 | ERROR 带 cause；**保留任务侧副本、不恢复软链**——那份副本可能是唯一的新凭据，复位软链等于丢掉它。下轮重试 |
| 恢复软链失败 | ERROR 带 cause；写回已成功不回滚，下轮再试恢复 |

**日志纪律（沿用 B19 立的规矩）**：只打账号键、`expires_at`、任务 id 三样，
**任何情况下不打 token 值**，也不把凭据内容写进事件或 render.log。

**关键节点日志**（按 `instrumenting-code`）：

- Info「grok 凭据已收编写回权威副本」——带 task、账号键、新旧 `expires_at`；
- Info「grok auth 软链已复位」——带 task、link 路径；
- Debug「任务侧凭据不更新，跳过收编」——高频路径降级到 Debug，避免刷屏；
- 上表每个错误分支各一条 ERROR/WARN，带 cause 与路径。

## 6. 残余风险（明确接受并记录）

### 6.1 用户运行中的长驻会话救不回来

用户本人**正在运行**的 grok 会话，内存里持有的是旧 refresh token；handoff 这边轮换掉
之后，那个进程下次刷新仍会失败。**写回救的是「用户下次启动 grok」，救不了「用户当前
这个长驻会话」。** 彻底消除它只有 §3.5（改用 API key，任务侧根本不碰 OAuth 凭据）；
§3.2 那条是假根治，不算出路。

### 6.2 临期时刻的任务间并发竞态（本设计新引入的可见面）

所有活跃任务软链的是**同一个** token，`expires_at` 完全同步。更糟的是 grok 判临期用的是
本地时钟而非服务端 401——README 记有 `GROK_AUTH_EARLY_INVALIDATION_SECS`（默认 300），
即「`expires_at` 前 300 秒就视为过期」，**所有任务因此会在同一时刻一起认定该刷新**。
临期那一刻，凡是正在发 API 请求的任务同时拿同一个 refresh token 去轮换——**只有一个
能成功**。输家的刷新失败，该回合报错、任务浮给审核者。

- 窗口窄：只有恰好在临期那几秒活跃出请求的任务才参赛，挂在 `waiting_review` 等审核的
  不发请求、不参与；
- 赢家的新凭据被巡检收编，用户登录态无损；
- **伤的是单个任务的单个回合，不再是用户的登录态**——这是把 B26 从「静默地雷」降级成
  「可见的偶发回合失败」。

接受该风险。若真机上观测到它频繁发生，再单独立项（届时的解法是任务间刷新串行化，
或 §3.5 的 API key 路线；两者都与本 spec 不冲突）。

## 7. 测试

全是文件操作，可纯单测覆盖，**不需要真机蹲到令牌临期**：`os.UserHomeDir()` 在 darwin 上
读 `$HOME`，用 `t.Setenv("HOME", t.TempDir())` 就能造出假的权威 home，零重构。

单测用例：

1. 软链未被替换 → 零动作，权威文件 mtime 不变；
2. 普通文件且 `expires_at` 更晚 → 收编写回 + 软链恢复；
3. 普通文件但 `expires_at` **更旧** → **不写回**（防倒灌，误伤防线，必须有），
   **但软链仍被恢复**（自审补的那条：陈旧拷贝必须被消灭，否则任务下次临期必死）；
4. 多账号：只覆盖该账号键，其他键原值保留；
5. 权威文件缺失 → 跳过、不创建、**也不建软链**；
6. 任一侧 JSON 损坏 → 不写，权威文件**字节级不变**；软链仍被恢复；
7. 写回失败（构造权威目录不可写）→ **任务侧副本被保留、软链未被恢复**
   （这条守的是「别把唯一一份新凭据丢掉」，与用例 3 方向相反，必须分开验）；
8. 看门狗两个出口各一条：`evClosed` 正常退场、探活判死退场，退场前都跑了最后一次巡检。

真机验收只验一件事：**跨过一次真实的令牌刷新后，`~/.grok/auth.json` 的 `expires_at`
前进了，且紧接着派发的新 grok 任务能正常起来。** devbox 上令牌 6 小时一轮，蹲一次即可。
