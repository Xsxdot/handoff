# B185：环节执行体入驻 agentd（CLI 的 --step 秒回）

- 卡：B185
- 级别：**L3**（动跨进程 wire 契约，见「定级说明」）
- 档位：**轻档**（契约冻结照做，实现归一轮）
- 状态：**已批准**（2026-08-23，用户批准第二版）
- 审阅：第一版经独立审阅（Fable 5）判为「批准但砍掉」，据此收窄范围并修正承重墙论证；
  恢复半边拆至 **B225**（阻塞边 B185 → B225）

> 第二版变更：范围从「搬宿主 + 回合恢复」收窄为**只做搬宿主**。第一版把两件事
> 论证成「必须同卡」，那个论证是错的——它只证明了「恢复依赖搬宿主」，没排除
> 「先搬宿主、恢复后置」。详见「为什么恢复不在本卡」。

## 问题陈述

卡的标题写了三件事，事实调查后：

| 标题里的 | 现状 | 本卡 |
|---|---|---|
| `card wait` 订阅流 | **已存在** | 不做 |
| `card dispatch --step` 秒回 | 未做：CLI 在自己进程里同步跑编排（`cmd/card_node.go:48` 直接 `runner.Run`） | **做** |
| 回合状态落账可恢复 | 未做，且是**刻意推迟**（`internal/agentd/cardstep.go:9-12`） | 另立卡 |

协调者敲一次 `card dispatch --step`，会话就得挂着等几十分钟——2026-08-23 实测单卡
最长一轮 43 分钟。这段时间里协调者做不了别的，而 CLI 进程一旦死掉（Ctrl-C、
终端关闭、机器睡眠），这一轮的收口自动化就没了：裁决不会落账、卡不会挪列。

**agentd 侧其实已经建好了大半**：`startCardStep`（`internal/agentd/cardstep.go:39`）
已存在、已起 goroutine 异步执行、已有「同卡同时只允许一个环节在飞」的守卫，
端点 `POST /api/cards/{id}/step` 已存在且已 202。编排代码本就是单一真相源
（`cmd/card_node.go:2-3` 明写「看板按钮装配的是同一个 StepRunner，只是注入不同的传输」）。
**本卡把宿主进程也统一掉**，缺的是三样：端点收不下 CLI 的一次性覆盖项、
端点认不出 CLI 的身份、以及一条挡住 implement 的错守卫。

## 方案

**采用**：CLI 的 `--step` 改为向本机 agentd 提交环节请求后立刻返回；agentd 成为唯一
跑 `StepRunner` 的地方。

三条支柱：

1. **单一执行体**。CLI 与看板都经同一端点提交，编排只在 agentd 里跑。
2. **一次性覆盖项与发起人身份上 wire**。`--target/--executor/--model`（B203）与
   `--extra`（B214）都是刚做完的一次性覆盖项，端点今天只收 `{step}`；发起人身份
   今天硬编码为 `web:` 前缀。两者都必须上 wire，否则 CLI 走过去等于让 B203/B214
   的成果失效、并让所有 CLI 派发在 timeline 上变成同一个匿名 web 客户端。
3. **implement 守卫的语义修正**。见接缝二。

### 弃选

- **弃选 A：CLI 保留本地编排，只额外提供「提交到 agentd」作为可选模式。**
  两套宿主并存会让「谁在编排这张卡」重新变得不可知——而那正是本卡要消灭的东西。
  降级路径的代价见「实现决定」。
- **弃选 B：不搬宿主，只把 CLI 的等待做成可中断/可重入。** 治标：会话仍要挂着，
  且 CLI 死后仍然没有任何进程接手收口。它也不为将来的恢复铺任何路。
- **弃选 C：连恢复一起做（第一版方案）。** 见下节。

## 为什么恢复不在本卡

第一版论证「两件必须同卡」，理由是 B189（`15dfc51f8`）**刻意废除了驱动租约的 TTL
过期语义**并删掉了心跳协程，裁决原文：

> 驱动方是有人在后面的会话，不是会静默死亡的进程；TTL 买到的收益前提不成立，
> 代价是人还在时被静默接管——双驱动互不知情比卡住更坏。

**这个论证只成立一半**：它证明了「自动恢复只能针对进程确知的死亡，因此**恢复依赖
把编排搬进常驻进程**」，但**没有排除「先搬宿主、恢复后置」**。后置的代价经核对为零：

- 本卡①单独交付「秒回」与「覆盖项仍生效」的全部价值；
- 恢复的判据是**读事件流的纯函数**，本卡的任何设计都不因它存不存在而改变；
- 缓做恢复的代价，就是 agentd 重启会孤儿化在飞环节——**而这正是看板路径今天的
  现状**，且已被 `cardstep.go:9-12` 白纸黑字裁决为「刻意的取舍，不是遗漏」。
  同一个取舍对看板可接受、对 CLI 不可接受，缺乏理由。
- **更关键**：激发本卡的那次事故（2026-08-23 一个任务冻结 76 分钟）真根因在
  **任务层**（agentd 重启丢了 executor 的终态事件，`resume` 的对账补回对 codex
  不支持）。环节层的恢复撞上它仍然只能转等人。**任务层修好之前，恢复的边际价值
  是打折的**——这决定了它的排期，不是它的归属卡。

**恢复另立卡，排在任务层终态事件丢失修复之后。** 两条已落 `docs/roadmap.md`。

## 用户故事

1. 作为协调者，我敲 `card dispatch <卡> --step <节点>` 后**立刻拿回控制权**，
   命令打印**卡号与节点名**并告诉我进展去哪看；要盯就自己敲 `card wait`。
2. 作为协调者，我在 `--step` 上传的 `--target/--executor/--model/--extra` **仍然生效**，
   与今天的行为逐字一致。
3. 作为协调者，卡的 timeline 上能看出**是哪个 CLI 会话**发起的这一轮，
   两个并发会话不会记成同一个身份。
4. 作为协调者，implement 节点**可以**经 `--step` 派发（今天它被硬拒），
   除非本次请求真的要求内联一个调用方本地文件。

## 契约语义与接缝（L3）

**只定语义，不定签名**——精确签名由 contract 节点对本轮工作树查证后落地。

### 接缝一：`POST /api/cards/{id}/step` 的请求语义

- 今天只承载节点名（`internal/agentd/ledgerapi.go:399-401`）。要扩成同时承载
  **本次派发的一次性覆盖项**（目标机、执行器、模型、一次性补充说明）与
  **发起人身份**。
- 覆盖项的**优先级沿用 B203 已冻结的规则**（CLI > 节点覆盖 > 模板），
  **成对规则照旧**：任何一层覆盖了执行器却没在同层给模型，就不得继承下层模型。
  本卡不改这条规则，只把它搬到 wire 上。
- **发起人身份是必须字段而非可选**：`StepRunner.Session` 的注释明确要求
  「CLI 使用带 pid 的运行会话，agentd 使用请求 actor；**它必须能区分两个并发驱动者**」
  （`internal/ledgerstep/runner.go:26-28`）。端点今天把 actor 硬编码为
  `"web:" + r.RemoteAddr`（`ledgerapi.go:413`）。若 CLI 不带身份走过去，
  所有 CLI 派发都记成同一个 `web:127.0.0.1`，B189 的 CAS 认领将失去分辨力
  ——那恰好是 B189 要防的「双驱动互不知情」。
- 新增字段**全部可选**（身份除外，见「实现决定」），看板无需改动即可继续工作。
- 响应保持「受理即 202」。

### 接缝二：implement 守卫的语义修正

今天 `handleCardStep` 硬拒 `implement`，理由写作「浏览器没有 plan 文件」
（`ledgerapi.go:396-401`）。**这条判据的主语错了**：真正不可达的是**调用方进程 CWD
里的那个文件**（`internal/ledgerstep/dispatch.go:94-95` 明写「`req.PlanPath` 按调用方
进程的 CWD 解析，agentd 一侧永远传空串」），而不是 implement 这个节点。

**静态铁证**：`StepRunner` **根本没有 `PlanPath` 字段**（`internal/ledgerstep/runner.go`），
`--plan` 只进不带 `--step` 的直派路径（`cmd/card_dispatch.go:192`）。也就是说
**经 `--step` 派发的 implement 从来就没有内联过任何本地文件**——plan 靠 git 分支
与附件路径到达执行者。（旁证：2026-08-23 B201 走了四轮 implement，`dispatched`
事件里没有一个带 `plan_path`。）

**语义修正**：守卫的判据从「节点名是不是 implement」改为「本次请求是否要求内联
一个调用方本地文件」。不要求内联的请求一律放行，与节点名无关。

### 接缝三：驱动归属

环节改由 agentd 托管后，卡的驱动会话身份由谁持有必须显式定义：**持有的是发起人的
身份，不是 agentd 的身份**——否则 B189 的「非空驱动一律拒」会把所有后续操作
都挡在一个匿名 agentd 名下。释放时机同理由 contract 节点对照 `ReleaseCard`
既有语义落定。**约束：不得引入 TTL 或心跳续租**（B189 已裁决）。

## 实现决定

- **CLI 不做「本机 agentd 不可用时回落本地直跑」的降级。** 干净失败并说清原因。
  理由见弃选 A。**这是新增的硬依赖**：今天 CLI 只需本地账本 + 直连目标机 agentd
  即可派发，本机 agentd 没起也能跑；本卡之后本机 agentd 必须活着。
- **CLI 拿到 202 后立刻返回**，打印卡号与节点名，并提示「进展见 `handoff card wait <卡>`」。
  **不打印 task id**：agentd 受理时 dispatch 尚未发生（它在后台 goroutine 里），此刻
  没有 task id；且一个节点回合可能产生多个 task。第一版写「打印任务标识」是措辞不准，
  由 breakdown 轮的「契约疑点」指出、协调者裁决更正（P2），**不重开契约**。
  **不跟随事件流**——跟随到终态等于把阻塞从编排换成旁观，与用户故事 1 互斥。
- 对外行为变更两条，须写进 CHANGELOG：`--step` 不再打印 `Outcome`；
  `--step` 新增对本机 agentd 的依赖。

## 测试决定（接缝清单）

落在**两个**接缝上，均为既有夹具，本卡不新建接缝：

1. **wire 契约固定件**（Go 侧生成 → `web/src/api/testdata/*.json` 逐字节比对，
   `internal/proto/contract_fixture_test.go:52`）：端点请求新增字段的唯一防漂移点。
2. **CLI 装配层**：flag → 请求 → `TemplateDispatch` 覆盖项透传，沿用 B203/B214
   已有的 `swapDispatchTransportWithOpts` 夹具。

变异必查项：覆盖项在 wire 上丢字段；成对规则失效；发起人身份退化成硬编码
`web:`；implement 守卫改宽到放行内联请求、或改窄回按节点名拒。

## Out of Scope

- **回合状态落账可恢复**（原方案的另一半）→ **另立卡**，排在下条之后。
- **任务层的终态事件丢失**（2026-08-23 那次 76 分钟冻结的真根因）→ 已落 roadmap。
- **重新引入编排者活性探测**：要做必须先推翻 B189 的裁决 → 已落 roadmap。
- **规则引擎自动点火下一环节**（B156.3 三期）。本卡是它的地基，不含它本身。
- **`card wait` 的任何改动**；**看板 UI 改动**。

## 定级说明

按 charter 定级两问：跨子系统的契约面改了一处（CLI ↔ agentd ↔ web 共用的 step
端点请求形状），且**动契约层**——该端点是跨进程 wire，并有契约固定件冻结它。
故 **L3**。

选档：单子系统工作量均不超过流程固定成本，且本卡的全部风险恰好集中在契约那一段
（四个覆盖项 + 身份字段 + 一处守卫语义反转），**轻档**把功夫放在契约冻结上、
实现归一轮，正对风险落点。不扇出子卡。
