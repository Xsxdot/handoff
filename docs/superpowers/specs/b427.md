## 问题与现状

用户报告桌面端快、移动端会话快，但移动端进入工作项列表与打开某张工作项均需约两秒以上。这个两秒是用户观察，当前尚未在真实手机复现。

基线的已确认请求放大有三处：移动端打开卡会写入 `card` URL 参数，工作项将它解释为加载全部历史卡；工作项与常驻 Shell 各自加载卡、决策和任务；钉版本工作流批量加载时，一个缺失版本会令已成功结果丢失。源码现状出处如下，执行节点须在本轮工作树复核：

- `web/src/app/shell/useMobileNav.ts:255-277`：移动端打开卡写 `/cards?card=…`。
- `web/src/app/cards/CardsPage.tsx:161-164`、`:201`：存在 `card` 参数即切到 `all=1`，参数变化再刷新。
- `web/src/app/shell/Shell.tsx:131`、`:218-219`、`:1183-1190` 与 `web/src/app/cards/CardsPage.tsx:162-164`、`:184`：Shell 已有任务、卡与决策流，移动工作项条件挂载后另起相同流。
- `web/src/app/cards/CardsPage.tsx:286-305`：钉版本工作流走整批 `Promise.all`，失败不保存成功项；`:309-311`：深链选中依赖列表中已有目标卡。
- `web/src/app/cards/CardDrawer.tsx:350-364`：既有单卡详情入口可按 ID 请求并呈现加载/错误状态。

本机接口样本显示当前卡与全部历史卡的响应规模相差明显，但不能用本机 API 读数替代手机网络与 DOM 渲染耗时；详细样本、未验证环境与图查询结果留在台账。

## 批准方案

1. 打开卡详情只选择该卡，不隐式切换到全部历史卡。用户显式启用历史范围时，保留现有历史列表功能。
2. 移动端工作项消费 Shell 已有卡、决策与任务数据，首次进入及返回时不为同一数据再首拉或另起轮询。独立工作项入口保留自己的数据来源。
3. 钉版本工作流各项独立保存成功结果；某个版本 404 不撤销其他成功项，也不在每次卡轮询时重取该缺失版本。暂时网络故障与不存在的版本分开处理。
4. 历史终态卡的深链通过既有单卡详情按 ID 恢复，不为找一张卡请求全部历史卡。当前卡详情、桌面普通点击与返回路径继续成立。

实现者可决定局部的数据注入与缓存表示，但不能增设新的全局缓存框架、改变账本权威状态、持久化失效规则或引入后端端点。缺失版本的记忆限于当前数据来源作用域；切换来源后不得沿用旧来源的卡、工作流或失败结果。未授权具体手机耗时目标，验收记录同环境前后读数及请求变化，不预先宣称两秒已解决。

弃选：只降低轮询频率不能消除详情隐式全历史请求；先合并 SQL 不能消除前端重复消费。本期先验证批准的前端修复，若真实手机仍慢，再依据请求与渲染证据定性。

## 测试与完成边界

先通过真实生产组件及 fetch 边界证明请求放大与重复消费的反例，再实现最小修复。局部纯函数或字符串断言不能替代 Shell 切换、点卡、深链和列表 DOM 行为。最终运行全量 Web 类型检查、测试与构建，并保留成功输出和既有失败的原始证据。

最终手机验证须在同一手机、同一服务入口记录列表首次、打开详情、返回再进入的可见结果、请求数量/范围及网络等待与渲染耗时。若手机或受管调试入口不可用，代码与自动化阶段可以交接，但 **B427 的真实手机性能验收仍未通过**；模拟移动视口、本机接口与构建不能替代该结果。
