### B235：下一节点起点 = 工作分支本地尖端与 origin 同名分支的快进并集

现状读数（`main` @ `6c59a3878` 仍适用，B277 只加了文档）：

- 后续节点覆盖基线：`internal/ledgerstep/dispatch.go:214-217`。有工作分支时 `base = workInfo.Branch` 且 `LocalBaseBranch = true`。卡的 `EffectiveBaseBranch` 只进 prompt 的「合并目标」，不进 git 起点。
- 工作分支定义：`internal/ledger/events.go:400-442` `WorkBranch` = 最近一次非审阅 `dispatched` 的分支名。
- 本地起点：`internal/agentd/workspace.go:1023-1030` `resolveLocalBaseBranch` **故意不 fetch**，注释写明「拿 origin 的陈旧镜像替代它会把接续节点悄悄带回错误代码」。
- `DispatchSnapshot`（`internal/ledger/events.go:115-131`）记了 `branch`，不记起点 sha。
- 旁证：`cmd/card_dispatch_test.go:407-409` 把 `--extra` 说成「往工作分支塞提交」这条路的逃生口。

源卡第一方案「改用卡的 `base_branch` 并 fetch」**弃选**。理由：BM1.1 现场里卡分支 `card/BM1.1-judge-calibration` @ `e38140d` 与工作分支 `cards/BM1.1-charter-2` @ `82f2767` 互不为祖先。若下一节点从卡分支起，上一节点的代码不在祖先里，静默丢实现。B192 要保的就是执行机本地工作分支。

推荐（B192 不变量保留，补上「origin 已快进」这一面）：

1. **有工作分支且同机**：仍然 `Base = 工作分支名`、`LocalBaseBranch = true`。跨机拒发原文不变。
2. **`LocalBaseBranch` 解析改为「本地 vs origin 同名分支，取快进并集」**：
   - fetch `origin/<工作分支>`（没有这条远端分支不算错，退回纯本地）；
   - 本地是 origin 的后代或 origin 不存在 → 起点 = 本地（执行者未 push）；
   - origin 是本地的后代 → 起点 = origin（协调者往**同一条**工作分支 push 了）；
   - 两边存在且互不为祖先 → **拒发**，文案必须同时给出两个 sha，并写「工作分支本地与 origin 已分叉，先合并再派」。禁止悄悄选任一侧。
3. 禁止用 origin 回退本地。这是 B192 要挡的那一类事故，本卡不得打开。
4. **卡 `effective_base_branch` 与工作分支名字不同**：不自动合、不改起点。派发 stderr 必须警告：卡基线分支上的新提交不会进入本节点，要把它们并进工作分支再派。BM1.1 那种「拍板写在另一条 worktree 分支」会从静默丢失变成看得见的警告；真正带上那些提交的动作仍是协调者合并，不是 dispatch 自动 merge。
5. `dispatched` 快照补两个键：`base`（本次用作起点的分支名）、`base_commit`（40 位 sha，从派发应答已有的 `BaseCommit` 回填）。这是源卡「至少打进事件」那条。老事件无此键，append-only 不回填。

无工作分支（首派）保持今天：`EffectiveBaseBranch` 走远端补拉，空则 `resolve_default_base`。

弃选：下一节点改从卡 `base_branch` 起；dispatch 自动 merge 两条不同名的历史；给 `card dispatch --step` 加 `--base` 当主修法（逃生口可另议，不构成本期主路径）。

### B257：同仓库 fetch 串行，锁竞争不得叫「基线不存在」

现状读数：

- 分支补拉：`internal/agentd/workspace.go:1152-1156`。`git fetch` 失败一律 `%w: 基线分支 %q 从远端 %q 补拉失败` 包进 `ErrBaseCommitMissing`（sentinel 原文是「基线提交在任务仓库中不存在」，`workspace.go:81-83`）。
- HTTP：`internal/agentd/server.go:1214-1216` 凡 `errors.Is(..., ErrBaseCommitMissing)` 记成「任务仓库落后于本地基线」并 400。
- 现场 fetch 原文含 `cannot lock ref ... is at X but expected Y`，X 正是先到那次已经推上去的 sha。

真因是同一 agentd 进程里两条派发 goroutine 对同一仓库 `git fetch` 同一 remote ref。git 的 ref 锁是对的；缺的是进程内互斥。退避重试是锁已经被别人拿过之后的补救，不是根因。

推荐：

1. **根因**：agentd 对同一仓库路径的出网 fetch（`git fetch` / `fetch --all`）加进程内互斥。后到的那次等先到的那次结束再 fetch，不应再撞 `cannot lock ref`。
2. **残留**：互斥之后 stderr 仍含 `cannot lock ref`（陈旧 `.lock`、或非本进程占用）→ 同一把锁内再试最多 2 次，间隔要短于派发超时、长于 git 放锁。
3. **归因**：上述路径耗尽仍失败，**不得**再 `errors.Is(..., ErrBaseCommitMissing)`。独立 sentinel，HTTP 仍 400，但报文首句必须是「基线补拉失败（远端 ref 锁竞争）」这类，并带 fetch 原文。禁止出现「基线提交在任务仓库中不存在」或「请先在本地 git push」——那两句会把人送去查 push / 分支名，而那些都是对的。
4. 真缺失（远端没有这条分支、对象库没有这个 sha）继续走今天的 `ErrBaseCommitMissing` 与 git push 提示。

弃选：只改文案不互斥；全局一把锁（无关仓库也排队）；协调者侧「兄弟卡必须串行」当唯一修法（那是规避，不是修）。

## 用户故事

1. 协调者在工作分支上 commit 并 `git push` 之后派下一节点，新分支的起点包含这些提交。
2. 执行机本地工作分支比 origin 新（执行者还没 push），下一节点仍从本地尖端起，不回退。
3. 本地与 origin 同名工作分支分叉时，派发失败并打出两个 sha，不静默选边。
4. 卡基线分支和工作分支不同名时，stderr 警告卡分支上的提交不会自动进来。
5. `dispatched` 事件能回答「这次起点是哪个 sha」。
6. 同一执行机、同一基线，两张卡相隔约 1 秒首派，两次都成功；即使仍撞锁，报文也不再说「基线不存在」。
7. 执行者把 breakdown 写成带日期前缀的文件名时，卡转等人，body 指出该改成哪条法定路径。
8. `handoff card show` 里 `tasks[].task_id` 与 `relations[].from` 可读，不再是 `None`。

## 测试决定（接缝清单）

1. **B235 快进并集** — 符号：`resolveLocalBaseBranch`（生产调用方 `resolveDispatchBase`）。断言必须真走 git：本地领先 origin → 起点是本地 sha；origin 快进领先 → 起点是 origin sha；分叉 → 错误含两个 sha 且不含「基线提交在任务仓库中不存在」。`LocalBaseBranch` 为真时不得走到「只信 origin、丢掉本地提交」的 D2 旧路径。
2. **B235 快照与警告** — 符号：`RecordDispatch` 的 payload 与卡派发 CLI stderr。断言：新 `dispatched` 含 `base` 与 40 位 `base_commit`；卡基线分支名 ≠ 工作分支名时 stderr 含「不会进入」语义。
3. **B257 同仓串行** — 符号：出网 fetch 的仓库互斥点（与 `gitRunNet` 的 fetch 调用同一把锁）。断言：两条 goroutine 同时补拉同一仓库同一分支，两次都成功且都不含 `cannot lock ref`；互斥不得跨仓库误伤。
4. **B257 归因** — 符号：`ResolveBaseBranch` / `writeDispatchError`。断言：锁竞争耗尽时 HTTP/错误文本含「锁竞争」或等价，**不含** sentinel「基线提交在任务仓库中不存在」；真缺失仍是 `ErrBaseCommitMissing`。
5. **B251 匹配与提示** — 符号：`containsPath` 的生产调用（产出校验段）+ `buildPrompt`。断言：改动列表只有带日期前缀的形似路径时仍 `haltForHuman`、不路由 `on_fail`；body 含法定路径；prompt 含「日期前缀」。精确相等仍通过。禁止改成后缀匹配还让测试绿。
6. **B260 CLI 键名** — 符号：`TaskLink` / `ledger.Relation` 的 JSON（`wire_test`）以及 CLI `card show` 真跑。断言：`tasks` 含 `task_id` 不含 `TaskID`；`relations` 含 `from` 不含 `From`。禁止只测 marshal 辅助函数、不跑 `card show`。
