### B235：下一节点起点 = 工作分支本地尖端与 origin 同名分支的快进并集

现状读数（`main` @ `6c59a3878` 仍适用，B277 只加了文档）：

- 后续节点覆盖基线：`internal/ledgerstep/dispatch.go:214-217`。有工作分支时 `base = workInfo.Branch` 且 `LocalBaseBranch = true`。卡的 `EffectiveBaseBranch` 只进 prompt 的「合并目标」，不进 git 起点。
- 工作分支定义：`internal/ledger/events.go:400-442` `WorkBranch` = 最近一次非审阅 `dispatched` 的分支名。
- 本地起点：`internal/agentd/workspace.go:1023-1054` `resolveLocalBaseBranch` **故意不 fetch**。`fetched` 恒 false。
- `DispatchSnapshot`（`internal/ledger/events.go:115-131`）记了 `branch`，不记起点 sha。
- `--step` 主路径：`cmd/card_node.go` POST 本机 agentd 后 202；ViaTemplate 在 `internal/agentd/cardstep.go:81-84` 异步跑。这次 CLI 进程没有 ViaTemplate 的 stderr。
- `ledgerstep.Transport` 只返回 `taskID`（`dispatch.go:45-46`）。`cliTransport` 与 `stepTransport` 都拿到 `task.BaseCommit` 后丢掉（`cmd/card_dispatch.go:76-97`，`cardstep.go:178-208`）。
- 旁证：`cmd/card_dispatch_test.go:407-409` 把 `--extra` 说成「往工作分支塞提交」这条路的逃生口。

源卡第一方案「改用卡的 `base_branch` 并 fetch」**弃选**。BM1.1 里卡分支与工作分支互不为祖先；从卡分支起会丢掉上一节点实现。

推荐（B192 不变量保留：本地更领先时不得被 origin 顶替；本地存在时不得因 origin 挂了而派不出）：

1. **有工作分支且同机**：仍然 `Base = 工作分支名`、`LocalBaseBranch = true`。跨机拒发原文不变。
2. **`LocalBaseBranch` 解析改为「本地 vs origin 同名分支，取快进并集」**：
   - 本地 `refs/heads/<工作分支>` 必须存在，否则保持今天的 `ErrBadWorkspaceReq`。
   - 尝试 fetch origin 上的同名分支（这次 fetch **走 B257 同一把 per-repo 锁**）。
   - 本地是 origin 的后代，或 origin 没有这条分支，或 **fetch 任何失败**（找不到 ref、网络、认证、超时）→ 起点 = 本地。**不得拒发。**
   - origin 是本地的后代 → 起点 = origin（协调者往**同一条**工作分支 push 了）。
   - 两边都拿到 sha 且互不为祖先 → **拒发**，独立 sentinel（不得 `errors.Is(..., ErrBaseCommitMissing)`），HTTP 400，文案含两个 sha 与「工作分支本地与 origin 已分叉，先合并再派」。
3. 禁止用 origin 回退本地。并集结果只作为**新分支**的起点 sha，不得 `reset` / `fetch origin work:work` 去移动已有工作分支 ref。
4. **不同名的卡 `effective_base_branch`**：不自动合、不改起点、**不在每次 `--step` 上打警告**（工作分支名与卡基线几乎总是不同，警告会变成噪音，且 `--step` 的 CLI stderr 看不见 agentd 解析结果）。可见性：`dispatched` 带 `base` / `base_commit`；skill 写明节点之间的提交必须落在工作分支。BM1.1 那种写在另一条 worktree 分支上的提交仍要协调者自己合并，本期不自动带上。
5. **`base_commit` 回填路径钉死**：`Transport` 与 `DispatchResult` 必须带回 agentd 应答里已经有的 40 位 `Task.BaseCommit`。`cliTransport` 与 `stepTransport` 都要传。禁止协调者本地 `git rev-parse` 猜测执行机解析结果。`RecordDispatch` 快照补 `base`（本次用作起点的分支名）、`base_commit`（40 位 sha）。所有新 `dispatched` 都带（含首派）；老事件缺键，`omitempty`，append-only 不回填。

无工作分支（首派）保持今天：`EffectiveBaseBranch` 走远端补拉，空则 `resolve_default_base`。

弃选：下一节点改从卡 `base_branch` 起；dispatch 自动 merge 两条不同名的历史；给 `card dispatch --step` 加 `--base` 当主修法；把「不会进入」钉在 `--step` 的 CLI stderr。

### B257：同仓库 fetch 串行，锁竞争不得叫「基线不存在」

现状读数：

- 分支补拉：`internal/agentd/workspace.go:1152-1166`。`git fetch` 失败一律包进 `ErrBaseCommitMissing`；成功则 `rev-parse FETCH_HEAD`。
- SHA 补拉：同文件 `1108-1121` `fetch --all --prune`，失败同样进该 sentinel。
- HTTP：`internal/agentd/server.go:1214-1216` 凡 `errors.Is(..., ErrBaseCommitMissing)` 记成「任务仓库落后于本地基线」并 400。未知错误走 500「派发任务失败」（约 1241–1243 行）。
- `FetchTimeout` 2 分钟（`workspace.go:834-836`）。
- `gitRunNet` 还服务于 clone（`projectadmin.go` 等）。clone 不是 fetch。

真因是同一 agentd 进程里两条派发 goroutine 对同一仓库 `git fetch` 同一 remote ref。git 的 ref 锁是对的；缺的是进程内互斥。退避重试是残留，不是根因。

推荐：

1. **根因**：按仓库路径（`filepath.Clean`）对出网 **fetch**（`git fetch` / `fetch --all`）加进程内互斥。B235 的 origin 同名 fetch、`ResolveBaseline` 的 `fetch --all`、`ResolveBaseBranch` 的 `fetch <remote> <branch>` 走**同一把锁**。clone **不**进这把锁。
2. **锁必须覆盖「fetch + 读本次目标 ref」**。禁止用 `FETCH_HEAD` 当起点 sha（并发另一次 fetch 会覆盖它）。`ResolveBaseBranch` 改读 `refs/remotes/<remote>/<branch>`；本地工作分支读 `refs/heads/<branch>`。
3. **残留**：互斥之后 stderr 仍含 `cannot lock ref` → 同一把锁内再试最多 2 次，间隔 50–200ms。不得把 `FetchTimeout` 叠成三次满额（总预算须明显小于客户端派发超时）。
4. **归因**：上述路径耗尽仍失败，独立 sentinel，**不得** `errors.Is(..., ErrBaseCommitMissing)`。`writeDispatchError` 单开 400 分支。报文首句必须是「基线补拉失败（远端 ref 锁竞争）」这类，并带 fetch 原文。禁止出现「基线提交在任务仓库中不存在」或「请先在本地 git push」。
5. 真缺失（远端没有这条分支、对象库没有这个 sha）继续走今天的 `ErrBaseCommitMissing` 与 git push 提示。

弃选：只改文案不互斥；全局一把锁；协调者侧「兄弟卡必须串行」当唯一修法；锁只包 `gitRunNet` 调用、读 ref 放在锁外。

## 用户故事

1. 协调者在**工作分支**上 commit 并 `git push` 之后派下一节点，新分支的起点包含这些提交。
2. 执行机本地工作分支比 origin 新（执行者还没 push），下一节点仍从本地尖端起，不回退。
3. 本地工作分支存在时 origin 不可达 / 没有这条远端分支，下一节点仍从本地起，不拒发。
4. 本地与 origin 同名工作分支分叉时，派发失败并打出两个 sha，卡上 `needs_human` 看得见，不静默选边。
5. `dispatched` 事件能回答「这次起点是哪个分支、哪个 sha」。
6. 同一执行机、同一基线，两张卡相隔约 1 秒首派，两次都成功；即使仍撞锁，报文也不再说「基线不存在」。
7. 执行者把 breakdown 写成带日期前缀的文件名时，卡转等人，body 指出该改成哪条法定路径。
8. `handoff card show` 里 `tasks[].task_id` 与 `relations[].from` 可读；HTTP 详情仍是 PascalCase。

## 测试决定（接缝清单）

1. **B235 快进并集** — 符号：`resolveLocalBaseBranch`（生产调用方 `resolveDispatchBase`）。真 git：本地领先 → 起点是本地 sha；origin 快进领先 → 起点是 origin sha；分叉 → 错误含两个 sha，且 `errors.Is` 不是 `ErrBaseCommitMissing`；本地存在 + origin 不可达 → 起点是本地、派发成功。`LocalBaseBranch=true` 不得调用 `ResolveBaseBranch`。事后 `refs/heads/<旧工作分支>` 仍是原 tip。禁止 mock 掉 git。
2. **B235 快照** — 符号：`RecordDispatch` 的 payload。新 `dispatched` 含 `base` 与 40 位 `base_commit`。必须覆盖 `stepTransport` 路径（`--step`），不能只测裸 `card dispatch`。`base_commit` 来自 Transport 回传，不是协调者本地 rev-parse。名字不等且卡基线是祖先时**不得**要求 CLI stderr 警告。
3. **B257 同仓串行** — 符号：出网 fetch + 读目标 ref 的同一把 per-repo 锁。两条 goroutine 同时补拉同一仓库同一分支，两次都成功且都不含 `cannot lock ref`；跨仓库不误伤。并发 fetch **两个不同分支**（或 `fetch --all` vs `fetch origin <work>`），各自 sha 不错位。clone 不得被这把锁挡住。禁止只测「有 mutex」。
4. **B257 归因** — 符号：`ResolveBaseBranch` / `writeDispatchError`。锁竞争耗尽：HTTP 400，文本含「锁竞争」或等价，不含 sentinel「基线提交在任务仓库中不存在」、不含「请先在本地 git push」。真缺失仍 `errors.Is(..., ErrBaseCommitMissing)` 且 400。`ResolveBaseline` 的 `fetch --all` 与 `ResolveBaseBranch` 抢同一把锁。
5. **B251 匹配与提示** — 符号：产出校验段（`containsPath` 的生产调用）+ `buildPrompt`。只有日期前缀形似路径 → `haltForHuman`，`Outcome.Action == ActionNeedsHuman`，不 `routeTo(breakdown)`；body 含法定路径与「请改名为」；prompt 含「日期前缀」；精确相等仍 pass。禁止改成后缀匹配还绿。
6. **B260 CLI 键名 + HTTP 负例** — 符号：`TaskLink` / `ledger.Relation` 的 JSON 以及 CLI `card show` 真跑。`tasks` 含 `task_id` 不含 `TaskID`；`relations` 含 `from` 不含 `From`。HTTP `GET /api/cards/:id` 的 `relations[]` 仍含 `From` 不含 `from`，`task_states[]` 仍含 `TaskID` 不含 `task_id`（可复用既有 contract fixture）。禁止只测 marshal 助手。

禁止用同一条夹具冒充两条缝。四条禁止抽公共 fake Git 门面同时冒充缝 1 和缝 3。
