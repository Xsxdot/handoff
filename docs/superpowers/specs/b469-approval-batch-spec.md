## 问题与方案

用户裁决原话（卡 #33005 转录）：「1，原来的工单没人收，2. 同意 3. 补进去」。本期 B469 修复**会话房间里唤起的执行者产生的原有任务工单没有审批责任人收到**；任务已有 permission/question 工单，不把故事替换成驻场协调者自身 CLI 权限桥。现状 `internal/agentd/wakeconsumer.go:215,502,746` 将工单映射为 WakeTicket，再按卡席位路由；origin pull 返回空是既有 `card wait` 契约，不应改成 push 或冒泡。房间驻场身份与卡席位不同，不能以“有 task”推导广播房间。

方案分三线：先修 B463 命令分析与审批环可观测；再做 B458 规则生命周期和 B470 解释/去重；B469 另以原任务工单验证明确归属和可靠收件。三线共用明确事实和审批语义，不建通用规则引擎。已有 B460/B465 的任务目标、工作树、产物/临时目录、只读政策与跨机上下文直接复用。

## 落位三问与架构

① 审批领域拥有条件规则、分类、求值、撤销/过期和裁决来源；任务编排拥有原工单与投递；agentd/会话领域拥有任务发起关联、房间驻场关系及审批责任路由；账本保存这些各自权威事实和不可变事件，不解释规则。

② 任务权限链消费统一审批能力；CLI/UI 经管理应用边界创建/查看/撤销。工单路由经任务/会话/卡公开契约取事实，不在审批域穿透他方内部。hostapi 不是本期新的权限消费者。

③ 裁决、规则变更、回答同步确认；通知从已提交工单/归属事实产生，按工单身份幂等。通知失败保留待办及重试事实，不能伪造外部回合与账本共同事务。

## 限制分类与求值顺序

分类是本期要形成的语义，**普通 push、部署目前没有完整结构化限制标识**；`internal/permgate/blacklist.go:38` 只列 force push 等黑名单，不能声称普通 push 已有静态拒绝。采用有限分类，新增精确 wire 名由 plan 冻结。

| 类别 | 可以明确规则覆盖的边界 | 不可覆盖优先例外 |
|---|---|---|
| 普通 push | 明确仓库、远端、ref、非 force 的操作 | 黑名单、执行包装器、未知目标 |
| 部署 | 首版闭集仅 `scripts/build-deploy.sh`、`handoff upgrade`；必须绑定目标机器/环境及动作，名单外不可证明 | 包装器/eval、截断及无法证明的动作 |
| handoff 管理 | 明确子命令与对象的普通管理动作 | 审批控制面（规则管理、handoff reply、handoff approver set/clear）；账本与 handoff 凭据访问/写入 |
| 凭据读取 | 明确的非账本/非 handoff 凭据对象 | `~/.handoff/config.yaml` 在内的账本/handoff 凭据，或目标不可证明 |
| 范围外写入 | 明确路径、机器、写操作与边界 | 审批控制面数据、账本/handoff 凭据、黑名单 |

**永不可被规则覆盖**：审批控制面（规则管理、handoff reply、handoff approver set/clear）、账本/handoff 凭据（含 `~/.handoff/config.yaml`）、截断、黑名单、执行包装器、eval。这里“不覆盖”表示规则不能改变既有要求人工/咨询的出口，不扩大现存静态全拒绝语义；明确危险出口仍维持其原有门禁。语法辨明 `grep -c` 是统计参数，不等于豁免真实执行包装器。

求值顺序：完整性与语法规范化 → 收集全部限制/例外及所需事实 → 永不可覆盖门禁 → 读取最新规则/有效期/撤销 → 条件及覆盖集合全匹配才允许 → 对未覆盖部分沿用静态安全判据、模型与人工链。规则在模型之前求值，模型不能放宽例外、补猜条件或创建规则。模型 approve 不能替代用户确认；仅规则派生grant复用必须重新过不可覆盖检查与授权来源新鲜性；现有人工同任务相同请求复用不收紧。多限制必须全部满足，不能命中一条就短路允许；规则读取错误不能用旧缓存 allow。

## 生命周期、解释与审计

规则有明确主体/操作/对象条件、项目或全局作用域、来源、开始/截止时间、版本与撤销事实。首版允许跨项目全局；无截止时间须在确认中明确显示“持续至撤销”，不能将缺失字段默认为永久。到期与撤销同样阻断新裁决。

撤销提交后开始的新裁决必见撤销；已交给原生执行者的动作不追杀。规则派生的批准必须携带规则身份/版本/期限；`Authority.FindReuse` 查询旧 allow 时复核该来源，撤销/过期/读取失败不得复用。**“本任务相同请求批准”保留现有同任务、同指纹复用**，界面/CLI使用“本任务相同请求批准”等符合事实的标签，明确显示此含义，不能写成“一次性 token”；其来源为人工本次而非规则，撤销规则不抹除独立人工批准。重复同一 request 的传输重放只是单次投递幂等，不另算授权。此语义已由 #33043 Q3 批准。

| 原因 | 用户可见结果 | 去重与重新触发 |
|---|---|---|
| 缺上下文 | 列缺失字段及补充入口，保留原待办 | 同任务/原权限请求/缺失事实版本合并；事实补齐才重评 |
| 规则不覆盖 | 显示未满足条件/限制和规则版本；可选“本任务相同请求批准”或显式保存 | 同请求/分类/规则版本合并；规则变化重评 |
| 审批器故障 | 显示候选环、超时/解析/不可用原因与重试，保持 fail-closed | 同请求/失败轮次合并通知；重试更新原待办不复制工单 |
| 确需人决策 | 明确人工原因、影响与原始工单，已有合法回答者可回答，通知接收人不垄断回答 | 同原工单/审批责任归属版本只留一个有效待办；换责任撤旧通知，不撤合法回答权 |

历史与命中视图从不可变裁决/规则变更/投递事件投影，显示来源工单、规则 ID/版本、命中或未命中、原因、actor 及主体、有效期/撤销、投递状态；敏感内容脱敏。registry 仅保存当前版本，不能拿 UPDATE 后的行充当历史。规则快照 CAS 与对应不可变审计写入同一账本事务，事务失败不宣称规则提交；既有事件 API 的新增契约须在实现前核定。

## B469 收件与通知归属（已批准）

复用**原任务工单**作为唯一回答载体，新增通知归属/投递记录。收件优先级固定：任务挂卡且该卡有合法席位→沿现有push唤醒/pull card wait；否则→发起该任务的会话驻场者；否则→可见needs_human给人本人。只认显式事实，不纳入组织者、不从房间成员或最后发言者推测、不广播。通知归属只决定收件，不限制已有合法回答者；原工单保留先到先得CAS、同答案幂等，换通知归属不撤销回答权。

未挂卡任务必须由执行机侧发布权限/问题工单并可靠镜像/同步至通知消费端，不能依赖只订阅card_tasks的旧镜像路径。目标记录以执行机/task/ticket及来源seq幂等；重连补发、重启恢复和独立投递记录归S3，S3不硬依赖规则线B。

现有`cmd/session.go:565-568`只消费EvRoomMessage，`residentwake.go:1-25`只为寻址房间消息按铃，不能假定原工单自然可见。本期新增持久、明确寻址的房间工单通知，关联执行机/task/ticket及原工单入口，由session wait既有候选读取/匹配链消费，并接print续轮及桌面门铃；新增字段/候选处理与游标错误传播列为wire验收。通知正文不是第二套回答载体。

驻场者不是卡席位：print载体按会话寻址投递，现有驻场续轮消费；桌面载体只按门铃信提示，唯一内容交付经 `session wait`。门铃不等于已收内容；跨机由目标驻场所在机消费、补铃/重试，本机不得声称已有自动转交。无可达驻场/投递失败保留可见待办与重试，最终needs_human给人。

push 收件只启动短回合消费待办；需要等人时将等待事实持久化并结束回合，释放 LaunchAdmit/执行准入；不得占用 30min 回合或槽位等待。合法卡pull继续由待办订阅/card wait消费；无可达责任人落 needs_human 并可人工重绑/重试。30min 定时界限、恢复/换席位行为须以现有实现和隔离实验验证，不能先声称外部执行者已经支持暂停。若承重实验发现必须修改 Runner/hostapi 契约，阻塞该段并回提案，不能顺手重做自身权限桥。
