## 问题与方案

用户裁决原话（卡 #33005 转录）：「1，原来的工单没人收，2. 同意 3. 补进去」。本期 B469 修复**会话房间里唤起的执行者产生的原有任务工单没有审批责任人收到**；任务已有 permission/question 工单，不把故事替换成驻场协调者自身 CLI 权限桥。现状 `internal/agentd/wakeconsumer.go:215,502,746` 将工单映射为 WakeTicket，再按卡席位路由；origin pull 返回空是既有 `card wait` 契约，不应改成 push 或冒泡。房间驻场身份与卡席位不同，不能以“有 task”推导广播房间。

方案分三线：先修 B463 命令分析与审批环可观测；再做 B458 规则生命周期和 B470 解释/去重；B469 另以原任务工单验证明确归属和可靠收件。三线共用明确事实和审批语义，不建通用规则引擎。已有 B460/B465 的任务目标、工作树、产物/临时目录、只读政策与跨机上下文直接复用。

## 落位三问与架构

① 审批领域拥有条件规则、分类、求值、撤销/过期和裁决来源；任务编排拥有原工单与投递；agentd/会话领域拥有任务发起关联、房间驻场关系及审批责任路由；账本保存这些各自权威事实和不可变事件，不解释规则。

② 任务权限链消费统一审批能力；CLI/UI 经管理应用边界创建/查看/撤销。工单路由经任务/会话/卡公开契约取事实，不在审批域穿透他方内部。hostapi 不是本期新的权限消费者。

③ 裁决、规则变更、回答同步确认；通知从已提交工单/归属事实产生，按工单身份幂等。通知失败保留待办及重试事实，不能伪造外部回合与账本共同事务。

## 限制分类与求值顺序

分类是本期要形成的语义，**普通 push、部署目前没有完整结构化限制标识**；`internal/permgate/blacklist.go:38` 只列 force push 等黑名单，不能声称普通 push 已有静态拒绝。采用有限分类，新增精确 wire 名由 plan 冻结。

| 类别 | 可以明确规则覆盖的边界 | 不可覆盖优先例外 |
|---|---|---|
| 普通 push | 明确仓库、远端、ref、非 force 的操作 | 黑名单、执行包装器、未知目标 |
| 部署 | 可证明的部署工具/动作、机器、环境、目标 | 包装器/eval、截断及无法证明的动作 |
| handoff 管理 | 明确子命令与对象的普通管理动作 | 规则管理面本身；账本与 handoff 凭据访问/写入 |
| 凭据读取 | 明确的非账本/非 handoff 凭据对象 | `~/.handoff/config.yaml` 在内的账本/handoff 凭据，或目标不可证明 |
| 范围外写入 | 明确路径、机器、写操作与边界 | 规则管理数据、账本/handoff 凭据、黑名单 |

**永不可被规则覆盖**：规则管理面本身、账本/handoff 凭据（含 `~/.handoff/config.yaml`）、截断、黑名单、执行包装器、eval。这里“不覆盖”表示规则不能改变既有要求人工/咨询的出口，不扩大现存静态全拒绝语义；明确危险出口仍维持其原有门禁。语法辨明 `grep -c` 是统计参数，不等于豁免真实执行包装器。

求值顺序：完整性与语法规范化 → 收集全部限制/例外及所需事实 → 永不可覆盖门禁 → 读取最新规则/有效期/撤销 → 条件及覆盖集合全匹配才允许 → 对未覆盖部分沿用静态安全判据、模型与人工链。规则在模型之前求值，模型不能放宽例外、补猜条件或创建规则。模型 approve 不能替代用户确认；同任务人工复用也必须重新过不可覆盖检查与授权来源新鲜性。多限制必须全部满足，不能命中一条就短路允许；规则读取错误不能用旧缓存 allow。

## 生命周期、解释与审计

规则有明确主体/操作/对象条件、项目或全局作用域、来源、开始/截止时间、版本与撤销事实。首版允许跨项目全局；无截止时间须在确认中明确显示“持续至撤销”，不能将缺失字段默认为永久。到期与撤销同样阻断新裁决。

撤销提交后开始的新裁决必见撤销；已交给原生执行者的动作不追杀。规则派生的批准必须携带规则身份/版本/期限；`Authority.FindReuse` 查询旧 allow 时复核该来源，撤销/过期/读取失败不得复用。技术提案：**仅本次批准保留现有同任务、同指纹复用**，界面/CLI使用“本任务相同请求批准”等符合事实的标签，明确显示此含义，不能写成“一次性 token”；其来源为人工本次而非规则，撤销规则不抹除独立人工批准。重复同一 request 的传输重放只是单次投递幂等，不另算授权。此提案尚待协调者拍板。

| 原因 | 用户可见结果 | 去重与重新触发 |
|---|---|---|
| 缺上下文 | 列缺失字段及补充入口，保留原待办 | 同任务/原权限请求/缺失事实版本合并；事实补齐才重评 |
| 规则不覆盖 | 显示未满足条件/限制和规则版本；可本次批准或显式保存 | 同请求/分类/规则版本合并；规则变化重评 |
| 审批器故障 | 显示候选环、超时/解析/不可用原因与重试，保持 fail-closed | 同请求/失败轮次合并通知；重试更新原待办不复制工单 |
| 确需人决策 | 明确人工原因、影响与原始工单，责任人可回答 | 同原工单/审批责任归属版本只留一个有效待办；换责任撤旧投递 |

历史与命中视图从不可变裁决/规则变更/投递事件投影，显示来源工单、规则 ID/版本、命中或未命中、原因、actor 及主体、有效期/撤销、投递状态；敏感内容脱敏。registry 仅保存当前版本，不能拿 UPDATE 后的行充当历史。规则快照 CAS 与对应不可变审计写入同一账本事务，事务失败不宣称规则提交；既有事件 API 的新增契约须在实现前核定。

## B469 收件承重提案（待拍板）

复用**原任务工单**作为唯一回答载体，新增的是显式审批责任归属/投递记录而非协调者自身新工单。发起任务时记录发起会话与关联房间，指定驻场审批责任人；只有可核实的显式归属才路由。不从房间成员、最后发言者或 task 存在猜责任。卡席位已有责任可复用；冲突必须显式处置。责任归属变化以版本避免旧新接收人同时回答生效，原工单回答 CAS/幂等保持恰好一次。

push 收件只启动短回合消费待办；需要等人时将等待事实持久化并结束回合，释放 LaunchAdmit/执行准入；不得占用 30min 回合或槽位等待。pull 继续由待办订阅/card wait 消费；无可达责任人落 needs_human 并可人工重绑/重试。30min 定时界限、恢复/换席位行为须以现有实现和隔离实验验证，不能先声称外部执行者已经支持暂停。若承重实验发现必须修改 Runner/hostapi 契约，阻塞该段并回提案，不能顺手重做自身权限桥。
