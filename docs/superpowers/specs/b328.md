# B328 `handoff room inbox` 把 `{"items":[]}` 当数组解码失败

- **卡**：B328

- **基线**：`origin/main` @ `3f327c59f`
- **发现自**：B156.3 真机验收 2026-09-04。B323 不 reopen。

## 问题陈述

谁在什么条件下，通过什么关系，使什么事实变化：协调者跑 `handoff room inbox` 时，CLI 把 GET `/api/inbox` 的响应体直接 `Decode` 成 `[]proto.InboxItem`；agentd 实际返回的是对象信封 `{"items":[...]}`。空收件箱 `{"items":[]}` HTTP 200 时 CLI 报 `json: cannot unmarshal object into Go value of type []proto.InboxItem`。工作台 `fetchInbox` 已经按 `{items}` 解。

现状读数：

- 服务端：`internal/agentd/roomsapi.go` `handleInbox` 末行 `writeJSON(..., map[string]any{"items": items})`
- 客户端：`internal/client/client.go` `Client.Inbox` 把 body `Decode` 进 `[]proto.InboxItem`
- 工作台：`web/src/api/rooms.ts` `request<{ items: InboxItem[] }>('/api/inbox').then(r => r.items ?? [])`
- CLI 夹具 `cmd/room_test.go` `TestRoomInboxWalksAgentdHTTP` mock 编码的是数组，锁的是错误信封，所以单测绿、真机红

## 方案

**只改 CLI 客户端解码，对齐服务端与工作台已冻结的 `{items}` 信封。** 不改 HTTP 字段名、不改 InboxItem 形状、不改聚合三源。

弃选：把服务端改回数组——工作台已经按对象解，改服务端会红前端。

## 用户故事

1. 作为协调者，空收件箱时 `handoff room inbox` 退出 0，不报 unmarshal object。
2. 作为协调者，有条目时仍能看到 origin/title/ref_id。

## 实现决定

- `Client.Inbox` 解码 `struct { Items []proto.InboxItem json:"items" }`，返回 `Items`（nil 当空切片）。
- `TestRoomInboxWalksAgentdHTTP` mock 改为 `{"items":[...]}`。
- 增加空信封夹具：body `{"items":[]}` → Inbox 成功、长度 0。

## 测试决定

缝：`client.Client.Inbox`（调用方 `cmd/room.go` `room inbox`）。

1. 现网形态：`{"items":[]}` → 无 error、len=0。变异：仍 Decode 成 `[]InboxItem` 必须红。
2. 非空：`{"items":[{origin,title,ref_id}]}` 经 `room inbox` 输出含这些字段（改现有 HTTP walk 测试的 mock）。

## Out of Scope

- **永不做**：把 `/api/inbox` 改回顶层数组。
- **本期不做**：B329 人坐下出示；B330 charter 绑小队；inbox 过滤/分页。

3. 验收：`go test ./internal/client ./cmd -count=1` 绿；本机 `handoff room inbox` 对活 agentd 退出 0。
