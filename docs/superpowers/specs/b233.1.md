## 定级理由

跨子系统、动契约层。一次普通派发要同时改三块契约面：

- **任务编排**（现状 `Manager` + store）：拥有任务、回合、Ask 事实、派发事件流
- **执行**（`d_execution` / OpenCode adapter）：产出事件、`Send` / 新增 `RespondAsk`、原生权限翻译与回传；不决定批谁
- **审批服务**（从 `Manager.handlePermission` + `permgate` + `Approver` 抽出的契约面，户口名归 contract）：政策快照、判定、升级、审计；经限定执行身份的 client 注入

`d_protocol` 复用既有事件词表；CLI / HTTP 的 `dispatch` / `wait` / `reply` 是同一生产入口改走新实现，即使命令名不变也按「对接已存在的跨进程 wire」计。

选轻档：这是一条贯穿用户故事（派发 → 订阅 → Ask → 审批 → 结束），拆并行子卡会在接缝上等对方。契约冻结与拆解照做，实现一轮收口。单子系统若在 breakdown 里超过固定成本，跨流迁重档，不重建卡。

## 问题陈述

谁：用 `handoff dispatch` 把普通任务交给本机 OpenCode 的协调者；同时 `handoff wait` / `reply` 盯进度、回答问题和处理需外部审批的操作。

条件：B233 要把基础设施按领域收口。当前 `Manager` 同时拥有任务状态机、Ask 工单、整条审批链和事件发布；OpenCode 的 `Send` 按内存里的挂起问题在「答问」和「新指令」之间切换。

通道：现有普通派发生产入口（CLI `handoff dispatch` → `client.Dispatch` → `POST /api/tasks` → `Manager.Dispatch`）接到新执行边界；不新增交互领域、不新增事件总线、工作流不参与本卡。

要变的事实：一次 OpenCode 普通派发由新执行边界真正跑完；进度、Ask、待外部审批、结果和失败可订阅。Ask 必须回到原问题身份；普通 `Send` 不得误答。免审按同一政策快照兑现，其余由审批 client 决定并回传原生权限请求。拒绝、取消、重复/迟到回答及断线补拉有可复跑证据。OpenCode 路径上旧审批编排不再是第二套权威。

## 方案

试点 harness：**OpenCode**。真机与探针必须走**免费模型**（会员已到期）。缺省用本机已配置的 `executor.model`（现状读数 `opencode-go/deepseek-v4-flash`）。该模型不可用时验收失败并报告原文，禁止改走付费会员通道，禁止把审批模型改成付费 OpenCode。

生产入口不变：`handoff dispatch --executor opencode`（模型取配置或显式免费 `--model`）→ 现有 HTTP → `Manager.Dispatch`。Dispatch 对 OpenCode 任务改走新执行边界，而不是另开一套派发命令。

### 1. 身份

| 身份 | 本期含义 | 不做什么 |
|---|---|---|
| 执行实例 | 一次普通派发产生的 `Task`（`Task.ID`） | 不另造 Execution 实体；载体绑定归 B233.5 |
| 回合 | 一次 `Start` 或 `Continue`，到 `completed` / `turn_failed` / 进入 `waiting_review` | 不把进程存活等同业务验收 |
| Ask 请求 | 原生 `QuestionID`；无则首次识别时生成并持久化；重放复用，不得每帧新建 | 不按「当前待答槽」寻址 |
| 审批请求 | 原生 `PermissionID`；对外工单继续 `taskID:permID` 命名空间（现状） | harness 不选择审批者 |

回答必须同时带执行实例、回合/尝试、请求身份。只给 task ID「找当前那条问题」不合法。

### 2. 派发事件流（复用，不新总线）

派发返回任务（执行引用）和既有可订阅事件流（store + hub + `wait`）。不增设 InteractionService，不增加第三条事件总线。

| 交互 | 事件类型（复用） | 谁拥有权威事实 | 谁唤醒 wait |
|---|---|---|---|
| 进度 / 输出 | `progress` | 任务 | 否（维持 `isDeliverable`） |
| Ask | `question` | 任务领域：问题、答案、投递状态 | 是 |
| 待外部审批 | `permission_request` | 审批服务：授权决定；事件只通知 | 是；仅审批服务无法自行有效决定时发布 |
| 回合结果 | `completed` / `turn_failed` | 任务 | 是 |
| 任务失败 | `failed` | 任务 | 是 |
| 应答未送达 | `delivery_failed` | 任务 / 审批投递状态 | 是 |

免审、审批模型内部裁决、复用授权：记审计事件（现有 `permission_auto_allow` / `approver_decision` / `permission_reuse`），不把它们伪装成待外部审批。

工作流本卡不订阅、不转发。

### 3. Send / RespondAsk / 原生权限回传

| 方法意图 | 用途 | 必须关联 |
|---|---|---|
| `Send` | 新的普通消息、补充指令、Continue 类输入 | 执行实例。按会话状态处理，**不得**消费任意挂起 Ask |
| `RespondAsk` | 回答一项明确问题 | 执行实例、回合/尝试、问题 ID、结构化答案 |
| 原生权限回传 | 审批服务形成的决定投递给 OpenCode 原生权限请求 | 执行实例、权限请求 ID、决定与范围。不是给上层绕过审批服务的入口 |

OpenCode 必须把 `Send` 里「有 pendingQuestion 就 ReplyQuestion」拆掉：那条路改由 `RespondAsk` 承担。CLI 仍用 `handoff reply --answer` 回答 Ask、`--approve` / `--deny` 回答待外部审批；内部不得再把 Ask 答案当一次无关联 `Send`。

`RespondAsk` 两种合法实现：原生问题仍挂起 → 回复该原生问题、不开新回合；提问回合已结束 → 核对待答身份后，以带关联的答案续接。底层可复用 prompt 机制，但不能丢掉「这是对哪次提问的回答」。

拒绝后的解释性消息如需另发，只能作附属指导，且必须关联被拒的权限请求，不得冒充新的 Ask 答案、不得再优先吞掉下一条提问。

### 4. 审批 client

执行实例得到**限定于自身身份和范围**的审批 client，不能自行扩大范围。harness 负责原生权限翻译与决定投递；Manager 不再为 OpenCode 路径实现一套审批链。

client 最小能力（语义，签名归 contract）：

- **PolicySnapshot**：按执行身份/范围取得版本化政策（可免审规则、明确禁止、其余动作的审批要求）
- **Request**：稳定原生请求 ID + 完整动作/资源/上下文 → 审批引用与当前决定
- **Await**：按审批引用等待最终决定（允许/拒绝及范围、理由）；等待与恢复在 client，不靠一个永远活着的函数栈
- **Acknowledge**：区分决定已形成、已送达原生请求、动作已执行

共享桥接可以提供 Authorize 便利方法。审批记录由审批域唯一写入；任务状态由任务域唯一写入。harness 不提供 ChooseApprover / EscalateToHuman / ApproveByModel。

审批模型只在政策允许委托给它的范围内判断，使用审批服务自身受限配置（现状 grok 一次性调用）。禁止把被审批任务的权限转交给审批模型，禁止模型审批自己。失败、超时、不可用 → 升级为待外部审批，不得解释成允许。

### 5. 政策快照生命周期

同一有效政策在 **Dispatch 启动**和每次 **Continue 开始**时解析一次，快照绑定该回合。运行中改配置、改上限、改免审表，不改变已经在跑的回合。下一回合或新派发取新快照。

OpenCode 只把快照里能精确表达的部分编译成原生规则。无法精确表达的允许条件送审批 client，**不准用更宽的原生 allow 代替**。明确禁止项直接实施；无法实施所需边界时报告能力不足，不得假装同等保证。

### 6. Ask / 审批状态与重启

Ask：待答 → 已答未投递 → 已送达；另有取消 / 失效。先落请求再通知订阅者。通知失败不能让问题消失，不能只靠内存 waiter 当唯一事实。本期允许继续用现有 Ticket 表存问答，但语义权威是任务问答，不是 Manager 的 goroutine。

审批：决定形成与原生投递结果分开记录。投递失败保留「已决未送达」，恢复时核对原生请求是否仍在。原生不支持幂等回复且送达不确定时，先对账，不宣称恰好一次执行。

重启后（agentd 或订阅者）：

- 未答 Ask 按稳定请求身份重挂等待，事件流按游标补拉，不新建第二张同身份问题
- 已答未送达可恢复投递；原生请求已消失则记失效，不把答案喂给新尝试
- 审批引用可恢复，不依赖重启前的 waiter 栈
- 重复相同回答幂等；竞争回答靠状态约束；迟到答案在取消 / 失效 / 已换尝试时必须被拒绝
- OpenCode 若仍能 Resume 且原生问题仍挂起，`RespondAsk` 走原生回复；不能 Resume 则按任务已保存的问答与能力边界报告，不静默丢问题

取消执行：停止实际执行、解除仍挂起的原生权限/问题、Ask 标取消、占用结束；已形成的审批决定不改写为允许。

### 7. 旧入口退役（仅 OpenCode 路径）

| 旧路径 | 本卡 |
|---|---|
| `Manager.Dispatch` / `POST /api/tasks` / `handoff dispatch` | 保留为生产入口，OpenCode 任务内部改调新执行边界 |
| `handleQuestion` + `waitQuestion` → `Adapter.Send` | 退役为权威实现；改为落 Ask 事实 + `RespondAsk` |
| `handlePermission` 内的静态门 / 审批模型 / 升级 / 回传 | OpenCode 路径退役为权威实现；改为审批 client。其他 harness 暂留旧路径 |
| OpenCode `Send` 消费 pending question | 退役 |
| 拒绝理由吞下一条提问 | 退役 |
| `handoff wait` / `reply` | 保留；内部接到新事实与新回程 |

Claude / Codex / Grok / AGY 本卡不迁入新边界，行为不得无故变坏。不得长期维护两套 OpenCode 业务事实。

## 用户故事

1. 我用 OpenCode + 免费模型普通派发一项任务（不建卡、不走工作流）。`wait` 订到进度、Ask、待外部审批、回合结果或失败；任务实际在新执行边界上跑完。
2. 执行者提出一项有身份的业务问题。我 `reply --answer` 后，答案回到**那个**问题：原生仍挂起则不开新回合；提问回合已结束则以关联答案续接。同一时刻 `Send` / Continue 普通指令不得把该问题答掉。
3. 工作区范围内的写/编辑按同一政策快照免审：不唤醒 wait、原生请求被允许、审计可查。
4. 越界、黑名单、截断描述等需外部审批：wait 收到 `permission_request`；我 `--approve` / `--deny --reason` 后，审批 client 形成决定并回传原生权限请求。拒绝不是执行成功。
5. 同一权限描述在本任务、本快照下已送达的 allow 可复用，不把网络故障或超时当成允许。
6. 我重复提交同一 Ask 答案：第二次幂等成功，不派发第二次原生回复。原问题已取消或已换尝试：迟到答案被拒绝，新回合看不到旧答案。
7. 我取消任务：执行停下，挂起的 Ask 与原生权限解除，wait 能看到取消/失败类结果，现场可诊断。
8. agentd 在未答 Ask 期间重启：重连后按游标仍能看到该问题，回答仍回到原请求。已答未送达的权限决定可恢复投递或明确失效，不出现「工单已消耗、executor 仍阻塞、无人可答」。
9. 用 Claude 或 Codex 派发的任务本卡仍走旧 Manager 路径，不要求新边界，也不被 OpenCode 迁移带崩。

## 契约语义与接缝（L3，定语义不定签名）

1. **任务拥有 Ask 与任务生命周期；审批服务拥有政策与授权决定。** 二者通过事件和返回结果关联，互不写入对方的权威表。
2. **执行边界只翻译与投递，不选择审批者、不解释卡列、不宣布业务验收。** OpenCode 适配器不得写 store、不得自行扩大免审。
3. **派发事件流是任务事件流。** Ask 与待外部审批都走它上浮；回程是有类型的调用（RespondAsk / 审批 client），不是普通 Send。
4. **政策快照绑定回合。** 免审原生映射 ⊆ 快照；映射失败必须暴露，不得放宽。
5. **请求身份稳定。** 重放复用；重发（旧单已答、原生又问）才新开身份。
6. **CLI / HTTP 命令名保持。** 变的是 OpenCode 路径的实现与退役范围，不新造交互子命令。
7. **依赖方向：** 任务编排持有执行契约与审批 client；执行实现（OpenCode）被注入审批 client；审批服务不 import OpenCode 包；协议类型双方可引用。组装点绑定具体类型。禁止执行适配器直达 `permgate` / `Approver` 具体实现（除组装点）。

精确签名、client 包路径、是否新立顶层域，归 contract。

## 实现决定

- 试点只接 OpenCode；其他 adapter 继续实现现有五动作。`RespondAsk` 作为执行契约增量，未实现的 adapter 不得被 OpenCode 路径误调。
- 真机 / 探针 / acceptance 的 OpenCode 任务使用免费模型；默认即本机 `executor.model`。禁止为「更好看」换成会员模型。
- 审批模型保持审批服务自己的受限一次性调用，不借用被审批任务的 OpenCode 会话。
- 业务事件泵不得被某一项长时间审批阻塞（等待在 client / 工单侧，不堵中介循环）。
- 日志可记任务 ID、请求 ID、政策版本、决定、投递结果；禁止把 Ask 全文和命令参数当默认 info。
- 本卡不搬目录、不改载体准入、不改工作区准备、不改跨机传输。

## 测试决定（接缝清单）

接缝尽量少。每条缝 = 符号意图 + 调用方。新建符号不写死签名。

1. **普通派发生产入口**（存量 `Manager.Dispatch`，调用方 `cmd/dispatch.go` / `client.Dispatch`）：OpenCode + 免费模型派发后，任务在新执行边界上进入可订阅状态；失败不得报成功。假缝禁令：不把「只 new 了 client 接口」当完成。
2. **Ask 回程**（新建 `RespondAsk`，调用方现有 `handoff reply --answer` → `client.Reply`）：答案命中原问题 ID；同一执行实例上的 `Send` 在有待答 Ask 时不得把它消费掉。覆盖：原生挂起回复、提问回合已结束后的关联续接。
3. **审批 client**（新建提供方 client，调用方 OpenCode 权限桥 / 共享 Authorize）：同一快照下范围内写操作免审且不发待外部审批；需外部裁决时发布 `permission_request`，`reply --approve/--deny` 经 client 回传原生 `PermissionID`。截断描述不得 AutoAllow（锁现有 `Gate.Judge` fail-closed）。
4. **事件订阅与补拉**（存量任务事件流，调用方 `client.WaitEvent` / `isDeliverable`）：重连按游标能拉到未决 Ask / 待外部审批；`progress` 默认不唤醒；`delivery_failed` 唤醒。边界型：事件类型字符串走 proto 词表，穿过序列化。
5. **取消、重复、迟到**（任务问答状态，调用方 reply 与 Stop/取消入口）：重复答案幂等；取消或换尝试后迟到答案被拒绝；取消后原生权限/问题不再可成功回传。

变异：把 Ask 答案改回 `Adapter.Send` → 故事 2 转红。把无法映射的免审写成更宽原生 allow → 故事 4 转红。把会员付费模型写进真机步骤 → 验收直接失败（环境约束，不是产品开关）。

本节点该干什么一律以注入的纪律块为准。

## Out of Scope

永不做：

- 独立交互领域 / InteractionService / 第三条事件总线
- 用无关联 `Send` 回答 Ask 或投递审批决定
- 把网络故障、拒绝、超时解释成允许
- 真机改走已到期的 OpenCode 会员模型

本期不做（已有去处，不在本卡实现）：

- 其他 harness 迁入新执行边界 → B233.2
- 跨机能力 client → B233.3
- 工作区 / Git 独立能力 → B233.4
- 载体 / 小队统一派发 → B233.5
- 工作流订阅转发与旧编排退役 → B233.6
- `internal/` 按理想图搬目录、client 包物理落点作为完成条件 → 父卡 B233，contract 可先立导出面
- 首次配置、自动发现、自动建载体 → 见 roadmap
- push 责任主体与默认授权 → 见 roadmap；本卡不擅改
- 把默认审批者改成 OpenCode 免费模型
- 新事件类型替换 `question` / `permission_request`
- 新的 CLI 子命令专门「答问」

## 备注
