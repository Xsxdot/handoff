### P3｜四包封界的切分粒度：`workspace` 公开能力函数是否随实现进嵌套

contract §2 写「实现细节（Manager 内部方法、**git 原语**、scheduling 内部读模型、approval 请求裁决实现）进 `internal/<包>/internal/`」。但实测（台账 §1）：`internal/workspace` 的公开导出面被 gateway 生产**直接调用 60+ 个符号**（`PrepareWorkspace`/`ReadFile`/`WriteFile`/`GitRun`/`RunCmd`/`ListDir`/`Err*` 哨兵…），又被 `internal/orchestration` 生产调用 30+ 个。若把这些「git 原语」搬进嵌套，`internal/agentd` 与 `internal/orchestration` 的 import 当场编译失败——它们不是可搬的实现细节，而是跨域公开能力面。

两选一：
- **方案 A（推荐）｜最小封界：nested 只收「无跨域消费者的实现细节」**（如 `workspace` 的 `gitCapability`、仅供包内使用的 helper；`orchestration` 的 Manager 内部方法体；`scheduling` 的内部读模型；`approval` 的裁决实现），公开能力函数与公开契约类型（`Capability`、`workspace.*` 能力函数、`scheduling.*`、`approval.Hooks`）留公开包。优点：与 spec §用户故事 2「在 gateway 里 import 里间路径即 `go build` 失败」一致，不改 gateway handler 消费方式（零行为面），有界；缺点：nested 目录内容较薄，封界的强度取决于实现节点如何划分「细节 vs 公开能力」。
- **方案 B｜彻底封界：把所有实现体搬进 nested，gateway 改走 `Capability`/接口。** 需重写 gateway 的 workspacefiles/projecttree/projectadmin 等 handler 与 orchestration 的 workspace 调用，超出「结构闸、行为零变化」约束，且触及 60+ 调用点。否。
- **推荐 A。请拍板。**（无论 A/B，contract §2「git 原语进 nested」的措辞须对齐，见 C-3。）

### P4｜`scheduling.*Service` 与编译期断言的落点（`*Service` 进不进嵌套）

contract §2 把「`*Service` 是否进嵌套」留 plan；#11 又要求四条编译期断言（`manager.go:322`/`capability_impl.go:19`/`client.go:79`/`scheduling_client.go:58`）迁入嵌套后仍能编译。实测该断言目前在 gateway 生产：`internal/agentd/scheduling_client.go:58` `var _ SchedulingClient = (*scheduling.Service)(nil)`——它 import 公开 `internal/scheduling`。若 `*Service` 搬进 `internal/scheduling/internal/`，gateway 无法再引用该具体类型，断言只剩两条路：把它迁进 nested（nested import 公开 `internal/agentd` 取 `SchedulingClient` 合法），或让它要求 `internal/scheduling` 反向 import gateway（**新增 `d_scheduling→d_gateway` 方向，违法**）。

两选一：
- **方案 A（推荐）｜`*Service` 留公开包**，gateway 断言原样保留（零方向新增）；nested 只收 `scheduling` 内部读模型/registry 适配等无跨域消费者的细节。改动最小，与 #21「`d_gateway→d_scheduling` 预算 0、entries/interfaces 不变」一致。
- **方案 B｜`*Service` 进 nested**，公开 `scheduling.New` 改返回接口类型、gateway 断言改在 nested 包内对公开构造返回值断言。改动大、`scheduling.New` 签名变化牵动 `cmd/agentd.go` 与多份测试。
- **推荐 A。请拍板。**（若裁 B，须先退回 contract 重冻 §2 与 #11 的断言落点，见 C-5。）
