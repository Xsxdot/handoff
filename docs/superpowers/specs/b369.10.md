### 1.1 键条：8 键浅色 vs 原型 12 键暗色 + Ctrl 粘滞（候选①）

- **原型 canonical**（mobile-task.html:133-136、mobile-terminal.html:87-89，两屏同一条键条，notes ②③ 明言「与任务现场共享」）：Esc / **Ctrl（粘滞，点按进入 on 态，`:62` `.k.on` 高亮、`:173` mock toggle）** / Ctrl-C / Tab / Shift-Tab / ←↑↓→ / **|** / **~** / **⌫** 共 12 键，暗色条（`#1c1c1e` 底 `#3a3a3c` 键，`:60-61`），容器自带 `overflow-x: auto`（`:60`）；键 min-width 40px，12 键 + 间距 ≈546px > 390——**原型键条自身就是横滑形态**。mobile-task note ②：「特殊键条（Esc/Ctrl/Ctrl-C/Tab/Shift-Tab/方向键/管道符）让系统键盘打不出的控制键可点；输入法组合状态确认后才进 xterm」。
- **现实现**（`MobileKeybar.tsx:18-27`）：`KEYBAR_KEYS` 受控键集 8 键 = Esc/Tab/⇧Tab/Ctrl-C/四方向（`MobileKeybar.test.tsx` 全锁受控键集与序列载荷）；浅色形态（`:34` `bg-background`、`:44` `border` 键）；挂载点 `TerminalTab.tsx:699-708`（`keybar={compact}` 门控在 `Shell.tsx:997`），点击经 `term.input(seq)` 与手敲合流。
- **定距**：(b)+(c) 混合。键位本体扩充（| ~ ⌫ 三键 + Ctrl 粘滞键位）与暗色形态 = (b)，进受控键集即可；**Ctrl 粘滞的输入层接线 = (c)**——粘滞修饰符要拦「下一击」（系统键盘字母/键条键）合成控制字符，而 xterm 的 `attachCustomKeyEventHandler` 唯一槽位被 `terminalInput.ts` 独占（文件头 ：15-16 纪律，B369.9 §1.2 实测），接线方案有真岔口（§2.1）。另有一处对 B369.9 验收口径的算术性翻案：B369.9 §4 要求「键栏无横滑」的前提是 8 键 ~348px 放得下 390；12 键 ~546px 放不下，且原型自身横滑——口径必须随原型更新（§2.1、§6 风险 2）。
- **B369.9 §5 的「键栏新键位扩展另立卡」预留位由本卡承接**：原型 12 键是形态权威明文，翻案逐条记明（§3）。

### 2.1 键条 12 键：受控键集扩充 + Ctrl 粘滞接线（翻案 B369.9 两处，逐条记明）

- **受控键集法定形态**（`KEYBAR_KEYS` 扩到 12 键）：既有 8 键序列零变更；新增 `ctrl`（粘滞键位，无直接 seq）、`|`（`\x7c`）、`~`（`\x7e`）、`⌫`（DEL `\x7f`）。原型 Ctrl 与 Ctrl-C 并存：**Ctrl-C 保持直发 `\x03`**，`ctrl` 是粘滞修饰键。
- **Ctrl 粘滞语义**：点按 `ctrl` 进入 armed（视觉 on 态，原型 `.k.on` 同形）；armed 期间的下一击经 Ctrl 修饰合成——键条键（方向→`\x1b[1;5A/B/C/D` 等 CSI 修饰序列）、系统键盘字母（`ctrl+letter` → `ord-0x60` 控制字符，如 Ctrl-D=EOF、Ctrl-R=反搜）；再点一次或发送后解除。这是「系统键盘打不出的控制键可点」（原型 note ②）的完整形态：粘滞补的是**组合**，直发键补的是**单键**。
- **接线落点（排除法）**：armed UI 与键位归 `MobileKeybar`（受控键集 + onKey 通道自然扩展）；系统键盘拦截只能在 TerminalTab 的 xterm 事件层做，而 `attachCustomKeyEventHandler` 唯一槽位被 `terminalInput.ts` 独占（补漏 handler，`terminalInput.ts:15-16`）——两个候选：粘滞合成**复合进既有 handler**（terminalInput 增加可选链式入口），或粘滞状态外提由 TerminalTab 在 handler 外先处理。两者都不新增 terminal* 文件（P3 只禁新增）；plan 选型，若评估出「必须开第二个 handler 槽」则回 spec 翻案。
- **形态**：暗色键条（终端窗格内 `#1c1c1e`/`#3a3a3c` 档）归 plan 配色 token。
- **翻案记明（§3 纪律的逐条清单）**：①B369.9 §5「键栏新键位扩展另立卡」——本卡即该卡，原型 mobile-task.html:133-136 / mobile-terminal.html:87-89 是明文权威；②B369.9 §4「键栏无横滑」口径——12 键 ≈546px > 390 且原型键条自带 `overflow-x: auto`，验收口径改为「受控键集全量在场、超宽横滑可达」（算术事实 + 原型形态，双依据）；pad 双列 ~380px 下同理横滑，B369.9 风险 4 预留的前提变化动作在此触发，记卡台账。

## 5. 非目标

- **原生壳/相机/Keychain/推送**：README:8 与原型 hub-note 明文 OOS；PairingGuide 不升级。

- **`/api` 与 wire 契约**：零新增端点、零新增字段；逐条验收开关、A/B 选项式作答、大文件分段加载、语法着色（新依赖）都因无 wire/依赖承载而 OOS 并记台账。
- **桌面形态**：所有 compact 增量以 prop 注入隔离（CardsPage/SessionTab/SettingsPage 先例），桌面 JSX 逐字节不动；FileTab/ReviewSidePanel/TuiTab 桌面分支零改动。

- **mobile-architecture 基建语义**：relay/bundle/壳定位是方案图流，本卡（web 侧校准）不消费。

## 6. 风险与开放问题

1. **项目列表层「折叠→详情」翻案的连带面**：B369.8 的 compact 折叠用例（`aria-expanded=false`、位置摘要）将随主点击改语义而重写；搜索行为变化（搜索命中项目→进详情看任务，不再展开树）是可达性收窄——辩护：详情面信息是展开区超集且原型明文；review 可翻案为「保留折叠 + 行内详情入口」双通道（代价：同信息两入口 + 1479 行组件继续长）。**需要 review 确认翻案幅度**。
2. **键条口径变更的连锁**：12 键横滑推翻 B369.9「无横滑」验收句——双依据（算术 + 原型形态）已记，但 B369.9 卡台账的对应验收记录需加注（协调者/验收节点知会），避免被误判为回归。
3. **横幅判据的双真相时差**：任务流 state（≤2.5s）与 TUI 会话流可能短暂不一致（横幅已亮、会话流未更新）；横幅是提示面不承载状态迁移，时差只影响提示早晚——plan 接缝处加 seq/时间戳口径备注，不做二次轮询。
4. **FileTab compact 只读化的能力收窄**：手机上「改个配置」场景从文件面移到终端（原型 08-11 评估的原意）；桌面草稿在 phone 只读态的呈现（草稿存在时的提示）归 plan，不得静默丢草稿。
5. **会话首页项目筛选行去留**：原型无此行，移除是能力收窄、保留是首页多一行——开放给 plan，两案都不违背原型语义（原型未覆盖 ≠ 否定）。
6. **设置 hub 呈现与 B369.8 拍板的张力**：拍板是「就地呈现不是链接墙」，原型是行式+›（mock 无落点）。倾向：三节标题 + 「需要你提醒」等行文对齐，就地呈现保留（拍板优先级高于原型 mock 形态），差异记台账——**需要用户/协调者裁决**（若裁定行式+›，则三个工作方式项要新 sub 页，语汇增量另议）。
7. **验收判据与代码现实无根本矛盾**：逐屏对齐（每屏有可达处置或台账偏离）、三闸（无新依赖）、不回归（锁法具体）、台账（模板在 §4）——无「无法自圆其说」项；最大口径风险是 1/6 两条翻案与张力点，均已前置记明。

## 8. 定级结论与落点

**L2**。理由：单子系统（`d_web`，改动面跨 shell/tree/workbench/task/cards/rooms/settings/files 八族 + 一个新组件文件，但全部在 `web/src/` 内）；无新 wire 契约（`/api` 零新增，唯一 URL 语汇增量是页面内导航参数）；机制全部有仓内先例承接（新面挂覆盖层体系、prop 注入隔离桌面、受控键集扩充、`api.activate`/`focusTab` 消费既有 tab），无架构级不可逆决策。**不落 L1 快道**：改动面广（八族 + 新面）、两处对已落卡验收口径的翻案需要测试面重写与台账动作，工作量显著高于流程固定成本。**不升 L3轻**：无跨子系统契约面、无新域；三个结构差虽是 IA 决策但都经排除法收敛到唯一/双选一明确解（§2.2 详情面新建 vs 塞树、§2.3 Shell 层横幅 vs 组件内、§2.1 handler 复合两条候选），不存在「做错要回炉方案选型」级的脊柱对赌。落点：spec 完稿后卡移 plan 列，plan 接手 §3.3 八个岔口；§6.1/6.6 两个翻案/张力点（项目折叠翻案幅度、设置 hub 呈现取舍）提请 review 与用户裁决。
