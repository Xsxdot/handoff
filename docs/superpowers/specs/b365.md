# B365 CLI 会话参与闭环：session wait 双形态（一次性/--follow 常驻）+ send 两面收回复锚（reply_to 发送半边）

- 级别：**L1 快道**（本 spec 末尾三节即实现计划，同一份文件挂 spec/plan 两个 kind）
- 来源：用户 2026-09-13 指示——「session wait 要像普通 wait 和 card wait 一样有两种方式：不带 follow 一次性收到事件就退出，带 follow 持续到主动退出」；回复发送半边为本卡原范围（B358 integrate 移交）。回落本地 subagent 执行（用户指示不派发）。

## 1. 现状与缺口

- `session wait <member>`（cmd/session.go）已是**一次性**订阅：命中输出一行 SessionWake JSON 退出 0。contract §3.8 当时把「常驻 follow」划给参战形态 v2 另卡；用户现指示提前入本卡。
- `session send` 两面（CLI cmd/session.go、HTTP internal/agentd/sessionsapi.go）都不收回复锚——`proto.RoomMessage.ReplyTo`（internal/proto/rooms.go:36）字段已冻结、wire golden 已锁（proto/sessions_fixture_test.go），`ResolveDelivery` 的 reply 隐式寻址判定已实现（internal/collab/sessions.go:163-171），**缺的只是发送半边把 ReplyTo 填进 RoomMessage**。
- `@` 已有能力不动：`send --mention <身份|卡号>`（可重复），`@卡号` 解析到卡当前席位。

## 2. 目标形态

### 2.1 `session wait --follow`（常驻订阅）

- `handoff session wait <member> [--since <seq>] [--timeout <dur>] [--follow]`。
- **不带 --follow**：现状不变——首个命中输出一行 SessionWake JSON 后退出 0。
- **带 --follow**：持续订阅，每个命中事件各自输出一行 SessionWake JSON（json.Encoder 逐行，同 card wait），**不退出**，直到：主动退出（SIGINT/SIGTERM，退出码 0）、`--timeout` 到点（退出码 124）。**follow 模式下 `--timeout` 语义改为空闲上限**（任意命中帧之间的最大间隔，0 = 不设限），与 `cmd/card_wait.go#runCardWait` 的 follow 语义同形（card_wait.go:55-56）。
- 订阅只读性质不变：不落账、不推进未读游标、不改会话状态。命中判定仍走 `collab.Service.MessageWakeTargets` 唯一入口，cmd 侧不重造寻址。
- 实现形态：读侧仍轮询 `Store.EventsFromAsc(nil, cursor, 500)` 全流读，一次性与 follow 共享同一条读循环——区别只在「输出首个命中后是否继续推进游标等下一条」。

### 2.2 `session send --reply-to <seq>`（回复发送半边）

- CLI：`handoff session send <session> <text...> [--reply-to <seq>]`，flag 值为被回复消息的账本 seq，透传进 `proto.RoomMessage.ReplyTo`。
- HTTP：`POST /api/sessions/{id}/messages`（sessionsapi 既有 handler）请求体增可选字段 `reply_to`，逐字映射 RoomMessage.ReplyTo；不新开端点、不改既有字段语义。
- 约束：`--reply-to 0` 与缺省等价（无回复锚）；负值拒 400/参数错。发送者的寻址判定（reply 隐式寻址原作者）走既有 `ResolveDelivery`，本卡不改判定逻辑。
- web 前端回复态（B358.8 已交付）在 B365 合入后补一行接线（send 请求体带 reply_to）——**不属本卡**，属 B358.8 的缝位消费，随 B358.8 finish 前顺手接。

## 3. 实现（plan）

1. `cmd/session.go`：wait 增 `--follow` flag 与共享读循环改造（一次性/常驻分叉点 = 首个命中后是否退出）；send 增 `--reply-to` int64 flag。测试：一次性现状回归 + follow 两连命中输出两行 + follow 主动退出 0 + reply-to 透传与负值拒绝。
2. `internal/agentd/sessionsapi.go`：messages handler 请求体增 `reply_to` 可选字段（注入测试：带锚发送落账 ReplyTo、缺省不带、负值 400）。
3. `internal/collab`（如需）：仅当现有 Send 校验拒绝 ReplyTo 时放开；判定逻辑零改动。
4. **验收**：`go test ./cmd/... ./internal/agentd/... ./internal/collab/...` 全绿且失败集合不扩（agentd 恰 B362 golden 一支的历史红不熔断）；CLI 真机链路一轮——终端 A 挂 `session wait --follow`，终端 B 连发两条 @ 命中消息，A 逐条吐两行 SessionWake；`send --reply-to <seq>` 后原作者的 wait 收到带 `referenced` 的载荷。wire golden（proto fixture）只增不改。

## 4. 红线

- 不新增组装点、不新增跨域边；wakeconsumer 分流零改动（外部身份命中本就不进 keystone）。
- 订阅通道只读性质（contract §3.8）不破：follow 不落账、不推游标。
- 不做 `@all`/`@here`、不做按成员集合投递（spec §永不做）。
