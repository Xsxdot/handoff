## 1. 问题陈述与北极星（为什么）

### 1.1 实证：一次真实开发会话的探索账单

2026-08-22 的「执行者耗时统计」会话（spec→contract→breakdown→plan 四节点）留下了完整取证：

- **133 次工具调用，其中 ~75 次是只读探索**，探索结果共 ~168K 字符进上下文；
- 探索行为收敛为四种模式：
  1. **「X 在哪/长什么样」**（~35 次）：grep 定位 → sed 读体，每个符号两连、两个回合；
  2. **「谁写/谁调 X」**（~12 次）：跨包找写点、调用方、出现次数；
  3. **序列化投影链追踪**（~10 次）：一个 wire 实体从产生到 UI 的每个投影点手动串联；
  4. **文档行号锚点验证与修漂**（~10 次）：出稿后逐条验证 file:line，同一会话内自己改文件就漂，两轮返工。
- **图里已有答案的符号照样被 grep**：`UpsertSpend`、`handleSpend`、`SpendEntry` 等节点带完整签名/字段/摘要躺在 baseline 里，会话零次调用 `graph chain/who-calls/domains`；另有 10 次用 python 手解图 JSON。
- 覆盖两个硬洞恰砸在探索主战场：executor 家族仅 15 节点（对照 agentd 530），web/TS 侧零节点。

结论：**探索开销一半是覆盖缺口，一半是采纳缺口**——图不在 agent 的默认动作序列里，且对已覆盖部分缺一条「单点直答」的查询。

### 1.2 北极星

**代码图的主目的：省下 agent 对已有代码的探索上下文与时间。**架构对照（target + check）是同一份数据的另一个消费者，继续按既有 spec 运转，但不再是主线——主线是把图变成 agent 回答「在哪 / 什么形状 / 谁依赖谁」的**第一信息源**，让 grep/read 成为图未命中时的回落手段。

度量口径（方向性判据，不设硬 KPI）：同类开发任务的只读探索调用次数与结果字符量。本次实证基线：75 次 / 168K 字符；预期一二期落完后同类任务减半。

## 2. 原则（怎么做的三条铁律）

1. **图管定位、形状与关系，不管代码体理解。**签名、字段、file:line、调用边、投影链是图的责任；emit 顺序、缓冲大小、fixture 内容等行为事实必须读真代码。~40% 的探索本就不该省，也不许为省它把源码塞进图（08-19 已冻结「不存源码」，重申）。
2. **查询输出永远准，图数据允许陈旧。**行号漂移在「文档与代码同分支共进化」的流程里是常态，治法是**查询时再锚定**：图内行号只作提示，查询命令出结果前对目标文件就地校验，漂了就近重找并吐当前行号；符号从图中位置彻底消失时明示而非猜。保鲜不靠加密重扫（分支内永远追不上），靠既有 absorb 流程副产物 + 查询时决议。
3. **采纳靠流程接线，不靠 agent 自觉。**工具存在≠工具被用（本次实证）。查询能力与采纳回路必须同期落地：charter 事实调查步骤明文「有图先查图」，会话开局注入图存在性摘要，未命中留下结构化的覆盖债记录。缺任何一半都测不出真实收益。

## 3. 能力路线（三条线并行，互不阻塞）

| 线 | 内容 | 归属 |
|---|---|---|
| **一期（本 spec）** | `graph sym` 单点查询（含查询时再锚定）+ 采纳接线（charter 条款 + 会话开局摘要 + 覆盖债记录约定） | 本地做 |
| **覆盖线** | executor 子包漏扫根因排查与补扫；web/TS 侧入图（schema 语言维度扩展随卡定） | **走派发**，另立卡，不占本期 |
| **二期挂账** | entity 投影链查询（wire 实体 → store → 手搭 map → types.ts → UI，自动化序列化边界四查）；文档符号锚 `file#Symbol` + resolve 渲染/校验；`graph contract set` 受检写入口；MCP 包装；agentd review 回路自动扫描（沿既有挂账） | 覆盖债还清后按收益排期 |

依赖关系：entity 链硬依赖 TS 入图（覆盖线），故不进一期——这是一期范围岔口的核心弃选理由（§4.1）。

## 4. 一期 Spec

**级别与档位：L2（单子系统，不动 wire 契约层）。**主体落图子系统（d_contract 域的 codegraph 包），CLI 薄壳沿 `d_cli → d_contract` 既有依赖方向；采纳接线是流程文档改动，不构成子系统。若 target 契约条目需把查询容器补进 entries，属既有方向上的入口声明补全，非新依赖方向。路由：plan → implement → review → acceptance → finish。判错纠偏走跨流迁移。

### 4.1 方案与弃选

| 方案 | 判决 | 理由 |
|---|---|---|
| **查询面 + 采纳接线同期落地** | **采用** | sym 直击最大宗模式（35 次两连）；采纳不接线则重演「图在没人用」；二者合起来才构成可度量的回路 |
| 一期直取 entity 投影链 | 弃 | 杠杆最高（对应最烂缺陷族）但硬依赖 TS 入图与 schema 扩展，等于让覆盖派发阻塞本期 |
| 采纳先行零代码，收数据再定查询面 | 弃 | sym 缺口已有 35 次两连的实证，再等一轮数据是重复取证 |
| 保鲜：靠扫描收敛行号 | 弃 | 分支内永远追不上，agent 自己的编辑即漂移源 |
| 保鲜：吐行号带「可能已漂」警告 | 弃 | 把返工塞回每次查询，省下的调用又花回去 |
| 文档符号锚进一期 | 弃（挂二期） | 复用「查询时再锚定」同一套决议逻辑，二期顺势；痛点真实但频次低（每 contract/breakdown 节点一轮） |

### 4.2 用户故事

1. agent 想知道某符号在哪、什么签名/字段：一条 `graph sym <名字>` 拿到已再锚定的 file:line + 签名/字段 + 摘要 + 所属容器与域，代替 grep→sed 两连；需要读体时按行号一发精确读。
2. agent 查的名字多义：命令列出全部同名候选（含容器限定形式），agent 自选，不猜。
3. agent 查的符号不在图里：命令明示「图未覆盖」并给近似候选；agent 回落 grep，并按 charter 条款把未命中符号记进本节点产出物的「图覆盖债」小节。
4. 图存的行号已漂（分支内有人改过文件）：查询输出的是当前真实行号，agent 不需要自己验证锚点。
5. 新会话开局：agent 在会话上下文里看到图的存在性摘要（规模、域数、可用子命令），知道「先查图」是本仓库的默认动作。
6. charter 的 spec/plan 节点做事实调查：步骤正文明文「项目有代码图时优先 graph 查询，未命中再 grep 并记债」。

### 4.3 实现决定

- `graph sym` 进既有 `handoff graph` 子命令族，**保持本地只读**（08-19 冻结的三层边界不动）：直读仓库 JSON + 只读目标源文件做再锚定，不经 agentd，离线可用。
- 名字决议复用既有 Resolve 语义（id 精确 > 名字精确 > contains 候选），多义不猜、未命中给候选——与 chain/who-calls 行为同族。
- 再锚定语义：命中节点后读目标文件，符号仍在图示行附近即吐图示行；漂了在文件内就近重找该符号定义并吐新行号；文件或符号消失则明示状态。**不回写图数据**（只读边界）。
- 覆盖债记录不给 CLI 加写副作用：未命中时输出结构化提示，债的沉淀走 charter 步骤（agent 写进节点产出物），重扫/absorb 时消化——基准靠流程副产物保鲜的既有纪律。
- 采纳接线两处落点：charter 仓的 spec/plan 节点正文加通用条款（写「项目有代码图时」，不写 handoff 专名——charter 是全局套件）；handoff 仓会话开局注入图摘要（形态归 plan 定）。
- 输出形态为 agent 优化：紧凑、可直接引用、行号即时可用；具体版式归 plan。

### 4.4 测试决定（接缝清单）

**最高可测缝一条：codegraph 包的查询导出函数**（d_contract 为 logic 域，机内可闭环）。

- 单测覆盖四态：命中（行号未漂）/ 命中但漂移（夹具文件故意错行号，验证再锚定）/ 多义（候选列表）/ 未命中（近似候选 + 图外明示）。
- CLI 薄壳一条烟测（参数到输出的通路）。
- 验收实证步骤：拿 2026-08-22 会话实际 grep 过的符号清单（UpsertSpend、handleSpend、SpendEntry、Cumulative、TaskCumulative、FrameWriter.ToolResult、mapToolPart 等）在真仓库跑 sym，记录命中率——已覆盖符号应全命中且锚点准确，executor/TS 侧未命中应正确走图外路径（该结果同时是覆盖线派发卡的验收基线）。
- charter 条款与会话注入属文档/配置改动，验收方式：新会话开局可见摘要、节点正文含条款（人工核对，不立自动化）。

### 4.5 Out of Scope（显式不做）

- **覆盖补齐**：executor 子包漏扫根因与补扫、web/TS 入图——走派发，另立两张卡，本期零实现。
- **entity 投影链查询**——二期（依赖覆盖线）。
- **文档符号锚 + resolve 渲染/校验**——二期。
- **`graph contract set` 受检写入口**——二期。
- **MCP 包装、agentd review 回路自动扫描**——沿 08-19/08-21 既有二期挂账，本文不改其状态。
- **web 查看器任何改动**——零。
- **「开新活强制必查图」硬闸**——不做。先靠条款与摘要注入，真踩坑（agent 明知有图仍绕过）再补闸，同 backlog 纪律的先例。
- **图查询进其他项目的通用化**——数据契约本就项目内自洽，但采纳接线只做 handoff + charter 通用条款，不逐项目铺。

### 4.6 备注

- 岔口拍板记录（2026-08-22，用户）：一期范围=查询面+采纳接线；保鲜=查询时再锚定；文档符号锚=挂二期。
- 覆盖线派发卡的先决事实：executor 家族 15 节点 vs agentd 530，怀疑扫描配方或时点问题，根因先查再补扫，不带病重扫。
- 二期排期时优先 entity 链：序列化边界是本项目缺陷史最烂一族（15 处手搭 map 回包、08-21 两次 wire 缺陷），自动化它的四查收益大于其余挂账项。
