## 6. 冻结清单

每条单独可判 pass/fail。

### 6.1 名称解析

1. 未给接收者名时，必须用已确认的默认载体名，不得用 `cfg.Executor.Default` 当接收者。
2. 未给接收者名且默认名为空时必须失败，错误链含 `ErrNoDefault`。
3. 未给接收者名且默认名只空白时必须失败，错误链含 `ErrNoDefault`。
4. 显式名非空时必须使用去空白后的该名，不得改走默认。
5. 同一名字只在载体表存在时，`ClassifyRegistered` 必须返回 `ReceiverCarrier`。
6. 同一名字只在小队表存在时，`ClassifyRegistered` 必须返回 `ReceiverSquad`。
7. 同一名字同时在载体表和小队表存在时必须失败，错误链含 `ErrNameConflict`。
8. 显式名两边都不存在时必须失败，错误链含 `ErrNotFound`。
9. 名称冲突时不得按「载体优先」或「小队优先」猜测。
10. 默认名两边都不存在时必须失败，错误链含 `ErrNoDefault`（不是只含 `ErrNotFound` 而不含 `ErrNoDefault`）。
11. 默认名只命中小队时必须失败，错误链含 `ErrNoDefault`。
12. 默认名冲突时必须失败，错误链含 `ErrNameConflict`。
13. `ReceiverCarrier` 的字节结果是 `carrier`。
14. `ReceiverSquad` 的字节结果是 `squad`。
15. 旧数据已有跨 kind 重名时，有类型的引用（显式查载体或显式查小队）仍可按原 kind 读取；无类型名称派发必须走第 7 条。
16. `PutCarrier` 时若同名小队已存在必须失败，错误链含 `ErrNameConflict`。
17. `PutSquad` 时若同名载体已存在必须失败，错误链含 `ErrNameConflict`。

### 6.2 默认载体

18. 默认载体 singleton 的 registry kind 必须是 `KindDefaultCarrier`。
19. 默认载体 singleton 的 id 必须是 `DefaultCarrierID`。
20. `KindDefaultCarrier` 的字节结果是 `default_carrier`。
21. `DefaultCarrierID` 的字节结果是 `current`。
22. `current` 不得被解析为可派发接收者名。
23. `EncodeDefaultCarrier("muse")` 的字节结果是 `{"name":"muse"}`。
24. `DecodeDefaultCarrier([]byte("{\"name\":\"muse\"}"))` 必须返回 `muse`。
25. `EncodeDefaultCarrier("")` 必须失败，错误链含 `ErrNoDefault`。
26. `DecodeDefaultCarrier([]byte("{\"name\":\"\"}"))` 必须失败，错误链含 `ErrNoDefault`。
27. 默认载体记录的 `name` 必须是已登记载体名，不得是小队名。
28. 没有默认载体记录时，空接收者派发必须 `ErrNoDefault`，不得回退裸环境。

### 6.3 物理身份与模型

29. `IdentityOf` 的 Machine 必须等于 `Carrier.Machine`。
30. `IdentityOf` 的 CLI 必须等于 `Carrier.CLI`。
31. `IdentityOf` 的 HomeDir 必须等于 `Carrier.HomeDir`。
32. `BindPhysical` 在 overlay 全未指定时必须返回原身份。
33. overlay.Machine 非空且不等于身份 Machine 时必须失败，错误链含 `ErrPhysicalOverride`。
34. overlay.CLI 非空且不等于身份 CLI 时必须失败，错误链含 `ErrPhysicalOverride`。
35. overlay.HomeDir 非 nil 且值不等于身份 HomeDir 时必须失败，错误链含 `ErrPhysicalOverride`。
36. overlay 三个物理字段与身份逐字节相同时必须成功（重述合法）。
37. 绑定后任务实际 target 必须等于绑定载体的 Machine。
38. 绑定后任务实际 executor 必须等于绑定载体的 CLI。
39. 绑定后任务实际 HOME 必须等于绑定当时的 HomeDir 快照。
40. `EffectiveModel("", "gpt-y")` 的字节结果是 `gpt-y`。
41. `EffectiveModel("gpt-x", "")` 的字节结果是 `gpt-x`。
42. `EffectiveModel("gpt-x", "  gpt-y  ")` 的字节结果是 `gpt-y`。
43. 模型覆盖不得改变 Machine、CLI 或 HomeDir。
44. 模型覆盖不得扩大该任务的有效权限（权限仍由载体提交的政策 + 233.1/233.2 快照决定）。

### 6.4 占用键与容量

45. `OccupancyCarrierKey("muse")` 的字节结果是 `carrier/muse`。
46. `OccupancyMemberKey("exec", "muse")` 的字节结果是 `squad/exec/muse`。
47. `OccupancyMemberKey("", "muse")` 的字节结果是空串。
48. `OccupancyKeys("", "muse")` 的成员键必须为空、载体键必须是 `carrier/muse`。
49. `OccupancyKeys("exec", "muse")` 必须同时返回成员键与载体键。
50. 载体直派（接收者是载体、无小队）只占用载体物理位，不得占用任何小队成员键。
51. 小队派发必须同时占用成员政策位与载体物理位（既有 `Admit`）。
52. 满员必须 `ErrNoSlot` 或转入既有点火队列，不得另造执行落点。
53. 准入成功之后、执行启动失败，必须释放本次占用。
54. 取消仍占用的执行必须释放占用。
55. 恢复/续接不得再次 `Admit` 同一占用。
56. `Release` 在计数已为 0 时不得把计数减成负数（既有幂等）。
57. 仍在使用的占用不得提前释放。
58. 编制域方法不得读取卡列或 import `internal/ledger` 的卡 API。

### 6.5 任务快照与共享准备链

59. `proto.Task` 必须声明 `Carrier` 字段，JSON 键为 `carrier`。
60. `Binding` 必须声明 `HomeDir` 字段，JSON 键为 `home_dir`。
61. HTTP `POST /api/tasks` 的接收者字段 JSON 键必须是 `receiver`。
62. `receiver` 空或缺席表示走默认载体，不是走 `executor.default`。
63. 本卡不新增 HTTP 路径。
64. 裸派发（`handleDispatch`）与卡节点派发（`startCardStep`）必须调用同一套 `ResolveLookup` → 准入 → `BindPhysical`。
65. `Manager.Dispatch` 不得调用 `ResolveLookup` / `ClassifyRegistered` / `EffectiveReceiverName`。
66. 任务一旦写入 Carrier/HomeDir/Target/Executor，事后 `PutCarrier` 改机器/引擎/HOME 不得改写该历史任务的解释。
67. 工作流/卡节点在绑定之后不得再拼接机器名与 HOME 作为执行落点。
68. 载体提交 HOME/规则/skills/有效权限；任务只叠加本次纪律快照（233.1/233.2），不得用任务纪律覆盖载体全局规则。
69. 小队只选择成员并计数，输出一个载体；小队本身不是执行落点。
70. `ErrNoDefault` 的字节结果是 `scheduling: 没有有效的默认载体`。
71. `ErrNameConflict` 的字节结果是 `scheduling: 名称同时登记为载体和小队`。
72. `ErrPhysicalOverride` 的字节结果是 `scheduling: 禁止覆盖已绑定载体的机器、引擎或 HOME`。
73. 具体编制实现只在登记的组装点绑定。
74. `internal/scheduling` 的本卡新文件不得 import `internal/ledger`。
75. `internal/scheduling` 的本卡新文件不得 import `internal/agentd`。

## 8. 三重闸门拍板记录

命中三条的决定：

1. **已确认默认载体存在编制 registry（kind `default_carrier` / id `current`），不存在 `config.executor.default`。** 回头要动 init、派发入口、编制域与设置页。后人看到 `executor.default` 仍在用会想「空接收者继续走它」。被否方案：把 `executor.default` 当隐式默认载体（这正是 spec 禁止的裸环境回退）；默认部门。首次配置/自动建载体仍 OOS——本卡只冻「读已确认默认」，不冻「怎么第一次写上」。
2. **名称解析、准入、物理绑定的权威在 `d_scheduling`；`Manager.Dispatch` 不解析接收者。** 回头要动 gateway、编排、目标图（会新开 `d_orchestration→d_scheduling`）。后人看到 Dispatch 是派发入口会想把解析塞进 Manager。被否方案：Manager 直调 `scheduling.Service`；CLI 直 import scheduling 做准入。gateway 的 `handleDispatch` 与 `startCardStep` 共用编制域函数，Manager 只消费已冻结身份。
3. **绑定后机器/引擎/HOME 不得被请求覆盖；模型可以逐任务覆盖且不扩大权限。** 反过来继续让 `bindingFor` 覆盖物理身份，现有小队测试仍可能绿（今日实现就是覆盖）。被否方案：维持 `bindingFor` 的「请求覆盖 > 载体缺省」；允许 HOME/target/executor 随任务改绑。空 overlay 保持载体值；显式相同值重述合法。

显式不做（spec 已否，此处不重复展开）：自动发现建载体、默认部门、改 push 归属、233.6 工作流订阅。
