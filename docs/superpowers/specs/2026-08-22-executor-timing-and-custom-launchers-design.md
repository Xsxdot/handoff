# Spec：执行耗时统计 + 工作台自定义启动项

日期 2026-08-22 · 分支 `claude/executor-timing-custom-tabs-e59c46`

**本文含两个彼此独立的需求，各自定级、各自成流。**共享的只有两处表面接触（都碰 d_contract 与 d_web），没有共享语义，可以并行走也可以先 A 后 B。

| | 级别 | 档位 | 路由 |
|---|---|---|---|
| 需求 A：执行耗时的采集、落账与展示 | **L3** | **重档** | contract → breakdown → 各子系统并行 → integrate → finish |
| 需求 B：工作台自定义启动项 | **L3** | **重档** | 同上 |

定级依据（按定稿范围复核）：两者都跨 3 个以上子系统的契约面，且都动跨进程 wire 契约（A 动帧格式与任务详情接口，B 动终端会话创建接口）。选档依据：两者各自都有单子系统工作量明显超过流程固定成本（A 的 d_executor 要改四家 adapter；B 的 d_web 要做配置对话框 + 列表 + 管理块）。

# 需求 A：执行耗时的采集、落账与展示

## A.1 问题陈述

任务跑完，今天能读到的只有两样：页头的「运行时长」（一个总数）与 `UsageChip` 的 token/花费账目。想回答「这次为什么跑了 40 分钟」时，没有任何可读数字——是模型在想，还是某条 `go test` 卡住了，还是在等审批，全靠翻 render.log 猜。

现状的三个具体障碍：

1. **grok 与 opencode 根本不产工具帧**。`FrameWriter.ToolCall/ToolResult` 今天只有 claudecode（[adapter.go:685](internal/executor/claudecode/adapter.go:685)）与 codex（[adapter.go:1128](internal/executor/codex/adapter.go:1128)）在调。grok 把 `tool_call` / `tool_call_update` 归了 `updateNone`（[adapter.go:727](internal/executor/grok/adapter.go:727)），opencode 的 `frameKind` 对 tool part 返回 `kindSkip`（[adapter.go:1516](internal/executor/opencode/adapter.go:1516)）。而 CLAUDE.md 的派发决策表把 codex 与 **grok** 列为两个常用执行器——不补 grok，这个功能对一半的实际派发无效。
2. **没有任何可聚合、可跨会话查询的耗时事实**。`frames.jsonl` 每帧有 `ts`，但前端有 `maxLoadedFrames = 5000` 的硬上限，到顶即停止回翻——统计会恰好在最长、最需要看的那些任务上失效。
3. **已有的 elapsed 打点只进日志**（[codex/adapter.go:327](internal/executor/codex/adapter.go:327)、[codex/proc.go:189](internal/executor/codex/proc.go:189)），不进任何可查询面。

> 顺带订正一处过时注释：[opencode/adapter.go:1511](internal/executor/opencode/adapter.go:1511) 写着「工具调用本身由 mapToolPart 以完整的 tool_call 帧上报」，但 `mapToolPart` 这个函数**不存在**，opencode 一个工具帧都不产。实现时一并删掉这句谎话。

## A.2 方案

**选用：显式打点 + 落账（与 `SpendEntry` 同构）。**

- adapter 贴着协议事件在两类边界显式打点，产出**幂等的耗时账目条目**，沿 `AdapterEvent` 交给 manager 落账（与 `Spend` 完全同一条路，见 [executor.go:195](internal/executor/executor.go:195)）
- 帧上带一个耗时字段，让工具卡不必回查账本就能画出单次耗时
- 补齐 grok（ACP `tool_call` → `tool_call_update`）与 opencode（`part.updated` 的 tool part，`state.status` 已可见，见 [api.go:445](internal/executor/opencode/api.go:445)）的工具帧

**弃选 1：纯前端从帧 `ts` 相减。** 零后端改动，最省。弃因：grok/opencode 不产工具帧，拿不到工具粒度；且统计只活在当前页面，`maxLoadedFrames` 到顶即失真。

**弃选 2：打点但不落账。** 省一张表。弃因：同上第二条——「回看昨天那个任务的耗时」要重新加载全部帧，长任务上必然失效。而落账的成本只是复用一遍 `UpsertSpend` 已经趟平的形状。

**弃选 3：只信上游自报**（如 claude `result` 行的 `duration_api_ms`）。最准。弃因：覆盖最稀（只有 claude 有），且四家口径互不可比——两次派发换个执行器数字就没法对照，恰好毁掉「优化流程」这个目的。

## A.3 口径：三分法（本需求的核心契约语义）

一个回合的墙钟时间被切成三类，**三类之和恒等于回合墙钟**：

| 段 | 边界 |
|---|---|
| **模型段** `api` | 从「回合开始」或「上一批工具结果全部提交」起，到「本轮模型输出结束」（出现工具调用，或回合终结）止 |
| **工具段** `tool` | 单次工具调用：从 tool_call 打点到对应 tool_result 打点 |
| **未归类** `other` | 回合墙钟 − Σ模型段 − Σ工具段。承载排队、等审批（`waiting_answer` / `permission_request`）、框架开销 |

三条硬规则：

1. **未归类必须单独显示，绝不摊进模型段。** 与仓库既有纪律同源（`CostUnknown` 绝不显示成 `$0.00`）：把「等人审批的 20 分钟」计进「API 耗时」，会让拿这个数字去优化流程的人优化错东西——而且看不出来。
2. **`other` 不由 adapter 上报。** 它是聚合侧按「回合墙钟 − 已上报之和」算出来的差额。adapter 看不见排队与审批，它编出来的 `other` 是假的。
3. **并发工具如实并列。** claude 会并行发多个 `tool_use`，此时 Σ工具段 > 工具占用的墙钟跨度。聚合面**同时**给出两个数（「工具耗时之和」与「工具墙钟跨度」），不取其一冒充另一个；`other` 用墙钟跨度算，否则会算出负数。

## A.4 用户故事

1. 我在 TUI 里看一张工具卡，右上角写着 `3m04s`，立刻知道是这条 `go test` 卡住了整个回合。
2. 我点页头的「耗时」chip（与 ctx 账目同形的弹出），看到本任务：`总 42m · 模型 8m12s · 工具 26m40s · 未归类 7m08s`。
3. 同一个弹出里，按工具名聚合的排行：`Bash 24m（37 次）· Read 1m20s（88 次）`；Bash 那一行可展开成按命令首词聚合：`go test 21m（9 次）· npm 2m（3 次）`。这是「各个命令耗费了多少时间」的主落点。
4. 我在命令行拿到同一份数字（结构化输出），可以脚本化对比两次派发。
5. 任务跑在 **grok** 上，我照样看得到工具粒度耗时——不是只有 codex/claude 才有。
6. 一个老任务（本功能上线前跑的）没有打点数据，面板显示「—」而不是 `0`，我一眼看得出是「没这份数据」而不是「没花时间」。

## A.5 契约语义与接缝（L3）

跨的子系统：**d_executor**（打点）→ **d_contract**（帧字段与账目类型）→ **d_ledger**（落账与聚合）→ **d_controlplane**（任务详情接口）→ **d_web** + **d_cli**（两个展示面）。

1. **耗时账目条目与 `SpendEntry` 同构**：带任务内**稳定且唯一**的幂等 Key，重复上报按**覆盖**不是累加（流式场景下同一次调用会被多次观测到）；Key 为空即拒写。这条不是「参考一下」，是要求走同一套幂等语义——两套幂等规则并存必然漂移。
2. **段的种类是封闭集合**：`api` / `tool` / `other`，其中 `other` 只在聚合层产生，adapter 永不上报（见 A.3 规则 2）。
3. **缺席语义**：某个 executor 报不出某类段时，聚合结果里该类是「未知」而不是 0，展示为「—」。与 `CostUnknown` 同一条纪律。
4. **依赖方向不新增**：adapter 经 `AdapterEvent` 把条目交出去，manager 落 store。d_executor **不直接依赖** d_ledger（目标图里也没有这条边）。
5. **帧上的耗时字段是投影，账本是真相**。它是刻意的小冗余（与 `Frame.Event` 冗余存类型名同款理由）：工具卡不必查账本就能画。两者不一致时以账本为准，界面不并列显示。

不在 spec 里定的（归 contract 节点）：精确字段名与类型、端点形状、表结构、CLI 子命令与旗标的确切拼写。

## A.6 实现决定

- **打点位置必须在 adapter 内、贴着协议事件**，不得在 `FrameWriter` 里按「写帧时刻」倒推——写帧时刻含轮询延迟（claudecode 的 tailer 是 200ms 轮询，见 [stream.go:33](internal/executor/claudecode/stream.go:33)），两侧延迟不对称时会系统性偏移。
- **时钟必须可注入**，否则测试立刻退化成计时竞态（`flaky-tests-are-proxy-conditions` 那一族）。
- 回合墙钟以 `turn_start` 帧与回合终结事件为准，不另立一套回合边界。
- 补 grok/opencode 工具帧时，`Input`/`Output` 沿用既有头尾截断与 `Bytes` 原始长度语义，不新造一套。

## A.7 测试决定（接缝清单）

- **主缝（一个）：adapter 的协议事件 → 耗时账目条目。** 四家各一组，喂固定事件序列 + 注入时钟，断言产出的条目集合。这是全部四家差异的收口处，也是唯一值得四倍投入的缝。
- **次缝：聚合函数（账目集合 + 回合边界 → 三分法结果）。** 纯函数穷举，必含两个边界：并发工具导致 Σ工具段 > 墙钟跨度；某类缺席时结果为「未知」而非 0。
- **不新造缝**：帧写入沿既有 `frames_test`，web 展示沿既有组件测试，CLI 沿既有命令测试。

## A.8 Out of Scope

- **回合级汇总行**（选型时明确未选）：不在回合分隔处显示模型/工具/未归类拆分。工具卡 + 任务级面板两处已覆盖需求。
- **跨任务 / 全局耗时看板**：本期不做。CLI 已能拿到单任务的结构化数字，跨任务对比先靠脚本。
- **与上游自报耗时对账**（claude 的 `duration_api_ms` 与三分法的差异分析）：不做，也不展示。
- **TTFT（首 token 延迟）单列一项**：不拆，含在模型段里。
- **历史任务回填**：已跑完的任务没有打点数据，一律显示「—」。不猜、不回填、不用帧 `ts` 事后倒推补一份质量不同的数据混进同一张表。
- **把耗时并进 ledger 的任务卡账**：不做，与账本域的关系限于 store 落盘。

# 需求 B：工作台自定义启动项

## B.1 问题陈述

空白 tab 与 `+` 菜单今天只有三项（新终端 / 新建文件 / 打开任务，见 [BlankTab.tsx:22](web/src/app/workbench/BlankTab.tsx:22)）。最常做的一类事——「带某份 Env 文件起一个终端，并跑某条固定命令」——今天要开终端、手动注入变量、手动敲命令，每次重复。

现状约束两条：

- `CreatePtySessionReq`（[pty.go:47](internal/proto/pty.go:47)）只有 `base_path` / `base_kind` / `rel` / `cols` / `rows`，**没有 env、没有命令**。
- 但底层 `ptyhost.OpenOptions` 已经有 `Env []string`（注释写明「完整环境，不会再自动追加 os.Environ」，见 [types.go:41](internal/ptyhost/types.go:41)）。所以缺的是上层契约与解析，不是底层能力。

## B.2 方案

**选用：机器级落盘的启动项配置 + 终端会话创建契约扩展。**

- 一条启动项 = **名字**（必填） + **Env 文件**（该机器上已有的一份，可选） + **执行命令**（可选）；Env 与命令**至少填一个**。
- 落在启动项所属机器上（与 Env 文件同机），管理入口在机器详情页，与 `MachineEnv` / `MachineExecutor` / `MachineDiscipline` 并列成第四块。
- 工作台的空白 tab 与 `+` 菜单，在内置三项之下列出「当前基准目录所在机器」的启动项。
- 选中即开一个终端 tab：起 login shell（注入所选 Env 文件的变量），shell 就绪后把命令送进去。**命令跑完人还能继续用这个终端**，Ctrl-C 只杀命令不杀会话。

**弃选 1：控制台全局一份。** 配一次到处可见，UX 最省。弃因：Env 文件是机器级的，一条引用 `prod.env` 的启动项在没有该文件的机器上只能在启动那一刻失败；且与 CONTEXT.md 里「Env 文件存放在**一台**代码宿主的 handoff 目录中」「执行器配置**属于机器**，不属于桌面端全局设置」的既有产品语言直接相悖。

**弃选 2：项目级。** 弃因：一个项目可以同时有本机位置与远程位置，两侧的 env 文件未必同名——会把「这条启动项属于谁」拆成两个真相。

**弃选 3：落进 `config.yaml`。** 弃因：config 以 `KnownFields(true)` 严格解析，新键会让**旧版 agentd 读到新版写的配置直接启动失败**——这是 `PathDirs` / `Proxy` 注释里逐字记着的坑（「omitempty 是硬要求，不是风格」）。启动项是一张会长的列表，单独一个文件没有这个换版风险。

## B.3 用户故事

1. 我在机器详情页新建一条启动项：名字「claude 生产」、Env 选 `prod.env`、命令留空 → 工作台里点它，得到一个已注入生产变量的终端。
2. 名字「跑测试」、Env 留空、命令 `go test ./...` → 点一下就开始跑；跑完我在同一个终端里接着敲别的。
3. 我只填了名字就保存，被拒，提示「Env 文件与执行命令至少填一个」。
4. 空白 tab 上，内置三项之下列着我的启动项，跟内置项一样一点即开。
5. 我在一台不能开终端的机器上（`pty_supported=false`），一条启动项都看不到——它们本质都是终端。
6. 我删掉了 `prod.env`，引用它的启动项在列表里被标为失效；点击时给出实话（「Env 文件 prod.env 不存在」），而不是静默起一个没有变量的终端让我在半小时后才发现。

## B.4 契约语义与接缝（L3）

跨的子系统：**d_web**（配置与列表）→ **d_contract**（两组线格式）→ **d_controlplane**（CRUD 与会话创建）→ **d_localint**（落盘）+ **d_host**（起 shell 与送命令）；远端机器还要穿 **d_remote** 的透传层。

1. **终端会话创建新增两项可选输入**：一份 Env 文件名、一条初始命令。**两者都缺席时，行为与今天逐字节相同**——这是兼容性判据，不是愿望，要有断言守住。
2. **Env 文件名的解析发生在服务端**，且复用 `envfile` 既有的纯文件名校验（含路径分隔符即拒，见 [files.go:151](internal/envfile/files.go:151)）。**客户端永不发送变量值**——凭据边界与 [proto/env.go](internal/proto/env.go) 里「本文件里没有任何字段承载 env 的值」是同一条。
3. **初始命令在 shell 内部执行，不是 shell 的 argv**：会话在命令退出后继续存在。命令原文由服务端在 shell 就绪后送进 PTY 输入。
4. **启动项配置是机器级资源**：读写与 Env 一样带 machine 参数，由汇总方透传到目标机。
5. **失效引用不静默**：启动项引用的 Env 文件不存在时，读取面把它标出来；创建会话时**拒绝**，不降级成无变量终端。

不在 spec 里定的（归 contract 节点）：端点路径、结构体字段名、启动项 id 的生成方式、落盘文件的确切格式与文件名。

## B.5 实现决定

- **「shell 就绪」的判据要在 contract/plan 阶段查证现状后定**，不得用固定 sleep 猜。这是本需求唯一有真实不确定性的点，必须当成一次事实调查而不是一个默认值。
- **home 基准目录下也展示启动项**：`pickItemsFor` 今天在 home 只留终端（[BlankTab.tsx:59](web/src/app/workbench/BlankTab.tsx:59)），启动项与终端同类，一并放行。
- **终端不可用时一并摘掉启动项，不置灰**——置灰是在承诺「以后能用」，用户会反复点它（BlankTab 既有纪律）。
- **启动项不分配快捷键**：内置三项有 ⌘T/⌘N/⌘⇧A，启动项数量不定，分配规则会立刻变成一张要维护的表。

## B.6 测试决定（接缝清单）

- **主缝（一个）：会话创建请求 → 实际起出来的 shell 环境 + PTY 首次输入。** 服务端侧，四种组合全覆盖（都不带 / 只带 env / 只带命令 / 都带），外加「env 文件不存在则拒绝」。「都不带 == 今天的行为」这条断言是兼容性的唯一守卫。
- **次缝：启动项配置的校验纯函数**（名字必填、至少填一个、纯文件名校验），穷举。
- **不新造缝**：web 的对话框与列表沿既有组件测试；远端透传沿既有 machine 参数的测试形态。

## B.7 Out of Scope

- **启动项指定工作目录**：不做。工作目录恒为当前基准目录，与「新终端」一致。
- **一条启动项选多份 Env 文件**：不做，与 `EnvBinding` 的「各自选择其中一份」保持一致。
- **启动项做成非终端形态**（直接开 TUI tab、直接派发任务）：不做。本期它就是「参数化的新终端」。
- **导入 / 导出 / 跨机同步启动项**：不做。机器级就是机器级。
- **快捷键分配**：见 B.5。
- **命令历史、参数占位符、启动项分组或排序自定义**：不做。

## B.8 备注

新字段要穿过远端汇总层。实现时必须验证 **「新版控制台 → 旧版远端 agentd」** 的行为（旧端不认识新字段会怎样：静默忽略从而起出一个没有变量的终端，还是报错）——这是本需求最容易漏、且漏了之后最难查的一处。

# 交棒

两条流各自 L3 重档，下一节点都是 `charter:contract`。建议先 A 后 B：A 的四家 adapter 改动面更大、也更需要完整的注意力；B 的形态已经定死，随时可以起。
