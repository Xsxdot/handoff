# B219：负向权限用例的前提自检——把「限制真生效了吗」从记忆变成结构

- **卡**：B219
- **级别与档位**：**L2**（定级理由见下「定级」节）
- **状态**：待用户批准
- **来源**：2026-08-23 B212/B215 两轮派发环境全量测试；卡上首条 comment 记的是「三处」，本 spec 的现状核查更正为**四处恒红 + 三处已有守卫**

## 问题陈述

仓库里有一类测试：**用 mode 位造出一个写不进（或读不出）的路径，然后断言应用在写失败时的降级行为**。

这类测试的前提——「造出来的限制真的挡得住我」——**不是所有机器都成立**：

- **root 持有 `CAP_DAC_OVERRIDE`，无视 mode 位**。而 linux-01 上的 executor 正是以 root 跑。
- **Windows 上 `chmod` 对目录基本是空操作**，同样表达不出「只读目录」。

前提不成立时，写照样成功、降级分支根本不进，断言必然落空——**用例恒红，且红得毫无信息量**。

这不是新问题：仓库已经在**三处**遇到并各自处理过（见现状核查）。问题在于处理方式是**每个作者自己记得写一行守卫**，于是四处漏了。

**为什么值得修**：与 B212（socket 路径超限）、B215（围栏用例的负向权限断言）是同一笔账——只要还有一族恒红，派发环境就永远拿不到一次干净的 `go test ./...`，纪律块里「没跑到结果不许写结论」这条判据在远端就**恒假**。B212、B215 已修；这是已知的最后一族。

## 现状核查（判据全量扫，不是「哪几条报过红」）

扫描判据：测试代码中任何「属主无写位」的 mode 常量（`0o0xx` / `0o4xx` / `0o5xx`）。**这个集合与「实际观测到红的集合」不是一回事**——观测视野受限于哪台机器跑过、输出有没有被过滤，判据的定义域才是真实范围。

| 站点 | 前提自检 | 该机器上的表现 |
|---|---|---|
| `internal/client/cursor_layout_test.go#TestReadCursorPermissionDeniedIsReported` | ✅ `Geteuid()==0 → t.Skip` | root 下跳过 |
| `internal/release/install_test.go#TestActivateUnwritableDir` | ✅ 两道：chmod 报错跳 + `Geteuid()==0` 跳 | root 下跳过 |
| `internal/prochost/fence_inherit_test.go#TestFenceCannotBeRaisedBack` | ✅ `Geteuid()==0`（B215 本轮所加） | root 下第 2 段跳过 |
| `internal/client/cursordir_test.go#TestCursorRootFallsBackToCwdWhenHomeUnwritable` | ❌ 无 | **root 下恒红** |
| `internal/client/cursordir_test.go#TestCursorRootErrorNamesBothPaths` | ❌ 无 | **root 下恒红** |
| `internal/config/config_test.go#TestLoadStripUpdateDoesNotBlockOnSaveFailure` | ❌ 无 | **root 下恒红** |
| `internal/executor/grok/authsync_test.go#TestSyncAuthKeepsTaskCopyWhenWriteFails` | ❌ 无 | **root 下恒红** |

四条恒红均为「构造上必红」，非偶发：root 下写成功 → 降级分支不进 → 断言落空。

两条与本 spec 相关的现状读数：

- **CI 跑在 `ubuntu-latest`（非 root）**（`.github/workflows/ci.yml:20,31`）。因此「不满足前提就跳过」**不丢覆盖**：这些用例在 CI 里照常有牙。
- **Windows CI 只跑 `internal/prochost` 与 `internal/executor/claudecode`**（`ci.yml:105,125`），本 spec 涉及的其余四个包今天不在 Windows 上跑。B154（Windows 全量跑）是独立在飞的卡，本 spec 只保证**不给它添新债**。

现状读数（`文件:行`）由 plan 节点对本轮工作树复核。

## 与 B215 的关系：形似而不同类

B215 也是「负向权限断言在 root 下不成立」，但**处置方向相反**，不要照搬：

| | B215 | B219（本卡） |
|---|---|---|
| 被测对象 | 围栏的**单向门**——「降了 RLIMIT 就抬不回来」，这本身就是内核权限语义 | 应用的**降级逻辑**——「写失败时别把状态搞坏」 |
| `chmod`/降限的角色 | 被测性质的一部分 | 只是**制造前提的手段** |
| root 下跳过的代价 | 在最需要围栏的那台机器上不设防 → 不可接受，故改断直接性质、按能力分档 | 无——被测逻辑与运行身份无关，root 下只是前提不可达 |

**B215 的正解是「改断直接性质」，本卡沿用的正是同一条纪律**——只不过这里的「直接性质」是「我现在真的写不进去吗」，而不是「我是不是 root」。

## 方案

### 采纳：新建测试辅助包，前提自检用**探针**而非 euid

一个只服务测试的 internal 包（先例：`internal/ptytestroot`，包注释明写「只服务测试辅助，不参与生产运行时」），对外两个动词量级的入口：

- **禁写**某个路径（目录或文件）
- **禁读**某个文件

每个入口做三件事，缺一不可：

1. 施加限制（`chmod` / 建目录时给受限 mode）；
2. **探针**——立刻自己试一次写（或读）。**成功即说明限制没生效**：还原现场后 `t.Skip`，并在 skip 文案里说清是「这台机器表达不出这个前提」，不是「这条用例被禁用了」；
3. 注册 `t.Cleanup` 还原 mode。

**为什么探针而不是 `Geteuid()==0`**：euid 是**代理条件**，它猜的是「只有 root 能无视 mode 位」。这个猜测在 Windows 上落空、在带 `CAP_DAC_OVERRIDE` 的非 0 uid 容器里落空，而落空时用例不是跳过而是**假红**——与今天一模一样。探针断的是直接性质，一口气盖住 root、Windows、容器能力、奇怪 ACL 四类情形，且**未来新平台不用再补**。

**为什么还原是 helper 的职责而不是调用点的**：`authsync_test.go:257` 的注释已经记着「必须还原，否则 `t.TempDir` 的清理会失败」——这是第二个靠记忆维持的不变量。`t.Cleanup` 是 LIFO，helper 在 `t.TempDir()` 之后注册，还原必然先于目录删除，顺序天然正确。

**为什么这个包要 import `testing`**（与 `ptytestroot` 的形态不同，后者只返回值、由调用点自己判）：本卡的根因就是「守卫要人记得写」。若 helper 只返回 `ok bool`，调用点仍须记得 `if !ok { t.Skip() }`——把同一个健忘点换了个位置。收下 `testing.TB` 才能让守卫**用了就有**。`testing` 只被 `_test.go` 传递依赖，不进任何生产二进制。

### 弃选一：只补四处 `Geteuid()==0`，不抽 helper

改动最小、与现有三处逐字一致。弃选理由：**根因是「漏写」而非「写错」**——这四条本身就是漏写的产物，第八处大概率还会漏。且它把 euid 这个代理条件又复制四份。

### 弃选二：换手段，让判据与运行身份无关（不跳过，真跑）

即不用 mode 位造失败，改用注入错误或天然失败（如写向一个目录拿 `EISDIR`）。方向上最理想——覆盖一点不丢。弃选理由是**它会换掉被测对象**：`cursordir_test.go:41` 的注释明写它要的形状是「`MkdirAll` 成功而 `CreateTemp` 失败——正是沙箱里的形状」；换成 `ENOTDIR` 会让 `MkdirAll` 就失败，打到另一条代码路径。四处各自定制、各自可能测偏，收益（在 root 机器上多四条覆盖，而 CI 已经覆盖）不抵风险。**落 roadmap**，不在本期。

### 弃选三：执行机不以 root 跑测试

一次性关掉整族，含未来新增用例。弃选理由：它改的是**执行机运行方式**而非测试，牵涉用户、仓库权限、`GOCACHE`/`GOPATH` 落点，且 agentd 自身仍是 root、两者要共存；影响面远超本卡，也不该由本卡单方面决定。**落 roadmap**。

## 用户故事

1. 作为在 root 执行机上跑全量测试的人，我看到的是「N 条因这台机器表达不出前提而跳过」，不是四条无信息量的红，于是 `go test ./...` 的绿是可信的。
2. 作为下一个要写「写失败时降级」用例的人，我在包里找到现成的 helper 并直接用，不需要知道 `CAP_DAC_OVERRIDE` 是什么，也不会忘记还原 mode。
3. 作为审这条用例的人，我从 skip 文案就能分辨「这台机器不支持这个前提」与「这条用例被人禁用了」——前者是环境事实，后者需要追责。
4. 作为在 Windows 上跑这些包（B154）的人，同一个 helper 已经替我处理了 `chmod` 空操作，不需要再补一轮平台守卫。

## 实现决定

- 新包落在 `internal/` 下，包注释按 `ptytestroot` 的格式写清**职责与边界**，首句点明「只服务测试辅助，不参与生产运行时」。
- **精确包名、函数名与签名交给 plan 节点定**——本 spec 只定语义。
- 三处**已有守卫的站点一并改用 helper**（`cursor_layout_test.go`、`install_test.go`、`fence_inherit_test.go`）。理由：留着两套写法，下一个人会照抄先看到的那套；且 `install_test.go` 的双保险正是 helper 语义的手工版，收编它本身就是对 helper 语义的一次校验。
  - **例外**：`fence_inherit_test.go` 的守卫护的是 `RLIMIT_NPROC`（`CAP_SYS_RESOURCE`），**不是文件 mode 位**，探针形态不同。plan 节点须先判断它能否落进同一个 helper；**判不进就保持原样**，并在本 spec 的收尾记录里注明——不得为了「统一」而把两种不同的权限语义硬塞进一个抽象。
- skip 文案统一形态：说明**是哪一个前提没成立**、以及**探针观察到了什么**（写成功/读成功），不写「因为是 root」——那是推断，不是观察。

## 测试决定（接缝清单）

**唯一接缝：helper 自己的决策函数。**

helper 的行为有两个分支（限制生效 → 继续；限制失效 → 还原并跳过），而**在同一台机器上无法同时走到两条**（非 root 机器上永远走第一条）。所以决策必须与探针分离：探针结果作为输入，决策是纯函数。测试注入两种探针结果，断言两条分支各自的产出（是否跳过、是否还原）。

这一条接缝同时罩住本卡最危险的失败模式：**探针本身因无关原因失败 → 静默跳过 → 假绿**。它比今天的假红更坏——假红至少会被看见。

其余四处调用点的改动不新增断言：它们的既有断言就是回归网。**但要先量一次这张网罩住什么**——按 `regression-net-guards-semantics-not-characters` 的纪律，改造前在非 root 机器上确认四条是绿的，改造后仍绿；并做一次变异（把 helper 的探针强制判为「限制失效」）确认四条**转为 skip 而非仍然绿**——否则说明它们根本没跑到断言。

## 定级

- **跨几个子系统的契约面**：改动落在 5 个领域的**测试代码**（`d_transport_channel` ×2 文件、配置、`d_executor`、`d_runtime_maintenance`、`d_execution_host`），但**生产代码零修改、无任何生产契约面变动**。新 helper 是测试脚手架，不进生产二进制。
- **动不动契约层**：否。无跨仓/跨进程 wire 契约。

→ **L2**。

**这个判决的薄弱处，明写在这里**：按字面读「跨子系统」，新 helper 确实成为 5 个领域测试代码共同依赖的一个面。判 L2 的理由是**契约面判据针对生产契约**，且本改动是一处新增小工具 + 四处同形态机械替换，没有需要契约先行去消解的跨子系统设计分歧。**翻盘条件**：若 plan 阶段发现 helper 为了同时容纳 `fence_inherit_test.go` 的 `RLIMIT` 语义而需要一个多形态抽象，那就是真的出现了跨子系统接口分歧——按跨流迁移带着已产出的东西迁到 L3，不重建卡。
