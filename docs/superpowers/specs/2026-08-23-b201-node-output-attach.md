# B201：产文档节点的产出物自动挂卡

> 状态：**已批准（2026-08-23，用户）** · **第二版**（方案从「声明 glob 后匹配」改为
> 「预先约定路径」，修订原因见「修订记」）· 级别 **L2** · 档位不适用

## 修订记（2026-08-23）

第一版的采纳方案是：节点声明产出物的 **glob**，runner 拿本轮改动文件去匹配，
唯一命中就挂。用户否掉了它，理由是「plan、spec 太多了，几乎不可能命中」。

核查后这个质疑成立，而且比「太多」更准确——**问题不在候选文件多，在执行者对产出物
路径的自由度大**。仓库实况：

```
docs/superpowers/plans/2026-08-23-b205-implementation.md
docs/superpowers/plans/2026-08-23-b202-pty-test-root.md
docs/superpowers/plans/2026-08-23-card-creation-project-branch-batch.md   ← 连卡号都没有
```

命名没有任何可依赖的规律。一个能写出第三种文件名的执行者，同样可能一轮里碰两份
`plans/*.md`（写新的、顺手更正旧的），也可能写到 glob 之外。第一版那句「显式声明的
成本只有一行 JSON」是在自我安慰：**声明的是模式，命中的是运气。**

用户的提法把它从「识别」改成「约定」——派发前就把产出物的确切路径定下来告诉执行者，
回合结束按那个路径挂。本版采纳它。glob 方案降为弃选 C。

## 问题陈述

产文档的派发节点（plan、contract、breakdown）每一轮**必然**以 `needs_human` 收尾，
即使这一轮完全成功。三方约束互相锁死：

1. 执行者按纪律**不能调 handoff CLI**（`internal/discipline/builtin/single-context.md`），
   所以它挂不上自己产出的文档；
2. 下一列的 gate **要那个附件**（`进 "implement" 需要 plan 附件（当前没有）`）；
3. `NodeStep.RunOnce` 在裁决落账后**直接路由**，中间没有任何环节去挂附件。

于是路由必拒 → 转等人。2026-08-23 实测四次（B190 plan、B196 plan、B192 contract、
B202 的 plan 轮两个 task），每次都是「裁决 pass=true，路由失败转等人」。

代价不只是多一步手工操作：

- **看板上出现假红旗**。一轮干得完全正确的节点被标成「需要你」，与真正出事的卡混在
  同一个筛选里——「需要你」这个信号被稀释了。
- **协调者要自己去找产出物在哪**。报文只说「需要 plan 附件（当前没有）」，不说文档写在
  哪儿。今天靠人去 diff 里翻。
- **它把「节点跑通了」和「卡能往前走」永久解耦**，于是流水线上每一个产文档节点都是
  一个必停的人工闸——而这些闸没有任何裁决价值。

## 现状事实（本轮工作树读数，交 plan 复核）

| 事实 | 出处 |
|---|---|
| 裁决落账后直接路由，中间无挂附件环节 | `internal/ledgerstep/node.go#NodeStep.RunOnce` |
| 路由失败一律转等人（刻意，不硬失败） | 同上，`#NodeStep.haltForHuman` |
| runner 收口时手上有 `target` 与 `taskID` | `internal/ledgerstep/node.go`（`Dispatch` 返回值、`Await` 入参） |

## 方案

### 采纳：节点声明产出物路径，派发时告知执行者，回合结束按约定路径挂

1. **节点定义新增产出声明**，与既有的 gate 对称——gate 说「进这一列要什么」，
   produces 说「这一列产出什么、写到哪」：

   ```json
   {
     "name": "plan",
     "produces": { "kind": "plan", "path": "docs/superpowers/plans/{{CARD_LOWER}}-plan.md" }
   }
   ```

2. **派发时渲染成确定路径并注入 prompt**：执行者收到的是「本节点的产出物写到
   `docs/superpowers/plans/b203-plan.md`，不要另起文件名」，而不是一个模式。
3. **回合裁决 pass 后，runner 直接按那条约定路径挂附件**——不匹配、不扫描、不猜。
4. **只做存在性校验**：确认该路径出现在本轮改动里。不存在 → 不挂、走今天的转等人路径，
   但报文必须写清**要求写到哪**与**本轮实际改了哪些文件**。今天的报文只说「缺 plan
   附件」，等于让人去 diff 里翻。

**这个方案与 glob 方案的差别不是精度，是性质**：glob 是在事后识别执行者的自由发挥，
约定路径是在事前取消这份自由。识别可能失败，约定不会。

### 路径模板的占位符与推荐写法

可用占位符：`{{CARD}}`（卡号原样，如 `B203`）、`{{CARD_LOWER}}`（小写，如 `b203`）、
`{{NODE}}`（节点名，如 `plan`）、`{{DATE}}`（派发当日）。

**推荐缺省不带 `{{DATE}}`**，理由是路径要充当「同一节点产出物的稳定标识」：带日期时
跨天重跑会渲染出第二个路径，旧文件成孤儿、附件指向新的那份，两份都在仓库里而只有一份
被引用。不带日期时，重跑就是同一份文档的新版本，git 记录历史，且 `AttachFile` 同 path
幂等，卡上永远只有一条。

**但要不要带日期是配置，不是代码**——`{{DATE}}` 照样提供，工作流定义的作者可以选。
本 spec 只给推荐与理由，不替仓库的命名惯例做决定。

### 弃选 A：开一条窄通道让执行者自己挂

即豁免「不许调 handoff CLI」，允许执行者调 `card update --attach`。

弃因两条，都是硬的（第一版这里写的是「纪律边界不属本卡范围」，那是回避，本版重写）：

1. **产出物的形态归工作流定义所有，不归执行者。** 门用附件验产出物存在；让被考核者
   自己提供考核材料，门就失去独立性。更要紧的是自动化方向本身要求声明式——同一个
   plan 节点，A 执行者挂 `plan:docs/x.md`、B 执行者挂 `spec:notes/y.md`，规则引擎就
   没法在上面建任何判据。本版把这条原则推得更彻底：**不只 kind 归定义所有，路径也是。**
2. **远程执行者根本够不到这本账。** 卡账本是协调者机器上的本地库（`cmd/ledgercli.go`
   直接开库，缺省 `~/.handoff/ledger.db`）；执行机经 relay 隧道接入，没有直连。执行者
   在那边敲 `handoff card update`，开的是**它自己那台机器的**账本——要么空库、要么
   「账本未启用」，写进去这边一个字也看不见。要让它写对，得给每台执行机配
   `ledger.dsn` 指向中心库加一份鉴权，那是一期账本域「中心库」那半步（B156.1），
   不是一个 CLI 白名单能了的。

与此相关但不冲突的一条：**执行者往卡 timeline 写 note 的窄通道**已经立案在
`docs/roadmap.md`（「来自 B207 spec 的划界」节）。那条是**写自己的账**——事实陈述、
不改变卡的位置、可被 diff 证伪；与本卡的**挂附件**（门的输入）性质不同，两者放不放开
可以分别决定。本卡不预判那条。

### 弃选 B：gate 放行，改由后续节点自己找文档

弃因：gate 存在的理由就是「防漏靠结构不靠记忆」。为了绕开一个必停的闸而拆掉闸，
是把结构性保证换成约定俗成。

### 弃选 C：节点声明 glob，runner 拿本轮改动去匹配（第一版的采纳方案）

弃因见「修订记」：命中率押在执行者的命名自由度上，而实况证明那份自由度极大
（有产出物的文件名连卡号都没有）。附带两个次生问题：多命中要转等人，等于把想省的
人工闸又装回来；而每轮命中不同文件名时，`AttachFile` 的 path 幂等救不了，卡上会堆出
多条同 kind 的附件，下游读哪条无定义。

### 弃选 D：runner 用启发式猜（本轮新增的唯一 `.md` 就是产出物）

弃因：无声明的猜测在「执行者顺手改了别的文档」时会挂错东西，而挂错比不挂更坏——
门会放行，下一个节点拿到一份不相干的文件。

## 用户故事

1. 作为协调者，plan 节点跑成功后，卡应当自己进 implement 列，而不是每次都停在
   「需要你」等我做一次机械的挂载。
2. 作为协调者，看板上的「需要你」应当只包含真正需要我判断的卡——一轮完全成功的
   节点不该出现在那里。
3. 作为执行者，我应当在开工时就知道产出物该写到哪个路径，而不是自己发明一个文件名
   再指望协调者找得到。
4. 作为协调者，产出物确实没写到约定位置时，报文要告诉我**要求写到哪**和**本轮实际
   改了什么**，而不是只说「缺 plan 附件」。
5. 作为工作流的作者，我给一列加 gate 时应当能在同一个地方声明它产出什么、写到哪，
   三者写在一起才不会各改各的。

## 实现决定

1. **`produces` 是可选字段**。没声明的节点行为一字不变（今天所有节点都没声明），
   老工作流定义不必重发。
2. **路径注入不受 `CarryCardContext` 开关管**。产出物路径是本节点的法定要求，不是
   「卡的上下文」；`carry_card_context=false` 的节点同样要收到它。落点与 `buildPrompt`
   的既有段落并列，不塞进那一段。
3. **挂载失败只告警不中断**，与既有的「清等人标记失败只告警」同款理由：裁决已落账，
   为一次收尾动作失败把整轮判成错误，会让人看不出发生了什么。挂载失败后照常尝试
   路由——门会拒，于是自然退回今天的行为。
4. **挂载动作的 actor 是节点自己**（与落裁决、清等人标记同一个 actor），事件流里能看出
   这个附件是节点挂的还是人挂的。
5. **存在性校验只认本轮改动**，不扫全仓——否则一份历史同名文档会让校验假绿通过。
6. **重跑覆盖同一路径是预期行为**，不加轮次后缀：同一节点的产出物就是同一份文档的
   新版本，历史归 git。`AttachFile` 的 path 幂等使卡上不会堆条目。

## 测试决定（接缝清单）

最高可测缝是 **`NodeStep.RunOnce` 的 Outcome 与账本副作用**——挂载发生在它内部，
且它已有完整夹具（`node_test.go` 里 Dispatch/Await 都是可替换的缝），不需要起 agentd、
不需要真派发。第二个缝是 `buildPrompt` 的产出（纯函数，验路径注没注进去）。

必须覆盖：

1. 声明了 produces 且约定路径在本轮改动里 → 附件已挂、卡**进了下一列**、Action 是 pass
   （这条是本卡的核心行为反转，今天必然是 needs_human）；
2. 声明了 produces 但约定路径不在本轮改动里 → 不挂、转等人、**报文同时含要求路径与
   本轮实际改动清单**；
3. **未声明 produces → 行为与今天逐字一致**（老定义不回归）；
4. 挂载本身报错 → 只告警、仍尝试路由（不把成功的一轮判成 error）；
5. **路径模板渲染**：`{{CARD}}` / `{{CARD_LOWER}}` / `{{NODE}}` / `{{DATE}}` 各自渲染正确；
6. **路径已注入 prompt**，且 `carry_card_context=false` 时同样注入；
7. **重跑同路径挂第二次幂等**：卡上仍只有一条该 kind 的附件。

第 3 条是防回归的主网：本卡改的是一条所有节点都要走的公共路径。

## Out of Scope

- **附件对下一个节点的工作树是否可达**。挂上的是路径，下一个节点的执行者能不能读到
  那个文件，取决于它有没有在卡基线上——那是 **B205** 的范围（正在 review），本卡不碰。
  两者叠加才是完整链路：B201 让附件挂得上，B205 让附件读得到。
- **豁免执行者调 handoff CLI**（见弃选 A）——本期不做，已在 roadmap 立案（归工作流
  纪律块重构），且它的前提是中心库可达。
- **产出物的内容校验**（挂上的 plan 是不是一份合格的 plan，或执行者往约定路径里写了
  别的东西）。约定路径只能保证「文件在该在的地方」，保证不了内容——那是 review 节点
  的活。**永不做**（在本卡范围内）。
- **补挂历史卡的缺失附件**。本卡只改往后的行为。
- **一个节点产出多份文档**（如 contract 节点同时产契约文档与目标图 diff）。本期单
  kind 单路径；真有需要时 `produces` 扩成数组是向后兼容的改动。落 roadmap。
