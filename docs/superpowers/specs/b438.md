## 问题陈述

relay 形态的 target（`config.Target.Relay` 非空）今天所有字节都经 relay 服务器拼接（现状读数：`internal/relay/dialer.go` `ensureTunnel` → WSS CONNECT → relay 1:1 splice 到 executor 的 yamux session 流；服务端 `handoff-server internal/relay/server.go:243-336` 逐字节计量计费）。后果：延迟 = 两段公网 RTT，吞吐受 relay 限速档，流量计入用户配额。

用户要的是：**配了直连地址（addr）的 target 照旧直连不动；relay 形态的 target 能打洞就点对点，打不通才走 relay。** 移动端（`internal/mobilecore/core.go:51-72` 同样经 `relay.NewDialer`）同策略。

## 方案

**甲（采纳）：relay 先通、后台打洞升级、新流优先走直连、直连断了回落 relay。**

1. relay 形态的 Dialer 照今天的样子先建 relay 隧道（首个请求不因打洞多等一毫秒）。
2. relay 隧道建好后，后台经**同一个 relay 再开一条普通 CONNECT 会话**作信令通道：先跑现有 E2E（token PSK，`internal/relay/e2e.go`），在密文内交换 ICE 凭据与候选（不 trickle，收集完一次交换），两端各跑 pion/ice（coordinator 为 controlling）。
3. ICE 连通后，在 ICE 连接上叠可靠有序流（pion/sctp 单流），再在其上**重跑同一套 E2E**，然后是同一套 app-yamux；executor 侧把它当作又一个会话、交给同一个 HTTP handler（与 relay 会话等价）。
4. Dialer 此后为**新的** app 流优先选直连会话；relay 隧道保留作兜底（空闲时只剩 yamux keepalive）。
5. 直连会话死亡（ICE failed/disconnected 或 yamux keepalive 超时）→ 新流立即回落 relay；后台按退避重试打洞。打洞失败同样按退避重试，不刷日志。

关键语义（消除承重歧义）：
- 「能打洞就打洞」指**稳态**走直连，不指首包等打洞——等打洞会让每次冷启动多数秒，且打不通时白等。这是采纳甲的核心理由。
- 切换只影响**新开的流**；已在 relay 上的流跑完为止，不迁移。直连死亡时在其上的在途流会断——与今天 relay 断线时的行为一致，由上层既有重试吸收。
- 端点候选**运行时经 relay 交换，不入库**：候选与 ICE 凭据每次尝试都变（srflx 随 NAT 映射漂移），入共享设备表（B439 `devices.attrs`）只会存过期数据并把全队网络拓扑写进共享账本；relay 本来就是两端都已连上的会合点。故本卡**不改账本 schema、不写 devices.attrs**。
- relay 服务端**零改动**：信令走的是一条普通 CONNECT 会话里的 E2E 密文，服务端只看见字节。生产 relay.chanliu.net 不需要任何部署。
- 安全：直连路径上跑的是与 relay 路径相同的 E2E（同 token PSK、同 account/node 绑定），ICE 被劫持或连错对端都过不了握手；ICE 凭据只在 E2E 内传。

弃选：
- **乙：先打洞，打不通再 relay**（字面顺序）。冷启动多等 ICE 收集+连通检查（典型 1–5 s，失败时到超时），对 CLI 一次性请求尤其伤。
- **丙：pion/webrtc 整套 DataChannel**。多一层 DTLS（我们已有 E2E）、依赖体量大一倍；我们只需要 ICE + 一条可靠流。
- **丁：KCP / QUIC 作可靠层**。非 pion 生态（另一套 UDP 栈与调参）；QUIC 还要 TLS 证书形态与 E2E 重复。sctp 与 ice 同属 pion，移动端已有先例（WebRTC 移动栈）。
- **戊：候选进设备表**。见上「不入库」。
- **己：relay 服务端加 STUN / 信令帧**。要改另一仓并部署生产，且信令根本不需要服务端理解。STUN 自托管列入 roadmap。

## 落位三问

① **读写谁的权威数据**：无持久权威数据。打洞状态（当前路径、候选、退避）是 Dialer/Listener 进程内的运行时状态，归**传输层**；NAT 穿透本身（ICE 代理、可靠流、信令编解码）有独立责任且有三个消费者（桌面 Dialer、Listener、经 Dialer 的移动端），按第一条、第五条成**新子系统 p2p**，不认识 relay 控制帧。配置项归 config。
② **谁消费**：p2p 由 relay 包的 Dialer/Listener 在同进程内调用（导出符号，relay → p2p 单向依赖）；mobilecore 只经 relay.Dialer 间接用，不直接 import p2p。新增跨进程契约只有一条：coordinator ↔ listener 的**打洞信令子协议**（在 E2E 会话内、以版本化魔数开头），由 plan「需冻结的外部承诺」节冻结（第四条）。relay 服务端 wire 不变。
③ **同步还是异步**：建 relay 隧道保持同步（调用方要立即可用）；打洞升级**异步**、后台进行（第十二条：调用方不等它的结果，失败只影响后续流的路径选择，可接受「稍后才变快」）。

## 目标架构与接缝语义

- **p2p（新子系统）**：职责 = 给定一条已认证、可靠的信令连接和角色（发起/应答）与 ICE 配置，产出一条经直连路径的可靠有序 `net.Conn`，或在有界时间内返回失败原因。它拥有 ICE 代理、候选收集（host + STUN srflx；不做 TURN——兜底就是 relay）、可靠流层、信令消息编解码。它**不认识** relay 控制帧、E2E、yamux、HTTP；不读配置文件（配置由调用方传入）。
- **relay（既有）**：编排者。Dialer 持「relay 会话 + 可选直连会话」两条，按「直连活着就用直连」选新流的路；拥有升级/回落/退避状态机。Listener 在 E2E 后的会话模式判别（现状 `listener.go` 按魔数分流 preview-raw 与 app）里加一种「打洞信令」模式：应答 ICE，成功后把直连流交给与 relay 会话相同的会话服务路径（E2E → app-yamux → 同一 handler）。依赖方向 relay → p2p，不反向。
- **config（既有）**：新增顶层 `p2p:` 配置块；relay 与 targetclient 不读文件，由组装点传入。
- **组装点**：`cmd/agentd.go`（Listener 与 Pool 的构造）、`internal/targetclient`（CLI 与池的 Dialer 构造）、`internal/mobilecore`（移动端 Dialer 构造，用内置缺省，无配置文件）。
- **路径状态的可见性**：本期只经日志可见（见 S1–S3 文案）；控制台/`handoff machines` 显示通道列归 roadmap。
- **信令子协议**：E2E 会话内以新的版本化魔数开头（与 preview-raw 魔数等长以复用现有判别）；一问一答交换 ICE ufrag/pwd/候选列表；未来版本不认识即关会话，发起方视为「对端不支持」。精确帧形状由 plan 冻结。

## 实现决定

- 用户可见配置（顶层，双端同一块）：

  ```yaml
  p2p:
    enabled: true          # 缺省 true；false = 只走 relay，且 listener 拒绝应答打洞
    stun:                  # 缺省内置列表；显式给空列表 = 只用 host 候选（局域网/IPv6 直连仍可成）
      - stun:stun.miwifi.com:3478
      - stun:stun.cloudflare.com:3478
      - stun:stun.l.google.com:19302
  ```

  缺省 STUN 选国内外各有可达者（国内网络对 Google 不可靠）。**缺省列表是 config 的缺省值**（与其它配置缺省同处定义），p2p/relay 代码里不写死任何 STUN 地址；移动端无配置文件，取同一份 config 缺省值。`p2p.stun` 显式设为空列表 = 只在 host 候选上尝试（局域网 / 同网段 / IPv6 直达），**不向外发任何 STUN 请求**。用公网 STUN 会向 STUN 运营方暴露本机出口 IP——PRIVACY.md 同批补一句，并说明可以 `p2p.stun` 换成自建。
- **代理语义**（协调会话补充，2026-10-19）：handoff 的出网代理（`proxy` 配置，如 socks5）只承载 TCP（relay 的 WSS 照旧经代理）；STUN 与 ICE 是 UDP，**不经代理，从本机出口直接发出**。因此配了代理的环境下打洞会绕过代理、向 STUN 运营方与对端暴露本机公网出口。需要全程走代理的用户应设 `p2p.enabled: false`。spec 与 PRIVACY.md 都写明这一点。可观察结果：**配了 proxy 且 p2p 开着时，进程启动打一次 INFO**（不是 WARN）`p2p 打洞流量不经代理，直接从本机出口发出；需全程走代理请设 p2p.enabled: false`（agentd 与 CLI 共用同一判据，CLI 只在实际构造 relay 形态 Dialer 时打）。
- 日志文案（用户可见，INFO）：`p2p 直连已建立`、`p2p 打洞失败，继续走 relay`、`p2p 直连已断开，回落 relay`、`p2p 对端不支持打洞，继续走 relay`。
- 只有 relay 形态走打洞；直连形态 target 的构造路径不碰 p2p（S4）。
- 不做 TURN、不做多路径并发、不迁移在途流。
- 资源边界：listener 同时应答的打洞会话设上限（防止被一个 coordinator 刷爆 UDP 端口），具体数值归 plan。
- 计费含义（知会）：直连后的流量不经 relay、不计入 relay 配额——正是本卡目标。配额耗尽时 CONNECT 被拒，信令开不了，不会新建直连；已建立的直连不受 relay 配额约束。

## 测试决定

- **竖切（S1/S2/S3）**：relay 包内，进程内假 relay（splice 两端 WS）+ pion vnet 两个 NAT 路由器 + 一台 vnet STUN，真实 Dialer 与 Listener（真 HTTP handler）跑：断言升级后新流走直连、relay 计数不再增长；对称 NAT 断言放弃时限与始终可用；中途断链断言回落。vnet 由 p2p 的配置入口注入（生产用真网络），这是本卡唯一的测试缝。
- **核心方法**：信令编解码（表驱动，含未知版本/畸形）；Dialer 路径选择与退避状态机；Listener 模式判别（新魔数 / preview-raw / app 三分）。
- **S5**：用现有不认识新魔数的 serveSession 行为作「旧 listener」；`p2p.enabled:false` 双向。
- **S6**：错 token 对端的直连握手失败；日志里不出现 ufrag/pwd。
- **真机（桌面）**：linux-01 上用 netns 造「公网」+ 两个 NAT（MASQUERADE 端点无关 / `--random-fully` 对称），公网侧跑隔离 relay 实例（handoff-server 本仓构建，连 linux-01 测试库）与 STUN（pion 自带 turn/stun 示例或 coturn 一次性），两个 NAT 后各一隔离 agentd；完全不碰在役 agentd、生产 relay、共享账本；用完拆 netns、DROP 测试库并注销账号。
- **移动端**：mobilecore 竖切；gomobile bind 双平台产物构建；Android 模拟器上取接口枚举证据；真手机与运营商 NAT 标未验。

## Out of Scope

- **永不做**：依赖 Tailscale / DERP / tailcat；候选入共享账本；直连形态 target 走打洞。
- **本期不做、后续要做**（落 `docs/roadmap.md`）：
  - relay 服务端自托管 STUN（替代公网 STUN，消除隐私暴露）。
  - 控制台 / `handoff machines` 显示每台机器当前通道（直连 / 打洞 / relay）。
  - 在途流跨路径迁移（直连死亡时不断流）。
  - TURN 或多 relay 区域选择。
  - 真手机运营商 NAT 下的打洞成功率实测（B438.2 标未验的那部分）。
