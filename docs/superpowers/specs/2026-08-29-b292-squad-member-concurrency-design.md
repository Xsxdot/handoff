# B292：小队并发按成员载体设置，载体上限跨小队封顶，空位协调者优先

- **卡**：B292
- **级别与档位**：**L3 轻档**。改已冻结的编制契约（小队成员形状、政策位计数从「按队一条」改为「按（小队, 载体）一条」、清队遇协调者满员不得中止整轮），跨 `d_scheduling` / `d_gateway` / `d_cli` / `d_web`。规则仍只在编制域收口，其余是投影；单子系统工作量未过重档线，契约冻结 + 拆解后一轮实现。
- **状态**：已批准（用户，2026-08-29）
- **基线**：`acc/b156.2-156.3`
- **形态权威**：`prototypes/b292-squad-concurrency/`（fork 自 `prototypes/base/`，`file://` 直开）。编制页小队卡/弹窗的结构以原型为准；本 spec 只写决策，不转述像素。
- **台账**：`docs/superpowers/ledgers/2026-08-29-b292-spec-ledger.md`

## 问题陈述

B156.3 把小队政策位做成**队级总并发**：`Squad.Members` 是载体名列表，另有一条 `MaxConcurrency` 按队计数；准入 = 小队计数 < 队上限 **且** 载体计数 < 载体上限（现状读数：`internal/scheduling/scheduling.go#Squad` 70–75 行、`#acquire` 385–399 行；契约 `docs/superpowers/specs/b156.3-contract.md` §4.2 条 1–2、§15 澄清 3）。控制台小队编辑是一个总数字 + 成员勾选（现状读数：`web/src/app/settings/SchedulingPage.tsx` 小队弹窗「并发上限」；原型 base 同款）。

这和编制的真实用法不符：

- 小队是部门，成员载体是同等能力的员工。**领任务的是小队**，不会预先绑死某一个载体。
- 真正消耗的名额在载体上。政策位是「这个部门能用这个员工几个」，不是「这个部门一共几个」。
- 载体不是 CLI 名，是 **CLI + 这一次的模型配置**。opencode 模型列空（走 CLI 默认，例如 glm-5.3）和模型列填 `glm-5.3-flash` 是两个载体、两套物理上限。
- 某个载体空出一位时，先给排队里**含这个载体、且该成员政策位还没用满**的协调者小队；没有再给执行者小队。不抢已经在跑的任务。
- 小队不会死等某一个员工：这个载体没位就用另一个成员；都没位才排队，谁先空出来用谁。协调者在等载体 A，不能把载体 B 上还能跑的执行者堵住。

现状清队在协调者拉起失败后直接结束整轮（`internal/agentd/scheddrain.go#drainQueuesOnce` 104–107 行），会变成「全局让路」——这是要改掉的行为，不是要保留的语义。

## 方案

政策位从「按队一条」改为「按（小队, 载体）一条」。载体物理位不变：同一载体跨小队全局封顶。准入改成：小队存在**至少一个**成员，同时满足该成员政策位和该载体物理位。排队只发生在全部成员都没名额时。空位分配时协调者小队优先，且只对「能用上这次空位所属载体」的请求优先，不中止其他载体上的执行者。

载体身份沿用已有字段 `Carrier.Model`（空 = 派发不覆盖模型，执行者走 CLI 默认），本卡把它从「一个可空字符串」钉成编制身份的一部分：同 CLI、不同模型（含空 vs 有值）是不同载体，禁止合成一个并发池。

弃选：

- **保留队级总并发再叠加成员上限**：否。用户明确不是总并发；两套政策位会让「部门一共几个」和「这个员工几个」互相打架。
- **协调者在排队就让所有执行者停**（现状清队失败即 return）：否。会让等载体 A 的协调者饿死载体 B 上的执行者。
- **同 CLI 合成一个物理池**：否。模型列空和 `glm-5.3-flash` 是两个载体。
- **把存量小队的队级数字抄到每个成员上**：否。旧语义是队总帽，抄过去会放大并发。存量该字段丢弃，成员政策位未填视为不限。
- **本期实体化账户池**（同 HOME 的多个载体共享真实额度）：否。B156.3 已记为已知缝；调度层仍按各载体自己的物理上限计数。

## 用户故事

1. 作为协调者，我在设置·自动化登记两个 opencode 载体：一个模型列空（CLI 默认），一个模型列填 `glm-5.3-flash`。它们各有物理并发上限，卡片上能看出「CLI 默认」和钉死的模型。
2. 作为协调者，我建/编小队时给每个勾选的成员填政策并发（留空 = 不限），没有队级总并发输入。小队卡片上每个成员 chip 带着该成员的政策位。
3. 作为协调者，我把「默认」和「flash」收进同一执行者小队。部门把谁收成成员，谁就在这份工作上同等可用：一个没位就用另一个，不会死等。
4. 作为协调者，载体空出一位时，若有含该载体且政策位还有空的协调者小队在排队，这一位先给协调者；否则给执行者小队。已经在跑的任务不被抢走。
5. 作为协调者，协调者小队在等载体 A 时，载体 B 上还有位的执行者小队照常领任务。
6. 作为协调者，我用 `handoff squad` 登记小队时，成员和政策位成对提交；小队级 `--max-concurrency` 不再存在。

## 契约语义与接缝

规则归编制域（架构法第五条），本卡修订 B156.3 契约 §4.2 / §15 澄清 3 的政策位半边。不新增依赖方向。精确签名与 registry 键字符串归 contract 节点。

**准入（替换「小队有位且载体有位」的队级读法）**

1. 政策位：对选定成员，该（小队, 载体）占用 < 该成员政策上限。上限 0 / 缺席 = 不限。
2. 物理位：该载体占用 < 该载体上限（跨小队全局）。上限 0 / 缺席 = 不限。
3. 一次领任务选**一个**成员同时满足 1 和 2；小队存在这样一个成员即可准入。全部成员都不满足才 `ErrNoSlot`（转排队）。小队内没有健康载体仍是 `ErrNoHealthy`（配置问题），两种失败不得混用。
4. 多个成员同时满足时，登记顺序只作决胜，不构成等待绑定——不得因为更靠前的成员满员就卡住整个小队。
5. 成员政策上限之和允许大于载体物理上限；有效名额取两者较紧的。例：载体物理 5，A 队该成员 4，B 队该成员 3，两队同时跑最多仍是 5。
6. 不抢占在跑任务。

**空位与协调者优先（替换「清队失败即停整轮」）**

7. 领任务是小队领；占用发生在绑定到具体载体的那一刻。
8. 某个载体出现可占用名额时：先看拉起队列里，小队含该载体且该成员政策位和载体物理位都还有空的协调者请求；有则给协调者。没有再看点火队列里同样能用该载体的执行者请求。同角色之间沿用就绪度 → 卡优先级 → 入队序。
9. 协调者本次对任何成员都 `ErrNoSlot` 时：该请求回队，**本轮清队继续**，不得中止其他载体上的执行者清队。
10. `QueueKinds` 拉起先于点火仍是同角色队列之间的顺序；它不能再被实现成「协调者失败就停掉执行者」。

**载体身份**

11. 载体仍是一等实体：机器 × CLI × HOME × 模型 × 凭据来源 × 物理并发。模型列空 = 派发不写模型覆盖，执行者用该 CLI 当时的默认模型；模型列有值 = 该载体固定用这个模型。空与显式写成当前默认值（例如 `glm-5.3`）是两个载体：空会跟着 CLI 默认变，钉死的不会。
12. 小队成员引用具体载体，不是 CLI 名。同一小队可以同时包含「默认模型」和「flash」；收成成员即视为这份工作上同等可用。

**登记面**

13. 小队不再有队级总并发。成员从「载体名列表」改为「载体名 + 该成员政策位」。空队仍合法（先建队再补成员）。
14. 存量小队的队级总并发丢弃，不翻译到各成员。
15. 政策位计数按（小队, 载体）；物理位计数仍按载体。这是对 §15 澄清 3「只有 squad/<队> 与 carrier/<载体> 两类」的修订：**政策位键换成成员粒度，不是在队级键之外再加一类。** `Release(小队, 载体)` 归还的就是这一对。

**接缝（每条符号 + 调用方）**

- 缝 1：`scheduling.Service.Admit` / `scheduling.Service.LaunchAdmit`（现状 `internal/scheduling/scheduling.go` 191–214 行，签名归 contract 复核）。调用方：`internal/agentd/scheddispatch.go` 小队节点点火（68 行）、`internal/agentd/scheddrain.go` 协调者拉起（181、219 行）。钉：任一成员可领、两级是成员政策位 × 载体物理位、满员才 `ErrNoSlot`。
- 缝 2：`Server.drainQueuesOnce`（现状 `internal/agentd/scheddrain.go` 85 行）。调用方：`Server.runAutomationPass`（同文件 75–81 行）。钉：协调者 `ErrNoSlot` 回队后本轮继续；不得因协调者等载体 A 而停掉载体 B 上的执行者。
- 缝 3（边界型）：小队 PUT 的成员+政策位 wire，解析入口 `handleSquadPut`（现状 `internal/agentd/schedapi.go` 122–157 行）。调用方：控制台编制页、`handoff squad create` / `set`。钉：不再接受队级总并发；成员与政策位成对；金样本双侧刷新。

假缝：`admitInto` / `acquire` 内部循环不占缝名额，从缝 1 走过去。成员行纯展示 helper 不占缝。

## 实现决定

1. 设置·自动化：载体卡继续展示模型（空 = 「CLI 默认」）和物理并发。小队卡去掉队级并发数字；成员 chip 带该成员政策位。小队弹窗每个载体一行（勾选 + 政策并发输入），去掉队级并发上限输入。结构以原型为准。
2. `handoff squad create` / `set`：小队级 `--max-concurrency` 删除。成员提交必须能带上该成员政策位（0 / 缺席 = 不限）。`handoff squad list` 小队行展示各成员政策位，不再展示队级总帽。
3. 清队：协调者拉起得到 `ErrNoSlot` 时回队并继续本轮；其他错误的处置不在本卡放宽。
4. 一次性覆盖（`--target` / `--executor` / `--model`）语义不变，仍是对命中载体字段的覆盖；载体模型列为空时，不覆盖即走 CLI 默认。

## 测试决定（接缝清单）

接缝越少越好，三条都是生产调用面：

1. 缝 1：并发准入。两载体物理位各有上限、小队成员政策位各自设置；成功占用落在成员键和载体键上，不再出现队级总帽键。变异：去掉成员政策位执法则超发。调用方路径用真实 `Admit` / `LaunchAdmit`，不测未导出 helper。
2. 缝 2：清队。拉起队列里一个协调者对所有成员 `ErrNoSlot`，点火队列里另一个执行者能用别的载体——本轮必须放行该执行者。现状失败即 return 必红。
3. 缝 3：登记 wire。小队 PUT 以成员+政策位为准即被接受。若请求里还带着旧的队级总并发字段，值丢弃不生效（与存量迁移一致），新 CLI / 控制台不再发送该字段。金样本钉新形状。

## Out of Scope

- **永不做**：队级总并发与成员政策位两套同时生效；抢占在跑任务；把「同 CLI」合成一个调度池。
- **本期不做、后续要做**（落 roadmap）：CLI 限额探测与账户池（同 HOME / 同凭据的多个载体共享真实额度）——B156.3 已记、本卡重申，调度层仍按载体物理上限保守计数。隔离 HOME 默认路径、改路径探测凭据、建载体后一次性唤起、运行命令复制、不健康不派发——B293。
- **本期不做**：机器发现与表单预填（B279 已推）；小队成员拖拽排序（B279 已推；本卡登记顺序只作并列有位时的决胜）；强制（机器, CLI, HOME, 模型）唯一约束（重名配置靠载体名区分，YAGNI）。
- **本期不做**：B293 的健康位从恒真改为探测结果——本卡沿用「没探测不得静默饿死」。
