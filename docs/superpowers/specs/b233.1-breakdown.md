### T1 · Ask 回程：拆 Send 兼答、落地 RespondAsk

**①契约引用**：冻结 9–15、31–33、75（幂等的原生侧）、86、92、94、95；变异「把 Ask 答案改回 Adapter.Send → 故事 2 转红」。

**②意图与为什么**：OpenCode `Send` 在有 `pendingQuestionID` 时走 `ReplyQuestion`，与 Continue 普通指令同名。这是「只给 task ID 找当前那条问题」的具体形态。拆开后，回答必须携带 `TaskID`+`TicketID`，`Send` 按会话状态处理且不得消费任意挂起 Ask。拒绝理由不得再优先吞下一条提问——那会把附属指导冒充 Ask 答案。

**③验收（行为化）**：

- `go test ./internal/executor/opencode -run 'TestSendDoesNotConsumePendingAsk' -count=1` 命中且 ok：构造挂起 question 后调 `Send`，原生 ReplyQuestion **零次**，pending 仍在；同一实例 `AskResponder.RespondAsk` 命中该 `QuestionID`。
- 原生仍挂起：`RespondAsk` 调用原生回复且不新开 Prompt 回合（可用 fake serve 计数 PromptAsync=0、ReplyQuestion=1）。
- 提问回合已结束：`RespondAsk` 核对待答 `TicketID` 后以关联答案续接（Prompt 带关联，不得当无身份 Send）。
- OpenCode 未实现 `AskResponder` 时，编排侧（T4 接线后）报能力不足，**不得** `Send`。本 ticket 先在 adapter 包内用编译断言 `var _ executor.AskResponder = (*Adapter)(nil)` 锁住「OpenCode 必须实现」。
- 拒绝理由：登记必须关联被拒的 `PermissionID`；下一条 question 事件仍创建 Ask 工单（反面：不得再走 `takeDenyGuidance` 吞问早退）。`go test ./internal/agentd -run 'TestDenyGuidanceDoesNotSwallowQuestion' -count=1` 在 T4 接线后变绿；T1 先锁 adapter 侧「Send 不是 guidance 通道」。
- 现有 `internal/executor/opencode/question_test.go` 中「Send 有 pending 则 ReplyQuestion」的**正向**断言必须退役或改锁 `RespondAsk`。留下会把新契约判红，或改测试迁就旧 Send 造成假绿。
- `go test ./internal/executor/opencode ./internal/executor -count=1` ok。
- 缺陷族入栏：见 §4 对应行。生命周期——pending 快照只读不清、成功后才清（现状注释，保持）。静默失败——Reply 失败必须保留挂起并让编排记 `delivery_failed`（T5 接）。假绿——必须有「Send 不得消费」反面断言。门禁——Ask 答案不自动扩大权限（spec；本 ticket 无授权写入）。

**④入口指针**：`internal/executor/opencode/adapter.go#Send`、`internal/executor/ask.go#AskResponder`、`internal/executor/ask.go#RespondAskReq`、`internal/executor/opencode/question.go`、`internal/executor/opencode/resume.go`（恢复后 pending 仍在则 RespondAsk 走原生回复）。有界文件集 = 上述 + 对应 `_test.go`。不改其它 harness 的 `Send`。

### T2 · 审批 client 实现、政策快照、复用加版本

**①契约引用**：冻结 34–52、56–58、63–74；client 对外只有 allow/deny/pending；Consult 不得出站；截断/失败/超时/不可用不得 allow。

**②意图与为什么**：政策与授权决定要有唯一写入者，经限定到单个 `Task.ID` 的 client 注入。Manager 不再为 OpenCode 路径实现第二套审批链，但 `Gate.Judge` 与 `Approver.Decide` 仍是服务内部步骤。复用必须钉在同一快照版本上，否则 Continue 换快照后会把旧 allow 带到新政策。

**③验收（行为化）**：

- 进程内假时钟/可注入 Judge：范围内写 → `Request` 立即 `allow`，且测试间谍观察到 **零** 次 `permission_request` 入库/Publish。
- 描述含 `TruncationMarker` → `Request` 不得返回 allow（锁现有 fail-closed）。
- Judge 失败、审批模型超时、审批模型不可用 → 不得 allow；对外 `pending` 或 `deny`（升级待外部审批的形状归实现，但不得解释成允许）。
- `Request` 不得返回 `Consult` 字面值（枚举白名单：对外三态）。
- 同一 `Task.ID` + 同一 Version + 同一 `PermFingerprint` + kind=gate + answer 严格 `allow` + `DeliveredAt` 非空 → 第二次 `Request` 复用成功，不发 `permission_request`，只入库 `permission_reuse`。
- 换 Version 后同指纹不得复用（P2 落点的反面断言；能变红）。
- 不同 `Task.ID` 不得复用。
- 网络故障/超时注入不得写成 allow。
- `Acknowledge`：formed 与 delivered 可分；delivered 与 executed 可分（三阶段各一条断言）。
- client 实例方法传入其它 task 的 NativeID/范围 → 拒绝，不写其它任务的工单。
- `StartReq.Approval == nil` 的调用方（其它 harness）不得被本实现解释成全部免审——本 ticket 用「nil client 的 adapter 不得走新路径」的编译/测试锁；行为锁在 T4/T6。
- 审批模型调用走 `executor.OneShotArgs` + `agentd.Approver`，测试断言 **没有** OpenCode session/API 被审批路径使用。
- P4 若选 (a)：`Authorize` 在 pending 时进入 Await，取消 ctx 后返回，不泄漏 waiter。
- `go test ./internal/agentd ./internal/store ./internal/permgate ./internal/executor -count=1` 相关测试 ok。
- 缺陷族：生命周期——Await 可恢复，不依赖重启前的 goroutine 栈（用 store 审批引用重挂）。静默失败——判据失败不得报 allow。门禁——client 限定单任务；检查与动作之间的 TOCTOU（复用查询与投递）接受项见 §4。序列化——client 是进程内接口，不经 HTTP；若 P2-(a) 则无新 Ticket 字段。承重安全——截断 fail-closed、超时≠allow、复用必须 DeliveredAt 非空，各有能变红的测试。

**④入口指针**：新增 `internal/agentd/approval_client.go`（名称归 plan）、`internal/agentd/approver.go#Decide`、`internal/permgate/permgate.go#Judge`、`internal/store/store.go#FindReusableGrant`、`internal/executor/approval.go#ApprovalClient`、`internal/executor/fingerprint.go#PermFingerprint`、`internal/agentd/manager.go#reuseDecision`（生产路径改为走 client 或包装 `PermFingerprint`，受预算 26/27 约束）。有界文件集 = 上述 + 测试。OpenCode 子包零 import permgate。

### T5 · 取消、重复答案、迟到答案、投递确认

**①契约引用**：冻结 75–83、51–52；Ack 三阶段与取消不得把已形成决定改写成 allow。

**②意图与为什么**：现状 `AnswerTicket` 第二次返回 `ErrNotFound`（HTTP 404），冻结要求相同答案幂等成功且不得二次原生回复。取消必须停执行、解除原生挂起、Ask 标取消/作废，但已形成的 deny/allow 不改写成 allow。迟到答案（取消/换尝试/void）必须拒绝，避免喂给新回合。

**③验收（行为化）**：

- 相同 Ask 答案第二次 `AnswerTicket`/`Reply`：成功（非 404），原生 `RespondAsk` 调用次数仍为 1。

## 4. 缺陷族对抗审查

项目清单：`docs/superpowers/specs/2026-08-21-handoff-instantiation-checklist.md` §3（五族 + 序列化边界 + 枚举白名单 + webview 候选）。顶部**没有**「基线版本：charter@\<commit\>」——对不上基线标注，本拆解按项目清单加严，并并入基线追加「承重安全属性」。清单债不在本卡改实例化协议。

### 4.1 通用五族

**生命周期 / 状态机中断**

- Ask：先落 Ticket 再 Publish。agentd 在 CreateTicket 与 AppendEvent 之间崩溃 → 有工单无事件；重放必须自愈补事件或重挂 waiter（冻结 31–32；T4 验收）。不得只靠 `Hub.WaitAnswer`。
- 审批：决定形成与原生投递分开。崩溃在 formed 未 delivered → 恢复按引用重投或失效，不宣称恰好一次（冻结 51–52、T5）。
- Await 不得堵中介循环：等待在 client/工单侧。P1 无论 (a)/(b)，permission 处理必须把 Await 放到独立 goroutine 或立即返回 pending。
- Stop/取消：停进程、void 工单、解除原生挂起。孤儿 serve 由既有 Stop/Kill/sweep 收；本卡不新资源类型。**无新孤儿类型，因为**不新增进程/工单表/临时目录种类。
- Continue 换快照：已跑回合不热更新（冻结 43）。P5 的 serve 配置重载是能力问题，失败必须暴露。

**静默失败 / 误导报错**

- Dispatch Start 失败不得返回成功 Task（既有 `errExecutorStartFailed`，T4/T6 保持）。
- `AnswerTicket` 第二次相同答案今日 404「不存在」是误导——T5 改幂等成功。
- 审批失败/超时/不可用解释成允许 = 本卡要消灭的窗口；T2 反面断言。
- 原生投影放宽 = 报「有政策」但门开得比快照宽；T3 反面断言。
- 拒绝理由吞真提问 = 用户以为问题被答了其实是 guidance；T1 退役该路径。
- `permission_reuse` 唤醒 wait = 误导成待外部审批；T4 修 isDeliverable。
- 通知失败不得删除 Ask（冻结 32）。
- 能力不足（AskResponder 缺失、禁止项无法实施、P5 serve 不重载）必须是可行动错误，禁止静默降级。

**跨平台假设**

- 本卡不新引入路径分隔、进程组或 webview 假设。工单 id 拼接是 `taskID + ":" + native`，与 OS 无关。
- OpenCode 原生权限 JSON、serve 热重载、Stop 杀进程树：沿用既有 adapter 行为。Windows 上 Remove/Kill/权限回调差异 **未验证，需真机**（§5 第 16 条）。
- **无其它新平台假设，因为**投影输出是 JSON 文件内容，测试锁的是字段取值不是 inode。

**假红 / 假绿测试**

- Ticket 0 金样本锁编码，不是行为；不得把「空壳存在」当故事 1 完成（冻结 85）。
- T1 必须退役「Send 消费 pending」的旧正向测试，否则新实现假红，或改测试迁就旧行为假绿。
- `isDeliverable` 缺省 true 会让「没列 permission_reuse」的测试假绿——T4 要显式假值断言。
- 夹具 fake serve 可以编码「投影已写入但 serve 不读」的世界——P5/范围内免审的**行为**走真机清单，机内只锁 JSON 子集与 client 调用。
- 测试锁的是调用方依赖的行为（Send 不消费 Ask、截断不 allow、reuse 要 DeliveredAt），不是投影表内部键顺序。
- 全包测试若遇沙箱 `Operation not permitted`：记原文，不归因；T6 要求无沙箱环境复跑。

**门禁绕过**

- 原生 allow 是第 0 道门，client 是第 1 道。两道必须 ⊆ 同一快照。只改 client 不改 `WriteTaskEnv` = 绕过。T3+T2 两侧都要测。
- 同一规则入口：OpenCode 原生回调（P1-(a)）与 Manager 事件（P1-(b) 或其它 harness）不得出现「一边免审一边升级」。P1 拍板后只保留 OpenCode 一条权威入口。
- `StartReq.Approval==nil` 不得全免审。
- 复用只认严格 `allow` + 已送达，deny 不可当复用键。
- TOCTOU：FindReusableGrant 与 RespondPermission 之间新政策生效——用回合绑定的 Version 缓解；窗口接受项 = 同一回合内配置热改不生效（冻结 43）。跨任务隔离由 Task.ID 限定。
- CLI `reply` 与 HTTP 同进 `Manager.RelayAnswer`，不另开绕门入口。Web 本卡不改。

### 4.2 追加设问

**序列化边界**

- 本卡默认不新增 Ticket/EventType 字段。事件类型字符串既有 `internal/proto/proto_test.go` 金样本，不复制第二份词表。
- `isDeliverable` 是事件类型穿过「是否唤醒」的投影点，必须单测（T4）。
- CLI `composeAnswer`：`--approve`→`allow`、`--deny`→`deny`/`deny: reason`，既有字面值；T6 回归，不新手搭 map。
- client 四方法是进程内接口，不是跨语言 wire。
- 若拍板 P2-(c)：`Ticket.PolicyVersion` 必须列入 proto fixture + 任何手写 JSON 投影，并区分缺席与空串——**先退回 contract**。
- 推荐：P2-(a) 避免这条链路。

**枚举新值过既有白名单**

- 不新增 EventType。`permission_reuse` 是存量生产者、消费侧缺口——补的是白名单假分支，不是新枚举。
- `ApprovalStatus` / `AckStage` 不得流入 `Ticket.Kind` 或 `isDeliverable` switch（契约 §11 C-5）。
- `gateDecision` 仍只认严格 `allow`→`once`，其余 reject（冻结 89–90，Ticket 0 已有金样本）。
- web `QUIET_EVENTS` / `PHRASES`：无新类型，预期零改。未知类型原样透出的既有纪律保持。

**承重安全属性（必须能变红）**

| 属性 | 锁在哪 |
|---|---|
| 截断不得 allow | T2 |
| 超时/不可用不得 allow | T2 |
| 复用必须同任务、同快照、同指纹、kind=gate、answer==allow、已送达 | T2 |
| client 不得扩大到其它任务 | T2 |
| nil Approval 不是全免审 | T4 |
| 迟到/void/换尝试答案拒绝 | T5 |
| 相同 Ask 答案不二次原生回复 | T5 |
| 原生 allow ⊆ 快照 | T3 |
| Ask 答案不自动扩大权限 | T1/T2：RespondAsk 不调审批放行 |

**webview / 平台表现差异（项目第六族候选）**

- 本卡不触及 Web 控制台交互与浏览器 API。**无，因为**事件词表不变、web 已把 `permission_reuse` 当静音审计，不需要逐 webview 验。
