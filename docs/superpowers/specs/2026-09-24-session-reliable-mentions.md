# 会话 @ 寻址与断线续收（r2）

> 状态：用户于 2026-09-24 批准 r2，进入 contract / Wave 0。级别：L3 重档（CLI 对外语义 + 共享账本游标）。
> 用户 2026-09-24 裁决：CLI 正文有效 `@` 与桌面一致；监听重启补收、避免重复处理；接收方式与普通 `wait` 一样，无逐条确认。r1 的 `session ack` / 一条一确认方案已弃选。

## 问题与现状

- CLI `session send` 仅把 `--mention` 写入消息的 `Mentions`；正文 `@agent:grok` 本身不寻址（现状：`cmd/session.go:499-512,558`）。桌面输入框会把正文的 `@` 提取为 `mentions`（现状：`web/src/app/rooms/SessionChat.tsx:158-168`）。真机 #19954 正文含 `@agent:grok` 但 `mentions=[]`，监听超时；#19946 带显式 mentions，监听可收到。原始结果见同日排查台账。
- `session wait` 不传 `--since` 时从启动时流尾 `MaxSeq` 开始（现状：`cmd/session.go:74-105`；冻结契约 `docs/superpowers/specs/b358-contract.md:421-423`）。监听退出期间的 @ 被越过。
- 普通 `wait` 用持久 cursor 续拉；`--follow` 在事件写出时推进 cursor，启动/重连时对账当前待办（现状：`internal/client/client.go:1459-1496,1741-1812`）。`card wait` 缺省首个可动作事件后退出，`--follow` 连续；建连时输出当前待办快照后从流尾跟随（现状：`cmd/card_wait.go:100-154,173-207`）。两者都无需逐条人工确认。

## 用户故事

1. S1：协调者通过 CLI 发言 `@agent:<名>` / `@user:<名>` / `@<卡号>`，账本 `mentions` 包含有效身份，目标监听能收到；显式 `--mention` 保持可用，去重后不广播。桌面与 CLI 用相同金样本判定 token。
2. S2：主 agent 挂 `session wait <member>`，收到一条后退出；再挂时从上次交付水位继续。挂 `--follow` 时新消息连续输出。断线或载体限额导致监听**停止**期间形成的定向积压，在重挂时补发；同一账本下换机器仍读取同一个进度。
3. S3：积压多条时先用一条摘要给出定向消息的 seq、会话、作者、正文与引用锚，再继续实时监听，避免恢复瞬间逐条唤醒风暴。重启后已成功写出的积压摘要不重复；游标写失败可见且允许重投，不静默跳过。
4. S4：正文无有效 `@`、无有效 `reply_to`、结构事件不叫醒主 agent；`@卡号` 仍由现有目标解析映射当前席位，外部身份仍逐字匹配。现有席位 keystone 路径不受影响。

## 方案与职责

- **输入编译**：CLI 与桌面从正文提取完整的统一身份/卡号 token，写入既有 `mentions` 字段；显式 `--mention` 合并去重。无法识别的 `@` 保留为正文但不寻址。账本旧消息不回填。`reply_to` 和 `collab` 的目标解析继续是唯一投递判据，不在 CLI 另造投递规则。
- **共享交付游标**：会话订阅进度按外部 member 存在共享账本，与 UI 已读游标及 `message_consumed` 分开。只有 stdout 成功写出定向唤醒或积压摘要后才单调推进；写失败不推进，进度落账失败则 Warn，下一次允许重复交付。进度不能跳过尚未输出的定向消息。相同 member 只运行一个主动监听器；并发多监听器的唯一认领不在本期承诺。
- **启动与重连**：未有交付游标时从全流起点扫描，以一条积压摘要呈现历史定向消息（旧时已人工处理的消息可能首次出现在摘要，不能冒称全是待办）。有游标时从其后扫描；无积压则阻塞等新消息。一次性模式有积压摘要就输出后退出；`--follow` 输出摘要后继续。重连与首次建连走同一对账路径。
- **实时交付**：无积压时，现有 `SessionWake` 逐条输出；一次性模式首条退出，`--follow` 保持运行。`--since` 显式设置时沿用现有排他起点，作为不读写持久进度的诊断/手工回放模式，避免探针误推进主 agent 的订阅水位。
- **交付与处理的界线**：按用户选择，与普通 `wait` 一样，把成功写到监听 stdout 视为已交付；不加 `session ack`。如果 stdout 已成功、但监听工具/模型随后因限额未执行处理，系统无法凭游标识别这一段，**不承诺补收这种已交付未处理事件**。使用方醒来仍应按会话当前状态复核。窗口内写盘失败可造成重复交付，以 seq 去重。

## 验收与 Wave 0

- Wave 0 先贯通“共享账本进度 → CLI 一次性 wait → 停监听期间入账 → 在另一台机重挂补收 → 游标不重复”，验证最重的恢复与跨机器接缝；再接 `--follow` 积压摘要和正文 @ 编译。
- 真机必须覆盖 CLI 发言到共享账本载荷、主 agent 监听 stdout、进度落账、进程重启与异机续收。反例：无寻址、无效 @、`reply_to`、seq 跳号、游标读写失败、首次无游标、历史已人工处理消息。Mock 只验证局部规则，不替代真机链。
- 日志记录 member、起点/终点 seq、积压条数、交付成功、进度写失败与原因；不记录 token 或消息正文。CLI/桌面 token 金样本与服务端目标解析共同验证。

## 兼容与流程

- 改动现有 `session wait` 无 `--since` 的起点承诺，以及新增共享游标与积压摘要线格式；实现前须在 contract 节点冻结向后兼容与 wire。显式 `--since` 保持旧手工回放行为。
- 需要 CLI、协作域与账本持久化的独立工作单元；单子系统工作量与跨机器验证超过轻档固定成本，按 L3 重档。用户批准后先做 Wave 0，再拆剩余故事。

## Out of Scope

- 不让额度已耗尽的模型凭空醒来；额度恢复、监听重新启动后补收未交付积压。
- 不承诺“stdout 已交付但载体未处理”的自动识别；这需要监听工具与模型处理回合之间的完成回执，用户本轮选择与普通 `wait` 一致的交付语义。
- 不做无寻址广播、不回写历史消息、不把 UI 已读或消费标记当交付进度。
- 不支持同一 member 多个主动监听器同时处理；后续若需要并行主 agent，另定唯一认领契约。
