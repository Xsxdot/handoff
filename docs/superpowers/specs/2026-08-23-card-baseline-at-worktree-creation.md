# 卡的基线在开工作树时定下来（B205）

**状态**：已批准（用户 2026-08-23）
**级别**：L3 · 轻档（拆解与契约冻结照做，实现归一轮）
**日期**：2026-08-23
**卡**：B205

---

## 问题陈述

派出去的执行者看得见附件路径、却读不到附件内容。2026-08-23 真机咬人两次：B179 的
plan 轮（opencode）读不到 spec 附件，把「附件不存在」反推成「我在 spec 节点」，
写了一份新 spec 并给自己判 pass；B181 同轮撞同一条，如实提问才被协调者救回。

这个症状的上游是**卡的基线（`base_branch`）在唯一能知道它的时刻写不进去**：

1. 卡在 backlog 阶段用 `card add` 建。那一刻工作树与分支都还不存在，
   `--base-branch`（`cmd/card.go:436`）有这个 flag 但无值可填。
2. `base_branch` 是**写一次**字段。全仓唯一的 SQL 写入点是建卡的 INSERT
   （`internal/ledger/cards.go:197`）；没有任何 `UPDATE cards SET base_branch`。
   `UpdateCardMeta`（`internal/ledger/cards.go:512`）只改 title/priority，
   `card update` 的 flag 只有 title/priority/attach/detach/accept
   （`cmd/card.go:449-453`）。web 建卡对话框更是明写「建卡后不可改」。
3. 实际开发流程是**领取时开工作树 + 开分支**，多张卡也可能合用一棵。
   那一刻基线才第一次有确定的值——而此刻已经没有任何写入通道。
4. 于是 `EffectiveBaseBranch`（`internal/ledger/relations.go:207`）沿父链找不到
   非空值，返回空；派发（`internal/ledgerstep/dispatch.go:169`）拿到空基线，
   回落项目主线。工作分支从 main 切，而 spec 在领取时那条分支上。

实测佐证：B178/B179/B181/B192/B202 五张卡 `base_branch` 全为空，`effective` 也
全为空；B179/B181 的 `base_commit` 都是 `31acac41`（main），与协调者当时所在
分支毫无关系。

**后果不止读不到文件。**基线同时是合并目标——`buildPrompt`
（`internal/ledgerstep/dispatch.go:275`）把它写进「本卡上下文」的「有效基线分支
（本卡的合并目标以此为准）」一行。基线错了，合并环节也会合错地方。

「建卡后不可改」这条约束本身不是错的，理由（改基线会让**已派出去的**任务与卡的
说法对不上）成立。它的毛病是把两个阶段压成了一个：**首次派发之前改基线是无害的**
——还没有任何任务按它工作。冻结点该是首次派发，不是建卡。

---

## 方案

### 选中：基线可写到首次派发为止 + 开工作树时顺手挂卡

分两层，下层是上层的前提：

**底座层 —— 让基线可写，并把冻结点挪到首次派发。**

- 新增 `Store.SetCardBaseBranch(id, branch, actor)`：卡尚未派发过任何任务时
  写入并落事件；已派发过则拒绝，错误里带上首个派发事件的分支与时间，让人知道
  为什么被拒。
- 「派发过没有」的判据取卡的 `dispatched` 事件流（`RecordDispatch` 落的
  `EvDispatched`，`internal/ledger/events.go:135`），不新增状态字段——账本的既有
  纪律是「推进状态从事件流推导」。
- 出口三个：`card update --base-branch`、`PATCH /api/cards/{id}` 加
  `base_branch` 字段（该 handler 已是「缺字段=不动该字段」的 `*string` 语义，
  `internal/agentd/ledgerapi.go:727`，形态天然吻合）、卡抽屉里可编辑。

**挂接层 —— 开工作树时一次动作搭好关系。**

- `proto.CreateWorktreeReq`（`internal/proto/projects.go:361`）加一个卡号数组。
  建树成功后，把这棵树的分支写成这批卡的基线；失败的卡逐张回报，不回滚已建好的树
  （树已经在磁盘上了，谎报没建反而更糟）。
- web 的新建工作树弹层（`web/src/app/tree/NewWorktreeDialog.tsx`）加一个卡选择器，
  默认空选。
- **同一个操作也要能作用在已存在的工作树上**：协调者的工作树未必由 handoff 建
  （本仓的 `.claude/worktrees/*` 由 Claude Code 的 harness 建，handoff 只是能
  探测到它们）。所以底层动作是「把某条分支写成某批卡的基线」，建树时顺手调它，
  已有工作树上也能调它。只做建树那一路会漏掉协调者最常走的路径。

### 弃选一：派发前校验附件可达，不可达就拒发

在下游堵。就算拒发做了，基线仍然是空的、合并目标仍然错，只是把一次错误的派发换成
一次拒绝。**它治的是「执行者别误判节点」，不是「卡不知道自己该在哪条分支上」。**
可以作为将来的安全网（见 Out of Scope），但不是本卡的修法。

### 弃选二：附件内容随派发注入（复用 `PlanB64` 通道）

同样在下游堵，且有三个新问题：要定多文件的体积与截断策略；内容落在任务目录而
prompt 说的是「仓内相对路径」，等于换个方向说谎；控制台按钮走的是 agentd 内的
`cardstep`，它没有协调者的工作树，读不到未提交/未合并的内容——两个入口行为会分叉。

### 弃选三：迁流（`workflow migrate`）时写基线

「领取即跨流」确实是现有纪律里的同一个动作，但迁流与建树是两个时刻，人完全可能
先迁流后建树，那时分支名还不知道。选中方案不排斥将来在迁流处也开一个入口，但
主入口放在「分支名已经确定」的那一刻。

## 用户故事

1. 作为协调者，我在 web 上新建一棵工作树时能同时勾选这一批卡，建完这些卡的基线
   就是这棵树的分支，我不需要记得另外补一步。
2. 作为协调者，我的工作树是 Claude Code 开的（不在 handoff 的建树流程里），我仍
   能把这批卡的基线设成当前分支——用 `card update --base-branch`，或在卡抽屉里改。
3. 作为协调者，我把卡的基线设成工作分支后派发，执行者的工作分支从该分支切出，
   卡上挂的 spec/plan 附件在它的工作树里真实存在，它不必靠「文件在不在」猜自己
   处在哪个节点。
4. 作为协调者，卡已经派过任务之后我再想改基线，会被明确拒绝，并告诉我是哪一次
   派发、在哪条分支上把它钉死的。
5. 作为协调者，我在卡抽屉里一眼能看出这张卡的基线是自己设的、继承自父卡的、还是
   空（回落项目主线）——今天这三种情况在界面上长得一模一样。
6. 作为协调者，建树时挂卡失败（比如某张卡已派发过），我看到的是「树建好了，这几
   张卡没挂上，原因是……」，而不是一个笼统的失败。

## 契约语义与接缝（L3）

**只定语义，签名归 contract 节点查现状代码后落地。**

- **谁拥有「卡的基线」这个事实**：账本域。agentd 与 web 都只是它的写入通道，
  冻结判定与事件留痕必须在账本域内完成，不允许任一通道自行判断「能不能改」。
- **冻结判据的数据来源**：卡的 `dispatched` 事件流，不新增状态字段。
  这条决定了判据在账本域内可自证，不依赖任何外部状态。
- **建树与挂卡的事务边界**：**不是一个事务。**建树是磁盘动作、挂卡是账本动作，
  跨不了同一个事务。语义定为「建树成功后尽力挂卡，逐张回报结果」，接口返回里
  必须能区分「树建好了」与「哪几张卡挂上了」。
- **依赖方向**：agentd 的建树路径新增对账本域的依赖（今天 `CreateManualWorktree`
  不碰账本）。这是新增的依赖方向，contract 节点要确认它与既有分层相容——尤其是
  账本未启用（`ledger.enabled: false`）时建树必须照常工作，挂卡静默跳过。
- **wire 契约变更两处**：`proto.CreateWorktreeReq` 加字段、`PATCH /api/cards/{id}`
  加字段。两处都是**加字段**，旧客户端不传即旧行为，无需版本协商。

## 实现决定

- 冻结判据用事件流推导，不加状态字段（理由见上）。
- `PATCH /api/cards/{id}` 沿用既有的「缺字段=不动该字段」`*string` 语义，
  不为基线单开端点。
- 建树挂卡失败不回滚工作树。
- 账本未启用时，建树请求里带了卡号一律静默忽略，不报错——控制台在无账本模式下
  本来就没有卡的概念。

## 测试决定（接缝清单）

**最高的可测缝是 `Store.SetCardBaseBranch`**，本卡的全部规则（能不能改、改完
`EffectiveBaseBranch` 算不算数、事件有没有落）都在这一层可判，且不需要 git、
不需要 HTTP、不需要浏览器。测试预算优先压在这里。

1. **账本层（主缝）**：未派发可写 / 已派发被拒且错误带出处 / 写完
   `EffectiveBaseBranch` 返回新值 / 子卡继承不被父卡的新基线意外改写 / 事件已落。
2. **建树挂卡（次缝）**：一次请求挂多张卡的成功与部分失败；账本未启用时静默跳过。
   用既有的 manual worktree 测试夹具，不新起真机。
3. **前端（最薄）**：弹层把勾选的卡号发出去；卡抽屉能区分「自设/继承/空」三态。
   不测 git 行为。

**不做**：端到端「建树→挂卡→派发→执行者读到附件」的自动化。这条链跨三个进程，
自动化成本远高于价值，留给验收阶段的一次真机走查。

## Out of Scope

**永不做**

- 让基线在派发之后可改。冻结点就是首次派发，这是本卡的核心结论，不留后门。
- 自动推断基线（例如「派发时拿协调者 cwd 的当前分支兜底」）。基线是一个决定，
  静默推断出来的决定没人为它负责，而它一旦错了后果是合并到错误的分支。

**本期不做、后续要做**（逐条进 roadmap）

- **派发前校验附件在目标基线上可达**（原 B205 的弃选一）。基线修对之后，这条
  从「主要修法」降级为「安全网」：它能抓住「基线设了但附件仍不在那条分支上」的
  剩余情形。值得做，但不该在同一期做——先让基线对，再看还漏什么。
- **迁流时也能设基线**。等选中方案跑一段时间，看人是否真的会先迁流后建树。
- **卡与工作树的双向可见**：从工作树看「这棵树上挂着哪些卡」。本期只做单向
  （卡知道自己的基线）。
