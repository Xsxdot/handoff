# B389 spec：协调者席位的承载记录与唤醒跨机路由

**上游状态：已批准**（用户 2026-09-19 夜两条裁定：`needs_human` 不唤醒但保留卡级订阅输出与会话列表待办；承载记录随 `coordinate` 席位新增独立记录、与坐席和换绑原子更新、存量有显式修复路径）
**级别：L3 轻档**——跨账本 / 调度 / agentd / CLI 四域，但按切片单轮实现可闭合，不新增子系统。
**上游事实源**：契约增量 `docs/superpowers/specs/b389-contract.md`（32 条原子断言 + 4 项拍板记录 + 显式欠账）；台账 `docs/superpowers/ledgers/2026-09-21-b389-contract-ledger.md`。

## 1. 要解决的问题

1. **唤醒不通**：协调者会话生在哪个载体的机器上，本机就唤不醒它——唤醒路径直接在本机跑 `opencode run -s <会话>`，远端会话必然 `Session not found`（生产实测：B332 每分钟一轮失败）。
2. **共库后互相抢**：两台 agentd 消费同一条事件流，同一张卡的唤醒被两边同时尝试、并发计数也在共享账本里 → 互抢名额（`并发已满`）；且单卡失败会断掉整轮消费，后面的卡全被堵住（实测：`session:10` 那条 `@B382` 的消息根本没被处理）。
3. **两个自激缺陷**：卡已终态仍反复唤醒；失败事件再引发唤醒。

## 2. 前提（用户口径，实现不得偏离）

1. 每台机器都可能承载协调者或执行者；**会话生在哪个载体，后续就由该载体所在机器的 agentd 续接**。
2. 共库是多机协作的基础；**同一条事件只被认领和处理一次**；处理者读出席位绑定的载体与机器，把唤醒请求**路由到那台机器执行**。
3. **首次拉起记录实际载体归属，后续唤醒不得重新选载体。**
4. 不接受"远端席位就跳过、等那台机器自己消费事件"。
5. `needs_human` 不触发协调者自动唤醒，但**保留卡级订阅输出与会话列表待办**；主 agent 看到后按故障原因处置。

## 3. 范围

**做**：契约 §2（承载记录：表、写面、读面、清座、存量修复路径）与 §3（认领、归属解析与路由、转交面、冻结载体准入、判据收口、不堵流），共七个切片，见契约 §5 与 §7。

**不做**：不复用 `driver_carrier` 兼容列；不改 `needs_human` 的两条展示通路；不做 §4-11 之外的终态语义改动；不碰 B381 的四条余项（另卡）；不动主线（合并永远人工）。

2. 本机侧不跑回合、不占名额：远端归属时 `resumes==0 && launches==0` 且两键计数不变。
