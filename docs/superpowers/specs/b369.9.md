现状复测的两点修正（与审计原文的出入，如实记）：

1. **「compact 下只是移开移动覆盖层」在覆盖期已不成立**：B369.8 T7 给覆盖期（`compact && !nav.detail` 或桌面 fullPageRoute，`Shell.tsx:579`）加了 aria-hidden+inert+pointer-events-none 三件套（`:957-962`），后台工作台对读屏/键盘/指针三路不可达。**但下钻态（`nav.detail=1`）内部原样**：mobile-home 整层让开（`:1087` 条件取反）、三件套整体摘除（`Shell.test.tsx:1676-1690` 反例锁），工作台成为活面——审计病灶的本体（单焦点投影缺席）在下钻态原样成立，这正是本卡的主战场。
2. **「页面横向滚动」复测不成立，横滚实际在键栏内部**：overflow-hidden 链（underlay `:959`、renderGroup 列容器 `WorkbenchPage.tsx:316`、外层 `:399`、pane-content `:386`）已把页面级横滚剪断（`WorkbenchPage.test.tsx:34` 锁「列压进窗口，不允许横滑」）。可复现的横滚是**键栏自身**：`MobileKeybar.tsx:34` `overflow-x-auto`，390 宽下两列各 ≈194px，8 键放不下 → 键栏内横滑，方向键尾部不可见不可点——即验收语「键栏不可发现的横向滚动」的命中面。「不保留并排桌面窗格」的复测成立（§1.1）。

### 1.1 根因重述：下钻态里 WorkbenchPage 对 compact 零感知，无窗格投影

WorkbenchPage 没有任何视口入参：`renderGroup` 把 activeGroup 的全部 columns（flex 横排，`WorkbenchPage.tsx:317-321`）与每列至多两格（`:322-388`，`tabs.ts:56` MAX_PANES_PER_COLUMN=2）无条件并排渲染，列间 GroupDivider 照常插拔（`:390`）。390 宽下两列即各 ≈194px——审计实测的两分栏、195px/栏逐字复现。

两分栏的来源不需要用户在手机上拖分栏：工作台布局经 `persist.ts:15`（`__global_workbench__`）持久化，桌面拖出的分栏在手机刷新/恢复时原样重现；`openTerminalAt`（`Shell.tsx:617-625`）「终端无去重键，落进独立新组」——项目终端与任务现场终端常落在两个组，配合 TabBar 组切换（`TabBar.tsx:133`）各自成面。键条侧 `keybar={compact}`（`Shell.tsx:994`）逐终端挂载（`TerminalTab.tsx:700-709`），两个终端窗格各一条键栏——审计「各自一条键栏」逐字复现。

结果：390 下进入终端，用户得到两块各 ≈194px 的挤压窗格、两条各自横滑的键栏，xterm 画布按 ≈194px 重排（FitAddon 量真实容器，`TerminalTab.tsx:233-251`），TUI 与命令行实际不可用。审计根因句在 B369.7/8 后的准确表述是：**覆盖期已被三件套收口，但下钻态内部的工作台投影缺席——修复应做紧凑视口的单焦点投影，同时保持 xterm/WS 常驻，不以卸载换布局**（此句原样成立）。

### 1.2 键条、真实键盘与 IME 的现状（实测）

- **键位集已齐**：`KEYBAR_KEYS`（`MobileKeybar.tsx:18-27`）= Esc、Tab、⇧Tab（`\x1b[Z`）、Ctrl-C（`\x03`）、四方向（CSI A/B/D/C）。北极星「键栏显式包含 Ctrl-C、Shift-Tab」**现状已满足**，本卡无键位新增。
- **事件路径**：键条 `onMouseDown preventDefault`（不抢 xterm textarea 焦点，`MobileKeybar.tsx:42`）+ `term.input(seq)`（`TerminalTab.tsx:701-708`）→ 与手敲合流同一条 `onData`（`:291-314`）→ WS。物理键盘走 xterm textarea 的 keydown/keypress/composition 标准路径。
- **IME 补漏先例**：`terminalInput.ts` 独占 `attachCustomKeyEventHandler` 唯一槽位（文件头 ：15-16），补 WKWebView 两类漏字符——多字符注入键事件（① espanso）与**中文输入法直接上屏的标点**（② WebKit 把 input 排在 keydown 之前，`terminalInput.ts:36-46`）；合成中的 input（拼词）与 composition 全留给 xterm 自己的 CompositionHelper（`terminalInput.ts:8-9`）。
- **测试现状**：`MobileKeybar.test.tsx`（B369.6 先例）锁受控键集/序列载荷/焦点不抢；`terminalInput.test.ts:147-179` 已有**合成 IME 事件**单测（「按下 Shift 后的第一个标点」三例 + 「合成中的 input（输入法拼词）不归补漏管」`:304`）。**缺口**：键条的 compact 挂载与投影后的「单键条」在 Shell/WorkbenchPage 层零自动化（`Shell.test.tsx` grep 无 keybar 断言）；真实浏览器与真机的 IME/物理键行为无自动化通道（§2.3 分级）。

## 2. 目标

### 2.1 单焦点投影模型：phone 档下钻态内只显示焦点窗格

**语义**：390×844（phone 档，`viewport==='phone'`，`useShellViewport.ts:19-23`）下，工作台任意时刻至多一个窗格可见 = 布局焦点格（`wb.activeGroupId` 组的 `focus[column,row]`；焦点判据与 `WorkbenchPage.tsx:294` 的 active 同源）。覆盖期与下钻态同构（投影是视口级门控，不随 detail 翻转）——避免进出下钻的尺寸抖动。组间切换走既有 TabBar（role=tablist，`:133`）；组内多窗格（2×1/1×2/2×2）时新增紧凑窗格切换入口（语义与归 plan 岔口见 §3.3）。隐藏窗格**连键条一起**随层隐藏——「共享单键条」由投影自然达成（§2.2）。

**机制选型（排除法，三条法定约束）**：

1. **不可卸载隐藏窗格**：卸载 TerminalTab 断 WS → 重放（B270/B280 病根；契约 S2 侧「后台连接常驻」是终端托管语义，`TerminalTab.tsx:16-18`「卸载只断 WS」纪律的逆命题——隐藏更不能卸）。
2. **不可 `display:none` / `visibility:hidden` / `opacity-0`**：捏尺寸弄死 FitAddon 测量与 WebGL 画布（`WorkbenchPage.tsx:302` 注释「不移出视口、不 opacity-0（那些会弄死 WebGL）」；B280 明令全禁）。
3. **隐藏层必须 aria-hidden+inert（+pointer-events-none）**：不进读屏树与 Tab 序（验收 a11y 条）。

唯一同时满足三条的是**仓内后台组先例原样下沉到列/窗格层**（`WorkbenchPage.tsx:301-314`：`absolute inset-0` 全尺寸叠放 + `z-0 pointer-events-none` + `aria-hidden` + React 19 boolean `inert`，焦点层 `z-10`）。事件层兼容已有：`TerminalTab.tsx:380` 事件守卫尊重 `[aria-hidden]`/`[inert]` 祖先。

**实现纪律（升格为验收可锁的不变式）**：投影必须以**样式/属性闸**落地——DOM 形状与 React key 路径不变（列、窗格两层的绝对叠层靠 className/style 与三件套属性随档翻转），**不得落成结构分支**（条件渲染两套树）。理由：结构分支会让 phone↔pad/desktop 跨档旋转（折叠屏展开、横竖屏）触发 TerminalTab 重挂 = WS 断开重放，恰好复活 B280 的病；属性/类式闸跨档零重挂（B369.8 三件套同款精神）。plan 若评估后仍选结构分支，须带着这条风险回 spec 翻案，不得静默选择。

**投影不是新布局模型**：tabs.ts 布局（groups/columns/panes/sizes/focus）零改动，投影纯显示层——桌面持久化的分栏布局在手机上只是「投影成单焦点」，回桌面布局原样。`openTerminalAt`/`openTaskTui`/`openMobileTerminal`/`openCoordinatorTerminal`（`Shell.tsx:617/:633/:683/:155`）的落组/激活语义零变更。

### 2.2 共享单键条：随焦点唯一化，不改键条所有权

- 键条**不搬家**：仍是各 TerminalTab 自己的子元素（窗格内容盒内、pty-host 之下，`TerminalTab.tsx:698-709`）。投影把非焦点窗格（含其键条）整层压入 inert 叠层后，**可见键条数恒 ≤1**——始终属于你看得到的那个终端。这不是偷懒：键条 `term.input` 直连本窗格实例（`:701-708`），搬去工作台层反而要新建跨窗格输入通道，徒增一条接缝。
- 键条门控 `keybar={compact}`（`Shell.tsx:994`）**不动**：phone 档由投影收束为一条；pad 档保持逐终端键条（现行为，§2.6）；桌面本就 false。
- 非终端焦点窗格（会话/文件/TUI/空格）无键条——无可喂对象；验收语境即「进入终端时」，语义自洽。BlankTab（选终端/文件的选择面）作为焦点窗格内容照常显示，选定后焦点落新窗格沿 `api.activate`/`setContent` 既有路径。
- 键位集零新增（§1.2）；键条钮触控尺寸若收口（现 ≈26px 高，B369.8 §1.8 量测口径）走 B369.8 触点基线类（TOUCH_BASELINE）同款机制，形状归 plan。

### 2.3 键行为与 IME 验收清单（自动化边界如实分级）

验收原文要求「键栏和真实系统键盘都必须完成 Esc、Tab、Shift+Tab、Ctrl-C、方向键与真实中文 IME 组合输入的浏览器行为验收」。逐项分级：

| 键行为 | 键栏路径 | 真实系统键盘路径 | 自动化（jsdom） | 真浏览器人工 |
|---|---|---|---|---|
| Esc / Tab / ⇧Tab / Ctrl-C / 四方向 | 键条 8 键既有（`MobileKeybar.test.tsx` 全锁）+ 投影后单键条用例（§4） | xterm 标准 keydown 路径（`terminalInput.ts` 只补漏不接管） | 键条：现有用例 + Shell 层键条单实例断言；物理键：`terminalInput.test.ts` 既有路径回归 | 390 实走逐键（键条）+ 桌面浏览器实体键盘逐键 |
| 中文 IME 组合输入 | 键条与 IME 是**互补**而非各自 IME：拼音合成走系统键盘/CompositionHelper，键条供 Esc/Ctrl-C 等组合介入 | WebKit 直上屏标点补漏（`terminalInput.ts:36-46`）+ CompositionHelper | **仅代码路径可锁**：合成 IME 事件既有三例（`terminalInput.test.ts:147-179`）+ 合成中不插手（`:304`）——真实 keyCode 229 次序、composition 次序 jsdom 无法真实化 | **真浏览器+真中文输入法**（桌面 Chrome 拼音 + 手机浏览器输入法）：拼词上屏进终端、合成中键条/物理 Esc·Ctrl-C 介入、候选数字标点 |
| 输入合流与取证 | `term.input` 合流 onData（`TerminalTab.tsx:701-708`） | 同一条 onData | TerminalTab.test 既有 | 实走观察 |

**如实结论**：IME 的「浏览器行为验收」= 真浏览器人工走查，自动化止于合成事件锁代码路径；iOS/Android webview 内的 IME（含外接键盘收起键条，父卡 story 6）归壳阶段真机清单——与验收原文「原生 WebView 壳测试留到壳阶段」一致，本卡验收表不虚列。

### 2.4 连接常驻：返回与两种切换路径不重连不丢状态

- **返回**（detail → mobile-home）：underlay 三件套挂回（`Shell.tsx:957-962`），xterm/WS 全不动——B369.8 已实现且已有反例锁（`Shell.test.tsx:1676-1690`），本卡投影不触碰该闸。
- **切换路径一（会话/窗格间）**：TabBar 组切换 + 组内窗格切换。后台组 keep-alive 既有（仅含终端的后台组叠放渲染，`WorkbenchPage.tsx:425`）；纯文件组切走即卸是既有语义不翻案（`WorkbenchPage.test.tsx:432`）。后台 TerminalTab 只被抢焦点不被重连（active effect `TerminalTab.tsx:644-695`）。投影的隐藏 = 属性闸，切换语义与现状同源。
- **切换路径二（项目终端 ↔ 任务现场间）**：exitDetail → mobile-home → 从卡/项目对另一终端 enterDetail——工作台常驻跨全程（B280 机制），仅覆盖闸翻转；`wb.openOrFocus`（`Shell.tsx:1169`、`:621`）幂等聚焦。投影全程不重排 DOM 身份。
- **几何语义（有意取舍）**：隐藏窗格按先例以全容器尺寸活着（inset-0）——FitAddon 量得全宽、PTY 按全宽 reflow。这是后台组切换的既有取舍（组级 inset-0 已如此），且把「195px 挤压下的 TUI」修复为「全宽可用的 TUI」；PTY resize 是 SIGWINCH 不是重连，scrollback/TUI 状态不丢（§6 风险 2）。
- **契约面**：`b369-contract.md` §3.2 连接核只管隧道与回环源，web 侧终端托管语义（会话跨 agentd 重启存活、卸载只断 WS、回放/重连归 `api/pty.ts`）本卡零触碰，`/api` 零新增。

### 2.5 a11y：隐藏窗格不进焦点序列，焦点窗格可达

- **隐藏窗格**：三件套沿后台组先例（§2.1 机制 3），Tab 序、读屏树、指针三路断；窗格标题/关闭钮/键条一并不可达（都在层内）。`Shell.test.tsx` 覆盖层硬闸 describe 的断言形态（`:1666-1724`）即窗格层用例的模板。
- **焦点窗格**：激活时 `term.focus()`（active effect `TerminalTab.tsx:669-694`）——键盘焦点落 textarea，键条钮在层外可达；窗格头（标题+关闭，`WorkbenchPage.tsx:362-385`）照常渲染。窗格切换入口的 aria 语义归 plan（§3.3）。
- **真读屏**：inert 树的 VoiceOver/TalkBack 播报只能人工/半人工走查（B369.8 §2.7 同口径）；壳内读屏归真机清单。

### 2.6 pad 不误收窄与桌面不回归的边界

- **投影门控 = phone 档**（`viewport==='phone'`，≤767）。pad（768–1023，`useShellViewport.ts:13-14`）**零接触**：多列并排、GroupDivider、逐终端键条（`keybar={compact}` 对 pad 的既有效果）全部保持——「不得把 pad 展开态误收窄」由门控直接成立，并落自动化锚（§4 pad 768 反例用例）。横屏手机（844 宽）落 pad 档得并排形态，是既有分档行为非回归。
- **桌面零接触**：投影判据不在桌面分支出现；GroupDivider/拖放五区/`terminalWheel`/`paneDrop` 桌面行为逐字节不动（B369.7/8 双档守卫同款口径）。WorkbenchPage 新增的投影入参由 Shell 下传（`compact={compact}` / `compact` prop 注入 ProjectTree 先例，`Shell.tsx:869`），WorkbenchPage 不自读视口。
- **样式闸跨档不变式**（§2.1 实现纪律）：跨档旋转只翻 className/属性，零重挂——pad/desktop 既有行为不回归的兜底。

## 3. 与 B369.7/8 的接缝（不发明第二套模型）

- **进出场景**：`nav.enterDetail`/`exitDetail` 是任务现场进出的唯一通道（B369.7 收口后全部下钻回调已走 URL，`Shell.tsx:148-150/:636`），返回条按 `from` 分派（`:1160-1178`）——本卡**零新导航状态、零新 URL 参数**，投影是 `nav.detail` 消费方的内部深化，useMobileNav 不改一行。
- **覆盖期 inert 已由 underlay 管**：壳层（workbench-underlay，覆盖判据 `Shell.tsx:579`）与工作台内部层（窗格三件套）是两个缝、两个判据——覆盖期整层 inert 时窗格层状态无所谓（都在 inert 祖先内），下钻态时 underlay 摘除、窗格层接管。测试互不重复，也不互相替代。
- **键条与 B369.8 触点基线**：键条钮尺寸收口（若做）走 TOUCH_BASELINE 同款 `:not()` 排除法，不新造特异度债（B369.8 T3 的特异度缺陷教训）。
- **P3 约束延续**（`b369-breakdown.md` P3 裁决）：不新增 `terminal*` 前缀源文件；MobileKeybar 保持非 terminal 前缀；本卡对 terminal* 文件族的净改动预期为零（键条门控与事件路径不动）。
- **B280 精神法定化**：「不卸载、不捏尺寸、WS 不断」在投影语境下的准确形态 = §2.1 三条约束 + 样式闸纪律；变异测试据此设计（§4）。

### 3.3 归 plan 的开放岔口（spec 只定语义不定形状）

1. **组内窗格切换入口**：法定语义 = ①非空窗格（含后台终端）均在两步内可成为焦点；②切换只写 wb 焦点（`api.activate`/`activateGroup`），不新增布局操作、不移动窗格；③入口在 compact chrome 层（不在任何 inert 层内）；④空槽位（null）不占切换位，BlankTab 是焦点窗格内容不是切换目标。形态候选：键条行左侧「窗格 N/M」钮、pane 头分段控制——归 plan 定。
2. **投影叠层的 className 具体形状**（列/窗格两层的 absolute/inset/z 序与三件套挂点）。
3. **键条钮触控尺寸收口**与否及数值（量测驱动；现 ≈26px 高对行内次级 ≥24 的基线是踩线达标）。
4. **拖放 handler 在投影层的去留**：保留（死代码路径，触屏 html5 DnD 本不可用）还是 phone 档不挂——两者桌面均零影响，归 plan 依可读性定。

## 5. 非目标

- **桌面多栏工作台**：分栏拖拽、五区拖放、组管理全部不动；投影只存在于 phone 分支。
- **pad 专属优化**：父卡 story 6 的「接外接键盘时键条收起」、pad 分栏触控优化不做（真机/壳阶段，同 B369.7/8 §5 口径）。
- **原生 WebView 壳测试**：验收明文留壳阶段——webview 内 IME、外接键盘、TalkBack/VoiceOver、cookie 桥接联调全部 OOS。
- **键栏新键位扩展**：北极星点名的 Ctrl-C 与 Shift-Tab 已在受控键集（§1.2），无新增；更多键位（Ctrl-Z/方向修饰等）另立卡。
- **B369.7 导航模型与 B369.8 硬闸**：零翻案、零重复实现；useMobileNav 与 underlay 三件套不改一行。
- **终端托管/PTY 服务端**：`/api` 零新增，`api/pty.ts`、会话生命周期、回放协议零触碰（契约 S2 语义守恒）。
- **触屏拖放**：html5 DnD 无触屏语义，投影期间拖放入口不可用不是回归（触屏本来拖不动）；移动端窗格重组交互若要做另立卡。

## 6. 风险与开放问题

1. **单焦点投影与既有并排双栏交互的冲突面**：GroupDivider（分栏拖拽）与多窗格投放（dropZoneAt 五区）在 phone 投影下不可达/无意义。处置 = 投影层不渲染 GroupDivider、拖放路径保留不拆（§3.3 岔口 4）——桌面回归零风险，触屏拖放本就不可用（如实记）。残留冲突是「手机所见与桌面持久化布局不一致」：投影是显示层语义，布局模型零改动，回桌面原样——这是特性不是缺陷（验收明文要求投影）。
2. **隐藏窗格全宽 reflow**：从 195px 挤压到全宽是一次 SIGWINCH——与后台组切换同一取舍（组级 inset-0 已如此）；长输出 TUI 一次重绘成本可接受，且 TUI 从 195px 不可用变为全宽可用是修复本体。风险在「用户后台跑着按 195px 排版的会话」被 reflow——record in plan：投影首次生效（升级后首次加载）时后台窗格统一 reflow 一次，此后稳定。
3. **样式闸实现纪律的执行风险**：若 plan 落成结构分支，跨档旋转引入重挂（WS 断+重放）——§4 已落跨档同节点变异锁，落红即回 spec，不得静默带过。
4. **pad 键栏横滚的量测前提**：768 宽两列各 ~380px，8 键 ~348px 放得下——pad 不触键栏横滚的前提是键位不扩与分栏不更窄；本卡两条件均守（键位零新增、pad 布局不动），前提变化时须重开键栏宽度问题（记入卡台账）。
5. **IME/真键盘自动化边界**（§2.3 如实分级）：jsdom 只能锁补漏不双发/合成中不插手的代码路径；真浏览器 IME 行为（keyCode 229 次序、composition 事件序、iOS Safari 差异）只能人工走查。若验收节点要求真机 IME 当场收口，本卡验收范围需扩——按父卡 S6 真机清单口径（`b369-breakdown.md` §3.7 真机走查 #4）留在壳阶段，本卡交付时知会。
6. **焦点窗格为 BlankTab/空格**：无键条（§2.2）——「进入终端时」语境自洽；风险仅在验收走查把它误读为键条缺失，走查表须标注「终端焦点窗格」前提。
7. **验收判据与代码现实无根本矛盾**：单焦点（投影机制可达）、单键条（投影收束）、常驻（先例机制现成）、pad 边界（分档现成）、IME（补漏先例+人工走查）逐条有可达处置；无「无法自圆其说」项。

## 7. 原型缺失说明

卡上原挂的两个原型 html **已不在盘上**（实测 `prototypes/` 下无 `mobile-app` 目录；`prototypes/base/` 为桌面形态镜像，无移动屏）。形态依据以卡上**北极星写回笔记（2026-09-22）为准**：「项目终端与任务现场共用单焦点终端形态和特殊键栏，键栏显式包含 Ctrl-C、Shift-Tab；后台终端保持服务端托管。原型只确认形态，真实 IME、连接保持、无障碍焦点及桌面/pad 回归仍待验收节点完成」——本卡 §2/§4/§5 即该「待验收」清单的法定承接。键条形态的既有实现（B369.6，`MobileKeybar.tsx`）即为该笔记的已落地部分，本卡不推翻其形态。

## 8. 定级结论与落点

**L2**。理由：单子系统（`d_web`，改动集中在 `web/src/app/workbench/WorkbenchPage.tsx` + `Shell.tsx` 下传入参 + 各测试；terminal* 文件族净改动预期为零）；无新 wire 契约（`/api` 零新增，连接核语义只在消费侧守恒）；机制全部有仓内先例承接（窗格三件套=后台组先例下沉 `WorkbenchPage.tsx:301-314`、键条门控=既有 prop、投影=显示层属性闸），无架构级不可逆决策。**不升 L3轻**：终端虽是高风险面，但风险落在验收成本（真浏览器/真机人工走查）而非方案选型——「做错要回炉」级的脊柱决策不存在：三条约束排除法只剩一个可行机制（§2.1），无并列方案对赌。a11y/IME 横切面按 B369.8 同口径处理（先例机制 + 人工走查如实分级），不构成升档理由。工作量显著高于流程固定成本（投影 + 窗格切换入口 + 双档守卫 + 变异锁测试面），不落 L1 快道。落点：spec 完稿后卡移 plan 列，plan 接手 §2.1 机制与 §3.3 四个岔口（窗格切换入口形态、叠层 className 形状、键条触控收口、拖放 handler 去留）。
