# B227：codex 在 linked worktree 里写不了 git 元数据

- **状态**：**已批准**（2026-08-25，用户以「继续」推进；未逐行审阅正文，批准的是本 spec 定稿的范围与方案）

- **档位**：—（L2 无选档）
- **卡**：B227
- **台账**：`docs/superpowers/ledgers/2026-08-25-b227-spec-ledger.md`

## 问题陈述

codex 执行器跑在 OS 沙箱里，可写域 = 工作目录 + 一组显式声明的可写根。今天声明的
可写根只有任务专属临时目录（现状读数：`internal/executor/codex/adapter.go:157`）。

派发用的工作树是 git 的 **linked worktree**（现状读数：`internal/agentd/workspace.go:313`
的第 3 层按 worktree 维度分派，走 `git worktree add`）。这种工作树里的 `.git` 是**指针文件**，
真实元数据在主仓库的 git 公共目录下——**不在可写域内**。于是任何需要写 git 元数据的操作
被沙箱拒绝（`Read-only file system`）。

范围比卡标题大：自带工作树的派发模式走的也是 linked worktree（归属校验正是靠公共目录
比对，现状读数：`internal/agentd/workspace.go:313` 的用户树分支），同样撞。只有原地模式
不撞——那时工作目录就是仓库根，`.git` 是它下面的真目录。全仓只有 codex 有 OS 级沙箱
（现状读数：`grep -rl sandbox internal/ --include='*.go'` 只命中 codex 包），其余三个执行器
不受影响。

### 真正的性质：不是「某类操作做不了」，是行为不可预测

执行者被沙箱拒绝后，**有时**会申请提权重试、**有时**直接放弃并如实汇报失败。三次复现
三种反应：一次停摆 2 小时、一次自己提权重试成功、一次放弃并把任务交回协调者。

取证证实提权路径本身是通的：某一轮产生 8 张 git 写工单，8/8 被审批链自动放行并成功执行，
含 `git commit`；而同轮的 `git fetch` **没有产生任何工单**——执行者选择了不提权。
（原始读数见台账 §1。这一条**推翻了本卡先前 comment 里「连提权都救不回来」的归因**。）

后果是：协调者下达的任何涉及 git 元数据写的指令——fetch、merge、rebase、stash——都是
**概率性可执行**的。这比「稳定地要一次审批」更难处置，因为它不产生可依赖的失败信号。

### 现状的绕法比修好更危险（反直觉，已查证）

被拒后的提权，其语义是**整条命令完全脱离沙箱执行**，不是「把某个路径加进可写域」
（codex 二进制内嵌原文：`use \`require_escalated\` for unsandboxed execution`，读数见台账 §3）。

codex 的内置指令明写：命令因沙箱失败时应带上脱沙箱标志重跑。所以被沙箱拒绝的 git 写，
执行者一旦选择重试，重试请求带的就是这一档——放行它等于放出一条**无沙箱的 shell 命令**，
其授权面**严格宽于**本 spec 要开的 git 公共目录可写权限。「不改沙箱、靠审批放行更保守」
这个直觉是反的。

**而审批侧看不见自己在批哪一档**（由另一张卡的协调者从 handoff 本仓代码独立验证，
与上面的二进制取证互不依赖）：审批报文的字段全集是 itemId / threadId / turnId /
command / cwd / commandActions，**不含任何沙箱或提权档位字段**，解析侧也不解析；
回发的裁决只有一个 `decision` 键，`once` → `accept`，其余一律 `decline`
（现状读数：`internal/executor/codex/perm.go` 的 `commandApproval` 与 `decisionFor`）。

两条合起来是本 spec 的核心论证：**协调者与审批链做的每一次 allow，都是在不知道自己批的
是沙箱内执行还是脱沙箱执行的情况下做的**，而且没有「只批沙箱内」这个选项可回发。
本 spec 的方案让这批请求在源头不再发生，因此顺带消除的正是今天绝大多数盲批实例。

## 级别与档位

按最优树，本 spec 的两处改动落在两个顶层领域（= 两个子系统）：沙箱可写域属**任务执行**，
git 调用加固属**任务编排**（归属查询见台账 §4）。

但架构法对 L3 的定义是「改动跨越 ≥2 个子系统的**契约面**」。本 spec 的两处改动**各改各的
内部实现**：彼此不通信、不新增依赖方向、不改任何导出面，没有需要冻结的缝。走契约节点
只会产出一份空洞的契约文档，而试点数据表明 L3 的价值恰在契约那半段。

**定级 L2。** L1 也不成立——空 hooks 目录的落点、公共目录路径的相对/绝对归一、可写根
在哪个构造点计算，都是真实的实现决定，三行写不完（L1 判据 1 不满足）。

## 方案

### 选定：扩可写域 + 堵住 hooks 逃逸链（两件事打包）

**其一**：把任务对应的 git 公共目录加进 codex 的可写根声明。

粒度必须是**整个公共目录**，不能更细。`git add` 要写对象库，`git commit` 还要写引用、
reflog、可能还有 packed-refs 与 config——它们散落在公共目录根上（落点分布见台账 §5）。
实测「只开对象库+引用+日志+worktree 私有目录」这个最精确的 allowlist 是**半坏的**：
删分支、打标签、gc、rebase 直接失败，而 add/commit/stash 虽然返回 0 却在 stderr 里带
拒绝噪声——后者更毒，因为模型很可能据此误判自己失败（读数见台账 §5）。

**安全论证**：这不新增权限类别。原地模式今天就是这个档位（工作目录即仓库根，公共目录
本就在可写域内）。本改动是把 worktree 模式**拉平**到与原地模式相同的档位，而不是开一个
新的口子。相比之下，今天的绕法（提权 = 无沙箱执行整条命令）授权面更宽。

**其二**：让 agentd 自己执行的 git 命令不再触发仓库内的 hook 脚本。

**这是其一的必要伴随**，理由是一条实测可行的宿主提权链：`git worktree add` 会触发共享的
`post-checkout` hook，而该命令是 **agentd 自己**在跑的——跑在 agentd 进程里，不在任何沙箱内。
于是链条成立：沙箱内的执行者往共享 hooks 里写一个脚本 → 下次任何人对同一仓库派发新工作树
→ agentd 以自身身份、无沙箱地执行它。**这不是「执行者能毁掉自己的成果」级别的代价，是提权到宿主。**

四项实验（含对照组）证实链条成立、且命令行级的 hooks 路径覆盖能堵住它，并**压得过被篡改的
仓库配置**（读数见台账 §2）。

**为什么必须同卡打包，不能拆两张**：两处改动只有合在一起才验收得完整——单验其一，只能证明
「记账不报错了」，证明不了「没把门开大」。且两张卡落地之间的窗口期，敞口是真实可利用的。

**该链今天已经存在**（原地模式下执行者本就能写 hooks），所以加固独立于本卡即应成立；
本卡只是让它从「得先设法拿到写权限」变成「默认就有写权限」，因此不能再拖。

### 弃选

| 方案 | 弃选理由 |
|---|---|
| **只开 worktree 私有元数据目录** | 不够。`git add` 就要写对象库，它在公共目录里（台账 §5）。 |
| **更精细的 allowlist（对象库+引用+日志）** | **实测判死**：删分支/打标签/gc/rebase 直接失败，其余动作带拒绝噪声（台账 §5）。可写根声明这个面**表达不出 deny**，做不出精细化。 |
| **把元数据 symlink 或挂载进可写根** | **实测判死**：沙箱按解析后的目标端判，不按链接端判（台账 §5）。 |
| **改用独立克隆替代 linked worktree** | 方向正确但昂贵且救不全：分支对象在主仓这一前提被六处运行期逻辑依赖——同步回程、bundle 端点、工作区回收、工作区探测、location 归并、归属校验（依赖点清单见台账 §5）。而且**救不了自带工作树那条路径**（不能替用户克隆）。收益本方案用一个可写根就拿到了。 |
| **不改沙箱，靠审批规则自动放行 git 写** | **安全序是反的**：放行的是无沙箱执行整条命令（台账 §3），比本方案宽。且判据是字符串匹配，救不了「执行者选择不提权」那一类。 |
| **换用 codex 的另一套权限声明面（支持 deny）** | 纸面最优——唯一能同时做到「git 完全好用」和「把 hooks 与 config 从可写域里 deny 出去」。但它与现用的声明面**互斥**，要把整套安全姿态迁到新面上，且**执行机上的 codex 版本未知**，需版本门与双轨回落。用一条可用性未知的新协议面，去换一个一行配置就能堵住的敞口，不划算。**落 roadmap，不进本期。** |
| **只在纪律块里告诉模型「被拒时用提权重跑」** | 补丁不是修：把不可预测性从「模型想不想得到」降到「模型听不听话」，根因（可写域与工作树拓扑对不上）一动没动。且它会让本卡的验收判据变模糊。**落 roadmap。** |

## 用户故事

1. 作为协调者，我在 `--extra` 里要求执行者「先 fetch origin 再核对某提交是否在基线」时，
   它能真的执行，而不是回报「Read-only file system」把任务交回给我。
2. 作为协调者，我派出去的每一轮 codex 任务不再为记台账、提交产出物而反复申请提权，
   回合里不再夹着一串与任务无关的 git 权限工单。
3. 作为协调者，我可以对同一张卡连续派多个节点，而不必担心某一轮因为工作树模式的差异
   （新建树 / 自带树 / 原地）表现不同。
4. 作为运维者，一个执行者即便在自己的工作树里写了恶意的 git hook，也不会在下一次派发时
   被 agentd 以自身身份执行。

## 实现决定

- **可写根的计算归执行器侧**，不经派发请求契约传递：执行器侧已有直接调用 git 取证的位置，
  公共目录由那里查得，因此**不改派发请求的契约**（现状读数：`internal/executor/executor.go:66`
  的 `StartReq` 与 `internal/executor/turn/gitprobe.go:24`）。
- **每个运行态只算一次并缓存**，算在运行态的**唯一构造点**上——不算在启动路径里。
  理由是恢复路径也经同一构造点；算在启动路径上会重演「两处构造点吃掉新字段」那类缺陷
  （现状读数：`internal/executor/codex/adapter.go:234` 是唯一构造点，启动与恢复都经它）。
- **hooks 加固落在 agentd 执行 git 的单点收口处**，不逐命令加——该处已是所有 git 调用的
  必经之路（现状读数：`internal/agentd/workspace.go:131`，其上的 `gitRun` / `gitProbe` 都从这里过）。
  覆盖必须是**命令行级**而非配置级：实测命令行级压得过被篡改的仓库配置（台账 §2 实验 c）。
- **工作目录不是 git 仓库时静默跳过**，不加可写根、不报错、不中止。派发到非 git 路径有
  独立的拒绝路径，本改动不承担那个职责。
- **其余沙箱姿态一字不改**：网络访问、排除共享临时目录这两项保持现值。本改动只增加一个
  可写根，不是重新设计沙箱策略。

## 测试决定（接缝清单）

两条缝，两个子系统各一条：

1. **沙箱策略的构造函数**（存量符号，现状 `internal/executor/codex/adapter.go:157`）
   ——调用方是 turn 参数的构造处（`adapter.go:468`），已有守门用例覆盖该函数的输出形状
   （`internal/executor/codex/discipline_test.go:29`）。本轮在同组用例里增加断言：
   公共目录进了可写根，且原有的两项排除开关仍为真。
   *合法性*：非导出但有生产调用方，且已是既有守门点，不是为本轮抽出来的假缝。

2. **agentd 执行 git 的单点收口处**（存量符号，现状 `internal/agentd/workspace.go:131`）
   ——调用方是同文件的 `gitRun` / `gitProbe`，最终服务于工作区准备（`workspace.go:313`）。
   缝级断言用台账 §2 的靶子形态：仓库里放一个 hook → 走工作区准备建新工作树 → 断言 hook 未运行。
   *合法性*：非导出但是全部 git 调用的必经之路，有生产调用方。

**真机验收另计**：沙箱语义是 OS 行为，本机（macOS/seatbelt）与执行机（Linux/Landlock）
不是同一套实现。机内用例只能验「可写根声明里有这一项」这个**契约形状**；
「沙箱真的放行了」属行为事实，必须在 Linux 执行机上真机跑一轮才算数。

## Out of Scope

**永不做**：

- 改用独立克隆替代 linked worktree（弃选理由见上表；六处运行期依赖 + 救不了自带工作树）。
- 在可写根声明面上做精细化 allowlist（实测判死：该面表达不出 deny）。
- 把 git 元数据 symlink 或挂载进可写域（实测判死：沙箱按目标端判）。

**本期不做、后续要做**（逐条落 `docs/roadmap.md`）：

- **换用 codex 支持 deny 的权限声明面**，把 hooks 与 config 从可写域里 deny 出去，
  从而不依赖外围的 hooks 路径加固。前置未知项：执行机上的 codex 版本（本轮未查，见台账 §6）。
- **改用「沙箱内追加权限」档替代现有的提权档**：codex 存在第三档，语义是沙箱内追加本次
  命令所需权限而非脱离沙箱，但需要开启一个功能开关（读数见台账 §3）。它能让**其余**仍需
  提权的场景不再等价于无沙箱执行。
- **同仓并行任务互相踩踏的收窄**：公共目录可写意味着同仓的两个任务能互改对方的索引与引用。
  本期接受（与原地模式同档），但并行派发是本产品的卖点，值得单独一张卡。
- **纪律块层面的兜底**：告知执行者 git 元数据被拒时应提权重跑，覆盖本卡未触及的边角情形。

**不属于本卡**：审批判据本身的降噪（另有专卡在做）。两者互补——本卡在源头让请求不发生，
那张卡在判据层决定怎么答。**但顺序有实质影响**：本卡落地后，那张卡立项数据里的绝大部分
（codex 的 git 本地写）会不再产生请求。二者不宜并行推进，先后由协调者裁决。
