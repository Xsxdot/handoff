- 状态：r1.1（plan 拍板回写：S3 括注更正、真机托管形态改系统级 systemd-run / 临时 plist）；r1 自批准（2026-10-22，用户离开期授权「如果 B453 做完我还没回来，你就自主继续推进这两张卡」；回来后可推翻）
- 级别：**L2**（单子系统：升级链路 = CLI `upgrade` + `internal/upgrade` + 构建脚本 + agentd 启动挂载；不新增、不改变 wire 契约，复用 `POST /api/update` 推送模式与 `GET /api/status`）
- 执行形态：**甲 本地盯**（形态判决第 1 条红线：验收要换版并重启 agentd——在役服务与派发系统自身；真机只用隔离实例，生产换版只在本卡 finish 由主会话执行）
- 卡：B462；台账：`docs/superpowers/specs/b462-ledger.md`

## 问题陈述

每张卡的 finish 都要把三台机器换成本地刚合并的版本。现在是手工流程：`scripts/build-deploy.sh` 分平台构建 → `mv` 覆盖 `~/.local/bin/handoff` 并手工留 `.bak-pre-<卡>` → Mac 上 `launchctl kickstart`、linux-01 上 `systemctl restart` → 人工查 `/api/cards` 与 `devices.updated_at`，挂不上就再重启一次。每次都踩坑：`pkill -f` 杀掉自己的 ssh、重启要试第二次、Supabase `too many clients`。

现状读数（执行节点复核）：

- `handoff upgrade` 已有完整的换版编排，只缺来源（`cmd/upgrade.go:277` 起，`internal/upgrade/remote.go:97 RemoteOne`）。
  - 已有能力：按对端 `status.version.platform` 选资产；`PushUpdate` 推包；agentd 侧 `release.Install` 依次做 sha256 复检、解包，并检查 `version` 首行是否等于 tag；`release.Activate` 同目录留 `.prev`；随后 exit 0，由 systemd/launchd 拉起；CLI 用 `WaitVersion` 等新版上线。
  - 已有闸门：活跃任务闸、非托管闸、自拉互斥闸。
  - 缺口：二进制只认 GitHub release（`releaseChecker`/`releaseFetcher` 两个接口，`cmd/upgrade.go:48-63`），推不了本机构建。
- `scripts/build-deploy.sh` 已能产出版本戳可信的开发构建：`releaseVersion=<12 位短号>[+dirtyN]`，内嵌前端，可交叉编译。但它只出裸二进制，不打 release 形态的包、不出 `checksums.txt`。
- 「too many clients 要再重启一次」的根因：`cmd/agentd.go` `setupLedger` 里，账本**打开**已对瞬时错误退避重试（`openLedgerWithRetry`）。但紧接着的 `agentd.SelfRegister` / `ImportLocalTargets` 一旦返回错误，账本子系统就**直接不挂载**，agentd 照常 Ready、`status` 回 200——卡账本从此不可用，直到人工重启。2026-10-19 linux-01 的事故即此形状（自登记时撞 53300）。

## 方案

**选：给 `handoff upgrade` 加一个本机构建来源**（`--from <目录>`），目录由 `build-deploy.sh` 的打包模式产出，形态与 release 资产逐字一致（`handoff_<tag>_<goos>_<goarch>.tar.gz` + `checksums.txt`）。CLI 用一个读本地目录的实现替换 release 来源，其余编排（判决、闸门、推送、自检、`.prev`、重启、等版本）一行不分叉。

弃选：

1. **另写一条 fleet-upgrade shell 脚本**（卡面原文）。它会与 `handoff upgrade` 形成第二套换版路径：闸门、平台选择、自检、`.prev`、重启方式都得再写一遍，且会持续漂移。卡面要的「一条命令」由 `--from` 达成。
2. **每台机器本地 `go build`**。执行机上不一定有源码与工具链，与「执行机无需出网」的既有承诺相悖。
3. **对 too many clients 「自动再重启一次」**（卡面原文）。这是补丁：真因是自登记不重试（见上）。在根上修，`WaitVersion` 成功即代表账本已挂。

备份：沿用既有 `.prev`（`release.Activate`），不再另造 `.bak-pre-<卡>` 命名（卡面原文）。理由：一个备份约定一条回滚路径（`handoff upgrade --rollback`）。远端一键回滚现在不支持，列入 Out of Scope。

## 落位三问

1. **读写谁的权威数据**：二进制文件与 agentd 进程归升级链路（`internal/upgrade` 编排 + agentd 的 update handler），设备表归账本（自登记是 agentd 启动挂载的一步）。本卡不新增任何权威数据（第五条）。
2. **谁消费**：`--from` 的来源实现只被同子系统内的 `cmd/upgrade` 消费，用导出符号，不建 client（第四条第 1 档）。跨进程仍走既有 `/api/update` 与 `/api/status`。
3. **同步还是异步**：同步。CLI 要等换版结果与新版上线，失败要立即呈现（第十二条第 1 问「是」）。agentd 启动挂载的重试在启动期内同步进行，由启动闸播报阶段。

## 实现决定

- 用户可见名字：flag `--from <目录>`（`upgrade` 子命令），打包模式由 `build-deploy.sh` 的一个开关触发（名字归 plan，须在 `--help`/脚本头注释写明）。
- `--from` 与 `--rollback` 互斥；与 `--push` 兼容（本来就是推送）；与 `--check`、`--now`、`--target`、`--force` 正交。
- 来源目录里的 tag 从目录内容得出（包名或清单），不靠目录名猜；目录内出现多个 tag 时拒绝。
- tag 形态沿用 `build-deploy.sh` 现规则（`<12 位短号>`），不冒充 `vX.Y.Z`。S1 拒绝脏树后，`+dirtyN` 不会进入打包产物。
- S3 的「账本可读」探针用既有只读端点，不新增 wire 字段。端点选择归 plan，判据是轻量、只读、ledger 未挂载时必定失败。
- S4 在 `setupLedger` 内收口，复用 `openLedgerWithRetry` 的退避、抖动、限频与启动闸播报，不另起一套。

## 测试决定

- 竖切：`cmd/upgrade` 用假 peer + 本地目录来源跑 `--now --from`，断言推送的包字节与 sha 来自目录、走推送而非自拉、缺平台资产的机器单独 fail。
- 核心方法：本地目录来源的解析（tag 唯一、checksums 行匹配、资产命名与 `release.AssetName` 一致——直接复用该函数，不复写命名规则）；S3 判据的四格（前可读/后可读、前可读/后不可读、前不可读/后任意、探针够不着）；S4 的重试序列（瞬时→成功、瞬时→停机、非瞬时→不重试）。
- 序列化边界：包内文件名与 release 资产一致（`handoff` / Windows `handoff.exe`），由 agentd 侧 `release.Install` 的真实解包与自检在测试里跑一遍（构造真实 tar.gz）。
- 真机（隔离实例，绝不动在役 agentd）：在 linux-01 用系统级 `systemd-run --unit=<b462 测试名> -p Restart=always` 起一个托管的隔离 agentd（让 `INVOCATION_ID` 生效、exit 0 后被拉起；root 未开 linger，`--user` 不可用）；本机用临时 plist（KeepAlive）+ `launchctl bootstrap` 同理。各接一个测试账本库，然后 `--from` 换版：
  - 版本上线、`.prev` 生成；
  - 换版前后账本均可读；
  - 人为让包缺一个平台，看失败呈现。
  环境做不出托管形态时，标「未验」并请求批准替代判据，不自行判等价。
- 生产使用（本卡 finish）：用本命令把三台换到合并后的版本，即是生产冒烟；手工流程作为回落。
