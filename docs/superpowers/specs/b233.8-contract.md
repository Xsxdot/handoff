## 1. 冻结边界

本节点冻结的是 ApprovalClient 的生产实现物理落点、Manager 组装端口、OpenCode 三条注入缝，以及不退役的旧业务入口。实现节点只把现有 `taskApprovalClient` 行为搬到新包并通过下述端口接回；不改变审批决定、事件、工单、快照或 OpenCode 权威路径。

不冻结为本卡工作的内容：Claude/Codex/Grok/AGY 的权限或提问权威迁移，`handlePermission`、`handleQuestion`、`waitQuestion` 的删除或收缩，`POST /api/tasks`、`Manager.Dispatch` 的退役，新 HTTP/CLI/事件，`d_execution→d_orchestration` 之外的新方向，以及 dead-contract 方向的假绿。

## 3. 迁出后的精确契约

### 3.1 实现包与公开符号

生产实现包冻结为 `internal/approval`，仍归现有 `d_orchestration`；不新增 `d_approval`。Ticket 0 已落下可编译空壳，精确签名如下：

```go
type AnswerHub interface {
	Publish(proto.Event)
	WaitAnswer(context.Context, string) (string, error)
}

type ConsultDecision struct {
	Approve   bool
	Reason    string
	ElapsedMS int64
	Err       error
}

type Hooks struct {
	Log                 *slog.Logger
	Store               *store.Store
	Hub                 AnswerHub
	JudgePermission     func(taskID string, ev executor.AdapterEvent) permgate.Verdict
	ShouldConsult       func(taskID string) bool
	Decide              func(context.Context, string, string) ConsultDecision
	CountConsultFailure func(taskID string)
	ResetConsultFailure func(taskID string)
	AutoAllow           func(taskID string, ev executor.AdapterEvent, verdict permgate.Verdict)
	TransitBestEffort   func(taskID string, to proto.TaskState, reason string)
	NoteDeliveryFailed  func(taskID, ticketID string, cause error)
}

type Client struct {
	taskID string
	snap   executor.PolicySnapshot
	hooks  Hooks
}

func NewClient(taskID string, snap executor.PolicySnapshot, hooks Hooks) *Client
```

上述骨架出处为 `internal/approval/client.go:20-79`；其中 `Client` 必须满足 `var _ executor.ApprovalClient = (*Client)(nil)`。`NewClient` 保留旧 `bindApproval` 的 TaskID 补全语义：仅当 `snap.TaskID == ""` 时写入 `taskID`。

### 3.2 Manager 组装

`Manager.bindApproval` 的外部可见（包内）签名不变：

```go
func (m *Manager) bindApproval(taskID string, snap executor.PolicySnapshot) executor.ApprovalClient
```

实现节点必须让它成为唯一组装点：调用 `approval.NewClient(taskID, snap, approval.Hooks{...})`，把现有 Manager 私有能力逐一接到 `Hooks`，不得让 `internal/approval` 反向 import `internal/agentd`。生产组装必须提供非 nil 的 `Log`、`Store`、`Hub`、判据、审批、事件与状态回调；`Decide` 的三项语义镜像现有 `Approver.Decide(ctx, permission, taskSummary)` 的 `Approve`、`Reason`、`ElapsedMS`、`Err`。

冻结的 Hook 映射为：

| `approval.Hooks` | 现状实现来源 |
|---|---|
| `Log` / `Store` / `Hub` | `internal/agentd/Manager` 的 `log` / `st` / `hub` 字段；字段定义见 `internal/agentd/manager.go#Manager`，`Hub` 定义见 `internal/agentd/hub.go:27-37` |
| `JudgePermission` | `internal/agentd/manager.go#Manager.judgePermission` |
| `ShouldConsult` | `internal/agentd/manager.go#Manager.shouldConsultApprover` |
| `Decide` | `internal/agentd/approver.go#Approver.Decide`，现状在调用方适配为 `ConsultDecision` |
| `CountConsultFailure` | `internal/agentd/manager.go#Manager.countApproverFail` |
| `ResetConsultFailure` | Manager 现有 `apMu`/`apFails` 清理逻辑，保持现有失败计数重置语义 |
| `AutoAllow` | `internal/agentd/manager.go#Manager.autoAllowPermission` |
| `TransitBestEffort` | `internal/agentd/manager.go#Manager.transitBestEffort` |
| `NoteDeliveryFailed` | `internal/agentd/manager.go#Manager.NoteDeliveryFailed` |

`internal/approval` 可直接消费 `store.Store` 的既有方法；不复制 Store/Hub 的权威状态。权限请求的 ticket payload 可在新包内定义同形私有 JSON，wire/event 类型仍由 `proto` 定义；这属于实现端口的必要接线，不新增事件字面值。

### 3.3 OpenCode 三条注入缝

以下每条都是独立断言，漏一条即失败：

1. OpenCode Dispatch 仍在 `StartReq.Approval` 注入 `executor.ApprovalClient`，来源是 `Manager.bindApproval`。
2. OpenCode Continue 仍先投影 `PolicySnapshot`，再经 `ApprovalBinder.BindApproval(taskID, client)` 绑定由 `Manager.bindApproval` 构造的新 client。
3. OpenCode 冷 Resume 仍在 `ResumeReq.Approval` 注入由 `Manager.bindApproval` 构造的新 client。
4. OpenCode 启动热恢复仍在 Resume 请求注入由 `Manager.bindApproval` 构造的新 client。
5. OpenCode adapter 的 `authorizeNativePermission` 继续调用 `executor.Authorize(ctx, r.approval, req)`；审批错误继续走拒绝回传，成功后继续按 `AckFormed`、`AckDelivered`、`AckExecuted` 顺序确认。
6. `internal/executor/opencode` 不 import `internal/agentd` 或 `internal/permgate`；adapter 只消费 `executor.ApprovalClient` 与可选 `NoteDeliveryFailed` 动态能力。

## 7. 三重闸门拍板记录

本节点命中一项：生产实现必须从 `internal/agentd` 迁至顶层 `internal/approval`，而不是保留在 agentd 或新立 `d_approval`。这是跨 Manager 私有依赖、执行契约与 OpenCode 组装点的难逆物理边界；没有本上下文时后人会自然认为审批实现应继续属于 agentd；取舍是新增一个窄 Hooks/Hub 端口与迁包接线，换取 `agentd` 不再拥有 ApprovalClient 实现。否决「留在 agentd」（直接违反物理迁包契约）、「internal/agentd/approval」（仍把实现留在 agentd 命名空间，边界不清）、「新立 d_approval」（违反 B233.1 已冻结的域形态）以及「approval import agentd」（形成循环依赖）。显式不做：本节点不把实现行为接入 Manager，不迁五家 harness 权威，不改入口、事件或 dead-contract 方向。
