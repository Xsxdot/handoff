> 状态：**r1 已批准（2026-10-22，主会话按用户授权自批）**——用户原话「可以，建两张卡，排在B453后面，如果B453做完我还没回来，你就自主继续推进这两张卡」（卡 note seq 29491）。B453 的代码与审查已完成、只剩用户裁决项（opencode-go 欠交），按授权推进本卡。
> 级别：**L1**（单子系统：仓内熟练工定义 + 文档；不改 Go 代码、不动契约；plan 增量为零，验收一眼可核）。本 spec 同时作 plan（`spec:` 与 `plan:` 双附件）。
> 执行形态：**甲**（L1；主会话亲自写模板与文档，真机派发一次核对）。
> 台账：`docs/superpowers/specs/b461-ledger.md`。

## 问题陈述

charter finish 的机械检查——新鲜全量测试、gofmt/vet、README 命令表对 `--help`、CHANGELOG 漏条、残余是否入 roadmap——今天都由主会话亲手跑、亲眼读输出。全量测试输出长、要辨认已知抖动，文档对照要逐条比，耗主会话上下文。按全局规则「机械活交熟练工」，这些只读检查应交熟练工，主会话只读结论。

## 方案

新增只读熟练工定义 `finish-check`（形态同 `code-investigate`：`mode: readonly`，在按基线提交检出的独立工作树里跑，产物写产物目录）。主会话在 finish 第 1 步与第 3 步派它：`handoff dispatch --template finish-check --prompt "<卡号> <基线说明>" --wait`，读回结构化结论。

弃选：
- **换版后冒烟读数也交它**：`handoff` 自身命令被权限门硬升级（B451/B460 规则层），只读熟练工跑不了 `handoff machines` / 账本读；冒烟由 B462 的换版脚本自验。
- **前端 vitest 也交它**：执行机的 detached 工作树没有 `web/node_modules`，`npm ci` 要联网且写工作树（只读形态不允许）；前端测试输出短，主会话本地跑。

## 落位三问

① 读写谁的权威数据：模板定义归账本 registry 的熟练工定义（已有 kind），仓内 JSON 是其源；本卡不新增数据。
② 谁消费：主会话经 `handoff dispatch --template finish-check` 消费（既有契约面）。
③ 同步还是异步：派发后 `--wait` 同步等结论（既有行为）。

## 用户故事

- **S1 定义**：仓内 `skills/handoff/skilled/finish-check.json`，`receiver: mimo`（linux-01，16 核，全量最快）、`mode: readonly`、`purpose: investigate`；提示词规定检查清单与回报格式（见下）。生产账本登记 `handoff template put finish-check --file …` → v1。
- **S2 检查清单**（提示词内容，执行者按序跑，每项给 通过/不通过/未跑+原因 与原始计数）：
  1. `gofmt -l $(git ls-files '*.go')` 须空；
  2. `go vet ./...`；
  3. `env -u CLAUDE_CODE_SESSION_ID go test ./... -count=1 -p 4`（输出全文写产物 `go-test.log`）；红的包单包复跑一次区分抖动；已知抖动清单写进提示词（opencode 包 `TestProbeReplayClassification/*`、`TestCoordinatorLaunchHonorsCancel` 并行负载下偶发红、单跑绿即非回归；`TestProductionHTTPClientCallersAreGatewayOnly` 仅嵌套 `.claude/worktrees` 下红）；
  4. 构建本树二进制到任务临时目录，`<bin> --help` 与各子命令 `--help` 对照 `README.md` / `README.zh-CN.md` 命令表：列出 README 里有而 `--help` 没有、或 `--help` 有而 README 没有的命令/参数；
  5. 若给了 BASE（`--prompt` 里写 `base=<提交>`）：`git diff BASE..HEAD` 新增行里的「未验证 / 下一期 / 留待 / TODO / FIXME / roadmap」等残余标记逐条列出，并核 `docs/roadmap.md` 是否已有对应条目（列「已入 / 未入」）；`CHANGELOG.md` 的 `[Unreleased]` 是否提到本卡（给卡号时）。
  回报格式：`## 结论`（每项一行：项名 — 通过/不通过/未跑 — 关键计数）+ `## 不通过明细` + `## 产物` + 末行 JSON 摘要。只读：不改工作树、不提交。
- **S3 使用说明**：`skills/handoff/SKILL.md` 熟练工节加 `finish-check` 一段（何时派、基线须已推送、合并后的树如何检查——合并提交先推临时分支 `finish/<卡>` 再派，或合并树与已检树同一 tree 时直接沿用，主会话记 tree 哈希）；全局 `~/.claude/CLAUDE.md` 熟练工条目补一句 finish 用它。`CHANGELOG.md` 记一条。
- **S4 真机**：用生产 `finish-check` v1 对一个已知结果的提交派一次（B453 分支 HEAD，独立审查第 1 轮已知：gofmt 空、vet 净、全量 67 包 ok 0 FAIL），结论与已知一致；人工工单 0 或接近 0（有则逐张记原因，属规则层缺口的落 roadmap）。

## 实现决定 / 测试决定

- L1 三行 plan：① 新建 `skills/handoff/skilled/finish-check.json`；② 改 `skills/handoff/SKILL.md`、`CHANGELOG.md`（与全局 `~/.claude/CLAUDE.md`，不入库）；③ 验收 = `go test ./internal/skill/ ./cmd/ -run 'Skill|Template'` 绿 + `template put` 后 S4 真机派发结论与已知一致。
- 无 Go 代码改动；若 S4 暴露规则层缺口（例如 `go build -o $TMPDIR/…` 或 `go test` 写 GOCACHE 被升级），不在本卡改权限门，落 roadmap。
