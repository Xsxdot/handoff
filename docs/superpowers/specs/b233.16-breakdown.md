## §0 待拍板清单（拍板者按此裁决）

> 每项都是「有两种做法、选哪种取决于偏好/契约取舍」的岔口。单上下文兜底：本稿不自批，以下全部待拍板。

### P1｜`handoff wait` 一次性消费点的具名入口缺口：退回 contract 加冻，还是把 RunE 认作组装点

spec 接缝表第 9 行（`docs/superpowers/specs/b233.16.md` §接缝清单）明列：「`cmd` wait 的一次性消费点（现状内联） | `waitCmd` RunE | 组合面（`+Attach`/`Status`）」，且 spec §方案要求「每个消费点必须落在可注入的具名符号上……不接受匿名内联调用作为终态」。contract §1 现状表也写「一次性消费点经收窄后的 `waitClient`」。但 **contract §2.1 冻结的 `cmd` 具名入口里没有它**，§5.3 具名入口清单（冻结条目 27–34）与 §5.4 编译期锁（条目 35）也不覆盖它。

实测反证：`cmd/wait.go:116` 在 `waitCmd.RunE` 内调 `newTargetClient()` 取**聚合** `*client.Client`，`:139` 直接内联 `cli.WaitEvent(...)`。该调用没有具名可注入符号，最小替身无法替换；`waitCmd` 是 `*cobra.Command` 包级 var，其 RunE 闭包无签名锁。因此 spec 接缝表这一条**没有被任何冻结物兑现**。

- **方案 A（退回 contract，加冻具名入口）**：contract 增冻 `runWaitOnce(cmd *cobra.Command, taskID, addr string, cli waitClient) error`（或等价具名符号），把 RunE 的一次性 `WaitEvent` + `autoSyncAfterWait` 收进去，并纳入 T1 签名锁与 §5.3 条目 27–34。优点：与 spec §方案「具名可注入」和接缝表逐条对齐；缺点：动冻结物，须退回 contract（不许边拆边加）。
- **方案 B（认定 RunE 为组装点，澄清不新开接缝）**：主张 RunE 是「构造客户端并立即消费」的组装点，聚合出现在组装点合法（spec §要变的事实 #2），一次性路径的实际可注入消费面由已冻的 `waitClient` 型 `autoSyncAfterWait`/`warnIfTimeoutBelowStall` 覆盖；在 contract 记一行边界澄清「wait 一次性 `WaitEvent` 直连属组装点，不另设具名入口」。优点：不动冻结物；缺点：与 spec §方案「不接受匿名内联调用作为终态」的字面冲突，且最小替身对 `WaitEvent` 这一跨机动作不可注入（`wait --timeout` 一次性路径的替身测试只能落到 RunE 外）。
- **推荐 A**（贴合 spec 明列接缝与「具名可注入」硬要求；B 会让 spec 一条明列接缝无冻结物兑现）。**请拍板。**

> **裁决（2026-09-11，协调者）：选 A——退回 contract 加冻具名入口。**
> 理由：①spec 接缝表第 9 行是本卡明列的消费点，「每个消费点必须落在可注入的具名符号上、不接受匿名内联调用作为终态」是 spec §方案的硬要求；②本卡已为 `reply`/`continue` 立过同型先例（RunE 内联 → 具名入口），`wait` 一次性路径不同待遇无正当理由；③`handoff wait` 是协调者最常用路径，缺口最可见，且 T2 最小替身对该跨机动作不可注入；④B 的边界澄清与 spec 正文冲突，属事后自证。
> 落地：**contract 轮 2** 增冻具名入口（建议 `runWaitOnce(cmd *cobra.Command, cli waitClient, taskID, addr string) error`，精确签名以 contract 冻结为准），把 RunE 的一次性 `WaitEvent` + `notify` + `writeEventLine` + `autoSyncAfterWait` 收进去；同步纳入 contract §2.1 冻结接口、§5.3 具名入口清单、§5.4 编译期签名锁（`cmd/execution_signature_lock_test.go` 加断言），并按 §4 形态跑一次配对还原的变异验证；C-0 / C-2 / C-3 三条边界澄清同轮回写。本稿的 P1 缺口在该轮回写后由 breakdown 复核轮重新核对。

### P2｜T2 的 CLI 替身注入形态：直接测具名入口 vs 新增工厂 var 缝走命令入口

spec §测试决定 T2 写「每个消费点配一个测试替身……替换跨机客户端后跑通现有用例（CLI 走命令入口……）」。但 `cmd/root.go#newTargetClient` 是**普通函数不是可替换 var**，cobra RunE 在内部构造聚合客户端后直接调具名入口；要让替身「经命令入口」进入，必须新增一个包内可替换缝。

- **方案 A（测具名入口，不动生产）**：CLI 侧替身直接调 `runStop` / `runReply` / `runContinue` / `dispatchTask` / `runUntilDone` / `runFollow` / `warnIfTimeoutBelowStall` / `autoSyncAfterWait` 等具名符号（它们已是 T1 锁定的注入面）；命令入口的 RunE 路径沿用既有 httptest 假 agentd 测试（如 `cmd/stop_test.go` 现形态）。优点：零生产改动、与 contract §7「既有命令测试的 RunE 路径不变；无需改测试入口」一致。缺点：未覆盖「替身经 cobra RunE 注入」。
- **方案 B（新增工厂 var 缝）**：把 `newTargetClient` / `targetClient` 改成包级 `var`（签名不变，仍返回 `*client.Client`），测试替换后走 RunE，实现替身「经命令入口」。优点：字面满足 T2；缺点：动生产文件、新增包内可变全局（并发测试需串行化）、且与 contract §7「缝签名不动」的克制取向相抵。
- **推荐 A**（contract §7 已明确 RunE 路径不变、`dispatchTransport` 系列缝签名不动，B 属多余扩张）。**请拍板。**

> **裁决（2026-09-11，协调者）：选 A。** 已冻的具名入口就是本卡定义的注入面（T1 签名锁锁的正是它们）；为测试给生产加包级可变全局，代价（并发串行化、全局状态、与 contract §7「缝签名不动」相抵）高于它买到的字面满足。命令入口路径继续由既有 httptest 假 agentd 用例覆盖，两类证据不互替（见 §4 假绿条）。

### P3｜T3 机械守卫的范围：仅 `cmd` vs 扩至 `agentd`/`ledgerstep`

spec §测试决定 T3 逐字写「扩展现有 `cmd/execution_surface_test.go` 的源码守卫」；contract §7 同款。但「执行面文件不得持聚合依赖」这条规则在三处都存在（`cmd/card_dispatch.go`、`internal/agentd/cardstep.go`、`internal/ledgerstep/runner.go`/`wire.go`）。

- **方案 A（仅 cmd）**：按 spec/contract 字面只扩 `cmd/execution_surface_test.go`；agentd/ledgerstep 由 T1 编译期签名锁覆盖。优点：范围最小、不新增测试骨架。缺点：源码守卫在三包不一致。
- **方案 B（扩至三包）**：在 `internal/agentd`、`internal/ledgerstep` 各加一条同构源码守卫。优点：规则三包一致；缺点：超出 spec 明写范围、多两条维护点，且 `ledgerstep` 的消费经结构字段（非函数参数），扫描判据不同。
- **推荐 A**（spec/contract 已定范围，T1 是「有牙」主形态，T3 仅补充；扩展属另一条缝，落 roadmap 更合适）。**请拍板。**

> **裁决（2026-09-11，协调者）：选 A——T3 仅 `cmd`。** 三包一致性由 T1 编译期签名锁承担（它比源码扫描更强、更难绕过）；把同构守卫铺到 `agentd`/`ledgerstep` 属另一条缝（`ledgerstep` 的消费经结构字段，判据本就不同），落 `docs/roadmap.md`。

### P4｜T3 白名单粒度与扫描判据（若 P3 选 A）

`cmd/card_dispatch.go` 同时含工厂 `targetClient`（返回 `*client.Client`，合法）与消费点 `dispatchTransport`/`dispatchTransportWithOpts`/`compensateCardDispatch`/`resolveCardDispatchDiscipline`（应收窄）。文件级白名单（整文件豁免）会漏掉消费点，且执行面五文件 `dispatch.go/wait.go/reply.go/continue.go/stop.go` 今日已无 `*client.Client` 字面（实测 grep 为空）。

- **方案 A（符号级白名单）**：扫描生产源码里 `*client.Client` / `client.New(` 的出现，白名单只放行工厂符号 `newTargetClient` / `newTargetClientNamed` / `targetClient`（`cmd/root.go` 与 `cmd/card_dispatch.go` 相关行），其余命中即红。优点：精确、能覆盖 `card_dispatch.go` 混合文件。缺点：文本扫描须避免把注释/字符串误判。
- **方案 B（AST/类型级检查）**：用 `go/types` 或 `go/ast` 检查执行面文件的函数签名是否引用聚合类型。优点：不受注释影响；缺点：比 spec「沿用既有形态」的源码扫描重。
- **推荐 A**（贴合既有 `TestCLIExecutionCommandsDoNotHandRollHTTP` 的源码扫描形态；白名单按符号/调用点而非整文件；扫描前剔除注释行以避误报）。**请拍板。**

> **裁决（2026-09-11，协调者）：选 A——符号级白名单 + 剔除注释。** 放行面恰为三个工厂符号（`newTargetClient` / `newTargetClientNamed` / `targetClient`）；扫描须跳过 `*_test.go` 与注释/字符串，并配一条**可变红**守卫（人为插入非白名单的聚合用法 → 测试必须变红），只断言「今日绿」不足以证明守卫有牙。
