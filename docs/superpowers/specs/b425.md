# B425 spec：codegraph/diffs/ 子目录积压 diff 对账与 ListViews 子目录盲区修复

> **级别 L2**（单子系统：codegraph 图工具链；diff 格式与对外 JSON 形态不变，ListViews 收紧属反静默既有错误路径，不动契约层）。
> **状态：待用户批准**（草案 2026-10-03；批准判决与日期批准后回写本行）。
> 调查读数全文：`docs/superpowers/notes/b425-recon.md`（同批提交）。

## 问题陈述

B379 台账 §7.8/§7.12 裁决 3 交接的两件事，机制与数据都已复核（读数见台账 §2/§3）：

1. **数据积压**：`codegraph/diffs/cards/B233.28-charter.json`（bad735a1，2026-09-15）是已完成卡 B233.28 的对账补齐视图（15 节点增/77 节点改/1 节点删/20 边增/39 边删），因躺在子目录里从未被吸收——15 个编排门面方法节点至今不在基线里。
2. **工具盲区**：`ListViews`（charter 仓 `graph/codegraph/load.go:47`，现状读数）用 `os.ReadDir` 只扫 `diffs/` 顶层、跳过目录条目；`views`（`cli.go:458`）与 `validate` 全视图校验循环（`cli.go:170`）都以它为清单——子目录里的视图对两者不可见。真仓复现：子目录文件在场，`views` 仍返回 `[]`。
3. **产生侧根因**：图对账/契约纪律条文写的是 `codegraph/diffs/<分支>.json`（charter 仓 `skills/recon/SKILL.md:16,27`、`skills/contract/SKILL.md:25`，现状读数），未规定分支名扁平化；B233.28 执行者照字面用带斜杠分支名落文件成子目录，其余卡执行者自行拍平。条文不改会重演。

不受盲区影响的面（消歧，防执行者误扩）：`absorb <view>` 与 `--view` 叠加走 `LoadDiff` 直连（`load.go:33`，斜杠路径可用），对账动作不被工具阻塞；`check` 基于基线不读 diffs 目录。

## 方案（含弃选与理由）

两段式（B379 同型，顺序为「工具先红、对账后绿」），外加一条纪律勘误：

- **第一段（charter 仓）**：`ListViews` 显式拒绝子目录（fail-closed）——遍历 `diffs/` 顶层遇任何子目录条目即返回错误，报文含目录名与修复指引（视图文件必须平铺顶层；视图名取分支名时把 `/` 拍平为 `-`）。`views`/`validate` 因此在任何子目录出现时立即报错。空子目录同样拒绝：git 不跟踪空目录，出现即本地残留，一次 `rmdir` 成本趋零，不设例外口径。`LoadDiff` 直连语义不动——历史遗留的子目录文件仍可被 absorb 显式点名吸收。
- **第二段（handoff 仓）**：对账直收——`codegraph absorb cards/B233.28-charter` 显式点名吸收（不经 ListViews），工具删除 diff 文件，`rmdir` 残留空目录，`views`/`validate`/`check` 回绿。
- **纪律勘误（charter 仓）**：`skills/recon/SKILL.md` 与 `skills/contract/SKILL.md` 的视图文件名条文补扁平化约定（`/`→`-`）与理由一行，跑 `scripts/regen_discipline.py` 同步纪律块。

**弃选一：ListViews 递归列出子目录**（view 名带斜杠进清单）。被弃理由：把一次性命名事故洗白成特性，违背 codegraph 反静默头号约定（check 无基准即拒执行的同族原则）；斜杠 view 名会渗进 views JSON 输出、validate 报文前缀、absorb 参数，为不存在的设计意图给下游埋成本；与既有视图命名惯例（扁平 dash 形态）不一致。若未来真出现组织化子目录需求，另走 spec 改判。

**弃选二：只对账不修工具**。盲区仍在，下一个带斜杠分支名的 diff 重演静默积压，且无 loud 失败让事故在最早环节暴露。

**弃选三：手工把文件搬到顶层改名直收、不动工具**。治标；产生侧条文缺口由纪律勘误收口后此选项更无必要。

## 实现决定（决策级落点）

- 拒绝口径在 ListViews 单点收口（load 层），views/validate 两个消费者自动继承；不在各命令层分别加检查。
- S1 → S2 顺序：工具先落地并在真仓变红（点名漏网文件），对账随后收口回绿。两段同卡同分支，main 不经过中间红态；真数据红同时充当 S1 真机证据。
- charter 仓实现从 master（82c6c216，含 B379 守卫）拉分支；二进制重建安装沿 B379 惯例（`go install` → `~/go/bin/codegraph`）。
- 版本对齐随 finish：charter 仓打 tag `graph/v0.10.3`，handoff 仓 `go.mod` bump `v0.10.2→v0.10.3`（B379 同款卫生）。
- 吸收后 baseline 的 meta.branch/commit 戳按工具既有行为（absorb 时点 HEAD），不手工改（B379 plan §4.8 先例）。

## 测试决定（真实入口与风险）

- 真实入口：codegraph CLI 的 `views`/`validate`/`check`/`absorb` 四命令，真仓（handoff 工作树）+ testdata 合成仓两层。合成仓只作局部验证；S1 真机红与 S2 四命令读数必须真仓。
- 风险一：nodesModified 77 条携带 2026-09-15 分支时态锚，吸收会以旧锚覆盖基线现行锚（其中部分可能被 B379 吸收的 diff 保鲜过）——`--stale` 计数可能上升。按 B379 裁决 1 读法如实记录，归 roadmap 重扫，不做数据干预。
- 风险二：`--view` 叠加查询在本卡不动；若 validate 闭合性报出未预见的容器/域问题，按 B379 §4.6 同款协议升级协调者，不现场手改基线。

## Out of Scope

- stale 存量的新鲜全量重扫（roadmap 既有行，B379 落账，本期不做）。
- 基线的任何手工编辑（absorb 是唯一合法入口，全局禁止项不变）。
- 子目录视图的组织化支持（弃选一，永不做，除非另 spec 改判）。
- codegraph 其它查询命令（context/chain/flow/sym 等）的子目录语义——它们不列 diffs 目录或经 LoadDiff 直连，无盲区。
- agentd/账本/charter 流程的任何改动（S3 只动条文两行）。
