## 待拍板岔口（集中清单，拍板者按此裁决）

**岔口一（重大，接缝缺口）：读模型数据供给不足——并入态投影缺失 + 终态房间无枚举源。**
契约 §4 要求「merged_into 非空时 ReadOnly=true」「终态卡沉底可列」，但冻结出站接口送不来这两份数据：
①`proto.Card` 无 Following/MergedInto 字段（亲读 internal/proto/ledger.go:15-32；merged 态只存在于 ledger.CardView.Following，agentd 视图投影 ledgerapi.go:149），collab 经 GetCard 看不见并入态；
②Facade.ListActiveCards 直通 ListCards{IncludeTerminal:false}（internal/ledger/api/api.go:37-50），终态卡房间没有列表来源。
- 方案甲（出稿倾向）：**一次 contract 微修订包**，随实现首卡同提交回 contract 节点补记——`proto.Card` 加 `Following string \`json:"following,omitempty"\``（cardWire 补一行投影；CardDetail 金样本用 omitempty，缺席不出键，亲读 contract_fixture_test.go 判定不受扰）；`client.LedgerClient` 加一直通方法（如 `ListAllCards(project)`＝ListCards IncludeTerminal:true 直通镜像，注释标注还债直通）。改的都是会话侧财产接口与既有 DTO 的可选字段，不动 §5 拍板与 §6 金样本。
- 方案乙：砍行为——merged 房间不置只读、终态房间不入列。直接违反 §4 冻结清单两条，需协调者明示豁免并回 contract 改清单。
- 方案丙：collab 经 EventsFromAsc 扫关系事件重建并入态/终态集。脆弱（事件≠现状）、违反「权威在卡字段」（拍板 5.1 同构判据），不推荐。

**岔口二：收件箱 decision 源的取数通道。**
§3.6 把三源编排冻在 gateway 层；但 spec §8.0 又有 blanket 句「凡本期新增的账本能力调用一律经新建的账本 api 门面」。gateway 收件箱要 ListDecisions(openOnly)：
- 方案 A（出稿倾向）：走 gateway 既有 `s.ledger *ledger.Store` 直调面（与同文件 GET /api/decisions handler 同形）。理由：ListDecisions 不是新能力（存量端点已在用），编排位置是 §3.6 明文冻结，「新增能力经门面」约束的是会话子系统的新增需求面（client.LedgerClient）；零新图边、零接口改动。
- 方案 B：给 ledger/api.Facade 加转调、gateway import internal/ledger/api。图上仍是 d_gateway→d_ledger 边但 entries 集合可能超声明面（现 entries=["ledger.Store","ledgerstep.StepRunner"]），有打红 check 的风险，且为既有能力绕一道弯。
- 方案 C：decision 源也经 collab（扩 client 接口）。违反 client.go 头注释「扩方法先回 contract」，且把裁决收件箱语义塞进会话门面，越界。

**岔口三：CLI `room inbox` 的三源获取方式。**
§3.5 说 CLI 五命令「直调 collab.Service，不经 agentd」；但 inbox 三源里的 ticket 源判据 `Hub.Watchers(taskID)==0` 是进程内快照——CLI 进程里 Watchers 恒 0，所有等待工单全部误上浮，判据失真。
- 方案 A（出稿倾向）：`room inbox` 单条命令例外走 agentd HTTP `/api/inbox`（d_cli→d_transport→d_gateway 既有边，`console`/`diff` 等命令先例），其余四命令照契约直调。Watchers 判据保真，零新图债。
- 方案 B：CLI 本地重算三源。接受 ticket 源全量上浮的失真并在帮助文本明示——把已知缺陷当功能发。
- 方案 C：编排逻辑下沉共享包。违反 §3.6「不进 collab 不进 ledger」的位置冻结，且 gateway/call 两处共享编排单元违背第六条按用例成编排。

**岔口四：A.1 未读游标存储介质。** collab 只持 client 接口、无库句柄，游标须自存。
- 方案 A（出稿倾向）：datadir 下 JSON 文件缓存（tmp+rename 原子写）。理由：拍板 5.4 已把游标降为纯缓存非权威，重启丢失无害且打开房间即自愈；免引入第二个数据库句柄。
- 方案 B：自开 SQLite 小表。耐并发写、可查询，但 collab 要多管一个连接生命周期，对纯缓存过重。
无论哪种：MarkRead 并发写必须原子（HTTP handler 并发到达），验收里钉死（见 C5 缺陷族栏）。

**岔口五：A.2 LastMessage 预览。** 冻结 `proto.RoomSummary`（internal/proto/rooms.go:56-68）没有 LastMessage 字段，wire 形状受 §6 金样本与文件头「改形状先回 contract」管辖。

- 方案 B：回 contract 给 RoomSummary 加字段+双侧金样本扩面。为一个 plan 附区装饰项动冻结物，不值。

**岔口六：Consume 对无效 seq 的错误面。** 契约哨兵集五个已冻结，无一贴合「seq 不存在/非 room_message」。

**岔口七：欠账 #10 纪律块文本修订的运行期写入归属。**

## 四、缺陷族对抗审查（基线五族 + 序列化边界 + 枚举白名单 + 承重安全属性 + webview 候选）

**1. 生命周期/状态机中断**
- agentd 中途重启：租约行留库 TTL 自愈（live=false），绑定值持久无损；收件箱 ticket 源 Watchers 归零短暂误上浮——拍板 5.4 附注明示接受的代价，观察项入真机清单 #3。孤儿资源：driver_leases 过期行永不清理？——表按 session 一行、upsert 语义，过期行无累积增长（同 session 覆写），可接受并注释言明。
- collab JSON 游标并发写：MarkRead 原子写钉进 C5 验收；进程崩溃留 tmp 文件——rename 原子性保证主文件完好，tmp 残屑无害。
- RunOnce 中间态检测竞态：卡状态读取与转等人落卡在同一 mutate 串行域内（C2/C3 同形），检查与动作无窗口。
- C6 新端点在 s.ledger==nil 时随 withLedger 503 降级（验收已钉）。
- 结论：有已识别风险面，全部落在可见机制（TTL 自愈/原子写/mutate 串行/降级路径），无静默孤儿。

**2. 静默失败/误导报错**
- 最大残余口子：C4 占位 return（未接线分支返回 ErrKindNotAllowed 冒充执法通过）——验收明令消灭占位+grep 检查；这是「报拒绝但没执法」的假绿温床，Ticket 0 测试已反防，本轮换正断言时保留其反向精神。
- Consume 无效 seq 的静默 nil（岔口六方案 A）——有意选择的幂等语义，测试+注释锁死，Pending/Mentions 只列未消费兜底；若裁方案 B 则有哨兵可报。
- HTTP 错误映射逐哨兵断言防「500 吞哨兵」；CLI rebind 冲突非零退出防脚本误判成功。
- ListRooms 数据源失败传播：C6 handler 退化 503 不吞错（与 withLedger 同形），C8 前端展示错误态非空白列表。
- 结论：三条残余口子各有明确防线与归属卡。

**3. 跨平台假设**
- 时间：LastActivity/ExpiresAt 走 store tval/toTime 两方言抽象与 RFC3339 wire；时钟判定全部注入式，无 sleep 依赖 CI 速度。
- carrier 字符串不透明化（澄清一）正是消除平台/格式假设的动作；JSON 游标文件路径走 datadir 既有解析。
- 无进程组/信号/webview 新假设；web 布局差异留真机清单 #1。
- 结论：无，因为唯一平台敏感物（时间、路径）已被既有抽象隔离，且本卡主动消除了 carrier 格式假设。

**4. 假红/假绿测试**
- 双时钟假绿温床：live 判定跨 collab 包内时钟与 Store 注入时钟，夹具若各用各的钟，「live 翻转」断言可能在真实世界失效而机内恒绿——C5 验收钉死两侧拨同一可拨时钟源。
- 占位翻绿：见族 2 第一条；TestCoordinatorKindsNotForgedBySkeleton 换正断言时必须保留「占位即红」的反面精神（变异：恢复任一占位→矩阵某支红）。
- Watchers 夹具：hub 订阅数是进程内状态，测试经真实订阅/退订翻转而非 mock 返回值——防「mock 说 0 就 0」锁不住生产行为。
- jsdom 断言锁数据流与文案，不锁布局（既有教训）；PG 方言只有 DDL 路径真机可验（清单 #6），SQLite 全绿不外推 PG 行为。
- 变异复验建议三点：去 RecordMessageConsumed 查重→恰好一次组红；writer 矩阵去绑定比对→条 4/7 红；mux 缺席断言去掉 Pointer 拒收→路由断言红。
- 结论：四个温床各有独立防线，变异清单随稿下发。

**5. 门禁绕过**
- Pointer 双门：Send 一律拒收（编译期+运行期）+ mux 注册表缺席断言（部署期）——TOCTOU 无（路由表静态注册，无并发窗口）。
- 直调禁令硬闸：collab 生产零 ledger import 由 graph check --view 执法（C4/C5 验收含跑）；gateway/CLI 只经门面实体（预定声明 entries 逐字）——穿透即超预算变红。
- 存量直调不扩大：C6 decision 源若采岔口二方案 A 是同面既有能力的再消费（非新方向非新 entries）；ticket 源走既有 d_gateway→d_orchestration 边（budget 321 内）；无任何新穿过 legacy 直调的新增能力调用。
- actor 伪造面：HTTP actor 服务端注入不经请求体（§3.5 冻结）、CLI 注入 cli:<user>@<host> 既有约定——user kind 的绑定值对抗（C4 条 7）防协调者伪装用户。
- 结论：有一个待裁决的通道选择（岔口二），无绕过；全部写路径共享 mutate/门面两道既有关卡。

**序列化边界（命中）**
手写投影全清单：①RoomMessage wire 双侧金样本已冻（Ticket 0，实现轮禁改）；②InboxItem.Payload RawMessage 三源 gateway 手搭投影——C6 集成冒烟含响应解码回 InboxItem 的 roundtrip 断言（可空字段缺失 vs 零值分辨：omitempty 键缺席断言在金样本内）；③RoomSummary.LastActivity time.Time↔TS string——孪生夹具覆盖一条真实序列化边界，roundtrip 属性测试推荐落点（随机构造时刻，断言 encode∘decode 恒等）；④若岔口一裁方案甲，cardWire 加 Following 投影一处+agentd 既有视图投影另一处，两处同步断言进 C1/C6 验收；⑤CLI stdout 人读文本非机器契约，不设金样本（A.3 排版自由）。
链路无遗漏投影点；②③构成穿过真实序列化边界的回归，满足「两端各自有测试≠链路有测试」。

**枚举新值过既有白名单（同构命中）**
- EvRoomMessage/EvMessageConsumed 已进 types.go 受控词表（charter 轮办结）；下游白名单核查：Go 侧无 event-type switch 白名单（appendEvent 泛化存储，亲读）；web 侧 eventKind（CardDrawer.tsx:204-209）未知类型兜底 'system' 泛化渲染——room_message 流入卡 timeline 显示为系统行，无通道分裂；timeline 专项样式属「对既有 timeline 语义改动」被 spec Out of Scope 禁止，不做。

- 结论：全部新枚举值有登记点与锁定测试，无中间白名单挡死风险。

**承重安全属性有测试锁住（命中）**
- 恰好一次消费：C2/C5 查重变异红；换绑剥权：C1 覆写+C4 ErrNotWriter 合取断言；书写者执法：C4 矩阵全支；pointer 仅系统：双门断言；白名单单点：Send 唯一写入口（Pointer 例外）由 mux 缺席断言背书。每条均有能变红的测试对应，acceptance 变异复验有靶子。

**webview/平台表现差异（候选第六族触发判定）**
