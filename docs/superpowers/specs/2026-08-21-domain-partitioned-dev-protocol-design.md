# 分域开发协议：契约先行的拆解流程与工作台落地

> 2026-08-21 brainstorm 定稿，同日按评审意见修订：协议正文通用化（不特指任何项目）、
> 子卡扇出升为立项能力、递归定为子卡机制的组合性质。
>
> **协议是通用的**：适用于任何按「子系统=大领域、接口协作、调配层收口」组织的项目。
> 工作台（B156）是协议的通用承载平台，服务未来所有项目的开发，不只是 handoff。
> 项目接入协议需提供「项目实例化清单」（§6）。handoff 与 tk 仅作为动机证据（§1）
> 与实例化样例（附录）出现，正文规范不依赖它们。

---

## 1. 背景与动机（证据来自两个真实项目，结论是通用的）

两个痛，根因不同，处方不同，本协议同时治理：

**痛一：写错（「一天写代码，六天改 bug」）。**
案例实测（handoff backlog 182 条）约 70% 是缺陷修复，按根因聚类后高度集中于少数
**缺陷族**（生命周期/状态机、静默失败、跨平台假设、假红测试、门禁绕过五族，详见附录 A）。
关键发现：这些 bug 几乎全部长在**接缝**上，根因不是执行者理解不足或实现错误，而是
**接缝行为在 plan 阶段根本没被指定**（进程中途重启谁收尾、错误如何传播、平台差异下
该发生什么）。独立代码质量评估（8/10）证伪了「屎山」假设：问题不在修法，在 bug 本可以
少产生一半——欠掉的规格在验收时一条条变成 backlog 还回来。

**痛二：写慢（项目变大后 plan 与执行速度崩、上下文消耗巨大）。**
精确说不是「理解不足」，是「理解不可复用」：每个任务从零重建对全系统的理解，重建成本
随代码量线性上涨，且每次都付。案例量化（tk）：代码总量 21.5 万行，契约层仅约 1.2 万行——
plan 写作者只读契约层时上下文压缩 18 倍。

**关键前提与关键反例（均来自 tk 实测）**：9 个子系统跨域触碰他域私有代码的违规数为 0，
证明编译器+目录约定能真实锁死大领域边界——这是分域派发的地基；同时单个域（nova）
长到 14 万行、占 66%，内部按层横切、小领域只存在于文件名前缀——域内失去局部性，
域 ticket 上下文下限数万行。故协议必须含域内递归规则（§9），否则外层白守。

## 2. 核心判断（决策依据，验收时可回溯）

1. **上下文局部性是代码局部性的下游。** 「agent 只看域内上下文」的前提是存在编译器
   强制的边界，边界内不看外面也能被正确理解。边界没立起来之前谈分域派发是空话。
2. **补偿机制不如恢复局部性。** 扫描代码生成的知识库是无主派生物，静默漂移、需专人
   维护，且它补偿的是「代码失去局部性」——直接恢复局部性（拆包、锁边界）更便宜。
3. **mock 的可信度取决于接缝对面是谁。** 对面是自有代码：契约即全部真相，mock 便宜且
   有意义；对面是外部现实（子进程、OS、版本库、网络、平台）：mock 编码的是假设，而
   缺陷史证明假设恰恰是出错的地方。据此把域分为**逻辑域**与**边界域**，验收规则不同（§7.3）。
4. **域的尺寸本身是架构约束。** agent 开发流让巨型包的成本当场可计量（ticket 圈不出
   文件集、token 消耗上涨），拆分理由从「人的认知负担」升级为硬性红线。

## 3. 明确不做什么

- **不建常驻领域 agent。** 域 ticket 就是普通 dispatch 任务，任何 executor 领到即天然
  只需加载该域。没有 agent 编排、画像、生命周期要维护。
- **不建扫描式代码知识库。** 沉淀只允许进 §4 的三层（编译器/测试/Review 强制），
  无主派生物一律不建。
- **不做大爆炸重构。** 存量巨型域走绞杀式迁移（§9）。

## 4. 沉淀的三层栈

| 层 | 载体 | 漂移风险 | 表达什么 |
|---|---|---|---|
| 编译器强制 | 契约层的类型、接口、语言级可见性边界 | 零，违反即报错 | 形状：签名、数据结构、可见性 |
| 测试强制 | 契约夹具（前后端共享 fixture）、录制回放、架构测试 | 漂移即红 | 行为样本、import/依赖规则 |
| Review 强制 | 每域一页的领域文档（§5） | 靠 DoD 纪律 | 类型说不出的一切：为什么、不变量、时序、故障语义 |

禁止第四层（扫描产物）。三层各司其职，不互相替代。

## 5. 领域文档规格（Review 强制层）

每个大领域一份，放在该域根目录。**目标体量一到两页**，只收稳定知识。

**必含六节：**
1. **职责与边界**——做什么、明确不做什么。
2. **契约语义补充**——契约层类型表达不了的：幂等性、错误语义、阻塞行为、排序约束。
3. **不变量**——必须恒真的陈述（如「事件与状态不得失配」「单写入者」）。
4. **时序与故障语义**——重启/崩溃窗口内的行为、谁负责清扫、补偿路径。缺陷族对抗审查
   （§7.1）直接对着本节核对。
5. **外部现实假设清单**（边界域必填，逻辑域可写「无」）——哪些假设 mock 验不了、
   必须真机；对应真机清单模板。
6. **领域词汇表**——统一语言，术语与代码标识符对照。

**禁入清单（与必含同等重要）**：实现细节、文件清单、流程步骤复述、任何随代码周更的
内容。一旦开始收易变物，本文档即滑向无主快照，宁缺毋滥。

**更新纪律**：任何改变域行为的变更，域文档更新属于同一变更的 DoD；review 时文档与
代码一起审。工作台落地后由域卡 Gate 硬化（§8）。

## 6. 项目实例化清单（项目接入协议时一次性提供，此后随演进维护）

协议正文与工作台模板是通用的；**项目差异全部收敛在这份清单里**：

1. **契约层声明**：本项目「契约层」指哪些路径/产物（例：Go DDD 项目为各域 `api/` +
   模块地图；前端项目可为类型定义 + API schema）。拆解节点的上下文即按此声明装配。
2. **领域清单与域文档**：大领域列表、各域的领域文档（§5 规格）、域类型标注
   （逻辑域/边界域）。
3. **缺陷族清单**：本项目的接缝失败模式清单，作为对抗审查（§7.1）的设问依据。
   **来源是本项目自己的缺陷史**（backlog/事故记录聚类），新项目可从参考样例（附录 A）
   起步；每当出现不属于既有族的新 bug，归族并回写清单——清单是活的。
4. **架构测试**：锁死域边界 import/依赖规则的测试（违规即红）。
5. **参数**：域尺寸红线、升格判据阈值、子工作流深度上限（默认值见 §9/§8，项目可覆盖）。

## 7. 分域拆解协议（流程主干）

```
拆解（缺陷族对抗审查）→ Ticket 0（契约落地为骨架 commit）
→ 扇出域子卡（各自出 plan、执行、域内审阅验收、更新域文档）
→ 集成卡（跨域接线 + e2e + 整体验收）→ 终审
```

### 7.-1 两档：先选档再走流程（2026-08-21 首次试点后补入）

**协议的成本随触及域数量固定**（拆解必须覆盖所有域），**收益随域内深度增长**。
两者的交叉点决定该走哪一档：

| 档 | 形态 | 适用 | 串行段 |
|---|---|---|---|
| **轻档** | 拆解 → 契约冻结 → **单轮实现** → 验收 | 宽而浅：多域但每域改动小（加个方法/端点/字段） | 与老流程同为 2 段派发 |
| **重档** | 完整扇出（§7.3 域子卡并行 + §7.4 集成卡） | 宽而深：单域工作量大到一个执行者一轮装不下 | 4 段 |

**选档判据：单域工作量是否超过固定成本。** 超过走重档，否则走轻档。

实测依据（B167，四个域、每域改动都浅）：重档固定成本约 70 分钟（拆解 35 + 拍板 5 +
契约冻结 15 + 集成 15），可并行部分只有约 20 分钟——**并行救不回来，因为固定成本比
被并行的部分还大**。同一需求老流程约 40 分钟。当每域工作量升到 60 分钟量级时对比反转
（老流程 250 分钟且单执行者上下文可能装不下，重档 130 分钟）。

**两档共享的是前半段**（拆解 + 契约冻结），差别只在后半段扇不扇出。
不要因为选了轻档就跳过契约冻结——试点数据表明**价值在契约那半段**（见 §12）。

### 7.0 拆解（协调者，上下文 = 契约层）

输入：需求 + 项目实例化清单装配出的契约层 + 各域领域文档。产出三样：
1. 触及域清单，每个域标类型（逻辑域/边界域）；
2. 各域**契约增量**——契约层的精确 diff，精确到可编译；
3. 子卡清单 + 依赖 DAG。

拆解时执行**上下文预算检查**：若某张域卡圈不出有界文件集，即为该域需要竖切的信号——
plan 里先插竖切还债卡，再派功能卡（§9.5）。

**契约定义应尽量前移进 spec 阶段**（2026-08-21 试点后补入）。拆解之所以必须跨所有域，
是因为**接缝缺陷不属于任何单个域**——它存在于域与域之间，没有哪个域「只看自己的契约」
能发现它（实战原型见 §12 的在飞门禁案例）。但这次跨域的思考**本该和用户一起做**：
spec 阶段的对话正是在跨域思考，把契约定义挪过去不是新增一轮，是把已经在发生的对话用满。

前移后拆解分成两段，只有前一段需要用户：

- **spec 阶段（与用户）**：定契约的**语义与接缝**——哪些规则跨域、在哪一层收口。
  这是判断，也是拆解里唯一真正承重的部分。
- **契约落地（可派，轻）**：把语义翻译成精确签名/端点/类型。纯机械查证。

**注意二者的分界不是随意的**：spec 阶段定得了语义与接缝（那是设计决定），
定不了精确签名（那是代码事实，得查）。硬要在 spec 里写死签名会写出对不上现状的契约。

### 7.1 缺陷族对抗审查（拆解的一部分，不可省）

对每个触及域，取**项目实例化清单里的缺陷族清单**，对照该域领域文档「时序与故障语义」
节逐族设问（样式：「本操作中途宿主进程重启会怎样？谁负责收尾？」，完整样例见附录 A）。
审查结论写进契约增量与各子卡验收栏。此步是「六天修 bug」被砍掉的位置，缺失即 plan
failure 级错误。

**新增字段必问「序列化边界」**（2026-08-21 实战补入，属静默失败族）：本次改动新增的
数据字段，从产生它的地方到消费它的地方，中间**每一处手写的序列化/投影**都必须列进
文件清单并加断言。手搭的 map、DTO 转换、CLI 自己拼的输出、跨语言契约的另一侧——
这些地方编译器不管，字段漏了不报错、测试也照绿。

判据：**「两端各自有测试」不等于「这条链路有测试」。** 若产生端测试测的是内部结构、
消费端测试用的是自造夹具，中间那根 wire 就是零覆盖——必须补一条穿过真实序列化边界
的回归测试（断言时用可空类型区分「字段缺失」与「值为零」，两者的症状完全不同）。

**新增枚举值必问既有白名单**（2026-08-21 实战补入，属静默失败族）：本次改动新引入的枚举取值（附件 kind、purpose、状态名等），凡流经既有校验器/白名单/switch 的，每一处都列进文件清单并确认已登记。白名单在设计处不报错、只在使用处拒绝，两端测试各自绿。实战原型：domain 流契约闸的 contract kind 被 attachmentKinds 挡死，Web 无法过闸而全链路测试无一转红。

实战原型（本协议第一次试用时踩到）：新增 `CardView.ChildrenTotal/ChildrenDone` 派生
字段，Store 侧测试绿、前端组件测试绿，但 HTTP 层 `handleCardsList` 手搭 map 没带上
这两个键——功能端到端不通而全链路测试无一转红。plan 的文件清单漏了那个序列化端点，
根因在拆解，不在实现。

### 7.2 Ticket 0：契约冻结

只做一件事：把审查过的契约增量落地为**可编译的骨架 commit**——契约层 diff + 空实现
stub，合入基线分支。域文档相关条目更新随行。此后所有域子卡基于该 commit 开分支，
契约错配在编译期爆炸而非集成时。契约是代码，文档是随行产物，顺序不可颠倒。

### 7.3 域子卡（意图层，可并行扇出）

每张 = 一个独立 dispatch 任务（独立分支/worktree）。**四段式**正文：

1. **契约**：引用 Ticket 0 的 commit + 本域相关 diff + 领域文档相关条目；
2. **意图与为什么**：要达成的行为与动机，不写实现步骤；
3. **验收**：按域类型二分——
   - 逻辑域：域内测试闭环，邻域一律 mock 其契约层接口，机内可跑；
   - 边界域：机内只验契约形状（含录制回放，见下）；行为验收写成显式
     **「真机清单，归协调者执行」**（派发出去的 plan 不得自己驱动派发基础设施本身）；
4. **入口指针**：相关文件入口，省探索时间。

「怎么实现」留白：域执行者在自己域内自行出 plan——这是域内上下文有界的兑现方式。
域文档更新属于子卡 DoD。

**mock 红线**：只在契约层接缝 mock 一层，禁止深 mock 内部；mock 中任何关于外部现实的
假设必须对应一条真机清单项，否则等于用测试给假设盖章。边界域优先用**录制回放**
（真实报文录成 fixture 回放）替代手写 mock——现实的快照优于假设的编码，且可进 CI。

### 7.4 集成卡（收口）

跨域协作逻辑**只允许**出现在这里：调配层接线 + e2e。整体验收含边界域真机清单的执行。
子卡全绿不等于完成，集成卡是必经节点。

### 7.5 终审

整分支终审 + 人工 Gate。合并进主线的决策留协调者/用户，不自动。

## 8. 工作台落地（B156 承载，平台能力对所有项目通用）

### 8.1 「分域开发」工作流模板

映射到现有 `WorkflowDef`/`NodeDef` 模型（Dispatch/Template/Verdict/MaxRounds/OnFail/Gate）：

| 节点 | 能力配置 | 说明 |
|---|---|---|
| 拆解 | Dispatch=on（模板=domain-breakdown，spec-draft 角色）、无 Verdict | 产出域清单/契约增量/子卡清单提案；**人工把卡移进下一列即拍板**，Decision 闭环挂此节点 |
| 契约冻结 | Gate=contract 附件、Dispatch+Verdict（模板=domain-ticket0，判据=stub 编译绿）、MaxRounds 2 | 拍板过的契约落成可编译骨架 commit |
| 域实现 | 纯人工列 | 扇出子卡归协调者（自指红线）；子卡各绑自己的工作流并行走 |
| 集成 | Gate=聚合闸（全部直接子卡完结）、Dispatch+Verdict（模板=domain-integration）、OnFail=域实现 | 调配层接线 + e2e |
| 终审 | Gate=验收判据、Dispatch+Verdict（review-generic + finishing 覆盖）、HumanBases=[main] | 合并决策留人 |

2026-08-21 落地时与首版的差异：拆解/契约冻结拆为两节点，人工拍板（移列+contract 附件）显式插在中间——归属依据见工作台基准 §5。

### 8.2 子卡扇出机制（立项做，引擎一等能力）

「一卡开多卡」本就在工作台路线图上，直接立项，不走临时方案。设计要点：

- **父子边**：卡携带 parent card id；子卡是**完整的一等卡**，不是特殊「子任务」类型——
  有自己的工作流、事件流、抽屉、账本记录。
- **聚合闸**：父卡所在节点可配「等全部子卡到达终态」的过闸条件；任一子卡失败时按
  父节点 OnFail 路由（重派该子卡 / 整组回拆解 / 升级人工）。
- **看板呈现**：父卡可展开子卡树；子卡计数与状态徽标在父卡上可见。
- **账本**：父子边入账本，审计链可回溯「这张卡为什么存在（源自哪次拆解）」。

### 8.3 递归子工作流（设计决策：组合性质，不是独立功能）

**子卡可绑定任意工作流模板——包括「分域开发」模板自身。** 递归由此免费获得：
超大域的域子卡自己再走一遍拆解→契约→扇出，即「域内再分域」（§9 的过程形态）。
不为递归建第二套机制，只加两个护栏：

- **深度上限**：链路上「分域开发」嵌套层数默认上限 3（项目实例化清单可覆盖）；
  超限的卡拒绝创建并提示先竖切。
- **环检测**：父链上出现同一 (工作流模板, 目标域) 组合即拒绝——防止拆解节点把活
  原样再拆给自己。

### 8.4 域卡 Gate 增补与健康度

- 域卡过闸检查项：「本域领域文档是否需要更新、已更新」——把 §5 的更新纪律变成硬门。
- **域健康度指标**（backlog idea）：账本按域记录 ticket 的上下文/token 消耗，
  趋势上涨 = 域在腐烂的早期信号，早于任何 code review。

## 9. 域内递归规则（防「单域巨型化」）

架构自相似：**小领域之于大领域 = 大领域之于系统**。外层三件套原样下沉一层：

1. **小领域升格为真实的包 + 语言级私有边界**（Go：嵌套 `internal/`，仅小领域子树
   可见——与外层同一个编译器机制，零新发明）。每个小领域是竖片（自带自己的分层），
   对外只露薄契约。
2. **跨小领域调配只许在域的调配层**——镜像外层「跨大领域只许在顶层调配层 + 集成卡」。
3. **架构测试钉住 import 规则**，违规即红。

**两条过程绊线**（防「以后再说」）：

4. **升格判据**：一个文件前缀家族 ≥5 个文件、或需要自己的持久层+服务层对，必须升格
   为包。写进后端架构 skill 的模块模板，使「新小领域 = 新子树」成为缺省形态。
5. **域尺寸红线**：单个可派发上下文单元超过约 2~3 万行（项目可覆盖），拆解节点必须
   拒绝直接派功能卡，先插竖切还债卡。红线动机是上下文预算，不是审美——它决定
   agent 流的快慢与成本。域内再分域的执行形态即 §8.3 的递归子工作流。

**存量迁移**：绞杀式。每张碰到某前缀家族的 ticket 附带「本家族升格为包」一步
（童子军军规），或按小领域立专门还债卡。竖切一个家族是小时级，缠死后是周级。

## 10. 落地物清单（本 spec 的后续，各自独立立项）

1. **子卡扇出机制**（§8.2）+ **递归护栏**（§8.3）：引擎能力，优先做——模板依赖它。
2. **「分域开发」工作流模板**（§8.1）：内建模板 + 拆解/域卡/集成三个 prompt 模板。
3. **skill 修订**：
   - writing-plans 伴随规则：拆解阶段强制缺陷族对抗审查 + 上下文预算检查 + 域类型
     标注（缺失即 plan failure，与 instrumenting-code 同级）；
   - 后端架构 skill 增补：§9 域内递归规则、升格判据、域尺寸红线、领域文档规格（§5）。
4. **backlog 新条目**（取号按汇流点纪律）：子卡扇出机制（立项）；域健康度指标（idea）。
5. **试点**：下一个横跨多域的真实需求走一遍全协议（含一个边界域），以「域卡平均上下文
   消耗」「集成卡阶段新发现缺陷数」两个数验证收益。

## 11. 验收判据（协议本身的）

- 试点需求的 plan 阶段上下文 ≈ 契约层 + 域文档量级（对照：全量代码）；
- 域子卡执行期间零次跨域私有代码触碰（架构测试背书）；
- 集成阶段暴露的契约错配为 0（应全部在 Ticket 0 编译期暴露）；
- 边界域子卡的真机清单在集成卡完成前全部执行完毕，无「事后补验」。

**补一条硬判据（2026-08-21 试点实测后补入）：真机验收不可省，且不可用「测试全绿」替代。**

理由不是谨慎，是结构性的：**API 事实可以静态核验，行为事实不能。**

- **API 事实**（方法签名、错误哨兵是否存在、某个写入方法叫什么）——grep 就能确认，
  「判据先在基线上跑」这条纪律罩得住它。
- **行为事实**（这个事件到底走不走镜像、那个字段实际由谁写入、某状态下真实响应是什么）
  ——只有把系统跑起来才知道。**测试夹具里每一个关于行为事实的假设，都是一次没人验证的
  断言**；夹具编码了错误的现实时，测试全绿、变异复验照样转红，因为它们忠实地验证了
  一个不存在的世界。

实战原型（B167）：在飞门禁功能完全不生效，而单元测试全绿、变异复验也红——夹具假设
`dispatched` 会以镜像事件出现（现实中它是账本原生事件），于是判定恒为「不在飞」。
机内所有关卡全部通过，只有真机复现把它揪出来。

**操作纪律**：顺序固定为 **复跑 → 变异复验 → 真机验收 → 才归档**。
验收前归档会关掉续接通道（`continue` 撞 409），只能重派并丢掉执行者上下文。

## 12. 首次试点回写（2026-08-21，载体 B167 跨流迁移）

协议第一次完整跑通的实测记录。**结论按「协议主张是否被证实」分三类**，
后续修订以此为基线，不要凭印象改。

### 12.1 耗时实测

| 环节 | 耗时 | 性质 |
|---|---|---|
| 项目实例化清单（handoff 首次接入） | 13.6 min | **一次性**，不计入稳态 |
| 拆解 | 35 min | 每需求一次，**应前移进 spec**（§7.0） |
| 契约拍板（协调者 + 用户） | 5 min | 每需求一次，**应前移进 spec** |
| 契约冻结（Ticket 0） | 55 min | 每需求一次 |
| 单轮实现 + 一次退回修复 | 32 min | |
| **真机验收** | ~12 min | **抓到 1 个致命缺陷** |
| 缺陷修复 + 复验 | ~20 min | |

老流程同一需求约 40 分钟（写 plan 10 + 实现一轮 30）。

### 12.2 被证实的主张

**① 契约先行确实把接缝缺陷前移了。** 拆解阶段自行发现「CLI 直连账本，看不见 agentd
进程内的在飞态」——同一条规则在 HTTP 通道能执行、CLI 通道执行不了。这个缺陷
**不属于任何单个域**，三个域各自履约都正确而系统语义是破的。契约拍板把门禁下沉到
Store 事务内后，接缝直接消失：API 子卡少一项工作，CLI 子卡的「走 HTTP / 承认能力不同」
二选一不复存在。**契约拍板把跨域协调工作变没了**，这是「契约先行」最实的一次兑现。

**② 契约冻结之后的实现，行为一次做对。** 实现轮退回的唯一一条是代码组织问题
（gate 检查在两处重复），不是行为缺陷。

**③ 真机验收不可省。** 见 §11 的补充判据。

### 12.3 被证伪的主张

**扇出并行不是普遍收益。** 对「宽而浅」的需求（多域但每域改动小），固定成本大于
可并行部分，扇出反而更慢。故 §7.-1 补入轻重两档，**扇出改为按需启用而非默认**。

试点选题本身也是一次教训：B167 被选中的理由之一是「规模适中」，而这恰恰是错的——
L3 重档要用在「每个域都重到一个执行者装不下」的需求上。**「规模适中」是轻档的信号，
不是重档的信号。**

### 12.4 附带产出（都已落地）

- **账本 wire 接入既有契约夹具机制**：`internal/proto` 的 fixture 生成器覆盖 35 个类型，
  而账本域的 `CardView`/`CardDetail`/`NodeDef`/`FlowDetail` 一个都不在里面——
  这是全仓唯一没有 wire 契约强制的区域，2026-08-21 踩到的两个 wire 缺陷全落在这块。
  现已接入，两层防线实测有效：改 Go 侧 JSON 键名 → Go fixture 测试红；
  用 `-update` 刷绿蒙混 → 前端镜像断言仍红。
- **判据盲区**：`internal/agentd` 19,870 行、61 源文件、零子包，**域尺寸红线与升格判据
  同时够不着它**（差 130 行不命中；最大前缀家族只有 3 个文件）。原因是升格判据抓的是
  「包内长出了家族」，对扁平命名的大包失效。补充判据见项目实例化清单
  （`2026-08-21-handoff-instantiation-checklist.md` §5.1）：**单包源文件数 ≥ 40 且无子包，
  拆解时必须显式回答「还能圈出有界文件集吗」**——命中不等于必须拆，但必须回答。
  该判据在本项目先行验证，成熟后回写本协议 §9。

### 12.5 待修的协议内部矛盾

`domain-breakdown` 模板要求执行者做缺陷族对抗审查，而工作台基准 §5 归属表把该项
划给「主会话 + 用户」。**实际可行语义是「执行者出稿、主会话拍板」**（与契约增量同构）。
两处措辞已按此统一（2026-08-21）。
