## 5. 冻结清单

每条单独可判 pass/fail。

### 5.1 身份

1. 执行实例身份是 `proto.Task.ID`。本卡不另造 Execution 实体。
2. Ask 尝试身份是 `Ticket.ID`。未答重放且原生 `QuestionID` 非空时，`Ticket.ID` 必须等于 `NamespacedTicketID(taskID, QuestionID)`。
3. 旧 Ask 已答、原生又用同一 `QuestionID` 提问时，必须新开 `Ticket.ID`，不得复用已答工单 id。
4. 审批请求对外工单 id 必须等于 `NamespacedTicketID(taskID, PermissionID)`。
5. `RespondAsk` 必须携带 `TaskID` 与 `TicketID`。只给 task ID 查找「当前待答问题」不合法。
6. `NamespacedTicketID("T1","perm-1")` 的字节结果是 `T1:perm-1`。
7. `NamespacedTicketID("T1","a:b")` 的字节结果是 `T1:a:b`。
8. `NativeIDFromTicket("T1", NamespacedTicketID("T1", native))` 必须等于 `native`。

### 5.2 Send 与 RespondAsk

9. `Adapter.Send` 不得消费任意挂起 Ask。
10. `AskResponder` 不是 `Adapter` 的第六个方法。
11. OpenCode 路径调用 Ask 回程时必须类型断言 `AskResponder`。
12. 断言失败不得回退为 `Send`。
13. 原生问题仍挂起时，`RespondAsk` 必须回复该原生问题且不得因此新开回合。
14. 提问回合已结束时，`RespondAsk` 必须核对待答身份后以关联答案续接。
15. 本卡其它 harness 继续只实现现有五动作。

### 5.3 事件流

16. 本卡不新增 `EventType` 字面值。
17. `question` 必须可交付（唤醒 wait）。
18. `permission_request` 必须可交付。
19. `progress` 必须不可交付。
20. `delivery_failed` 必须可交付。
21. `completed` 必须可交付。
22. `turn_failed` 必须可交付。
23. `failed` 必须可交付。
24. `permission_auto_allow` 必须不可交付。
25. `approver_decision` 必须不可交付。
26. `permission_reuse` 必须不可交付。
27. 免审成功不得发布 `permission_request`。
28. 审批模型内部批准不得发布 `permission_request`。
29. 授权复用成功不得发布 `permission_request`。
30. 仅当审批服务无法自行形成有效决定时才发布 `permission_request`。
31. Ask 必须先落请求再通知订阅者。
32. 通知失败不得删除已落库的 Ask。
33. 内存 `Hub.WaitAnswer` 不是 Ask 的唯一事实源。

### 5.4 审批 client

34. `ApprovalClient` 定义在 `internal/executor`。
35. client 实例限定于单个 `Task.ID`，不得扩大到其它任务。
36. `StartReq.Approval == nil` 不得被实现方解释成全部免审。
37. OpenCode adapter 不得 import `internal/permgate`。
38. OpenCode adapter 不得引用 `agentd.Approver` 具体类型。
39. 审批实现不得 import `internal/executor/opencode`。
40. 具体 client 只在登记的组装点绑定。
41. `PolicySnapshot` 在 `Dispatch` 启动时解析一次并绑定该回合。
42. `PolicySnapshot` 在每次 `Continue` 开始时解析一次并绑定该回合。
43. 已在跑的回合不因运行中改配置、改上限、改免审表而更换快照。
44. `ApprovalClient` 对外状态只有 `allow` / `deny` / `pending`。
45. client 不得把 `Consult` 当作对外状态返回。
46. `Request` 在权限描述含 `TruncationMarker` 时不得返回 `allow`。
47. `Request` 在判据失败时不得返回 `allow`。
48. `Request` 在审批模型超时时不得返回 `allow`。
49. `Request` 在审批模型不可用时不得返回 `allow`。
50. `Await` 按 `ApprovalRef` 等待最终 `allow` 或 `deny`。
51. `Acknowledge` 的 `formed` 与 `delivered` 必须能区分。
52. `Acknowledge` 的 `delivered` 与 `executed` 必须能区分。
53. harness 不提供 `ChooseApprover`。
54. harness 不提供 `EscalateToHuman`。
55. harness 不提供 `ApproveByModel`。
56. 审批模型只使用审批服务自身受限一次性调用（现状 `executor.OneShotArgs` + `agentd.Approver`）。
57. 审批模型不得借用被审批任务的 OpenCode 会话。
58. 审批模型不得审批自己。

### 5.5 原生映射

59. OpenCode 写入原生配置的 allow 集合必须是当前快照可精确表达部分的子集。
60. 快照允许但原生无法精确表达的条件必须送 `ApprovalClient`。
61. 不得用更宽的原生 allow 代替无法精确表达的允许条件。
62. 快照中的明确禁止项，原生无法实施所需边界时必须报告能力不足。

### 5.6 指纹与复用

63. 命令域指纹是 `sha256("cmd\x00"+command)` 的十六进制。
64. 路径域指纹是 `sha256("paths\x00"+Tool+"\x00"+排序后 Paths 以 NUL 拼接)` 的十六进制。
65. 全文域指纹是 `sha256(Text)` 的十六进制。
66. `PermFingerprint` 对 `Command="echo hello"` 的命令域结果必须是 `7d0130b080382e74c685d247932d8e5379402827c2715a5e89f876e38f0d97b6`。
67. 复用必须限定同一 `Task.ID`。
68. 复用必须限定同一政策快照 `Version`。
69. 复用必须限定同一 `PermFingerprint`。
70. 复用必须限定 `kind=gate`。
71. 复用必须限定 `answer` 严格等于 `allow`。
72. 复用必须限定 `DeliveredAt` 非空。
73. 网络故障不得当成允许。
74. 超时不得当成允许。

### 5.7 Ask / 取消 / 迟到

75. 相同 Ask 答案第二次提交必须幂等成功，且不得第二次调用原生回复。
76. 对同一工单的不同答案必须被拒绝。
77. 工单已取消后的迟到答案必须被拒绝。
78. 工单已换尝试后的迟到答案必须被拒绝。
79. 工单已作废（`VoidAnswer`）后的迟到答案必须被拒绝。
80. 取消执行必须停止实际执行。
81. 取消执行必须解除仍挂起的原生权限与问题。
82. 取消执行必须把未答 Ask 标取消或作废。
83. 取消执行不得把已形成的审批决定改写为 `allow`。

### 5.8 生产入口与退役范围

84. 生产入口保持 `handoff dispatch` → `client.Dispatch` → `POST /api/tasks` → `Manager.Dispatch`。
85. OpenCode 任务经该入口进入后必须在新执行边界上跑，不得只 new 一个未接线的 client 接口。
86. `handoff reply --answer` 仍是 Ask 回程 CLI。
87. `handoff reply --approve` 的编码仍是 `allow`。
88. `handoff reply --deny` 的编码仍是 `deny` 或 `deny: <reason>`。
89. `gateDecision("allow")` 必须得到 `once` 且原因为空。
90. `gateDecision` 对其余 trim 后字符串必须得到 `reject`。
91. 本卡不新增专门「答问」CLI 子命令。
92. OpenCode 路径上 `handleQuestion`+`waitQuestion`→`Send` 不再是权威实现。
93. OpenCode 路径上 `handlePermission` 内的静态门 / 审批模型 / 升级 / 回传不再是权威实现。
94. OpenCode `Send` 消费 pending question 必须退役。
95. 拒绝理由优先吞下一条提问必须退役。
96. Claude / Codex / Grok / AGY 本卡仍走旧 Manager 路径。

## 7. 三重闸门拍板记录

命中三条的决定：

1. **审批 client 与 AskResponder 定义在执行契约包；本卡不新立顶层审批子系统。** 回头要动编排、执行、政策三域与目标图；后人看到审批类型住在 `executor` 会想「拆到 d_approval / permgate」。被否方案：本卡改 `best.json` 立 `d_approval`（轻档并不并行开发，且物理落点是父卡 OOS，图会撒谎）。不做新顶层域。
2. **AskResponder 作为可选接口，不进 Adapter 五动作。** 加第六方法会强迫 Claude/Codex/Grok/AGY 本卡改接口；后人看到「执行契约增量」会想直接加到 Adapter。被否方案：扩 Adapter。其它 harness 本卡保持五动作。
3. **政策快照绑定 Dispatch 启动与每次 Continue 开始；运行中改配置不改已跑回合。** 反过来写不会有任何现有测试变红。被否方案：热更新已跑会话的免审表。不做热更新。
4. **原生 allow 必须是快照可精确表达部分的子集，不得放宽。** 反过来把无法映射的条件写成更宽原生 allow，现有 OpenCode 任务环境测试仍可能绿。被否方案：继续 `WriteTaskEnv` 写死独立白名单当权威。
5. **相同 Ask 答案第二次幂等成功。** 现状 `AnswerTicket` 第二次返回 `ErrNotFound` 再被 HTTP 译成 404。后人看到 CAS `answer IS NULL` 会当正确实现留下。被否方案：保持第二次 404。幂等成功且不得二次原生回复。

显式不做（spec 已否，此处不重复展开）：独立交互领域、第三条事件总线、用无关联 `Send` 回答 Ask、把故障解释成允许、真机走付费 OpenCode 会员模型。
