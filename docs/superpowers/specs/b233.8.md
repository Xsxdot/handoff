本节点该干什么一律以注入的纪律块为准。

## 定级理由

跨子系统，动已有跨包契约的物理落点：生产实现今天在 `d_gateway`/`internal/agentd`，接口在执行契约包。单条迁包缝，一轮可收口 → L3 轻档。五家 harness 的权限/提问权威迁移超过轻档，不纳入本卡。

## 问题陈述

谁：共享派发行为已闭环，但 ApprovalClient 的生产类型仍住在 agentd。编译器、图闸和后人都会把审批实现当成网关的事。

条件：B233.1 把物理落点交给父卡；B233.7 R3 只把「审批逻辑迁出 agentd」留给本卡，并写明非 OpenCode 旧路径暂留。`POST /api/tasks` / `Manager.Dispatch` 是保留生产入口。

通道：现有 `bindApproval` / Dispatch / Continue / Resume 组装点。不新造 HTTP、CLI、事件。

要变的事实：

1. ApprovalClient 的**生产实现类型**不在 `internal/agentd` 包。agentd 只组装、注入。adapter 仍不得 import agentd / permgate。
2. OpenCode 已有审批/答问行为不回退（含 Dispatch / Continue / Resume 三条注入）。Claude 今日只注入快照写 settings，运行时权限仍走 `handlePermission`——本卡不把它改成权威已迁。
3. `handlePermission` / `handleQuestion` / `waitQuestion` 对本卡是**点名残桩**：继续服务非 OpenCode。本卡不删、不改它们的权威。

## 方案

原则：只搬家、不改非 OpenCode 行为。生产入口名字不变。

`taskApprovalClient`（或合同等物）离开 `internal/agentd`。新包名由 contract 按 ideal 图裁定，spec 不写死路径。agentd 的 `bindApproval` 只保留组装。OpenCode 的 Dispatch/Continue/Resume 三条注入必须一起迁，避免冷恢复回退到旧实现包。

本卡若迁包后能消 `TestRepoContractGate` 的 ApprovalClient dead-interface，必须消；`d_execution→d_orchestration` dead-contract 方向不假装绿。

**弃选**

- **本卡把 Claude/Codex/Grok/AGY 的权限或提问权威迁到 ApprovalClient / RespondAsk**：超出 R3，且 Codex/Grok/AGY 无 AskResponder；另开卡。
- **全仓按 best.json 重排 internal/**：无界。
- **新立 d_approval**：B233.1 已否。
- **删除 `POST /api/tasks` / `Manager.Dispatch`**：生产入口。
- **删除 `handlePermission` / `handleQuestion`**：非 OpenCode 仍依赖它们。

## 契约语义与接缝

- 审批决定的唯一写入者仍是 ApprovalClient；生产实现的包从 agentd 迁走。
- 允许：新实现包 → `executor` 契约包。禁止：adapter → agentd；ledger → client。
- 不新增事件/HTTP/CLI。非 OpenCode 权威路径本卡不动。

接缝（符号 + 调用方）：

1. `internal/agentd/approval_client.go#taskApprovalClient`（现状生产实现）——调用方 `Manager.bindApproval`。迁出后该符号不得留在 agentd 包；调用方仍是 bindApproval（或 contract 裁定的组装函数）。
2. `internal/agentd/manager.go#Manager.bindApproval` ——调用方 `Manager.Dispatch`、OpenCode 的 Continue 与 Resume。三条都必须接到迁出后的实现，漏 Resume 即冷恢复回退。
3. OpenCode 运行时权限权威保持现状 client 链——调用方 OpenCode adapter 权限事件 / `Manager.handleEvent` 对 OpenCode 的分流。本卡回归：迁包后 OpenCode 越界权限仍不进 `handlePermission` 为权威。

假缝禁令：不把「grep agentd 无 struct」当成唯一缝；C1 必须穿过 bindApproval 生产调用。

## 实现决定

- 命令名与 HTTP 路径不变。
- OpenCode 不回退到 Send 消费 pending、不回退到 handlePermission 权威。
- `internal/agentd` 不得再定义实现 `executor.ApprovalClient` 的生产命名类型。测试假实现不得当生产。
- Claude Dispatch 注入快照的现状可保留或随实现一起改注入来源，但不得把 Claude 运行时权限权威改到 client（那是下一张卡）。

## 测试决定

- C1：经 `bindApproval`（或后继组装函数）构造的生产 client 的 Go 包路径不是 `internal/agentd`；agentd 包内生产命名类型实现 ApprovalClient 为零。
- C2：OpenCode Dispatch / Continue / Resume 三条路径在迁包后仍注入非空 ApprovalClient（现有 Continue 重绑测试必须绿）。
- C3：OpenCode 越界权限回归不进 `handlePermission` 权威；RespondAsk 现有测试绿。
- `TestRepoContractGate` ApprovalClient dead-interface：能消必须消。dead-contract 方向不归因本卡。
- 非 OpenCode：至少一支现有 `handlePermission` / `handleQuestion` 测试保持绿，证明本卡未改它们的权威。
