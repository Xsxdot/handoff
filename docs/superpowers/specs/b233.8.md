## 定级理由

跨子系统，并动已有跨包契约的物理落点：

- **编排 / 网关**：`taskApprovalClient` 今天住在 `internal/agentd`，随 Manager 实现
- **执行契约**：`executor.ApprovalClient` 接口已在执行包；实现不得继续藏在 agentd
- **其余 harness**：Dispatch 只对 OpenCode 与 Claude 注入 ApprovalClient；Codex / Grok / AGY 仍走 `handlePermission` / `handleQuestion` 旧权威

选轻档：一张卡、一条迁包缝 + 同一套旧入口退役，不拆并行子卡。契约冻结与拆解照做，实现一轮收口。全仓 `internal/` 按 ideal 图重排目录超过轻档，列入 OOS。

## 问题陈述

谁：共享派发已经行为闭环（B233.1–.7），但完成条件里的**物理落点**和**旧入口退役**还没做。协调者、执行器和编译器看到的仍是「审批实现住在 agentd、非 OpenCode 路径仍走 manager 旧函数」。

条件：B233.1 明确把 `internal/` 按理想图搬目录、client 包物理落点交给父卡；B233.7 R3 把 ApprovalClient 迁包留给本卡。`POST /api/tasks` / `Manager.Dispatch` / `handoff dispatch` 是保留的生产入口，不是要删的旧入口。

通道：现有 Dispatch / Continue 组装点与 `executor.ApprovalClient`。不新造 HTTP、CLI、事件类型。

要变的事实：

1. ApprovalClient 的**生产实现**不在 `internal/agentd` 包内。agentd 只在组装点注入。adapter 继续不得 import agentd / permgate。
2. 凡本卡纳入的 harness，权限与提问的权威路径与 OpenCode 相同：走注入的 ApprovalClient / Ask 事实 + RespondAsk，不再以 `handlePermission` / `handleQuestion` 为权威实现。
3. 旧权威函数要么删除，要么降为「未纳入 harness 的明确残桩」——残桩必须在 OOS 点名，不得 silently 服务本卡已纳入的 harness。

## 方案

原则：迁的是**实现落点与权威路径**，不是再发明一套审批。生产入口名字不变。

**迁包**

`taskApprovalClient`（或合同等物）离开 `internal/agentd`。落点由 contract 按 ideal 图与导出面裁定：编排实现可以靠近任务生命周期，但包路径不得再是 `internal/agentd`。agentd Manager 只构造并注入。`bindApproval` 若仍叫这个名字，也只能是组装薄封装。

本卡顺手能消掉 `TestRepoContractGate` 里 `ApprovalClient` dead-interface 的，必须消；消不掉的（dead-contract 方向）写清为什么，不得假装绿。

**旧入口退役**

本卡纳入的 harness：OpenCode（回归不回退）、Claude（已注入则改权威）、Codex、Grok、AGY。纳入后 `handlePermission` / `handleQuestion` 不得再是这些 harness 的权威实现。未纳入的路径必须在 OOS 点名。

拒绝理由吞提问对纳入的 harness 必须退役（B233.1 已对 OpenCode 退役；其余纳入者同样）。

**弃选**

- **全仓按 best.json 重排 internal/**：无界，不是「共享派发」收尾。
- **新立 d_approval 顶层域**：B233.1 已否；本卡不翻案。
- **删 `POST /api/tasks` / `Manager.Dispatch`**：那是生产入口，B233.1 明确保留。
- **只搬文件不改权威路径**：迁包若仍从 handlePermission 分流，旧入口没退役。

## 契约语义与接缝

- 审批决定的唯一写入者仍是审批 client；agentd 不再持有生产实现类型。
- 允许新增依赖：编排实现包 → 执行契约包（已有方向）；**禁止**执行 adapter → agentd，禁止 ledger → client。
- 事件/HTTP/CLI 词表不新增。`permission_request` / `question` / `delivery_failed` 语义不变。
- 纳入 harness 的权限/提问权威从 Manager 旧函数迁到注入的 client / AskResponder。

接缝清单（符号 + 调用方）：

1. `executor.ApprovalClient` 生产实现的构造 —— 调用方：`Manager.Dispatch` / `Continue` 组装（现状 `bindApproval`）。新建落点由 contract 定包名，不在 spec 写死路径。
2. 纳入 harness 的权限事件入口 —— 调用方：adapter 权限事件到达后的生产路径；权威必须是 ApprovalClient，不得再进 `handlePermission` 作为该 harness 的实现。
3. 纳入 harness 的提问事件入口 —— 调用方：adapter 提问事件；权威必须是 Ask 事实 + RespondAsk（或该家已冻结的答问能力），不得再以 `handleQuestion` 为权威。

假缝禁令：不为迁包抽出无生产调用方的纯函数当缝。

## 实现决定

- 生产入口名字不变：`handoff dispatch`、`POST /api/tasks`、`handoff reply`。
- OpenCode 已迁入路径只许回归，不许回退到 Send 消费 pending。
- 迁包用编译器封界：`internal/agentd` 不得再定义实现 `executor.ApprovalClient` 的命名类型（测试假实现除外，且假实现不得当生产）。
- 其余 harness 若某家没有 Ask/权限能力，明确报不支持，不准用更宽的旧 manager 路径顶上（与 B233.2 能力面一致）。

## 测试决定

每条缝至少一支从生产入口进入的缝级断言：

- C1：Dispatch/Continue 注入的 client 类型不在 `internal/agentd` 包；agentd 包内 grep 生产 `type … struct` 实现 ApprovalClient 为 0。
- C2：纳入的非 OpenCode harness 至少一家（优先已有夹具的 Claude 或 Codex）越界权限走 client，且 `handlePermission` 在该路径上零调用（spy / 钩子）。
- C3：纳入 harness 的提问不走「拒绝理由吞提问」；OpenCode 现有 RespondAsk 回归保持绿。
- `TestRepoContractGate` 的 ApprovalClient dead-interface：本卡能消则必须消，作为 C1 的图闸；其余既有 dead-contract 不归因本卡。
