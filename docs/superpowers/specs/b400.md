# B400 spec：新卡首个节点的基线护栏——不许静默落在「不是工作线」的默认线上

**上游状态**：待用户批准（无人值守模式起草，未越过批准硬门）
**级别：L2 单子系统**（`internal/ledgerstep` 的派发前置校验 + `internal/ledger` 的基线冻结点；先例 B396「`internal/ledger` + `cmd`/`agentd` 判据面」同形）
**入口节点**：debug（根因与现场已在卡上）；本节点只出 spec，不动实现

---

## 1. 问题陈述

新卡的首个节点派发时，若卡上没有显式 `base_branch`，基线由**项目仓库记录的远端默认分支名**解析（`internal/workspace/gitworkspace.go:1328 ResolveDefaultBaseBranch`）⇒ 落在 `main`。而在「实际工作线 ≠ main」的仓上（本仓：main 落后功能线 438 个提交），后果是：

- 执行者**对着一份陈旧代码**写产出（plan 描述的是 438 个提交前的树）；
- **读不到卡自己的附件**——spec/plan 的提交在功能线上，main 的树里没有该路径（本次事故：`docs/superpowers/specs/b398.md` 不在 main 上）。

现场（2026-09-22，B398 首个 plan 轮）：分支 `cards/B398-charter` 落到 `85840cf`（main），停轮后手工把功能线并进该分支（因无自有提交而是快进）才恢复。

**纠错侧同样是死路**：`SetCardBaseBranch`（`internal/ledger/cards.go:642`）在卡上出现**首条 `dispatched` 事件即拒**（`ErrBadState: 基线已冻结`）——一旦点过一次火（哪怕当轮立刻停掉、零产出），基线就再也改不了，CLI 面也没有窗口内的纠正入口。

## 2. 级别与档位

**L2 单子系统**：改动落在派发前置校验（`internal/ledgerstep`）与基线写入契约（`internal/ledger`），不新增子系统、不新增依赖方向、不改 wire 契约。

## 3. 方案（含弃选与理由）

**采用：首节点派发前的「附件在场」护栏，fail-closed。**

- 触发点：**卡的首次节点派发**（卡上尚无任何非审阅 `dispatched` 快照时）。
- 判据：解析出的基线分支树里**必须存在本卡附件的路径**（至少 `spec`；有 `plan` 时一并查）。判据用「路径在不在那棵树上」这一机械事实，不猜「哪条才算工作线」。
- 失败动作：**拒发**，文案给三样东西——① 解析到的基线分支名；② 缺哪条附件路径；③ 可行动作（显式设 `base_branch` 后重试，或确认默认线正确）。
- 为什么是这个判据：它直接命中事故形态（「附件不在基线上」＝「基线选错了」），且**零假阳性代价可控**——附件是先于执行列存在的强约束（计划列的门就要求 spec 附件），首个节点派发时必然已有附件。

**弃选与理由**

- **A. 无条件要求首节点前必须有显式 `base_branch`**：会打断一切存量流程（本仓绝大多数卡都不设，靠默认线工作），且与「默认线本来就对」的场景为敌。**不做**。
- **B. 自动推断「实际工作线」**：无从判断（工作线是人的约定，不在任何机器可读位置）。**不做**。
- **C. 仅把冻结点后移**（允许首个节点未通过时改基线）：**单靠它修不了树**——错误基线已经开出的工作分支不会因为改了 `base_branch` 而换树；后续节点的 base 仍取工作分支（错的那条）。它是「纠正」的一半，另一半是把工作分支指到正确分支，那正是 **B382 spec §3（人工登记工作分支）** 要正规化的能力。**本卡不做，改由 B382 机制承担**（见 Out of Scope 的依赖说明）。

## 4. 用户故事

1. 作为协调者，当我在一个「默认线不是工作线」的仓上开新卡点火时，我会**被拒发**并被告知：解析到了哪条基线、缺哪条附件、以及怎么改——而不是静默开工，等执行者交出一份对着旧树的产出。
2. 作为执行者，我不会再遇到「卡上明明挂了 spec，我的树里却没有这个文件」。
3. 作为后来者，我从拒发文案就能看出「基线错了」这件事，不需要再去猜「为什么读不到 spec」。

## 5. 实现决定

- **判据收口在派发侧「首个节点」这一个点**：只在卡上无任何非审阅 `dispatched` 快照时执行该检查；后续节点不查（它们 base 取工作分支，不需要这个判断）。
- **检查的是路径在场性**，不是分支名形态：不引入「哪条是工作线」的配置或约定。
- **fail-closed 且可行动**：拒发文案必须含「解析到的分支 + 缺失路径 + 改法」，由测试锁关键词。
- **冻结点与纠正窗口不动**（弃选 C）：本卡只加护栏；把工作分支指到正确分支的能力归 B382 机制（依赖关系写进 Out of Scope）。
- **不新增用户可见命令**（本卡零新命令）。

## 6. 测试决定（接缝清单）

**接缝 1（承重缝）**：首个节点的派发前置校验（现状入口：`internal/ledgerstep/dispatch.go` 的派发决议段，其中已有 `WorkBranch` 判定 `hasWorkBranch`，见 `:192-205`）。
调用方（现状）：`card dispatch --step`（`internal/agentd/cardstep.go`）与队列出队路径。
断言：① 卡无快照 + 附件路径在该基线树中缺失 ⇒ **拒发**，文案含分支名与缺失路径；② 同样的卡但附件在场 ⇒ 通过（零假阳性）；③ 已派发过的卡（有快照）⇒ 跳过该检查（回归锁，不影响既有行为）。

**接缝 2（边界）**：未挂任何附件的卡（理论上不该出现在执行列，但防御性覆盖）⇒ 按「无附件可检」通过，不因缺附件而拒发（把「附件缺失」留给既有的列门去管，避免双重执法）。

**假缝禁令核对**：两条缝都在生产派发路径上、都有真实调用方；无「未导出、无生产调用方」的纯函数占名额。内部锁（例如「路径在场」判定的单元级用例）归 plan，不占缝名额。

## 7. Out of Scope

- **不做**：无条件要求显式 `base_branch`（弃选 A）、自动推断工作线（弃选 B）。
- **依赖（不在本卡）**：**误基线已造成时的纠正**——把卡的工作分支指到正确分支——归 **B382 spec §3「人工登记工作分支」**；本卡只保证「不让它静默发生」。B382 机制落地时应覆盖本事故形态（工作分支无自有提交、可直接快进到正确基线）。
- **不做**：`ResolveDefaultBaseBranch` 的语义变更（默认线仍取远端默认分支名；本卡只在它与卡附件不一致时拦下）。
- **归用户**：`handoff` skill 补一句操作纪律（新卡首节点前先确认基线）——skill 仓属用户，见卡上修向第 4 条。
- **本期不做、后续要做**：基线的**可见性**（`card show` 暴露 `base_branch` 与其解析来源）——本次排查时 CLI 看不到该字段，只能绕道 `effective_base_branch`；是否要暴露与格式，留待下一期。残余落 roadmap。
