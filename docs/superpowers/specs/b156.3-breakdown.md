## 待拍板岔口（集中清单，拍板者按此裁决）

**岔口一：hostapi.RunTurn 的 CLI 覆盖面**
- 方案 A（推荐）：仅实装 opencode；其余 CLI 值返回明确「未支持」可行动错误，不静默。理由：spec §4.5 协调机 claude 长期未登录、协调者小队初始成员用 opencode 载体（spec §3 台账④）；四跳真机判据只有 opencode 有上游实测背书（台账⑫），其他 CLI 无从钉起。
- 方案 B：通用化到全部既有执行者 CLI。一次到位，但 claude 凭据前提未清账，四跳对非 opencode 无真机判据，易产出「机内桩测绿、真机未验」的面。
- 取舍实质：范围钉死可真机验收 vs 名义覆盖面。

**岔口二：已升级用户的工单是否仍产生唤醒边**
- 方案 A：全部 permission_request / question 都唤醒（spec §5.3 表格字面语义）；破坏性件由醒来的协调者识别跳过。不漏，代价是升级件双通道打扰（收件箱 + 协调者回合各一次）。
- 方案 B（推荐）：走自动审批通道的工单才唤醒；已被 approver 链判 escalate 到用户的工单只留收件箱、不产生唤醒边。降噪（升级件已有专人），代价是唤醒侧要读 approver 判定结果，引入一处顺序依赖。
- 取舍实质：宁多勿漏 vs 噪声控制。两案都不改变「破坏性照旧升级用户」的硬纪律。

**岔口三：并发准入的执法形态（对抗审查·门禁族发现，见 §四-5）**
- 方案 A（推荐）：把两级上界判断折进计数的 CAS 循环（acquire 时带上界重试），Admit/LaunchAdmit 保持无锁直调，任何调用方并发都安全；修法落在 `internal/scheduling` 包内。
- 方案 B：所有准入与出队收敛到清队循环单一 goroutine 串行，HTTP 手动点火也转投入队。实现最简，但手动点火延迟增加，且安全性从「谁调用都安全」退化为「约定串行」。
- 取舍实质：域内自洽的原子性 vs 编排侧集中串行。

**岔口四：协调者小队/载体的出厂种子做不做**
- 方案 A：agentd 启动时若无 coordinator 角色小队则自动登记缺省 opencode 载体+小队。开箱即用，但属「引擎偷偷造配置」，与 B230 拆出厂种子的裁决方向相逆，且缺省 HOME 目录位置需要额外约定。
- 方案 B（推荐）：不做种子；未登记时拉起端点/hook 返回指路 `handoff squad create` 的可行动错误。配置显式，首用多一步。
- 取舍实质：开箱即用 vs 不焊私人编制。

## 岔口拍板记录（协调者，2026-08-26）

四条全部当场裁决，不留悬置——悬置的岔口会在实现票里被各自解释成不同的东西。
裁决理由写全，便于后人推翻（推翻要驳倒理由，不是重新表决）。

**岔口一 → 方案 A（仅实装 opencode，其余 CLI 返回带 CLI 名的「未支持」错误）**

理由：范围钉死可真机验收，胜过名义覆盖面。spec §4.5 已认定本机 claude CLI 长期
未登录，四跳真机判据也只有 opencode 有上游实测背书；对无从真机验的 CLI 铺面，
产出的必然是「机内桩测绿、真机未验」——正是本卡反复在防的那一族。**附加约束**：
那条错误必须含 CLI 名（K1 已有该反面断言），不许静默兜底到 opencode——静默兜底
会让「换个载体试试」变成「看起来换了其实没换」。

**岔口二 → 方案 B（只有走自动审批通道的工单产生唤醒边），但加一条兜底**

理由更正一处：出稿把 A 说成「spec §5.3 表格字面语义」，实际不是。§5.3 工单那行
写的是「无破坏性的协调者直接批……破坏性/不可逆照旧升级用户」——它本来就在区分
两类，并没有要求升级件也敲醒协调者。所以 B 不是偏离已批准的 spec，是更贴合它。

成本侧也支持 B：升级件敲醒协调者之后它什么也做不了（按设计就该等用户），醒来
看一眼再睡回去，烧掉一个准入名额和一份 CLI 额度——小队这个概念存在的意义正是
省这两样。而且「醒来识别再跳过」就是空转回合的标准形态。

**兜底（必须实现，否则 B 会静默退化）**：审批链**不可用或被禁用**时（事件流里
的 `approver_disabled` 是既有形态），一切工单退回 A 的行为、照常唤醒。否则
「只有走自动通道的才唤醒」在没有自动通道的机器上等价于「永不唤醒」，卡会挂着
协调者睡死，而且全程不报错。K5 验收加一条：`approver_disabled` 生效时
permission_request 仍产一次 Wake。

**归位**：用户看到的东西两案完全相同（升级件照样进收件箱），差别只在协调者被不
被叫醒与由此消耗的额度——这是实现级取舍，故本席裁决，未上升用户。

**岔口三 → 方案 A（上界判断折进计数的 CAS 循环）**

理由：架构法第五条——规则属于数据的所有者。名额上界是编制域自己的不变式，执法
就该在 `internal/scheduling` 包内闭合，而不是靠「所有调用方都记得从单一 goroutine
进来」。A 给的是「谁调用都安全」，B 给的是「约定串行」；约定不是执法，下一个新增
的调用方（Web 手动点火、CLI、将来的规则引擎）没有任何机制阻止它绕过约定。

**附加约束**：K2 验收里那支并发测试必须带变异复验——去掉上界判断则该测试必翻红。
没有变异复验的并发测试是本项目里最典型的稳定假绿（并发规模不够时它恒绿）。出稿
自己提到的重试预算问题（N≤16 vs CAS 重试 8 次）也要写进验收注记：翻红时先查重试
预算再查语义，别把预算不足误判成语义错。

**岔口四 → 方案 B（不做出厂种子，未登记时返回指路 `handoff squad create` 的错误）**

理由：与 B230「handoff 出厂不预设任何工作流」是同一条裁决的延长线——引擎不焊私人
编制。种子方案还要额外约定缺省 HOME 目录位置，而 HOME 恰恰是 spec §4.3 要求由载体
登记**显式携带**（不拼 `~`）的那个值；出厂种子等于在引擎里硬编一个它无权知道的
本机路径。首用多一步，换来配置全程可见。

**附加约束**：那条错误必须可行动——含具体命令与最小参数示例，不是「未配置协调者
小队」。K4 验收按此写死断言。

**边界澄清**（核对中做出，结论均为「不退回 contract」，修订记录已回写契约文档 §15）：

1. **唤醒映射表的边界**：WakeKind 与账本事件类型的机械对应归 plan 逐枚举核对

   不产生唤醒（否则自己敲醒自己）；**未映射事件一律不唤醒且不报错**（progress 类
   语义，蓝图过滤规则保持）。
2. **LaunchForCard 的 SessionSpec 生效语义**：拉起会话的实际形状（CLI/HOME/模型）

   参数传入；keystone 现状 launchRound 忽略入参自造空 spec 是骨架期欠账，实现票
   必须改为消费入参——签名不动，行为补齐。
3. **sched_running 计数键形状**：计数键只有 `sched_running/squad/<队名>` 与
   `sched_running/carrier/<载体名>` 两类，按（角色,名字）二元组计数、不按卡——与
   Release(squadName, carrierName) 签名互证，plan 不得引入第三类计数键。

## 三、子卡清单 + 依赖 DAG

```
K1（承载实装）──────────────┐
K7（registry PG 回归）       │（独立，随时并行）
                             ▼
K2（派发接入）──► K5（自动化编排）◄─ K4（协调者生命周期接线）
                     ▲                    ▲
K3（人机登记面）─────┘（K3 先于 K4，减少同文件路由注册冲突）
                             ▼
                    K6（Web 控制台页面）
```

排序理由：K1/K2/K3/K7 无相互依赖可并行；K4 依赖 K1（真实拉起要有能跑的 RunTurn）
与 K3（路由注册处错峰）；K5 依赖 K2（有队可清）与 K4（Wake 的 SessionSpec 来源在
组装点解析链上）；K6 收尾（消费 K3/K4 定型的端点形状）。全卡 implement 另受
B156.2 阻塞边约束，扇出顺序归协调者。

### K1：hostapi.RunTurn 承载实装（opencode 四跳）

- **①契约引用**：§7 hostapi 面（TurnRequest/TurnReply/ErrUnavailable 签名不变）、
  §9 测试义务①、§6.3 Runner 缝铁律（只 Launch/Resume 两动作，不进派发状态机、
  不产生 task）；spec §4.3 隔离 HOME、§4.5 载体前提。岔口一裁决适用。
- **②意图与为什么**：coordinatorRunner 已直通 RunTurn（server.go:2313–2327），
  hostapi 实装后整条拉起/唤醒链自动通电——它是 keystone 一切行为的物理前提，
  也是唯一接缝对面是外部现实的子卡（边界型）。
- **③验收**：
  - 机内（逻辑半边）：假 CLI 桩（shell 脚本）下 RunTurn 新建会话返回非空 SessionID、
    带 SessionID 续接走 resume 分支、Timeout 到点判失败不挂死——三条各有红绿判据
    的测试；`go build ./... && go test ./internal/hostapi/... -count=1` 绿。
  - 反面断言：RunTurn 对未实装 CLI 值返回的错误信息含该 CLI 名（不许静默兜底到
    opencode）；Runner 缝类型系统上不存在派发入口（竖切已有断言，本票不得删除）。
  - 真机（行为半边）：四跳实跑落证（真机清单第 1 条）。
- **④入口指针**：`internal/hostapi/hostapi.go`（ErrUnavailable:19、RunTurn:47）；
  复用参考 `internal/prochost/`（原语）与 `internal/executor/opencode/`（serve 协议
  知识，同属 d_execution 子域不跨界）；组装侧直通层 `internal/agentd/server.go#coordinatorRunner`。
- **有界文件集**：`internal/hostapi/`（hostapi.go + 新增实现文件与测试），一个包，圈得出。

### K2：派发链接入——Squad 解析层 + 排队分支 + 准入原子化

### 配对原语归属表（协调者补，2026-08-26）

K2 的 plan 轮审计发现 **`scheduling.Service.Release` 的生产接线没有任何一张卡认领**

**`Release` 归 K5 的理由**：释放的正确时点是「一个协调者回合结束」，而回合的开始与
结束都在 K5 的编排循环里可见（`Wake` → `RoundResult`）；放在 K2 拿不到回合终点，
放在 K4 只覆盖拉起那一路、覆盖不到唤醒轮。

**K5 必须带的判据（能变红的那种）**：一次完整的「点火 → 准入 → 回合结束」跑完后，
`sched_running/squad/<队名>` 与 `sched_running/carrier/<载体名>` 两个计数**回到起始值**；
**变异复验**：删掉 `Release` 调用，该测试必须翻红。契约 §11 提到的「启动时对账」是
丢失 Release 之后的兜底，**不是它的替代**——只有兜底而没有释放，等于每次重启才回一次血。

**这张表本身也是判据**：后续任何卡若新增一对原语，必须在此表补一行并点名两半的归属；
只派一半即为拆解缺陷，退回本节点。

**这条规则第一次被违反就发生在本表写下之后（2026-08-26，协调者补记）**：K2 的 implement
轮新增了导出哨兵 `scheduling.ErrRetryExhausted`（一对新原语的「产出」半），**没有在此表
补行**，于是它的「分流消费」半无人认领——生产链路上 `errors.Is(..., ErrRetryExhausted)`
只出现在 scheduling 包自己的测试里，而 `scheddispatch.go` 的分流是「`ErrNoSlot` → 转排队 /
其余一律 → 派发失败 → `haltForHuman`」，于是**瞬态 CAS 争用会把卡推去等人**。
实现轮与审阅轮都没看见它（编译过、测试绿、`graph check` 零 fails、diff 完全正当），
是协调者在**追认**阶段核「新增导出符号的去向」时挖出来的。

**因此本表补一条执法动作**：审阅节点必须逐个列出本轮新增的导出符号，并对每一个回答
「**谁在生产代码里消费它**」——`git grep` 该符号名、排除 `_test.go` 与注释行。
只在自己包的测试里被调用，就是半边缺失。「测试覆盖漂亮」恰恰是这一族的伪装：
`ErrRetryExhausted` 有测试、`collab.Service.Consume`（对方线同族一例）有 10 处测试调用。

**这条判据必须配两个自检，因为它有两个方向的失效模式，而两种失效都不报错：**

1. **模式坏了 → 假阳性**（把有消费方的报成孤儿）。`git grep -E` 用 POSIX ERE，
   **不认 `\b`**：`\bName\(` 会被当成字面 `bName(`，一条也匹配不到且退出码正常。
   正确写法 `(^|[^A-Za-z0-9_.])Name\(|\.Name\(`。
   **自检**：拿一个确定有大量调用方的符号（如 `New`）跑同一条命令，命中数必须是三位数；
   个位数或零就是模式坏了，不是代码干净。（对方线实测：坏模式一次造出 12 个假孤儿，
   戳破它的不是重跑，是**分布的整齐度**——所有 `func` 类全 0、所有 `method` 类都有真数字。
   真实缺陷不会按语法类别整齐排列。）
2. **排除坏了 → 假阴性**（把只有测试调用的报成「有消费方」）。`grep -v '_test\.go'`
   漏掉时，测试里的调用会被算成生产调用，半边缺失就此隐形。
   **自检**：拿一个确定只在测试里被调用的符号跑同一条命令，生产命中数必须为 0；
   不为 0 就是排除没生效。

**并且：生产命中与测试命中要分开数、都写进产出物**，不要只报一个「有/无消费方」的结论。
两个数放在一起才看得出「10 处测试、0 处生产」这种形态；只报结论时它长得跟「有消费方」一样。

**通则**：凡产出聚合计数，都要能展开成可逐条证伪的清单。聚合数字既可能**掩盖信息**
（`misplacedSkipped: 114` 不点名，于是没人知道是哪 114 个），也可能**掩盖错误**
（「34 个孤儿」不列出，于是没人发现其中 12 个是正则坏了）。

  重放扫不到它。缓解：出队删除改「标记后删」会违反冻结条目 6 的 CAS 语义，故本
  票验收加一条：**单次出队的丢失窗口只允许存在于进程崩溃场景**，且唤醒机制的
  task 终态事件会在下次点火时暴露缺口（可发现性兜底）。彻底消除需事务化出队，

  天然承接）。接管态丢失=拍板记录③明文接受（宁可误唤醒不可漏唤醒）。
- 已派发在飞环节：维持 cardstep.go 现状不恢复（契约 §11 移交区原文），唤醒机制使
  危害可控。
- 结论：有风险，窗口如上，全部落进 K5 验收与真机清单；无无人认领的孤儿资源。

**4. 假红 / 假绿测试**
- 最大温床：PG smoke 默认 skip（LEDGER_TEST_PG_DSN 未设时）——skip 是绿的。K7
  验收强制 skip 输出原因 + 真机清单要求至少一次非 skip 落证；同理 K1 的四跳若
  做成环境探针式 skip 也算假绿，真机清单第 1 条要求原始输出落账。
- 竖切测试用 fakeNarrator/fake runner：锁的是调用方依赖的行为（决策表/合并/兜底
  链/互斥），换 Runner 实现不应翻红——判据写的是接口交互次数与结果，不是内部
  帮手调用；符合「换实现不改需求不红」。但 fake 世界编码了「Pointer 可用」的假设，
  该世界的真实性由 C7 落地后的跨卡集成验证，本卡标注为已知边界（未验证，需真机
  ——见真机清单第 7 条）。
- 反面断言盘点：K2 存量不变（改前改后事件序列比对）、K4 不产生 task、K5 progress
  不唤醒/幂等、K1 未实装 CLI 报错含名字、K3 未登记返回空集——每票至少一条。

  > **强制正控（协调者补，2026-08-26，对上列每一条都适用）**：反面断言（不存在 X /
  > 不产生 Y / 不唤醒 / 零引用）**必须配一次强制正控**——把 X 临时加进去，断言**必须
  > 翻红**；还原后必须回绿。**两个读数都要进交付物**，review 的点名项是「看正控的两个
  > 读数」，不是「看断言绿不绿」。
  >
  > 理由（两条实证，本线与对方线各一）：
  > 1. **K1 本轮实测**：岔口一的附加约束原写「未实装 CLI 的错误必须含该 CLI 名」，
  >    变异审查发现**把门禁整个删掉后 `exec.LookPath` 自己报的错同样含 CLI 名**，
  >    断言照样通过。已加强为「含专门的未实装标记词」。
  > 2. **对方线 C6**：判据「遍历 mux 注册表断言无可达 Pointer 入口」在本仓根本写不出来
  >    （标准库 `http.ServeMux` 不提供枚举已注册模式的 API）。而**被断言「不存在」的东西
  >    今天本来就不存在**，于是执行者挑的任何替代品（猜 URL 断 404 / grep 源码 /
  >    重构出可枚举路由表）**全都是绿的，选对选错在输出上完全不可区分**，走完实现加
  >    两轮审阅也不会有任何信号。
  >
  > 这一族的特征：**「断言在守」和「断言压根不会红」长得一模一样。**判据写错时执行者会
  > 撞墙来问；判据与实现之间有洞时，执行者既撞不了墙也无从察觉，还会无可指摘地全绿。
  > 正控是唯一能把这两种情况分开的读数。

- **符号级 grep 判据必须按接收者类型判，或显式排除并写明理由**（协调者补，2026-08-26）：
  裸匹配选择器会撞同名符号。本仓实测：`grep -rn "\.Pointer(" --include=*.go` 排除测试后
  **共 7 处命中，其中 6 处是 `unsafe.Pointer(`**（`internal/prochost/taskmark_darwin.go` 1 处、
  `platform_windows.go` 5 处），只有 1 处是 `roomNarrator.Say` 里真正的
  `collab.Service.Pointer` 调用。写成「调用方计数」或「非白名单包零命中」的判据会**假红 6 次**；
  更糟的是有人为了消红去放宽匹配，把真正要守的那一处也放过去。K4「拉起路径不产生 task」
  若落到符号级匹配上属同族，同样处理。

- **判据必须能被违反，不能只能被满足**（协调者补，2026-08-26）：形如「某措辞不在了」
  「某调用不存在」的判据一旦满足即**恒真**——它和零执法断言是同一族毛病，绿了什么也没证明。
  一律改写成**正面断言**（断言应有之物在场），把否定式降为次判据；并配强制正控证明主判据
  会红。**自检问法**：这条判据在什么情况下会变红？答不出来就不是判据。

- **指针行断言一律写成存在式，禁止计数式**（协调者补，2026-08-26）：`RoomMessage`
  没有字段记录「哪个系统组件写的」，落账 actor 是 collab 包内常量 `"system:pointer"`，
  且该签名已冻结不含 actor 参数。因此本卡的 narrator 指针行与对方卡 C7 的派发指针行
  **在账本里只能靠正文散文区分**。判据写成「恰好一条 pointer 行」「pointer 行数 +1」
  这类计数式，两边上游都落地后会**互相把对方变成偶发红**。一律写「存在一条正文匹配
  ⟨本卡特征⟩ 的 pointer 行」。
- 负载/并发翻红风险：K2 原子化测试并发 N 路打 M 上限，在 CAS 重试 8 次上限内
  应收敛；高争用下 8 次不够会假红——验收注明并发规模（N≤16）与重试上限的关系，
  翻红时先查重试预算再查语义。
- 结论：有风险，口子已各配独立动作。
