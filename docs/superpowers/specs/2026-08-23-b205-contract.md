## 2. 契约增量

### 2.1 账本门面

新增精确签名：

```go
func (s *Store) SetCardBaseBranch(id, branch, actor string) error
```

现状代码证据是本提交 Ticket 0 的 `internal/ledger/Store.SetCardBaseBranch`
（`internal/ledger/cards.go:534-540`）；同形写入口 `UpdateCardMeta` 的现状签名和事务接线在
`internal/ledger/Store.UpdateCardMeta`（`internal/ledger/cards.go:511-532`）。实现节点必须满足：

1. `id` 不存在返回可由 `errors.Is` 识别的 `ErrNotFound`。
2. 在同一 `mutate` 事务中查该卡最早的 `EvDispatched` 事件；按 `seq ASC` 判定，首次事件
   的 `DispatchSnapshot.Branch` 与 `Event.CreatedAt` 必须保留在拒绝错误中。审阅用途仍是
   `dispatched` 事件，但本 spec 的“首次派发”不因 `PurposeReview` 而消失：任何已派发事件
   都冻结基线。
3. 没有任何 `EvDispatched` 时，`branch` 非空写入 `cards.base_branch`；显式空串清除自身
   覆盖值，让 `EffectiveBaseBranch` 回到父链/项目主线语义。不要在账本层猜 `main` 或
   `master`。
4. 写入同时更新 `updated_at`，并沿用活跃的 `EvComment` 事件类型留下变更痕迹；payload
   至少含 `base_branch` 的新值和可读 body。不得新造一个没有消费者的状态常量。
5. 任何写入或事件失败都回滚 cards 与事件；成功后 `EffectiveBaseBranch` 立即读到新值。

一次调用只处理一张卡、一笔账本事务。多卡建树由控制面逐卡调用，不能把跨卡循环伪装成
账本原子事务。

### 2.2 CLI 写入口

在现有 `card update`（命令定义/接线为 `cmd/card.go:136-176`，当前 flag 注册位于
`cmd/card.go:447-453`）增加：

flag 必须能区分“未提供”（不改）和“显式提供空串”（清除覆盖值）；命令只调用

### 2.3 HTTP 写入口

复用已注册的 `PATCH /api/cards/{id}`（handler 当前为 `internal/agentd/Server.handleCardPatch`，
`internal/agentd/ledgerapi.go:727-777`），请求体增加：

```json
{"base_branch":"cards/B205-charter"}
```

`base_branch` 使用 `*string` 语义：键缺席是不动，键存在且为空是清除。标题、优先级、验收
判据与基线在同一请求中都存在时，按现有 handler 的顺序逐项调用各自账本门面；基线的冻结
判定只能由 `SetCardBaseBranch` 做。实现节点必须把 `ErrNotFound` 映射 404，把 `ErrBadState`
映射 409；不能沿用当前元信息分支的 400 把冻结原因吞掉。

前端类型镜像为 `web/src/api/ledger.ts#CardPatch`（本提交 `web/src/api/ledger.ts:239-247`，其中新增
`base_branch` 字段），
现有发送函数 `web/src/api/ledger.ts#patchCard`（`web/src/api/ledger.ts:249-250`）签名不变。

### 2.4 建树 wire

请求仍是：

```text
POST /api/projects/{name}/worktrees[?machine=]
```

现状入口是 `internal/agentd/Server.handleProjectWorktreeCreate`（`internal/agentd/projectadmin.go:905-952`），
已有 `proto.CreateWorktreeReq`（`internal/proto/projects.go:370-380`）增加：

```go
CardIDs []string `json:"card_ids,omitempty"`
```

响应仍为 HTTP 200 的 `proto.Workspace`，在其上增加：

```go
type CardBaseBranchResult struct {
	ID    string `json:"id"`
	OK    bool   `json:"ok"`
	Error string `json:"error,omitempty"`
}

// Workspace 的新增字段
CardResults []CardBaseBranchResult `json:"card_results,omitempty"`
```

当前 Ticket 0 的可编译定义证据为 `internal/proto/Workspace`（`internal/proto/projects.go:19-61`）。
规则为：

1. `card_ids` 缺席或为空时，响应省略 `card_results`；工作树响应保持原形。
2. git 工作树成功后，按请求顺序逐卡尝试写入；每个请求卡号有且只有一个结果项。
3. 单项 `ok=false` 只说明该卡未挂上，`error` 带该卡原因；工作树已经成功，不回滚磁盘。
4. git 建树失败仍走现有 400/500 错误响应，不伪造 `card_results`。
5. `ledger == nil` 时静默忽略 `card_ids`，工作树照常创建且不返回卡结果；这是 spec 明确
   的 ledger disabled 兼容语义。

`Workspace` 原有的 `path/branch/head/is_main/managed/created_at` 事实见
`internal/proto/Workspace`（`internal/proto/projects.go:23-50`）；新增字段使用 `omitempty`
避免改变项目树、旧客户端和无卡请求的 JSON。前端镜像为 `web/src/api/types.ts#Workspace`
（`web/src/api/types.ts:129-148`）和 `web/src/api/types.ts#CreateWorktreeReq`
（`web/src/api/types.ts:213-219`）。现有客户端 `web/src/api/client.ts#createWorktree`
（`web/src/api/client.ts:620-626`）仍返回 `Promise<Workspace>`，实现节点只需透传新增可选字段。

### 2.5 建树与转发边界

`CreateManualWorktree` 的现有签名保持不变（`internal/agentd/manualworktree.go:71-89`）：先完成
git 建树，再由 `handleProjectWorktreeCreate` 逐卡调用 `s.ledger.SetCardBaseBranch(id, ws.Branch, actor)`。
循环不得包一层“跨磁盘和账本”的伪事务，也不得在 git 成功前写基线。

`forwardIfRequested` 在当前 handler 的第一步（`internal/agentd/forward.go:41-69`），并由
`forwardTo` 原样搬运请求/响应（`internal/agentd/forward.go:72-83`）。因此显式 `?machine` 请求
由真正创建工作树的目标 agentd 执行挂卡；本地转发方不提前写卡、不重复写卡。该归属利用了
现有转发边界“目标机解释业务语义”，不是新增一个中心账本路由。

## 3. 原子化冻结清单

下列每行都是可独立判 pass/fail 的断言，不把两个动作合在一个复合条目里：

- `SetCardBaseBranch` 对不存在卡返回 `ErrNotFound`。
- `SetCardBaseBranch` 对已有任意 `EvDispatched` 的卡拒绝写入。
- 拒绝错误包含首次派发快照的分支。
- 拒绝错误包含首次派发事件的时间。
- 未派发卡可写入非空显式基线。
- 未派发卡显式写入空串会清除自身覆盖值。
- 成功写入后 `EffectiveBaseBranch` 返回自身新基线。
- 子卡未设基线时仍按既有父链规则解析。
- 基线写入与 `EvComment` 事件在同一账本提交中成功或一起回滚。
- `card update --base-branch` 缺 flag 时不改基线。
- `card update --base-branch ''` 表示清除基线。
- `PATCH /api/cards/{id}` 缺 `base_branch` 时不改基线。
- `PATCH /api/cards/{id}` 的空 `base_branch` 清除基线。
- 已派发卡的 HTTP 基线改写返回 409。
- 建树 git 成功后才开始逐卡挂基线。
- 每个请求卡号产生一个独立成功结果或失败结果。
- 任一卡挂基线失败不回滚已成功的 git 工作树。
- 账本未启用时带卡号建树仍成功。
- 账本未启用时带卡号建树不返回伪造卡结果。
- 带 `?machine` 的跨机建树，卡基线写在**协调者侧**账本，不转发给目标机。
- 跨机建树的 `card_results` 如实反映协调者侧账本的逐卡写入结果。
- 建树 git 失败时不返回卡结果。
- 显式 `?machine` 转发由目标 agentd 执行建树一次，协调者侧 agentd 执行挂卡一次（勘误见 §2.7）。
- 无 `card_ids` 的旧建树请求仍省略 `card_results`。

## 5. 拍板记录（三重闸门命中）

### 5.1 用 `EvDispatched` 事件流冻结，而不是加 `dispatched` 状态列

这是难逆转的账本判据（会影响账本写入、HTTP、CLI 与建树挂接），无上下文时后人会想把
它改成更直观的状态列，而且存在被否的像样方案（新增布尔列或复用任务挂账表）。选择
事件流是因为账本现有状态与派发事实已经由事件推导，首个 `seq`、分支和时间可同时取证；
被否方案会制造第二个真相源。审阅事件也冻结，避免把“派发过”按用途重新解释。

### 5.2 建树先成功、再逐卡挂接，失败不回滚工作树

这是难逆转的跨磁盘/账本边界，无上下文时后人会想把它包成全成功才返回，且存在真取舍：
先写账本可以让卡先有基线，但可能留下不存在的树；回滚 git 又会删除已可用的用户产物。
选择“树成功即保留、卡逐项回报”与 spec 的跨事务语义一致；反过来写步骤顺序不会靠现有
状态测试自动变红，所以把顺序作为本记录而不是流程口头约定。

### 5.3 复用 `Workspace` 可选结果字段，不另造建树响应信封

这是难逆转的 wire 形状，无上下文时后人会想把“树”和“挂卡结果”分成两个 endpoint，且
存在像样替代（新增 `CreateWorktreeResp{Workspace, Results}`）。选择在现有 `Workspace`
上追加 `card_results,omitempty`，因为当前客户端已固定 `Promise<Workspace>`，旧客户端可
忽略缺席键，且项目树响应不会因空列表改变。字段命名与逐卡结果形状由 Ticket 0 金样本测试
冻结；不做第二个并行响应真相。
