## 2. 架构决定：户口复核（spec §7.0 的 contract 落地）

### 2.1 两域二分维持，命名落码

对 spec 提议的编制域 / keystone 域二分做架构法第一条与派卡四条复核，结论：**维持二分，
判据成立**——两域数据所有权不同（编制域拥有载体/小队/队列的规则数据；keystone 域不拥有
任何持久数据、只做编排决策），消费者集合不同（前者是环节派发路径/控制面/CLI/控制台，
后者是 card_events 消费循环/控制面/CLI/控制台），合并会造出既管配置数据又管事件编排的
god object。判错的纠偏是合并两域，不是推翻本节。

| 户口 | 域 id | 包 | 类型 |
| --- | --- | --- | --- |
| 编制调度（第 13 个顶层域） | `d_scheduling` | `internal/scheduling`（入站 api）、`internal/schedclient`（出站端口） | logic |
| 协调者 Keystone（第 14 个顶层域） | `d_keystone` | `internal/keystone`（入站 api）、`internal/keysclient`（出站端口） | logic |

B156.2 会话子系统未落地，无顺延问题；它落地时取下一个户口号，与本卡无关。

**命名判据（包名不用 `api` 子包）**：代码图扫描按 Go 包名生成容器 id，多域各开
`internal/<x>/api` 会撞成同一批 `k_api_*` 容器（ptyhost/engine→k_engine_* 的既有先例证明
前缀取末段）。故门面包取唯一名：`ledgerapi` / `hostapi` / `ptyapi`，端口包取
`schedclient` / `keysclient`。

### 2.2 双向门面与依赖 DAG

两个新子系统按标准架构立：入站 api 门面 = 外界唯一入口（Go internal 可见性 + graph check
执法）；出站 client 接口定义在使用方一侧（架构法第九条），由组装点绑定实现
（`target.json` assembly 已登记 `main.go` / `internal/agentd/server.go` /
`internal/agentd/codegraph.go`；本期绑定全部落在 `internal/agentd/server.go#Server.SetupAutomation`，
2235）。组装点之外不得 new 他方具体类型。

冻结后的新增依赖方向（全部已写入 target.json；归一轮后裸 `graph check` 退出码 0，
fails=0，两侧符号均已进 baseline——视图 diff 已按 absorb 语义併入基线并删除）：

## 3. 账本侧新增能力（d_ledger 内部 + ledgerapi 门面）

### 3.1 注册表原语（拍板记录④）

载体/小队/点火队列/并发计数的持久化用**通用版本化 KV 表 `registry`**，不为每个实体建专表：
账本是持久化设施，编制域才是这些实体的规则所有者；实体形状演进不牵动账本 schema。同款
先例是 workflows 表存 JSON definition（`internal/ledger/store.go` ensureSchema，234–236）。

```go
// internal/ledger/registry.go（新表进 ensureSchema 双方言 DDL）
func (s *Store) RegistryPut(kind, id string, expectVersion int, body []byte, actor string) (int, error)
func (s *Store) RegistryGet(kind, id string) (RegistryEntry, error)      // 缺失 ErrNotFound
func (s *Store) RegistryList(kind string) ([]RegistryEntry, error)       // seq 升序
func (s *Store) RegistryDelete(kind, id string, expectVersion int, actor string) error

type RegistryEntry struct {
    Kind    string; ID string; Version int; Seq int64; Body json.RawMessage
}
```

CAS 语义：expectVersion 必须等于当前版本（0 = 必须不存在的新建），不符返回
`ErrCASConflict` 包装错误，与 `MoveCard` 同判据；版本从 1 起。Seq 是全表单调写入序。

## 4. 编制域契约（d_scheduling）

### 4.1 实体（版本化经 registry，kind 常量冻结）

```go
// internal/scheduling/scheduling.go
type Carrier struct { Name, Machine, CLI, HomeDir, Model string;
    Credential CredentialSource /* standalone | main_home_sync */ ;
    MaxConcurrency int /* 物理位，0=不限 */ ; Healthy bool }
type Squad struct { Name string; Role SquadRole /* executor | coordinator，不混编 */;
    Members []string /* 载体引用集 */ ; MaxConcurrency int /* 政策位，0=不限 */ }
type IgnitionRequest struct { Card, Squad, Node string;
    Target, Executor, Model string /* 一次性覆盖 */ ;
    Priority string; Ready bool /* 入队快照，见下 */ ; Actor string }
type Binding struct { Squad, Carrier, Target, Executor, Model string }
```

registry kind 冻结为五个：`carrier`、`squad`、`sched_running`、`ignition_queue`、
`launch_queue`。健康位本期只有形状：登记缺省 Healthy=true，限额探测在 roadmap，探测结果
才有资格置 false——没限额数据的载体不得被静默饿死。

### 4.2 准入与队列（冻结清单条目，逐条可判 pass/fail）

1. 准入判据 = 小队计数 < 小队上限 **且** 载体计数 < 载体上限；两级独立计数，缺一不放行。
2. 载体上限是物理位（跨小队全局计数同一载体）；小队上限是政策位（按队计数）。
3. 抢并发时协调者优先：清队顺序恒为 `launch_queue` 先于 `ignition_queue`
   （`scheduling.QueueKinds` 是该顺序的唯一权威常量）；只在准入排序生效，**不抢占在跑任务**。
4. 队列顺序三级：就绪度快照降序 → 卡优先级（高=0 中=1 低=2，未知词垫底）→ 入队序升序
   （body.Seq 定格首次入队，registry.Seq 仅作终极 tie-break）。
5. Priority/Ready 是**入队时刻快照**，出队时不重读卡状态；新鲜性由出队后的协调者确认
   基线兜底（拍板记录②）。
6. 同一（卡,节点）重复入队按更新处理且保留原入队序；出队即删除（CAS 版本防并发双取）。
7. 计数与队列全量持久于 registry，agentd 重启不丢；恢复以账本为准不信内存。
8. 解析序：一次性覆盖（Target/Executor/Model）> 命中载体的 Machine/CLI/Model；
   成员按登记顺序找第一个健康且有空的载体。
9. 满员返回 `ErrNoSlot`（转排队的常态），小队内没有健康载体才返回 `ErrNoHealthy`
   （配置/限额问题）——两种失败处置不同，不得混用。

## 6. Keystone 域契约（d_keystone）

### 6.1 唤醒决策（事件清单的机械化）

```go
// internal/keystone/keystone.go
type WakeKind string // task_terminal | ticket | queue_release | message
type WakeEvent struct { Kind WakeKind; Card, Summary string }
type Decision struct { Wake bool; Reason string }
func (s *Service) Decide(ev WakeEvent) Decision
```

冻结决策表：四种 WakeKind 唤醒；清单外种类（progress/心跳类）一律不唤醒且必须给出原因。
`message` 种类为 B156.2 房间消息预留——通道未落地前不会产生该事件，接口形状先冻结。
attach 人工接管中（`SetAttach(card,true)`）时 Decide 对一切种类恒判不醒。

### 6.2 唤醒回合与兜底链

```go
func (s *Service) Wake(ctx context.Context, card string, evs []WakeEvent) (RoundResult, error)
func (s *Service) LaunchForCard(ctx context.Context, card, source string, spec keysclient.SessionSpec) (RoundResult, error)
func (s *Service) SetAttach(card string, active bool)
func (s *Service) AttachActive(card string) bool
func (s *Service) Locate(card, workdir string) (keysclient.AttachInfo, error)
type RoundResult struct { Woke bool; SessionID string; Rebuilt, Escalated bool; Output string }
```

1. **同卡合并**：Wake 的一批事件合成一次 runner 调用（一回合），开场简报携带全部积压摘要；
   醒来先读账对齐现场（GetCard/EffectiveBaseBranch/EventsFromAsc），以 ledger 为准不信记忆，
   天然幂等。
2. **两入口合一**：LaunchForCard 的 source 参数（card_create=开卡即绑 / manual=一键拉起）
   只进审计，两入口共用同一实现；人开会话领卡恒为合法第三通道（B156.2 已定，不在本域）。

## 10. 三重闸门拍板记录

命中三重闸门的决定共六项（难逆转 × 无上下文会惊讶 × 真取舍）：

1. **编制域持久化端口字节化**：`schedclient.Registry` 只收发序列化 JSON，编制域零 import
   账本类型。后人看到会想「改成 facade 类型别名更顺手」（被否方案：outward 接口直接引用
   ledgerapi.DTO）；改回去要动端口、服务、适配器三层。字节化的收益是两域可在不起账本下
   独立测试、账本 schema 演进不牵动编制域。
2. **就绪度/优先级入队快照定格**：出队不重读卡状态（被否方案：出队时实时查卡——会把
   编制域耦合回账本读面，且出队瞬间状态可能又变）。新鲜性责任明确移交给出队后的协调者
   开场评估（spec §5.2 本来就要求醒来先读账）。没有此记录，一次「修 staleness bug」就会
   把耦合加回来。
3. **attach 人工接管态只在进程内存**：不持久化。依据是环境事实——PTY 会话本就随 agentd
   生死（`internal/ptyhost/engine` 内存态），重启后接管态指向的对象已不存在；持久化会造成
   「永久静音」事故（自动唤醒永不恢复）。被否方案：持久化 + TTL。方向上宁可误唤醒也不
   可漏唤醒，因为误唤醒还有 Decide 的账本对齐兜底。
4. **注册表通用版本化 KV，而非逐实体建表**（carrier/squad/queue 各一表的被否方案）：实体
   形状仍在快速演化（限额探测、账户实体化都在 roadmap），逐实体建表把每次形状变更变成
   账本 schema 迁移。账本只承诺 CAS+版本+写入序，不理解 body——这正是「账本是设施、
   编制域是规则所有者」的执法形态。
5. **协调者优先只作用于准入排序，不抢占在跑任务**（spec 台账⑨的机械化落点）：清队顺序
   以 `QueueKinds` 常量冻结为本域唯一权威；反过来写不会有任何测试变红，故在此立字据。
6. **小队作为解析层、存量直绑降级为匿名单载体语义而不迁移**：workflow 定义不可变版本化，
   强迁移等于逼所有用户重新发布工作流。Squad 字段缺席 = 旧语义逐字节保留；这条反过来写
   （加载时自动补匿名小队对象）也不会有测试变红——禁止那种实现。
