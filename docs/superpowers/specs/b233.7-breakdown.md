### S1：Ask 原生身份与 permission 投递失败统一可见

#### ①契约引用

- contract §2.1、§2.2、§4；冻结 #1–#24。
- `internal/agentd/manager.go#Manager.Dispatch`、`internal/agentd/manager.go#Manager.waitQuestion`、`internal/agentd/manager.go#Manager.RelayAnswer`、`internal/agentd/manager.go#Manager.NoteDeliveryFailed`。

#### ②意图与为什么

把 native question 的稳定身份从产生、持久载荷到回答回程保持为同一个 QuestionID；已答问题可产生新的可答单，未答重放仍复用旧单。原生 permission 的失败必须成为 Manager 已有的 delivery_failed 权威事实，成功才形成 Delivered ack。S1 不决定 P1 的私有承载方案，不新增公共事件或 store 旁路。

#### ③验收

- 运行定向 agentd/executor 回归：给同一任务先产生一个带原生 QuestionID 的 ask，再答复后重新产生同一原生问题；穿过真实 ticketRequest JSON 后，第二张 ticket 可答、持久 question_id 与回程 RespondAsk.QuestionID 均等于原值，未答重放只保留一张 ticket/一条 ask 事实；没有原生 id 时才允许 uuid 兜底。
- 运行真实 manager → OpenCode adapter 的 permission 竖切测试：RespondPermission 失败时事件类型精确为既有 delivery_failed，payload 含 task:permission、真实原因（最长 500 rune）和可执行 hint，且不存在 AckDelivered；成功时才出现 AckDelivered/后续执行 ack。若 P1 尚未拍板，该验收只能标为待定，不得以 helper 单测冒充通过。
- 运行 JSON roundtrip 回归，区分 question_id 缺失、"" 和非空值；同时穿过 deliveryFailedPayload 的真实事件序列化边界，不能用两端各自 struct 单测替代。
- 错 task、错 ticket、重复答复必须返回非零且不改变原 ticket；原生问答/权限在真实 OpenCode 服务上的回程行为列真机清单。
- **生命周期/状态机中断：有风险。** Manager 在答复与 adapter 回传之间重启时，持久 QuestionID/ticket 是恢复依据；permission 失败事实的重启窗口由 P1 承载方案负责。旧 goroutine、未消费 ticket 和远端 pending request 是否最终回收，**未验证，需真机**，真机覆盖重启前后各一次 answer/permission。
- **静默失败/误导报错：有风险。** 当前 authorizeNativePermission 失败只写日志，正是本卡 R4；验收必须证明 failure 不再落入“返回成功/永远等待”窗口，delivery_failed 的 task/ticket/reason/hint 可行动。事件追加失败本身的存储告警与恢复，**未验证，需真机**。
- **跨平台假设：有风险。** OpenCode 的原生 HTTP/webview 回传、连接断开和权限模型是外部现实；Manager 内的 JSON/事件形状可机内验，跨 OS/CLI 行为**未验证，需真机**。
- **假红/假绿测试：有反面断言。** 测试必须穿过真实 JSON、Manager、adapter 和既有事件消费，且断言失败无 Ack、未答重放不增 ticket、错 ownership 被拒；只测 NamespacedTicketID 或 NoteDeliveryFailed helper 不能通过。并发 answer/permission 竞态**未验证，需真机**。
- **门禁绕过：有风险。** 所有回答仍须经过既有 task/ticket ownership、ApprovalClient 和 RespondPermission；adapter 不得直接写 store。检查 ownership 与动作之间的并发窗口、重启后旧 ticket 是否仍被隔离，**未验证，需真机**。
- **序列化边界：命中。** ticketRequest 的 question_id、Manager 的 JSON 读回、RespondAsk 的原生 id、deliveryFailedPayload 以及 event payload 都列入回归；缺失/空值/非空必须可区分。
- **枚举新值过既有白名单：无，因为复用 ask、question 与既有 delivery_failed，不新增事件名。** 仍需核对 EventTypeDeliveryFailed、WaitDeliveryPolicy、web/CLI event switch 均不会把失败吞成成功。
- **承重安全属性：有。** 一次性回答、同原生问题的未答去重、ticket 隔离、失败不 Ack 各需一支能变红的测试；不能只靠当前 map/内存态“恰好如此”。

### S3：ResultRef.Commit 驱动任务 diff

#### ①契约引用

- contract §2.4、§4；冻结 #35–#40。
- `internal/agentd/server.go#Server.handleTaskDiff`、internal/agentd/workspace_capability.go 的 Manager.assembleResultRef、internal/workspace/capability.go 的 Capability.DiffRange。
- 相关 internal/agentd/diffbase_test.go、resultref_test.go、server/HTTP diff tests。

#### ②意图与为什么

让 diff 调用方消费同一次任务结果组装出的权威 commit；准确 commit 存在时不再退回原始 head，缺 commit 时保持既有可观察 fallback 与日志。不改变 HTTP response 形状，不把空 Path 误判成必须阻断。

#### ③验收

- 通过任务 diff HTTP/Server 竖切，用 spy Capability 断言：assembleResultRef 返回非空 commit C 时，唯一 DiffRange 调用收到字节相同的 C；响应仍无新 commit 字段。
- 用 rev-parse 失败/空 commit 夹具，断言 DiffRange 收到原 headRev、日志含降级原因；Path 为空时请求仍按现有语义返回，不因空 Path 伪造“没有 diff”成功。
- **生命周期/状态机中断：无，因为 S3 不创建长寿命进程、ticket 或临时任务；**但真实 worktree 被回收/任务重启时 commit 是否仍可读，**未验证，需真机**。
- **静默失败/误导报错：有防线。** 组装 ref 失败必须保留真实原因并使用明确 fallback；非空 commit 被丢弃或错误 branch 仍返回 200 的窗口必须由 spy 反面断言抓出。
- **跨平台假设：有风险。** git 命令、路径权限、Windows worktree 与不同 shell 的 rev-parse 行为属于 boundary；Go 参数形状机内可验，真实多平台仓库状态**未验证，需真机**。
- **假红/假绿测试：有反面断言。** 测试必须穿过 handleTaskDiff 到 Capability，断言非空 commit 精确传递、空 commit fallback、无 response 字段；只测 assembleResultRef helper 会假绿。并发 worktree 变化**未验证，需真机**。
- **门禁绕过：有风险。** diff 必须沿已有 Server/Workspace 权限与路径校验；不能为拿 commit 另开读仓旁路。check 与 diff action 的 worktree 变化窗口，**未验证，需真机**。
- **序列化边界：命中。** HTTP 请求解码、Server 调 Capability、结果 JSON 编码都要断言 commit 不泄漏为新 response 字段、空 Path/缺 field 可区分；真实 git commit 作为外部载荷需用 roundtrip/spy 锁定。
- **枚举新值过既有白名单：无，因为 S3 不新增 diff/event/state 枚举。** 现有错误状态与 HTTP status 分支仍须逐项保持。
- **承重安全属性：有。** “非空 ResultRef.Commit 与 DiffRange 入参同值”必须有能变红的断言；错误 commit、空 commit fallback 和空 Path 允许性均需独立断言。

| 写/网络调用失败或收到 delivery_failed | 现有任务 status/event 与文档的 status-first 规则 | 协调者先 show/status，再决定 resume 或重新 dispatch | 文档不保证重派仍同一任务；用户不会把失败重试误解为幂等派发 | S6 |

闭环结论：七条跨子系统承诺均有归属；R4 的“失败事实如何跨 adapter→Manager”缺少当前代码中的既有载体，已在 S1/P1 和 contract §9 明示，未拍板前不准把该格写成已实现。

## 6. 真机清单（机内不能代验）

以下均显式标为**未验证，需真机**，归协调者在 acceptance/统一收尾执行；机内夹具通过不解除这些项。

1. OpenCode 原生 question 实际再问：前单已答与未答重放各跑一次，确认真实 CLI 的 question API 产生/复用的原生 id、真实 answer 回程和任务继续执行。
2. OpenCode 原生 permission 的真实回传失败：让 native endpoint/进程在决定落库后断连，确认用户能在真实 wait/status 看到 delivery_failed，resume 后任务能继续或转人工；覆盖 agentd 重启窗口。
3. 五家 executor 的普通任务 overlay：在各真实目标平台以生产规则文件名启动至少两个同名任务，确认 executor 实际消费任务层正文且不污染全局规则；覆盖文件权限、HOME、目录大小写和进程重启。
4. 真实任务 diff：任务完成、worktree 被回收/切换、commit 可读/不可读各跑一次，确认 UI/CLI 看到的是准确 commit diff 或明确 fallback，不把空 Path/旧 head 当成功事实。
5. WakeHome：在 macOS/Linux/Windows（可用目标）分别覆盖 CLI 真可用且有非空输出、凭据存在但 CLI 不能回合、空输出、webview/权限阻断；确认 readiness 与机内 probe 结论一致。
6. B350 真实 carrier：用物理 carrier CLI 与请求 override 冲突的 admission/点火流程，确认实际启动的是 carrier CLI/Home/Target，模型覆盖仍按既有限制；覆盖离线、满槽和重启回收。
7. 直连/relay 网络失败与文档处置：真实 write/reply 失败先查 status，再由协调者分别选择 resume 或重新 dispatch；不把任一次结果写成“重派同任务”保证。
8. 所有涉及“重启后无孤儿 task/ticket/overlay/进程”的结论：必须观察真实 agentd、executor、临时目录、pending ticket 和工作树回收；机内测试只锁持久字段/错误形状，不能证明回收行为。
