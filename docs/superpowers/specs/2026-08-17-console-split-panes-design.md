# 控制台分屏：三栏封顶、可拖拽、⌘D

> 上游：`2026-08-12-w4-shell-calibration-design.md` §2.1「tab 组与分屏」。
> 那一期把分屏做成了「面包屑右侧一个按钮 + 最多两组 + 固定五五开」，本轮补齐它欠下的三件事。
>
> 影响面只在 `web/src/app/workbench/` 与 `web/src/app/shell/`，不动后端、不动 API。

## 为什么要有这一轮

用户的原话是「我们当初说好做左右分屏的，但是现在无法分屏」。

08-17 在真实控制台（`127.0.0.1:7777`）实测复现，结论是**分屏功能本身是好的**——点面包屑右端的分栏图标一次，中央区确实分成左右两组。用户撞到的是另外两件事：

1. **找不到入口**。图标在**中间栏**面包屑的右端，它右边还压着 280px 的文件树，所以它不在窗口的右上角。用户按 Orca 的肌肉记忆往右上角找，扑空。
2. **⌘D 按了没反应**。全站只注册了 ⌘K / ⌘T / ⌘O / ⌘A / ⌘S，从来没有 ⌘D。

顺带查出第三件当时被判为「本期不做」、现在该还的债：

3. **第三次点击是静默空操作**。`splitGroup` 在已有两组时原样返回（`tabs.ts:222`），按钮不给任何反馈——从用户视角看，这与「按钮坏了」不可区分。

**入口位置本轮不动**：用户在实测截图里看到图标之后当场决定「就放在那儿吧」。挪到窗口右上角需要新起一条横跨全宽的顶栏（现在的壳是三列 flex，顶部没有通栏），代价与收益不成比例。

## 0. 本轮做什么

| # | 事项 | 判据 |
|---|---|---|
| 1 | 分屏上限 2 → 3 | 连点三次分屏得到三栏；第四次按钮已是 disabled |
| 2 | 分屏比例可拖拽 | 拖分隔条改变两侧宽度，任一侧不小于 240px |
| 3 | ⌘D 快捷键 | 任意焦点下按 ⌘D 分屏，且不弹浏览器书签框 |
| 4 | 到顶时按钮 disabled | 三栏时按钮置灰、`title="最多三栏"`，不再静默无效 |

**不做**：挪图标、上下分屏、拖 tab 跨栏、比例持久化、新栏预填内容。逐条理由见 §6。

## 1. 组数上限：2 → 3

### 1.1 上限值与不变式

`tabs.ts` 提一个常量：

```ts
// MAX_GROUPS 是中央区最多能分出的栏数。
//
// 为什么是 3 而不是「无限」：1280px 宽度下减去左树 260 与文件树 280，中央区
// 只剩 740px；三栏时每栏 ~245px，刚够放下一个 tab 标题加关闭按钮（这也是
// §2.3 那个 240px 最小宽度的来源）。第四栏必然要靠横向滚动或折叠 tab 条
// 才能存在，那是另一个形态问题，不是把上限数字改大就能解决的。
export const MAX_GROUPS = 3
```

`Workbench.groups` 的不变式从「1 或 2 组」放宽到「1..MAX_GROUPS 组」。`splitGroup` 的判据换成 `wb.groups.length >= MAX_GROUPS`，其余逻辑不变。

### 1.2 新组插在末尾，不插在当前栏右边

VS Code / Orca 的语义是「在当前 pane 右侧插入一栏」。**本轮不这么做，新组仍然 push 到数组末尾。**

理由是一处真实的失效窗口，不是省事：`(group 下标, tabId)` 二元组是全代码库定位一个 tab 的方式，而 `Shell.tsx` 的 `closingPty`、`closingDirtyFile` 在确认弹层打开期间把这个下标**存进了 state**。紧邻插入会让后面所有组的下标 +1，于是弹层里存着的下标指向别的组——用户点「确认关闭」，关掉的是另一栏的 tab。要正确支持紧邻插入，得先把全局寻址从「组下标 + tabId」换成「全局唯一 tabId」，那是一次波及 `TabBar` / `WorkbenchPage` / `Shell` 的重构。

三栏封顶下，两种插入方式的可观察差别只有一条：焦点在第 1 栏时按分屏，新栏出现在最右而不是紧邻右侧。代价与那次重构不成比例。

> 这一条是有意的取舍，记在这里是为了将来真要做「拖 tab 跨栏 / 无限分屏」时知道**先还哪笔债**。

### 1.3 关空一组后的焦点接替（必须跟着改）

`tabs.ts:170-175` 现在是：

```ts
if (g.tabs.length === 0 && next.groups.length > 1) {
  next.groups.splice(gi, 1)
  next.active = 0          // ← 写死回第 0 组
}
```

两组时 `0` 恰好就是「另一组」，所以这个写死一直没暴露。三栏时它会让焦点从被关掉的第 3 栏莫名跳到最左边。改成接替相邻组：

```ts
next.active = Math.min(gi, next.groups.length - 1)
```

**这是提上限必须跟着改的一处，不是顺手改**：不改的话「关掉最右一栏，焦点跳到最左」是三栏才出现的新缺陷。

## 2. 宽度模型

### 2.1 sizes 存在 Workbench 里

```ts
export interface Workbench {
  groups: TabGroup[]
  active: number
  // sizes 是各栏的宽度权重，与 groups 等长，渲染时作为 flexGrow 用。
  // 单位是相对权重不是像素：容器宽度会随窗口、随左右栏的显隐变化，
  // 存像素等于每次窗口 resize 都要重算一遍并处理「加起来不等于容器宽」。
  sizes: number[]
}
```

`EMPTY_WORKBENCH` 相应变成 `{ groups: [...], active: 0, sizes: [1] }`，`cloneWorkbench` 要把 `sizes` 一起拷（它现在只拷到 groups 与 tabs 两层）。**不变式：`sizes.length === groups.length` 恒成立**，所有改动组数的函数都要维持它——这是 §2.2「组数一变就重置等分」在实现上唯一需要记住的事。

跟着 `useWorkbench` 的 `byBase` 按基准分持——切目录整组换掉、切回来连比例一起恢复，与 tab 组同一口径。

**不持久化**，刷新即丢，与 shell-calibration spec §10「tab 组存内存」一致。

### 2.2 组数一变就重置为等分

`splitGroup` 与 `closeTab`（关空一组那一支）都把 `sizes` 重置为等分。

**不做「从当前栏借一半」**：借了之后关掉该还给谁？还给原来那栏还是均摊？两种都能自圆其说，于是就有了第三种状态。等分是唯一不需要记「这份宽度是从谁那儿来的」的规则。用户手动拖过之后 sizes 才非等分，直到下一次组数变化。

### 2.3 最小宽度 240px

拖拽时两侧都夹住 240px 下限：拖到底就停住，不允许把一栏压成一条缝。240 的来源见 §1.1 的注释——TabBar 放得下一个 tab 标题加关闭按钮的下限。

容器窄到连 `240 × 组数` 都放不下时（比如用户把窗口拖到很小），**不自动合并栏**，交给容器横向滚动。自动合并会让「窗口拖小一下，我的 tab 组没了」——那是不可逆的数据丢失，而横向滚动只是难看。

## 3. 拖拽分隔条

现在 `WorkbenchPage` 用 `gap-px bg-border` 制造 1px 分隔线，那只是背景色透出来，不是元素。改成显式组件：

```
<section 组1 /> <Divider /> <section 组2 /> <Divider /> <section 组3 />
```

`Divider`（新文件 `web/src/app/workbench/GroupDivider.tsx`）：

- `role="separator"`、`aria-orientation="vertical"`、`aria-label="调整栏宽"`
- 视觉 1px（沿用 `bg-border`），命中区 5px，hover 时加深，`cursor-col-resize`
- pointerdown 时 `setPointerCapture`，pointermove 把位移换算成两侧权重写回，pointerup 释放
- `tabIndex={0}`，← → 每次调 2%——既有代码在 a11y 上一直是认真的（每个图标按钮都有 `aria-label`），一个只能用鼠标的控件是倒退

纯函数放 `tabs.ts`，组件只管事件：

```ts
// resizeGroups 把第 i 个分隔条左右两栏的宽度按 delta 重新分配。
// delta 是相对容器宽度的比例（正数 = 分隔条右移）。两侧都夹在 minRatio 之上。
export function resizeGroups(wb: Workbench, dividerIndex: number, delta: number, minRatio: number): Workbench
```

`minRatio` 由组件传入而不是纯函数自己算：`240 / 容器宽度`，而容器宽度只有 DOM 知道。纯函数拿到的是一个已经无量纲的比例，测试里直接给 `0.2` 这种值就能断言夹紧行为，不用去 mock 布局。

**终端不需要特殊处理**：`TerminalTab.tsx:154` 已有 `ResizeObserver → fit.fit()`，而 `term.onResize`（`:145`）只在 cols/rows **真的变了**才往 WS 发 resize 帧。拖拽经过一个字符宽度才发一帧，不会打出一串无谓的帧。

## 4. ⌘D

### 4.1 注册位置：window 级，在 Shell

和 `BlankTab` 的 ⌘T 走**面板级**监听正相反。那里是有意为之（`BlankTab.tsx:75`）：分屏后屏上可能有两个空白面板，window 级监听会让一次 ⌘T 开出两个终端。⌘D 没有这个问题——它只作用于**当前焦点组**，全局唯一，所以 window 级正好。

### 4.2 必须 preventDefault

macOS 浏览器里 ⌘D 是「加入书签」。不拦就会在分屏的同时弹出书签面板。

**不排除输入框**：⌘D 在 `<input>` / `<textarea>` 里没有默认语义，排除它只会让「光标在 Composer 里时 ⌘D 不好使」变成一个要解释的例外。

### 4.3 到顶时的行为

- **⌘D**：静默无效。快捷键没地方挂提示，弹 toast 属于反应过度。
- **按钮**：`disabled` + `title="最多三栏"`。这一条直接回应用户「点了没反应」的困惑——位置不动，但让「到顶了」看得见。

## 6. 不做，以及为什么

| 不做 | 理由 |
|---|---|
| 把图标挪到窗口右上角 | 现在的壳是三列 flex，顶部没有通栏；要「真正的右上角」得新起一条横跨全宽的顶栏。用户在实测截图里看到图标位置后当场定了「就放在那儿吧」 |
| 无限分屏 | 见 §1.1：1280px 下第四栏必须靠横向滚动或折叠 tab 条才能存在，那是另一个形态问题 |
| 新栏预填当前 tab（Orca / VS Code 的 ⌘D 语义） | 会撞上跨组去重不变式（`tabs.ts:125`：同一个目标在任何组里只开一份）。同一个文件在两栏各开一份，「哪份是真的」当场变成问题，文件类得单独设计。用户选了保持空栏 |
| 上下分屏 / 拖 tab 跨栏 | 都要先把全局寻址从「组下标 + tabId」换成全局 tabId（见 §1.2） |
| 比例持久化 | 与 tab 组不持久化同一条口径；单独持久化比例会出现「刷新后 tab 没了、比例还在」 |
