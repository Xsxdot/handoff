# B448 协调者首轮拉起按载体机转发

- 状态：**待批准**（2026-10-19 起草）
- 级别：**L3**（agentd 跨机：新增 agentd↔agentd 的转交 wire 契约，叫机器人与建会话驻场者两条拉起路径都改；不扇出，单卡一轮）
- 难度与分工（全局规则「按级分工」）：**高难度**——新增跨进程契约面，且真机须两台 agentd 共库 → **主会话亲自盯**。人可推翻。
- 来源：2026-10-19 人在 E13/E16 会话撞「leader 指向 cline（linux-01）仍是远端被拒」，问「为什么一定要本机」；B444 finish 的 roadmap 残余「建会话 / 叫机器人只接受本机载体」。

## 问题陈述

协调者首轮（卡「叫机器人」、B444 建会话 / 叫驻场者）只能由**载体所在机**的 agentd 受理：

- 现状读数：`runOnCoordinatorCarrier`（`internal/agentd/scheddrain.go:375`）在受理请求的 agentd 进程里拉起载体 CLI；载体登记在别的机器时直接拒绝（`scheddrain.go:391-398`「print 协调者只支持本机载体」）。
- 人用的是控制台所在机（今天 mac-mini），协调小队的载体在 macbook-pro / linux-01 → 叫机器人与建会话都失败；CLI `card coordinate` 在非载体机执行同样失败。
- 而**续轮唤醒早已跨机**：席位承载在远端时转交给承载机 agentd 执行（`transferCoordinatorWake`，`scheddrain.go:434`；收件端 `handleCoordWake`，`coordapi.go:172`，CAS 校验席位后本端执行）。首轮拉起是唯一没接上转交的一环——这是缺口，不是设计约束。

## 方案

**首轮拉起与续轮唤醒同形：受理机选定载体后，载体在远端就把「这一轮」转交给载体机 agentd 执行；载体机在本机拉起、落席位/驻场行、持有名额；受理机同步等回执并原样回给调用方。**

1. 受理机照旧按小队准入**选定载体**（`LaunchAdmit`）。载体在本机 → 行为完全不变。
2. 载体在远端 → 受理机**立即归还**刚占的名额，把请求连同「冻结载体」转交给载体机（经设备表客户端池，带防环头，与续轮转交同一出站面）。
3. 载体机收到转交：按冻结载体**重新准入**（`AdmitSeatCarrier`，与续轮转交收件端同口径，名额由执行机持有、执行机归还），然后走本机拉起路径——卡：首轮 + 落 push 席位与承载（含 B446 自坐兜底）；会话：B444 的「先坐下→拉起→补写 push_session」全套与失败处置（请下 + 指针行）。
4. 回执原样回给受理机，受理机按今天的 HTTP 映射回给调用方（成功 200；名额满 409；席位冲突 409；其它 502）。
5. 防环：带转交头的请求，载体若仍不在本机 → 拒绝、不再转交（两机设备表不一致时不打乒乓）。

**弃选**：
- **受理机持有名额、远端只跑回合**——受理机若在等待中途重启，名额挂在受理机名下无人归还（只能等启动对账）；而且与续轮「执行机持有」两套口径。弃。
- **把整条原请求原样转给载体机、由它重新选载体**——小队成员可能分布在多台机，受理机不先选载体就不知道该转给谁；远端再选可能选到第三台。弃。
- **前端按载体机直连对端 agentd**——控制台要持有每台机的令牌与可达地址，CLI 也得各自实现一遍；转交收口在 agentd 一处。弃。

## 落位三问

① **权威数据**：载体与名额归调度领域（共享账本里的占用计数，`internal/scheduling/scheduling.go:1231 stepRunning`）；席位与承载归卡账本；驻场行归会话领域——都在**共享账本**，执行机直接写，不新增跨机写协议。转交只是「在哪台机跑这一轮」的编排，由 **agentd 编排层**收口（第六条）。
② **谁消费**：受理机 agentd 经 **agentd HTTP 契约面 + `internal/client`** 调载体机 agentd（第四条；同续轮转交的既有方向）；Web 与 CLI 不变，仍只打本机 agentd。
③ **同步/异步**：**同步**——调用方今天就同步等首轮（叫机器人、建会话都是），转交只多一跳，不改调用方语义（第十二条：调用方需要结果、失败须即时可见、无排队需求）。

## 目标架构与接缝语义

- **新增一个 agentd↔agentd 转交端点族**（卡首轮、会话驻场者首轮各一，或一个带类型的端点——签名归 plan）：请求带冻结的小队 + 载体（+ 卡号 / 会话号），必须带防环头；收件端只在载体是本机时执行，否则拒绝。它是**新的跨进程 wire 契约**，plan 须在「需冻结的外部承诺」节冻结（混版本：老对端 404 → 受理机报「对端 agentd 版本过旧，请升级 <机器>」）。
- **收口点**：转交判定放在 `runOnCoordinatorCarrier` 这一共用拉起骨架上（卡与驻场两个调用方共用，B444 已抽出），不在两个 handler 里各写一遍。
- **允许的依赖方向**：agentd → client（转交出站，既有方向）；不新增 scheduling / ledger / collab 对外依赖。
- **执行机身份**：「载体是不是本机」沿用 B441 统一判据（自名 / 设备表），目标机地址经设备表客户端池解析（B441 `clientForTarget`）。

## 首故事

单卡一轮不扇出。实现顺序上 **S1 先行**（卡叫机器人跨机）：它定下转交契约、名额归属与失败映射；S2 在其上复用同一骨架。

## 实现决定

- 用户可见文案：对端不可达 → 「协调者载体 <载体> 在 <机器>，转交到该机失败：<原因>」；老版本对端 → 「<机器> 的 agentd 版本过旧，不支持首轮转交，请升级」；防环拒绝 → 「转交到本机的协调者首轮，但载体 <载体> 不在本机（设备表不一致？）」。
- 现有提示「请把协调者小队的成员指向本机载体」删除（不再成立）。
- 超时：转交出站超时 ≥ 本机首轮回合超时（今天 30 分钟），不得比本机路径更早放弃。
- 日志：受理机与执行机各落一行带「受理机 / 执行机 / 载体 / 卡或会话」的转交日志，两端可对账。

## 测试决定

- 真实入口：`POST /api/cards/{id}/coordinator/launch`、`POST /api/sessions`（带 squad）、`POST /api/sessions/{id}/resident/launch`；CLI 三条命令走同一 HTTP。
- 竖切：两个 agentd 进程（测试内起两个 Server 共一个账本，或真机两台）——受理机拉起 → 转交 → 执行机 fake Runner 收到 Launch → 席位 / 驻场行落库 → 受理机返回。
- 反例：老对端 404；对端不可达；对端名额满；防环二跳；本机载体不经转交（既有测试零改）。
- 序列化边界：转交请求 / 回执穿过真实 HTTP 编解码，断言冻结载体字段缺失时收件端拒绝（区分缺失与空）。
- 真机：linux-01 上建临时 PG 测试库，**两台隔离 agentd**（linux-01 与 mac-mini 各一，独立端口 / HOME / datadir，共用该测试库与一张设备表）；载体在 linux-01（opencode 免费模型），从 mac-mini 隔离实例的控制台叫机器人与建会话。**不碰在役 7777、不碰生产账本。** 通过后上 fleet 生产复核（mac-mini 控制台 → macbook-pro 载体）。
- 顺带清 B444 残余「PG 迁移腿未跑」：本卡真机本就用 PG 测试库，B444 / schema 版本闸的 PG 用例一并在该库跑一次。

## Out of Scope

- **永不做**：前端按载体机直连对端 agentd（弃选理由见上）。
- **本期不做、后续要做**（落 roadmap）：
  - 转交途中受理机已向调用方超时而执行机仍在跑时的「结果找回」（今天本机路径同样没有：调用方断开后首轮照跑、席位照落，人刷新可见）。
  - 小队成员跨多台机时的「就近选载体」偏好（今天 LaunchAdmit 的选择规则不变）。
