## 4. 架构户口

### 4.1 不新立顶层 harness 子系统

架构法第一条：值不值得为这条缝付冻结成本来换**并行开发**？本卡选轻档，明确不拆并行子卡。五类能力是同一提供方面上的子集，不值得改 `best.json` 结构树。

- 不新增 `d_harness`。
- 能力接口落在既有 `internal/executor`（`d_execution_contract`）。
- `hostapi` 仍归 `d_execution_host`（包注释已声明「同属 d_execution 顶层域」）。**不把 hostapi 升格或搬出执行域**。
- `keysclient.Runner` 仍是 keystone 出站缝的现状类型；实现节点改为持有 `Coordinator`，不在本节点改 keystone 生产 import（避免 Ticket 0 先开 `d_keystone→d_execution` 死契约）。
- 物理搬目录是父卡 B233 的 OOS。

### 4.2 依赖方向

| from → to | 本卡 | 说明 |
| --- | --- | --- |
| `d_orchestration → d_execution` | 既有，预算 27 | Manager / Approver 持 Adapter 与将来的 Coordinator/OneShot/Profile。本节点不新增 call 边 |
| `d_keystone → d_execution` | **预定**，零预算 + `interfaces: ["Coordinator"]` | 待 `keysclient`/keystone 首个消费边同提交写入。现在写入会 dead-contract |
| `d_cli → d_execution` | 既有预算 11 | `handoff skill install` 将来持 `Skills`；本节点不改 cmd 生产路径 |
| `d_execution → d_policy` | **禁止** | adapter 不得直达 `permgate` |
| `d_execution` 各家包 → `agentd.Approver` 具体类型 | **禁止**（除组装点） | 接 233.1 |
| `keysclient` / `Manager` → 某家内部路径知识 | **禁止** | 不得再写 `.config/opencode` 或 `switch executor` 拼 argv |
| `d_execution → d_orchestration` | 既有 `ApprovalClient` 缝 | 本卡不改 |

组装点仍是 `main.go` / `internal/agentd/server.go` / `cmd/agentd.go`（adapter 表）。具体 Provider 只在组装点绑定。

### 4.3 能力契约在提供方

消费方不得对同一能力二次抽象。因此：

- 不在 `keysclient` 再定义一套与 `Coordinator` 方法语义不同的能力接口。
- 不在 `Manager` 再定义一套与 `Adapter` 平行的 `Executor`。
- `hostapi.Host` 保持进程承载门面，不是第三套协调契约。

### 5.1 能力报告（`internal/executor/capability.go`）

```go
type CapabilityName string // "execution" | "coordination" | "oneshot" | "profile" | "skills"

type CapabilityDecl struct {
    Name         CapabilityName
    Supported    bool
    NativeLimits []string

    Harness string

type Provider interface {
```

`BaselineReport` 是查询面金样本，不是「已经接线」。

### 5.3 协调会话（`internal/executor/coordinator.go`）

54. adapter 不得 import `internal/permgate`（除组装点）。
55. adapter 不得引用 `agentd.Approver` 具体类型（除组装点）。

## 8. 三重闸门拍板记录

命中三条的决定：

1. **五类能力接口定义在 `internal/executor`（提供方契约包），不按第九条拆到各消费方。** 回头要动编排、keystone、CLI skill、执行四域与目标图；后人看到 `Coordinator` 住在 executor 会想「搬回 keysclient」。被否方案：在 keysclient / Manager / skill 各定义一套能力接口（二次抽象，正是 spec 禁令）。不做新顶层 `d_harness`。
2. **执行会话不另立 `Executor` 接口，沿用 `Adapter` + 可选 `Recoverer`。** 加平行接口会让 Manager 同时持两套执行面；后人看到「能力归拢」会想再包一层。被否方案：新 `Executor{Start,Events,Send,Stop}`。AskResponder 继续不进五动作。
3. **grok `--effort low` 是调用方 Limits，不是 grok 一次性默认。** 反过来把 low 写回 `OneShotArgv` 默认，现有 `TestOneShotArgs` 仍绿。被否方案：把「一次性 = 廉价」继续编进 `OneShotArgs`。审批侧传入 `EffortLow`。
4. **`hostapi` 留在 `d_execution_host`，`RunTurn` 不是消费方面。** 把 hostapi 收成 Coordinator 会让 keystone 依赖进程承载实现细节；搬出执行域要改结构树。被否方案：把 hostapi 升格为协调子系统，或让 keysclient 继续当唯一协调契约。
5. **Profile 与 `ProbeHome`/`WakeHome` 不合并。** 反过来写成一个 Inspect，B293 的登录三态与本卡的规则/skill 供给会缠在一起，现有探测测试仍可能绿。被否方案：把 Prepare 塞进 WakeHome。
6. **argv 编码留在各家包，不在 executor 再开第二张 `OneShotArgs` switch。** 反过来在契约包集中拼 argv，消费方看起来干净、提供方边界被架空。被否方案：用 `EncodeOneShotArgv` 替换 `OneShotArgs` 仍放在契约包。

显式不做（spec 已否，此处不重复展开）：只迁 OpenCode+第二家、逼每家长出协调会话、复制会话库/整棵 HOME、OpenCode 真机走付费会员模型、本卡做首次安装/自动发现、跨机传输（B233.3）、物理目录搬迁。
