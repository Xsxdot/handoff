## 定级理由

四条都是局部修，不新增跨子系统能力，不值得付 L3 契约冻结成本换并行开发。

- B243 / B242 收口在环节执行体对「回合终态 / 裁决块」的消费。
- B244 改回合协议铁律的**提示词原文**，trailer JSON 字段集合不变。
- B241 给既有 HTTP 投影补一个 `omitempty` 字段。派发路径今天已经直读账本，不走这条投影。

计划写出来不会只复述本页（宽限怎么注入、容错解析的失败分级、铁律措辞要过既有 prompt 单测），所以不是 L1。

## 问题陈述

谁：走 charter 流的协调者。  
通道：`card dispatch --step` → 执行者回合 → 环节等终态 → 解析 `handoff-verdict` → 按 pass/fail 路由。  
要变的事实：这一轮的真实结论必须到达路由，不能被「半成品 completed / 打碎的 JSON / 互斥铁律 / 丢掉的 purpose」静默弄丢。

四条各自的失败形态：

| 源卡 | 谁观察 | 今天发生的事 |
|---|---|---|
| B243 | 环节执行器 | 同一回合两条 `completed`，先到的没有 `final_text`。等终态的人被第一条叫醒，把摘要当成报文，裁决围栏丢失，整轮转等人。 |
| B242 | 环节执行器 | 围栏拿到了，`notes` 里未转义引号把 JSON 截断，`verdict=pass` 也解析失败，整轮转等人。 |
| B244 | 只读节点的执行者 | 铁律第 2 条无条件要求 commit；角色纪律禁止改工作树。执行者现场发明「交一份台账」或 `git archive` 副本。 |
| B241 | 控制台 / HTTP 读工作流的人 | 账本里 review 节点有 `purpose=review`，HTTP 投影丢掉它。前端类型已经有这个字段。控制台读-改-存会把 purpose 从下一版工作流里抹掉。 |

B243 与 B242 都表现为「裁决解析失败」，**根因相反**：B243 是围栏没送到解析器；B242 是送到了但 JSON 非法。测试必须能把两条分开，禁止用同一条夹具冒充。

## 方案

四条不共享抽象，禁止抽公共框架。各自改法如下。

### B243：消费侧等「带 final_text 的 completed」

现状（`internal/ledgerstep/wire.go#waitForTurnEnd`）：只看 `event.Type`，`completed` / `turn_failed` / `failed` 一律立刻返回，不读 payload。生产接法（`internal/ledgerstep/runner.go#awaitNode`）把阻塞的 `Client.WaitEvent` 传进去：返回一条可动作事件就把 cursor 写到该 seq（`internal/client/client.go#WaitEvent`），下一次从下一条开始阻塞，**自己没有超时**。随后 `finalMessageFromEvents` 倒序找 `completed`，没有 `final_text` 就回落 `summary`。

生产侧发两条 completed 是刻意的（迟到成功结果要补回重启丢终态的报文；空 `FinalText` 在 `internal/agentd/manager.go` 收成缺字段、键省略）。本卡**不改生产侧**。

推荐：

1. `waitForTurnEnd` 必须反序列化 `completed` 的 payload，语义与 `finalMessageFromEvents` 同一套：非空 `*final_text` 才算「有正文」；字段缺失进入宽限；显式 `final_text:""` **不算**有正文。
2. `completed` 且有非空 `final_text` → 终态。
3. **从未出现过任何 `completed`** 时，`turn_failed` / `failed` → 立刻终态（失败回合不得挂死）。
4. `completed` 但没有非空 `final_text` → **还不是终态**，从这一刻起进入秒级宽限（覆盖已观测 65ms / 214ms，且远小于 stalled 看门狗）。
5. **宽限怎么打断阻塞的 WaitEvent**（审查 Issue 1，必须按此实现，否则故事 2 挂死或把到期误报成「未取到裁决报文」）：
   - 残缺 `completed` 已经交付、cursor 已越过它。后续每一次传入 `wait` 的 ctx 必须是 **parent 的 child deadline**（宽限时长），不是再调一次无 deadline 的 `WaitEvent`，也不是 `Sleep` 完再 Attach，也不是另起一个不取消的 WaitEvent goroutine（goroutine 会在 `Done` 之后仍推进 cursor）。
   - child `DeadlineExceeded` 且 **parent 仍活着** → `waitForTurnEnd` 返回 **成功**（不是 error）。然后 `clientFinalMessage` / Attach 回落 `summary`。第一条残缺 completed 仍在 `RecentEvents` 窗口里。
   - parent 取消（停环节、agentd 退出）仍原样报错，宽限不得吞掉。
6. **宽限期内的 `turn_failed` / `failed` 不打断**（审查 Issue 3 选 a，不依赖 `handleResult` 丢掉 trailing 失败那道守卫）：继续等带非空 `final_text` 的第二条 `completed`，或等到宽限到期。到期后交给现有 `finalMessageFromEvents`（completed 优先于 trailing `turn_failed`）。未出现过 completed 的真失败仍走第 3 点，一次返回。
7. 取报文：多条 `completed` 时非空 `final_text` 优先；跳过显式空串；全都没有非空正文时，缺字段的那条回落 `summary`，**只剩显式空串则报错**，不回落 summary（与存量 `wire_test.go`「显式空串报错」一致）。

宽限时钟必须可注入，单测不睡真实时间。接缝 1 的 fake `wait` 必须在 `ctx.Done()` 上返回，否则锁不住这条活路径。

弃选：改生产侧攒齐再发唯一一条（与重启补报文决议冲突）；读到无 `final_text` 就重读一次 Attach（定时器补丁，当退路不写进判据）；宽限期内把 `turn_failed` 当立刻终态并依赖 `manager.go` 丢弃守卫（审查 Issue 3 的 b，现网碰巧挡住、流中断会重开 TOCTOU）。

### B242：解析侧容错，不改执行者要写的格式

现状（`internal/ledgerstep/verdict.go#ParseVerdict`）：只对**最后一个**围栏做整段 `json.Unmarshal`；失败则 `haltForHuman("裁决解析失败")` 把整份报文写成评论。抢救成功走 `RecordReviewVerdict`，只存 `verdict.Raw`，不会自动写那条失败评论。

推荐：先走今天的严格解码。失败后只在**已经切出的最后一块围栏正文**里抢救（禁止在整份回合文本上扫 `"verdict"`）：

- `verdict` 取该正文里**第一个** `"verdict":"pass"` 或 `"verdict":"fail"`（对象字段在前、notes 在后；last-match 会把 notes 里引用的 `"verdict":"pass"` 当成结论，审查 Issue 4）。
- 读到 ∈ {pass,fail} → 按该值路由，本轮**不**因 notes 损坏转等人。
- `findings` 能解出来就保留，解不出来当空切片，不猜。
- `notes` 解不出来就留空。
- `Verdict.Raw` 抢救后仍是**围栏原文**，不得改写成重建的 `{"verdict":"pass"}`。
- notes 被丢弃或 findings 被清空时，调用方必须再写一条普通评论（或等价 timeline 事件）说明抢救过、哪段丢掉了。不能只靠 Raw——成功路径今天不走 `haltForHuman`。
- 围栏不存在、`verdict` 读不出或不在 {pass,fail} → 仍失败，行为与今天相同。

弃选：改围栏格式让 notes 走 heredoc（所有执行者一起改，本期不做）；只靠纪律要求执行者转义（靠自觉）。

### B244：铁律第 2 条把「是否 commit」交给角色纪律

现状（`internal/executor/turn/protocol.go` 的 `ProtocolRules` 第 2 条）：无条件「必须 git add 并 commit」，然后输出 trailer。trailer 的解析不校验「这是不是新提交」；无 trailer 时才用 git 实况兜底。

推荐：第 2 条改为——

- 仍必须输出同一条 trailer JSON（字段不增不减）。
- **是否 commit 听角色纪律**：角色禁止改工作树 → 不 commit，`commit` 填当前 HEAD；角色要求提交 → 维持今天的「必须 commit」。
- 不改 trailer schema，不允许 `commit` 为空（空值会把 completed 链上的 hash 弄丢）。

弃选：给 `RenderPrompt` 按 purpose 分叉两套铁律（purpose 与「只读」不是一一对应，recon 要提交视图）；允许 trailer.commit 为空由 agentd 回填（动 completed 契约，本期不做）；只在角色纪律里写解法、铁律原文不动（冲突仍在 prompt 里）。

### B241：投影补上 Purpose

现状：账本 `internal/ledger/types.go#NodeOverride` 有 `Purpose`。`internal/proto/ledger.go#NodeOverride` 没有。`internal/agentd/ledgerapi.go#ledgerNodeWire` 只抄四个字段。

派发不走这条投影：`internal/ledgerstep/runner.go` 把 `node.Override.Purpose` 传给 `PurposeOverride`；`internal/agentd/cardstep.go` 的 HTTP 派发同样 `ResolveNode` 直读账本。B183 不会沿 CLI / 看板派发静默复活。

GET 工作流走投影。前端 `web/src/api/ledger.ts` 的 `NodeOverride` **已经有** `purpose?`。控制台读-改-存会把账本里的 purpose 从下一版本抹掉。

推荐：proto DTO 补 `Purpose`（json `purpose,omitempty`），投影抄上。列表接口（`handleFlows`）今天已经把账本 `Def` 原样序列化，**已经含 purpose**；详情 GET 走投影才会丢。编辑器走详情 GET。补上之后 GET 与列表对齐。

PUT 解码的是账本类型，客户端**送来**该键就会留下。抹掉发生在 GET 丢掉 → 编辑器 `purpose` 为空 → PUT 没有该键。所以本卡锁的是「GET 读回 + 把这次 GET 的 nodes 原样 PUT 回去再 GET 仍在」，不是「只 marshal 投影函数」。

弃选：只改控制台展示、不补 proto（读-改-存仍然丢字段）；只测投影函数、不经 HTTP（审查 Issue 5：与已有 produces 投影单测同级，锁不住读-改-存）。

## 用户故事

1. 同一回合先到一条没有 `final_text` 的 `completed`、65–214ms 后再到带围栏的那条：环节按带围栏的那条路由，不转「等人·没有 handoff-verdict」。
2. 只有一条没有 `final_text` 的 `completed`（老执行器 / 对账补发不带 `FinalText`）：宽限到期后仍能收口，取摘要，**不挂死、不报「未取到裁决报文」**。
3. **从未出现过 `completed`** 的 `turn_failed` / `failed` 一到就收口，不等 `final_text`。宽限期内（已经见过残缺 completed）的 `turn_failed` **不**切断等待。
4. 围栏里 `verdict`/`findings` 合法、`notes` 含 `"enabled":true` 这类未转义引号：按 `verdict` 路由，不转等人；Raw 仍含损坏的 notes。
5. 围栏缺失或 `verdict` 不是 pass/fail：仍解析失败，转等人（不放宽）。`verdict=fail` 且 notes 里出现 `"verdict":"pass"`：仍是 fail。
6. 只读角色按铁律收尾、不建新提交、trailer.commit 为当前 HEAD：回合按完成收口，不强迫交台账。
7. 产出型角色的铁律仍要求 commit，回归不回退。协议层不点名 review/recon。
8. `GET /api/flows/{name}` 的 JSON 里，charter 的 review 节点带 `override.purpose = "review"`。把这次 GET 的 nodes 原样 PUT 回去，再 GET，purpose 还在。

## 实现决定

- 四条按源卡独立落地，不抽「白跑框架」。
- B243 的宽限可注入；默认秒级；单测不睡真实时间。不为宽限单独导出计时器类型——宽限的可观察形态是**后续 wait 的 ctx 带 deadline**。
- B243：残缺 completed 之后禁止无 deadline 的二次 `WaitEvent`，禁止泄漏未取消的 WaitEvent goroutine。
- B243 取报文：多条 `completed` 时非空 `final_text` 优先；跳过显式空串；只剩空串报错。
- B242：只扫最后一块围栏；第一个 `verdict`；Raw=围栏原文；丢弃必须可见（timeline 评论）。
- B244 只改铁律原文和锁住该原文的测试；各 adapter 的 `finish` 分支已经接受「trailer.commit = 当前 HEAD」。铁律必须同时说清两半：角色禁止改工作树则不 commit 并填 HEAD；**角色要求提交则必须 commit**。
- B241 是加字段，旧客户端忽略未知键。禁止为了本卡改工作流定义本身。接缝走 HTTP GET→PUT→GET，投影单测只作辅。
- 本节点该干什么一律以注入的纪律块为准。

## 测试决定（接缝清单）

1. **`waitForTurnEnd` ← `StepRunner.awaitNode`**（存量，`internal/ledgerstep/runner.go` 传入 `Client.WaitEvent`）  
   - fake 事件必须带 JSON payload，不能只填 Type。非空 `*final_text` 才终态。  
   - 先无 `final_text` 的 `completed`、再有 `final_text` 的 `completed` → 等到第二条才返回。  
   - 只有无 `final_text` 的 `completed`：打进后续 `wait` 的 ctx **必须有 deadline**；fake wait 在 `ctx.Done()` 上返回；到期 `waitForTurnEnd` 返回 **nil**（成功），不是 error。  
   - 从未出现 `completed` 的 `turn_failed` 仍一次返回。  
   - 残缺 `completed` 之后、宽限内收到 `turn_failed` → 不返回，继续等（或等到 deadline）。  
   - 存量 `TestWaitForTurnEndSkipsNonTerminalEvents`：最后一条 completed 必须带非空 `final_text`，禁止继续把「等到第一条无 payload 的 completed」当绿。  
   反面：不能把「等到第一条 completed」继续当绿。

2. **`finalMessageFromEvents` ← `clientFinalMessage`**（存量）  
   - 快照里两条 `completed`、只有后一条有非空 `final_text` → 返回那段正文。  
   - 只有摘要、字段缺失 → 仍回落摘要。  
   - 显式 `"final_text":""` 仍报错，不回落 summary（存量语义，不得改掉）。  
   与缝 1 分开：缝 1 是「何时醒」，缝 2 是「醒了拿哪条」。`TestFinalMessagePrefersCompletedOverTrailingTurnFailed` 只覆盖 Attach，**不能**冒充缝 1 的「宽限期内收到 turn_failed」。

3. **`ParseVerdict` ← 裁决路由**（存量，`internal/ledgerstep` 在解析失败时转等人）  
   - 严格 JSON 仍绿。  
   - 源卡形态：`notes` 含 `"enabled":true` 且 `verdict=pass` → Pass=true，**Raw 含损坏 notes**。  
   - `verdict=fail` 且 notes 里出现 `"verdict":"pass"` → Pass=false。  
   - 无围栏 / `verdict=maybe` → 仍错。  
   - 抢救成功且 notes/findings 被丢弃：timeline 有一条可见评论（或等价事件），不是只有重建过的短 JSON。  
   夹具必须带围栏；本缝不依赖 `final_text`，避免冒充 B243。

4. **`ProtocolRules` ← `RenderPrompt`**（存量，`internal/executor/turn`；codex 常驻指令复用同一份原文）  
   - 渲染结果含「是否 commit 听角色纪律」和「无新提交则 commit 填 HEAD」。  
   - 同时含「角色要求提交则必须 commit」（或等价），避免实现收成「只读则永不 commit」误伤 recon 有视图。  
   - 不再出现无条件的「必须 git add 并 commit」作为**唯一**收尾指令。  
   - trailer 三字段名字不变。协议层不点名 review/recon。  
   这是教模型的协议原文，改了用户（执行者）能察觉。

5. **`handleFlowGet` / `handleFlowPut` ← 控制台读-改-存**（存量，`internal/agentd/ledgerapi.go`；前端 `fetchFlow` → `putFlow`）  
   - 账本节点 `override.purpose=review` → **HTTP** `GET /api/flows/{name}` 的 JSON 含 `"purpose":"review"`。  
   - 零值 purpose 不出现在 JSON 里（omitempty）。  
   - 把这次 GET 的 `nodes` **原样 PUT** 回去，再 GET，`purpose=review` 仍在。  
   投影函数的 `json.Marshal` 单测可留作辅，**不能**单独充当本缝。契约 fixture 加一个带 `purpose` 的样本（现有 `FlowDetail` 样本 override 为空，加 omitempty 字段不会让旧 fixture 变红）。

假缝：不为宽限单独导出计时器类型当接缝。宽限锁在缝 1 的「后续 wait ctx 带 deadline」。
