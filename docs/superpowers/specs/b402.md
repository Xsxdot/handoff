# B402 spec：仅零文本回合失败自动续接一次

**状态：已批准**（用户 2026-09-25 批准；范围 B：仅 `zero_text` 自动重试一次）  
**卡：B402**  
**级别：L3 轻档**　**入口：debug**  
**台账：** `docs/superpowers/ledgers/2026-09-25-b402-spec-ledger.md`

## 1. 问题与根因

B402 的现场是派发节点回合以零文本结束，协议 trailer 缺失，节点只能收到失败说明；`internal/ledgerstep/node.go:278-295` 随后把这段说明交给 `ParseVerdict`，解析失败转 `needs_human`。同一函数在 `Await` 返回后注册 `FinishTask` defer（`internal/ledgerstep/node.go:283-290`），因此解析失败、后续 diff/产出校验/写闸/发布失败等所有早退路径仍会执行 `FinishTask → Done`，把任务归档。归档后协调者再 `continue` 只能得到 409；这是状态机的正确反应，不是继续失败的根因。

卡上四起实录跨 runner/mimo、pro/cmd 等载体，公共签名是 `serve exit code=-1`、无 `render.log` 正文；其中零文本分支已在各 adapter 的明确收尾路径产生 `OK=false` 结果（OpenCode `internal/executor/opencode/adapter.go:2204-2234`、Codex `internal/executor/codex/adapter.go:907-915`、Grok `internal/executor/grok/adapter.go:672-682`、Claude Code `internal/executor/claudecode/adapter.go:886-897`、AGY `internal/executor/agy/adapter.go:683-695`）。

现状还有两个放大问题：

1. `waitForTurnEnd` 只返回错误/成功，`finalMessageFromEvents` 只返回字符串（`internal/ledgerstep/wire.go:47-94,137-214`），下游拿不到 `turn_failed` 的类型、序号和结构化分类。
2. `FailedPayload` 只有人读 `FailReason`、git 实况和占用快照（`internal/orchestration/contracts.go:136-164`）；客户端若靠文案判断，就会把供应商文案变化当协议变化。B100 已冻结禁止这种做法。

B402 的第一性修复不是给所有失败加重试，而是先把“这是明确的零文本故障”从自由文本提升为跨进程封闭分类，再在节点生命周期边界只消费这一类。

## 2. 用户已选范围

用户 2026-09-25 明确选择 B：仅零文本失败自动重试一次。

本次同时修复 B341 引入的生命周期根因：任何仍需人工的终态都保持任务 `waiting_review`，不得调用 `Done` 归档；只有有效业务裁决完成、产出/发布/路由等节点收口动作完成后，才允许 `FinishTask`。

## 3. 目标与结果

1. 明确的 `failure_class=zero_text` 第一次出现时，由节点执行体复用既有 `ExecutionClient.Continue`，自动续接同一 task 一次。
2. 第二次终态为有效 `handoff-verdict` 时，按正常节点流程完成并归档；不再吵醒人工重派。
3. 第二次仍为零文本、出现其他失败、续接失败、报文解析失败或任何节点收口失败时，任务保持 `waiting_review`，落 `needs_human`，绝不 `Done`/`archived`。
4. 旧 agentd、旧 adapter 或缺少分类字段的历史事件不自动重试，保持 fail-closed。
5. `FailReason` 继续只承担人读诊断，不参与任何行为分支。

## 4. 方案

### 4.1 类型化失败分类

在协议纯类型层新增封闭的 `FailureClass`，至少包含精确值 `zero_text`。该类型由 executor 内部结果和跨进程失败 payload 共用；`AdapterEvent` 不新增重复字段，因为其已有 `Result *Result`。

生产路径为：

```text
adapter 明确零文本分支
  → executor.Result.FailureClass=zero_text
  → Manager.handleResult 透传
  → turn_failed.failure_class
  → HTTP/WS 与账本镜像原样保留
  → ledgerstep 节点等待器读取并决定一次续接
```

约束：

- 只认结构化字段的精确值；空值、未知值、`failed` 终态和其他 `turn_failed` 一律不重试。
- `FailReason` 文案不新增匹配规则，也不要求改供应商文案。
- `NoTrailerResult`（无 trailer 但已有新提交）不自动归类为 `zero_text`；已有工作必须先由协调者裁决，避免重复执行。
- 权限被拒后转 `question`、原生提问、非零文本无 trailer、内容过滤、连接/进程死亡等邻近分支不分类为 `zero_text`。
- `failure_class` 是 additive、omitempty 的 wire 字段；不新增事件类型、不新增 HTTP 端点、不迁移账本表。

### 4.2 节点等待与重试边界

等待层必须返回“带元数据的回合终态”，至少保留事件类型、事件序号、最终正文或失败说明和 `FailureClass`；不能再把 `WaitEvent` 得到的 `turn_failed` 压成裸字符串。

节点执行体对一次 `RunOnce` 的处理顺序固定为：

1. 派发 task。
2. 等待第一个终态。
3. 若终态为 `turn_failed` 且分类为 `zero_text`，使用既有 `Continue` 能力向同一 task 发送一次非空、固定的续接指令。
4. 再次等待终态；本次结果才进入正常裁决解析。
5. 仅当最终结果能完成业务裁决及节点收口时，调用 `FinishTask`。

一次 `RunOnce` 最多自动续接一次。人工在耗尽后显式 `continue` 属于人工重试，不计入自动重试；重新派发是新节点尝试，不继承本轮的自动计数。进程重启不自动重放已消费的失败事件，避免重复耗费 token；若需要恢复，交由既有显式恢复/重新派发流程。

### 4.3 任务生命周期

`FinishTask` 不再在 `Await` 返回后注册无条件 defer。它只能在以下条件全部成立后调用：

- 业务裁决已成功解析并落账；
- 审阅只读闸、产出物校验、工作分支发布、卡路由等需要 task 工作树的收口动作已完成；
- 节点最终 Outcome 已确定。

以下路径一律不调用 `FinishTask`，任务留在 `waiting_review`：

- 等待/传输失败或 task 已归档；
- 裁决缺失、格式错误或 JSON 无法确认；
- 自动续接失败或续接后的终态仍失败；
- diff、产出、写闸、发布、落账或路由失败；
- 运行锁失效。

任务归档失败必须显式记日志并转人工可见结果，不能把“已移卡”伪装成“task 已归档”。

### 4.4 并发所有权

同一张卡的运行锁仍是单一节点执行闸。自动续接调用仍受目标 task 的 `waiting_review` 状态门保护；若外部协调者先完成续接，节点执行体不得再次抢占、不得调用 `Done`，按续接失败路径安全退出并保留可审计结果。

本次不改变 `turn_failed` 的既有唤醒投递和账本镜像面；首个零文本事件仍可能被外部观察者看到。安全性来自“任何路径都不提前归档”和状态门，而不是隐藏事件。若后续要抑制首个自动重试事件的唤醒，应另开唤醒面契约卡处理。

## 5. 弃选方案

- **只修生命周期、不自动重试**：能修复 409/归档根因，但不能减少 B402 已记录的“丢一轮、吵醒人”代价。
- **所有 `turn_failed` 自动重试一次**：会重试模型 400、内容过滤、无 trailer 但已有提交和非零文本故障，违反现有“失败交协调者、不自动烧 token”的契约。
- **匹配 `FailReason` 中的“零文本”文案**：供应商文案可改，旧事件无分类，客户端行为会静默漂移。
- **给 manager 做全局自动重试**：会把节点专属策略施加到所有 task，扩大生命周期和唤醒竞态。
- **把已有提交的 `NoTrailerResult` 一并重试**：可能重复执行已落地的修改，先保留人工裁决。
- **新增 retry 事件、数据库列或 HTTP retry 端点**：现有 `turn_failed` 与 `Continue` 已足够，新增第二套重试协议会制造双重状态源。

## 6. 用户故事

1. 作为无人值守节点执行者，收到明确 `zero_text` 失败时自动续接同一 task 一次，不丢当前会话上下文。
2. 作为协调者，第一次零文本不再把 task 归档；第二次仍失败时能在 `waiting_review` 中看到 `needs_human`，并可人工继续或处理。
3. 作为旧版本消费者，收到新增字段时继续按旧规则工作，不因缺字段误重试。
4. 作为排障者，日志和事件能区分“第一次自动续接”“续接后成功”“续接耗尽/外部竞争”，不靠失败文案猜测。

## 7. 契约语义与接缝

### 7.1 契约面

- 协议层拥有 `FailureClass` 词表；executor 结果和失败 payload 复用该类型。
- 失败事件仍为 `EventTypeTurnFailed`；只有该事件且分类精确为 `zero_text` 才进入自动续接。
- `ExecutionClient.Continue` 是唯一续接能力来源；不新增端点。
- ledger 镜像保留原始 payload，不重新解释失败文案。
- 旧字段缺失时协议语义是“不可自动重试”，不是“零文本”。

### 7.2 测试接缝清单

| 缝 | 生产调用方 | 必须锁住的行为 |
|---|---|---|
| `internal/executor/*` 各 adapter 的零文本收尾分支 | adapter 事件循环/测试导出入口 | 只有明确零文本分支写 `zero_text`；question、failed、无 trailer 有提交、邻近失败不写 |
| `internal/orchestration.Manager.handleResult` | `Manager` 中介事件循环 | typed Result 透传到 `turn_failed`；其他失败 payload 不带分类 |
| `internal/ledgerstep.waitForTurnEnd` / typed terminal seam（精确签名由 contract 冻结） | `StepRunner.awaitNode` | 保留终态类型/序号/分类；不把首个 zero_text 压成普通字符串 |
| `internal/ledgerstep.finalMessageFromEvents` | `clientFinalMessage` | 成功终态仍取最终正文；失败终态可携带分类，不改变 completed 优先与宽限语义 |
| `internal/ledgerstep.NodeStep.RunOnce` | `StepRunner.Run` / agentd `runStep` | 自动续接恰一次、第二次结果路由、任何早退不归档 |
| `client.ExecutionClient.Continue` | `StepRunner` 节点等待器 | 复用现有状态门和 HTTP 能力；续接错误 fail-closed |
| `FailedPayload` JSON 编解码边界 | Manager 事件写入、HTTP/WS/账本镜像消费者 | 缺字段保持旧 wire；有字段精确保留；不把未知值当可重试 |

不得用只在测试包内调用、没有生产调用方的 helper 占据接缝名额；实现细节可拆，但必须由上表生产路径调用。

## 8. 实现决定

- 失败分类只由 adapter 的明确零文本分支生产；不从最终字符串、事件顺序或 git 状态反推。
- 等待/续接/归档的顺序由节点执行体统一编排；adapter 只报告事实，manager 只迁移状态和落事件，客户端只消费契约。
- 自动续接使用既有客户端能力；续接指令为固定非空文本，不携带用户自由输入，具体文本由 contract 节点冻结。
- `FinishTask` 从无条件 defer 改为收口阶段的显式动作；任何需要 task 工作树的动作仍先于 Done。
- 继续失败、状态竞争、解析失败和写闸失败均不得调用 Done。
- 失败日志只记录上下文、分类、事件序号、尝试次数和受控错误尾部，不记录完整 prompt、正文或供应商密钥。
- 本卡不改任务状态枚举、失败文案、`VoidReason`、账本表结构、唤醒策略或跨版本部署流程。

## 9. 测试决定

### 9.1 红色反馈回路

主红测使用 `httptest.Server` + 阶段化 task 状态，完全由测试推进事件，不依赖 sleep：

1. 第一次 `turn_failed` 返回 `failure_class=zero_text`；
2. `/continue` 只能从 `waiting_review` 成功并切到 `running`；
3. 第二次返回有效 `completed`；
4. 断言 `continue=1`、`done=1`、业务 verdict 成功。

主反例为 `zero_text → zero_text`：

- `continue=1`；
- 第二次失败后 `done=0`、无 `archived`、节点 Outcome 为 `needs_human`；
- 随后显式 `continue` 可成功，不得再得到 409。

测试夹具必须让第一次失败使用与实现无关的 `FailReason` 文案，以证明分支只依赖 `failure_class`。

### 9.2 必测矩阵

- `zero_text → completed`：自动续接一次并正常归档。
- `zero_text → zero_text`：只续接一次，耗尽后不归档。
- `zero_text → 普通 turn_failed`：不二次续接，不归档。
- `turn_failed` 无 `failure_class`：不续接，不归档。
- `failed` 终态即使带字段：不续接。
- 成功 `completed` 无 trailer：解析失败，不归档。
- 解析失败、diff 失败、产出失败、发布失败、写闸失败：均不调用 Done。
- 旧 wire 缺字段：结果形状与现有行为兼容。
- 未知 `failure_class`：不续接。
- `NoTrailerResult` 有新提交：不续接。
- 五家 adapter 的明确零文本分支分别断言分类；question/权限/内容过滤/进程退出邻近分支断言不分类。
- 事件镜像、HTTP/WS 和 JSON 解码均不丢 `failure_class`。
- 日志断言至少能看见 task、event seq、failure class、attempt、continue/done 结果；不得出现完整正文或凭据。

### 9.3 验收顺序

1. 编译全量与相关单测（含现有 `handleresult_notrailer_test.go`、ledgerstep wire/runner、executor fallback 族）。
2. 测试局部：typed wire、ledgerstep 重试红测、五家 adapter 分类测试。
3. 集成全量：`go test ./...`、`go test -race` 关键包、`go vet ./...`、代码图检查。
4. 用阶段化 fake task 做一条真实 agentd/manager 接线烟测；不依赖真实供应商。
5. 只有上述证据齐全才进入人工验收；不把“测试全绿”冒充供应商流中断根因已修复。

## 10. Out of Scope

**永不做**：

- 匹配 `FailReason` 文案决定行为。
- 对所有 `turn_failed` 或 `failed` 自动重试。
- 自动重试权限被拒、内容过滤、进程死亡、已有提交但无 trailer 的分支。
- 在本卡内抑制首个 `turn_failed` 的唤醒投递或改造 wakeconsumer。
- 新增 retry 数据库字段、事件类型、HTTP 端点或跨重启自动重放。

**本期不做、后续要做**：

- 首个零文本事件的唤醒抑制与 retry ownership 的全局可见性：另开卡，避免把唤醒面和节点生命周期混改。
- 跨 agentd 重启的同一 task 自动续接计数与恢复：需要单独冻结持久化/恢复契约。
- 供应商流中断本身的根因治理：本次只处理已确认的零文本分类、一次续接和生命周期丢失。

后续项须登记到 `docs/roadmap.md`，不得只留在本段。

## 11. 缺陷族结论

- **生命周期/状态机中断**：已回答；只有最终收口才 Done，所有早退保留 waiting_review。
- **静默失败/误导报错**：已回答；缺分类、未知分类和所有收口错误都显式转人工，不归档。
- **跨平台假设**：已回答；分类来自 adapter 契约，不依赖平台路径或 UI。
- **假红/假绿测试**：已回答；主回路阶段化、状态门可观测，且含耗尽反例。
- **门禁绕过**：已回答；续接仍走 `waiting_review` 状态门，Done 只由节点收口显式调用。
- **序列化边界**：已回答；executor → manager → wire → mirror → consumer 各有穿透测试。
- **枚举白名单**：已回答；`FailureClass` 是封闭词表，未知值 fail-closed，镜像不重新解释。
- **承重安全属性**：已回答；一次自动续接、无分类不重试、二次失败不归档均有可变红断言。

## 13. 备注

- 根因来自 B341 的生命周期改动与 B402 的零文本故障叠加：B341 让所有 Await 后早退路径归档，B402 让零文本节点最容易走该路径。
- 现有 B100 已规定 `turn_failed` 与 `failed` 语义分离；本卡沿用该事件类型，只增加可选分类，不重开事件终态设计。
- `internal/ledgerstep/wire.go` 的 completed 优先逻辑保留；只有等待器明确收到首个 `turn_failed(zero_text)` 时进入自动续接分支。
