# B380 spec：关单镜像断流——ticket_answered 不进实时流导致卡流幽灵未决单

**上游状态：已批准**（审批者 2026-09-23 批准，四点裁定：①关单进实时流但不叫醒协调者；②终态任务清掉未决单；③水位逐 seq 对账本期不做；④L2，词表和 wire 不动。验收与合 main 归人）
**级别：L2 单子系统**（`internal/orchestration` + `internal/approval` 的发布点 + `internal/ledger` 的投影面）
**根因**：已复核（本会话，读数全在台账 `docs/superpowers/ledgers/2026-09-23-b380-spec-ledger.md`）
**入口节点**：spec（现象实录在卡上 #16404；根因与修复方向由本 spec 定稿）

---

## 1. 问题陈述

`handoff card wait` 建连快照（`cmd/card_wait.go` `encodeCardWaitSnapshot` → `ledger.Store.OpenTickets()`，`internal/ledger/taskstate.go:147`）把**早已答复的工单**当未决列出。夜班实测与本次复核（2026-09-23）：

- 任务侧 `handoff show 3bb5b62d… --target linux-01`：`state=completed`，工单 `per_09f3d22ee001KZKop4mpnZBa0m` 的 `ticket_answered` 在 seq 35973，任务 archived 在 36084——全部已答。
- 卡流侧 `card wait B369 --subtree` 首行快照 actionable 列出同一工单；**B369 全子树快照列出 100+ 张幽灵单**。
- 逐 seq 对照（本次复核）：卡流镜像到了 `permission_request`（卡流 14006/14007/14032 ← 任务侧 35970/35972/36031）与 `completed/archived`（14042/14047 ← 36083/36084），但**任务侧全部 ticket_answered（35967…36081）一条都没镜像进卡流**。同卡另一任务 c99a527d 恰有 2 条 ticket_answered 进了卡流（13939/13941 ← src 35819/35821）——它们落在订阅建立时的重放窗口内。

### 根因链（四个环节，环环有出处）

1. **关单事件不进实时流**：`ticket_answered` 的全部三个写入点都只 `AppendEvent` 不 `hub.Publish`——人工 reply 路径（`internal/orchestration/facade.go:125` `Manager.AnswerTicket`）、Manager 中介审批者路径（`internal/orchestration/manager.go:2577` `approvePermission`）、OpenCode 面审批者路径（`internal/approval/client.go:430`）。这是 `internal/proto/proto.go:104-106` 冻结的「审计事件只入库不 Publish」语义。
2. **镜像实时通道只承载 Publish 的事件**：账本镜像（`internal/ledgermirror`）经远端 `/ws/events` 订阅；该通道「先订阅 hub 实时流，再补发 store 历史」，补发只在**订阅建立时**做一次（`internal/agentd/handlers.go:1451` 起）。此后审计类事件只在 store 里，实时流见不到。
3. **watermark 跳过缺口**：镜像水位 = `MAX(source_seq)`（`internal/ledger/mirror.go:104`）。订阅建立后错过的 `ticket_answered`，水位被后续可交付事件（如 permission_request）推过去；重连回放从水位起——**缺口以下的关单事件永久丢失**。
4. **投影重放出幽灵**：`OpenTickets()` 按镜像事件重放：开单靠 `permission_request/question`（都 Publish，镜像在），关单靠 `ticket_answered/tickets_voided`（不 Publish，镜像缺）→ 开了关不掉，幽灵未决单。

### 影响面

- 任何挂 `card wait` 的协调者/人首行就看到幽灵单（B380 卡上 #16404 的 5 天前实例是常态而非孤例）；
- 卡详情 `open_tickets` 计数（`internal/agentd/ledgerapi.go:171`）同源同错；
- 自动唤醒消费面不受影响（`WaitDeliveryPolicy` 本就过滤 ticket_answered，不产生误唤醒）——错的是快照与计数这两个**读数面**。

## 2. 级别与档位

**L2 单子系统**：改动落在 `internal/orchestration`（2 个发布点）、`internal/approval`（1 个发布点 + Hooks 触点）、`internal/ledger`（投影面）。

定级先例：B396「L2 单子系统（`internal/ledger` + `cmd` 判据面）」、B393「L2 单子系统（`internal/agentd` + `internal/keystone`）」同形。

**不动契约层**：

- B233.1 词表冻结的 17 个事件类型不增不改；`ticket_answered` 本就在词表与客户端交付策略表里（`internal/client/delivery.go:29` 列为不可交付）；
- hub 是进程内扇出、不跨进程不跨仓；跨机消费端（账本镜像）早已认识该类型（重放窗口一直在投递它）；
- payload schema（`TicketAnsweredPayload`）不变；
- 随代码修订的是 `proto.go:104-106` 的「只入库不 Publish」**注记**（该注记给出的理由——「唤醒 wait」——早已被客户端交付策略承接：`isDeliverable/WaitDeliveryPolicy` 在消费端过滤，发布它不会唤醒任何 wait）。

## 3. 方案（含弃选与理由）

**采用：两层修复——根因层发布 + 投影层自愈。**

### 3.1 根因层：发布 `ticket_answered` 进 hub

三个写入点在 `AppendEvent` 成功后（且仅在本次真的追加了事件时）补 `hub.Publish`：

1. `internal/orchestration/facade.go` `Manager.AnswerTicket`——人工 reply 路径；
2. `internal/orchestration/manager.go` `Manager.approvePermission`——Manager 中介审批者路径；
3. `internal/approval/client.go` 审批者批准路径——该 Client 无 hub 触点，经 `Hooks` 新增一个可选发布函数（nil 安全；生产装配处注入现有 hub，装配点由 contract/plan 核对）。

消费面就绪证据（实现不得再动）：`client.WaitDeliveryPolicy`（`internal/client/delivery.go:29`）已把 `ticket_answered` 列为不可交付 → `card wait`、`handoff wait`、agentd 唤醒消费（`internal/agentd/wakeconsumer.go` `automationWakeEvent`）都不会因它叫醒任何人；`WaitAnswer/NotifyAnswer` 是独立通道不受影响；浏览器控制台与 workspace 任务镜像（`internal/workspace/mirror.go`）会实时看到该事件——与重放时本来就会看到一致，无新语义。

幂等重答（`applied=false`）不 AppendEvent 也不 Publish，与现状逐字一致。

### 3.2 投影层：终态镜像关单（存量自愈）

`OpenTickets()`（`internal/ledger/taskstate.go:147`）在既有重放逻辑上追加一条规则：扫到某 `(card_id, source_target, source_task)` 的镜像 `completed` / `failed` / `archived` 时，清空该任务名下全部未决工单（终态任务的工单不可能合法未决）。

- **存量幽灵单自愈**：B369 等任务的 `completed/archived` 镜像都在卡流里，升级后 `OpenTickets` 重放即关闭全部幽灵单，无需回填迁移；
- **对 3.1 的兜底**：任何未来路径若再漏发关单事件，任务终态镜像一到即收口；
- 重放按 seq 升序，语义是「终态之后该任务不再有未决单」，与任务侧不变式（终态即无挂起工单，`VoidTicketsWithAudit` 收口）一致。

### 3.3 弃选与理由

- **弃选：把 watermark 从 `MAX(source_seq)` 改成逐 seq 连续性对账（补洞重拉）**。能根治镜像丢审计类这一族问题，但要给镜像加缺口表、对账协议与回拉策略，量级数倍于本卡收益；3.2 已把「丢关单镜像」的可见后果（幽灵单）兜住。留作后续卡候选（见 Out of Scope）。
- **弃选：改 `tickets_voided` 的发布语义**。它伴随 `completed/failed` 同时刻产生且 `completed/failed` 会发布并被镜像，3.2 的终态关单已覆盖其全部投影职责；多发布一种审计事件没有增量收益。
- **弃选：card wait 快照侧按任务终态过滤**。只治快照不治 `open_tickets` 计数，且把正确性放在消费端三处各抄一份——账本投影面是唯一正确的收口位置。

## 4. 用户故事

1. 协调者挂 `handoff card wait B369 --subtree`：已完成任务的已答工单不再出现在首行快照 actionable（存量自愈，升级即生效）。
2. 任务运行中工单被答（人工 reply 或审批者批准）：数秒内卡流出现 `task_mirrored(ticket_answered)` 关单，`card wait` 不再把它当未决。
3. 卡详情 `open_tickets` 计数与快照一致，不再把已归档任务算出未决工单。

## 5. 实现决定（决策级）

- 发布点收口在「AppendEvent 成功且本次真的写入」之后；发布失败不影响应答主流程（`Hub.Publish` 本就无返回值、满缓冲丢弃）。
- `approval.Hooks` 新增发布触点为可选依赖，nil 时行为与现状一致（只入库）——旧装配不破坏。
- `proto.go` 事件类型注记随代码修订：`ticket_answered` 改述为「会 Publish，但客户端不可交付」（对齐 `delivery.go` 现状）；README / handoff skill 的事件表若标注了交付性，实现时逐一核对同步。
- 不新增事件类型、不改 payload、不改镜像协议、不动 watermark 语义。
