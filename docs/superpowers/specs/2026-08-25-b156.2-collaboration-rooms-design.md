# B156.2 二期·协作层：房间制会话与升级简报

> 状态：**已批准（用户，2026-08-25）**。批准同时追加架构约束：会话独立成子系统、
> 双向 api/client 门面、不直调、按 `codegraph/best.json` 立户口——见 §8.0。
> 卡：B156.2 ｜ 级别：**L3**（新增会话子系统 × 账本域/协调控制面/Web 控制台域/协调者纪律层）
> 选档：**重档倾向**（控制台 IM 面与会话子系统各自远超流程固定成本且可并行；contract/breakdown 复核）

## 1. 问题陈述

一期（L1 账本域）解决了「状态散在各会话」的记账问题，但注意力问题只解决了一半。
用户的注意力模型是**前置的**：重仓押在 spec 节点，之后期望主会话自主推进。这个
姿势依赖一条今天不存在的通道——**高质量的「协调者→人」升级通道**：

- 真问题在 spec 之后暴露（spec 是对世界的猜想，实现是检验），此时用户语境已移走；
- 问题「如何发生、为什么发生」淹没在主会话长输出里，理解成本高于「同意」的成本，
  用户只能「你看着办」——**橡皮图章是经济学问题不是纪律问题**，每次低语境批准都在
  放大下一次偏差（批量自主推进 bug 卡时最重）；
- diff 不可读（一个分支几千上万行），用户读的必须是「对 spec 的 diff」；
- 「需要你」v1 定位错了：它上浮的工单实际都被主会话批掉——**工单需要的是协调者；
  真正需要用户的是协调者本身**：协调者需要用户注意什么，并把发生了什么/为什么讲透。

二期目标（按用户开题重述，蓝图四项是手段不是目标）：**单人 + N agent 会话下，
人的注意力与理解力**；其次防跑偏、防过度设计——让 agent 跑偏/做大这件事被用户
早看见、早说话（强制层面 review 节点已有，缺的是早期廉价干预与讲透的叙事）。

## 2. 方案总览

四大件，互为表里：

1. **偏差两级制 + 升级简报**：把「协调者→人」这一刻的质量做透（§3）。
2. **房间制会话**：一种 Room 类型承载全员群/项目群/卡会话三级，卡:房间=1:1，
   每房间恰一个协调者绑定席位（§4–§6）。
3. **注意力面**：待回复收件箱 + 未读游标 + 扁平活动排序列表（§7）。
4. **会话独立成子系统**：双向 api/client 门面、不直调、按 best.json 立户口——
   用户批准时追加的硬约束，是本期的架构地基而非附带项（§8.0）。

### 弃选记录（含理由，均为对话实测裁决）

- **泄漏点读面铺开**（首轮框架：卡级简报/收件箱/评论路由/文档实体化四件套）——
  用户否决消费姿势：不轮询读面，要「协调者对你说」的推送深度。
- **子树消息聚合视图**——把细节层砸进提纯层，在防淹没立项上开倒车；聚合由父卡
  协调者的**衔接叙事**完成，不由 UI 数据合并完成（经理向你汇报，不是数据库拼聊天记录）。
- **按 charter 档位设兼任/分派默认策略**——子卡轻重混杂时判据不干净；机制双轨、
  产品不定性，三期自动唤起时再议。
- **节点边界把用户留言注入 executor prompt**——指令类留言会绕过偏差分类直达执行者、
  审阅轮被注入污染独立裁决；改为留言只送协调者（§6）。
- **树形分组会话列表 + 未读沿父链上卷**——PM 形态不是 IM 形态；改扁平活动排序 + 项目筛选。
- **叙事员轮**（派发便宜会话代写叙事）——多养一个会话物种；真实用法本来就有活着的
  协调者；三期再评估。
- **重档聊天面**（聊天气泡内跑 agent 会话/看工具调用/思维链）——**永不做**：那是
  桌面端/TUI 会话这种工作面的活（用户原话），等于在控制台重造 Claude Code。
- **数字阈值的累计偏差检视**——魔法数字是假干净（4 条同向小偏差比 7 条无关的更该升）；
  改协调者义务条款 + 收口摘要兜底。

## 3. 偏差两级制与升级简报

### 3.1 判据表

| 情形 | 级别 |
|---|---|
| 实测证伪 spec 商定（验收判据不成立、选定方案跑不通、契约语义与现状冲突） | 推翻级 |
| 要改 spec 定下的范围、验收判据、契约语义——扩大缩小都算 | 推翻级 |
| 不可逆/外部可见动作（合 main、删数据、动生产配置、对外发布） | 推翻级（既有硬纪律并入） |
| 超轮/僵局（修复轮封顶、审阅不收敛） | 推翻级（既有等人机制并入，改走简报形态） |
| spec 未覆盖的实现选择（内部结构、命名、依赖细节） | 填补级 |
| 顺手小修、新发现问题落新卡（`discovered_from` 边） | 填补级 |
| 测试策略微调、非契约面的内部调整 | 填补级 |

**推翻级**：停卡（= 打「等人」标记，reason=推翻级请示；**在飞执行轮让其自然跑完
但不推进下一节点**，不 stop 在飞任务——不可逆动作已有工单硬纪律兜底）、发升级
简报、等用户答复。**填补级**：协调者自主决定、落偏差叙事、不停。
**拿不准 → 按推翻级**（代价不对称：漏报=跑偏复利；误报=多答一条便宜简报，且用户
一句「这种以后不用问」就让判据表长一条）。
填补级试金石：**「这个决定当时写进 spec，用户会改变主意吗？」**不会→填补级。
**累计偏差检视**：当填补级偏差的累计效应让协调者觉得「这已经不是当初商定的那个
东西了」，必须升一条推翻级简报（类型=累计偏差检视）。无数字阈值，收口摘要兜底。

### 3.2 升级简报六段契约（缺段拒收，格式是契约不是模板建议）

1. **一句话**：什么被推翻/要动什么，挂卡号；
2. **商定 vs 实测**：spec 第几条写的什么 ↔ 实际发现什么，证据用链接锚进 timeline
   （测试原文、文件清单、轮次），正文不贴代码；
3. **根因**：为什么当时没预见（世界变了/当时信息不足/理解偏差）；
4. **影响半径**：动哪条判据/范围/契约，波及哪些卡；
5. **选项 + 后果 + 推荐**：2~3 个，只要可行必含「维持原商定」（防简报变成既成事实
   追认书）；
6. **停在哪**：不答复卡停在什么状态、多久后再提醒。

**简报的语言是「对 spec 的 diff」，不是对代码的 diff**——spec 是用户注意力驻留过
的地方，这是把用户语境接回来的最短路径。

### 3.3 答复：结构化控件直达

简报消息携带 Decision（一期已有对象，`internal/ledger/types.go#Decision`），控制台
把 options 渲染为按钮 + 可选文字补充；用户点击**直接写 `decision_answered` 落账**
（用户经控制台是账本合法书写者），不经协调者转写。答复即时从「待回复」消失；卡的
等人标记由恢复推进的协调者清除；**协调者不在场时界面明示「答复已落账，等待协调者
唤醒」**——看板不说谎延伸到会话面。

### 3.4 收口摘要（卡到终列时协调者发的最后一条消息）

四段：做了什么（一段话）；**全部偏差清单**（推翻级裁决结果 + 填补级逐条——自主
消化的不许消失，这是安全网执法点）；验收证据指针（timeline 锚）；残余去向（落
roadmap/新卡的逐条链接）。父卡收口另带子卡汇总（几张顺利、几张有值得读的偏差、链接）。

## 4. 房间制：一种 Room 类型

**只有一种 Room 类型**（预留类型扩展字段本期不用）。全员群/项目群/卡会话的唯一
差别是**默认加入策略**：

- **卡会话**：与卡 1:1。创建触发：用户点「新建会话」，或绑定产生时自动建房
  （含派发即认领产生的绑定——有绑定必有房间，义务性消息才有落点）。成员：绑定
  协调者 + 用户。
- **项目群 / 全员群**：默认成员 = 范围内「已开始未结束」卡会话的协调者们 + 用户。
  协调者开卡会话即自动加入卡会话/所属项目群/全员群三处；**卡收掉时按派生成员规则
  重算**（兼任者只退出该卡房间，仍驱动的其他房间与群不受影响）；成员动态、历史不动
  （退出者消息留存；安静期项目群可以只剩用户，安静不是缺陷，不造内容填它）。

**绑定席位制**：每张卡一个房间、**每房间恰一个协调者绑定席位，同一协调者实体可占
多张卡的席位**（兼任合法）。绑定由行动产生——谁的会话开始驱动这张卡（派发即认领
CAS 的延伸）谁上席位，或用户显式建会话绑定；**派发前置校验绑定归属**：卡已有绑定
且非本会话时拒绝，提示走换绑（防「驱动者≠房间绑定者」双头态）。

**协调者 = 可 resume 的持久会话**。载体：控制台拉起的会话 / Claude Code 桌面端
会话 / 其他 agent 的 CLI。绑定落卡（session 标识 + 载体类型）；今天的 driver lease
降为绑定的**活性心跳**（绑定答「对手方是谁」，心跳答「它现在活着吗」）。唤起：能
resume 则 resume；不能则拉新载体承接同一逻辑协调者身份——**承接与换绑共用同一
重建纪律**（§6.3）。

**兼任/分派机制双轨、产品不定性**：由用户决定父卡协调者兼任子卡、还是给子卡建
独立协调者（类比：主会话派不派 subagent 是语境内判断，不是全局政策）。**本期拉起
动作一律由用户执行**；父协调者向子卡协调者的「简报下传」= 父协调者以成员身份加入
子卡房间发消息（流程性加入只有父子这一种；绑定席位仍恰一个）。三期规则引擎拉起时
再议定性。

**executor 永不入房间、永不写账**（账本凭据物理隔离在协调机，蓝图 §3.1 铁律）。
协调会话不走执行派发流程——那是执行会话的状态机，两个物种。

## 5. 会话内容契约

**白名单制**（不在单上的不进房间）：

1. 四种机器叙事消息：推翻级简报 / 填补级叙事 / 收口摘要 / 父卡衔接消息；
2. **协调者对用户发言的应答**（对话式回复——聊 spec 等基础用例的合法载体；
   白名单的敌人是心跳与日志，不是对话）;
3. 用户发言与裁决答复；
4. 薄里程碑指针行（可折叠灰字：「spec 已定稿 →」「implement 已派发」）——书写者
   是**协调机侧系统组件**，不是协调者。

**书写者规则**：叙事类消息（1、2 类）书写者 = 房间成员中的协调者实体（含以成员
身份入房的父协调者）；指针类 = 系统组件；executor 与非成员不可写。**无协调者在场
时房间面退化为机械信号**（工单上浮、needs-human、指针），**不伪造叙事**，接管者
唤醒后补写。

**卡会话默认静默**：不发「开始了/进行中/跑测试了」心跳。**没消息 = 按 spec 在走**。
消息 = 纯文本 + 引用锚（git 路径 / timeline 锚 / 卡号 / 附件），无富文本存储。
技术细节的家是卡 timeline，语义现状不变（timeline 是账，房间是播）。文体：同事
协作叙事——讲发生了什么/为什么/意味着什么；凡引证据给链接，正文不贴代码。

**项目群/全员群准入判据一条**：涉及两张以上根卡、或无卡可挂的事务才进群（单卡
事务回卡房间）。**项目级裁决（CardID 为空，一期已有）落项目群并进待回复收件箱**；
全员群同构（跨项目事务 + 全局裁决）。

**@（本期做，成员寻址）**：@成员——卡号即该卡协调者的名字，用户有自身标识。
对 agent = **消费定向**：群消息默认不进任何协调者的消费队列，@到谁进谁的（防
群消息扇出污染全体协调者上下文）；对用户 = 提及高亮进收件箱。跨卡临时沟通走
项目群 @，跨项目走全员群 @——不加入对方卡房间（参考同事沟通：不闯别队私聊，
在公共频道 @）。

## 6. 送达、消费与生命周期

### 6.1 用户留言的送达

**留言只发给协调者，绝不注入 executor。**送达时机 = **协调者回合末**（如主会话
挂 wait 间隙收消息的现状形态）。协调者收到后自行决定转译：口头应答、按偏差两级
分类、下一轮 continue/派发时按自身判断带给 executor。协调者不在场 → 留言排队，
resume/换绑后按重建纪律读取。**每条留言恰好消费一次，消费即落账事件**（游标语义
归 contract）；@定向的群消息同规则。**不做主动唤醒休眠会话**（三期）。

### 6.2 房间生命周期

- **并入承载卡**（merge）：成员卡解除绑定（承载卡协调者接管，成员卡未消费留言由
  它按重建纪律读取）；房间置顶「已并入 →」指针、转只读，列表沉底折叠；拆回解冻恢复。
- **卡到终态**：协调者发收口摘要后按派生规则退出；房间转**只读归档**（用户再发言
  时警示引导开新卡，杜绝无人消费的黑洞）。
- **搁置→复活**：沿用原房间（历史不动），成员按派生规则重算。

### 6.3 换绑与重建（本期手动，三期自动化）

限额、载体更换、接管：用户手动换绑（新载体可为另一 agent 的 CLI）。**换绑写入按
当前绑定 CAS 校验，写入即撤销旧会话的房间写权与推进权**（防旧会话醒来继续发消息
推卡）。新任协调者开局**重建四步**：读卡（字段/附件/验收判据）→ 读卡会话史 →
读 timeline → 读仓内文档。**会话史天生是交接简报**——会话面的一切契约第一读者是
用户，第二读者是下一任协调者；配套义务：**凡承重的必须落账**（跨 agent 换载体时
旧 transcript 不可携带，账外无不可再生之物）。限额检测/自动拉起/自动换绑归三期。

## 7. 注意力面

- **会话列表**：一条扁平的、按最近活动排序的总列表（全员群/项目群/卡房间混排，
  谁有动静谁浮上来）；**项目做筛选器**（与控制台既有 FilterBar 形态一致），默认
  「全部」。无树形分组、无未读上卷（弃选记录）。
- **待回复收件箱**：全局直达，内容 = 挂 open 裁决的简报 + **兜底上浮的工单**
  （无人驱动时工单上浮给用户；破坏性工单一律升级人工的硬纪律不变）+ @用户的提及。
  永不下沉。
- **未读游标**：按成员按房间记（多人预留已定形状）；打开房间即已读。不做已读
  回执、提醒设置。
- 「需要你」v1（`web/src/app/cards/CardsPage.tsx` 的等人∪裁决筛选）保留在看板侧；
  会话侧的注意力面以待回复收件箱为准。

## 8. 契约语义与接缝（L3：定语义，不定签名）

### 8.0 架构决定：会话独立成子系统，双向门面，不直调

用户批准时追加的硬约束（2026-08-25）：**这是全新子系统，按标准架构立，不再欠债。**

**立户口**：会话/房间是**新的顶层子系统**（`codegraph/best.json` 的 domains 加一个
顶层领域，`containers` 逐个指名归属；子系统 = 顶层领域）。按架构法第一条核过：
①只以契约面对外 ②可独立开发/测试/交付 ③消费者有控制面、CLI、Web 控制台——
三条全中；派卡四条（有界文件集、契约面可枚举、对同级依赖可排 DAG、类型=逻辑型）
亦齐，具备按子系统扇出的资格。

**双向门面（架构法第四条第 3 档，本子系统法定用档）**：

- **入站 `api`**：外界调会话子系统**只经此门面**，不得 import 其内部（第十条穿透
  禁令，Go 由 `internal/` 可见性执法）。契约面唯一，一个能力只声明一次，消费方
  不得二次抽象。
- **出站 `client`**：会话子系统需要外部能力时**不直调对方内部**。按架构法第九条
  「接口归使用方」，所需能力的接口**定义在会话子系统这一侧**的 client 包；具体
  实现由**组装点**（`target.json` 的 assembly 已登记 main/server）绑定注入，
  组装点之外不得 new 他方具体类型（第八条）。

**被依赖子系统的还债路径（用户指定，与架构法总则 3「绞杀式还债、升格随卡走」一致）**：
本期用到哪个子系统，就**给那个子系统建它自己的 api 门面包**（薄门面，包住既有
实现，不改其内部），会话子系统经自己的 client 接口绑到该门面上。**以后找机会再把
那些实现迁进标准结构**——本期不做专项重构，只在碰到的缝上还债。

**存量直调不扩大**：今天 `d_gateway → d_ledger`（legacyBudget 17，entries
`ledger.Store`/`ledgerstep.StepRunner`）与 `d_cli → d_ledger`（4）是既有直调债。
本期**不新增任何一条穿过它的直调**：凡本期新增的账本能力调用，一律经新建的账本
api 门面。`graph check` 是硬闸，新增边必须先在 `target.json` 声明契约面
（预期新增方向：控制面→会话、CLI→会话、会话→账本、Web 契约层→会话端点）。

### 8.1 契约语义

- **消息即账本事件**：房间消息落为 card_events 单流的新事件类型（群级消息为无卡
  事件，同流）；蓝图 §3.5「timeline 是账、群聊是播」在二期演进为「群聊也产账，
  播是读面」。消费方：控制台、账本 wait、三期规则引擎——只消费这条流（蓝图 §3.8
  扩展点④）。事件类型细目归 contract。
- **数据归属与读写方向**：Room/成员/绑定席位/消息是**会话子系统自有的数据与规则**
  （架构法第五条：规则归数据所有者）；卡、事件流、Decision 仍归账本域。会话子系统
  经 client 接口读写账本能力（发布事件、读卡与绑定所需字段、写 decision_answered），
  **不直接持有账本的 Store**。跨两域的编排（如「简报落房间 + 开 Decision + 打等人
  标记」）按第六条按用例成编排单元，落在控制面组装侧，不堆进任一域的 god object。
- **绑定与心跳**：绑定席位的 CAS 语义与「派发即认领」同源；活性心跳沿用 driver
  lease 机制——二者的**权威存放位置**（账本域卡上 vs 会话子系统内）由 contract
  裁决，判据是第五条：谁拥有这份数据谁写规则。
- **依赖方向（DAG，无环）**：Web 控制台 → 控制面（gateway）→ 会话 api；会话 →
  client 接口 →（组装点绑定）→ 账本 api。执行域零新增依赖——**executor 不认识
  房间**，`card_id` 标签之外照旧不认识账本，账本/会话凭据物理隔离在协调机。
- **协调者纪律落 skill/纪律层**（非代码）：简报六段、叙事文体、收口四段、偏差
  上报义务（executor 纪律块补「执行中偏差如实记入 ledger 收尾段」——填补级偏差
  账的完备性来源）、重建四步。环节执行体需幂等补解析「有终态无裁决事件」的中间态
  （协调者死亡窗口），归 contract。
- **控制台**：新 dock 入口 + 路由（扩展点②）：会话列表页、房间页、收件箱。

### 测试接缝清单（每缝：符号 + 调用方；plan 的接缝覆盖闸按此执法）

架构决定（§8.0）使主缝天然落在门面上——**入站 api 与出站 client 就是本子系统的
两条法定缝**，不需要为可测性另抽内部函数（假缝禁令）。

1. **会话子系统入站 api 门面**（新建）：调用方 = 控制面 gateway 的 HTTP/WS 层、
   CLI 房间命令族；导出到会话子系统的 api 包（外界唯一入口）。本缝断言全部会话
   语义：消息恰好消费一次、绑定席位 CAS 与换绑剥权、成员派生规则（开卡入三处/
   收卡按规则重算/兼任多席）、房间生命周期（并入冻结、终态只读、复活沿用）、
   白名单书写者规则、@定向消费。
2. **会话子系统出站 client 接口**（新建）：调用方 = 会话子系统内部；接口定义在
   会话侧、由组装点绑定账本 api 门面实现。本缝用**测试替身**断言对外依赖的调用
   契约（发布事件、写 decision_answered、读绑定所需卡字段），并保证会话逻辑可在
   不起账本的情况下独立测试——这正是双向门面换来的可测性（第 2 档 interface 的
   正当用途，注释标注测试缝）。
3. **card_events 单流消费缝**（存量）：`internal/agentd` 的 Hub 发布/订阅
   （`n_agentd_Hub_Publish`，调用方 wait/控制台 WS）——新消息事件类型流经既有
   单流、群级无卡事件可订阅。
4. **环节执行体缝**（存量）：`internal/ledgerstep` 节点驱动（调用方
   `handoff card dispatch --step`）——推翻级停卡=等人标记、在飞轮跑完不推进、
   「有终态无裁决事件」幂等补解析。
5. **控制台契约层缝**（存量结构，新增端点）：Web 侧 api client（`d_web_contract`
   的 `k_web_api_client`/`k_web_api_ledger` 同构，调用方 = 房间页/收件箱组件）
   ——答复直达 decision_answered、收件箱三源聚合（open 裁决简报 + 上浮工单 +
   @提及）、无人在场明示文案。

前端组件级断言随 5 走（jsdom 看不见布局的既有教训适用，布局类验收留真机）。
**契约面机械执法**：`graph check` 对 `target.json` 新声明的契约面为硬闸——本期
新增跨子系统边必须先声明，穿透他方内部即违法。

## 9. 用户故事

1. 深夜清账：打开会话列表 → 收件箱两条待回复（一条推翻级简报、一条兜底工单）→
   逐条读六段简报、点选项答复 → 读三条收口摘要 → 关屏。全程不读 diff、不进 timeline。
2. 开卡：从卡点「新建会话」→ 工作台拉起协调者会话聊 spec（卡上下文自动注入）→
   房间落「spec 会话已开启」「spec 已定稿 + 要点」两条指针。
3. 批量 bug：五张散卡并入承载卡 → 一个协调者一个房间推进 → 收口摘要列全部偏差。
4. epic：父卡协调者创建 N 子卡后兼任（占 N 个席位逐张推），或用户给 A/B 各建
   协调者、父协调者入子房间简报下传；子卡 B 推翻级简报 → 用户答复 → 恢复。
5. 换绑：协调者限额，在房间里如实说「到限额了」（或心跳丢失被看板亮出）→ 用户
   换绑另一 agent 的 CLI → 新任按重建四步接手，会话史即交接简报。
6. 跨卡沟通：B123 协调者发现改动影响 B145 → 项目群发言 @B145 → B145 协调者
   回合末收到，纳入自己的下一步。

## 10. Out of Scope

**永不做**：聊天面内跑 agent 会话/展示工具调用与思维链（桌面端/TUI 会话的活）；
executor 入房间或写账；富文本消息存储。
**多人时代再议（落 roadmap）**：多个人类成员、登录与权限体系、线程、已读回执、
在场状态、消息搜索。（@ 已按成员寻址进本期；推迟的是多人类语义。）
**三期再议（落 roadmap）**：规则引擎自动拉起协调者；兼任/分派定性；限额检测与
自动接手；答复/消息事件主动唤醒休眠会话；叙事员轮评估。
**本期不做**：对既有 timeline/看板语义的任何改动（「需要你」v1 保留）；markdown
导出器扩展；移动端。
**本期不做的架构还债（后续要做，已落 roadmap）**：把被依赖子系统的**实现**迁进
标准结构——本期只为用到的子系统建薄 api 门面（绞杀式还债、升格随卡走）；存量
`d_gateway → d_ledger`（17 条）与 `d_cli → d_ledger`（4 条）直调边的清理不在本期，
本期只保证**不新增**穿过它们的直调。
