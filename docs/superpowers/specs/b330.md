## 问题陈述

谁在什么条件下走排队：`card dispatch --step` 点火 charter 派发节点时，编制域只在 `node.Override.Squad` 非空时 `Admit`。现网 charter v10 七个派发节点的 Squad 全空，于是走模板默认执行者，两级并发和看板排队横带对真卡是哑的。用户已经建好执行者小队 `runner`（角色 executor，成员 muse/5）。这是编制没接到工作流，不是 runner 登记失败。

现状读数（2026-09-04）：

- `internal/agentd/cardstep.go`：`if node.Override.Squad != ""` 才 `admitSquadStep`。
- `internal/agentd/scheddispatch.go#admitSquadStep`：满员 `ErrNoSlot` 转 `Enqueue`；一次性 `--target/--executor/--model` 仍经 `effectiveCovers` 交给 Admit。
- 协调者拉起走 `leader` 小队 + `LaunchAdmit`，不经本文件。本卡不改协调者入口。
- `handoff squad list`：载体 grok(mac-02, grok, 3)、muse(mac-02, opencode, 5)；小队 `leader`(coordinator, muse/5)、`runner`(executor, muse/5)。
- charter v10 派发节点 squad 全空：contract / breakdown / plan / implement / review / integrate / 图对账。人工列 待办 / spec / acceptance / finish / 已完成 本来就不是派发节点。
- 卡钉版本：`workflow put` 只产生新版本，钉 v10 的在飞卡不吃新定义，除非显式 `workflow migrate`。

## 方案

**只 put 新版本，把七个 `dispatch: true` 节点的 `override.squad` 设为 `runner`。** 其余字段（template、discipline、purpose、produces、gates、board、max_rounds、节点能力开关、产出、路由）与 v10 Def **语义相同**。人工列继续不填 squad。

不 migrate 任何在飞卡（含 B329、本卡自己）。新卡和显式迁过的卡才走 runner。`--target/--executor` 一次性覆盖语义保持现网 Admit（请求覆盖 > 节点覆盖；节点现在多了 squad 解析层，有覆盖仍占 runner 名额，不退回空 squad 直绑）。

弃选：

- **改 Go 让空 squad 也走 runner**：会把所有未绑小队的流一齐推进队，B156.3 契约是「空 = 存量直绑」。
- **七个节点只绑 implement**：plan/review 仍绕开排队，卡面问题只修一半。
- **把 `runner` 写进 `deploy/workflows/charter-v4.json` 当出厂默认**：小队名是本机编制，不是仓库出厂物。本卡定义文件挂在 spec 旁，给本账本 put，不冒充出厂种子。日后也禁止用未含 squad 的出厂种子再 put 把接线覆盖掉。
- **migrate 全部在飞卡**：钉旧版、正在走模板默认（本机 + charter-default 的 codex）的轮次会被改去 muse/opencode。
- **把 review 绑到别的小队**：用户只准备了一支执行者小队。
