## §0 待拍板清单（拍板者按此裁决）

> 以下每项都是「有两种做法、选哪种取决于偏好/契约取舍」的岔口。协调者 2026-09-11 已逐项回写裁决 + 理由。

### P1｜AutoAllow 无工单时，`RespondPermission` 失败「不产 `delivery_failed`」的闸位放哪

冻结条目 #11 写「OpenCode AutoAllow 终态下 `RespondPermission` 失败**不得调用** `NoteDeliveryFailed`，不得追加 `EventTypeDeliveryFailed`」。但 `executor.Authorize` 只回传 `ApprovalDecision`（仅 `Status/Reason/Rule`），**丢弃 `ApprovalResult.Ref`**；adapter 在 `authorizeNativePermission` 内自造 `NamespacedTicketID`，既有返回值里没有「本次决定是否有工单」的信号。AutoAllow（无工单）与 approver allow / deny（有工单）都是 `RespondPermission` 一次，失败时若只按调用事实上报就会打出假 `delivery_failed`。闸位选哪种做法：

- **方案 A（adapter 按 rule 白名单判定）**：`authorizeNativePermission` 认为 `Status==Deny` 或 `Rule` 属「有工单」集合（`approver`/`reuse`）时才上报；AutoAllow 的 `safe-command`/`self-command` 视为无工单，跳过上报。优点：签名零改动，adapter 自己闭合 #11。代价：adapter 耦合 approval 包的 rule 字符串（且不得 import permgate），rule 分类需在 executor 契约里获得稳定含义——可能等于新增一条契约语义。
- **方案 B（闸在 `approval.Client.NoteDeliveryFailed`）**：adapter 照旧经 `deliveryFailureReporter` 上报，`Client.NoteDeliveryFailed` 先查 `hooks.Store` 有无该工单，无工单只记日志、不转发 hook。优点：签名零改动，adapter 不猜 rule；贴合 spec「回传失败按有没有工单分叉」。代价：与 #11 首句「不得调用」字面冲突（调用发生、只是不转发），需 contract 边界澄清（见 §2.3 C-2）；会让 `TestClientNoteDeliveryFailedTaskIsolation` 的 fixture 需要真实工单。
- **方案 C（闸在 `Manager.NoteDeliveryFailed`，事件产出点）**：调用链不变，`Manager.NoteDeliveryFailed` 先查 `m.st.GetTicket(ticketID)`，不存在则不 `AppendEvent`。优点：最贴合「工单是送达事实的权威」；`Manager` 已是全部 `delivery_failed` 的唯一产出点。代价：同样与 #11 首句字面冲突，需澄清；会波及 `internal/agentd/approver_test.go#TestApprovePermissionAdapterForFailureNotesDeliveryFailed`（该测试未建工单就直接 `approvePermission`，须补建工单才faithful）。
- **方案 D（给决定加投递归属信号）**：在 `executor.ApprovalDecision`（或 `ApprovalResult`）新增字段（如 `TicketBacked bool`），AutoAllow 置 false，其余置 true，adapter 据此跳过。优点：语义最干净、adapter 不猜。代价：**新增导出字段 = 新导出符号**，与 contract Ticket 0「无新导出符号」及冻结 #1 的克制口径冲突，**需退回 contract** 才能实施。

**裁决：A。** 冻结 #11 按**调用级**执行（adapter 不得调用 `NoteDeliveryFailed`）。`authorizeNativePermission` 仅在 `Status==Deny` 或 `Rule` 为 `"approver"` / `"reuse"` 时上报失败；`Allow` 且 rule 为免审（`safe-command` / `self-command` 等非上述二者）则跳过。否掉 B/C（与 #11 字面冲突）、D（退回 contract）。理由：贴合已冻「不得调用」与 Ticket 0 无新符号；adapter 用既有 `ApprovalDecision.Rule/Status`，不猜工单。

### P2｜冻结条目 #16 的「一条穿过生产 `bindApproval` + `authorizeNativePermission` 的测试」落在哪个包

contract #16 要求「经生产 `bindApproval` 的 AutoAllow 走进 `authorizeNativePermission` 时，全程 `RespondPermission` 次数为 1；生产钩子次数为 0」。生产 `bindApproval` 在 `package agentd`（未导出），`authorizeNativePermission` 在 `package opencode`（未导出），两者互相看不见：

- **方案 A（拆两条、传递覆盖）**：(1) agentd 内以生产 `bindApproval` 构造 client，注入记录型 fake adapter，`Request` 命中 AutoAllow，断言生产钩子 `RespondPermission`==0 且审计事件恰好 1；(2) opencode 内以 allow 的 fake client 驱动 `authorizeNativePermission`，断言 fake server 恰收 1 次权限应答。两条合起来覆盖 #16 的行为，但偏离 #16「一条」的字面。代价最小。
- **方案 B（单条组合测试放 agentd）**：agentd 测试内用真实 `opencode.New()` 经 `Start` 驱动，并**在 agentd 测试里重造一个 opencode HTTP/SSE 假服务**。满足字面，但把 opencode 包 `fakeServer`（`adapter_test.go:144`）整套复制到 agentd，重且脆；且 `authorizeNativePermission` 仍不可直接触发。
- **方案 C（opencode 包新增导出测试缝）**：给 adapter 加导出注入/触发入口。**新导出符号**，与 Ticket 0 冲突，需退回 contract。

**裁决：A。** 两条测试传递覆盖 #16：agentd 经生产 `bindApproval` 断言钩子零回传；opencode 经 fake client 断言 adapter 恰一次。否掉 B（复制 fakeServer 脆）、C（新导出）。理由：Ticket 0 禁止新符号；#16 的「一条」按行为合取验收，不按单测文件字面。

### P3｜`autoAllowPermission` 拆成两条包内路径的形态与自动放行计数归属

contract §6 要求把 `Manager.autoAllowPermission`（`internal/agentd/manager.go#Manager.autoAllowPermission` :2302，现状审计 + 回传）拆成「只审计」与「审计 + 回传」两条包内路径，`bindApproval` 只绑前者，`handlePermission`/`respondAutoAllowReplay` 走后者；但没冻结拆法。岔口：

- **拆法**：(i) 新增 `auditAutoAllowOnly(taskID,ev,verdict)` 只做审计，`autoAllowPermission` = `auditAutoAllowOnly` + 既有回传，`bindApproval` 绑 `auditAutoAllowOnly`；(ii) `autoAllowPermission` 变为只审计，回传调用下沉到 `handlePermission`/`respondAutoAllowReplay` 两个调用点；(iii) 共享函数加 `respond bool` 参数。三者在「谁的名字挂在 `Hooks.AutoAllow` 字段」上不同，影响既有测试的替换面。
- **计数归属**：现状 `noteAutoAllowed`（:2348）在 `RespondPermission` 成功后才调用。拆开后，OpenCode 走只审计路径不会回传，若计数仍在回传后，则 OpenCode 的免审计数从汇总里消失（`takeAutoAllowed` 汇总见 :3561）；若把计数移进审计函数，则非 OpenCode 在回传失败时也会计数（现状不计数）。两选一都改动可观察汇总。**未发现测试锁住 `aaCount`**，但这是行为变化，需拍板。

**裁决：拆法 (i)；计数跟审计走。** 新增包内 `auditAutoAllowOnly`，`autoAllowPermission` = 审计 + 既有回传；`bindApproval` 只绑 `auditAutoAllowOnly`。`noteAutoAllowed` 放进审计函数（spec：钩子写审计及既有计数）。否掉 (ii)/(iii)。理由：OpenCode 不再回传，计数若留在回传后会从汇总消失；计数跟决定走，不跟原生投递走。

### P4｜第二处锁错时序测试的处置与 contract 回写

`internal/agentd/approval_client_test.go#TestApprovalClientApproverAllowCreatesReusableGrantAndSecondRequestReuses`（:482，尤其 :559「DeliveredAt 必须非空」与随后立即复用）与只读的 contract 现状表所记 `internal/approval/client_test.go#TestClientConsultAllowPersistsGrant`（:411）锁的是同一错误时序，但 contract 未列此第二处。建议：**纳入本卡有界文件集**，改成 `Request` 后 `DeliveredAt==nil`，第二次复用前显式 `Acknowledge(AckDelivered)`；并在 contract 现状表补录一行（见 §2.3 C-1）。请拍板是否确认该回写与测试改法。

**裁决：纳入。** 该测试改成 `Request` 后 `DeliveredAt==nil`，`Acknowledge(AckDelivered)` 之后才复用。contract §8.1 已补录，确认。理由：不改会在 implement 假红，且与冻结 #6/#13 同向。

### P5｜非 OpenCode 的 AutoAllow 重放路径是否随本卡一并改语义

`respondAutoAllowReplay`（:2685）在重放时对免审再次 `RespondPermission`。契约只在 `handlePermission` 侧要求「AutoAllow 仍回传一次」。本卡应**只断 OpenCode 的二次投递与提前送达**，`respondAutoAllowReplay` 保持既有回传行为（agy HOME+workspace 双 hook 依赖它）。请拍板确认这是本卡边界（建议：保持，不动 replay 语义，只把它归入「审计 + 回传」那条包内路径）。

**裁决：保持 replay 语义。** `respondAutoAllowReplay` 走「审计 + 回传」路径，不改 agy 双 hook 重放。理由：本卡只断 OpenCode 二次投递；非 OpenCode 权威不迁（冻结 #14）。

## §4 单一实现范围（本卡，不建子卡）

### `B233.12-impl`｜审批入站收口：Hooks 不再投递，送达只在原生回传成功后

#### ①契约引用

- `docs/superpowers/specs/b233.12-contract.md` §1–§7，冻结条目 #1–#16（重点 #3、#5–#7、#10–#14、#16）。
- `docs/superpowers/specs/b233.12.md` §方案、§实现决定、§测试决定。
- 执行入口：`internal/agentd/approval_client.go#Manager.bindApproval`、`internal/agentd/manager.go#Manager.autoAllowPermission`、`internal/approval/client.go` 的 `Request`/`consult`（图未收录，源码锚）、`internal/executor/opencode/adapter.go#Adapter.authorizeNativePermission`。

#### ②意图与为什么

让「谁投递、何时算送达」各归一位：审批 client 拥有决定（allow/deny/pending、工单 answer、审计），harness adapter 拥有原生投递，`DeliveredAt` 只表示原生回传已成功。OpenCode 路径上：

1. `bindApproval` 绑给 `Hooks.AutoAllow` 的实现只写审计（及既有计数，见 P3），**不得** `RespondPermission`；原生投递只由 `authorizeNativePermission` 对一次权限请求做一次。
2. `consult` 在返回 allow 前**删除** `MarkTicketDelivered`，`Request` 成功路径也不写送达；只有 `Acknowledge(AckDelivered)` 在 `RespondPermission` 成功之后写 `DeliveredAt`。
3. 原生回传失败：有工单的 approver allow 走既有 `NoteDeliveryFailed`（工单保持未送达、可 resume）；无工单的 AutoAllow **不产** `delivery_failed`（闸位按 P1），不把「第一次已送到、第二次才失败」打成假事件。

非 OpenCode 不改权威：`handlePermission` AutoAllow 仍回传一次，因此「审计」与「非 OpenCode 回传」必须拆成两条包内路径，禁止继续共用一个「审计顺带回传」函数给两条路径（拆法见 P3）。

不写实现步骤之外的事实：本卡不迁 `Manager`、不迁五家 harness 权威、不拆 Judge/Transit/Store、不改 HTTP/CLI/事件类型、不新增导出符号（P1-D 例外，需退回 contract）。

#### ③验收（按子系统类型分流 + 缺陷族逐族）

**逻辑型：`d_orchestration`**

- `go test ./internal/approval -run 'TestClient(ConsultAllowPersistsGrant|AutoAllowHasNoTicket|NoteDeliveryFailedTaskIsolation)' -count=1` 返回 `ok`：`Request` 命中 approver allow 后工单 `answer=allow` 且 `DeliveredAt==nil`；`FindReusableGrant` 未命中；`Acknowledge(AckDelivered)` 之后才可复用（`Request` 第二次返回 `Rule=="reuse"`）。变异：把 `MarkTicketDelivered` 加回 `consult`，测试必须红。
- `go test ./internal/agentd -run 'Test(ApprovalClientApproverAllowCreatesReusableGrantAndSecondRequestReuses|ApprovalClientAcknowledgeStages|SafeCommandPermissionAuditsOnceWithoutTicket|ApproverApprovesPermissionWithoutWaking)' -count=1` 返回 `ok`：agentd 侧同一时序断言改后通过；`handlePermission` 的 AutoAllow 仍恰回传一次（`adapter.recordedPerms()` 长度为 1，重放后为 2）；非 OpenCode `approvePermission`/`waitPermission` 仍 `markDelivered`。变异：`handlePermission` AutoAllow 分支去掉回传，测试必须红。

- 回传失败可恢复（有工单）：approver allow 后模拟 `RespondPermission` 失败，`UndeliveredAnswers(taskID)` 含该工单，`FindReusableGrant` 不命中；免审 AutoAllow 失败不进该列表（无工单）。
- `client` 侧 `NoteDeliveryFailed` 跨任务隔离保持（`TestClientNoteDeliveryFailedTaskIsolation`）；若 P1 选 B/C，需新增「无工单不转发/不产事件」的反面断言。

**序列化边界**

- 本卡不新增数据字段。手写投影清单：`permissionAutoAllowPayload`（`manager.go`，AutoAllow 审计）、`deliveryFailedPayload`（`internal/agentd/manager.go#Manager.NoteDeliveryFailed`）、`ticketAnsweredPayload`/`approverDecisionPayload`（`approval/client.go`）均**不变**。需一条穿过真实 Store 事件流的断言：AutoAllow 无工单时**不存在** `delivery_failed` 事件（区分「字段缺失」与「值零值」在此不适用，因为没有新字段；用事件类型的存在/缺失断言）。**无 roundtrip 新字段。**

**追加缺陷族对抗审查**

- **生命周期 / 状态机中断：** 提前标记送达会在宿主/进程重启前留下「已送达」假事实，让 RecoverStuck 不再重投。改后送达只在原生成功后落库。`consult` 删除提前写入后，`Request` 返回与 `RespondPermission` 之间崩溃 → 工单「已答未送达」，由 `UndeliveredAnswers` + resume 补投；该请求-回传崩溃窗口的真实行为**未验证，需真机**。孤儿资源（无工单 AutoAllow）不由 `UndeliveredAnswers` 兜底，符合 B249。
- **静默失败 / 误导报错：** `consult` 的日志「审批者批准已持久化并送达」在去掉提前标记后必须改为「决定已落、尚未送达」（spec 实现决定），否则报成功却未送达。`Acknowledge(AckDelivered)` 对无工单是 0 行 no-op（C-4），不得被读成错误；`MarkTicketDelivered` 失败仍在 `Acknowledge` 返回错误。AutoAllow 无工单不产事件，避免误导协调者去 resume 不存在的工单。
- **跨平台假设：无，因为**本卡只改审批/投递时序，不解析 OS 路径、进程组、权限模型或 webview；OpenCode 原生 HTTP 的跨平台现实归 `d_execution` 真机清单。Linux 机内绿不得推广到 macOS/Windows。
- **假红 / 假绿测试：** 禁止只用替身 `Hooks.AutoAllow`（`client_test.go:136` 那种只计数的 fixture）冒充生产钩子——P2 方案 A 的 (1) 必须经 `bindApproval`。禁止只断言 `Request` 返回 allow 就算「未送达」——必须读回 Store 的 `DeliveredAt`（可空指针区分「缺失」与「零值」）。「只回传一次」断言要锁调用方依赖的行为（对同 PermissionID 的 `RespondPermission` 次数），换实现不改需求时不应乱红。变异必须能变红：`consult` 加回提前标记、生产钩子加回 `RespondPermission`、adapter 对 AutoAllow 仍上报，三者各对应一条可变红测试。
- **门禁绕过：** `DeliveredAt` 的写入口仍有多处（`approval.Acknowledge`、`Manager.markDelivered` 的 :1972/:2003/:2639/:2998/:3139），本卡只移除 `consult` 这一处违约写入，并核对其余均在成功 `RespondPermission` 之后。检查与动作之间：`consult` 建单→答题→返回 allow 与 adapter 回传之间没有送达门，故不担心 TOCTOU；须确保没有第二个「提前写送达」的旁路出现在 `Request` 的其他分支（现状排查：仅 `consult` 一处）。
- **序列化边界：** 见上，无新字段；`delivery_failed` 事件存在性是行为事实。
- **枚举新值过既有白名单：无，因为**不新增 EventType、TaskState、AckStage、ApprovalStatus 或 kind；复用既有 `delivery_failed`/`permission_auto_allow`/`allow`/`delivered` 字面值。
- **承重安全属性有测试锁住：** 「送达只在原生回传成功后」（一次/顺序属性）必须有一条能变红的测试（变异 `consult` 提前标记 → 红）；「一次权限请求一次原生投递」同（变异生产钩子回传 → 红）；「AutoAllow 无工单失败不冒充送达/不产事件」同（变异 adapter 无条件上报 → 红）。三者不得只靠实现恰好为真。
- **项目第六族 webview / 平台表现差异：无，因为**本卡不改 `d_web`、浏览器 API 或 webview 渲染；但 OpenCode 原生 HTTP 与执行机平台仍属边界真机项。

## §6 真机清单（未验证，需协调者执行）

1. **OpenCode 免审只投递一次：** 跑真实 OpenCode 任务命中白名单命令，确认 harness 只收到一次原生 allow；事件流有 `permission_auto_allow`，无二次回传失败打出的 `delivery_failed`。
2. **审批者放行送达时序：** 真实 OpenCode 审批者放行，确认 `Request` 返回时 Store 工单 `answer=allow`、`DeliveredAt` 空；原生回传成功后 `DeliveredAt` 才非空；同指纹下一请求送达前不走 reuse。
3. **回传失败可恢复：** 令 OpenCode 原生应答 4xx/断连，确认 `UndeliveredAnswers` 能列出该工单、`handoff resume` 能补投、`FindReusableGrant` 不命中。
4. **请求-回传崩溃窗口：** 在 `consult` 返回 allow 到 `RespondPermission` 成功之间重启 agentd/执行机，记录工单、`DeliveredAt`、executor 阻塞状态，确认由 resume 补投而非错误复用。
5. **非 OpenCode 不回退：** 跑 agy（HOME+workspace 双 hook）的免审与已答重放，确认仍各回传一次、`respondAutoAllowReplay` 行为不变。
6. **平台矩阵：** 在支持的 Linux/macOS/Windows 执行机抽查 OpenCode 原生 HTTP 与 `RespondPermission` 路由；一个平台的绿不得推广为全平台结论。
