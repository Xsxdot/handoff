# B229：纪律块分层重构 + 入账本 + 派发期下发

> 状态：**已批准（用户，2026-08-24）** · 级别 **L3** · 档位 **重档**
> 来源：B229（纪律块版本管理与跨机同步）+ 2026-08-24 梳理会话的四问（配置同步 / 纪律块注入 / 工作流同步 / 流程讲解）
> 现状事实均为本轮工作树与三台在役机器的读数，交 contract 节点在其工作树复核。

## 问题陈述

纪律块今天有三个互相咬着的缺陷，它们同源：**纪律块的正文散落在每台机器的磁盘上，靠"名字匹配 + 多路回退"决定用哪一份。**

### 缺陷一：层归属判错，平台层把实现类纪律灌给了只读角色

`internal/discipline/platform.go:8` 的平台不变量第 3 条是「每确立一个事实就往台账文件追加一行」，收口自查再问一遍「② 台账是边干边追加的吗？」。而 `~/.handoff/discipline/charter-review.md:38` 原文是「**审查是只读回合**：不 commit、不改文件、不建分支内容；合法产出只有裁决表与 findings」。

两段进同一个 prompt。**2026-08-24 实测：grok 在一个审阅任务上反复找台账在哪儿。**

根因不是层数不够，是归属判错。B207 的归属表把「台账落盘」判给平台层，它真正要解的是「走 charter-\* 派的 implement 永远不落台账」——本轮复核，`charter-implement.md` 中「台账」出现 **0 次**，至今如此。**根因在"角色层缺内容"，修法却是"提到平台层强灌所有人"**，于是泄漏到每一个角色。

### 缺陷二：正文跨机漂移，且审计链接不住

`internal/ledgerstep/dispatch.go:8` 包注释写死「不解析纪律块——只把角色名传下去，正文由 agentd 解析注入」。解析发生在**执行机**，读的是**执行机自己的** `<DataDir>/discipline/`。

2026-08-24 实测三台在役机器，**7 份 charter 纪律块有 6 份跨机不一致**：

| 文件 | linux-01 | 本机 |
|---|---|---|
| charter-plan.md | 5367 B | 8113 B（少 34%） |
| charter-implement.md | 12493 B | 15390 B（少 19%） |
| charter-contract.md | 6005 B | 7144 B |
| charter-review.md | 16781 B | 17334 B |
| charter-breakdown.md | 7882 B | 8053 B |
| charter-recon.md | 2330 B | 2388 B |
| charter-integrate.md | 2184 B | 2184 B（一致） |

linux-01 全面偏旧；该机 `<DataDir>/discipline/` 另有两个 macOS AppleDouble 残留（`._new-plan.md`、`._new-review.md`）。**没有任何东西会告诉你副本旧了。**

而审计链答不了这个问题：`internal/ledger/events.go:113` 明写「原字段是正文指纹；纪律块改为具名资源后正文不再经过 CLI，指纹无从算起，同一个问题的答案换成名字」。**指纹是被主动放弃的。** 今天只能回答「用了哪个名字」，不能回答「用了哪份正文」。

### 缺陷三：老 agentd 静默降级，安全哨兵一并失效

mac-02 跑 v0.3.5。`git show v0.3.5` 复核：`internal/discipline/resolver.go` 中 `func (r *Resolver) ByName` **0 处**，`internal/proto/proto.go` 中 `DisciplineName` **0 处**；该机 `<DataDir>/discipline/` 文件列表为**空**。

于是往它派 charter 节点会发生：请求里的 `discipline:"charter-review"` 被 JSON 宽松解码**静默忽略** → 退回 `For("codex")` → `single-context.md` → **审阅节点拿到实现纪律「每个 task 完成即 commit」**。模板 `charter-default` v5 里那个 `discipline: "charter-must-override"` 哨兵（故意写不存在的名字逼节点 override）在它面前**也失效**——不拒发，静默降级。

本轮核实 mac-02 上 108 个任务中 `cards/` 前缀 **0 个**，故此缺陷当前**潜伏未触发**。

### 三者同源

`Resolver` 今天有六条回退分支：`ByName` 三档（`resolver.go:141`：磁盘 `<name>.md` → 内置同名 → 报错）、`For` 三档（`resolver.go:91`：配置有值 → 显式空串关闭 → 内置默认）。**每一条都是"猜用哪份"的机制，也都是漂移的载体。**

## 级别与档位

**L3**。定级两问：

1. **跨几个子系统的契约面**：账本域（新聚合 + schema）、控制面（组装点与派发编排）、执行契约（wire 字段与能力位）三处同动。
2. **动不动契约层**：动。派发协议新增正文字段，且必须处理老 agentd 的降级——`internal/proto` 是跨进程 wire 契约。

**重档**。选档判据是「单子系统工作量是否超过流程固定成本（约 70 分钟）」：账本侧（新表 + 读写 + CLI 命令族 + 存量 7 份导入）与控制面侧（三层重构 + 协调者侧解析 + 能力位拒发闸 + 删内置）各自明显超过。两侧有强依赖（控制面要用账本新表），这正是 contract 节点先冻结接口再并行要解决的形态。

## 方案

### 采纳：正文入账本 + 协调者组装下发 + 三层归位

**权威副本入账本**（`disciplines` 聚合），**协调者在派发时取正文、组装、随任务下发**，执行机不再读自己的盘。

三条子决定：

**① 引用形态：`(name, version)`，与既有两个聚合逐字同构。**

`internal/ledger/store.go:234,237`（PG）与 `:296,299`（SQLite）中，`workflows` 与 `dispatch_templates` 主键都是 `(name, version)`；**这个库里今天没有代理 ID 这回事**。工作流节点写 `discipline: "charter-review"`，派发时取最新版，版本号记进 `DispatchSnapshot`。

弃选**加 ID 列**：`disciplines` 是不可变版本化的，一个名字 N 个版本 = N 行，"加一列 ID"立刻分叉成行级（绑 ID 即钉死版本，改一句纪律要发新工作流版，而工作流版是卡钉着的，存量卡不跟进）或聚合级（要拆两张表，成为本库第一个例外）。而 ID 的主卖点"改名不断链"在不可变模型下本就不成立——行永不删，旧名字的行永远在，旧工作流版本照样解析得开；改名是「发一个新工作流版本指向新名字」，那本就是工作流的正常操作。

弃选**内嵌快照**：`charter-review.md` 单份 17 KB，七个节点内嵌逾 100 KB 塞进每个工作流版本，改一句话复制一份全量，且纪律块无法跨工作流复用。

**② 三层，按所有者切。**

| 层 | 谁决定 | 能否被下层改 | 内容 |
|---|---|---|---|
| ① 平台 | handoff，二进制内置 | 不能（只有机器级 `platform_invariants:false` 整体关，保留现状） | 不派发 / 不调 CLI / 不起 executor；没跑到不许写结论；按协议输出 trailer。**「落台账」从此层移出** |
| ② 角色 | 工作流节点点的名 | —— | 账本 `disciplines` 里的行。**「落台账」落到此层**，只给产出型角色（implement / contract / breakdown / plan），review 不给 |
| ③ 执行器附注 | 机器级 `Discipline` 映射，追加 | —— | **本轮只定语义不实现**（见 Out of Scope） |

**① 的准入判据**（今天缺的正是它，B207 才会判错）：

> 写一条平台层纪律，逐个角色问「这个角色执行得了吗」。有一个执行不了，它就不是平台层的。

现有四条过判据：不派发 ✓、没跑到不许写结论 ✓、trailer 收口 ✓、**落台账 ✗**（review 是只读回合，没有写通道）。判据精确挑出这一条，且只挑出这一条。

弃选**按执行器分类定制**（即为每个 executor 各备一套完整纪律）：切不开这刀。**同一个 grok，跑 implement 该落台账，跑 review 不该落**——执行器不是这条缝的所在。要么两边都落（今日之病），要么两边都不落（B207 之前之病，已实测）。

弃选**把"执行器能力层"抬成独立一层**：`internal/discipline/discipline.go:95` 的 `builtinByName` 只在 `NameImplement` 分支调 `builtinFor(executor)` 分档，review / spec-draft / plan-writing / finishing 四个角色**根本没有档位这回事**。它不是一条轴，是 implement 内部的一个分叉；抬成层会造出只有一个成员用得上的轴。

**③ 内置角色块全删。**

`internal/discipline/builtin/` 六份（subagent / single-context / review / spec-draft / plan-writing / finishing）删除。重构后一切正文从账本取，回退阶梯不存在，兜底内容随之无意义。

**`platform.go` 的平台层正文留在二进制**——它是 ① 层，按定义不能被数据替换，否则「恒在」是假的。

**弃选：接口推送 + 对账子命令。** 复用现成的 `PUT /api/discipline/file?machine=` 加推送命令，零 schema 变更、不给派发链路加依赖。但推送是命令式的：新机器、漏推、推一半就漂；版本与对账要自己造。这是**给正在漂的形态加固**，治标。

**弃选：正文入库但执行机自己连库读。** 协议改动最小，但要求每台执行机长期具备"连得上账本库"这个属性，且要向各执行机分发库凭据（今天它们连读都不需要——`internal/ledgermirror/mirror.go:1` 的镜像跑在协调者侧）。更根本的是它**表达不了「协调者临时捏一份纪律块下发」**——那只能引用库里存着的行。

## 用户故事

1. 作为协调者，我在任意一台机器上改一句纪律，全网下一次派发立刻生效，不需要往每台机器推文件。
2. 作为协调者，我能对着一张卡的派发事件回答「这一轮用的是哪一版纪律块正文」，而不只是「哪个名字」。
3. 作为协调者，我能为某一次派发临时组装一份纪律块直接下发，不落库、不影响其他派发。
4. 作为审阅节点的执行者，我不再被要求做只读回合做不到的事（往台账文件追加行）。
5. 作为协调者，把任务派到一台还没换版的执行机时，我得到**明确的拒发**并知道原因，而不是一份静默降级成实现纪律的审阅任务。
6. 作为协调者，我不需要知道纪律块正文在哪台机器的哪个目录——那个概念消失了。
7. 作为方法论维护者，我改 charter 仓的 SKILL.md 后跑一次 regen，产物带版本号进账本，可回溯、可 diff。

## 契约语义与接缝（L3）

**只定语义，不定签名**——精确签名归 contract 节点。

### 跨子系统规则与收口层

- **正文解析收口在协调者侧，且只有一处。** 今天 `internal/agentd/manager.go:359` 的 `resolveDisciplineFor` 是唯一裁决点（三个调用点：首派 `:754`、continue `:1265`、resume `:3374`），这个"唯一"必须保住并搬到协调者侧。分开写的表现是首回合注入了下发的正文、continue 之后悄悄换成执行机本地的——首回合是对的，事后极难查。
- **`internal/ledgerstep` 的既有边界反转。** `dispatch.go:8` 的「不解析纪律块——只把角色名传下去」作废；改为由持库方解析并把正文放进派发请求。这是本轮**唯一**被显式撤销的既有契约声明。
- **执行机的纪律块目录与本地解析路径退役。** 执行机 agentd 不再读 `<DataDir>/discipline/`，`Resolver` 的六条回退分支全部删除。
- **账本从可选变必需。** `internal/config/config.go` 中 `LedgerConfig.Enabled` 默认 false、关闭时 card/workflow/decision 三族拒执行；纪律块入库后，关账本等于没纪律块。该开关退休或翻默认，兼容路径归 contract。

### 依赖方向

新增方向：协调者侧派发编排 → 账本 `disciplines` 读。
**不新增**：执行机 → 账本（执行机仍然不碰账本，凭据不外发）。

### 能力位与拒发（wire 契约）

目标机是否支持"接收下发正文"，用**既有能力位范式**判定，不比版本字符串（脆）。`internal/agentd/server.go:680-683` 已在用 `PtySupported *bool` / `LaunchersSupported *bool`，**nil = 老版本不支持**。

**语义：目标机不支持即拒发，带真因，绝不静默降级。** 这与既有纪律同源——`resolver.go` 的「配置指向的文件缺失是错误而不是退回内置：悄悄换一份比失败更危险」。缺陷三就是这条纪律在 wire 层缺席的后果。

### 事件与数据流向

`DispatchSnapshot`（`internal/ledger/events.go:113`）新增纪律块版本号。B107 那个问题——「那次派发用的哪版纪律块」——从"名字"升级回"名字 + 版本"，恢复 B207 之前放弃掉的可回放性。

### 源头与权威副本的分工

**charter 仓（`~/workspace/charter`）是源头，账本是权威副本。** 今天链路是 `skills/*/SKILL.md` → `scripts/regen_discipline.py` → 本机磁盘；改为 regen 的落点写账本、带版本号。像编译：源码在仓库，产物在库里可回溯。regen 脚本本身在 charter 仓，其改动不属本卡。

## 实现决定

1. **裸 `handoff dispatch`（不点名）只注入平台层 ①。** 内置角色块删除后没有兜底可言；不点名就是不点名，不去猜。要角色纪律就显式点名。
2. **`charter-*` 前缀保留。** 内置删除后它不再承担"与内置区分"的职责，改为承担方法论命名空间——将来有非 charter 的流时仍有用。
3. **存量 7 份 charter 纪律块导入账本为各自的 v1**，以**本机副本**为准（本机今日跑过 regen，是三台里最新的）。导入后 `charter-implement.md` 需补台账纪律一句——这是缺陷一的内容侧修复，机制侧修复（台账从 ① 降到 ②）不会自动补出源头没有的东西。
4. **机器级 `Discipline` 映射本轮不动。** 本轮实测三台机器（本机 `discipline: {}`、mac-02 与 linux-01 bindings 全 `mode:default`）该映射**全空**，从引入至今无人使用；其语义改造留待真需求出现。
5. **全网同批升级是本卡的前置**，不是可选项。三台机器现为三个版本（本机 `d0d868fdbbb4`、mac-02 `v0.3.5 4b38262e`、linux-01 `213b58d8`）。

## 测试决定（接缝清单）

理想一缝，本轮两缝——它们分属存储契约面与派发契约面，合并会造出一个既读库又拼文本又判 wire 能力的巨函数。

1. **协调者侧派发纪律解析入口**（新建符号，导出到派发编排的公开面）。
   一次派发的正文全链路收口于此：取库 → 三层组装 → 判目标机能力 → 返回正文或拒发理由。
   **将被谁调用**：`internal/ledgerstep` 的模板派发路径，与 agentd 的环节执行体（今 `internal/agentd/cardstep.go`）；continue / resume 两条路径同样经它，不得另起解析。
   **导出到哪一层**：派发编排包的公开面；执行机侧不导出（执行机不再解析）。

2. **`disciplines` 聚合的读写**（新建符号，`internal/ledger` 公开面）。
   **将被谁调用**：`cmd` 的 discipline 命令族与缝 1。
   **形态**：与 `internal/ledger/templates.go#PutTemplate` / `GetTemplate` 同构（不可变版本化、只插新版）。

**假缝禁令核过**：两条缝都有生产调用方且导出到包公开面，非"只为走满分支抽出的纯函数"。`discipline.Compose` 的三层化改造属缝 1 的内部实现，**不单列**——它今天虽已导出，但重构后其唯一调用方在缝 1 内，单列会占一个名额却测不到跨层行为。

**边界型例外**：目标机能力位的 `*bool` 三态解释（nil / false / true）属对端 wire 载荷解析，其解析入口即缝上符号，表驱动测试视为穿过缝 1，不占内部锁名额。

## Out of Scope

**永不做**：

- 按 executor 分类定制整套纪律（判据见"方案·弃选"，切不开 implement/review 这刀）。
- 向执行机分发账本库凭据。
- **完整配置分层分类表（原 Q1）与工作流主流程/每命令讲解文档（原 Q4）**。2026-08-24
  用户判决不做。分类结论已并入本文"契约语义·账本从可选变必需"与下方"其余策略类配置"
  两处，不再单列成文。

**本期不做、后续要做**（逐条落 `docs/roadmap.md`）：

- **③ 执行器附注层的实现**。本轮只定语义（机器级 `Discipline` 映射改为"任何路径都追加"，空串 = 无附注）。今天三台机器该映射全空、无人使用，无需求即不造。真需求出现时从这个已定的语义长出来，不另起概念。
- **其余策略类配置的同步**：`Executor`（缺省执行者/模型）、`Approver`、`StallTimeout`、`Sync.Auto`、`Terminal.Auto`、`PlatformInvariants`。它们同属"该同步而今天没同步"，但每一项都要单独回答"机器级覆盖怎么表达"，混进本轮会把 spec 撑爆。
- **工作流引用的其余名字的同步**：`executor` 名与 `target`（机器）名今天仍指向每机 config。工作流形状在账本里全网一致，这两个名字在不同机器上仍可指向不同的东西。
- **`launchers.json` 的同步定性**：其 `Command` 可能含凭据（`internal/agentd/launchers_api.go:11` 已为此立下"命令原文绝不进日志"的纪律），是否可同步需单独判。
- **linux-01 上两个 AppleDouble 残留文件的清理**（`._new-plan.md`、`._new-review.md`）。执行机纪律块目录退役时一并消失，无需单独动作；此处只登记，避免它在退役前被误当作有效纪律块。
