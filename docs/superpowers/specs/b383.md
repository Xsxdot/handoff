## 1. 问题陈述

夜班实测（卡事件 16420）暴露两类成本：**噪声**（opencode 双 WARN 把 agentd.log 冲成噪声场，真实告警被淹；权限门判据假阳性把合法动作升级人工）与**往返**（同类命令反复升级、一次拒绝吃两次人工往返）。四件中两件已修（§2），本 spec 覆盖剩余三块：

1. **opencode 双 WARN**——每张权限工单打两条「未找到工具等待窗口」WARN；
2. **路径/判据假阳性**——rm 黑名单不看 scope（含相对删除目标无判据）、heredoc 正文执行面未定义、只读命令旗标内容误判自指令、cd 越界存疑待证；
3. **拒绝双往返与同类重复升级**——被拒后 adapter 主动合成第二张 ask（实时与断线对账两个面）；同类命令没有任务内已批复用之外任何收口。

## 3. 工作包与方案

### WP1 第 1 项：opencode 双 WARN（结构性修复承诺 + 取证只裁范围与叙事）

**机制事实（已证，与成因无关）**：

- 请求侧 WARN：`permission.asked` 处理登记 `permTiming` 后调 `Segmenter.PauseWaiting`，0 命中即 WARN（`internal/executor/opencode/adapter.go:1619-1637`）；应答侧 WARN：`RespondPermission` 成功后 `Resume`，0 命中即 WARN（`adapter.go:751-763`）。登记先于判定，一次落空必成对。
- **H1（子会话）是结构性成立**：`acceptForeign`（`adapter.go:1432-1457`）对已认亲子会话只放行 `permission.asked`（:1436-1448），其余事件一律丢弃（:1450-1456）→ 子会话的工具 part 永远开不出段（段开启只发生在主会话 `mapPartUpdated`→`ToolStart` 与 `BeginTurn`，均被 acceptForeign 闸住）→ 任何子会话权限请求必然 `PauseWaiting`/`Resume` 双落空、等待不被任何段承载。这是代码结构证明，不依赖现场复现。
- **H2（主会话序 B/C）能产生同形 WARN**：独立评审 harness 实测「permission 先于非空 running」的序同样双 WARN、等待被吞进 api/tool 桶（卡事件 16677）；两份入库样本（`testdata/spike3-events.jsonl`、`spike5-events.jsonl`，均单会话、序 A、零 WARN）与常态负载未观测到该序。
- 夜班请求的 `is_child` 关联不可得（当晚 agentd 日志在远端执行机，本机 `~/.handoff/agentd.log` 0 命中）。

**修复承诺与取证的角色（v3 收紧）**：

- **H1 修复是本卡承诺**：结构性成因无需现场复现背书，验收主证据 = 子会话合成回放夹具（缝 2）红→绿——修前恰成对 WARN + 等待无承载，修后零 WARN + 等待归属正确；spike3/5 原样本回归零 WARN 不变。
- **H2 修复是超卡增量**（评审方向：首个 part 事件即开段、帧与 Detail 延后入参就绪），仅当取证证实时纳入，plan 可单独裁剪。
- **取证程序**：下一次真实派发零额外成本挂观测（或一次专用探针任务），留存 `permission.asked` 归属 INFO（`adapter.go:1610-1611` 已带 `is_child`）与成对 WARN 的 permID 关联、对应 SSE 样本（复用既有 probe/抓包机制）。结论只有两种记法：证得分布 → 记录并裁定 H2 纳入与否；**零复现 → 只记「观测窗口内未复现（未验证）」——不关闭 H1 修复面、不判故事通过**（验收由合成回放 + 语义门收口，与现场是否复现脱钩）。
- **不依赖取证的语义门（无条件生效）**：禁止成对 WARN；每条权限等待必须归属可辨——要么承载计时、要么单条 Info 声明「不承载」；等待不得静默吞进 api/tool 桶（看板不说谎）。

### WP2 第 3 项：权限门判据假阳性（判据扩容，分轮落地）

**现状读数（v3 复核）**：

- 重定向写落点已有提取器：`RedirectTargets`（`internal/permgate/redirect.go:48-104`）摘 `>`/`>>`/`>|`/`n>`/`&>` 落点交 `judgeBash` 落点循环（`permgate.go:225-249`）；其边界明写**不处理 heredoc、不跟 cd**（redirect.go:8），且自记 cd 相对写的误放行残余（redirect.go:15-17：`cd /etc && echo x > passwd` 按 Workdir 拼成范围内）。
- **相对路径解释基准错位**：`InScope` 把相对路径一律按 `scope.Workdir` 解释（`path.go:41-43`）——先 cd 再相对**写**（落点解释错位）与先 cd 再相对**删**（无任何判据，见下条）都悬空。
- **rm 无目标提取器**：`writeCommands`（`writeargs.go:44-53`）无 rm；rm 走 `builtinBlacklist`（`blacklist.go:38`）整串命中即拦（`judgeCommand`，`blacklist.go:133`，不看 scope）。原始场景 `cd "$TMPDIR" && rm -rf verify` 的 `verify` 是**相对删除目标**——v2 的 rm 规则只认临时目录路径、cd 规则只覆盖相对写，相对删除无判据可依（v2 缺口，本稿闭环）。
- **判定次序**：`judgeBash` 落点循环（`permgate.go:242-249`）先于 `judgeCommand` 的安全命令白名单（`safeCommandID`，`permgate.go:267`）——以 `Paths` 上报的越界读在白名单之前就被范围门拦下，白名单扩容救不了这类读。
- 自指令判据已是 3(c) 修后形态（`selfcmd.go` `judgeSegment`），旗标内容仍 fail-closed。

**判据扩容清单**（每条成对给出「放宽后仍拦」的反例，先红后绿；解析不了的形态一律维持升级，fail-closed）：

- **a. rm 目标提取器 + scope 感知**（评审裁定的最危险项，**单独一轮**；**独立造提取器**，不与 RedirectTargets/WriteArgTargets 强制合并——「删除目标」与「重定向写落点」语义不同源，共用提取器只会扩大耦合面）：绝对目标按解析后 Rel 判，只许落在 `Scope.TaskTmpDir` 与字面 `$TMPDIR`；**相对删除目标按 cd 解释基准（见 b②，写与删共用同一基准）判定**——原始场景 `cd "$TMPDIR" && rm -rf verify`：cd 目标落在 TaskTmpDir 基准内 → `verify` 按该基准解析 → 放行；基准不成立 → 升级。跨段逐条 rm 逐个目标全过；命令内变量不展开；包装器维持硬拦。反例集：`$TMPDIR/../../etc`、`rm -rf $TMPDIR/a; rm -rf /etc`、`TMPDIR=/etc rm -rf $TMPDIR/*`、`sh -c "rm -rf …"`、cd 出基准后的相对删除。
- **b. heredoc 正文与 cd 相对路径的语义定义（v3 收紧）**：
  - ① **heredoc 豁免只给受限形态**：定界符被引用（`<<'D'`/`<<"D"`）**且**消费正文者是不会执行正文的命令（cat/tee 白名单）——此时正文按数据从命令判据面剔除（重定向提取/黑名单/自指令都不扫正文）。**其余一律维持升级**：定界符未引用（正文中的命令替换会执行——用户本机实验 2026-09-28 确认，POSIX 语义：未引用定界符时正文先经外壳展开）、消费者会执行正文（bash/sh 等，引用定界符也不豁免——正文作为脚本被执行）、嵌套/解析不了。fail-closed。
  - ② **cd 解释基准（写与删共用）**：相对落点（重定向写、写命令参数位、rm 目标）的解释基准 = 本段内已 `cd` 且 **cd 目标本身落在允许基准内**（Workdir/TaskDir/TaskTmpDir）的目录；cd 目标不在基准内或解析不了 → 该段升级。
  - ③ 09-21 heredoc 升级事件（卡事件 17074）先复现取证、钉住确切触发判据，作为本条红测试来源。
- **c. 自指令匹配面修正（`-c/-e/-E` 旗标内容）**：psql/rg/grep 等工具旗标内容里的 handoff 不作「命令位置」候选（卡事件 16971 的 psql 误拦）。**只改自指令判定的匹配面，不构成任何放行**——黑名单、越界、写面判据照旧；反例（段首/包装器后的真 handoff）必须保持命中。
- **d. cd 越界（3(a)）真机取证先行**：worktree 任务的 `Workdir()` 就是工作树本身，裸 `cd` 本在白名单，触发入口是请求带 `Paths`（opencode `external_directory`）——本案可能不存在（评审裁定）。证真才修：只加**本任务**精确路径基准、过 `resolveExistingPrefix`、绝不放 `.worktrees` 父目录或通配。

**拆轮纪律**（评审裁定）：rm（清单 a）单独一轮，不与清单 b/c/d 混做。

### WP3 第 4 项：拒绝双往返 + 同类重复升级（方向已裁定，本节定收口语义）

**现状读数**：

- 一次拒绝 = 两次人工往返的机制链：deny → opencode 零文本终结回合 → `mapIdle` 识别 `turnRejected`（`adapter.go:2204-2219`）→ adapter **主动合成** question（`rejectedTurnQuestion`，`adapter.go:944-956`、发射点 `:2211-2213`）→ `Manager.handleQuestion` 建 `kind=ask` 工单（`manager.go:2888-2965`）→ 协调者再答一次。零文本→result 是 B21、被拒→question 是 2026-08-08 P0（`adapter.go:2205-2207`）——同一反挂死家族的两条目，后者不是 opencode 行为。
- **对账路径是双义面**：row4 判据 `ToolStatus == "error"`（`reconcile.go:168-169`）同时涵盖「权限被拒」与「普通工具报错」，`classifyReconciled` 对 row4 一律补发 question（`reconcile.go:223-233`）。**归因判据已实证存在**：真实抓包夹具 `testdata/session_rejectedend.json` 里被拒工具 part 的 error 文案是 opencode 固定哨兵 `"The user rejected permission to use this specific tool call."`——归因不依赖猜测。实现前提：`SessionMessage` 现只带最后工具 part 的 `state.status`（`api.go:446`），需扩带其 error 文案（adapter 内部模型扩展）。
- **VoidReason 现两档**（`internal/executor/executor.go:105-110`）：executor 消失 / 回合纪律违规——一次**有意的权限拒绝**两者都不是。另：opencode 现存零文本 result 未设 VoidReason（`adapter.go:2230-2234`），缺省记「executor 已终结」，与其 FailReason「executor 仍在线」自相矛盾（executor.go:99-104 记载的历史审计病）。
- 同任务内 allow 复用是 B57② 冻结语义（`manager.go:2552`、`internal/approval/authority.go` `FindReuse:244-261`：只复用 allow、只同任务内、查询失败 fail-closed）；指纹含快照版本（`fingerprint.go:41-43` + `manager.go:452`）→ 跨任务/跨版本必再升级。

**裁定 A（用户 2026-09-28）：b——被拒终止回合转失败结果**，收口语义如下：

1. **实时路径**：`mapIdle` 的被拒空回合分支改发 `result{OK:false, FailReason=被拒描述}`，落 waiting_review——拒绝本身就是协调者对「这批动作」的一次决策，第二张 ask 是在向已表达过决策的同一人重问；`handleResult` 对 `OK=false` 的既有处置（作废挂起工单 → turn_failed 事件 → waiting_review，`manager.go:3414-3530`）正是反挂死要的唤醒面，continue 随时可发。既有测试 `adapter_test.go:1612-1628` 随改写。
2. **VoidReason 扩档**：被拒终局的 result 必须带**新档作废理由**（语义：「权限被拒，executor 仍在线」）；枚举名归 plan。零文本 B21 路径顺带补 `VoidReasonTurnDiscipline`（消 `adapter.go:2230-2234` 的审计矛盾）。
3. **对账归因（v3：走可靠归因，不接受范围缩减）**：row4 且最后工具 part 的 error 文案命中权限拒绝哨兵 → 补 `result{OK:false}` + 同一新 VoidReason 档（与实时同形，**断线场景的双往返一并消除**）；哨兵不命中（版本改文案/普通工具报错/文案缺失）→ 维持 question 现状（fail-closed，绝不误标被拒）。哨兵是 opencode 原生英文文案、存在版本漂移风险——漂移的退化方向是安全侧（回到兜底 ask），不产生误判 result；漂移实际发生时在台账记「哨兵失配」并回归 contract 复核文案。

**裁定 B（用户 2026-09-28）：a——静态判据扩容承接，只收可证明安全的子集**：

- 跨任务指纹记忆表（原拍板 B 的 b 案）被本裁定否决 → §8 OOS → roadmap 落账。

## 5. 契约语义与接缝（L3）

**职责与权威**（三顶层子系统分立，本卡零转移；域归属按 `codegraph/best.json` 容器映射）：

- **`d_policy`——静态判据权威**：allow/deny/escalate 的命令/路径判据只能从 permgate 产出（`k_permgate_* → d_policy`）；adapter 与 orchestration 不得自设判据（现状不变式：**adapter 不 import permgate**，保留）。
- **`d_orchestration`——工单/状态权威 + 复用判定权威**：`handlePermission`/`handleQuestion`/`handleResult` 消费契约事件、作废挂起工单、迁移 waiting_review，不改写 adapter 已定的终局语义；人工批准复用判定（approval `Authority.FindReuse`，`k_approval_* → d_orchestration`）也在此域——v2 误记其归 policy，更正。
- **`d_execution`——事件语义权威**（`d_execution_adapters`/`d_execution_contract` 为其子域）：SSE 事实 → AdapterEvent（result/question）的翻译只在 adapter（实时 `mapIdle`、对账 `classifyReconciled`），两者的同形/异形状态必须显式声明；契约定义面（`Result.VoidReason` 枚举）在 contract 子域，本卡的枚举扩档是其内部改动，随 implement 落地。
- **依赖方向（现状不变式，本卡零新增跨层通路）**：orchestration（含 approval）→ execution_contract（消费事件）已有；orchestration → policy（判定入口）已有；execution_adapters → execution_contract（产出事件）已有，且**不**依赖 policy。

**事件/数据流（裁定 A=b 后）**：deny → adapter 实时终局（`turnRejected` 证据）→ `result{OK:false, VoidReason=权限被拒档}` → orchestration `handleResult`（作废挂起工单、turn_failed 事件、waiting_review）→ continue 可续。对账侧哨兵归因命中时同形转 result，未命中维持 question。等待计时：adapter `Segmenter` 是唯一计时权威，不产第二计时源。

## 6. 实现决定

- 收口层不变：权限判据全收 `internal/permgate`；回合终局语义收在 adapter（`mapIdle` 实时 + `classifyReconciled` 对账归因）；manager 只按既有 `handleResult`/`handleQuestion` 消费。
- schema：裁定 A=b + B=a 组合下**零 schema 改动**（VoidReason 是常量扩档；对账归因是 adapter 内部消息模型扩字段）。
