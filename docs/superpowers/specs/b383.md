## 1. 问题陈述

夜班实测（卡事件 16420）暴露两类成本：**噪声**（opencode 双 WARN 把 agentd.log 冲成噪声场，真实告警被淹；权限门判据假阳性把合法动作升级人工）与**往返**（同类命令反复升级、一次拒绝吃两次人工往返）。四件中两件已修（§2），本 spec 覆盖剩余三块：

1. **opencode 双 WARN**——每张权限工单打两条「未找到工具等待窗口」WARN；
2. **路径/判据假阳性**——rm 黑名单不看 scope、heredoc 正文与 cd 相对路径解释未定义、只读命令旗标内容误判自指令、cd 越界存疑待证；
3. **拒绝双往返与同类重复升级**——被拒后 adapter 主动合成第二张 ask；同类命令没有任务内已批复用之外任何收口。

## 3. 工作包与方案

### WP1 第 1 项：opencode 双 WARN（假说化取证 → 按证据定修复范围）

**机制事实（已证，与成因无关）**：

- 请求侧 WARN：`permission.asked` 处理登记 `permTiming` 后调 `Segmenter.PauseWaiting`，0 命中即 WARN（`internal/executor/opencode/adapter.go:1619-1637`）；应答侧 WARN：`RespondPermission` 成功后 `Resume`，0 命中即 WARN（`adapter.go:751-763`）。登记先于判定，一次落空必成对。
- 子会话路径**能够产生**成对 WARN（代码链路已证）：`acceptForeign`（`adapter.go:1432-1457`）对已认亲子会话只放行 `permission.asked`（:1436-1448），其余事件一律丢弃（:1450-1456）→ 子会话的工具 part 永远开不出段（段开启只发生在主会话 `mapPartUpdated`→`ToolStart` 与 `BeginTurn`，均被 acceptForeign 闸住）→ 子会话权限的 `PauseWaiting`/`Resume` 双落空，等待不被任何段承载。
- 主会话路径**也能够产生**成对 WARN：独立评审 harness 实测「permission 先于非空 running」的序（B/C）同样双 WARN、等待被吞进 api/tool 桶（卡事件 16677）；但两份入库样本（`testdata/spike3-events.jsonl`、`spike5-events.jsonl`，均单会话、序 A、零 WARN）与常态负载未观测到该序。
- 当晚 agentd 日志在远端执行机、本机 `~/.handoff/agentd.log` 0 命中 → 夜班请求的 `is_child` 关联**不可得**。

**成因假说（待验证，不预设立场）**：

- **H1 子会话假说**：夜班双 WARN 主要来自子 agent 的权限请求（H1 链路见上）。
- **H2 主会话序假说**：夜班双 WARN 来自主会话的事件序 B/C（重放/在飞交错的产物）。
- 两者可并存。修复范围由取证裁定，本 spec 不预判。

**取证程序（WP1 第一个动作，修复范围的裁定门）**：下一次真实派发时零额外成本挂观测（或一次专用探针任务），留存：① `permission.asked` 归属 INFO（`adapter.go:1610-1611` 已带 `is_child` 字段）；② 成对 WARN 的 permID 与归属行关联；③ 对应 SSE 原始样本（复用既有 probe/抓包机制，`testdata/probe-s*-opencode.jsonl` 的采集路径）。结论回写本节并裁定 implement 范围：

- H1 命中 → 修子会话等待归属；H2 命中 → 修主会话解耦（评审方向：首个 part 事件即开段、帧与 Detail 延后入参就绪；**超卡增量**，卡面只要求双 WARN 与等待归属，本条可由 plan 单独裁剪）；双命中 → 都修；取证期内零复现 → 保留语义门、关闭修复面并记台账。

**不依赖取证的语义决策（先行有效）**：禁止成对 WARN；每条权限等待必须归属可辨——要么承载计时、要么单条 Info 声明「不承载」；等待不得静默吞进 api/tool 桶（看板不说谎）。

**验收形状**：按取证裁定的形态各出合成回放夹具（缝 2）——修前成对 WARN + 等待无承载（红），修后零 WARN + 等待归属正确（绿）；spike3/5 原样本回归零 WARN 不变。

### WP2 第 3 项：权限门判据假阳性（判据扩容，分轮落地）

**现状读数（v2 修正）**：

- **重定向写落点已有提取器**：`RedirectTargets`（`internal/permgate/redirect.go:48-104`）从命令原文摘 `>`/`>>`/`>|`/`n>`/`&>` 落点，交 `judgeBash` 的落点循环（`permgate.go:225-249`）做范围判定——「cat > file 的落点没人提取」是 v1 的错误判断。
- **真实未定义面**（redirect.go 自记边界）：① **不处理 heredoc**（redirect.go:8）——heredoc 正文被当普通命令文本扫进 `RedirectTargets`/黑名单/自指令各判据面，正文里的 `>` 与内容会被误提取、误判定（09-21 heredoc 升级事件的确切触发判据未定，WP2.b 复现取证）；② **不跟 cd**（redirect.go:8、:15-17）——`InScope` 把相对路径一律按 `scope.Workdir` 解释（`path.go:41-43`），「先 cd 再相对写」既会误放行（`cd /etc && echo x > passwd` 摘到 `passwd` 按 Workdir 拼成范围内）也会误拦截（`cd $TMPDIR && cat > x` 落点解释错位）。
- **rm 无目标提取器**：`writeCommands`（`writeargs.go:44-53`）无 rm；rm 走 `builtinBlacklist`（`blacklist.go:38`）整串命中即拦（`judgeCommand`，`blacklist.go:133`，不看 scope）——任务临时目录内的清场 rm 一律升级。
- **判定次序**：`judgeBash` 落点循环（`permgate.go:242-249`）先于 `judgeCommand` 的安全命令白名单（`safeCommandID`，`permgate.go:267`）——以 `Paths` 上报的越界读在白名单之前就被范围门拦下，白名单扩容救不了这类读。
- 自指令判据已是 B383 3(c) 修后形态（`selfcmd.go` `judgeSegment`），旗标内容仍 fail-closed。

**判据扩容清单**（每条成对给出「放宽后仍拦」的反例，先红后绿；解析不了的形态一律维持升级，fail-closed）：

- **a. rm 目标提取器 + scope 感知**（评审裁定的最危险项，**单独一轮**）：**独立造 rm 目标提取器**，不与 RedirectTargets/WriteArgTargets 强制合并——rm 是黑名单命令，其「删除目标」语义与「重定向写落点」不同源，共用提取器只会扩大耦合面。语义：rm 目标按解析后 Rel 判，只许落在 `Scope.TaskTmpDir` 与字面 `$TMPDIR`；跨段逐条 rm 逐个目标全过；命令内变量不展开；包装器维持硬拦。反例集：`$TMPDIR/../../etc`、`rm -rf $TMPDIR/a; rm -rf /etc`、`TMPDIR=/etc rm -rf $TMPDIR/*`、`sh -c "rm -rf …"`。
- **b. heredoc 正文与 cd 相对路径的语义定义**：① heredoc 正文是**数据**——重定向提取、黑名单、自指令判定不得把定界符正文当命令面扫描（需 heredoc 感知的最小解析：识别 `<<[-]?['"]?定界符` 并截除正文段）；正文内部确实要执行的命令由后续独立命令段表达，本卡不做正文执行语义。② 相对落点的解释基准 = 本段内已 `cd` 且 **cd 目标本身落在允许基准内**（Workdir/TaskDir/TaskTmpDir）的目录；cd 目标不在基准内或解析不了 → 该段维持升级（fail-closed，不放宽到任意 cd 跟随）。③ 09-21 heredoc 升级事件（卡事件 17074）先复现取证、钉住确切触发判据，作为本条红测试来源。
- **c. 自指令匹配面修正（`-c/-e/-E` 旗标内容）**：psql/rg/grep 等工具旗标内容里的 handoff 不作「命令位置」候选（卡事件 16971 的 psql 误拦）。**只改自指令判定的匹配面，不构成任何放行**——黑名单、越界、写面判据照旧；反例（段首/包装器后的真 handoff）必须保持命中。
- **d. cd 越界（3(a)）真机取证先行**：worktree 任务的 `Workdir()` 就是工作树本身，裸 `cd` 本在白名单，触发入口是请求带 `Paths`（opencode `external_directory`）——本案可能不存在（评审裁定）。证真才修：只加**本任务**精确路径基准、过 `resolveExistingPrefix`、绝不放 `.worktrees` 父目录或通配。

**拆轮纪律**（评审裁定）：rm（清单 a）单独一轮，不与清单 b/c/d 混做。

### WP3 第 4 项：拒绝双往返 + 同类重复升级（方向已裁定，本节定收口语义）

**现状读数**：

- 一次拒绝 = 两次人工往返的机制链：deny → opencode 零文本终结回合 → `mapIdle` 识别 `turnRejected`（`adapter.go:2204-2219`）→ adapter **主动合成** question（`rejectedTurnQuestion`，`adapter.go:944-956`、发射点 `:2211-2213`）→ `Manager.handleQuestion` 建 `kind=ask` 工单（`manager.go:2888-2965`）→ 协调者再答一次。零文本→result 是 B21、被拒→question 是 2026-08-08 P0（`adapter.go:2205-2207`）——同一反挂死家族的两条目，后者不是 opencode 行为。
- **对账路径是双义面**：断线对账的 row4 判据 `ToolStatus == "error"`（`reconcile.go:168-169` 判据表）同时涵盖「权限被拒」与「普通工具报错」，`classifyReconciled` 对 row4 一律补发 question（`reconcile.go:223-233`，文案「工具被拒或工具报错」，不作被拒断言）——对账侧**没有**实时路径的 `turnRejected` 清单，重启后无从自证成因。
- **VoidReason 现两档**（`internal/executor/executor.go:105-110`）：`VoidReasonExecutorGone`（executor 没了）与 `VoidReasonTurnDiscipline`（回合纪律违规、executor 在线）——一次**有意的权限拒绝**两者都不是。另：opencode 现存零文本 result 未设 VoidReason（`adapter.go:2230-2234`），缺省记「executor 已终结」，与其 FailReason「executor 仍在线」自相矛盾（executor.go:99-104 记载的历史审计病）。
- 同任务内 allow 复用是 B57② 冻结语义（`manager.go:2552`、`internal/approval/authority.go` `FindReuse:244-261`：只复用 allow、只同任务内、查询失败 fail-closed 到照常问人）；指纹含快照版本（`internal/executor/fingerprint.go:41-43` + `manager.go:452`）→ 跨任务/跨版本必再升级。

**裁定 A（用户 2026-09-28）：b——被拒终止回合转失败结果**，收口语义如下：

1. **实时路径**：`mapIdle` 的被拒空回合分支改发 `result{OK:false, FailReason=被拒描述}`，落 waiting_review——拒绝本身就是协调者对「这批动作」的一次决策，第二张 ask 是在向已表达过决策的同一人重问；`handleResult` 对 `OK=false` 的既有处置（作废挂起工单 → turn_failed 事件 → waiting_review，`manager.go:3414-3530`）正是反挂死要的唤醒面，continue 随时可发。净效果：第二次交互从必答变可选。既有测试 `adapter_test.go:1612-1628` 随改写。
2. **VoidReason 扩档**：被拒终局的 result 必须带**新档作废理由**（语义：「权限被拒，executor 仍在线」——一次有意的拒绝不是 executor 消失也不是纪律违规）；枚举名归 contract 节点。零文本 B21 路径顺带补 `VoidReasonTurnDiscipline`（消 `adapter.go:2230-2234` 的审计矛盾）。
3. **对账收紧（不 blanket 改向）**：reconcile row4 **不得**全部标成被拒——仅当 error 载荷可归因权限拒绝时才补 result（同新 VoidReason 档）；归因判据（opencode 工具 part 的 error 载荷是否携带权限拒绝标识）由 contract 节点对真实载荷核实，**核实不出归因判据前，row4 维持 question 现状**（其文案本就不作被拒断言）。实时与对账允许暂时不同形，差异必须显式记台账与测试，不许静默。

**裁定 B（用户 2026-09-28）：a——静态判据扩容承接，只收可证明安全的子集**：

- 只读白名单只收**可静态证明只读**的类（如 rg/grep 的搜索词含 handoff 等），每类成对反例。
- **明确维持人工审批的清单**（裁定为终态，不是残余工作）：`git checkout -- <文件>`（写工作树、可覆盖未提交变更）；`psql -c`（任意 SQL，不可笼统认作只读）；内联 python；**Go 模块缓存读**——以 `Paths` 上报时在 `judgeBash` 落点循环（`permgate.go:242-249`）先于安全命令白名单（`permgate.go:267`）被范围门拦下，白名单扩容救不了，承接需 Scope 层「只读基准」语义，另立卡（§8 OOS → roadmap）。
- 跨任务指纹记忆表（原拍板 B 的 b 案）被本裁定否决 → §8 OOS → roadmap 落账。
- 第 4 项真机验证部分需真机 + 在场 + 烧额度，排 acceptance 轮。

## 5. 契约语义与接缝（L3）

**职责与权威**（三域分立，本卡零转移）：

- **判定权威在 `d_policy`**：allow/deny/escalate 结论只能从 permgate 判据 + approval 复用判定产出；adapter 与 orchestration 不得自设判据（现状不变式：**adapter 不 import permgate**，保留）。
- **回合终局语义权威在 `d_execution_adapters`**：SSE 事实 → AdapterEvent（result/question）的翻译只在 adapter（实时 `mapIdle`、对账 `classifyReconciled`）；两者的同形/异形状态必须显式声明。
- **工单与任务状态权威在 `d_orchestration`**：消费契约事件、作废挂起工单、迁移 waiting_review；不改写 adapter 已定的终局语义。
- **契约层 `d_execution_contract`**：`Result.VoidReason` 枚举扩一档（权限被拒）——本节点定语义（「作废理由必须如实描述终局成因」），枚举名与签名归 contract。

**依赖方向（现状不变式，本卡零新增跨层通路）**：orchestration → execution_contract（消费事件）已有；orchestration → policy（判定入口）已有；execution_adapters → execution_contract（产出事件）已有，且**不**依赖 policy。

**事件/数据流（裁定 A=b 后）**：deny → adapter 实时终局（`turnRejected` 证据）→ `result{OK:false, VoidReason=权限被拒档}` → orchestration `handleResult`（作废挂起工单、turn_failed 事件、waiting_review）→ continue 可续。对账侧 row4 归因判据核实前维持 question（§3 WP3.3）。等待计时：adapter `Segmenter` 是唯一计时权威，不产第二计时源。

## 6. 实现决定

- 收口层不变：权限判据全收 `internal/permgate`；回合终局语义收在 adapter（`mapIdle` 实时 + `classifyReconciled` 对账，异形显式声明）；manager 只按既有 `handleResult`/`handleQuestion` 消费。
- schema：裁定 A=b + B=a 组合下**零 schema 改动**（VoidReason 是契约枚举扩档，不是表结构变更）。
