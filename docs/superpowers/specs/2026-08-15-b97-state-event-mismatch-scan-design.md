# B97 设计：事件与状态失配的对账扫描

**日期**：2026-08-15
**基线**：`w4-delivery`（含 B100 及其补漏 `9f5fe441b`）

> **本 spec 由审核者在用户外出期间独立撰写。** §3.2 的「自动迁移而非只告警」与
> §3.3 的「只处理本次启动之后的事件」是两处**可推翻的判断**，各自写了理由与代价。

---

## 1. 前提：这个不变量到今天才成立

B97 的判据是「**有 `failed` 事件、任务却不在终态**」。这句话在 B100 之前**是假的**：
`handleResult` 当时也发 `failed`，而它迁的是 `waiting_review`——最常见的正常路径
会被判成失配，扫描一上线就天天误报。

B100 把 `failed` 收窄为「任务终结」、回合级失败改发 `turn_failed`；其补漏
（`9f5fe441b`）又修掉了对账路径同样的问题。到此 `failed` 只剩四个生产者，
**全部真终态**：

| 生产者 | 迁到 |
|---|---|
| `manager.go` `Stop` | `failed` |
| `watchdog.go` `transitFailedWithEvent`（进程失控强制回收） | `failed` |
| `reconcile.go` `reconcileExecutorGone` | ~~failed~~ → 已改发 `turn_failed`，收 `waiting_review` |
| `RecoverOnStartup` | 同上（走同一条） |

所以现在只剩两个真生产者，判据才干净。**这条依赖关系要写在实现的注释里**——
将来谁再往 `failed` 上挂一个非终态用法，这个扫描会当场开始误伤。

## 2. 失配从哪来：两处「先追加事件、后迁状态」

B92 根因报告 §2.2/§2.3 查实的两处，至今未改：

- `manager.go` `Stop`：`AppendEvent(failed)` → `transit(failed)`
- `reconcile.go` `reconcileExecutorGone`：`AppendEvent(...)` → `recoverTransit(...)`

第一步成、第二步失败，就留下「事件说终结了、状态还是 running」。任务卡在那儿，
直到 2 小时看门狗把它标成 stalled——**而 stalled 只唤醒不修复**。

## 3. 方案：根因 + 保险丝，两件都做

### 3.1 根因：把两处改成「先迁状态、后追加事件」

与 `handleResult` 和 `transitFailedWithEvent` 已有的顺序对齐（后者的注释写明了理由：
「事件一落库就可被 WS 重放读到，状态必须先就位，否则审核者在一个仍 running 的
任务上看到 failed 事件会困惑」）。

**代价要说清**：反过来之后，失败形态从「有事件没状态」变成「有状态没事件」——
任务正确地落到 `failed`，但没有一条说明原因的事件。两害相权取后者：**状态错**会让
协调者对着一个假的 running 干等并且 CLI 全线拒绝操作；**事件缺**只是少一句解释，
状态机是对的、后续操作都能做。

### 3.2 保险丝：看门狗加一条对账扫描（可推翻）

在 watchdog 现有的巡检里加一条 `scanStateMismatch`：

**判据**（三条**同时**满足才算失配）：

1. 任务状态**非终态**（`pending` / `running` / `waiting_answer` / `waiting_review`）；
2. 该任务的**最新一条**事件是 `failed`——不是「历史上出现过」。
   （`failed → running` 是合法迁移，重跑过的任务历史里带旧 `failed` 很正常）；
3. 那条事件的年龄 **≥ 30 秒**。这是**防抢**：§2 那两处正常执行时也会短暂处在
   「事件已落、状态未迁」的中间态，扫描冲进去会把人家正在做的事搅了。

**动作**：走 `Manager.transit(taskID, failed, "mismatch-scan")` 把状态补上。

- **必须复用 `transit`，不许裸调 `UpdateTaskState`**：终态迁移的挂起工单作废与
  审计留痕（B63 收口）挂在 `transit` 上，绕过它就只改了状态、留下一堆永远不会被
  回答的工单。
- **不补第二条 `failed` 事件**（会重复），改为追加一条 `progress` 审计：说明这是
  对账修的、原始事件的 seq 是多少。状态凭空变了却没有痕迹，比不修更难排查。
- **不清扫进程**：那是 `SweepTaskProcs` 的职责，且能走到这一步说明 executor 早已
  被判死，清扫在别的路径上已经做过。

**为什么自动迁移而不是只告警（可推翻）**：这个失配不是「可能有问题」的怀疑，
是一个**已经出过错的中间态**——事件已经代表决议落库了，状态行只是没写成功。
留着它没有任何信息价值：协调者对它做任何操作都会被状态机拒（`continue`/`done`
要 `waiting_review`），只能干等到 2 小时 stalled。告警的价值在于「让人来判断」，
而这里没有可判断的东西。

**若用户更倾向只告警**：改的是本节的动作，判据与护栏不变——把 `transit` 换成
发一条 `stalled` 同款的唤醒事件即可。

### 3.3 只处理「本次 agentd 启动之后」产生的 failed 事件（可推翻）

扫描跳过启动时刻之前的事件。

**为什么必须有这条**：B100 之前的历史数据里，**存在合法的「`failed` 事件 +
`waiting_review`」**——那时对账路径就是那么写的。升级后若不加这条护栏，扫描会把
这些**正等着协调者裁决**的任务直接判死。这是真实存在的数据形态，不是假想。

（08-15 实测：两台机器当前 `waiting_review` 任务数都是 0，所以眼下没有存量受害者；
但护栏不能建立在「碰巧现在没有」上。）

**代价**：agentd 重启前一刻产生的失配永远不会被这条扫描修。可以接受——
`RecoverOnStartup` 本来就会在启动时对全部非终态任务做一次探活对账，那条路覆盖了
重启场景。

## 4. 影响面

| 文件 | 改动 |
|---|---|
| `internal/agentd/manager.go` | `Stop` 改成先迁状态后追加事件 |
| `internal/agentd/reconcile.go` | `reconcileExecutorGone` 同上 |
| `internal/agentd/watchdog.go` | 新增 `scanStateMismatch` 并接进巡检 |
| `cmd/agentd.go` | 若扫描需要新的接线参数（如启动时刻） |

## 5. 风险

**自动改状态是本仓库里少数几件「机器替人做决定」的事**，与 B47 误杀、B93 强制回收
同级。三条护栏（最新事件 / 30 秒 / 本次启动后）少一条都会扩大误伤面，实现时不得
以「简化」为由省掉任何一条，每条都要有对应用例。

**判据依赖 `failed` 的语义纯度**（§1）。实现的注释必须写明：谁再让 `failed` 用于
非终态，这个扫描就会开始误伤。

## 6. 验收

1. `go build/vet/test ./...` 全绿。
2. **判据用例**（每条都要能被变异咬住）：
   - 最新事件是 `failed` + 状态 `running` + 事件够老 → **迁移到 `failed`**；
   - 同上但事件只有 10 秒 → **不动**（防抢）；
   - 历史上有 `failed` 但最新事件是 `progress` → **不动**；
   - 最新事件是 **`turn_failed`** + 状态 `waiting_review` → **不动**（这是健康态，
     本条是防误伤的正身）；
   - `failed` 事件产生于 agentd 启动之前 → **不动**；
   - 任务已是终态 → **不动**。
3. **迁移走的是 `transit`**：用例断言迁移后挂起工单已被作废（证明没绕过 B63 收口）。
4. **审计事件**：迁移后有一条 `progress`，文本含原始事件 seq。
5. **根因两处的顺序已反转**：各有一条用例断言「状态先就位」——例如让 `AppendEvent`
   失败，断言任务仍然落到了 `failed`（旧写法在这种情况下状态不会迁）。
6. 真机复验由审核者做（构造 executor 中途死亡，观察扫描是否不误伤正常的
   `turn_failed + waiting_review`）。

## 7. 明确不做

- 不改状态机、不加新状态。
- 不在扫描里清扫进程、不杀 executor。
- 不处理「续接回合正常完成但结果被吞」——B92 报告已指出扫描兜不住它（库里只有
  stalled，扫描无从知道回合其实跑过）。**本条是保险丝不是根治**，这句话要写进注释。
- 不顺手动 B101 / B105 / B107。
