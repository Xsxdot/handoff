# B460 熟练工工单治理：遇工单即交回、只读任务少找人、跨机推送不延迟

- 状态：**r1 已批准**（2026-10-21 用户批准，原话「批准」；同日主会话出稿；OOS 后续项已落 `docs/roadmap.md`「B460 残余」）
- 级别：**L3**。跨四个子系统：命令行（等待命令）、任务编排与审批（审批链上下文，含跨机审批的 wire 请求加字段）、权限门（放行规则）、agentd 事件转发（跨机推送）；外加 opencode 执行器适配。预计**不扇出**：每处增量小于流程固定成本，一张卡单轮交付；plan 复核。
- 执行形态：**甲 本地盯**（全局 CLAUDE.md §3 形态判决第 1、2 条）。理由：验收要驱动派发系统自身（派熟练工到 linux-01 看工单能否当场交回）；跨机推送延迟的根因未明，要先排查。
- 来源：B453 spec 期间熟练工 W2/W3 撞权限工单未叫醒主会话，用户发现（卡 B460 note seq 29349–29363）。用户裁定（2026-10-21）：①`--wait` 遇工单立即以专用退出码退出并打印工单；②只读任务自带权限范围；③审批链拿到任务上下文；④网页抓取不审批、直接放行；熔断不做、先观察；挂卡降为可选；放行尺度选 A（规则层能证明安全的放行，其余交审批链，审批链拿不准才找人）；排序先于 B453。
- 台账：`docs/superpowers/specs/b460-ledger.md`；现状读数：`docs/superpowers/specs/b460-facts-code.md`（熟练工 W1，基线 fad1aadf）

## 问题陈述

谁：主会话把机械活交给熟练工（`handoff dispatch --template … --wait`），任务跑在本机或别的机器。

现状（读数，执行节点复核；出处见 facts-code）：

1. **等待命令遇工单不退出。** `WaitFinal`（`internal/client/skilled.go:159`）遇 question/permission_request 只往 stderr 打一行提示并继续等（`cmd/skilled.go:241-244`）；退出码只有 0/3/4/124（`cmd/exit.go:20-28`）。主会话把 `--wait` 放后台跑，进程不退出就不会被叫醒，任务停在工单上无人知晓。
2. **跨机 `--follow` 推送延迟。** 任务在 linux-01，本机 `handoff wait <id> --follow` 收到远端工单晚约 2.5 分钟，像被转发层压到后续帧到达才冲出（台账「更正：不是断流」条，推测）；本机任务无此现象。根因未明。
3. **网页抓取直落人工。** opencode 的 webfetch 请求不带命令也不带路径，适配层产不出结构化请求，权限门按「adapter 未提供结构化权限载荷」直接升级给人（`opencode/adapter.go:1790-1826`、`approval/authority.go:166-172`）。agy 的网页抓取带结构，走审批链——两家不一致。
4. **任务自己的目录也被拦。** 产物目录在任务目录子树内，写文件工具写绝对路径时自动放行；但 bash 用相对路径或 cd 进产物目录、以及 opencode 的 external_directory 请求，落到「交审批链」而非放行（facts §3）。W1 对自己的产物目录 `ls; mkdir -p` 被升级人工两次。
5. **审批模型缺上下文。** 审批者只拿到权限原文与任务摘要（`approval/client.go:334-341`、`orchestration/approver.go:710-718`），不知道任务是只读形态、工作树与产物目录在哪，于是对只读调查常见的 Python 读文件、在临时目录处理数据一律升级（W2 16 张）。
6. 实测规模：W2 17 张、W3 4 张、W1 2 张人工工单，全部无风险。

## 方案

- **等待命令**：`dispatch --wait` 与 `wait --final` 在任务出现**需要人答的工单**（权限请求或提问，已被审批链自动处理的不算）时立即退出，退出码 **5**；stdout 打印工单全文（取工单存的全文，不取事件里截断到 200 字的正文）、答复命令与续等命令。进入等待时任务已有待答工单，同样立即以 5 退出。答完后用 `handoff wait <id> --final` 续等，行为与首次等待一致（再遇工单再以 5 退出）。
  - 弃选：stdout 只打提示、继续等（现状，不叫醒）；改用 `--follow` 由调用方自己过滤（每条事件一行、调用方要写过滤器，且受跨机延迟影响）。
- **跨机推送**：先排查延迟根因，再在根因处修；结果要求见 S5。不预设修法。
- **网页抓取放行**：网页抓取在权限门统一判为放行，并照常留一条自动放行审计事件（含 URL），对所有执行器、所有任务形态一致。opencode 适配层为 webfetch 产出结构化请求（工具名 + URL），与 agy 对齐。
  - 弃选：在各执行器原生配置里把 webfetch 设成 allow（不经权限门、无审计事件、五家各配一遍）。
  - 已知风险（用户接受）：网页抓取可经 URL 把数据带出；由下面「审批链拦凭据读取」兜底，规则层不另设域名白名单。
- **任务范围内的操作放行**：命令或请求涉及的路径全部落在任务范围内（工作树、任务目录含产物目录、任务临时目录），且属于规则层能证明的形态（只读命令、建目录、写入范围内），即放行。适用所有任务形态，不限只读。cd 进范围内目录后的相对路径按实际目录解释。
- **审批链拿到任务上下文（放行尺度 A）**：规则层判不了的请求照旧交审批链，但审批者额外拿到：任务形态（只读/分支）、工作树路径、产物目录、任务临时目录，以及对只读形态的裁决政策——为调查而读代码、读文档、在范围内跑脚本处理数据、往产物目录写报告，应允许；读凭据文件（如 `~/.codex/auth.json`、`~/.ssh/`、各 CLI 的 auth.json）、写到范围外、推送代码、带凭据向外发请求，应升级。审批者拿不准才升级给人。跨机审批（审批环在另一台机器）同样带上这些上下文。

## 落位三问

① **读写谁的权威数据**：工单与任务状态归任务编排（agentd），等待命令只读不写；放行规则归权限门；审批上下文由任务编排从任务记录取出交审批领域；推送转发归 agentd 事件流。无双写，不需要新编排单元（第五条）。
② **谁消费**：等待命令经 agentd 既有任务 API 读工单（另一进程 → 既有契约面 + client，第四条第 3 档，不新增端点为缺省，需新增由 plan 定）；审批上下文经跨机审批的既有 wire 请求加可选字段（契约面，第四条第 3 档）；权限门由编排在进程内以导出符号调用（第四条第 1 档）。
③ **同步还是异步**：等待命令对事件流是订阅观察（异步事件，命令自身同步退出）；审批是同步调用（调用方要等结果，第十二条第 1 问「是」）；跨机推送是既有异步事件流，本卡只修时延不改通道。

## 目标架构与接缝语义

- **等待命令（命令行，client 侧）**：「需人答的工单」判据以 agentd 任务快照里的待答工单列表为准，事件流只作唤醒；工单全文取工单记录。等待命令不自己判断工单是否已被审批链处理——进入待答列表的就是要人答的。
- **权限门（规则层）**：「任务范围」= 工作树 + 任务目录 + 任务临时目录，三者由编排在构造权限门输入时给出（现状已给前三者中的部分，plan 核）。网页抓取作为一种工具在权限门判放行，执行器适配层负责把它表达成结构化请求。规则层不引入任务形态维度：放行规则对所有形态一致；形态只进审批上下文。
- **审批领域**：审批提示新增上下文段与只读政策段；上下文由编排在发起审批时从任务记录取出传入，审批领域不反查任务。跨机审批 wire 请求加可选字段，向后兼容：缺字段按无上下文处理（现状行为）。
- **事件转发（agentd）**：本卡只修跨机推送的时延，不改事件通道与帧格式；修法待根因。
- 依赖方向不变：命令行 → agentd API；编排 → 权限门、审批；审批 → 跨机审批端点。无新增依赖方向。

## 实现决定

1. 退出码 5 名为「待答工单」，加入退出码表；`dispatch --wait` 与 `wait --final` 共用同一判据与输出格式。stdout 打印格式：工单 ID、类型（权限/提问）、全文、`handoff reply …` 命令、`handoff wait <id> --final` 续等命令；stderr 不再承载工单提示。
2. 退出码 5 是否需要 `--wait` 的开关（如保留旧行为）：不提供，旧行为对任何调用方都无价值（用户裁定①）。
3. 网页抓取放行对所有执行器生效；opencode 之外的执行器若其原生配置把网页抓取设为 ask，经权限门后同样放行，原生配置不改（plan 核各家是否都能走到权限门）。
4. 「任务范围内放行」只扩大可证明形态的覆盖面（相对路径按实际目录解释、external_directory 路径归属、建目录），不放行任意脚本；任意脚本按 A 交审批链。
5. 审批政策文案写进审批提示模板，措辞归 plan；凭据文件清单至少含本机已知各 CLI 的凭据位置（codex、opencode、grok、claude、ssh）。
6. 跨机推送：implement 排查节先找根因，根因与修法回写本 spec 修订号与台账。
7. handoff skill「熟练工」节同步改写（S9）；全局 CLAUDE.md「机械活交熟练工」条里的等待用法如需改，finish 时按文档对齐处理。

## 测试决定

- **真实入口**：S1–S3、S5 用隔离 agentd（不碰在役 agentd，见记忆「real-machine tests use isolated agentd」），mac-mini 与 linux-01 各起一个隔离实例，派一个会撞工单的只读任务（提示词让执行者执行一条规则层判不了的命令，审批环配成升级），量退出时延与推送时延。
- **S4**：opencode 真机抓公开文档页，核事件流。
- **S6**：权限门表驱动测试覆盖相对路径、cd、external_directory、建目录各形态的放行与反例（范围外路径、范围内但含黑名单命令）；外加 opencode 真机一次。
- **S7/S8**：机内断言审批提示含上下文与政策（真实消费者：编排发起审批的生产路径）；真审批环回放 W2 样本与凭据反例各一；跨机审批用隔离实例，另用旧二进制当审批机验向后兼容。
- **风险**：跨机推送根因可能在转发层也可能在客户端读循环，排查前不承诺改哪层；审批者为模型，S7 的裁决有随机性——回放各跑 3 次，样本 3 次全放行、反例 3 次全升级才算过。
