# B394 spec：唤醒回声自激——协调者的账务动作把它自己唤醒

**上游状态：已批准**（用户 2026-09-22 决定：把该现象建卡走流程）
**级别：L2 单子系统**（`internal/agentd` 唤醒判据面；不动 keystone 与路由）
**入口节点：debug**（先根因后修：这是"机制自激"，必须先证明环路在哪一段闭合）
**上游证据**：B394 卡上的账本原文（`needs_cleared` → 立刻 `needs_human` 成串；协调者自诊断 `17722`/`17728`）

## 1. 问题

协调者在回合内做账务动作（清 `needs_human`）→ 产生 `needs_cleared` 事件 → **该事件又唤醒它自己** → 它再做一次动作（或被 keystone 的重打叠加）→ 成串乒乓。**当前是协调者靠自觉打断**（原文："清→重打的乒乓无意义，不再清标"），机制侧没有护栏。

## 2. 范围

**做**：让协调者自身的账务动作不再触发唤醒（或唤醒源需通过 actor/来源比对）；给出能变红的回归测试。
**不做**：不改 `needs_human` 已被移出唤醒映射的现状（B389 已收口）；不动『无寻址不唤醒』与『知会类结构事件不进聊天流』；不动路由/承载记录；不把 keystone 的失败重打一并改掉（那是另一个归因，见下）。

## 3. 待查（先取证再改）

1. `internal/agentd/wakeconsumer.go` 的 `automationWakeEvent`：现白名单里有哪些事件？`EvNeedsCleared` 在哪一行、为何留？
2. 契约侧（**先读再决定改实现还是改文档**）：`docs/superpowers/specs/b358-contract.md` 规则 31 与 `b389-contract.md` 的判据收口条目，对 `needs_cleared` 有无规定。
3. 是否已有"自回声抑制"机制（唤醒记录里比对 actor/来源）？没有则评估加它的代价。
4. **分开归因**：`17717/17727` 的 `needs_human` 是**唤醒失败**的产物（keystone 重打），与回声叠加才成串——修回声不等于修失败重打。

## 4. 验收判据

1. **红色回路**：能在单测里复现"清标 → 产生新的唤醒轮"（今天预期红）；修复后同一回路转绿。
2. **变异复验**：把护栏去掉要重新变红。
3. **不误伤**：正常的唤醒源（`task_mirrored`、真人寻址消息等）仍能唤醒；「无寻址不唤醒」等既有反例不回归。
4. **真机**：在 B382 上重放"清标"动作，账本不再出现新的唤醒轮（或唤醒轮不因清标而起）。
