# Handoff 工作台蓝图：从派发 CLI 到自主推进的多智能体工作平台

> 状态：蓝图（方向性文档，不是单期 spec）。一期 spec 见
> [2026-08-18-workbench-phase1-design.md](2026-08-18-workbench-phase1-design.md)。
> 讨论定案 2026-08-18；同日经业务逻辑与领域拆分双审阅修订（v2），
> 修订要点：账本宿主定死 home agentd + 事件镜像、工作流聚合拆分、
> 「等人」升为骨架级正交标记、blocked 解除语义收紧、双状态机对账规则。

## 1. 愿景与问题

handoff 目前是「派发 CLI + 人肉审核回路」：backlog 是 git 里一份 100KB 的
markdown 总账，任务模型是单层的 dispatch→running→waiting_review→done，
协调者回路完全靠人（用户 + 交互主会话）驱动。

真实使用中暴露的核心问题：**人的注意力是系统里唯一没有被管理的资源。**

- 并行开 3–4 个会话时，任务状态散在各会话上下文里，唯一汇聚点是用户的脑子；
- plan 执行期长且信息量大，真正需要用户知道/重视的很少，重要内容常被淹没；
- 「做完了没看到」「忘了合并」「重复开会话把同一件事又做一遍」反复发生；
- backlog.md 多分支分叉，加行要先算 max，已到入库临界点。

目标终态：用户往系统里推一个需求或 bug，系统自主推进——写 spec、拆子任务、
派发、审阅、合并、验收——人只出现在三个位置：**审 spec、看整功能验收结论、
合 main**。中间全程可自动，也全程可人工插手。

## 2. 四层架构

所有功能落在四层上，层间有严格的依赖顺序，分期按层推进：

| 层 | 内容 | 对应分期 |
|----|------|---------|
| **L1 数据层** | 工作项图谱：backlog 条目、子任务、阻塞边、状态、工作流配置、事件流 | 一期 |
| **L2 协作层** | 评论、群聊、跨任务摘要共享、上下文文档实体化 | 二期 |
| **L3 自动化层** | 事件触发、routines、agentd 自主唤醒协调者会话 | 三期 |
| **L4 目标层** | 蓝图（goal）：一个目标挂一串工作项，规则引擎驱动自主推进 | 四期 |

**Keystone 原语**：agentd 能自主唤起「协调者角色」的会话。今天 agentd 只会唤起
executor；协调者只存在于用户面前的交互会话里。一期用「人开一个常驻主会话」作为
它的手动版（协作/无人值守两种坐姿），三期由 agentd 自己拉起，无人值守彻底闭环。

## 3. 核心概念

### 3.1 WorkItem（工作项）与账本宿主

新的一等实体，即现在的 B 号：标题、状态、priority（一期仅展示/排序，无消费
语义）、project 归属、spec/plan 引用、验收记录。spec/plan 仍是 git 里的文件，
条目只存引用。

**账本宿主（设计裁决，不可含糊）**：现状 store 是 per-机器的——task 行落在被
派发那台执行机（mac-02/win-b37）各自的 SQLite 里，协调者本机只有客户端 cursor。
「全局账本」因此必须钉死单一宿主：**账本只活在协调者本机 agentd（home）**
（桌面形态已定 agentd 托管 Web UI，本机常驻 agentd 是既定前提）。work_items/
workflows/派发模板等表只建在 home agentd 的 store；执行机 agentd 永不建这些表。
否则第一次跨机派发就会逼出「跨库分布式事务」或「每台机各长一份账本」——后者是
backlog.md 分叉的数据库版，且没有 git merge 可救。

**引用方向**：账本侧存 `(target, task_id)` 二元组弱引用指向 task；task 侧只加
一个 opaque 的 `work_item_id` 标签字段（像 Name 一样只存不解释，不设跨库外键，
不校验）。执行域除这个标签外**不认识**账本，保住 manager 单写者与「adapter 不碰
store」两条现有不变量。

**事件镜像（跨机聚合的唯一路径）**：home agentd 出面订阅各 target agentd 的事件
流（断线用既有 cursor 续拉语义补齐），把挂账 task 的事件**镜像进账本的
work_item_events**——一个事件源、一套 seq。多路 wait、看板、后期规则引擎都只读
这一条单流，不各自跨机拨号。镜像断链时看板卡片显式标「事件流滞后」，绝不静默。
裸 `handoff dispatch` 出来的无主 task 在看板呈现为「未挂账」泳道，消除重复开工
检测的盲区。

- **子任务 = 子工作项**（树形 parent 指针）。父 item 状态独立驱动（不由子树
  自动推导），看板显示子树 rollup，防止两套真相。
- **阻塞 = 工作项之间的有向边**。写入时环检测在单事务里读全图判定（含 parent
  树与 dep 边混合成环、祖先-后代间挂 dep），依赖 SQLite 单写者串行化。
- **task 不动**：它是「一次执行」。一个工作项挂 N 次执行（spec 会话、plan
  会话、实现派发、修复、审阅、验收各算一次），工作项完整历史第一次可被机器查询。

### 3.2 状态机：固定骨架 + 前后插入 + 两个正交标记

骨架状态钉死，用户不可改名不可删除：

```
待办 → 进行中 → 待审阅 → 已完成        （另有「终止」态收纳取消/废弃）
```

（骨架终态取名「已完成」而非 done，避免与 `handoff done` 任务归档命令撞名，
主会话 prompt 里两个 done 并存迟早派出歧义指令。）

用户只能在锚点之间**插入**自定义状态（如「待合并」插在 待审阅 与 已完成 之间）。
插入位置本身携带语义：系统逻辑（阻塞判定、自动化判「到没到审阅」）只挂在锚点上，
不认自定义名字。

**两个骨架级正交标记**（衍生/标志位，凌驾于任意状态之上，不是流水线列位）：

- **`blocked`**：由阻塞边推导。解除条件是**全部 blocker 达到「已完成」**——
  blocker 进「终止」不解锁下游（「blocker 不存在了」≠「blocker 被满足了」），
  而是给下游打「等人」标记（reason=前置被取消），由人裁决改依赖还是一并取消。
  已在「进行中」的 item 被挂新 blocker 边：允许挂，但 blocked 标记只对
  「待办」生效，看板对这种情况显示提示徽标。
- **`等人`（needs-human）**：所有自动化路径的失败出口，带 reason（审阅超轮、
  合并冲突、前置被取消、关联 task failed、裁决解析失败等）。它是系统语义，
  必须在骨架层，不能指望用户恰好配置了某个名字的自定义状态。看板单列/高亮呈现。

### 3.3 工作流与派发模板：两个聚合，不是一个

双审阅共同结论：状态机形状与派发配方变更节奏完全不同，塞一个聚合会让「改一句
纪律块措辞」波及所有存量 item，且审计链断裂。拆成两个聚合：

- **Workflow（状态机形状）**：状态集合（骨架 + 插入节点）+ 转移合法性。
  **不可变版本化**：edit 产生新版本，item 钉版本，旧 item 走显式迁移（防止删
  自定义状态后在途 item 悬空）。
- **DispatchTemplate（派发模板，带版本号）**：executor 类型、纪律块（引用+
  版本/hash）、prompt 模板、目标机、分支策略、**per-target 模型覆盖**（模型名
  按机器不同是实测教训：mac-02 codex 用 gpt-5.6-luna、win-b37 用
  deepseek-v4-pro，跨机复用第一个事件就是 400）。工作流的转移上引用模板 id。
  **每次派发把所用模板版本与纪律块 hash 快照进派发事件**——「B107 那次派发用的
  是哪版纪律块」必须答得上，这是本项目取证文化的延续。

**纪律块搬家**：CLAUDE.md §4 的 A 版/B 版纪律块迁入派发模板，成为带版本的产品
数据。纪律块按执行器类型绑定，顺手根治「A 版派给 codex」的实测坑。迁移完成后
CLAUDE.md §4 退役为指针（跨机器、跨 worktree 的多副本切换顺序写进一期迁移步骤）。

### 3.4 节点定义三方共用：共用配置，也共用执行体

「节点」（审阅节点、合并节点等：派谁、带什么 prompt、结论怎么处理）在三种触发
方式之间共用，只差触发者：

1. **主会话驱动**（一期主路径）；
2. **看板按钮**（一期人工插手通道）；
3. **事件自动触发**（三期）。

**执行体唯一化（领域审阅修订）**：只共用配置不够——裁决解析、回合计数、超限转
等人这些硬规则若留在 prose（skill 规约）里，主会话、看板后端、三期规则引擎会
三处各自对齐、迟早分叉。这几条必须**落码为唯一的节点执行器**（一期在 CLI/
内部包实现，三期规则引擎复用同一执行体），skill 规约只描述「何时调它」。

### 3.5 事件流与注意力

每个工作项有 append-only 事件流（timeline）：状态转移（带 actor：主会话/看板/
CLI/用户）、派发（含模板版本快照）、审阅结论、备注（「记一笔」）、镜像来的
task 事件。**timeline 是账，群聊是播**——二期的群聊只是订阅事件流做聚合广播的
平面。一期由 timeline + 看板承担「需要你」的显性化。

**工单必须上注意力平面**：无人值守时最需要人的信号是 permission_request/
question 工单，它们经事件镜像进入账本流，看板卡片与「等人」列必须呈现，否则
注意力平面在最关键的信号上失明。

**executor 不写账**：一期 executor 永不调用账本命令（与 B115 自指令收口零冲突），
记账由协调者代记；二期做群聊时再评估是否开受控口子。

### 3.6 双状态机对账（task 态 ≠ item 态，谁都不许说谎）

WorkItem 与 task 是**两个聚合根**，各有状态机，不合并。对齐规则一期就定死：

1. item 状态写入一律 CAS（沿用 `UpdateTaskState` 的读-校验-写回模式），事件带
   actor；**派发即认领**——「待办→进行中」的 CAS 转移就是 claim，第二个会话
   对同一 item 的 dispatch 干净失败并提示「已被 X 认领」。
2. 看板渲染时**实时 join 关联 task 状态**：item 账面与 task 实况矛盾（item=
   进行中 但 task=failed/stalled）时显式亮「状态冲突/需要人」徽标——不信账面。
   主会话挂了、task 被看门狗判 failed 而 item 停在「进行中」的场景，看板必须
   把真相亮出来，否则注意力平面复刻它要解决的痛点。
3. 主会话每次被唤醒先从账本 + 事件流重建现场再动作（「以 ledger + git log 为准，
   不信记忆」）；修复回合计数等推进状态一律从 work_item_events 推导，不存会话
   记忆。
4. item 上记轻量 **driver lease/心跳**：看板能回答「这个 item 现在有没有会话在
   驱动」，主会话死了用户一眼看见哪些子树在裸奔。

## 4. 推进模型（以标准例走一遍）

需求聊完 → 出一份大 spec → 拆 5 个子任务，依赖图 `1 → 2 → (3 ∥ 4) → 5`：

1. 建 5 个子工作项，挂阻塞边 2←1、3←2、4←2、5←3,4。任务 1 进「待办」，
   其余显示 blocked。
2. 主会话按工作流派发任务 1（CAS 认领），挂**多路 wait**——订阅的是账本单流
   （工作项子树的事件，含镜像来的 task 事件），不是 task 集合，因此 wait 挂起
   期间新派发的任务 2-5、审阅 task 天然进流，无动态成员问题。退出条件：子树
   全部 item 达骨架终态。
3. 任务 1 执行完成 → 镜像事件到账 → 主会话推 item 进「待审阅」→ 触发审阅节点：
   **默认由审阅执行者承担**（一次普通 dispatch，带审阅 prompt + diff 或分支
   worktree，返回结构化裁决 pass/fail + 发现项；裁决 schema、传递通道、解析
   失败转「等人」由一期 spec 定）。主会话留给整功能验收——那需要跨子任务全局
   上下文，才值得动用重原语。
4. 裁决 fail → 自动对任务 1 `continue`，带发现项原文，**回合数封顶（默认 3 轮，
   按 item × 节点计，从事件流推导）**，超限打「等人」标记并在看板亮出。这是防
   无人看管死循环的硬安全阀。
5. 裁决 pass → 合并节点。**LLM 裁决 pass 只是必要条件**：合并节点自带客观判据
   （测试、gofmt——「executor 的 ledger 会漏 gofmt」是实教训）。**合并分两层**：
   子任务分支自动合入**功能集成分支**（冲突则打「等人」，带冲突文件清单与双方
   commit 范围落 timeline；合并顺序按 done 时序钉死并落事件）；功能分支合入
   **main 永远人工**——既是既有硬纪律，也是「忘了合并」痛点的正解：自动化把
   子任务全收拢，最后看板只剩一张牌等用户。
6. 任务 1 已完成 → 主会话查阻塞图，任务 2 解除 blocked，自动派发。循环至 5 个
   全部完成。
7. 整功能验收（主会话/协调者角色）→ 父工作项进「待合并」→ 用户合 main → 已完成。
   验收后发现 bug 开**新 item 挂关联**，不 reopen（与 task 机对齐，账本历史
   不改写）。

全程主会话只在出问题时出声：协调、裁决、或转人工。用户看着 = 协作模式；
用户走开 = 无人值守模式。

## 5. 安全阀（不可妥协项）

- **修复回合封顶**：审阅 fail 的自动 continue 默认 3 轮，超限转「等人」。
- **两层合并**：集成分支可自动（带客观判据），main 永远人工。
- **审批硬纪律不变**：破坏性/不可逆/外部可见的 permission_request 一律升级人工；
  自动化推进到「门」为止，人不在场时能推进的都推进，但不是无人监督。
- **等人锚在骨架层**：任何自动化路径的失败出口都是「等人」标记 + 看板显性化，
  绝不静默吞掉或死循环；它是系统语义，不依赖用户配置。
- **看板不说谎**：账面与实况矛盾必须显式亮出（状态冲突徽标、事件流滞后标记、
  driver lease 缺失提示），宁报冲突不报假账。

## 6. 分期

### 一期：L1 + 看板 + 主会话驱动（spec 另出）

WorkItem/子任务/阻塞边入库（home agentd）；固定骨架 + 插入状态 + 两个正交标记；
Workflow 与 DispatchTemplate 双聚合（版本化）；事件镜像；Web 看板（状态分列、
多项目过滤、blocked/等人/状态冲突显性化、工单上卡片、一键派发/转移）；CLI 对等
能力；账本单流多路 wait；节点执行器落码（裁决解析/回合计数/超限转等人）；每
工作项极简备注流；最薄 markdown 只读导出器（逃生门）；存量迁移（沿用 B 号，
B 号→item id 映射落库，backlog.md 冻结与 skill 切换按序执行）。

明确不做：事件自动触发、群聊、富评论、上下文文档实体化、蓝图、自动合 main、
executor 写账。

### 二期：L2 协作层

群聊（订阅工作项事件流的聚合广播平面）、富评论（@、线程）、跨任务摘要共享、
上下文文档实体化（类 artifacts：调研记录、决策记录挂在工作项上）。

### 三期：L3 自动化层

agentd 规则引擎（状态事件 → 调用与一期同一个节点执行器，替人点按钮）；
**keystone：agentd 自主拉起协调者会话**（无人值守彻底闭环，不再依赖用户手动开
主会话）；routines（定时触发：每晨扫账、canary 巡检入 backlog）。

### 四期：L4 蓝图（goal）

蓝图 = 一个目标挂一串工作项 + 一套推进规则。用户设目标与规则，系统在无人介入时
自主推进：前置解除 → 自动开协调会话写 spec/plan → 派发 → 审阅 → 集成 → 验收，
推进到人工门为止。人审 spec、看整功能验收、合 main，其余机器推。

## 7. 与现有纪律/资产的关系

- CLAUDE.md §4 派发决策表与纪律块：迁入派发模板后退役为指针（多副本切换顺序
  见一期迁移步骤）。
- product-backlog skill：一期迁移完成后由 CLI/看板取代，改写为「操作 handoff
  账本」的薄指引。
- handoff skill（审核者回路）：主会话驱动模型是它的结构化升级，随一期改写；
  「Monitor 挂 wait --follow」升级为账本单流多路 wait，progress 不唤醒的过滤
  规则在聚合层保持。
- 派发硬纪律（探活、git push、干净工作区）：进入派发模板的前置检查，产品化。
- B115 自指令白名单：一期 executor 不写账，新 CLI 命令不进 executor 白名单。
