- 执行形态：**甲 本地盯**（L1）

## 偏离与自主决定

1. readonly 的形态说明行**逐字保留**（含「readonly = 」前缀），只改 branch 的说明——最小改动，readonly 任务的提示词与本卡之前逐字节一致。自行拍板；在任务授权「readonly 才写只读解释」范围内。
2. 未知形态（proto 只有 branch/readonly 两值）不加括注，不替审批者猜语义。自行拍板。
3. 未增删 `readonlyApproverPolicy` 的任何「应批准 / 必须升级」条目，未动 `approverPromptTemplate`（B451 逐字批准行）。B460 plan §6 决策权限：「§9 政策文案的语义改动……增删条目要回 spec 批准」——本卡只改上下文段的形态说明行（§9 第一个代码块），属措辞层面，未触及政策条目，故不回 spec。B460 plan §9 草案原文同步改为分形态写法。
4. branch 括注写明「git commit 到本地任务分支；push 等改变远端仓库的操作不在此列」——审查第 1 轮 Important：原拟「提交到任务分支」易被读成推送远端，而基线模板未点名 push、静态规则只拦 force push。这是对形态的范围说明（收窄），不是新增「应批准 / 必须升级」条目，仍在措辞授权内。

## 现象

共享审批链（单环 linux-01 / opencode / deepseek-v4.1-flash，2026-10-22 由 agy 换入）对 implement 节点的分支任务大量升级，理由几乎都是「任务形态为 readonly 只读调查，禁止改仓库」。实测 xianyu-bridge X2.10：implement 任务 15e9af86 放行 18 / 升级 11，8db4c1ae 放行 2 / 升级 10；被拦的全是工作树内改源码、改测试、改文档、`git add && git commit`。只读 finish-check 任务几乎不受影响。

## 根因

`internal/orchestration/approver_context.go` `approverContextSection` 的形态行无条件写：

```
- 任务形态：<mode>（readonly = 只读调查：不改仓库、不提交，结论写成报告交回）
```

分支任务的提示词里也带着只读解释；括注里唯一的语义词是「只读调查」，flash 模型把它当成本任务的形态说明。B460 plan §9 的草案即如此（「<readonly 或 branch>（readonly = …）」），R6 回放时审批模型是 agy，未暴露。

## 修复

形态行只解释本任务实际形态（`modeExplanation`）：

- branch（含 Mode 为空的旧任务，已有逻辑归一为 branch）：`- 任务形态：branch（分支任务：可在任务工作树内改代码、git commit 到本地任务分支；push 等改变远端仓库的操作不在此列）`
- readonly：原文不变。

## 验收

- 红：`TestB465BranchContextHasNoReadonlyExplanation` 断言红（branch 提示词含「只读调查」）；`TestB465ReadonlyContextKeepsReadonlyExplanation` 修前即绿（守 readonly 不回归）。经真实组装函数 `approverPrompt`。
- 绿：两条 B465 测试 + `internal/orchestration` 全包绿；零值上下文金样本（B460 V6）不变。
- 生效条件（审查补充：用本地配置链、未接共享链的机器在本机组装，也须各自换版）：提示词由跑环的那台 agentd 组装（`RunLocalRing` → `approverPrompt`），当前环在 linux-01，**须 linux-01 换版才生效**；发起方机器换不换版不影响。
