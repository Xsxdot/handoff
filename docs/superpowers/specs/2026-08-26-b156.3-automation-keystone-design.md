## 1. 问题陈述

一期把账记住了，二期把「协调者→人」的升级通道修好了（B156.2）。但整条流水线
仍有一只人手拔不掉：**每个派发节点点火之前，要有人看一眼上一节点的产出，再按
一次按钮**。现状读数（2026-08-25/26 读本轮工作树，contract 复核）：

- 节点跑完只移列、不点下一节点（`internal/ledgerstep/node.go` 的 routeTo 之后
  返回即止）——「逐节点点火」是协调者的法定检查点，不是没做完的自动化；
- 协调者只存在于人开的会话里，agentd 只会拉执行者（蓝图 keystone 缺口原文）；
- 在飞环节不可恢复（`internal/agentd/cardstep.go` 包注释明写「在飞集合是进程内
  状态，agentd 重启即清空」，并注明是刻意取舍——其前提「人从 timeline 看得出来」
  在无人值守下不再成立）；
- 事件不唤醒任何人：裁决落了、任务到终态了、房间里留了言，都要等下一次有人路过。

三期目标（用户裁决，台账①）：**agentd 能拉起并唤醒「协调者」会话——替手，同时
替眼**。自动点火若不配一双看产出的眼睛，等于把检查点静默 nop 掉——空转报 pass
（只改台账零行业务代码）、plan 轮越轨（直接把实现干完）、工具缺失的空壳 pass，
三种形态全是靠「点火前有人看了产出」拦下的实测事故。所以三期的自动化不是
「规则引擎直接调环节执行体」，而是**机器协调者带着纪律推卡**。

## 2. 方案总览

五大件：

1. **小队（Squad）与载体（Carrier）**：并发控制的编制，分执行者小队与协调者
   小队；工作流节点从绑执行者改为绑小队（§3）。
2. **协调者载体**：复用执行域的进程承载、不复用派发状态机；隔离 HOME 把两个
   物种在环境层钉死（§4）。
3. **拉起两入口 + 事件唤醒**：开卡即绑、卡上一键拉起；绑定后事件敲醒（§5）。
4. **人工门契约**：自动推进到门为止，门的清单本期写死为系统语义（§6）。
5. **新增子系统按标准架构立**：两个新顶层子系统、双向 api/client 门面、不直调、
   用到谁就给谁建薄门面——用户批准后追加的硬约束，是本期的架构地基而非附带项
   （§7.0）。

### 弃选记录（含理由，均为对话实测裁决，台账①–⑥）

- **规则引擎按状态事件直接调环节执行体**（蓝图三期三件套之一）——替手不替眼：
  检查点的价值在有人看产出，规则直接点火=把检查点静默 nop 掉且失效时不报错。
  规则引擎收窄为「什么事件唤醒哪个协调者」，点火由协调者做。
- **先派执行者评估「适不适合现在做」**——评估要读账本（依赖、优先级、基线），
  而执行者永远够不到账本（凭据物理隔离铁律）；够得到账的评估者按定义就是协调者。
  收编为协调者醒来的第一个回合（§5），不烧执行派发。
- **全量自动拉起**（每张不阻塞卡自动排队拉协调者）——推四期。理由：开卡动作
  本身就产生绑定（B156.2「行动产生绑定」的延伸），不存在「spec 后补拉」的空档；
  而对几十张待办卡全量拉起会把 spec 聊天变成推送轰炸，与「注意力前置在 spec」
  的模型相反。B156.4 的内核由此明确：全量自动拉起 + goal 驱动。
- **全局规则实体**——1:1:1（卡:房间:协调者）下事件路由已唯一，匹配引擎解的是
  一个不存在的路由问题；「按范围配策略」用小队与项目默认即可表达。
- **routines**（每晨扫账/canary 定时触发，蓝图三期三件套之一）——需要「无卡
  协调者」新物种，与二期砍「叙事员轮」同判（多养一个会话物种）；四期做全量
  自动拉起时它自然有家（扫账的产出就是拉起决策）。
- **第二套 TUI**——与 B156.2「聊天面跑 agent 会话=永不做」同判；深聊走原生
  CLI 自己的 TUI，handoff 只负责把用户送到门口（§4 attach）。

## 3. 小队

**实体**：名字 + 角色（执行者队 / 协调者队）+ 成员集 + 并发数。入库版本化
（与 workflow 定义同款待遇）。**一个小队不混编**——两种成员的绑定语义不同：
执行者小队绑工作流节点，协调者小队绑拉起通道。

**载体（Carrier）实体 = 机器 × CLI × HOME 档案 × 模型 × 凭据来源 × 并发上限**，一等实体、
独立于小队存在；**小队成员 = 载体引用**（台账⑧）。归并的理由四条：HOME 天生是
CLI 专属的（认证态、配置、skill 都按 CLI 分家，拆开引用无意义）；模型名按机器
不同（跨机复用第一个事件就 400），载体绑机器后模型自然挂载体；**限额是账户的
属性，账户 = 凭据 = HOME**——健康位（CLI 限额探测本期只预留形状、探测落
roadmap：没限额的载体不领活）挂在载体上才有唯一归属；多账户 = 同机同 CLI 的
两个载体，一等表达。同一载体可入多个小队（并发计数按小队记，限额健康按载体记）。
**凭据来源两值**：独立（自己的账号）或主 HOME 同步（把主环境的认证态搬进隔离
HOME）。

**两级并发，载体凌驾于小队**（台账⑨）：载体自身有并发上限（跨小队全局计数，
物理位——账户真实承载力），小队并发是政策位（按队计数）；**准入判据 = 小队
有位 且 载体有位**。**抢并发时协调者优先**：控制面优先于数据面——协调者回合
短而稀疏、是消费执行产出的那一环，被数据面饿死会令整条流水线停摆（任务终态
没人看、下一节点没人点，执行机还在满负荷空转）；优先只在准入时生效（下一个
空位先给等着的协调者），**不抢占在跑任务**。已知缝：主 HOME 同步的两个载体
共享同一真实账户的额度，载体级上限管不到跨载体的账户池——本期以保守配额规避，
账户实体化并入「限额探测」roadmap 条目。

**「领任务」是语义，实现是协调机侧调度**：队列与并发计数在账本（协调机侧），
有空位时协调机把任务推过去；执行机全哑，压根不知道小队这个词。两条铁律因此
一条不动：账本凭据物理隔离在协调机；执行域离线优先（不新增在线轮询依赖）。

**节点绑小队**：工作流的派发节点从「绑 target/executor」改为「绑小队名」；
`--target/--executor/--model` 一次性覆盖语义保留，降级为「指定载体/载体字段」
的覆盖。存量直绑 target 的工作流如何兼容归 contract——预期形态是小队作为解析
层，直绑降级为「单载体匿名小队」，不逼存量迁移。

**排队**：并发满时点火请求入队（账本内持久，agentd 重启不丢），看板出现
「排队中」形态；出队时先唤醒绑定协调者确认基线仍新鲜再真派（§5）。队列顺序：
就绪度优先，其次卡优先级——与领活推荐同一权衡，机械化落码归 contract。

**协调者小队**：管协调者会话的并发（并发满时新拉起请求排队）。成员载体必须
落在协调机上（账本凭据在哪，协调者只能在哪），HOME 档案 = 全套（§4.3）。
**初始成员用 opencode 载体**（成本低，用户裁决台账④）；跑起来要换载体，
在小队里换成员引用即可，不动别处。

## 4. 协调者载体

### 4.1 复用与不复用

- **派发状态机不复用**（task 生命周期 / waiting_review / verdict 解析）——
  协调者没有「待审阅」，它就是审的那一方；协调会话不进执行派发状态机
  （B156.2 台账⑨已定，此处沿用）。
- **进程承载/适配层复用**（无头拉起一个 CLI、喂 prompt、收事件流）——纯技术
  能力，与角色无关，单独写一套是用代码重复执法物种边界，弃。

### 4.2 物种包装三点（每点与执行者相反）

1. **身份**：执行者禁用 handoff CLI（自指令收口）、够不到账本；协调者**必须**
   能跑 handoff CLI、必须有账本凭据——它干活的方式就是节点点火、写房间消息、
   落 note、批工单。
2. **生命周期**：执行者一个 task 跑到终态即完；协调者**事件唤醒 → 一个回合 →
   休眠**，跨天长活，靠 resume 续同一会话。
3. **纪律**：喂协调者纪律（charter 节点地图、卡驾驶手册、派发盯法、B156.2
   偏差两级制与简报六段、点火前看产出的检查点义务），不是执行纪律块。装载
   机制归 contract；spec 只定一条：**agentd 拉起的协调者与人开的会话必须吃到
   同一套纪律**。

### 4.3 隔离 HOME（物种边界的环境执法）

协调者和执行者可能是**同一个 CLI 二进制**，分野钉在 HOME 上（台账⑦）：

- **协调者 HOME = 全套**：全局规则文件（如 `~/.claude/CLAUDE.md` 一类）、自装
  skill、MCP、账本凭据——它是带着方法论上岗的。
- **执行者 HOME = 干净会话**：无规则、无 skill；它需要的一切由派发注入，纪律块
  是唯一输入——**干净度就是可复现性**（同一纪律块在任何载体上行为一致，不被
  机器上残留的用户配置污染）。
- **凭据来源是载体实体的属性**（§3：独立 / 主 HOME 同步）；供给动作的
  自动化程度归 plan。

### 4.4 resume / attach——不做第二套 TUI

会话对外两个通道：

- **resume**：agentd 无头续会话，唤醒的常规路径；
- **attach**：一键在**对应机器 → 对应目录**的终端 tab 打开原生 CLI 的同一会话
  （深聊通道）。房间管异步叙事，attach 管同步深聊，分工不混。

**attach 与自动唤醒互斥**：人工接管中 agentd 不得无头唤它——同一会话不许两个
驾驶员；机制归 contract（预期落在绑定心跳上加「人工接管中」态）。attach 里聊的
**凡承重必须落账**（B156.2 义务条款原样适用——终端里说的不落账等于没发生）。

**模型**：协调者模型独立配置（载体属性），与执行者不绑定。opencode 从便宜档
起步；换档判据是唤醒质量（重建频率、简报质量、误判率），不预设。

### 4.5 载体前提（环境事实，implement 前必须清账）

- 协调机本机 claude CLI 长期未登录（用户只用桌面端）——keystone 的前提是协调机
  上有一个**已登录、能无头拉起**的 CLI；
- **opencode 的 resume 可靠性与「无头 ↔ TUI 接管 ↔ 交回无头」往返能力现状未验**，
  contract 前钉死。若 resume 不可靠，唤醒退化为每次重建四步——能活但贵，这就是
  换载体的判据线。

## 5. 拉起与唤醒

### 5.1 拉起两入口（本期全部，均为用户显式动作）

1. **开卡即绑**：CLI 开卡动作发生时，agentd 拉起协调者并绑定——用户开完卡后
   只待在桌面端房间里聊即可，不必开本地工作会话（命令形态归 contract）。
2. **卡上一键拉起**：看板/桌面端从卡拉起协调者并绑定。

人开会话领卡（行动产生绑定）恒为合法第三通道——B156.2 已定，不重定。
**兼任/分派定性继续悬置**：本期每次拉起都是用户的语境内判断，定性问题没有
出现的场合；四期自动拉起真来了再定。

### 5.2 开场评估回合

协调者醒来第一件事：读卡、查依赖、看基线新鲜度。判「现在不适合推」就在房间
说一句原因并休眠——这就是被铁律拦下的「先派执行者评估」的正确形态。

### 5.3 唤醒事件清单

绑定协调者休眠中，以下事件敲醒它：

| 事件 | 语义 |
|---|---|
| 房间用户留言 / @ | 兑现 B156.2 明写推给三期的「消息事件主动唤醒休眠会话」；裁决答复也在房间发生，被本行覆盖（台账⑥），不设独立唤醒边 |
| 挂账 task 到回合终态（waiting_review / needs_human / turn_failed / failed） | 它派的活干完了或卡住了——「点火前看一眼产出」检查点的自动化落点：醒来先看文件清单再看裁决块，纪律义务随协调者纪律走 |
| 工单（permission_request / question） | 无破坏性的协调者直接批（取证依据：三天 1377 次判定，人批 238 拒 6 且 6 次全与安全无关——人肉批准链已是橡皮图章）；破坏性/不可逆照旧升级用户，硬纪律不变 |
| 排队出队 | 排队的点火请求轮到时，协调者醒来确认基线仍新鲜再真派 |

**不唤醒**：progress / 心跳类事件（蓝图过滤规则保持）。
**合并**：同卡积压的多个事件合成一次唤醒回合；醒来先读账对齐现场（以 ledger
为准，不信记忆），天然幂等。

### 5.4 唤醒失败兜底

resume 失败 → 自动拉新载体**承接同一协调者身份**（重建四步：读卡 → 会话史 →
timeline → 仓内文档），房间落「载体已更换」指针；重建再失败 → 转等人 + 看板亮。
B156.2 的重建纪律与换绑 CAS 剥权原样适用。修复回合封顶（MaxRounds=3，从事件流
推导）不变——超限转等人本来就是唤醒事件之一（task 到 needs_human）。

## 6. 人工门

自动推进到门为止。门本期写死为系统语义，不是配置项：

| 门 | 协调者做到哪 | 停在哪 |
|---|---|---|
| spec 批准 | 房间里聊需求、写 spec 稿 | **批准永远是用户**；批准前禁实现（charter 硬门原样） |
| 验收结论 | acceptance 的机械半段：复跑、变异、真机命令在协调机上跑、证据落账、收口摘要发房间 | **「结论确认」是用户**——证据摆好，用户点头卡才过 |
| 合 main | finish 准备：分支干净、CI 绿、图对账过 | **合 main 永远人工**，一次都不自动 |
| 推翻级简报 | 发六段简报（B156.2 契约） | 停卡等答复 |
| 破坏性工单 | —— | 升级用户（硬纪律） |
| 待裁决未回复 | **软门**：可提前问，继续做不依赖答案的部分 | 只有待裁决**真的阻塞下游**时才停——停不停是协调者自己的判断（台账⑦） |

acceptance 行是对现状的真变化（今天是纯人工列）：机械动作本来就在协调机上执行，
用户的注意力留给「结论对不对」，不留给「命令跑没跑」。

## 7. 契约语义与接缝（L3：定语义，不定签名）

### 7.0 架构决定：新增子系统按标准架构立，双向门面，不直调

用户 2026-08-26 追加的硬约束（spec 批准后的显式修订，与 B156.2 §8.0 同源同判）：
**本期新增的都是全新子系统，按标准架构立，不再欠债**——理由是用户原话「之前
欠的债太多了」。

**立户口**：本期新增**两个顶层子系统**（`codegraph/best.json` 的 `domains` 加两个
顶层领域，`containers` 逐个指名归属；子系统 = 顶层领域）。现状读数：best.json
今天有 **12 个顶层领域**（d_orchestration / d_gateway / d_workspace / d_execution /
d_sessions / d_transport / d_protocol / d_ledger / d_cli / d_web / d_policy /
d_maintenance）与 232 个 containers；本期是第 13、14 个（B156.2 的会话子系统若先
落地则顺延）。**最终户口划分与命名由 contract 节点按架构法第一条与派卡四条复核
裁决**，spec 只定语义边界：

1. **编制域**（载体 / 小队 / 准入与点火队列）：资格三条——契约面对外（准入判定
   与队列语义）、可独立开发测试交付、消费者有环节执行体 / 控制面 / CLI / 控制台。
2. **Keystone 域**（协调者拉起 / 唤醒决策 / resume / attach 定位）：资格三条——
   契约面对外（拉起、唤醒、接管互斥、attach 定位）、独立生命周期、消费者有控制面 /
   CLI / 控制台 / card_events 消费循环。

**两域为何不合一**：数据所有者不同（编制域拥有载体与小队的数据与规则，keystone
域不拥有任何持久数据、只做编排决策），且消费者集合不同；合并会造出一个既管配置
数据又管事件编排的 god object（架构法第五、六条）。合不合最终以 contract 的
复核为准，判错的纠偏是合并两个域，不是推翻本节。

**双向门面（架构法第四条第 3 档，两个新子系统的法定用档）**：

- **入站 `api`**：外界调本子系统**只经此门面**，不得 import 其内部（第十条穿透
  禁令，Go 由 `internal/` 可见性执法）。契约面唯一，一个能力只声明一次，消费方
  不得二次抽象。
- **出站 `client`**：本子系统需要外部能力时**不直调对方内部**。按第九条「接口归
  使用方」，所需能力的接口**定义在本子系统这一侧**的 client 包；具体实现由
  **组装点**绑定注入（`target.json` 已登记 main.go / `internal/agentd/server.go` /
  `internal/agentd/codegraph.go` 三个组装点），组装点之外不得 new 他方具体类型
  （第八条）。

**被依赖子系统的还债路径**（绞杀式，升格随卡走）：**本期用到哪个子系统，就给那个
子系统建它自己的薄 api 门面包**（包住既有实现、不改其内部），本期新子系统经自己的
client 接口绑到该门面上；**以后找机会再把那些实现迁进标准结构**——本期不做专项
重构，只在碰到的缝上还债。本期预期要建/复用的门面：

| 被依赖子系统 | 用途 | 门面处置 |
|---|---|---|
| `d_ledger` 卡片账本 | 卡与事件流、Decision、驱动绑定、载体/小队持久 | **复用 B156.2 建的账本 api 门面**；B156.2 未落地时本期建同一个门面包，**不建第二个** |
| 会话子系统（B156.2 新建） | 房间消息（唤醒源与叙事落点）、简报 | 复用其 api，不另抽象 |
| `d_execution_host` 进程承载 | 无头拉起 / 续接一个 CLI 进程（§4.1 复用的正是这一半） | **新建薄 api 门面**，只暴露承载能力，不暴露派发状态机 |
| `d_sessions` 终端会话（PTY） | attach 的终端 tab 承载 | **新建薄 api 门面** |
| `d_gateway` 控制门面 | 本期是**被调方向**（控制台 → 控制面 → 新子系统 api） | 入站方向，无需出站门面 |

**存量直调不扩大**：既有直调债（`d_gateway → d_ledger`、`d_cli → d_ledger`）
本期不清理，但**不新增任何一条穿过它的直调**——本期新增的账本能力调用一律经账本
api 门面。`graph check` 是硬闸：新增跨子系统边必须先在 `target.json` 声明契约面，
穿透他方内部即违法。

**命名警示（三个「会话」不同物，contract 命名须显式区分）**：`d_sessions` 是终端
PTY 域；B156.2 的会话子系统是协作房间域；本期 keystone 域管的是**协调者会话的
拉起与唤醒**——三者同名不同物，勿并入、勿复用彼此的领域 id。

### 7.1 契约语义

- **载体与小队的数据归编制域**（架构法第五条：规则归数据所有者）：载体（机 ×
  CLI × HOME 档案 × 模型 × 凭据来源 × 并发上限 × 健康位）、小队（名字 + 角色 +
  载体引用集 + 并发数）、两级并发计数、点火队列——**持久化经账本 api 门面落库**
  （账本是持久化设施，编制域是规则所有者，二者不混）；版本化与 CAS 语义与既有
  实体同款。
- **拉起/唤醒归 keystone 域**：消费 card_events 单流（蓝图扩展点④——规则引擎
  「只消费这条流」的承诺兑现在这里），产出「唤醒回合」；跨编制域 / 账本域 / 会话
  子系统的编排按第六条按用例成编排单元，落在控制面组装侧，不堆进任一域。
- **进程承载复用面**：`d_execution_host` 的承载半段经新建的薄 api 门面供 keystone
  域复用；铁律：**执行域不新增对账本 / 会话 / 编制域的认识**，`card_id` 标签之外
  照旧不认识账本。
- **节点绑小队改 workflow/模板 schema**：兼容语义归 contract（预期：小队作为
  解析层，存量直绑降级为单载体匿名小队）。
- **Web 控制台**：载体与小队配置页、排队中形态、卡上「拉起协调者」按钮、attach 入口
  （终端 tab 由既有 PTY 域承载；`d_sessions` 是终端 PTY 域，与 B156.2 会话
  子系统同名不同物的命名警示沿用）。
- **依赖方向（DAG）**：控制台 → 控制面 →（小队调度 / 拉起编排）→ 账本 api、
  会话 api（B156.2 的双向门面延伸：新增账本/会话能力调用一律走门面，不新增
  穿越存量直调债的边）。执行域零新增依赖。
- **对 B156.2 的依赖面**：房间消息（唤醒源与叙事落点）、简报/Decision、绑定
  席位与换绑 CAS、重建四步。B156.3 卡已挂 blocked-by B156.2 边。

### 测试接缝清单（每缝：符号 + 调用方；plan 的接缝覆盖闸按此执法）

架构决定（§7.0）使主缝天然落在门面上——**两个新子系统的入站 api 与出站 client
就是它们的法定缝**，不需要为可测性另抽内部函数（假缝禁令）。

1. **编制域入站 api 门面**（新建）：入队/出队/两级并发计数（小队位 + 载体位）/
   协调者优先准入/角色约束（小队不混编）/载体解析/队列持久。调用方 = 环节执行体
   （`internal/ledgerstep` StepRunner 派发路径）、agentd 控制面、CLI 小队命令族。
2. **Keystone 域入站 api 门面**（新建）：拉起（两入口）/ 唤醒决策（该不该醒、
   同卡合并）/ attach 与自动唤醒互斥 / 失败兜底降级链（resume → 重建四步 → 等人）。
   调用方 = agentd 的 card_events 消费循环、控制面、CLI。
3. **两个新子系统的出站 client 接口**（新建）：接口定义在本侧、由组装点绑定
   （账本 api / 会话 api / 进程承载 api / PTY api）。本缝用**测试替身**断言对外
   依赖的调用契约，并保证新子系统可在不起 agentd、不起账本库的情况下独立测试
   ——这正是双向门面换来的可测性（第 2 档 interface 的正当用途，注释标注测试缝）。
   同缝覆盖「以协调者身份拉起/续接一个 CLI 会话**不进派发状态机、不产生 task**」
   这条铁律断言。
4. **环节执行体缝**（存量，`internal/ledgerstep` StepRunner，调用方 = 协调者
   会话跑的 handoff CLI 与看板按钮）：协调者点火与人工点火同构；新增断言 =
   小队解析路径与排队分支。
5. **控制台契约层缝**（存量结构，新增端点；调用方 = Web 前端 api client）：
   小队 CRUD、排队中呈现、拉起、attach 定位（机器 → 目录 → resume 命令）。

假缝自查：五条缝全部有真实生产调用方，无为走分支而抽的纯函数。
**契约面机械执法**：`graph check` 对 `target.json` 新声明的契约面为硬闸——本期
新增跨子系统边必须先声明，穿透他方内部即违法。

## 8. 用户故事

1. **开卡即绑**：用户从 CLI 开一张卡，协调者拉起、绑定、房间开聊 spec；用户
   全程只待在桌面端。
2. **批准后放手**：spec 批准回写后，协调者自主逐节点点火 contract → breakdown
   → plan → implement → review，每次点火前看上一节点产出；填补级偏差落叙事，
   推翻级停卡发简报。
3. **唤醒兑现**：深夜 review 裁决 pass，任务终态事件敲醒协调者，它看完 diff
   文件清单做完 acceptance 机械半段；早上用户收件箱里只有一条「验收结论待确认」。
4. **排队**：五张卡同时点火 implement，执行者小队并发 2，三张排队；出队时各自
   协调者醒来确认基线再派。看板「排队中」一目了然。
5. **attach 深聊**：简报讲不清楚，用户点「打开终端」，在那台机器那个目录的
   原生 TUI 里跟协调者深聊；结论由协调者落账后交回无头。
6. **工单静音**：装依赖的 permission_request 半夜到，协调者直接批掉；`rm -rf`
   类照旧躺在收件箱等用户。

## 9. Out of Scope

**永不做**：第二套 TUI / 聊天面内跑 agent 会话（B156.2 同判）；执行者写账、
入房间、感知小队。

**四期（B156.4 内核，本期显式让渡）**：全量自动拉起（不阻塞卡自动排队拉协调者，
含待办卡的自动 spec 聊天）；goal 驱动自主推进；routines（每晨扫账 / canary——
需要无卡协调者，全量自动拉起时自然有家）；兼任/分派定性。

**roadmap（本期不做、后续要做）**：CLI 限额探测（载体健康位本期只预留形状；账户实体化并入本条——主 HOME 同步的载体共享真实账户额度，跨载体账户池要有归属）；
多协调机下的拉起仲裁实测（机制按镜像 lease 同模式设计，真出现第二台协调机再验，
与 roadmap 既有「双协调机对等复活条件」条目合流）。

**本期不做**：对既有「需要你」v1 与看板语义的改动；执行域任何 schema 变更
（`card_id` 标签之外照旧不认识账本）。
**本期不做的架构还债（后续要做，已落 roadmap）**：把被依赖子系统的**实现**迁进
标准结构——本期只为用到的子系统建薄 api 门面（绞杀式还债、升格随卡走）；存量
`d_gateway → d_ledger`、`d_cli → d_ledger` 直调边的清理不在本期，本期只保证
**不新增**穿过它们的直调。
