### P-1｜读路径 handler 切门面后「manager 未注入」的行为与测试夹具范围

**现状事实（本轮实测）。** 任务/项目的**读路径**（`ListTasks`/`GetTask`/`PendingTickets`/`EventsFrom`/`EventsFromAsc`/`LatestEvent`/`CountEvents`/`ListMirrorTasks`/`MirrorTaskTarget` 与项目位置读）今日**不经 manager**：`s.mgr == nil` 时它们仍按本机 `s.st` 正常应答 200/404。生产恒在 Serve 前注入 manager（`cmd/agentd.go:236` `srv.SetManager(mgr)`，早于 `RecoverOnStartup`）。切到 `s.mgr.*` 后，`s.mgr == nil` 会 panic，必须补未就绪守卫。受影响测试面：大量夹具**默认不注入 manager** 却打到这些 handler——`newTestEnv`（外部包 `agentd_test`，19 用例）与 `newTestAgentdEnv`（内部包 `agentd`，27 用例）都不调 `SetManager`；其中明确落入门面收口面且当前不注入 manager 的有 `server_test.go`（`TestAuthRequired` 打 `GET /api/tasks` 期望 200、`TestAttachEmptyListsAreArrays` 打 `GET /api/tasks/{id}` 期望 200、`TestReplyAnswersTicketAndNotifies`/`TestReplyUnknownTicket404`）、`taskplan_test.go`、`tasksfanout_test.go`、`roomsapi_test.go`、`codegraph_test.go`、`projecttree_test.go`、`taskroute_test.go`、`mirrorws_test.go`、`diffbase_test.go:232`、`workspacefiles_test.go`、`wakeconsumer_test.go`（本轮 grep 清点）。

- **方案 A（推荐）｜读路径一律走 `s.mgr`；`s.mgr == nil` 时按既有写路径同款 503 + Warn 守卫；受影响测试按需注入真 Manager。** 优点：与 spec §要变的事实 1／§测试决定「gateway 测试只打门面」正面一致；未就绪语义与 `handleStatus`/`handleDone` 等写路径统一。代价：读接口在「引导态无 manager」下由 200 变 503（生产 Serve 前不可达，仅测试/装配错序可见）；测试文件集改动变宽。
- **方案 B｜读路径在 `s.mgr == nil` 时回落 `s.st`。** 优点：测试零改动。代价：**直接违反** spec §要变的事实 1「gateway 不再自己写任务库」与 §测试决定「断言：gateway 测试只打门面」，且把「无 manager 可用」这一引导态永久焊进生产读路径。否。
- **推荐 A。请拍板。**（若裁 A，需在 contract 回写 C-1；若裁 B，须退回 spec/contract 重画「门面唯一通道」承诺。）

### P-2｜`projectIndex()`/`buildLocalTree()` 的 workspace 注入源：保持 `s.st` 还是改 `s.mgr`

**现状事实（本轮实测）。** `internal/agentd/handlers.go#Server.projectIndex` 调 `workspace.LoadProjectIndex(s.st, s.log)`；`internal/agentd/projecttree.go#Server.buildLocalTree` 调 `workspace.BuildLocalTree(ctx, s.st, …)`。二者把 `*store.Store` 当作 `workspace.ProjectLocationLister`（`internal/workspace/projectjoin.go#ProjectLocationLister`，仅含 `ListProjectLocations()`）注入 workspace 域——**调用边是 gateway→workspace（既有方向）**，不是 handler 对 `s.st.X()` 的直调方法。contract §1.1/§1.3 的 move 清单**未收录**它们（本轮 `s.st` 全量清点亦未列入）。`s.mgr` 恰有同形 `ListProjectLocations()`，可作替代注入源。

- **方案 A（推荐）｜本卡不动。** 理由：它们不是「handler 直打 store 方法」，而是经 workspace 窄接口的注入；改注入源会给 `d_gateway→d_orchestration` 增加接口调用边，触碰 contract §5.3 #17「预算 76 不抬」——一旦命中上升即违约，需整图重扫复核。contract 澄清一行（C-2）即可：经 workspace 窄接口注入的位置表读取不在本卡门面收口面。
- **方案 B｜一并改 `s.mgr`。** 优点：语义更彻底（连注入源也不碰 store）。代价：需重扫；若 `d_gateway→d_orchestration` 命中 > 76，违反 §5.3 #17，须**退回 contract**重冻预算。
- **推荐 A。请拍板。**

### P-3｜迁移后 `ticket_answered` 事件是否需在编排门面内 `Publish`

**现状事实（本轮实测）。** 现状 `handleReply` **只** `s.st.AppendEvent(EventTypeTicketAnswered, …)`（`internal/agentd/handlers.go:403`），**不** `hub.Publish`；编排内既有审批者应答路径同样只 `AppendEvent`、不 `Publish`（`internal/orchestration/manager.go:2515`，`approvePermission`）。contract §5.2 #8 只要求 `applied=true` 路径 append 该事件。唤醒 executor 靠 `hub.NotifyAnswer`，事件消费靠事件表（attach/wait/`EventsFrom*`）。

- **方案 A（推荐）｜门面 `AnswerTicket` 内只 `AppendEvent`、不 `Publish`。** 与现状及编排内既有应答路径逐字一致；gateway 侧保留 `hub.NotifyAnswer`（唤醒）+ `mgr.RelayAnswer`（自愈中继），contract §5.2 #13 已冻结。零对外行为变化。
- **方案 B｜门面内补 `Publish`。** 新增一条现状不存在的事件广播，可能改变 wait/attach 时序与去重分界（`handleEvents` 的 `maxReplayed`/`lastWrittenSeq` 逻辑依赖事件先落库后订阅），越界。否。
- **推荐 A。请拍板。**
