# B207：平台不变量恒在层

> 状态：待用户批准 · 级别 **L2** · 档位不适用
> 来源：B200 的决定性实验（根因取证在 B200 卡上）
> **本文替换同路径的前一版（方案 D：角色契约段 + 方法论段）。前一版作废**——
> 它试图连「任务契约归谁」一起解，而那属于工作流纪律块重构的范围（见 Out of Scope）。

## 问题陈述

派发时注入的纪律块是**二选一**，不是拼接。`internal/agentd/manager.go#resolveDisciplineFor`：
点了名走 `ByName`，没点名走 `For`；`ByName` 内部又是「磁盘覆盖文件 **或** 同名内置块」。
于是工作流节点一点名（整条 charter 流都点名），handoff 自己那份内置纪律**整份出局**。

内置那份里混着三类不同所有者的内容（以 `builtin/single-context.md` 九条为样本）：

| 条 | 内容 | 所有者 | 换个任务类型还成立吗 |
|---|---|---|---|
| 1 前半 | 不派发、不调 handoff CLI、不起新 executor | **平台** | 成立 |
| 4 | 没跑到结果不许写结论 | **平台** | 成立 |
| 5 | 台账落盘 | **平台** | 成立（写法要改，见下） |
| 9 尾 | 按协议输出 trailer 收口 | **平台** | 成立 |
| 1 后半、3、9 首 | 自己逐 task 干、自我双裁决、不中途结束回合 | 执行器能力 | 不成立 |
| 2、6、7、8 | 一次一个 task、终审、按 plan 原文 commit | 任务/角色 | 不成立 |

平台那四条**没有安全的家**：它们住在一份可被整份替换的块里，所以每次点名派发都陪葬。

已观测到的后果（全部实测，不是推演）：

1. **plan 节点连续 4 轮直接写实现代码**（B190/B196/B192 各一轮，B202 一轮）。根因是
   `charter-plan.md` 缺「红线」节，而内置 `plan-writing.md`（开篇即「你这一轮的产出是
   一份实现计划，不是代码」）因覆盖机制从未被用上。补回红线节后重派，产出立刻变成
   941 行纯 plan 文档、零实现代码。
2. **走 charter-\* 派的 implement 永远不落台账**。`charter-implement.md` 中 `ledger`
   命中 0，而内置 `single-context.md` 要求落盘。这**不是漂移**——charter 是方法论文档，
   本来就不该谈台账；拷贝再新也补不出源头没有的东西。
3. **执行器适配一并丢失**。`charter-implement.md` 里零处「自己逐 task 干 / 不中途结束
   回合」。选错档的代价已实测：同一份 6-task plan 从「0 推动 26 分钟跑完」退化成
   「9 次人工推动只到 3/6 且最后卡死」。
4. **trailer 指令可能根本没下去**。全仓只有 `single-context.md` 一处在教执行者输出
   trailer，而平台侧有 `VoidReasonTurnDiscipline`（「executor 活着但没守回合纪律：
   无 trailer、零文本」）专门处理它缺失。**这条是待查事实，见「实现决定」第 4 条。**

后果 1 已手工止血（plan/review 两份重新拷贝、两机同指纹并验证），2/3/4 未解。
止血只对「漂移」这一类有效，且有效期到 charter 下次改动为止，而**没有任何东西会告诉
你副本旧了**——这次是靠一个连续四轮的事故才发现的。

## 现状事实（本轮工作树读数，交 plan 复核）

| 事实 | 出处 |
|---|---|
| 三个派发调用点（Dispatch / resumeForContinue / ResumeTask）已收口于一个函数 | `internal/agentd/manager.go#resolveDisciplineFor` |
| 点名解析：磁盘覆盖文件 → 内置同名 → 都没有则报错 | `internal/discipline/resolver.go#Resolver.ByName` |
| 未点名解析三档：有值读文件 / **显式空串关闭注入** / 无 key 用内置默认 | `internal/discipline/resolver.go#Resolver.For` |
| Resolver 无状态、每次派发重新读盘（改文件不必重启 agentd） | 同上，类型注释 |
| 纪律块来源会回显给协调者（`纪律块: <来源>`） | `internal/discipline/discipline.go#Block.Source` |
| 工作流定义里存的是**名字**不是正文 | `deploy/workflows/charter-v4.json:53` |

## 方案

### 采纳：恒在层拼接注入

平台不变量成为**独立的第四层来源**，在解析结果之外**无条件拼接**，不参与「二选一」。
无论点名与否、无论覆盖文件写了什么，它恒在。

四条正文（措辞必须任务类型中立——审阅轮、扫描轮、写文档轮都读得懂）：

1. 不要派发、不要调用 handoff CLI（只读本地图数据的 `handoff graph` 子命令除外）、
   不要起任何新的 executor 进程或子任务。
2. 没有亲自跑到结果的命令，不许写它的结论。跑了但失败，贴原始报错原文，不要替它归因；
   不确定就写「未验证」。
3. 每确立一个事实就往台账文件追加一行——提交、跑过的命令与原始输出、放弃的尝试、
   做出的判断。**不要攒到回合结束再写：回合可能不会有结束。**
4. 按协议输出 trailer 收口。

第 3 条的措辞是本卡的一处刻意修正：原文是「每 task 完成、每轮修复各追加一行，含
commit 范围」，把「增量写」这个**承重性质**和「task/commit」这个**任务形态假设**焊在
一起。审阅轮没有 task 也没有 commit，照原文注入等于发一条它执行不了的指令。而如果
改写成「回合结束前落盘」，则**恰好消掉它唯一的用途**——断掉的回合没有结束，那一刻
文件是空的。增量是判据，不是修辞。

### 弃选 A：改 `ByName` 的覆盖语义为「追加」

让覆盖文件追加而非替换内置块。弃因：内置块里 6/9 条是执行器能力与任务契约，追加等于
把「一次一个 task、按 plan 原文 commit」灌给审阅轮和扫描轮。**它把该废的和该留的
一起留下了。**

### 弃选 B：给纪律块加生成器与漂移检测

弃因：只对后果 1 有效。后果 2 的那句话**在 charter 源头里根本不存在**，同步得再勤也
补不出来；后果 3、4 同理。它让漂移可见，没让丢失禁令变得不可能。

### 弃选 C（前一版方案 D）：角色契约段 + 方法论段

弃因：范围越界。它连「任务契约归谁写、怎么和工作流同版本」一起解了，而那是工作流
纪律块重构的范围。在此之前先把地基那四条钉死，重构怎么改都不影响它们成立。

## 用户故事

1. 作为协调者，无论工作流点名了哪份纪律块、无论那份块是不是旧的，我都要确信执行者
   不会去派发、不会起新的 executor 进程。
2. 作为协调者，一个远程回合跑到一半断了，我要能从台账文件读到它断之前确立了哪些事实
   ——而不是一个空文件或一份只在收口时才会写出来的文件。
3. 作为协调者，我要能从派发回显看出这一轮**同时**注入了哪些来源，而不是只看到一个名字。
4. 作为使用者，我确实想关掉平台不变量时要有显式且留痕的做法，而不是靠「覆盖文件恰好
   会替换掉它」这种隐式行为。

## 实现决定

1. **拼接发生在 `discipline` 包内**，暴露成一次显式的组装调用，由
   `manager.resolveDisciplineFor` 唯一调用。理由与该函数既有注释同款：三个派发调用点
   必须用同一套判定，分开写的表现是首回合对、`continue` 之后悄悄换掉，事后极难查。
2. **头尾各注入一次，但尾部不是逐字复制**：头部是正文，尾部是换过说法的收口自查
   （「收口前逐条自查：① 有没有把没亲自跑到结果的命令写成结论？② 台账是边干边追加
   的吗？③ 这一轮碰过 handoff CLI 或起过新 executor 吗？」）。
   两个理由：逐字重复容易被整体当成模板噪声打折；且这几条恰好都是**收口那一刻**才违反的。
   **尾部是否真的有效属于待验证判据，见「测试决定」——它防的是一个我们一次都没观测到
   的失败模式（禁令在 prompt 里但位置太靠前被忽略），不是既定结论。**
3. **`For` 的「显式空串 = 关闭注入」不再关掉平台不变量**。那个开关的语义是「这台机器
   给这个执行器派任务时不注入**执行纪律**」，与平台底线不是同一件事。要连底线一起关，
   走下一条的显式开关。
4. **trailer 那条先查后写**：`internal/executor/*/adapter.go` 各 adapter 是否已在
   prompt 层单独注入 trailer 指令。已注入的话第 4 条改为不注入（避免重复），并把这个
   事实写进注释；未注入则按原样进恒在层。**不许假设，B202 那轮能正常收口不能证明所有
   执行器都行。**
5. **关闭出口**：机器级配置一个显式开关，关闭时派发回显必须明写「平台不变量已关闭」。
   不做成「覆盖文件里声明」——那正是今天这个 bug 的形状：一份拷来的文件能静默关掉底线。
6. **来源回显改成可以列多个**，如 `内置:平台不变量 + 配置:charter-plan`。

## 测试决定（接缝清单）

最高可测缝是**组装函数的返回值**——「解析出什么正文」的唯一收口点。四条不变量是否恒在、
覆盖文件如何参与、显式关闭是否生效、头尾是否各一份，全部可在这一个缝上断言，
不需要起 agentd、不需要真派发。

必须覆盖的四个输入组合：点名且覆盖文件存在 / 点名且退回内置 / 未点名走 executor 默认 /
**未点名且配置显式空串**（第 4 种是最容易漏的，也正是第 3 条实现决定所改的那个语义）。

一条真机对照实验（不进单测，作为验收判据）：同一张卡、同一模板、同一纪律，只动
「尾部自查有没有注入」一个变量，各派一轮，比对执行者收口时有没有漏台账、有没有把
没跑到结果的命令写成结论。判据形态与 B200 那轮红线实验同款，成本约十几分钟。
**实验结果为「无差异」时，尾部注入应当删掉，不留。**

## Out of Scope

以下全部归**工作流纪律块重构**，本卡不碰（用户 2026-08-23 明确划界）：

- 任务契约层与执行器适配层的所有权、选择键、是否废除内置。
- `For` 在「配置里没这个 key」时**静默**用内置默认——这条静默正是「内置 `plan-writing`
  从未被用上却四轮无人察觉」的根子，但它属于第三层的选择机制。
- 纪律块与工作流同源同版本（今天工作流在账本里有不可变版本，它点名的正文在磁盘上没有
  版本，回答不了「linux-01 上跑的是哪一版」）。
- 执行者往卡 timeline 写入的通道。今天纪律块第 1 条禁止调 handoff CLI，`card note`
  正在禁令内，所以**台账文件不是设计选择，是禁令逼出来的唯一出口**。要让执行者写
  timeline，得开一条只写 note、不碰任务不派发的窄通道，并把它从禁令里豁免。
- 台账文件与卡 timeline 的职责边界；无卡的普通派发靠什么恢复现场。

以下本期不做、后续要做，已落 `docs/roadmap.md`：

- 推平 breakdown / implement / integrate / contract / recon 五份副本的两机差异。
