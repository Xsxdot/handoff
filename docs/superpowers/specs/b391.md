# B391 spec：IM 寻址 `@卡号` 前缀不被解析

**上游状态：已批准**（用户 2026-09-21 决定：B390 的 P3 另立卡，高优）
**级别：L2 单子系统**（collab 寻址面 + CLI 文案一致性）
**上游事实源**：B390 的 debug/plan 轮实测（`@B1` 存原样、`GetCard` 查不到故不唤醒；CLI 帮助写「@成员或卡号」与实现不一致）；契约锚 `docs/superpowers/specs/b358-contract.md` §3.8（寻址语义，**先读再改**）。

## 1. 问题

主 agent 用 `handoff session send <会话> '…' --mention @B382 --agent commandcode` 发消息：命令返回 ok、账本落账（实测 seq 16861），**但从不唤醒**该卡的席位。B390 的排查确认：`@` 前缀未被剥离/解析，`@B382` 被原样存储，`GetCard` 查不到该值，寻址不命中。

后果：spec §4.3 的真机验收链（`@B382` → 认领 → 路由 linux-01 → 协调者回话 → 主 agent 在 IM 看到）**第一步就不成立**，与名额键泄漏是两个独立堵因。

## 2. 范围

**做**：让 `--mention <目标>` 接受文档已宣称的 `@卡号` / `@成员` 形态（或在文档与实现之间取一致——以契约 §3.8 为准），并补能变红的回归测试：`@B1` 必须命中该卡**当前席位**（含换绑后仍找得到）；`@agent:<名>` / `@user:<名>` 同理。
**不做**：不改寻址的语义模型（`reply_to` 隐式寻址、无寻址不唤醒、知会类结构事件不进聊天流的既有规则不动）；不动 B390 的消费轮可见性/重试；不给「@所有人」开门。

## 3. 待查（先取证再改）

1. `internal/collab/sessions.go` 里 mention 的**解析与存储**路径：`@` 前缀在哪一步被丢/被保留；`user:` / `agent:` 成员记法与卡号的分支判断在哪。
2. `internal/collab/service.go` 的寻址投递（`Pending` / `Consume`）如何按 consumer 匹配。
3. CLI 帮助文案的来源（`cmd/session*.go`），确认真实契约是哪一侧——**若契约写的是不带 `@`，则改的是文档而不是实现**（这一步决定改哪边，不许两条都改）。
4. 既有测试：`internal/collab/*_test.go` 里 mention/寻址相关用例，确认改动不会破坏「无寻址不唤醒」等既有语义。

## 4. 验收判据

1. 回归测试能对当前 bug 变红：`@<卡号>` 寻址在修复前不命中、修复后命中该卡当前席位（变异复验：把 `@` 剥离去掉要重新变红）。
2. `@agent:<名>` / `@user:<名>` 与裸 `agent:<名>` / 裸卡号 的既有行为不回归（既有用例全绿）。
3. 无寻址发言仍然**不唤醒任何人**（反例断言在场）。
4. 文档与实现一致：`session send --help` 的措辞与真实接受的形态逐字对应（若改文档，给出契约出处）。
