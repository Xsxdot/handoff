# B382 spec：非派发实现卡的工作分支来源（人工登记）

**上游状态：已批准**（用户 2026-09-22 批准；同日两条裁定：裁决 #10 选 E、登记只在无快照时生效）
**级别：L2 单子系统**（`internal/ledger` 的工作分支判据面 + `cmd` 卡命令面）
**入口节点**：debug（根因已复核，见卡上 #17718 段）；本节点只出 spec，不动实现
**裁决指针**：decision #10 答复（选 E）；本 spec 是它的定稿形态

## 1. 问题陈述

账本回答「这张卡的工作分支是哪条」只有一个来源：`dispatched` 事件快照（`Store.WorkBranch`，`internal/ledger/events.go:575`；跳过审阅轮、取最后一条非审阅快照的 branch）。派发审阅轮时，取不到就直接拒发（`internal/ledgerstep/dispatch.go:245-248`，报「审阅轮取工作分支: 卡 X 没有非审阅的 dispatched 快照（还没派过实现轮？）」）。

于是**凡是实现不是「派发出去的 implement 轮」做的卡，review 一个都进不去**，卡停在 review 列没有出口：人工在本机直接改的、跨机手工接续的、从 PR 进来的都是这一类。

真机实例（2026-09-22 核验，卡上可对质）：

- **B373**：dispatched 快照 **0 次**，实现在本机手工做（`feat/b373-opencode-monitor`），分支早已合入功能线，卡却只能人工绕行收口。
- **B320 / B367 / B372**：同为人工直提功能线（`80e53e17f` / `398b3551f` / 合并 `d46d4ec3e`），同样 0 快照、同样只能人工复核 + 记偏差后收口。

这不是「没合并回基线」的问题——节点之间是链式切分支（下一轮的 base 取上一轮的工作分支），全程唯一的合并在 finish 由人工做。缺的是**「工作分支」这个事实缺少人工形态的来源**。

## 2. 级别与档位

**L2 单子系统**：`internal/ledger`（工作分支判据面）+ `cmd`（卡命令面）。

定级先例（本仓成文）：B396「L2 单子系统（节点运行锁：`internal/ledger` 的锁实现 + `cmd`/`agentd` 的判据面）」与本卡形态同形；B393「L2 单子系统（`internal/agentd` + `internal/keystone` 的唤醒执行链）」同理。

不动契约层：不新增跨机器依赖方向、不改 wire 端点、不改权限/裁决语义；账本事件词汇是**追加一个成员**，老读者忽略未知事件即在（现状即如此：派发快照之外的注释类事件都是这样消费的）。

## 3. 方案（含弃选与理由）

**采用：给账本补一个「人工登记工作分支」的来源。**

- 新增一条账本事件记录「某卡的工作分支被人工登记为某条分支」（谁、何时、哪条，进事件流可查）；
- 账本的工作分支判据读序改为：**非审阅 dispatched 快照 → 人工登记 → 报错**；报错文案指路到登记动作；
- 卡命令面给一个登记入口（用户可见名字见 §5）。

**弃选与理由**（逐条对过已冻结契约与产品不变式）：

- **A. `WorkBranch()` 回落读卡的 `base_branch`**：实测不可行——四张人工实现卡的 `effective_base_branch` **全为空**，回落拿不到值，A 对真实卡无效；一旦人工去设它，就把 finish 的合并去向一起改了（`base_branch` 的正常值是合并目标，如 B233.28 = `cards/B233.1-charter-7`），且这种错**静默**（review 跑起来、看着成功，看的却是另一棵树）。另，`SetCardBaseBranch` 的契约本身就写着「为**尚未出现任何 dispatched 事件**的卡设置或清除显式基线」（`internal/ledger/cards.go:639`），拿它表达工作分支是把两个概念焊死。
- **A′. 卡上加 `work_branch` 字段**：语义干净，但要动 schema（两处 CREATE + 一条 ALTER 守卫）、SELECT 列表、setter API 与迁移路径——比事件路径重一档。事件流本就是账本的通用载体，追加事件不需要迁移。**若事件路径在实践中暴露不足，A′ 是后续选项（见 Out of Scope）。**
- **B. `card dispatch --base/--branch` 显式覆盖**：每轮都要手填，且节点绑小队时 `--target/--executor` 被禁，覆盖通道与小队绑定的入口冲突需单独设计——一次性、不可复用、长期更贵。
- **C. 只改报错文案**：不修复，非派发实现卡仍无出口。

**生效范围（用户 2026-09-22 裁定）**：人工登记**只在卡上还没有过非审阅 dispatched 快照时生效**。快照一旦存在即为权威，不允许覆盖——避免同一事实两个来源；「人工接手一条已派发卡的工作分支」本期不做。

## 4. 用户故事

1. 作为协调者，当一张卡是本机人工实现时，我能在卡上登记它的工作分支；此后 review 节点能从该分支切出一次性审阅分支，卡恢复正常路径。
2. 作为协调者，我登记错了可以重新登记（最后一条登记胜）；卡上还没有快照时可以用空串清除登记。
3. 作为后来者（换人/换会话接管），我在卡的事件流里能看到「谁、什么时候、把工作分支登记成了哪条」。
4. 作为执行者（review 轮），当卡既无快照也无登记时，我看到的报错直接指路登记动作，而不是问「还没派过实现轮？」。
5. 作为协调者，当登记的分支在别的机器上不存在时，拒发文案告诉我先 `git push origin <分支>`（沿用现状跨机闸，不新增机制）。

## 5. 实现决定

- **判据收口在账本层**：工作分支的答案由账本给出（一个查询入口回答），派发侧不再自己拼来源——这样「快照 → 登记 → 报错」的顺序只有一处实现。
- **生效范围**：登记只在无快照时被采纳（§3 裁定的落地）。有快照时登记被忽略（不报错、不进判据）。
- **登记是可覆盖的追加**：再次登记 = 最后一条胜；空串 = 清除。清除与覆盖都留事件流痕迹。
- **用户可见的名字**：新增卡命令 `handoff card work-branch <卡号> <分支>`（空串清除）。弃选形态：把 flag 挂到既有 `card update --work-branch`——同一动作但可见性弱一档，且 update 已承载多种字段设置。
- **跨机不新增机制**：登记的分支跨机时由现状「工作分支已发布 origin」闸兜住（未发布 → 拒发 + 指路 push）。
- **报错文案**：把现状那句「还没派过实现轮？」改成指路（登记命令名 + 一句为什么），文案由测试锁住关键词。

## 6. 测试决定（接缝清单）

**接缝 1（承重缝）**：`Store.WorkBranch`（现状符号，`internal/ledger/events.go:575`）。
调用方（现状，可 grep 核验）：`internal/ledgerstep/dispatch.go:192`（取 base 与跨机判据）、`internal/ledgerstep/node.go:430`（pass 后推 origin）。
断言三条：①无快照 + 有登记 → 返回登记的分支；②无快照 + 无登记 → `ErrNotFound` 且文案含登记命令名；③有快照 + 有登记 → 返回快照（生效范围裁定）。

**接缝 2**：登记写入口（**新建符号**，签名归 contract/plan 落地；声明：将被 `cmd` 卡命令族调用，导出到账本包对外 API 一层）。
断言：登记后事件流可查（谁/何时/哪条）；再次登记 → 最后一条胜；空串 → 清除。

**接缝 3（边界，回归锁）**：跨机判据复用现状 `WorkBranchPublished`（`internal/ledgerstep/dispatch.go:208`）。
断言：登记的分支未发布 origin 且目标机与上一台不同 → 拒发并给出 push 指路。无新缝。

**假缝禁令核对**：以上三条都是导出符号或 CLI 入口，且都有生产调用方；无「未导出、无生产调用方、只为走满分支」的纯函数占名额。内部锁（如登记事件的编解码往返）记入 plan 的内部锁候选，不顶替缝级断言。

## 7. Out of Scope

- **永不做**：为人工实现补一条伪造的 `dispatched` 快照——审计事件只能由真实派发产生，伪造即污染审计链。
- **本期不做、后续要做**：卡字段 `work_branch`（A′ 形态）——若事件路径在实践中暴露不足（例如需要按分支索引、需要与卡字段一同 CAS），再起一期；残余落 roadmap。
- **本期不做、后续要做**：「登记可覆盖快照」——支持人工接手一条已派发卡的工作分支；本期由用户裁定只在无快照时生效。残余落 roadmap。
- **本期不做**：「登记来源机」追踪与自动发布登记分支——跨机沿用现状 origin 闸。
- **本期不做**：`base_branch` 语义变更、权限/裁决语义变更、路由与承载语义变更。
