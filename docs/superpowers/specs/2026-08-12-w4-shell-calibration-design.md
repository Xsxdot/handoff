# W4 外壳校准期设计

> 形态基准：`prototypes/desktop-console/`（可运行原型 + 20 张实现截图）。
> 本轮**以还原原型为骨架**，五处刻意偏离在 §8 逐条记录并说明理由。
>
> 上游：`2026-08-11-web-console-master-design.md` §5「W4 工作区资源」。
> 本轮是 W4 的**第一期**，只做形态与框架对齐，不做 PTY、不做浏览器预览、不做文件写入。

## 为什么要有这一期

W3 交付后用户的第一反应是「跟原型完全不一样，那原型做了干啥」。

追下去发现：W3b 的 spec 第 5 行就写明形态基准是 `prototypes/desktop-console/`，第 10 行写「W3b 不设计形态，只还原形态」，然后 §0 把「中央的 terminal / editor / browser 工作台与右侧文件树」整块划到本轮不做——而那恰恰是让原型看起来像原型的东西。**裁剪是当初写进 spec 的既定决策，不是跑偏；失误在交付时没有人说明「所以现在不像原型，这是预期的」。**

这一期的目的就是把这笔债还掉：**先把页面形态和基础框架对齐，再谈往里填功能**。判据只有一条——把本期成果和 `implementation-complete-workbench.png` 并排看，结构能对上。

## 1. 信息架构

### 1.1 四级树

```
项目 (ProjectNode)                       ← origin_url 派生，跨机同一
└ 开发机 (ProjectLocationNode.machine)   ← ""=本机
  └ 目录 (Workspace)                     ← 主目录与各工作树平级
    └ 任务 (Task)                        ← 按 work_dir 挂到目录下
```

第三级里「主目录」（`is_main=true`）与工作树是**兄弟节点**，与原型一致（截图中 `🏠 主目录 ~/workspace/super-d…` 和 `⑂ integration/b2-b3` 并排）。

任务挂到目录的依据是 **`Task.work_dir` 与 `Workspace.path` 的路径等值**，纯前端 join，不需要新接口。`work_dir` 为空表示原地模式，此时挂到主目录（与 `proto.Task.Workdir()` 的回退语义一致）。

### 1.2 「当前目录」是唯一的全局选中态

选中一个目录，同时决定三件事：

1. 中央显示哪一组 tab
2. 右栏文件树的根
3. 顶部面包屑 `项目 / 开发机 / 目录` 的内容

**切换目录时，中央整组 tab 与右栏一起切换。** 这是原型 AGENTS.md 的原话（*Selecting a directory changes both the central workspace context and the right file tree*），也是用户复述过的核心要求。

未选中任何目录时：中央显示空态，右栏**不渲染**（原型：*The file tree appears only when a concrete directory is selected*）。

### 1.3 什么不跟目录走

任务看板、工单面板是**全局**的，跨目录可见，不被当前选中目录过滤。理由：这两者都是「你还欠哪些没处理」的总账，被当前选中项筛掉会直接导致漏处理。

## 2. 中央 tab 系统

### 2.1 tab 组与分屏

中央区可以是一组或**左右两组** tab（原型：左组是任务 TUI，右组是编辑器）。

- 每组有自己的 tab 条、自己的激活 tab、自己的 `+` 按钮
- 分屏比例可拖拽
- 关掉一组的最后一个 tab，该组消失，另一组占满
- **两组同属当前目录**：切目录时两组一起换

分屏的开启方式：顶部面包屑右侧的分栏图标（原型截图右上角那三个图标之一），以及 tab 的右键菜单/拖拽。本期实现按钮开关即可，拖拽分屏不做。

### 2.2 tab 的身份与去重

**只有三种 tab：终端、文件、TUI。** 没有别的种类。

三种 tab 都能从两个地方开出来，区别只在**基准目录**：

| 从哪开 | 基准目录 | 本期可选种类 |
|---|---|---|
| 中央 tab 条的 `+`，或左栏/看板的快捷操作 | **当前选中的工作树目录** | 终端、文件、TUI |
| 悬浮按钮 | **用户 home** | 仅终端（原因见 §2.6） |

「点左栏目录开终端」「点左栏任务开 TUI」「点右栏文件开文件 tab」「点看板卡片开 TUI」都是**快捷操作**——它们是「新建一个 X 种 tab 并直接指定目标」的捷径，不是独立的 tab 种类。

tab 的身份 = `(基准目录, 种类, 目标)`，同身份**不重复打开**，已存在则激活：

| 种类 | 目标 | 快捷操作入口 |
|---|---|---|
| `terminal` | 序号（同一目录可开多个） | 无（只能从 `+` 或悬浮按钮） |
| `file` | 基准目录内的相对路径 | 点右栏文件 |
| `tui` | task id | 点左栏任务行；点看板卡片 |

### 2.2.1 空白 tab 与种类选择

新开一个 tab 的默认状态是**空白**，中间列出可选种类，带快捷键——形态参照 Orca 的新建面板：

```
  ⌨  新终端            ⌘T
  📄  打开文件          ⌘⇧O
  🤖  打开任务 TUI      ⌘⇧A
```

选中一种之后该 tab 才变成对应内容。「打开文件」「打开任务 TUI」需要再选目标（文件选择器 / 该目录下的任务列表）。

这一条是形态上的关键：**中央区域在没有 tab 时不是一块死掉的空白**，它是一个可用的起点。整个中央区域一个 tab 都没有、且没选中目录时，显示全局空态（参照 Orca：logo + 「从侧边栏选择一个目录开始」+ 添加项目按钮 + 快捷键提示）。

### 2.3 TUI tab = 桌面端 TUI

**这是本期最重要的一条决定，也是对原型的最大偏离（见 §8.1）。**

原型里这个 tab 装的是 executor 原生的 OpenCode/Codex CLI 界面。本项目**不再走 attach 原生 CLI 这条路**，改由 handoff 自己渲染任务会话。W3/W4b 已经交付的四块内容，就是这个「桌面端 TUI」的当前成熟度：

| 原型里 OpenCode 原生 TUI 的部件 | handoff 的对应物 | 状态 |
|---|---|---|
| user/assistant 对话流，`✓ 读取文件` / `✓ 编辑文件` 行 | `TimelinePanel`（W4b，读 `frames.jsonl`） | 已有 |
| 底部输入框「输入你的指令或问题…」 | `AdvanceActions` 的修改指令框（`continue`） | 已有 |
| Todo / 当前操作 | `EventsPanel` | 已有 |
| （原型没有） | `ReviewPanel`：diff / 跑命令 / 读文件 / 完成任务 | 已有，handoff 独有 |
| 顶栏 `Model: gpt-5-codex`、`Context: 144,390 tokens (14%)` | 无 | 缺，后续补 |

所以 TUI tab 本期**装真内容**，不是占位。布局按原型的单栏纵向流：会话正文在上，指令输入框固定在底部。`ReviewPanel` 作为任务进入 `waiting_review` 后出现的区段接在正文末尾——它是「这一轮干完了，你来验」的自然延续，不是一个常驻侧栏。

`TicketsPanel` **从 TUI tab 移出**，去处见 §5.2。

**TUI 的终局是一个 agent。** 等它做完整（补上模型名、context 用量、真正的交互式会话）之后，它本质上就是「一个可以对话的 agent 实例」，那时它也应当能从悬浮按钮以 home 为基准开出来——即「不挂在任何工作树上的一个 agent 会话」。**本期不做**，此处只记录方向，避免后面把 TUI 写死成「必须绑定 task id」的形态。

### 2.4 终端 tab

壳按最终形态做：图标、标题（`bash · <目录名>`）、关闭、参与分屏。内容区是一句明确的占位：

> PTY 后端尚未实现。当前查看 executor 现场请用 `handoff attach <task>`。

**不做置灰按钮**（W3b §0 的既有纪律：置灰控件承诺"以后能用"，用户会反复点）。这里是可点、可开、内容诚实说明未就绪——因为形态校准需要它真能开出来。

### 2.5 悬浮按钮

右下角常驻的悬浮按钮，点击弹出与 §2.2.1 同一个种类选择面板。形态参照 Orca 的悬浮面板（可最小化、可展开、带 `+`）。

与中央 `+` 的唯一区别是**基准目录是用户 home，不是当前工作树**。语义是「开一个不挂在任何项目上的东西」——临时跑个命令、看个不属于任何工作树的文件。

**本期这个面板里只有「新终端」一项**，理由见 §2.6。

### 2.6 为什么本期悬浮按钮不放「文件」

以 home 为基准浏览文件，意味着 agentd 的文件接口要接受 `$HOME` 作为根。这是一个**安全边界的实质放宽**，不能在校准期顺手夹带：

- `~/.handoff/config.yaml` 里存着 **agentd 主令牌**（`token` 字段）。
- 控制台会话是**刻意做得比主令牌弱**的凭据——一次性 ticket 换取、可吊销、按设备记录。
- 如果一个控制台会话能读 `$HOME` 下的任意文件，它就能读出主令牌，**弱凭据当场提权成强凭据**，整套会话管理的意义归零。
- `$HOME` 下还有 `~/.ssh/`、各种 CLI 的凭据文件，问题同理。

所以 home 基准的文件浏览必须单独设计（至少要有：排除清单 / 显式授权目录 / 或者干脆只允许用户在设置里逐个添加可浏览根），那是独立一轮的事。**本期悬浮按钮只开终端**——而终端本期还是占位，所以这条路径这一期根本不通到磁盘上，风险为零。

同样地，§7.1 的目录列举接口保持「只接受已探测到的 `Workspace.path`」这条白名单，不为悬浮按钮放宽。

## 3. 左栏

### 3.1 语义改造

`ProjectTree.tsx` 的层级结构不动，改的是点击语义：

| 行 | W3 现在的行为 | 本期行为 |
|---|---|---|
| 项目 | 写 filter（筛看板） | 展开/折叠 |
| 开发机 | 写 filter | 展开/折叠 |
| 目录 | 写 filter | **选中为当前目录**（切中央 tab 组 + 右栏 + 面包屑） |
| 任务 | `navigate('/tasks/:id')` | **选中其所在目录 + 在中央开 TUI tab** |

看板的筛选改由看板弹出层自己的 `FilterBar` 承担（`filter.ts` 的纯函数原样复用，只是不再由树写入）。

保留 W3b 的两条诚实展示纪律，不得回退：不可达机器保持可见并标「已断开」+ 原因原文；未归属任务（`project_id === ""`）挂在树末尾的「未归属」分组。

### 3.2 底部按钮区

原型左栏底部是 `+ 添加项目` 与右下角一个齿轮。本期为三个入口：

```
[ + 添加项目 ]        [🎫 3]  [⚙]
```

- `+ 添加项目` —— 复用 `AddProjectWizard`
- **工单**（新）—— 带未处理数量角标，点开全局工单弹出面板（§5.2）。数量为 0 时按钮仍在，角标不显示
- **设置** —— 打开设置页（§6）

W3b 因为「不渲染未实现功能的入口」而没渲染齿轮，本期齿轮有了真落点，可以出现。

### 3.3 任务看板入口

原型把 `任务看板` 和 `开发机` 放在左栏**顶部**作为顶层导航。本期看板改为弹出层（§8.3），入口保留在同一位置——左栏顶部的 `⊞ 任务看板` 按钮，点击弹出而非替换内容区。`开发机` 按钮取消（收进设置页，§8.4）。

## 4. 右栏文件树

仅在选中目录时渲染。内容对照原型：

- 头部：`文件` + 刷新 + 更多 + 折叠面板
- 搜索框（本期做前端过滤即可，不发请求）
- 根标题 = 当前目录名（原型显示 `integration/b2-b3`）
- 树体：目录可展开，文件可点击 → 中央开 `file` tab
- **git 状态角标**：原型在 `transport_test.go` 和 `Makefile` 上有 `M` 标记

数据来源：由 `GET /api/tasks/{id}/diff` 已有的改动文件列表推导，**仅当该目录上挂着任务时才有**；没有任务的目录不显示角标。不为此单开接口——`git status` 接口是 W4 后续期（文件写入）真正需要时再做的事，本期为一个装饰性角标引入它不划算。

**语义要诚实**：`handoff diff` 是 `git diff base...HEAD`，只反映**已提交**的改动，看不见工作区里未提交的编辑。所以这个角标的含义是「相对基线已改动」，不是 git status 的「工作区已修改」。角标的 tooltip 必须说明这一点，不能让人以为它等价于 IDE 里的 `M`。

## 5. 弹出层

### 5.1 任务看板

复用 `BoardPage` 的四列布局与卡片，容器从整页改为**居中弹出层**（遮罩 + Esc 关闭）。

- 四列：等待执行 / 进行中 / Review / 完成
- 干预态是**卡片级**标记而非额外列：`● 等待审批`、`● 等待 Review`（橙色）
- 顶部：搜索、全部项目下拉（多选）、全部开发机下拉、`⚠ 只看待处理`
- **点卡片 → 关闭弹出层 + 选中该任务所在目录 + 在中央开它的 TUI tab**（原型 AGENTS.md：*Opening an actionable card returns to its existing task session in the workbench*）

### 5.2 工单面板

复用 `TicketsPanel`，容器为弹出层，与看板同一类控件。

- **全局**：列出所有目录下的全部挂起工单，不被当前选中目录过滤
- 每张工单可就地批准 / 拒绝（必须填理由）/ 回答
- 每行标注它属于哪个项目 / 目录 / 任务，并提供「跳到该任务」

**数据来源（无新接口）**：`pending_tickets` 只出现在 `GET /api/tasks/{id}` 的响应里，任务列表上没有，也没有跨任务的工单列表接口。本期这样取：

1. 从任务流（`useTasks`，2.5s）筛出 `state === 'waiting_answer'` 的任务——按状态机，有工单挂起的任务必然处于这个状态
2. 对这批任务各发一次 `GET /api/tasks/{id}` 取 `pending_tickets`
3. 左栏角标 = 这些 `pending_tickets` 的总条数（一个任务可能挂多张）

N+1 在这里是可接受的：`waiting_answer` 的任务每一个都在**阻塞一个人**，数量天然极小。若将来这批常态化到两位数，再加 `GET /api/tickets` 汇总接口，那时它有真实依据。

跨机暂不涉及：前端目前只请求本机 `/api/tasks`，不带 `?scope=all`。

保留 W4b 既定的纪律：**审批入口唯一**。时间线里的 `EventMark` 仍然不可点，只做「裁决入口在工单区」的指向——`EventMark.tsx` 的文案需要从「右侧工单区」改为与新位置一致的说法。

## 6. 设置页

原型里设置与开发机是两个独立顶层页，本期合并（§8.4）。

**设置页是整页替换中央内容区，左栏保持可见——不是弹出层。** 三条理由：它内容重、有多个分区，塞进弹层会挤；它是低频的配置动作，不需要「扫一眼就回去」的弹层语义；原型的开发机页本来就是这个形态，这一点不必偏离。同时也避免了三种弹层互相叠加。

退出设置回到工作台时，中央 tab 组与当前选中目录保持不变。

分区：

- **开发机**：复用 `MachinesPage` + `MachineDetail`。列表 + 右侧详情（连接信息、目录与任务计数、可用执行者开关、重启 agent、打开终端）。其中「可用执行者开关」「重启 agent」「打开终端」三项**本期只渲染不接线**，点击提示未实现——它们需要 agentd 侧的写接口，不在本期。
- **常规**：桌面行为等，本期空占位。
- **Env 文件**：原型有完整设计（每台机器下的物理 `.env` 文件，每个文件多个变量），本期不做。

## 7. 后端新增

本期唯一需要动 Go 的地方，两个接口。

### 7.1 目录列举

```
GET /api/workspaces/dir?path=<工作树绝对路径>&rel=<相对路径>
```

响应：

```json
{
  "entries": [
    {"name": "internal", "is_dir": true},
    {"name": "go.mod", "is_dir": false, "size": 1284}
  ]
}
```

- `path` 必须命中 `GET /api/projects/tree` 探测出的某个 `Workspace.path`（等值比对，`filepath.Clean` 归一化后），否则 403。**不接受任意路径**——这是防止把 agentd 变成任意目录浏览器的唯一闸门。
- `rel` 在该工作树内解析，复用 `ReadFile` 已有的 `os.OpenRoot` 内核级越狱防护：单次系统调用完成符号链接解析，不留 TOCTOU 窗口。
- 不递归。一次一层，前端按需展开。
- 排序：目录在前，各自按名称字典序。

### 7.2 按工作树读文件

```
GET /api/workspaces/file?path=<工作树绝对路径>&rel=<相对路径>
```

语义与现有 `GET /api/tasks/{id}/file` 完全一致（同一个 `ReadFile`，同一套错误映射：`ErrPathEscape`→400、`fs.ErrNotExist`→404、`ErrPathIsDir`→400、`ErrNotRegularFile`→400），只是寻址从任务改为工作树。

**为什么要另开而不是改**：`/api/tasks/{id}/file` 是 CLI `handoff fetch` 在用的既有契约，不动。而工作树可以没有任务（人手开的工作树、任务已 done 的工作树），文件浏览不能依赖任务存在。

### 7.3 不做的接口

- 写文件 / 新建 / 删除 —— 下一期
- `git status` —— 见 §4 的理由
- PTY —— 后续期

## 8. 与原型的偏离（四条）

每条都是用户明确裁决的，记录在此以免下次验收时又对不上。

### 8.1 不 attach executor 原生 CLI，改由 handoff 自渲染

原型 AGENTS.md 原文：*handoff is the executor attachment layer. A task opens the executor's native Codex CLI/OpenCode-style TUI; **do not represent handoff itself as a task-table TUI**.*

**这条已作废。** TUI tab 由 handoff 自己渲染（§2.3）。

理由：attach 原生 CLI 要求一条能把远程 TTY 流转成网页的通道，而 handoff 已经有了更结构化的东西——W4a 的 `frames.jsonl` 把回合拆成了带类型的帧，W4b 已经用它渲染出了时间线。自渲染能做原生 CLI 做不到的事（审阅取证、跨任务的工单总账），且不依赖 PTY。

**动作**：需要同步修改 `prototypes/desktop-console/AGENTS.md`，删掉上面那句并记录新决定，否则它会误导下一个读原型的人。

### 8.2 去掉底部 dock

原型右分屏组的编辑器下方有 `终端 | 问题 | 输出 | 调试控制台` 四页签的 dock。

**整个去掉。** 问题 / 输出 / 调试控制台三项不需要（handoff 不是 IDE，没有语言服务器和调试器）。终端改为一种普通 tab（§2.4），从中央 `+` 或悬浮按钮开出，与其它 tab 平级、参与分屏。

理由：去掉三项之后 dock 只剩终端一项，一条横栏承载一个页签是浪费垂直空间；而终端本来就适合作为一个可分屏的 tab。

### 8.3 任务看板改为弹出式

原型：看板作为顶层页**替换中央内容区**，左栏保持可见。

**改为弹出层。** 理由：看板是全局总览，不属于任何目录；替换内容区会把用户当前正在看的 tab 组挤掉，而看板的典型用法是「扫一眼、点进去」，看完就该回到原处。

### 8.4 开发机收进设置页

原型：`开发机` 是与 `任务看板` 并列的顶层导航页。

**收进设置页。** 理由：开发机页的内容是配置性质的（配对、执行者开关、Env、重启 agent），使用频率远低于看板；作为顶层导航占位不划算。

**注意**：开发机在左栏树的第二级仍然出现，那是**导航**（这个项目在哪台机上有落点），与设置页的**管理**是两回事，不冲突。

### 8.6 取消浏览器预览 tab

原型右分屏组里有一个 `◉ localhost:5173` 的预览 tab。

**整个取消，不是推迟。** tab 只有三种：终端、文件、TUI。

理由：预览一个本地端口，用户的真实浏览器做得比嵌一个 iframe 好——有开发者工具、有扩展、有已登录的会话。为它单独造一种 tab，收益低于它在 tab 系统里增加的复杂度（URL 作为身份、跨源限制、导航栏）。真需要时，「在浏览器中打开」是一个链接，不是一种 tab。

### 8.5 一处已知的不一致（不改，记录）

原型 AGENTS.md 有一条硬约束：*A project can never bind more than one remote machine*——一个项目最多绑一台远程机（可另加本地）。

agentd 现在不保证这条：`ProjectNode.Locations` 是数组，可以有多台。**本期不在 UI 里强制**，按实际数据渲染。理由：诚实展示优先——真有两台时藏掉一台比多显示一台危险得多。这条约束该不该落到后端，留给后续裁决。

## 9. 验收标准

1. 打开控制台，左栏能看到 项目 → 开发机 → 目录 → 任务 四级，主目录与工作树平级；断开的机器仍在列并标原因
2. 点一个目录：面包屑变成 `项目 / 开发机 / 目录`，右栏出现该目录的文件树，中央切到该目录的 tab 组
3. 切到另一个目录再切回来：两边的 tab 组各自保持自己的 tab 与激活项
4. 点左栏一个任务：中央开出 TUI tab，里面能看到回合时间线、事件流、底部指令输入框；任务处于 `waiting_review` 时能看到审阅取证并能跑 diff
5. 点右栏一个文件：中央开出文件 tab，能看到内容（只读）；再点同一个文件不重复开
6. 开左右分屏，两组各放一个 tab，切目录时两组一起换
7. 点中央 tab 条的 `+`：开出一个**空白 tab**，中间列出「新终端 / 打开文件 / 打开任务 TUI」三项带快捷键；选一项后该 tab 变成对应内容
8. 点右下角悬浮按钮：弹出同一个选择面板，但**只有「新终端」一项**；开出的终端 tab 标题显示基准目录是 home，不是当前工作树
9. 终端 tab（无论从哪开）：能关、能分屏，内容区是「PTY 后端尚未实现」的说明
10. 左栏底部工单按钮带角标，点开是全局工单列表，能就地批准/拒绝/回答；批准后角标数量下降
11. 点左栏顶部任务看板：弹出四列看板，卡片上的干预态是橙色标记；点一张卡片，弹层关闭并跳到该任务所在目录、开出它的 TUI tab
12. 点设置：能看到开发机列表与详情
13. **形态对照**：与 `implementation-complete-workbench.png` 并排看，左栏 / 面包屑 / 中央分屏 / 右栏文件树 四个区域的位置与层次能对上；差异只应落在 §8 记录的五条上（外加 §8.5 那条已知不一致）

## 10. 风险

- **tab 状态的存储位置**。tab 组按目录分别持有，目录数量可能不少。本期存内存即可（刷新丢失），不做持久化——持久化要处理「目录被删了但 tab 还在」这类失效态，本期不值得。
- **`ProjectTree` 的改造范围**。它同时承担筛选写入与注销入口，改语义时容易误伤。改造前先确认 `filter.ts` 的纯函数不受影响（看板弹出层仍要用）。
- **弹层叠加**。看板与工单都是弹层（设置不是，见 §6），必须保证同时只有一个打开，否则 Esc 关哪个会含糊。
