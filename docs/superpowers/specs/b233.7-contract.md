## 1. 范围与现状查证

本卡冻结以下既有契约面的语义补全：

1. 同一 OpenCode 原生问题再次出现时，新工单仍可答，并保存原生问题身份供回程使用；未答重放继续复用旧工单。
2. OpenCode 原生权限决定经已有审批 client 形成、经 harness 回传；回传失败产生可订阅的 `delivery_failed`，不只写日志。
3. 普通任务把协调者侧的纪律正文交给执行 Profile 的任务层；任务层不覆盖载体全局规则，Verify 检查内容而非只检查文件存在。
4. 任务 diff 消费 `ResultRef.Commit`；无准确 commit 时保持现有按分支的可观察降级。
5. 热加载证明必须来自真实可观察的探测结果；不以恒真探针或与生产无关的假文件名作证明。
6. 载体绑定的物理机器、CLI、HOME 不被请求字段覆盖；B350 竖切与此规则一致。
7. 一元 HTTP 调用不自动重试；失败先查任务状态，再由协调者决定是否重新派发；不提供“重派仍为同一任务”的保证。

## 3. 允许的依赖方向与组装点

本卡沿用现有图面，不增加领域、接口方向或预算：

```text
协调者 / Manager
  ├─→ executor 契约：StartReq、ApprovalClient、AskResponder、RespondPermission、Profile
  └─→ workspace.Capability：assembleResultRef → DiffRange

控制门面 / Server
  └─→ 既有 Manager.Workspace() → workspace.Capability.DiffRange

  └─→ Manager-owned delivery_failed 事实入口（通过现有运行态组装接线）
```

- `ApprovalClient` 的实现仍由 `internal/agentd/approval_client.go#taskApprovalClient` 提供；R3 不把审批逻辑迁到 executor，迁包留给 B233.8。
- `Profile` 的五家实现仍位于各自 executor adapter 包；`internal/agentd/coordinator_home.go`（`coordinatorHomeSupplier.Prepare`）是协调者专用准备路径，当前只填 Rules/Skills，不应被冒充成普通任务的 TaskOverlay 生产调用。
- `ResultRef` 仍归 `internal/workspace`；`handleTaskDiff` 只消费既有 `Manager.Workspace()` 能力，不新增 HTTP 字段。
- 载体物理身份仍归 `internal/scheduling#bindingFor`；B350 只改竖切测试和过时注释，不改该生产函数。
- R8 的说明书与 handoff skill 是文档接缝，不生成新的运行时调用边或重试器。

## 4. 冻结清单

每条均为可独立判定、失败可定位的原子断言。

### 4.1 Ask 身份与回程

1. 已回答后同一原生 `QuestionID` 再次到达时，`handleQuestion` 必须创建不同于已回答工单主键的新工单。
2. 已回答后新建的 Ask 工单必须保持 `Kind == "ask"`。
3. 已回答后新建的 Ask 工单必须能被协调者回答。
4. 已回答后新建的 Ask 工单持久化的 `question_id` 必须等于原生 `QuestionID`。
5. 已回答后新建工单的 `waitQuestion` 必须从持久化原生身份恢复 `QuestionID`。
6. 已回答后新建工单经 `RespondAsk` 回程时必须携带原生 `QuestionID`。
7. 已回答后新建工单经 `RelayAnswer` 自愈回程时必须携带持久化的原生 `QuestionID`。
8. 未回答的同一 `taskID:QuestionID` 重放必须复用已有工单主键。
9. 未回答的同一问题重放不得创建第二张工单。
10. 未回答的同一问题重放不得发布第二条 `question` 事件。
11. 没有原生问题 id 的提问仍可使用一次性 uuid 工单。
12. 没有原生问题 id 的提问回程不得伪造非空 `QuestionID`。

### 4.2 OpenCode 权限投递与失败可见

13. OpenCode 原生权限决定必须经 `executor.Authorize` 消费已绑定的 `ApprovalClient`。
14. OpenCode 原生权限回传必须经 `Adapter.RespondPermission`。
15. OpenCode 原生权限回传失败必须产生 `proto.EventTypeDeliveryFailed`。
16. 原生权限投递失败事件的 `ticket_id` 必须定位到该次权限决定的 `taskID:permissionID` 引用。
17. 原生权限投递失败事件的 `reason` 必须包含实际回传错误并遵守现有 500 rune 截断上限。
18. 原生权限投递失败事件的 `hint` 必须保留现有 resume 处置指引。
19. 原生权限投递失败不得发布 `AckDelivered`。
20. 原生权限投递成功后必须发布 `AckDelivered`。
21. `delivery_failed` 必须被 `WaitDeliveryPolicy` 判定为可交付事件。
22. OpenCode Ask 回程失败与原生权限回传失败必须共用 `Manager.NoteDeliveryFailed` 事实入口。
23. 权限审批 client 的形成/等待/Ack 仍由 `ApprovalClient` 契约承载。
24. 本卡不得新增审批事件名替代 `delivery_failed`。

### 4.3 任务纪律 Overlay

25. 普通任务执行启动必须向 Profile 传入非空任务纪律时的 `ProfileReq.TaskOverlay`。
26. 任务纪律正文必须逐字节成为对应任务层 `ProfileFile.Content`。
27. TaskOverlay 必须写入 `HomeDir/.handoff/task-overlay/`。
28. TaskOverlay 不得写入五家 Profile 的全局 `RulesRelFile` 落点。
29. 任务层与全局规则同名时，全局规则文件内容必须保持不变。
30. `Profile.Verify` 必须检查任务层文件内容，而非只检查全局规则文件存在。
31. 任务层文件缺失时，`Profile.Verify` 不得返回 `Verified == true`。
32. 任务层文件内容不符时，`Profile.Verify` 不得返回 `Verified == true`。
33. 五家 Profile 对本卡任务层语义必须使用各自已存在的 `Profile` 接口。
34. `coordinatorHomeSupplier.Prepare` 的协调者专用 Rules/Skills 供给不得被当作普通任务 TaskOverlay 已接线的证据。

### 4.4 结果引用消费

35. `handleTaskDiff` 必须保留 `assembleResultRef` 返回的 `workspace.ResultRef`。
36. `ResultRef.Commit` 非空时，`handleTaskDiff` 传给 `Capability.DiffRange` 的 head 必须等于该 commit。
37. `ResultRef.Commit` 为空时，`handleTaskDiff` 必须保留原 `headRev` 降级路径。
38. ResultRef 降级到原 `headRev` 时必须有可观察日志。
39. `GET /api/tasks/{id}/diff` 的对外响应不得新增 ResultRef 字段。
40. `ResultRef.Path` 为空不得阻止准确 commit 被用于 diff。

### 4.5 探测、物理身份与 R8 文档边界

41. `WakeHome` 的 ready 证明必须来自检测回合的实际输出。
42. 仅有凭据文件不得单独证明 `WakeHome` ready。
43. 探测测试不得以恒真 `reloadProbe` 作为热加载成功证明。
44. Overlay 不覆盖全局规则的测试必须使用生产规则文件名，而非 `task-1.md` 这类另名文件。
45. 载体 CLI 为 `opencode` 且请求 `Executor` 为 `claude` 时，`bindingFor` 产出的 `Binding.Executor` 必须为 `opencode`。
46. 载体绑定的 `Binding.Target` 必须来自载体物理身份。
47. 载体绑定的 `Binding.HomeDir` 必须来自载体物理身份。
48. B350 竖切不得再断言请求 `Executor` 覆盖载体 CLI。
49. 一元 OpenCode HTTP 调用不得自动重试。
50. R8 文档必须说明网络失败后先查任务状态。
51. R8 文档不得承诺重新派发仍对应同一远端任务。
52. R7 跨机真机验证不在本卡 acceptance 内。

## 5. 可执行冻结、三重闸门与迁移边界

本卡无新增哈希、密钥派生或跨实现编码格式，因此无新增金样本向量。`ResultRef.Commit` 的 40 位小写 hex 约束是既有 `internal/workspace#NewResultRef` 事实，本卡只冻结消费它，不重新定义编码。

### 5.2 三重闸门拍板记录

本节点无新增三重闸门命中；R6、R7、R8 的取舍已由获批源 spec 与 `docs/superpowers/ledgers/2026-09-08-b233.7-spec-ledger.md` 记录，本契约只将其翻译为可核对断言。特别是“不做派发认重/幂等重试”“审批 client 不迁出 agentd”“跨机真机延后统一验收”均不在本节点重新拍板。

### 5.3 Out of scope

- 不做派发幂等键、服务端去重或 client 重试器。
- 不把审批 client 从 agentd 迁到 executor 或其它包。
- 不做本卡单独的跨机真机验收；跨机 Ask/审批留统一收尾闸。
- 不修改 `bindingFor` 的生产语义。
