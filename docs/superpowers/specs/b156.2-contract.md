## 2. 架构户口与依赖方向

### 2.1 立户口（best.json 随本提交冻结）

- 新增顶层域 **`d_collab`**（label 协作房间，type logic）：Room/成员投影/消息播发/未读与消费游标的规则所有者。responsibility 一行写明与 d_sessions 的区分。
- 新增容器：`k_collab_Service`（入站门面 Service）、`k_collab_client`（出站 client 接口包）、`k_ledger_api`（账本薄门面包 internal/ledger/api，归 d_ledger）、`k_web_api_rooms` + `k_web_api_rooms_model`（TS 契约层镜像，归 d_web_contract）。
- 架构形态声明：本仓为存量图，分层形态沿 best.json 现状（顶层域平铺 + boundary/logic 标注）；d_collab 以 logic 型顶层域加入，不引入新的分层概念。

### 2.2 双向门面（架构法第四条第 3 档，法定用档）

- **入站 api**：`internal/collab`（package collab）。外界（gateway、CLI）只 import 此包 + proto DTO；不得深入其内部文件。Go 的 `internal/` 可见性只在跨 module 边界执法，仓内穿透由 `graph check` 硬闸执法（见 §2.3）。
- **出站 client**：`internal/collab/client`（package client）。所需外部能力的接口**定义在会话侧**（`client.LedgerClient`，注释标注测试缝）；具体实现 `internal/ledger/api.Facade` 在组装点（main.go / internal/agentd/server.go，均已在 target.json assembly 登记）构造注入；组装点之外不得 new 他方具体类型。
- **还债路径**：本期只为 d_ledger 建薄门面 `internal/ledger/api`（包住既有 `*ledger.Store`，不改其内部）；d_orchestration 的工单能力本期不被 collab 直连（收件箱组装在控制面，见 §3.6），无需建门面。

### 2.3 target.json 契约面（随本提交冻结）

**本轮已声明且已有活跃边背书的三条**（`graph check --view cards-B156.2-charter-2` fails 空为证）：

### 2.4 执行域零新增依赖

executor 不认识房间：消息事件走 card_events 单流，而 Follow 只投喂子树成员卡的卡级事件（§1.1 第 4 行）；群级消息一律无卡事件，物理上进不了任何执行会话的等待流。账本/会话凭据仍物理隔离在协调机，本期不动。

## 3. 契约增量

### 3.1 账本事件词表增量（types.go 词表随本提交扩展）

新增两个事件类型常量（落 `internal/ledger/types.go` 既有事件常量块）：

```go
// 房间消息（协作房间域的唯一内容事件；kind 受控词表见 proto.RoomMsgKind*）。
// 卡会话消息 CardID=卡号；项目群/全员群消息 CardID=""（无卡事件，
// 天然不进多路 wait——follow.go 现状语义，executor 零感知）。
EvRoomMessage = "room_message"

// 房间消息被恰好一次消费的落账标记（谁、消费了哪条）。消费判定在账本
// 同一事务内查后写（照 ClearNeedsHumanFrom 同形），权威在此事件的存在性。
EvMessageConsumed = "message_consumed"
```

消息载荷 schema 定义在 proto（wire 唯一定义处），ledger 不解释字段：

```go
// internal/proto/rooms.go —— internal/proto/rooms.go#RoomMessage（本分支视图）
type RoomMessage struct {
    Room       string   `json:"room"`      // 卡号 | project:<name> | global
    Kind       string   `json:"kind"`      // 受控词表，见下方 RoomMsgKind*
    Body       string   `json:"body"`
    Refs       []string `json:"refs,omitempty"`        // 引用锚：git 路径 / timeline 锚 / 卡号 / 附件路径
    Mentions   []string `json:"mentions,omitempty"`    // @成员：卡号（=该卡协调者）或用户标识
    DecisionID int64    `json:"decision_id,omitempty"` // 简报挂的裁决 id（kind=escalation 时应非零）
    BySystem   bool     `json:"by_system,omitempty"`   // true=系统组件书写的指针行
}

// kind 受控词表（白名单制，不在单上的 kind 拒收）
const (
    RoomMsgEscalation = "escalation" // 推翻级简报（六段正文进 Body，选项挂 DecisionID）
    RoomMsgDeviation  = "deviation"  // 填补级偏差叙事
    RoomMsgClosing    = "closing"    // 收口摘要（四段+子卡汇总）
    RoomMsgRelay      = "relay"      // 父卡衔接消息（父协调者以成员身份书写）
    RoomMsgReply      = "reply"      // 协调者对用户发言的对话式应答
    RoomMsgUser       = "user"       // 用户发言
    RoomMsgPointer    = "pointer"    // 薄里程碑指针行（仅系统组件，HTTP 面不可达）
)
```

裁决答复**不另发 room_message**：用户点击选项直接走既有 AnswerDecision 落 decision_answered；房间面对答复的渲染从 decision_answered 事件投影。否则同一事实两处落账，必漂移。

### 3.2 绑定与心跳（权威位置裁决 → 账本域卡上）

**裁决：绑定权威在账本域卡上；心跳（活性租约）权威在账本域新表。会话子系统只持投影。**

判据（架构法第五条：谁拥有这份数据谁写规则）：

1. 绑定回答的第一问题是「谁的会话在驱动这张卡」，第一消费者是**派发前置校验与派发即认领**——那是账本域的单事务路径；move.go:23-25 明文警告认领与移列拆两次写会留窗口。绑定若挪去会话侧，每次派发都要跨域两写，窗口成为必然。
2. spec §4 原文「**绑定落卡**（session 标识 + 载体类型）」。§8.1 把权威存放位置显式留给 contract 裁决，本裁决与 §4 字面一致。
3. 换绑 CAS「与派发即认领同源」只有在对**同一份存储**执法时才成立；两个真相源必然漂移。
4. 心跳沿用 driver lease 机制=运行锁已验证的租期/续租/过期模式（runlock.go 全套）；但**不复用 card_run_locks 表**——那是运行尺度（每轮编排一行、holder=运行实例），绑定的活性是人尺度会话的，混用会破坏 runlock.go 文件头「两锁互不代写」的边界。新表独立。

签名增量（Ticket 0 空壳，除注明外；符号锚 `internal/ledger/binding.go#Store.RebindDriver` 等，`codegraph resolve --view cards-B156.2-charter-2` 可决议）：

### 3.6 收件箱聚合（控制面编排单元）

`GET /api/inbox` 由 gateway 编排三源，响应形状：

```go

    Origin  string          `json:"origin"`          // decision | ticket | mention
    Title   string          `json:"title"`
    CardID  string          `json:"card_id,omitempty"`
    RefID   string          `json:"ref_id"`          // decision id / ticket id / message seq 的十进制字符串形

    InboxOriginDecision = "decision"
    InboxOriginTicket   = "ticket"
    InboxOriginMention  = "mention"
)
```

三源判据（冻结）：
1. **decision**：ListDecisions(openOnly=true) 全量（项目级与卡级都在内；简报六段正文经 room_message 关联查询补齐）。
2. **ticket**：处于等待人工输入态的任务上的未答复工单，且 `Hub.Watchers(taskID)==0`（无人驱动的可操作判据）；破坏性工单不受 Watchers 条件约束、一律上浮（既有硬纪律不变）。Watchers 是进程内快照、agentd 重启后短暂归零会造成误上浮，接受此代价（拍板 5.4 附注）。
3. **mention**：collab.Mentions(用户标识) 的未消费提及。

编排代码落在 gateway 层（跨 d_ledger/d_orchestration/d_collab 三源的用例编排，spec §8.1 第六条指定位置），不进 collab 也不进 ledger。「有终态无裁决事件」的中间态处置见 §3.7。

### 3.7 环节执行体幂等补解析（ledgerstep 缝，spec §8.1 指定归 contract）

## 5. 拍板记录（三重闸门命中）

### 5.1 绑定与心跳的权威在账本域，会话侧只持投影

难逆转：绑定存储位置牵动账本事务、派发校验、房间写权、看板显示四处。无上下文会惊讶：后人看到房间子系统居然不存「谁是房间主人」会想把它搬回会话侧。真取舍：被否方案是「绑定席位作为会话侧自有表、卡上 driver_session 降为兼容投影」——它更符合 §8.1 第一句的字面分组，但要求派发路径跨域两写，撞 move.go:23-25 明文警告的事务窗口，且换绑 CAS 变成对两个真相源的先后校验。判据落第五条：这份数据回答的问题是「这张卡被谁驱动」，第一消费者是账本的派发事务，所以归账本。spec §4「绑定落卡」原文与本裁决一致；§8.1 把位置留给 contract 正是为消解两句间的表面张力。

### 5.2 消息=单一事件类型 room_message + 受控 kind 词表

难逆转：事件类型进 types.go 受控词表后被 timeline 渲染、wait、三期规则引擎消费，加类型容易改类型难。无上下文会惊讶：后人看到七种消息共用一个事件类型可能想拆成七种便于 SQL 过滤。真取舍：被否方案是七事件类型各给常量——SQL 端过滤更省事，但白名单、书写者、消费游标逻辑要在七个类型上重复展开，且未来新增消息形态（三期自动拉起通知等）又要动词表。kind 收在载荷里让「白名单制」成为单一检查点；消费方按需解码 payload。反过来写（七类型）不会有测试立刻变红，故记录于此。

### 5.3 房间读面走 REST 轮询，不新增 WS 推送通道

难逆转：推送通道一旦建立，收件箱、列表、房间页都会长在上面，回收困难。无上下文会惊讶：「IM 面竟然没有实时推送」会显得像缺陷。真取舍：被否方案是给 /ws/events 加账本事件旁路或开 /ws/rooms——但既有卡片时间线就是 REST+usePoll 轮询形态，账本事件到达浏览器从未有过推通道；单人使用下轮询延迟无感，而新通道要把 Hub（taskID 键控）改造或平行复制一套扇出，爆炸半径远超本期。群消息不打扰 wait 已由 Follow 的项目级排除保证，实时性收益只剩人面前的秒级刷新。

### 5.4 消费恰好一次的权威在账本 message_consumed 事件，会话侧游标降为纯缓存

难逆转：消费判定决定留言是否会丢/重，牵动 Pending、Consume、重建纪律三方。无上下文会惊讶：后人会想「游标当然存会话子系统」并把账本标记当成冗余。真取舍：被否方案是 collab 自持游标表做 exactly-once、账本不留痕——但消息事实在账本、游标在会话侧，跨存储无法同事务，协调者崩溃窗口必产双消费或丢失；且「凡承重的必须落账」（§6.3）直接否掉账外游标承重。照 ClearNeedsHumanFrom 同形在账本事务内查后写，恰好一次由单写者串行化免费获得。附注：ticket 上浮用的 Watchers 是进程内快照、重启后短暂归零，误上浮代价被接受（修复属三期活性基建，不在本期）。

### 5.5 父协调者的写入权仅及直接父卡一级

难逆转：写权矩阵是白名单执法的核心分支，放宽要动 Send 判定与其全部测试。无上下文会惊讶：看到 relay 只查一层父卡会有人提议「沿父链整链传递更完备」。真取舍：被否方案是祖先链全传递——epic 套 epic 时曾祖协调者获得重孙房间的叙事权，「流程性加入」从最小授权变成链式扩散。spec 原文「流程性加入只有父子这一种」按最窄读法执行：一级。跨层沟通走项目群 @，与用户故事 6 一致。
