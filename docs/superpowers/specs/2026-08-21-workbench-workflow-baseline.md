## 1. 入口纪律：建卡不预判形态

一件事被记下来的那一刻，往往还不知道它是什么（是 bug 还是需求？涉及几个域？）。
**强迫建卡人当场选对流程，等于把定性错误固化成流程错误**——你会得到一张走在
bug 流上的跨域改造，或一张走在重流程上的一行小修。

因此入口规则：

- **缺省建卡不预设工作流**：handoff 出厂不预设任何流；不指定 `--workflow` 时按账本
  流数量三态解析：零条报错指路、唯一条自动采用、多条要求显式指定并列出可选流名。
  建卡人只写标题、项目、优先级——和往 backlog 记一行的成本一样。
- **形态已明确时允许直建**到已安装的目标流（明知是小 bug 就直接建 `bug` 卡）。
  `triage` 等流如仍需使用，须先由用户自行安装。

## 2. 三级流程梯度

按「触及域数 × 是否动契约」分级，向上兼容、按需升级：

> **2026-08-22 修订（B174）**：L2/L3 统一收敛到单条 `charter` 流——L2 是 L3 的子集
> （L3 = contract/breakdown 的头 + N 个 L2 形状子卡 + integrate 的尾），条件边一期用
> 人工 move 表达，门（plan 列要 spec 附件、implement 列要 plan 附件）作结构性执法。
> `feature`/`domain` 流被 charter 流吸收，退役出日常（定义保留不删）。下表为修订后形态。

| 级 | 工作流 | 适用 | 形态 | 现状 |
|---|---|---|---|---|
| L1 | `bug` | 单域小修，根因明确，不动契约 | 待办 → 进行中(派发实现) → 待审阅(裁决) → 已完成 | 🧩 需自行安装 |
| L2 | `charter`（跳列） | 单域功能，需要 spec，不动跨域契约 | spec ─跳→ plan(闸:spec) → implement(闸:plan) → review → acceptance ─跳→ finish | ✅ charter v2 |
| L3·轻 | `charter`（顺链不扇出） | 跨域协作，但**每域改动浅**（加个方法/端点/字段） | spec → contract → breakdown → **单轮** plan/implement/review → acceptance ─跳→ finish | ✅ charter v2 |
| L3·重 | `charter`（扇出子卡） | 跨域协作，且**单域工作量大到一个执行者一轮装不下** | spec → contract → breakdown ─跳→ integrate 等聚合闸；子卡各从 plan 起步跑到 review | ✅ charter v2 + split/聚合闸 |
| — | ~~`feature`~~ / ~~`domain`~~ | 已被 charter 流吸收（B174），定义保留、日常不用 | — | 🗄️ 退役 |

判级判据（定性节点回答两个问题即可定级）：

1. 触及几个大领域？——1 个 → L1/L2；≥2 个 → L3。
2. 要不要改契约层（域的 `api/`/接口/共享数据结构）？——要 → 至少 L2，跨域 → L3。
3. **定 L3 之后再问一次：单域工作量是否超过固定成本（拆解+契约+集成，约 1 小时量级）？**
   超过 → L3·重（扇出）；不超过 → L3·轻（不扇出，单轮实现）。
   依据：协议成本随域数量固定、收益随域内深度增长，B167 实测「宽而浅」时扇出赢不回
   协调开销（分域协议 spec §7.-1 与 §12.3）。**两档共享前半段（拆解 + 契约冻结），
   差别只在扇不扇出——轻档不等于跳过契约冻结。**

## 3. 升降级：跨流迁移的三个基准场景

这是本档的核心对标点。卡的形态判断**允许错、允许改**，纠错动作是**跨流迁移**，
不是关卡重建（重建会丢事件流与关系边，审计链断裂）。

**场景 A（升级）**：建卡时以为是 bug，走 L1 到「进行中」，根因排查发现要动三个
域的契约 → 迁移到 L3 分域流，落点「拆解/契约冻结」列。排查产出（timeline 里的
根因记录）随卡带走，成为拆解节点的输入。

**场景 B（降级）**：L2 feature 卡走到「已出spec」，spec 写完发现就是个一行修
→ 迁移到 L1 bug 流，落点「进行中」。spec 附件仍挂在卡上，审阅有据可查。

**场景 C（平级直通）**：单域小功能改进 → 直建 L2（或明确不需要 spec 时直建 L1），
全程不迁移。**大多数卡应该走场景 C**——迁移是纠错通道，不是常规路径；如果
大量卡在频繁迁移，说明定性判据（§2）出了问题，先修判据。

### 迁移语义（引擎落地时按此验收）

1. **显式落点**：迁移必须同时指定目标流与落点列，不做「自动映射到同名列」的
   猜测——猜错列比多敲一个参数贵得多。
2. **防悬空**：落点列必须存在于目标流钉住的版本中（现 `MigrateCardWorkflow`
   的校验逻辑平移）。
3. **事件留痕**：timeline 落一条迁移事件（从哪条流哪列 → 哪条流哪列、操作者），
   审计链能回答「这张卡为什么换了流程」。
4. **在飞环节先收口**：卡有环节在跑（派发中/等裁决）时拒绝迁移——先等回合
   结束或 stop，避免旧流的裁决回写到新流的列上。
5. **子卡不随迁**：父卡换流不影响子卡各自的工作流；聚合闸语义（等全部子卡
   完结）与父卡在哪条流上无关。

## 4. 全程串起来（预期终态的一天）

```
记下一件事 ── 建卡(按账本流数量解析) ──→ 定性：单域小修？ ──→ 迁 L1 → 派发 → 审 → 完
                                │  单域功能？   ──→ 迁 L2 → spec → 派发 → 审 → 合 → 完
                                │  跨域协作？   ──→ 迁 L3 → 拆解/契约(Decision)
                                │                        → 扇出域子卡(并行,各走 L1/L2 级子流)
                                │                        → 聚合闸 → 集成 → 终审 → 完
                                └─ 形态早已明确 ──→ 直建对应流（场景 C，多数路径）
中途发现判错级 ──→ 跨流迁移（场景 A/B），事件留痕，审计链不断
```

## 5. 节点归属：什么留主会话，什么归执行者

> 2026-08-21 补入。将来 L3 模板落地时，节点的执行者绑定直接照本节配；
> 与派发决策表（全局 CLAUDE.md §4）冲突时以本节为准——本节是它在 L3 场景下的修订。

### 归属判据（四条，新环节先过判据再进表）

1. **对话回路**：需要与用户多轮往返才能定的（定性、契约拍板、验收标准）→ 主会话。
2. **裁决与不可逆**：并入主线、`done` 收口、破坏性审批 → 主会话；不可逆的升级给用户。
3. **上下文经济**：活在谁的上下文里最便宜就归谁——域内实现细节归域执行者，
   跨域全局观归「主会话 + 契约层」。
4. **自指**：驱动 handoff 自身的操作（派子卡、调 CLI、起 agentd）→ 主会话
   （纪律块硬约束，B105 实测教训）。

### L3 分域流节点归属表

| 节点 | 归属 | 依据 |
|---|---|---|
| 定性（按已安装工作流） | 主会话 | 判据 1 |
| 拆解：域清单 + 契约草案 + **缺陷族对抗审查初稿** | 执行者（可派） | 机械收集与逐族设问，出稿便宜 |
| 拆解：**审查初稿的把关 + 契约拍板** | 主会话 + 用户 | 判据 1、2——契约错了全域返工 |
| Ticket 0 骨架 commit | 执行者 | 契约已定，落码机械 |
| 域子卡 plan 编写 | **域执行者自写** | 判据 3，见下方明示的规则改变 |
| 域子卡 plan 审核 | 主会话 | 只审契约符合性 + 判据在基线可跑 |
| 域子卡执行 | 域执行者 | 扇出的意义所在 |
| 域卡代码审查 | 执行者纪律块自审 + 主会话抽查 diff | |
| 聚合闸后的集成卡 | 执行者 | 合分支、跑全量、修接缝 |
| 集成结果并入主线 | 主会话裁决 | 判据 2，既有硬规则 |
| 终审 + 验收走查 | 主会话 | 实战证据：wire 缺陷是验收走查抓到的，两侧测试全绿都没抓到 |
| 域文档写回 | 域执行者写、主会话审 | 写的人有上下文，审的人防漂移 |
| 破坏性/不可逆审批 | 用户 | 判据 2，既有硬规则 |

**「出稿」与「拍板」的分界**（2026-08-21 统一措辞）：缺陷族对抗审查与契约增量同构——
**执行者逐族设问并写出结论草案，主会话判断「这份审查够不够、漏没漏族」并拍板**。
早先本表把整个对抗审查划给主会话，而 `domain-breakdown` 模板要求执行者做，
两处矛盾；现按可行语义统一，模板措辞已同步修改。

L1/L2 归属简单：L1 根因排查派 grok（小修顺手、架构级回主会话定性换流，§3 场景 A）；
L2 的 plan 谁写都行（单域上下文小），执行派 codex，验收留主会话。

### 明示的规则改变：L3 域 plan 下放执行者写

现行全局规则是「本地 writing-plans → 派发执行」。**L3 场景下这条被修订**：主会话
替 N 个域写 plan 就得拉进 N 个域的内部上下文，扇出白扇。故 **plan 编写权下放、
审核权上收**——域执行者依契约 + 域文档自写 plan（含在基线跑通判据，见
`plan-criteria-must-be-verified-on-baseline` 教训），主会话只审「是否越出契约、
判据能否在基线跑通」，不审实现细节。

### 主会话角色终态

契约守门人 + 裁决者：写的是拆解意见、审核结论、裁决；读的从「全量代码」收敛到
「契约 + diff + 判据」。主会话上下文消耗从 O(代码量) 降到 O(契约 + diff)。

## 6. 现状与缺口清单（对标用）

| 项 | 现状 | 缺口/去向 |
|---|---|---|
| 建卡可后定形态 | ✅ 建卡不给 workflow 即按账本流数量三态解析（零条报错指路、唯一条自动采用、多条要求显式指定） | — |
| 跨流迁移 | ✅ 五条语义全部落地并真机验收（B167） | — |
| L1/L2 流 | 🧩 `bug`/`feature` 等目标流需自行安装 | — |
| L3 分域流模板 | 🧩 domain 流与三模板需自行安装（domain-breakdown/ticket0/integration） | 分域协议 spec §8.1 |
| 子卡扇出/聚合闸/递归护栏 | ✅ 已合入 | — |
| 定性判据进 prompt | ❌ | 用户如安装定性流并加派发节点（AI 辅助定性），判据 §2 进模板；先人工定性跑通再说 |

**B167 已完成**（08-21，分域开发协议的首次试点载体，尖端 `460ea2bce`）。两半均已落地：
①建卡不指定流即落 `triage`（**该行为已于 2026-08-24 被 B230 改为按账本流数量三态解析**，
此处保留 B167 当时的原文——它记的是那一天的事实，不是现行口径）；
②跨流迁移，§3 五条语义逐条验收通过。

真机验收的承重判据是**双通道一致性**：同一张有 running 任务的卡，HTTP 与 CLI 各迁一次，
**两者报同一条错、指向同一 task id、措辞一字不差**。它证明的是契约拍板那个决定——
在飞门禁从镜像/派发事件派生并下沉到 Store 事务内，因此两个入口共享同一道门。
（此前 CLI 直连账本，根本看不见 agentd 进程内的在飞态。）

同一轮验收还抓到一个**全链路测试全绿的致命缺陷**：在飞判定原本只扫镜像事件，
而刚派出去的任务零镜像事件 → 门禁静默失效。根因是 plan 的测试夹具假设 `dispatched`
走镜像（实为账本原生事件）。教训写进分域协议 spec §11：**API 事实可静态核验，
行为事实不能**；顺序固定为复跑 → 变异 → 真机 → 才归档。

## 7. 对标验收（全部落地后走查）

- 三个场景 A/B/C 各真实走一遍，timeline 审计链完整、无重建卡；
- 一张 L3 卡全程：拆解 Decision 留痕 → 扇出 N 子卡并行 → 聚合闸拦截/放行各一次
  → 集成 → 终审归档；
- 一张误判卡在「有环节在飞」时迁移被拒，收口后迁移成功。✅ **已验**（B167 真机）；
  并加验**双通道一致性**：HTTP 与 CLI 对同一张在飞卡报同一条错。
- L3 两档各走一遍：轻档（不扇出，单轮实现）与重档（完整扇出），
  对照 §2 判据 3 确认选档没选反。轻档已验（B167）；**重档待一个「宽而深」的需求**。
