# 工作台工作流基准：卡的入口、定性与三级流程梯度

> 2026-08-21 与分域开发协议（`2026-08-21-domain-partitioned-dev-protocol-design.md`）
> 同日定稿，作为**对标基准**：描述卡从「记下一件事」到「归档」的预期全程形态。
> 将来引擎能力与模板逐个落地时，逐条对照本档验收；与实际使用发生偏差时，
> 先改本档再改实现——基准漂移比实现偏差更贵。

---

## 1. 入口纪律：建卡不预判形态

一件事被记下来的那一刻，往往还不知道它是什么（是 bug 还是需求？涉及几个域？）。
**强迫建卡人当场选对流程，等于把定性错误固化成流程错误**——你会得到一张走在
bug 流上的跨域改造，或一张走在重流程上的一行小修。

因此入口规则：

- **缺省建到 `triage` 定性流**（纯人工三列：`待办 → 定性中 → 已定性`，无派发
  节点；它是数据不是代码，控制台即可建）。建卡人只写标题、项目、优先级——
  和往 backlog 记一行的成本一样。
- **形态已明确时允许直建**到目标流（明知是小 bug 就直接建 `bug` 卡）。triage
  是缺省不是强制，别把它变成所有卡的过路税。

## 2. 三级流程梯度

按「触及域数 × 是否动契约」分级，向上兼容、按需升级：

| 级 | 工作流 | 适用 | 形态 | 现状 |
|---|---|---|---|---|
| L1 | `bug` | 单域小修，根因明确，不动契约 | 待办 → 进行中(派发实现) → 待审阅(裁决) → 已完成 | ✅ 出厂已有 |
| L2 | `feature` | 单域功能，需要 spec，不动跨域契约 | 待办 → 已出spec(闸:spec 附件) → 进行中(派发) → 待审阅(裁决) → 待合并(人工门) → 已完成 | ✅ 出厂已有 |
| L3 | `分域开发` | 跨域协作，需契约变更与拆解 | 拆解/契约冻结(Decision) → 域实现(扇出子卡) → 集成 → 终审 | 🔨 协议 spec §8.1，模板待落地 |

判级判据（定性节点回答两个问题即可定级）：

1. 触及几个大领域？——1 个 → L1/L2；≥2 个 → L3。
2. 要不要改契约层（域的 `api/`/接口/共享数据结构）？——要 → 至少 L2，跨域 → L3。

## 3. 升降级：跨流迁移的三个基准场景

这是本档的核心对标点。卡的形态判断**允许错、允许改**，纠错动作是**跨流迁移**，
不是关卡重建（重建会丢事件流与关系边，审计链断裂）。

**场景 A（升级）**：建卡时以为是 bug，走 L1 到「进行中」，根因排查发现要动三个
域的契约 → 迁移到 L3 分域流，落点「拆解/契约冻结」列。排查产出（timeline 里的
根因记录）随卡带走，成为拆解节点的输入。

**场景 B（降级）**：L2 feature 卡走到「已出spec」，spec 写完发现就是个一行修
→ 迁移到 L1 bug 流，落点「进行中」。spec 附件仍挂在卡上，审阅有据可查。

**场景 C（平级直通）**：单域小功能改进 → 直建 L2（或明确不需要 spec 时直建 L1），
全程不迁移。**大多数卡应该走场景 C**——迁移是纠错通道，不是常规路径；如果
大量卡在频繁迁移，说明定性判据（§2）出了问题，先修判据。

### 迁移语义（引擎落地时按此验收）

1. **显式落点**：迁移必须同时指定目标流与落点列，不做「自动映射到同名列」的
   猜测——猜错列比多敲一个参数贵得多。
2. **防悬空**：落点列必须存在于目标流钉住的版本中（现 `MigrateCardWorkflow`
   的校验逻辑平移）。
3. **事件留痕**：timeline 落一条迁移事件（从哪条流哪列 → 哪条流哪列、操作者），
   审计链能回答「这张卡为什么换了流程」。
4. **在飞环节先收口**：卡有环节在跑（派发中/等裁决）时拒绝迁移——先等回合
   结束或 stop，避免旧流的裁决回写到新流的列上。
5. **子卡不随迁**：父卡换流不影响子卡各自的工作流；聚合闸语义（等全部子卡
   完结）与父卡在哪条流上无关。

## 4. 全程串起来（预期终态的一天）

```
记下一件事 ── 建卡(triage) ──→ 定性：单域小修？ ──→ 迁 L1 → 派发 → 审 → 完
                                │  单域功能？   ──→ 迁 L2 → spec → 派发 → 审 → 合 → 完
                                │  跨域协作？   ──→ 迁 L3 → 拆解/契约(Decision)
                                │                        → 扇出域子卡(并行,各走 L1/L2 级子流)
                                │                        → 聚合闸 → 集成 → 终审 → 完
                                └─ 形态早已明确 ──→ 直建对应流（场景 C，多数路径）
中途发现判错级 ──→ 跨流迁移（场景 A/B），事件留痕，审计链不断
```

## 5. 现状与缺口清单（对标用）

| 项 | 现状 | 缺口/去向 |
|---|---|---|
| 建卡可后定形态 | ❌ 必须指定流（CLI 缺省 feature） | `triage` 流用控制台建（**纯数据，零代码**）；CLI/控制台缺省值改为 triage 可后续再议 |
| 跨流迁移 | ❌ `MigrateCardWorkflow` 只换版本不换流 | **新 backlog 条目**：放开 workflow name + 显式落点列 + §3 五条语义 |
| L1/L2 流 | ✅ 出厂 `bug`/`feature` | — |
| L3 分域流模板 | ❌ | 分域协议 spec §8.1，依赖子卡扇出（已派发实现中） |
| 子卡扇出/聚合闸/递归护栏 | 🔨 实现中（linux-01 任务 `card-fanout-aggregation`） | 按其 plan 验收 |
| 定性判据进 prompt | ❌ | triage 流如加派发节点（AI 辅助定性），判据 §2 进模板；先人工定性跑通再说 |

**建议新记的 backlog 条目**（取号按汇流点纪律，由协调者记）：
1. 跨流迁移：`MigrateCardWorkflow` 支持换 workflow name，按 §3 五条语义验收；
2. `triage` 定性流入库为出厂默认（连带评估建卡缺省值是否改为 triage）。

## 6. 对标验收（全部落地后走查）

- 三个场景 A/B/C 各真实走一遍，timeline 审计链完整、无重建卡；
- 一张 L3 卡全程：拆解 Decision 留痕 → 扇出 N 子卡并行 → 聚合闸拦截/放行各一次
  → 集成 → 终审归档；
- 一张误判卡在「有环节在飞」时迁移被拒，收口后迁移成功。
