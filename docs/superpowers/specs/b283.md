## 问题陈述

谁：多机器池（本机 + mac-02 + linux-01）上每天开关桌面端的用户。
通道：桌面端打开 → 控制台恢复流程（`useWorkbenchSync` 拉落盘快照 + `scope=all` 会话扇出 → `buildRestore` 合成）→ 悬浮窗 tab。
要变的事实：**连续多次打开桌面端之间，悬浮窗（与中央区）的终端 tab 数不得增长**；某台机器暂时离线时打开桌面端，它名下的终端 tab 不得被悄悄换成新 shell；一台机器上开的 home 终端不得出现在另一台机器的悬浮窗里。

### 根因链（排查结论，证据见台账与卡 note）

1. **误判死亡的唯一现实来源是扇出缺席**。PTY 会话由独立宿主进程 ptyhost 持有，跨 agentd 重启存活（`internal/agentd/ptyreclaim.go:10`：不参与崩溃/升级重启；`internal/ptyhost/survive_test.go`：agentd 客户端整体消失再回来，会话与滚屏都在）。会话真正消失只有三条路：机器重启、shell 退出、显式 `service stop`。但恢复时的会话列表来自 `scope=all` 现场扇出，单台机器失败**静默缺名单**（`internal/agentd/pty_api.go:186` 起，失败只进 machines 行的 error 与日志——本机 agentd.log 有 114 条扇出失败），缺席的活会话被恢复层当成死的。
2. **剥引用**：不在列表里的 sessionId 被 `pruneDeadDockSessions`（`web/src/app/homedock/dockPersist.ts:133`）与 `pruneDeadSessions`（`web/src/app/workbench/persist.ts:203`）剥掉，tab 留位。
3. **静默自建**：悬浮窗一开，无 sessionId 的 tab 挂载即自建新会话（`web/src/app/workbench/TerminalTab.tsx:379`）。旧会话在 ptyhost 存活设计下必然还活着，成为永久孤儿（无空闲回收）。
4. **跨机收编累积**：恢复 ③ 把「活着但快照没引用」的 home 会话收进悬浮窗（`web/src/app/workbench/restore.ts:196` 起），**不限机器**——mac-02 的 home 终端被收进本机悬浮窗，tab 只增不减。多机互收编进一步放大。

真机证据：本机 dock 快照 4 个 tab 全为收编形状（id==sessionId、machine=mac-02、seq 1..4 递增）；这 4 个会话建于 2026-08-28 11:17:57 的 41ms 内、pid 连号——一次挂载风暴。红色回路 `web/src/app/workbench/b283-redloop.test.ts`：两次打开 tab 数 1→2，红。

### 设计边界（用户裁决，2026-08-28）

- **悬浮窗是本机面**：home 终端不跨机器同步。mac-02 上开的 home 终端归 mac-02 的悬浮窗。
- **中央区是同步面**：工作台 tab 布局跨机同步照旧（2026-08-20 状态同步 spec 的既有决定），外来 workspace 会话的收编语义不变。

### 现状读数（消歧用，contract 节点复核）

- 快照本身已是机器本地：每台机器的 agentd 各存各的 workbench state，控制台连谁就用谁的那份。跨机泄漏只发生在会话收编，不在快照存储。
- `PtySessionsResp.machines` 已在 wire 与前端类型上（`web/src/api/types.ts:728-731`，`?scope=all` 时出现；wire 侧 `internal/proto/pty.go:42`、契约夹具 `web/src/api/testdata/PtySessionsResp.json` 同证）；本机行恒 `ok=true`（`internal/agentd/pty_api.go:189`）。workbench 侧终端 tab 的 TabContent 没有 machine 字段（`persist.ts:64` 形状），悬浮窗 HomeTab 有（`dockPersist.ts:97` 强制 string）——门控的机器归属来源因此两处不同（见方案 3）。
- 悬浮窗终端 tab 的 `machine` 修复后恒为本机（空串）：新建走 `newTerminal()` 不带机器，收编仅限本机后外来 tab 被清（见方案）。`Shell.tsx:610` 的 `base={HOME_BASE}` 因此不再是不对称缺陷。
- 陈旧话术：`web/src/app/shell/Shell.tsx:655` 弹层文案「agentd 重启会清掉所有会话」与相关注释已不成立，是本次排查被误导的直接来源。

## 方案

判据收口在恢复合成层，一处管两个面：

1. **home 收编仅限本机**：恢复 ③ 跳过 `machine !== ''` 的 home 会话。外来 home 会话归它自己机器的悬浮窗管。
2. **存量外来 tab 一次性清除**：恢复 ② 解码快照后丢弃 `machine !== ''` 的悬浮窗 tab（终端与文件同规则）。不 bump `DOCK_PERSIST_VERSION`——decode 照旧接受旧数据，丢弃发生在合成层。清除命中 `activeId` 时将其置 null，交给恢复层既有的「有 tab 无激活项」兜底重指（`restore.ts:225`——现状兜底只认 `activeId === null`，不认悬空，所以必须由清除显式置 null）；清完后 tabs 为空时把 `windowOpen` 一并收为 false，升级后首启不该凭空弹一个只有 tab 条的空壳浮窗。用户可见效果：升级后首启，原本不属于本机的外来 tab 消失——设计内的一次性变化，不是回归（acceptance 勿误报）。
3. **扇出缺席不判死**：`buildRestore` 增加 machines 入参，恢复层按「会话所属机器本次扇出是否 ok」门控两处 prune——机器 `ok=false` 或缺席时，它名下的会话引用不剥（tab 保引用，机器回来照常接上；机器网络不可达时挂载走连接错误路径，会话已不存在时走既有 1008 判死，两条路都有「重开」终态，不静默自建）。悬浮窗与中央区同规则；两处 prune 的机器归属来源不同：dock 侧读 `tab.machine`，workbench 侧读 tab 所在 base 行的 `machine`（TabContent 没有 machine 字段，唯一可靠归属是 base 行）。
4. **话术订正**：关闭确认弹层文案（`Shell.tsx:655`）与散布的陈旧注释（`Shell.tsx:217/270/301`、`TerminalTab.tsx:8/616`）改为准确表述——会话跨 agentd 重启存活，消失途径是机器重启 / 退出 shell / 显式 stop。

### 弃选与理由

- **弃：扇出重试/等机器就绪再恢复**。把冷启动挂在最慢机器上，且覆盖不了机器被注销；门控判据在恢复层一次算清，不需要第二轮请求。
- **弃：dock 快照迁 localStorage（设备本地化）**。用户要的边界是「机器」不是「设备」；服务端 per-agentd 存储天然满足，且 localStorage 换浏览器/清缓存即丢现场，降级路径更差。
- **弃：外来 tab 打标记保留**。修完后它们连不上（1008 歳）且永不属于本机，留着只占 tab 条。
- **弃：修 `Shell.tsx:610` 的 machine 传递**。收编仅限本机 + 存量清理后，悬浮窗终端 tab 的 machine 恒为空串，该不对称不可达；改它属死代码加固，YAGNI 砍掉（file 分支的 `t.machine` 读取保留原样）。

## 用户故事

1. 作为多机用户，我连续多天开关桌面端，悬浮窗的终端 tab 数量不因机器离线抖动而增长；昨天收起时是几个，今天打开还是几个（会话真死的除外：tab 保留、终端重开）。
2. 作为 mac-02 上的用户，我在 mac-02 开的 home 终端不会出现在另一台机器的悬浮窗里，反之亦然。
3. 作为用户，某台机器暂时离线时打开桌面端，它名下的终端 tab（悬浮窗与中央区）不会被悄悄换成新 shell；机器回来后接上的还是原来那个会话。
4. 作为用户，关闭终端的确认弹层不再用「agentd 重启会清掉所有会话」这种已不成立的话术误导我。

## 实现决定

- 三条判据全部收口在 `buildRestore`（合成层），UI 层不散落判断；机器 ok 映射由 `useWorkbenchSync` 从既有的扇出响应取出传入。
- 本机会话不设特殊分支：本机行恒 `ok=true`，走同一张门控表。
- 快照里 machines 行缺席的机器按「不 ok」处理（保守：宁可留一个连不上可显式重开的 tab，不静默造孤儿）。
- 存量清除的两个边界形态：purge 命中 `activeId` 即显式置 null（`restore.ts:225` 既有兜底只认 null，会重指到剩下的第一个 tab）；purge 后 tabs 为空则 `windowOpen` 收为 false。
- 门控的机器归属来源：dock 侧按 `tab.machine`，workbench 侧按 tab 所在 base 行的 `machine`（TabContent 无 machine 字段，被判死的会话也不在会话行里，那条取法不存在）。
- 收编的 seq 计数、计数器播种等既有机制不动（被清 tab 的 id 是 UUID 形状，本就不参与 `h<n>` 计数器播种，无撞号面）；红色回路用例转正并入 `restore.test.ts` 并转绿——open1 的「sessionId 被剥」断言按方案 3 反转为「保引用」，不是原样搬。
