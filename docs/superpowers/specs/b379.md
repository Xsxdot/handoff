# B379 spec：视图 diff 对陈旧基线的吸收防线与存量对账

> **级别**：L2（单子系统：codegraph 图工具链；不动契约层——diff 格式与工具对外行为不变，仅收紧校验）
> **批准**：2026-10-02 用户显式授权协调者全权处理（含批准权），本 spec 依授权定稿生效。
> **台账**：`docs/superpowers/notes/b379-absorb-recon.md`（复现记录、十二份分类原始计数、领域归属读数）

## 问题陈述

codegraph 的保鲜回路：分支工作树扫描产出视图 diff（`codegraph/diffs/cards-<分支>.json`）→ 分支合并回主线后 `codegraph absorb` 机械併入 `codegraph/baseline.json` 并删除该 diff。

2026-09-14 B233.26 全量重扫重建了基线（归域迁移、d_coordination_api 等领域解散、条目再锚定）。十二份彼时积压未吸收的历史视图 diff 从此挂在已不存在的旧基线上。absorb 对「基线已漂移」没有任何防线，两类暴露：

1. **静默腐化**（2026-10-02 /tmp 合成复现，台账 §2）：ValidateDiff 对 `nodesAdded` 撞基线同 id 不设防（charter 仓 `graph/codegraph/validate.go#ValidateDiff` 只查容器引用闭合），Absorb 对 NodesAdded 无条件按 id 覆盖（`graph/codegraph/absorb.go#Absorb`）。B233.1–6 与 B358 七份视图的全部 nodesAdded 已存在于基线、其中 108 条锚已漂移——吸收即把重扫后的再锚定回退成分支时态旧锚，且 diff 文件随吸收删除，证据一并销毁。
2. **硬拒无出路**：B374 容器 k_collab_model 已在基线（同内容同领域），absorb 直接拒；B272 容器 k_dropdir_fn 挂在已解散的 d_coordination_api 上，同样被拒。两份都还挟着未入基线的合法新增内容，没有出路只能继续积压。

## 方案（含弃选与理由）

**两刀，一守一清：**

1. **工具守卫**（charter 仓 `graph/codegraph`）：ValidateDiff 补一条判据——`nodesAdded` 同 id 已存在于基线 → 报「新增节点 %s 已存在于基线，nodesAdded 只接受新节点」并拒。与 containersAdded 的既约（契约 §7-R1 容器版）完全对齐，是它的节点版。Absorb 保持纯函数不动。这一刀把静默腐化整族变成显式拒绝：重演本卡七份视图的情形时，操作者拿到的是拒绝报文，不是被覆盖的基线。
2. **存量对账**（handoff 仓 `codegraph/`）：十二份按台账 §3 四组处置——

| 组 | 视图 | 处置 |
|---|---|---|
| 取代组（7） | B233.1-charter-2、B233.2–6、B358 | 删除 diff 文件（内容已被 09-14 重扫捕获，重放=制造第二份陈旧 diff） |
| 修剪组（1） | B374 | 从 diff 剔除 `containersAdded.k_collab_model`（基线已有同内容），其余原样吸收 |
| 改挂组（1） | B272 | `containersAdded.k_dropdir_fn.domain` 改挂 d_gateway（判据见实现决定），其余原样吸收 |
| 直收组（3） | B369、B395-charter-5、B398-charter-12 | 原样吸收 |

**弃选：**

- **diff 烙基线指纹**（生成时记录基线 scannedAt/commit，吸收时对不上即拒）：根治漂移类，但要动 diff schema + 扫描纪律 + 全部执行器生成侧。守卫落地后腐化类已是显式拒绝，指纹的边际收益降为「把部分拒绝提前」，收益配不上改动面。→ Out of Scope，落 roadmap。
- **只清数据不加守卫**：下一份漂移 diff 照样静默覆盖基线并自毁证据。根因不除，否决。
- **七份视图重放/重扫**：其内容已在基线，任何形式的重放都是倒退。

## 全部必交用户故事

- **S1 吸收防线**：操作者对「nodesAdded 撞基线」的视图跑 `codegraph absorb`，得到显式拒绝报文（含节点 id 与「只接受新节点」语义），基线字节不变；对干净视图 absorb 照常併入并删 diff。验收环境：本机，charter 仓 `go test ./...` 全绿（含新增判据用例）+ 合成仓端到端一例。
- **S2 存量清零**：操作者跑 `codegraph views`，输出不含十二份积压视图名；`codegraph validate --stale` 与 `codegraph check` 零问题退出 0；基线含直收组内容（k_dropdir_fn 在册且归 d_gateway、B374 九个新增节点在册）。
- **S3 退役无损抽查**：取代组约 33 条未复现边中抽 3 条，对当前 main 源码核实该调用/实现关系确不存在（读调用点取证），结论记台账——证实「重放才是倒退」，退役不丢现实存在的关系。

## 实现决定（决策级落点）

- 守卫收在 **ValidateDiff**：它是工具唯一的 diff 闸（absorb 命令闸序 = ValidateDiff → CheckEdges → Absorb，charter 仓 `graph/cli/cli.go` absorb 子命令），单点收口，Query 族不经过它不受影响。
- 报文语气对齐 containersAdded 同款句式；判据范围 = `d.NodesAdded` 的 id 对 `g.Nodes` 的存在性，不涉及 NodesModified/Deleted（它们已有「须在基线」判据，语义本来就不同）。
- **B272 改挂 d_gateway 的判据**：重扫后 agentd 包的既存容器（k_agentd_Server / k_agentd_fn / k_agentd_model / c_http）全部归 d_gateway（台账 §4）；dropdir 是 agentd HTTP drop 面的包级函数组，随包归属。
- 对账全程在 git 分支上以**现有 codegraph absorb 命令**执行（不手改 baseline.json 的图内容）；修剪/改挂只编辑 diff JSON 文件本身。charter 仓守卫与 handoff 仓对账是本卡的两个落地分支，finish 时分别合并。
- 守卫落地后须重建并安装 codegraph 二进制（charter 仓 `go install ./graph/cmd/codegraph`），使后续 absorb 用上新判据。

## 测试决定（真实入口与风险）

- S1 的真实入口是 **absorb 命令**，不是只测 ValidateDiff 函数：新增单测进 charter 仓 validate_test.go / absorb_test.go（函数级），另以 /tmp 合成仓端到端一例（复用台账 §2 的复现场景，断言拒绝报文与基线不变）。mock 不替代命令级证据。
- S2 的真实入口是本仓三个只读命令：`codegraph views` / `validate --stale` / `check`。
- **已知风险——CheckEdges 误拒**：修剪/改挂后的视图吸收时，CheckEdges 会按当前源码校验每条新增边的真实性。若它拒绝某条分支时态边（源码中该关系已不存在或换了形态），处置是：逐条对源码裁决，确属旧关系的边从 diff 剔除并记台账——这是对账语义的一部分（与取代组同判据），不是绕闸。
- S3 抽样取证记录进台账文件（提交原文与结论）。

## Out of Scope

- **diff 基线指纹 / 扫描侧漂移防线**：本期不做、后续要做 → 落 roadmap（来源本 spec；触发条件：守卫拒绝率显示对账成本失控时提前）。
- **codegraph CLI 内建扫描命令**（分支视图产出收进工具）：同上 → roadmap。
- **取代组约 33 条未复现边的全量追查**：重扫扫描配方的边提取保真度问题，与对账无关，若后续咬人另卡。
- **target.json / best.json 的任何修订**：本卡只动 baseline.json、diffs/ 与 charter 仓 ValidateDiff 判据。
- **十二份以外的新积压**：对账以本卡侦察时点的十二份为界。
