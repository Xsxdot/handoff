# 审核回路的持续订阅 —— 设计

> 状态：待实现
> 来源：08-11 用户复核「挂了四个任务、回来发现进展不大」后定案
> 关联：[B52 opencode 子会话权限被丢弃](../backlog.md)（执行侧根因，与本设计正交）

---

## 1. 背景与目标

### 1.1 实撞的现场

08-10 夜间到 08-11 上午，devbox 上有五个任务在飞。两个死于 B52（子会话权限请求被丢弃），
其中 `f7d07ece`（B47/B41/B48 的执行者）的完整时间线如下（**本地时间 +08:00**，与
`agentd.log` 一致；`handoff show` 的事件时间是 UTC，相差 8 小时，读日志时务必先确认时区）：

| 时刻 | 发生了什么 |
|------|-----------|
| 00:22:41 | 最后一条进度事件（正在派发 Task 5） |
| 00:31:31 | 子会话权限请求被丢弃（B52），模型自此零活动 |
| 00:49:29 | 审核者挂上 `wait --timeout 1h` |
| **01:49:29** | **wait 到点退出（退出码 124）。此后再无任何订阅** |
| 02:22:47 | 看门狗报 `stalled`（idle 2h）——**没有任何人在听** |
| 10:06:06 | 人工 `handoff stop` |

**从 `stalled` 到被处置，空转 7 小时 43 分。** 从 wait 断开算起是 8 小时 17 分。

同期唯一存活的任务 `8f7a4f18` 也有同类问题：审核者虽然一直在重挂 wait，但空窗从
凌晨的 8~27 秒恶化到白天的 13 分、18 分，最差一次 **41 分 25 秒**（09:23:05 → 10:04:30）
没有任何订阅。

**排除项：会话没死。** 同仓库的会话 `local_f1144768` 在 02:17（UTC）仍有活动，比
`f7d07ece` 的 wait 死亡时刻晚 28 分钟。所以这不是「会话被关掉了救不回来」，
而是**循环自己断了，且没有任何东西能发现它断了**。

### 1.2 根因：兜底与被兜底的东西是同一个进程

[2026-08-07-handoff-design.md](2026-08-07-handoff-design.md) 第 91 行写着：

> 兜底：`wait --notify` 在事件到达时发 macOS 系统通知，提醒用户会话已不在时重新拉起。

这是个**循环依赖**。通知由 wait 进程自己发；审核者会话不在时 wait 也不在，通知就不会发。
`cmd/wait.go` 的文件头注释把它称为「spec §7 风险#4 的兜底」，但它兜不住自己那一格。

### 1.3 两个不同的断法，要分开治

| 断法 | 证据 | 本质 |
|------|------|------|
| ① 回合结束了却没重挂 | `f7d07ece`：01:49 退出后再无连接 | 重挂是**需要模型每次记得做的动作**，漏一次即永久断链 |
| ② 重挂了但太慢 | `8f7a4f18`：空窗 13 分 → 41 分 | 模型回合本身要几分钟到几十分钟，**这期间没有订阅** |

两者同源：**`wait` 是「一事件一退出」，所以每两个事件之间必然有一段无人值守的真空。**
skill 里那句「处理完必须重新挂」是在用纪律填一个结构性的洞。

### 1.4 目标

1. **消除真空**：审核者对一个任务的订阅在会话存续期间连续，不因回合边界中断。
2. **让断链可感知**：订阅进程的任何异常退出都变成一条到达审核者的信号。
3. **让「无人值守」成为可见事实**：`handoff tasks` / `status` 能直接看出某个活跃任务没人在听。

### 1.5 非目标

- **不做人肉告警**（桌面通知/手机推送/云端 routine）。用户明确要求「不叫人、不拉起新会话，
  在原会话上继续」。
- **不做自动处置**（自动 stop、自动 continue、自动答工单）。审批权不下放给无人监督的循环。
- **不覆盖「会话被关闭」**。这是本设计的已知边界：会话不存在时没有任何机制能续上，
  见 §7.2。
- **不修 B52**。执行侧的子会话权限归属是独立缺陷，与本设计正交——但要注意 B52 是
  昨晚两个任务静默的**直接原因**，本设计只保证「静默能被及时发现」，不保证「不再静默」。

## 2. 契约：`handoff wait --follow`

### 2.1 行为契约

底层 `waitOnce` 已经是 `for { conn.Read(ctx) }`（[internal/client/client.go:789](../../../internal/client/client.go)），
`--follow` 只是不在首个事件后返回。

| 维度 | 现状（一事件一退出） | `--follow` |
|------|---------------------|-----------|
| stdout | 单行事件 JSON | **每事件一行**，同一 JSON 契约 |
| 退出时机 | 交付首个事件即退 | 任务落 `failed` 或被归档才退。**`completed` 不退**——那只是一轮结束，`continue` 后还有事件 |
| `--timeout` | 到点未等到事件 → 124 | 语义改为**空闲超时**，见 §2.2.1 |
| 断线重连 | 退避重连，凭 cursor 续拉 | 不变，且**对上层完全透明**（不额外打行、不退出） |
| 永久失败（401 / 任务不存在） | 立即非 0 退出 | 不变 |
| `completed`/`failed` 时自动 pull | 有 | 保留，每次遇到都同步 |
| `--notify` | 事件到达发系统通知 | 保留但**不建议与 `--follow` 同用**（事件已进会话，再弹通知是噪音） |

一次性 `wait`（不带 `--follow`）**保留**：派发后等第一个事件这类场景仍然适用。

### 2.2 `--timeout` 的空闲以「任何帧」为准，且必须大于 `stalltimeout`

**空闲的定义：距上一次从 agentd 收到任何帧的时长**，包含被客户端过滤掉的 `progress`。

progress 的过滤发生在**客户端**（[client.go:668](../../../internal/client/client.go)
「跳过 progress，除非 all=true」），服务端把全部帧都推过来。所以 follow 端能看到 progress，
即使它不打印。

为什么不以「可交付事件」为准：一个健康的长跑任务可以数小时只有 progress 而没有任何
需要审核者动作的事件（`8f7a4f18` 连续跑了 15 小时）。用可交付事件计时会让它每隔
`--timeout` 无故 124 一次，把兜底变成噪音。`--timeout` 的职责是「连接还活着吗」，
不是「有没有活干」。

**硬约束：`--timeout` 必须大于 agentd 的 `stalltimeout`（当前配置 2h）。**

两者都在测「多久没动静」，但结论的质量差一个数量级：`stalled` 是 agentd 带着
`last_seq` 和 `idle` 时长给出的**诊断**，124 只是客户端说「我没收到东西」。若两个计时器
同时到点，124 会抢在 `stalled` 前面退出进程，把一个已经诊断清楚的任务停滞降级成一次
连接超时——审核者拿到的信息严格更少。

因此 §4 的推荐值取 `--timeout 3h`。实现时应在 `--follow` 且 `--timeout <= stalltimeout`
时打一条 WARN（agentd 的 `stalltimeout` 可经 `handoff status` 得知，无法得知时不阻断）。

### 2.3 退出码语义

| 码 | 含义 | 审核者应对 |
|----|------|-----------|
| 0 | 任务落 `failed` 或已归档，跟随自然结束 | 进入终态处置 |
| 124 | 空闲超过 `--timeout` 无任何帧（§2.2） | **本身可疑**——正常情况下 agentd 的 `stalled` 会先到。先 `handoff show`，再考虑 agentd 是否失联（不同于旧语义的「继续挂」） |
| 其他非 0 | 鉴权失败 / 任务不存在 / 连接永久失败 | 看 stderr，按排障表办，**不要盲目重开** |

**关键不变量**：follow 进程的**任何**退出都会被上层感知（Monitor 报告退出码）。
昨晚的洞正是 wait 静静退出 124 而无人接住；本设计下退出本身就是信号。

### 2.4 一个必须记录的取舍：cursor 会跑在「已读」前面

现状 cursor 只在 wait 交付事件时推进，而「交付」约等于「审核者看到了」——一事件一退出，
不处理完就不会有下一个。

`--follow` 打破这个耦合：事件可能在审核者正忙时流入，cursor 已推进而人还没看。
**此刻会话若崩溃，该事件不会再重放。**

**决定：接受这个回退。** 理由：

1. 事件流本就不是权威。skill 早已规定「醒来先 `show`，`state` + `pending_tickets` 说了算」。
2. 真正不能丢的是**工单**，而工单在 agentd 侧持久，`pending_tickets` 是权威清单。
3. 现行的「cursor 即已读」语义本身是假的——昨晚 `f7d07ece` 的 cursor 精确停在 01:49，
   而它真正需要人的时刻是 02:22 的 `stalled`。cursor 忠实地记录了一个没有人的位置。

`--follow` 把「事件是唤醒信号、`show` 是权威」从建议变成必须。skill 要相应加粗这一条。

## 3. `watchers`：把「没人在看」变成可见事实

### 3.1 数据来源

`Hub` 已持有 `subs map[string][]chan proto.Event`（[internal/agentd/hub.go:34](../../../internal/agentd/hub.go)）。
新增：

```go
// Watchers 返回当前订阅该任务事件流的连接数（运行态）。
func (h *Hub) Watchers(taskID string) int
```

走现有 `mu`，纯读，零额外状态。

**这个数字是干净的**：全仓 `Subscribe` 只有一个调用点——`/ws/events` 的处理器
（[internal/agentd/server.go:1054](../../../internal/agentd/server.go)）。没有内部订阅者虚高，
它精确等于「有几个审核者正在听」。

### 3.2 API 视图：不污染 `proto.Task`

`proto.Task` 是落库结构。往里加运行态字段等于让存储层背一个它不该知道的概念，
迟早有人把它写进 SQLite。改用嵌入，定义放 `internal/proto`（它是客户端也要解码的线格式）：

```go
// TaskView 是 proto.Task 的 API 视图，附带不落库的运行态。
//
// 为什么用嵌入而不是给 proto.Task 加字段：Watchers 是 Hub 的瞬时状态，
// 与任务的持久身份无关；嵌入让存储结构保持纯粹，同时 JSON 字段提升后
// 线格式与旧版逐字节兼容（仅多一个 watchers 键）。
type TaskView struct {
    proto.Task
    Watchers int `json:"watchers"`
}
```

`handleListTasks` / `handleGetTask` 在响应时拼装。老客户端解码不受影响。

### 3.3 异常判据

**必须写死**，否则会退化成天天误报的狼来了：

| 状态 | `watchers == 0` 算异常 | 为什么 |
|------|----------------------|--------|
| `pending` / `running` / `waiting_answer` | **是** | 这三个状态里事件随时会来，没人听 = 事件掉地上。昨晚 `f7d07ece` 正是 `running` + 0 |
| `waiting_review` | 否 | 等审核者裁决，挂几天都正常，本就不需要有人盯 |
| `completed` / `failed` | 否 | 终态 |

### 3.4 展示

- `handoff tasks`：每行 JSON 增加 `watchers` 键。
- `handoff status`：活跃任务行在现有三态存活结论（`executor 存活` / `已不在（理由）` /
  `存活性未知（理由）`）之后追加 `⚠ 无人值守`。

这两条命令是审核回路里敲得最勤的，异常状态会自己撞进视野——不需要 hook、不需要定时器、
不多消耗一个 token。

**值得记下**：这个字段一直存在，只是从未外露。昨晚 `handoff show f7d07ece` 返回
`running` + `pending_tickets: 0`，看上去一切正常；同一时刻 agentd 内部
`len(h.subs["f7d07ece…"])` 就是 `0`——它一直知道没人在听，只是没有人问过它。

## 4. 审核者回路的新形态（skill 必须改写）

`skills/handoff/SKILL.md` 现在**明文规定**旧形态：

> 「每一轮 = 一条后台命令，内容就是一条裸的 wait」
> 「处理完必须重新挂，否则后面的事件没人接」

这两段必须整体替换，否则下一个会话照旧按旧纪律办事，§2 白做。

**新形态**：

```
Monitor({
  command: "handoff wait --follow <完整 task-id> --timeout 3h",
  description: "handoff <任务名> 事件流",
  persistent: true
})
```

开一次，活到会话结束。事件作为通知流入，**没有「重挂」这个动作**。

纪律变化对照：

| 旧 | 新 |
|----|----|
| 醒来 → show → 处置 → **重挂** | 醒来 → show → 处置。**无重挂** |
| 退出码 124 = 超时，直接重挂 | 124 = 空闲 3 小时**一帧都没有**，**本身可疑**（`stalled` 本该先到），先 `show` 再怀疑 agentd 失联 |
| wait 退出是常态 | **follow 退出是异常信号**，必须看退出码 |
| 新会话接管：清 `pending_tickets` → 重挂 wait | 接管：`handoff tasks` 看 `watchers`，给所有 `watchers==0` 的活跃任务补开 Monitor |

红旗表新增两条：

| 念头 | 事实 |
|------|------|
| 「Monitor 退出了，再开一个就行」 | 先看退出码。401/404 重开一百次也是同样的结果 |
| 「事件流进来了，直接按它处置」 | 事件是唤醒信号，`show` 是权威。`--follow` 下 cursor 跑在已读前面，这条比以前更要紧 |

## 5. 错误处理与失败语义

| 情况 | 行为 |
|------|------|
| 断线 | 现有退避重连，凭 cursor 续拉；对上层透明，不打行不退出 |
| 永久失败（401 / 任务不存在 / `StatusPolicyViolation`） | 立即非 0 退出，stderr 给原文 |
| 空闲超过 `--timeout` | 退出 124 |
| 任务落 `failed` / 归档 | 退出 0 |
| `Watchers` 并发读写 | 走 Hub 现有 `mu`；订阅/退订与读取必须 `-race` 覆盖 |

## 6. 测试与验收

| 层 | 用例 |
|----|------|
| `wait --follow` 单测 | 连续多事件逐行交付；cursor 逐个推进；`failed` 后退出 0；空闲超时退 124；永久失败立即非 0 |
| 空闲计时口径 | **只有 progress 帧流入时不得触发 124**（§2.2 的核心断言）；完全无帧才 124；`--timeout <= stalltimeout` 时打 WARN |
| 断线续拉 | 中途断连重连，不重不漏，**不额外打行** |
| `Watchers` 单测 | 订阅数正确；退订后归零；并发订阅/退订 `-race` 干净 |
| `TaskView` 拼装 | 线格式与旧版兼容（仅多 `watchers` 键）；老客户端解码不破 |
| 展示 | `status` 的 `⚠ 无人值守` 只在 §3.3 的三个状态下出现，`waiting_review` 不出现 |
| 集成 | 起 agentd → 开 follow → 推 N 个事件 → 校验 N 行；杀 agentd → 校验退出码 |
| 真机验收 | 派一个真任务全程 Monitor：`watchers` 走完 0→1→0，`status` 标记与状态同步 |

## 7. 影响面与已知边界

### 7.1 兼容性

- `wait` 默认行为**不变**，`--follow` 是可选开关。旧脚本与旧 skill 用法继续可用。
- `/api/tasks` 与 `/api/tasks/{id}` 只增字段，不改不删。老客户端解码不受影响。
- 无数据库变更。`watchers` 不落库。

### 7.2 已知边界：会话关闭不在覆盖范围内

Monitor 是会话级的。**会话一旦关闭，订阅随之消失，没有任何机制能续上。**

这是用户明确接受的边界（「不叫人、不拉起新会话」）。需要说明的是，它并不覆盖昨晚的事故
——昨晚会话是活着的（§1.1）——但如果将来真出现「合盖睡觉、会话被系统回收」的场景，
本设计给不出任何东西。届时唯一的出路是常驻进程（B54.2 的 `handoff service` 已提供
launchd/systemd 基建），那是另一个设计。

### 7.3 被显式排除的备选方案

| 方案 | 排除理由 |
|------|---------|
| `Stop` hook 守门 | 基线成本近零（shell，不进模型），但**误报即烧 token**：agentd 不暴露订阅状态时判据只能退化成「有活跃任务就提醒」，变成每回合拦一次的 token 泵，且很快被当噪音忽略。`watchers`（§3）以零成本拿到了它想要的可见性 |
| `ScheduleWakeup` / 定时轮询 | 纯轮询、延迟不可控，且**仍依赖模型每次记得排下一次**——病因 ① 原样保留 |
| `CronCreate` | 会话内内存态，会话结束即消失。正是昨晚失效的那类机制 |
| 云端 routine（`RemoteTrigger`） | 跑在 Anthropic 侧，够不到 Tailscale 内网的 devbox 与本机 |
| `Monitor` 的 ws 模式直连 agentd | agentd 的 WS 鉴权走 `Authorization: Bearer` 请求头（[client.go:765](../../../internal/client/client.go)），而 Monitor 的 ws 参数只接受 `{url, protocols}`，**不支持自定义 header** |
