# W4 控制台形态修复设计

**形态基准**：`prototypes/desktop-console/`（真实前端的形态镜像）。
本文不设计新形态，只把实现与基准对不上的地方掰回去——唯一的例外是 §6 配色里
「项目色」这一项，基准也没有可直接照抄的数据来源，需要现定口径。

**来源**：08-14 用户在真实控制台（`feat/b83-cumulative-usage` 构建，含 W4 全部
已交付部分）上逐条走查提出六条。其中五条形态问题 + 一条配色诉求收在本文；
第六条「悬浮按钮改为独立浮窗」是新形态，另出一份 spec。

---

## 0. 六条的性质分类

分类不是形式主义——它决定了每条的**判据从哪来**。照着原型改的，判据是原型；
原型也没有的，判据必须在本文里现定，否则实现时又要猜。

| 条目 | 性质 | 判据来源 |
|---|---|---|
| §1 「项目 N」计数粘连 | 实现漏了间距 | 原型 |
| §2 行尾计数是裸文本 | 实现与原型形态不同 | 原型（含一处有意偏离） |
| §3 注销按钮浮在子树正中 | 定位上下文选错，真 bug | 原型 + 常识 |
| §4 「添加项目」跟着树滚走 | 滚动容器划错 | 原型 |
| §5 看板弹层高度随内容伸缩 | 原型无对应（弹层是实现独有形态） | 本文现定 |
| §6 整体缺配色 | 原型有三套色源，实现一套都没落地 | 原型 + 一处现定 |

---

## 1. 「项目 N」的计数间距

**现状**：`ProjectTree.tsx` 渲染 `<span>项目</span><span>{count}</span>`，两个 span 之间
没有任何间隔，浏览器里就是「项目2」，数字像是标签的一部分。

**原型**：`<div className="sidebar-section-title">项目 <span>{n}</span></div>`，
配 `.sidebar-section-title span { margin-left: 3px; color: #969696; font-weight: 500 }`
——数字紧跟标签、比标签浅一档、字重更轻。

**改法**：补回间距，并让数字取更浅的前景色、字重与标签区分。

**为什么不把数字右对齐到栏边**（走查时讨论过的另一种形态）：基准是原型，
这条已裁决按原型来。右对齐会让它与下方每一行的行尾计数排在同一条竖线上，
反而容易被误读成「这一行也有计数」。

**判据**：标签与数字之间有可见间隔；数字颜色浅于标签。

## 2. 行尾计数改回图标形态

**现状**：`RowCounts` 收一个已经拼好的字符串，渲染成 `2·0·0`。这是本条被吐槽
「太丑」的直接原因——三个数字挤在一起，没有任何东西说明它们各自是什么，
只有 `title` 属性里藏着一句「目录·运行·待处理」，鼠标悬停才看得到。

**原型**：`SummaryCounts` 渲染三段 `图标 + 数字`：

| 语义 | 图标（lucide） | 说明 |
|---|---|---|
| 开发目录数 | `Folders` | `title="开发目录"` |
| 运行中任务数 | `Activity` | `title="运行中的 handoff"` |
| 待处理数 | `TriangleAlert` | `title="需要处理"` |

排版：`display:inline-flex; gap:7px`，每段内部 `gap:2px`，等宽字体
（`var(--mono)`）9.5px，颜色 `#7b7b7b`。

**改法**：`RowCounts` 的接口从「收字符串」改成「收结构化计数」，由它自己配图标。
签名改为：

```ts
function RowCounts({ dirs, running, pending }: {
  dirs?: number      // 省略时不渲染这一段（目录行没有「目录数」这个概念）
  running: number
  pending: number
})
```

三种行的用法：

| 行 | 渲染 |
|---|---|
| 项目行 | `<RowCounts dirs running pending />` |
| 机器行 | `<RowCounts dirs running pending />` |
| 目录行 | `<RowCounts running pending />` |

**一处有意偏离原型**：原型的机器行只渲染两段（`SummaryCounts` 收到 `machine`
标记时不渲染 attention）。**实现保留三段。** 理由：待处理数是「你还欠哪些没答」
的信号，机器是任务的实际落点，在这一层把它藏掉等于让用户必须展开到目录才看得见。
原型这么画很可能只是 mock 数据里机器层恰好没有待处理项，不是有意的信息裁剪。
这条偏离要写进走查记录，不要在验收时当成"没对齐"。

**判据**：三种行的计数各自带图标；悬停任一段能看到它的语义；机器行有三段。

## 3. 注销按钮的定位上下文

**根因（已实测定位）**：注销按钮的类名是
`absolute right-2 top-1/2 hidden -translate-y-1/2 … group-hover:inline-flex`，
它依赖最近的定位祖先来决定「right-2 top-1/2」相对谁。而实现里带
`group relative` 的那个 `<div>` 包的是**整个项目子树块**（项目行 + 它下面所有
机器/目录/任务行）。浏览器实测该块高 578px，于是 `top-1/2` 把按钮放在了
这 578px 的正中间——视觉上就是一个删除按钮凭空浮在列表中央，且不挨着任何一行。

**改法**：把定位上下文收到**机器行自身**。具体是给机器行的直接包裹元素加
`group relative`，让子树块那一层不再是定位祖先（去掉它的 `relative`；`group`
若还有别的 hover 语义依赖，一并挪到机器行）。

**为什么是机器行而不是项目行**：注销的对象是「项目在某台机器上的位置」
（`onUnregister` 的参数是 project + machine），不是整个项目。按钮必须长在
它作用的那一行上，否则语义与位置对不上——这也是这个 bug 之所以让人困惑的原因。

**判据**：hover 机器行时按钮出现在**该行**右端且垂直居中于该行；hover 项目行
或目录行时不出现；子树展开或折叠都不改变按钮位置。

## 4. 左栏底部固定

**现状**：整个 `<aside>` 是 `overflow:auto`。实测 `scrollHeight` 1137 > 视口 1024，
「添加项目」按钮的 `top` 是 1100——它在滚动内容的最下面，项目一多就被推出视野，
必须滚到底才能找到入口。

**原型**：左栏是 `display:flex; flex-direction:column` 的三段式：

```
.left-sidebar   { display:flex; flex-direction:column }   /* 自身不滚 */
.sidebar-tree   { flex:1; min-height:0; overflow:auto }   /* 只有树滚 */
.sidebar-footer { min-height:51px; border-top:1px solid } /* 钉在底部 */
```

**改法**：照搬这个三段式。顶部导航 + 搜索框 + 「项目 N」标题不滚，中间树独占
滚动区，底部 footer（添加项目 + 设置图标）钉死。`min-height:0` 是必须的——
flex 子项默认 `min-height:auto`，不写这一句 `overflow:auto` 不会生效，树会把
父容器撑高、footer 照样被顶出去。

**判据**：项目多到溢出时，搜索框与「添加项目」都始终可见；滚动只发生在树内部；
`<aside>` 自身的 `scrollHeight` 等于 `clientHeight`。

## 5. 看板弹层固定高度

**现状**：弹层高度贴着内容走。零任务时四列缩成薄薄一条，有任务时又长开——
每次打开尺寸都不一样，且空看板看着像出了错。

**原型无对应形态**：原型的看板是顶层页（替换中央内容区），实现按
[shell-calibration spec §8.3](2026-08-12-w4-shell-calibration-design.md) 有意改成了
弹层。所以高度得在本文现定。

**改法**：弹层高度**固定 70vh**，不随任务数变化。四列各自 `overflow-y:auto`，
列头（列名 + 计数）在滚动区之外不动。

**判据**：零任务与几十个任务两种情况下，弹层外框高度一致；列内滚动时列头不动。

## 6. 配色

**现状**：`ProjectTree.tsx` 里除了工单计数徽章那一处琥珀色，**所有图标都是
`text-muted-foreground`**——项目、机器、目录、任务、文件，全是同一个灰。整棵树
没有任何颜色可以用来区分层级或状态，这就是「单调」的来源。

原型的颜色来自**三个互相独立的来源**，要分开做，不要混成一次「加点颜色」。

### 6.1 项目色（唯一需要现定口径的一项）

原型给每个项目一个固定色，画在项目行的图标上：

```jsx
<Boxes size={16} color={project.color} strokeWidth={2.3} />
```

mock 里的五个色值：`#9b5de5` 紫 · `#4aa3df` 蓝 · `#44b678` 绿 · `#619df0` 靛 ·
`#171717` 近黑。

**问题**：真实 API 里**没有项目色字段**（`api/types.ts` 的 `ProjectNode` 里查无
此项）。所以颜色必须有个来源。三条路：

| 方案 | 说明 | 取舍 |
|---|---|---|
| A. 后端加字段 + 设置页可改 | 用户自定义，最贴原型的"每个项目一个身份色" | 要动 proto / store / 登记接口 / 设置 UI，为了配色开这么大口子不划算 |
| **B. 前端按 `project_id` 稳定哈希取色（推荐）** | 从固定调色板里按哈希取一色，同一项目每次同色、跨机器同色、零后端改动 | 用户不能指定"我要这个项目是红的"；同调色板下少量项目可能撞色 |
| C. 不做项目色 | 只做 6.2 / 6.3 | 满足不了本条诉求——树的主体仍然全灰 |

**裁决：走 B。** 调色板就用原型那五色，按 `project_id` 的稳定哈希取模。
哈希必须是纯函数且与列表顺序无关——按数组下标取色是错的，插入一个新项目会
让所有已有项目换色，用户会以为是 bug。

### 6.2 文件树的文件图标着蓝

原型：`.file-row > svg:nth-of-type(2) { color: var(--blue) }`（`--blue: #2187d7`）
——**文件**图标着蓝，**文件夹**图标保持灰。这个对比正是右栏不显得平的原因。

修改标记 `M` 用 `#c46e15`（琥珀偏棕），9px、字重 650。

### 6.3 状态点四态色

原型 `.status-dot` 是全局共用的小圆点，四态：

| 态 | 色 | 用在哪 |
|---|---|---|
| online（缺省） | `--green` `#18a86b` | 机器已连接、任务运行中、agentd 已连接 |
| attention | `--amber` `#e79b18` | 待处理（等你答复 / 等 Review） |
| neutral | `#aaaaaa` | 无明确状态 |
| offline | `--red` `#df554f` | 机器已断开 |

实现里已有的四个状态语义 token（B75 那一期建的）应当复用，不要再造一套色值。
本条的工作是**把这些点接到该有的位置上**，不是新定义颜色。

**判据**：项目行图标按项目呈不同色且刷新后不变；文件图标蓝、文件夹灰；
机器连接态与任务干预态用同一套状态点色。

## 7. 明确不做

- **不改看板改弹层这个决定本身**（§8.3 已裁决过），本文只定它的高度。
- **不做项目色的用户自定义**（§6.1 方案 A），需要时另起一条。
- **不动 `WorkbenchPage` 的 `renderContent` 签名**——那是另一份 spec 的地盘，
  两边同时改必打架。
- **不碰任何 Go 侧代码。** 本文六条全部是前端形态，一行 Go 都不该改。
  出现 `.go` 改动就是跑偏了。

## 8. 验收标准

逐条对着跑起来的控制台看，每条都要能当场判真假：

1. 左栏标题渲染为「项目 5」而非「项目5」，数字浅于标签
2. 项目行/机器行三段计数各带图标，目录行两段
3. hover 机器行，注销按钮出现在该行右端并垂直居中于该行
4. 项目撑满左栏后，搜索框与「添加项目」仍可见，只有树在滚
5. 零任务时打开看板，弹层仍是 70vh，四列等高
6. 项目图标按项目呈不同色，刷新页面后同一项目仍是同一色
7. 文件树里文件图标蓝、文件夹图标灰，修改标记是琥珀 `M`
8. 全程无 `.go` 文件改动；`npx vitest run` / `npm run typecheck` / `npm run lint` /
   `npm run build` 四条全绿

## 9. 已知风险

- **§2 改 `RowCounts` 接口会动到它的现有测试**。测试里如果是断言
  `'2·0·0'` 这个字符串，改完必然红——那是**预期的**，应当把断言改成按
  语义查（例如按 `title` 或 aria 查三段）。不要为了让旧断言绿而保留裸文本形态。
- **§3 的 `group` 类如果还有别的 hover 效果依赖它**（例如整块的背景变化），
  挪 `relative` 时要一并确认，别把别的 hover 弄丢。
- **§6.1 的调色板在深色模式下的对比度未验**。当前控制台只有浅色一套，
  本文不引入深色适配；将来做深色时这五个色值要重新取。
