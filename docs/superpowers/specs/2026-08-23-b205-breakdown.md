## 2. 契约增量核对

逐条对照 contract 的冻结物，本拆解不增加新的业务接缝；以下是每条的归属与越界结论。

| contract 冻结物 | 子卡使用方式 | 越界结论 |
|---|---|---|
| `SetCardBaseBranch(id, branch, actor)` | T1 实现唯一冻结门；T2/T3/T4/T5 都只通过它间接写卡 | 不越界；不允许入口复制“是否已派发”判断 |
| 首次 `EvDispatched` 按 `seq ASC` 冻结，审阅派发也算已派发 | T1 用同一事务内的事件判定，错误携带首个分支和时间 | 不越界；不新增 `dispatched` 状态列 |

### 2.1 边界澄清回写记录

本轮对“谁写卡”和“谁消费 wire”的判断已回写 contract §2.7，具体澄清如下：

1. `d_controlplane` 是收到请求的一侧，拥有本机账本；`?machine` 的目标机只是外部建树
   现实，不拥有协调者卡的身份空间。
2. `d_cli` 的 `card update` 是账本门面的包外入口，不是新的契约面；`d_web` 的
   `CardPatch` 和建树请求是既有 HTTP 面的调用者，不新增端点。
3. `d_contract` 的 Ticket 0 字段已冻结；本拆解的真实序列化断言归 T4/T5，不能借“Go 与
   TS 各自有类型”代替跨边界回归。

未发现需要退回 contract 才能成立的新接缝。唯一待处理的是 §3 旧句勘误，不处理它就
不能把 T4 解释成已批准的实现计划。

### 2.2 手写序列化/投影清单

以下链路必须在验收中逐处点名；“两端单测都绿”不算穿线通过：

1. `web/src/api/client.ts#createWorktree` 把可选 `card_ids` 交给 JSON 请求底座。
2. `internal/agentd/projectadmin.go#handleProjectWorktreeCreate` 将 JSON 解码到
   `proto.CreateWorktreeReq`，并把 `proto.Workspace` 写回响应。
3. P1 选择 A 时，T4 的 route-specific forward helper 把请求投影为“无 `card_ids` 的
   目标建树请求”，再把目标响应解码回 `Workspace`；这是为避免目标机误写自身账本的
   关键手写边界。
4. T4 在协调者侧把 `ws.Branch` 与每个原始 card id 交给 `Store.SetCardBaseBranch`，
   再把逐项结果投影进 `Workspace.CardResults`。
5. `web/src/api/types.ts#Workspace` 消费 `card_results`；弹层不得只看 HTTP 200，必须
   读每一项 `ok/error`。
6. `web/src/api/ledger.ts#CardPatch` → `internal/agentd/ledgerapi.go` 的 JSON struct
   使用可空指针/显式 key presence，区分“键缺失”和“空值清除”。
7. T1 写 `EvComment` payload 时显式保留 `base_branch: ""`；事件回读测试区分字段缺失
   与值为空，防止清除动作变成不可审计的普通 comment。

### 2.3 枚举与白名单核对

本次不新增状态名、事件类型、purpose、attachment kind 或其它枚举值：复用
`EvDispatched`、`EvComment`、`ErrBadState`。因此没有新值需要登记既有 switch/白名单；

## 3. 子卡清单与依赖 DAG

```text
Ticket 0 / contract + wire fixture
          │
          ▼
T1 d_ledger：SetCardBaseBranch 事务门与事件审计
       ├───────────────┬─────────────────┐
       ▼               ▼                 ▼
T2 d_cli          T3 d_controlplane  T4 d_controlplane + d_remote
                  PATCH 卡基线       建树逐卡挂接/跨机转发
       └───────────────┬─────────────────┘
                       ▼
                 T5 d_web：选择器、结果与三态编辑
                       │
                       ▼
                 协调者真机清单 / review
```

T2 与 T3 可在 T1 后并行；T4 需要 T1 的可观测门与 Ticket 0 wire。T5 依赖 T3/T4 的
真实响应形状。以下每张卡均按四段式列出，并明确机内/真机验收分流。

### T1 · 账本门：首次派发前设置/清除卡基线

**①契约引用**

- contract §2.1、§3 的账本原子断言；
- `internal/ledger/Store.SetCardBaseBranch`（Ticket 0 空壳）；
- `internal/ledger/EffectiveBaseBranch` 与 `effectiveBaseTx`；
- `internal/ledger/Store.RecordDispatch`、`EvDispatched`、`DispatchSnapshot`；
- `internal/ledger/Store.mutate` 与 `appendEventAt`。

**②意图与为什么**

把“首次派发前可写、首次派发后冻结”变成账本自己的单一事实源。一次调用在同一
`mutate` 事务里完成取卡、按 `seq ASC` 取最早派发、决定能否写、更新 `base_branch`、
更新 `updated_at` 和写 `EvComment`。这样 CLI、HTTP、建树批量循环不会各自复制门禁，
也不会在独立读查询与写事务之间留下 TOCTOU 窗口。空串只清除自身覆盖值，不替父卡或项目
主线做推断。

有界文件集：生产 `internal/ledger/cards.go`；测试优先 `internal/ledger/cards_test.go`，
如需验证继承再改 `internal/ledger/relations_test.go`。不得因本卡顺手改 `events.go` 的
全局事件模型。

**③验收（logic，机内闭环）**

行为判据：

1. 运行 `go test ./internal/ledger -run 'Test(SetCardBaseBranch|EffectiveBaseBranch)' -count=1`，
   输出该包 `ok`，且命令没有 `no tests to run`。
2. 不存在卡返回 `errors.Is(err, ErrNotFound)`；未派发卡写入非空分支后，读卡的自身
   `BaseBranch` 与 `EffectiveBaseBranch` 都返回该分支。
3. 未派发卡显式写入空串后，自身覆盖值为空；有父卡时有效基线回到既有父链值，无父卡
   时保持空，不自动出现 `main`/`master`。
4. 预置两条 `RecordDispatch` 事件（第一条包含分支和时间，第二条不同），调用改基线，
   返回 `ErrBadState`，错误正文同时含第一条分支和第一条事件时间；删除门禁的变异下该
   反面断言必须转红。
5. 预置 `PurposeReview` 的 `EvDispatched` 后仍拒绝改基线，证明“任意已派发”与
   `WorkBranch` 的“跳过审阅找工作分支”是两个口径，未被错误合并。
6. 用同一张卡的读回事件断言 comment payload 有 `base_branch` 键，清除时键存在且
   值为 `""`；cards 行与 comment 事件在可注入失败时一起不可见，不允许半提交。
7. 子卡自身为空时，父卡有效基线仍可被解析；子卡自身成功写入后只覆盖自己，不篡改父卡。

缺陷族对抗：

- **生命周期 / 状态机中断**：本操作只持有账本事务，不创建进程、工单或临时目录；事务
  未提交时宿主退出由数据库回滚，提交后卡与 comment 同时存在。没有新增孤儿资源，因而
  无，因为 T1 没有跨进程资源；建树/HTTP 宿主重启窗口归 T3/T4 真机项。
- **静默失败 / 误导报错**：不存在卡、已派发卡、数据库写失败都返回非 nil 错误；已派发
  错误带首个分支和时间，用户可行动地知道“何时、在哪条分支冻结”。同事务消除“卡已改
  但事件没落”的报成功窗口。无，因为所有入口都必须调用此门面。
- **跨平台假设**：SQL 通过 `Store.q`/既有 `mutate` 适配 SQLite 与 PG，时间沿用账本
  编解码；不新增路径、进程组或权限模型假设。SQLite 行为可机内闭环，PG 锁/网络故障
  的实际行为仍标为未验证，需真机。
- **假红 / 假绿测试**：测试必须用真实 `RecordDispatch` 写事件后再调用门面并回读 JSON，
  不能直接造一个“已派发 bool”；正反两态、审阅事件、继承和事件落账都有断言。并发
  两个写调用的最终唯一性/一个成功一个冻结需在高负载或 PG 环境真机复核，机内夹具不冒充。
- **门禁绕过**：T1 是所有新增写入口共享的冻结门；直接 CLI、HTTP、建树循环都不准自判。
  cards 更新与首次派发读取在同一 `mutate` 内，检查与动作之间无 TOCTOU。无，因为本卡

### T4 · 建树控制面：成功后逐卡挂接与跨机转发

**①契约引用**

**②意图与为什么**

协调者 agentd 才拥有卡账本；显式 `?machine` 只把去掉 `card_ids` 的建树请求交给目标，
收到 `Workspace` 后由协调者用 `ws.Branch` 写本地卡，再返回本地 `card_results`。目标机
不得因为 `ledger == nil` 把协调者的卡挂账静默吞掉。

有界文件集：生产 `internal/agentd/projectadmin.go` 与必要的 `internal/agentd/forward.go`；
测试 `internal/agentd/projectadmin_test.go`、`internal/agentd/forward_test.go`。不改
`internal/agentd/manualworktree.go` 的 Git 语义，不把通用转发管线改成可变换所有业务请求；
route-specific 辅助若需放在 `forward.go`，只供建树路径调用。

**③验收（logic + boundary 分流）**

机内行为判据：

1. 运行 `go test ./internal/agentd -run 'TestProjectWorktreeCreate(CardAttach|Results|LedgerDisabled|Forward)' -count=1`，
   输出 `ok` 且命中真实 HTTP handler；若测试名不同，等价要求必须能由测试列表证明命中，
   不能接受 `no tests to run`。
2. 本机账本启用、Git 建树成功、请求含 N 个不同 card id 时，HTTP 200 的 `Workspace.branch`
   是工作树分支，`card_results` 按请求顺序恰有 N 项；每项 `ok` 与账本实际读回一致。
3. 第二张卡已派发或不存在时，第一张仍成功、第二张 `ok:false` 且 `error` 含真实原因；
   工作树目录仍存在，响应不把整个请求伪装成 Git 失败。反向变异为“任一卡失败删树”时
   必须转红。
4. 无 `card_ids` 或空数组时，响应 JSON 省略 `card_results`；Git 建树失败时返回既有
   400/500 且不返回任何卡结果；`ledger == nil` 时带 card id 仍返回成功树且省略结果。
5. P1-A 的 `?machine` httptest 穿线必须证明：目标收到的 JSON 没有 `card_ids`；目标返回
   的 `branch` 回到协调者；协调者账本的卡得到该分支，目标自己的 ledger 不新增任何卡
   事件；响应结果逐项反映协调者写卡。此测试必须经过真实 HTTP 转发/解码，不可直接调用
   `SetCardBaseBranch` 拼出结果。
6. 目标不可达/转发 502/请求 context 取消时，协调者返回既有可行动错误，不写本地卡；
   普通无 `?machine` 建树的旧请求仍保持现有行为。目标建树成功但本地一张卡失败时，
   HTTP 仍是成功树+逐项结果，不把“卡未挂”说成“树未建”。

边界型行为必须写入真机清单，机内 httptest 不得替代：目标 agentd 版本、真实 relay/直连、
不同 OS 的 Git worktree、请求取消后的真实目录状态。

- **生命周期 / 状态机中断**：顺序固定为 Git 成功→逐卡账本写，避免账本先指向不存在的

缺陷族对抗：

- **生命周期 / 状态机中断**：候选读取用现有 effect 的 alive 清理，弹层关闭后不写死
  React state；提交不自动重试，避免用户不知情地重复建树/重复挂卡。服务器中断与孤儿树
  不由组件假设已收尾，归 T4 真机清单。无，因为前端不拥有进程/工单清理职责。
- **静默失败 / 误导报错**：选择结果、逐卡 `error`、patch 409 和账本不可用都各有可见
  文案；HTTP 200 无结果不被渲染成“挂卡成功”。失败时不调用成功回调或不隐藏用户刚选的
  卡。无，因为测试断言 UI 文本与请求 payload 双面一致。
- **跨平台假设**：只用原生 select/checkbox、文本和既有 fetch，不用剪贴板、下载、路径
  拼接或 webview 专属 API；WKWebView/Chromium 的真实表单焦点与跨机响应展示仍**未验证，
  需真机**。无新增路径/进程组假设。
- **假红 / 假绿测试**：组件测试必须检查真实 `createWorktree`/`patchCard` 调用参数、
  缺席字段、混合结果 DOM 和 409 反面；不只查按钮存在。真实跨机机名、远端结果延迟和
  用户中途关闭由真机清单验证，mock 不代表目标机行为。
- **门禁绕过**：前端只负责候选禁用和展示，服务端 T1/T3 是唯一权限/冻结门；即使通过
  devtools 手造一个已派发卡 id，响应仍必须是单卡失败。无，因为 UI 没有第二个写 API。
- **序列化边界**：`CreateWorktreeReq.card_ids`、`Workspace.card_results`、`CardPatch.base_branch`
  都要用实际 client request/response 测试；`undefined`、`[]`、`""` 三种输入不能以同一
  断言覆盖。TS 类型通过不等于服务端已消费。
- **枚举新值过既有白名单**：无，因为 UI 展示的是已有字符串分支与布尔结果，不新增状态
  或事件枚举；错误文案不作为枚举解析。
- **承重安全属性有测试锁住**：UI 层不承担冻结唯一性，因而无，因为安全属性由 T1/T3
  的能变红测试锁住；本卡能变红的隔离反例是“强行提交已派发 id 后仍显示成功”，必须覆盖。
