### D. 三条未定的观察（验收时发现，没做决定）

1. **合并节点只认 origin 上的工作分支**：`internal/ledgernode/wire.go` 的
   `NewLocalObjective` / `NewLocalMerge` 都跑 `git fetch origin <分支>`，而纪律块
   禁止执行者 push、`handoff pull` 只把分支拉到协调者本地——**流程里没有任何一步
   把工作分支推到 origin**，于是合并节点必然报 `couldn't find remote ref`。
   验收时靠审核者手工 `git push origin <分支>` 绕过。
   两个方向：让协调者流程显式包含这一步，或让节点在 origin 缺失时回落本地分支。
2. **派发解析基线时不 fetch**：执行机的仓库镜像陈旧时，`--base-branch main` 的卡
   会基于旧 main 起分支，且刚推的新分支会报「起点不存在」。手工在该机
   `git fetch origin` 后恢复。
3. **合并节点会把协调者工作区留在基线分支上**：它 `git checkout <base>` 后不切回；
   工作区有未提交改动时这一步还会直接失败。

## 这轮真机验收挖出的坑（会重复踩，务必先读）

单测结构上挡不住、只有真机跑才会露的，共 11 处，都已修复。最值得记的四条：

1. **只读审阅任务没有合法的收尾出口**（最贵的一条）。注入每个任务的回合铁律
   （`internal/executor/turn/protocol.go` 的 `ProtocolRules`）只给两个出口：
   `{"ask":...}` 提问，或**先 commit 再**输出 `{"branch","commit","summary"}`。
   审阅纪律块禁止提交 ⇒ 唯一合法出口只剩提问。codex 与 grok 三次都把裁决塞进
   提问工单——**它们是在守铁律，不是不听话**。协议其实认**只带 summary** 的收尾行
   （`decodeProtocolJSON` 里 `t.Summary != ""` 即判 finish）。已写进
   旧审阅纪律副本第 8 条与 `reviewVerdictContract`。
   **推论：以后给任何不产生提交的任务（勘察、纯分析）写纪律块，都要明确告诉它
   收尾行长什么样。**
2. **节点等的必须是「回合终态」而不是「首个可动作事件」**。`WaitEvent` 返回首个
   可动作事件，审阅跑只读命令照样过权限门 ⇒ 几乎必然醒在 `permission_request` 上，
   随即报「事件流中没有 completed/failed」。已修为 `waitForTurnEnd` 循环
   （`internal/ledgernode/wire.go`）。
3. **`completed` 之后的 `turn_failed` 是传输层假警报**，codex 与 grok 都会补一条。
   取最终报文必须优先认 `completed`（`finalMessageFromEvents`）。
4. **显式写 `main` 的基线也要当主线**。合并节点原来只判空基线，
   `card add --base-branch main` 建的顶层热修卡会被当集成线**自动合进 main**，
   绕开主线人工门。已修（`isMainline`）。

另有两条产品级的：派发失败回滚要连驱动租约一起退（驱动身份带 pid，否则本人换个
进程重试都被自己挡住 5 分钟）；「需要你」这类计数与呈现必须同源，凡是算进徽标却
在屏幕上看不见的，都是 bug（本期踩到三次：空列把卡挤出视野、项目级请示藏在筛选后、
等人原因在抽屉里不显示）。
