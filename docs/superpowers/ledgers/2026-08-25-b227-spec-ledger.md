## 2. hooks 逃逸链：本机实测（含对照组）

**目的**：验证「A′ 开放 .git 可写域后，codex 可经 .git/hooks 提权到宿主」是否成立，
以及 `-c core.hooksPath=<空目录>` 能否堵住。

**靶子**：`/tmp/b227chk` 一次性 git 仓库（git 2.50.1 Apple Git-155, macOS）。
在主仓 `.git/hooks/post-checkout` 放一个把 pid/cwd 写进证据文件的脚本。

```
实验 a  git -C repo worktree add -q $D/wt1 -b probe1
        → HOOK_RAN pid=57798 cwd=/private/tmp/b227chk/wt1

实验 b  git -C repo -c core.hooksPath=$D/nohooks worktree add -q $D/wt2 -b probe2
        → (hook 未运行)

实验 c  先 git -C repo config core.hooksPath "$D/repo/.git/hooks"（模拟 codex 篡改 config）
        再 git -C repo -c core.hooksPath=$D/nohooks worktree add -q $D/wt3 -b probe3
        → (hook 未运行)  命令行 -c 压过 .git/config

对照组  git -C repo worktree add -q $D/wt4 -b probe4   （不加 -c，config 仍指向 hooks）
        → HOOK_RAN pid=57817 cwd=/private/tmp/b227chk/wt4
```

**对照组是本实验的判别力来源**：它排除了「hook 本来就不跑」的假绿。四项全部符合预期。

**结论**：
1. `git worktree add` 触发共享 `.git/hooks/post-checkout`。该命令由 agentd 自己执行
   （`internal/agentd/workspace.go` 第 3 层的 `gitRun`），**跑在 agentd 进程里、不在任何沙箱内**。
2. 逃逸链成立：沙箱内 codex 写 `.git/hooks/post-checkout` → 下次任何人对同仓派发
   `--new-worktree` → agentd 以自身身份无沙箱执行该脚本。
3. `-c core.hooksPath=<空目录>` 有效，且**压得过被篡改的 `.git/config`**。
4. 该链**今天已经存在**：原地模式下 cwd 即仓库根，`.git/hooks` 本就在可写域内。
   本卡只是把 worktree 模式拉平过去，因此加固独立于本卡即应成立。

## 3. codex 二进制策略面：strings 取证

**靶子**：`/opt/homebrew/lib/node_modules/@openai/codex/node_modules/@openai/codex-darwin-arm64/vendor/aarch64-apple-darwin/bin/codex`，`codex-cli 0.147.0`。

**读数（逐字摘录）**：

```
use_default | with_additional_permissions | require_escalated

"Per-command sandbox override. Defaults to `use_default`;
 use `require_escalated` for unsandboxed execution."

"Sandboxed filesystem or network access for this command;
 only with `sandbox_permissions: \"with_additional_permissions\"`."

"additional permissions are disabled; enable `features.exec_permission_approvals`
 before using `with_additional_permissions`"

`permissions` cannot be combined with `sandboxPolicy`
`permissionProfile` cannot be combined with `sandboxPolicy`
`permissions.filesystem` is reserved for requirements-level filesystem constraints
 and cannot define a profile
```

**三条结论**：

1. **`require_escalated` = 整条命令完全脱离沙箱**，不是「把某路径加进可写域」。
   因此「permgate 白名单放行 git 写」（C / B249 第 2 条）放行的是**无沙箱执行**，
   其授权面**严格宽于** A′ 要开的 `.git` 可写。安全序是 **A′ > C**，与直觉相反。
2. **存在第三档 `with_additional_permissions`**：沙箱内追加权限、不脱沙箱，
   但需 `features.exec_permission_approvals`。今天 handoff 未使用该档。
3. **`permissions` 面与 `sandboxPolicy` 互斥**，且 `permissions.filesystem` 另有约束
   （不能在此定义 profile）。方案 D 的落地成本因此高于「换个字段名」。

**未查证**：执行机 linux-01 上的 codex 版本（本轮未上执行机）。方案 D 的可行性完全压在这条上，
故 D 只作 roadmap 条目、不进本期。

- **窄 allowlist 实测判死**：只开 `objects`+`refs`+`logs`+`worktrees` 四棵子树时，

  `git add`+`commit` / `stash` / `checkout -b` rc=0 但 stderr 带
  `packed-refs.lock: Operation not permitted` 等拒绝噪声。

  `index`/`HEAD`/`FETCH_HEAD`/`logs/HEAD` 在 `.git/worktrees/<id>/`（每树私有）；
  `objects`/`refs/heads/*`/`logs/refs/*`/`packed-refs`/`config` 在 `.git/`（common，共享）。
  → 只开 `.git/worktrees/<id8>/` 必然不够，`git add` 就要写 objects。
- **B（clone --shared）的依赖点清单**：`cmd/pull.go:70` 与 `internal/agentd/bundle.go:32`
