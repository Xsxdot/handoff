## ⑭ 的四个子项

集成线 `acc/integration-B156.1`（验收用临时分支，验完删）刻意加一条分叉提交，
与 main 分开：集成线 `26ccf234`、main `1e5cd040`。

1. **工作分支各落各的基线**：epic 子卡 B9009.2 的工作分支 base_commit = `26ccf234`
   （集成线 tip）；顶层热修卡 B9010 的 base_commit = `7dec3118`（该机 main ref）。
2. **子卡自动合回集成线**：`card dispatch B9009.2 --node merge --repo .` →
   客观判据（临时 worktree 里跑 `gofmt -l` + `go test ./...`）通过 → `--no-ff`
   合入 `acc/integration-B156.1` 并 push，返回 `{"Action":"merged"}`。
   **前提**：工作分支必须先在 origin 上（见下方观察三）。
3. **热修卡不自动合、进「待合并」**：`card dispatch B9010 --node merge` 输出
   `needs_human / 基线是主线：合并永远人工`，卡状态 = 待合并。
4. **跨基线 merge 被拒且点名两侧**：`card merge B9010 --into B9009` →
   `卡 B9010 基线 "main" ≠ 承载卡基线 "acc/integration-B156.1"`。

## 这轮真机验收挖出的缺陷（单测结构上挡不住的）

1. 审阅节点等的是 `WaitEvent`（首个可动作事件）而非回合终态，审阅过权限门就醒，
   随即报「事件流中没有 completed/failed」——审阅回路从未跑通过。已修（`waitForTurnEnd`）。
2. 回合铁律只给「提问」与「commit 后收尾」两个出口，只读审阅被禁止提交，
   于是三个执行器都把裁决塞进提问工单。协议本就认只带 summary 的收尾行，
   纪律块与契约已写明。
3. 合并节点的「主线永远人工」只判空基线，`card add --base-branch main` 建的卡
   会被当集成线**自动合进 main**，绕开主线人工门。已修（`isMainline`）。
4. 派发失败回滚只退状态、不退驱动租约，卡停在「待办但有主」；驱动身份带 pid，
   本人换个进程重试也被自己挡住 5 分钟。已修（`ReleaseCard`）。
5. 取最终报文串到收尾断连文案（codex 与 grok 都在 `completed` 后补 `turn_failed`）。已修。
6. 审阅轮复用工作分支名导致 `branch already exists` / `already used by worktree`。已修（每轮抛弃式审阅分支）。
7. 裁决解析失败时节点抛错、卡上什么也不留。已修（落原文 + 转「需要你」）。

## 观察（未改，留给判断）

- **派发解析基线时不 fetch**：linux-01 的仓库镜像停在旧 main（7dec3118）时，
  `--base-branch main` 的卡就基于旧 main 起分支，且新推的分支报「起点不存在」。
  手工在该机 `git fetch origin` 后恢复。是否该在派发前对账基线，留给决策。
- **合并节点只认 origin 上的工作分支**：客观判据与合并都跑 `git fetch origin <分支>`，
  而纪律块禁止执行者 push，`handoff pull` 只把分支拉到协调者本地——流程里没有任何
  一步把工作分支推到 origin，于是合并节点必然报「couldn't find remote ref」。
  本次靠审核者手工 `git push origin <分支>` 绕过。要么让协调者流程显式包含这一步，
  要么让节点在 origin 缺失时回落本地分支。**未决**。
- **合并节点会把协调者工作区留在基线分支上**：它 `git checkout <base>` 后不切回，
  本次实测跑完后 HEAD 停在 `acc/integration-B156.1`（手工切回）。工作区有未提交
  改动时这一步还会直接失败。
- **`deny` 的理由送不到执行器**：拒绝越界读取后事件流落 `deny_guidance_dropped`，
  执行者拿不到方向，只能靠 `continue` 补。与既有 memory 一致。
